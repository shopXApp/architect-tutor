SECTION 01 — THE REAL PROBLEM

When Application Servers Scale but the Database Does Not

The most common mistake in growing systems: add more API servers and assume everything gets faster. The database is a single writer — and that writer has a hard ceiling.

Picture the classic three-tier flow:

USERS100 → 1,000 → 10,000 → 100,000 RPS
LOAD BALANCERSpreads across APIs
API SERVERSScale horizontally easily

But then every API server writes and reads from one database:

FIG. 13.1 — WHY ADDING SERVERS IS NOT ENOUGH

At 100 RPS the database barely notices. At 1,000 it starts working. At 10,000 the connection pool fills, query time climbs, and errors begin. At 100,000 it is not a slow database — it is a broken system, even though all ten API server instances are healthy.

WHAT AN ARCHITECT SAYS FIRST

Before recommending any database change, ask: "Is the database actually the bottleneck?" Check CPU, connection usage, top queries, replication lag, and whether the slowdown correlates with traffic, not a deploy. Many "database problems" are actually bad queries or missing indexes — fixes that cost hours instead of months.

SECTION 02 — THE TWO DIRECTIONS

Vertical vs Horizontal Scaling

Every database can grow in two directions. Know both before you pick.

Vertical ScalingMake one server stronger. Bigger CPU, more RAM, faster SSD. Simple, fast, requires no application changes. Limit: physical ceiling of one machine — and a single point of failure. When: early growth, simple apps, when you need results this week.
Horizontal ScalingUse multiple servers. Replicas for reads, sharding for writes. More complex, requires data design, but no hard ceiling. Limit: distributed data, consistency questions, rebalancing. When: large scale, high availability, multi-region — and when vertical is maxed.
Vertical is often firstMost systems do not need sharding on day one. Upgrade the instance, add indexes, separate reads — then measure if that was enough. Don't build a billion-user architecture for a 10,000-user problem.
Horizontal is the long gameRead replicas, partitioning, then sharding — each adds a layer of design. The architect's job is to delay sharding as long as simpler options carry the load, and to know the trigger that forces the next step.
THE ARCHITECT'S DECISION RULE

Scale vertically until you hit a real constraint — CPU ceiling, memory ceiling, disk I/O, or connection limit. Only then consider horizontal. The best design is the smallest one that survives the real constraints.

SECTION 03 — READS CAN BE SEPARATED

Read Scaling with Replicas

Many systems are read-heavy — product catalogs, reports, search results. The primary handles all writes, but most traffic is just reading. Read replicas let reads move to other servers.

FIG. 13.2 — READ SCALING: WRITE TO PRIMARY, READ FROM REPLICAS

How it works

  • Writes go to the primary. It is the only writer — no conflicts.
  • Reads go to replicas. Each replica is a full or partial copy of the data.
  • Replication copies changes from primary to replicas — usually near-real-time, but never instant.
  • Stale data is acceptable for product catalogs, recommendations, search. Not acceptable for bank balances or order confirmations.
PRODUCT CATALOG EXAMPLE

A customer searches products — that is a read. It can come from a replica, even if the catalog just changed 200 ms ago. But when they click "Order" — that must read from the primary (or a strongly consistent source) to see current stock and pricing.

SECTION 04 — DATA MOVES IN ORDER

Replication: Why, How, and the Delay

Replication is not backup — it is making more copies of the same data, continuously.

Why use itRead scaling across replicas · high availability (failover to replica) · backup source (replica can be frozen for backup without affecting primary).
How it worksPrimary writes to a transaction log · replicas read that log and apply changes. Usually asynchronous — replicas can lag.
Replication delayUsually seconds, sometimes minutes under heavy load. Reads from replicas see slightly older data. Design for it: never read balance checks or critical confirmations from a replica.
FailoverIf the primary dies, a replica can be promoted to become the new primary. Need automation and testing — untested failover is a guess.
REPLICATION IS NOT BACKUP

A replica has the same failure modes as the primary — human error (DROP TABLE), corruption, malware, bad deploys all replicate. Backup is a separate, frozen, tested, off-system copy. Both are required.

SECTION 05 — SPLITTING THE TABLE

Partitioning: One Table, Many Pieces

Instead of one giant Orders table with 1 billion rows, split the data so each piece is smaller and faster to query — still in the same database server.

FIG. 13.3 — PARTITIONING BY DATE: SMALLER PIECES, SAME DB

How to partition

  • By date (range partitioning) — older data is rarely queried; archive or delete. Best for time-series data.
  • By tenant (list partitioning) — separates each company's data within the same table. Good for isolation, but cross-tenant queries become hard.
  • By region (hash or range) — keeps data close to users. Complex to manage if regions change.
WHY, BENEFIT, RISK

Why: faster queries, smaller indexes, easier archiving, faster backups.
Risk: cross-partition queries slow; some queries must touch every partition; partition management (adding, removing) requires design.

SECTION 06 — SPLITTING ACROSS SERVERS

Sharding: Different Tables on Different Machines

Sharding goes further: data lives in different database instances, not just different pieces of the same table. Each shard is an independent database.

FIG. 13.4 — SHARDING BY TENANT: DATA ACROSS INDEPENDENT SERVERS

Key concepts

  • How data is distributed — usually by a shard key (TenantId, CustomerId, region). A hash function decides which shard holds which data.
  • How requests find the shard — the application or a routing layer uses the shard key to direct the query.
  • One shard overloaded — a hot tenant or region can overload one shard while others idle. Needs rebalancing or a better shard key.
  • Rebalancing is hard — moving data between live shards requires downtime or complex migration.
  • Cross-shard queries — asking for all orders across all shards requires querying every shard and combining results — slow.
  • Cross-shard transactions — a transaction that updates two shards needs distributed transactions (complex, often avoided).
SHARDING IS LAST

Sharding should be considered after vertical scaling, read replicas, indexing, caching, and partitioning. The reason: sharding introduces distributed systems problems (rebalancing, cross-shard queries, failure domains) that simpler designs avoid.

SECTION 07 — SIDE BY SIDE

Partitioning vs Sharding

DIMENSION PARTITIONING SHARDING
Data location Same database server — pieces of one table Different database instances
Main purpose Make large tables faster to query / archive / manage Distribute write load and data volume across machines
Complexity Medium — partition definitions, query planning High — routing, rebalancing, cross-shard queries, transactions
Scaling benefit Query speed, archive, maintenance — not raw write scale True write-scale — more servers = more capacity
Cross-data queries Possible — database handles combining partitions Hard — must query each shard and combine
Typical use Time-series, large tables with range access, archiving Very large write-heavy systems, multi-tenant isolation at scale

Five scenarios — which fits?

SCENARIO ANSWER WHY
Product catalog, mostly reads, 10M products Partitioning Large table, read-heavy, range queries by category — no need to split servers.
Orders table, 1B rows, mostly recent orders queried Partitioning by date Archive old years; query recent partitions only.
10,000 tenants, each with high isolated traffic Sharding by tenant or shared DB with schema separation Isolation + scale; sharding when shared DB can no longer carry writes.
Social feed, massive writes, every user writes Sharding by user Write load is the bottleneck — need more writers.
Reporting queries that scan all data Neither alone — read replicas + separate reporting DB Cross-partition/shard scans are slow; separate read-focused store is simpler.
SECTION 08 — FAST READS

Indexing: The Architect's Most Costly Decision

Indexes speed up reads — but every index is a write cost at insert/update time and storage cost at rest. The architect chooses which reads are worth the price.

The example

SELECT orders WHERE CustomerId = 48291; -- WITHOUT INDEX: scan every row (millions)

Without an index: the database scans the entire table — O(n), slow, and growing slower as data grows.
With an index on CustomerId: the database finds the entries directly — O(log n), fast, and growing slowly.

Index types (conceptual)

Primary indexOn the primary key — automatic, required, the table is ordered by it.
Composite indexOn multiple columns together — (CustomerId, OrderDate) answers both filters at once.
Covering index (conceptual)The index includes all columns the query needs — no table lookup required.

The trade-off

Indexes make reads faster but slow writes (every insert/update must update every index) and increase storage. Too many indexes: writes become sluggish, storage grows, and the query optimizer may choose poorly. The architect asks: which queries are frequent and slow? Index those. Everything else is noise.

THE ONLY QUESTION THAT MATTERS

Before adding any index: "What query does this speed up, how often, and is that query on the critical path?" If the answer is "maybe someday," do not build it.

SECTION 09 — WHEN THE API IS SLOW

Query Performance: The Investigation Flow

When an API slows, do not guess. Walk the chain — each step reveals whether the problem is in the query, the data, the locks, or the connections.

  • API → QueryWhich endpoint? What does the SQL look like? Is it the same query or a new one after a deploy?ASK: "WHAT QUERY IS RUNNING?"
  • Query → Execution PlanDoes the database use an index? Scan a table? Join the wrong way? The execution plan tells you everything.ASK: "IS IT USING THE INDEX?"
  • Execution Plan → IndexDoes the index exist? Is it the right columns? Has it become fragmented or stale?ASK: "IS THE INDEX RIGHT?"
  • Index → Data VolumeHow many rows? Has the table grown past a threshold where the plan changes? Has data become unbalanced?ASK: "HOW BIG IS THE DATA?"
  • Data → Locks / ConnectionsAre other queries holding locks on the rows this needs? Is the connection pool full? Is another process running a long transaction?ASK: "WHO IS BLOCKING IT?"
  • Locks / Connections → RemediationFix the query or the index, kill the blocking query if safe, scale connections or reduce transaction duration.ASK: "WHAT CAN WE CHANGE FIRST?"
    • ARCHITECT INSIGHT

    The fastest fix is usually the index; the best fix is the query redesign — but the first fix you must defend is what the data says. Do not change code until the execution plan tells you the truth.

    SECTION 10 — REUSE, DON'T RECREATE

    Connection Pooling

    Opening a new database connection for every request is like opening a new office for every customer — possible, but wasteful.

    How it worksA pool keeps connections open and reuses them. The application borrows a connection, uses it, and returns it. No new TCP handshake, no new authentication, no new memory allocation.
    Pool too smallRequests queue, timeouts climb, and the system appears slow when the database is idle. Add connections to the pool — or check why they are not being returned.
    Pool too largeToo many connections overwhelm the database — every connection uses memory and a thread. More is not better; match the pool to the database's capacity.
    Database overloadedEven with the right pool, a slow database makes every request slow. Pooling solves overhead, not query performance.
    DESIGN DECISION

    For ASP.NET Core with SQL Server / PostgreSQL: use the framework's built-in pooling (connection strings with pool settings), size the pool to roughly 1.2–1.5× the database connection capacity per application instance, and always release connections promptly (using statements / using blocks).

    SECTION 11 — SHORT IS HEALTHY

    Transactions at Scale

    A transaction locks what it touches — and keeps those locks for its entire duration. Large transactions are the hidden cause of many database slowdowns.

    FIG. 13.5 — LARGE TRANSACTION: LOCKS EVERY RESOURCE FOR THE FULL DURATION

    Why large transactions hurt

    • Duration — the longer the transaction, the longer locks are held.
    • Locking — other queries that touch the same rows wait.
    • Contention — under load, everyone waits — throughput collapses.
    • Deadlocks — two transactions each hold a lock the other needs — both freeze until one is killed.
    THE ARCHITECT'S RULE

    Keep transactions as small as practical. Call the payment gateway before or after the transaction — not inside. Write the order, commit quickly, then do the external work. If you must include external work, use outbox / saga patterns (see messaging days) — not a database transaction spanning the web.

    SECTION 12 — THE CHOICE IS NOT POPULARITY

    SQL vs NoSQL for Scale

    The database is not chosen by fashion. It is chosen by access patterns, relationships, consistency needs, and scale direction.

    DIMENSION SQL (SQL Server / PostgreSQL) NoSQL (Mongo / Cosmos / DynamoDB)
    Relationships Native — joins, foreign keys, nested queries Limited — embedded docs for simple nesting, application-level joins for complex
    Transactions ACID — multi-table, multi-row Single-document / single-item; multi-document possible but complex
    Scale (writes) Vertical then replica reads; sharding is hard Built for horizontal scale — easy to add nodes/partitions
    Query patterns Flexible — ad-hoc queries, aggregates, reports Design for the query — access patterns must be planned ahead
    Schema Fixed / structured — migrations needed Flexible — documents can vary; schema is in code
    Global distribution Possible but complex (multi-region replicas) Built-in for many (Cosmos global, DynamoDB global tables)
    THE DECISION FRAME

    Need strong consistency across related records, complex queries, reports, and ACID transactions? SQL. Need massive write scale, flexible document shapes, and planned query patterns? NoSQL. Many systems use both — SQL for orders/payments, NoSQL (Mongo / Cosmos) for catalogs, user preferences, or session data.

    SECTION 13 — SHARED VS ISOLATED

    Multi-Tenant Database Strategies

    Ten thousand companies share the same platform. How does their data sit in the database?

    Option 1 — Shared DB, Shared TablesCost: low. Isolation: weak. Complexity: lowest. Every tenant's data in the same table with a tenant ID column. Best for: early stage, low data volume, where isolation is not critical.
    Option 2 — Shared DB, Separate SchemaCost: medium. Isolation: medium. Complexity: medium. Each tenant has their own schema (tables) inside the same database server. Easier to separate data, but still shares server resources.
    Option 3 — Separate DB Per TenantCost: high. Isolation: strong. Complexity: high. Each tenant gets their own database instance. Best for: high-value, compliance-heavy, or noisy-tenant-sensitive customers.
    Option 4 — HybridCost: medium-high. Isolation: flexible. Complexity: high. Most tenants in shared DB; high-value or noisy tenants moved to separate DBs. Best for: large SaaS at scale where all options must coexist.
    RECOMMENDATION FOR 10,000 COMPANIES

    Start Option 1 (shared DB, shared tables) with a TenantId on every table and strict tenant filtering in every query — this is the cheapest, fastest, and most scalable start. Move to Option 2 (separate schema) when isolation demands grow, and to Option 3 (separate DB) only for specific high-value tenants — never for all 10,000. The hybrid (Option 4) is the long-term goal.

    SECTION 15 — BEING READY TO LOSE DATA

    Backup, Recovery, RPO and RTO

    Every system loses data eventually. The architect defines how much and how long before the business notices.

    BackupA copy of data — full (everything) or incremental (changes since last full). Must be tested: an untested backup is a hope.
    RestorePutting data back from backup. The time to restore is part of the RTO — test it regularly.
    Point-in-time recoveryRestoring to a specific moment (e.g., "before the bad deploy at 14:03"). Requires continuous transaction-log backups.
    RPO — Recovery Point ObjectiveHow much data can we afford to lose? 1 hour = at most 1 hour of data lost. 5 minutes = near-zero loss.
    RTO — Recovery Time ObjectiveHow long can we afford to be down? 4 hours = system back online within half a workday. 15 minutes = near-instant failover.
    3 SCENARIOS

    Internal tool — RPO = 1 day (data rebuilt from source), RTO = 8 hours (business can wait). SaaS platform — RPO = 15 min, RTO = 30 min (money and customers at risk). Financial / health — RPO near zero, RTO near zero — requires multi-region, continuous replication, automated failover.

    Stage 1 (small): one PostgreSQL instance, simple schema, basic indexes.
    Stage 2 (growing): add read replicas, index strategically, partition old orders.

    SECTION 17 — THREE STAGES

    Architecture Evolution

    The lesson: don't build a billion-user architecture for a 10,000-user problem. The database design grows with the problem — not ahead of it.

    FIG. 13.6 — EVOLVE WITH THE PROBLEM, NOT AHEAD OF IT
    WHAT LIMITS EACH STAGE

    Stage 1: single server CPU, memory, disk I/O, connections — vertical ceiling.
    Stage 2: write rate to the primary; replication lag; index maintenance speed — horizontal reads help, writes still limited.
    Stage 3: only sharding (and sometimes multi-region) removes the single-writer ceiling — but at high design and operational cost.

    SECTION 18 — BEFORE YOU CHANGE ANYTHING

    10 Questions an Architect Must Ask

    QUESTION WHY IT MATTERS POSSIBLE DECISION TRADE-OFF
    Is the DB actually the bottleneck? Many slow APIs are bad queries or missing indexes — not server capacity. Fix query/index first, then scale Hours vs months of change
    Is the problem reads or writes? Reads scale with replicas; writes need different answers. Read replicas vs sharding vs vertical Cost and consistency differences
    Can indexing solve it? Often yes — the cheapest fix. Add composite / covering index Slightly slower writes, more storage
    Can caching solve it? If reads are repeated, cache removes them from the DB. Redis / CDN / application cache Stale data; cache failure planning

    What happens during failover? Un-tested failover is never safe. Auto-failover, tested drills, runbooks Complexity; potential data loss window
    What is the recovery requirement? Defines backup frequency, retention, RPO/RTO targets. Point-in-time, multi-region, automated restore Cost vs speed vs completeness
    SECTION 19 — THE GRAVEYARD

    10 Mistakes That Break Database Designs

    1 · Sharding too earlyBuilds distributed complexity before it's needed. Start simple; sharding is the last option.
    2 · No indexing strategyQueries scan full tables; performance collapses as data grows.
    3 · Too many indexesEvery write updates every index; writes become slow; storage explodes.
    4 · Scaling apps while DB bottlenecksMore APIs = more load on one database = worse performance.
    5 · No read/write separationReads compete with writes; reports slow the production primary.
    6 · Ignoring replication delayReading stale balance data after a payment = serious errors.
    7 · Poor tenant distributionOne noisy tenant on a shared DB slows everyone; no isolation.
    8 · Large transactionsLocks held for seconds; deadlocks; throughput collapses under load.
    9 · No backup testingAn untested backup is a wish — restore fails when it matters most.
    10 · No disaster recovery planNo multi-region, no tested failover, no RPO/RTO targets — failure is a guess.

    Troubleshooting Exercise

    Start with the incident. Then new information arrives — gradually. At each step, make the call.

    START — THE INCIDENT

    1. 09:42Order API response time 300 ms → 8 s. DB CPU 95%.
    WHAT DO YOU CHECK FIRST? METRICS → QUERY → INDEX → DATA → LOCKS

    CLUE 1 — MISSING INDEX

    1. 09:45The query on orders has no index on CustomerId — full table scan.
    FIRST FIX: ADD INDEX — FASTEST PATH
    CLUE 2 — READ TRAFFIC 80%

    Most traffic is reading, not writing. Read replicas can take load off the primary — but only after the index is fixed.

    CLUE 3 — ONE TENANT 40%

    ACME is consuming 40% of traffic. Per-tenant metrics expose this; throttle or separate resources for this tenant.

    CLUE 4 — REPORTING ON PRIMARY

    Heavy reports run on the production database. Move them to a read replica or separate analytics DB — immediately.

    CLUE 5 — CONNECTION LIMIT REACHED

    The database is at max connections. Scale connections, reduce pool per instance, kill long queries — but the root is the load from clues 1–4.

    YOUR DECISION

    Fix order: Index (immediate) → Reports moved off primary → Read replicas for reads → Tenant throttle → Connection scale. Each fix removes load; each reveals whether the next was needed.

    DAY 13 — CLOSE

    The Architects of Data

    Five rules from today. If you remember nothing else, these carry you through any database conversation.

    01

    Scale vertically first.

    The simplest fix is often the right fix. Add resources, fix indexes, separate reads — then measure whether the problem is solved. Don't build distributed complexity for a single-server problem.

    02

    Reads can leave; writes are hard.

    Read replicas are easy to add. Writing at scale requires different answers — and those answers cost more. Always separate the two in your design thinking.

    03

    Shard only after everything else.

    Partitioning handles large tables. Replicas handle reads. Vertical handles growth. Only when all three are maxed — and writes still bottleneck — does sharding become justified.

    04

    An index is a choice, not a default.

    Every index costs writes and storage. Index only the queries that matter — and defend each with a clear reason.

    05

    Backup is a process, not a file.

    A backup that was never tested is a wish. Test restore monthly, define RPO/RTO with the business, and treat disaster recovery as architecture — not a manual.

    A database architecture is not a diagram — it is a series of decisions made at different scales, each defending the last, each paused until the problem demands the next. Design for the problem you have, not the one you imagine.
