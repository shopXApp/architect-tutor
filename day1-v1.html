SECTION 01 — FOUNDATION

What is Software Architecture?

Simple words first: architecture is the set of decisions that are expensive to change later.

A developer makes decisions that are easy to undo — a variable name, a helper method, a split class. An architect makes decisions that are hard to undo: how the data is owned, where the boundaries are, what talks to what, and what happens when a part fails.

Every project contains both kinds of decisions. The difference is not skill. The difference is which decisions you treat as decisions — and which you leave to instinct.

PLAIN ENGLISH — THE HOUSE

Painting a wall is a developer decision — cheap to redo. Moving a load-bearing wall is an architecture decision — expensive, and it must be planned before the roof goes on. Most architecture pain is load-bearing walls moved after the roof is up.

Same problem, three lenses

The project: an online shop. Someone says — "the checkout is slow." Watch three roles hear the same sentence and think different thoughts.

  DEVELOPER TECHNICAL LEAD ARCHITECT
First thought "Which part of the code is slow?" "Which request is slow, for how many users, and since when?" "What should 'fast' be — and does this design even allow it?"
What they do Profile the code, add an index, optimize the query, ship the fix. Set up monitoring, fix the top 3 hotspots, plan tests and rollback, split the work across the team. Question the requirement (fast for which action?), find the structural cause (synchronous chain? DB bottleneck? no cache?), pick a shape change — and decide what not to change.
Time horizon This bug, this sprint. The team's delivery, the next quarter. The next 3 years: cost, change, failure, risk.
  DEVELOPER TECHNICAL LEAD ARCHITECT
"Add a discount rule to checkout." Which endpoint, which model, which screen. Which team owns it, how we test it, when we ship it. Discount rules change weekly. Where does this logic live so a new rule touches one place? Can it be configured without a deploy? What breaks if two rules conflict?
ONE-LINE VERSION — MEMORIZE THIS

Developer: "How do I build this?" · Technical Lead: "How do we ship this well?" · Architect: "What should we build — and what will we regret in two years?"

Notice: the architect is not coding faster. The architect is deciding what is worth deciding. That is the skill the next 30 days are about.

INTERVIEW ANGLE

The moment you start asking before answering — "how many users? what counts as fast? what breaks if this fails?" — you are signalling architect thinking. In that room, the question is worth more than the answer.

From today on, every system you look at gets filtered through five lenses. Here they are.

SECTION 02 — THE FIVE LENSES

The 5 Things Every Architect Must Think About

Reliability, Performance, Scalability, Security, Maintainability. Learn them as questions, not definitions. Each one has the same shape: what it is, why it matters, what problem it solves, what happens when you ignore it, and two examples you should be able to tell in one breath.

01

Reliability

Does it keep working when things break?
What is it?
Reliability is the promise that the system keeps delivering when parts of it fail — because parts will fail. A server. A disk. A network cable. A bug in your code. A third-party API. Reliability is not "it works when the demo works." It is "it still works on the worst day."
Why it matters
Users do not forgive twice. In banking, a 10-minute outage is money lost, customers furious, and regulators watching. In food delivery, one evening of downtime is dinner that never arrives.
Problem it solves
The domino problem. Without reliability thinking, one small failure — one dead service, one full disk — travels through the system and takes down everything. Reliability design stops the dominoes.
Four things you design
FailuresAssume every part fails: your code (bugs), your servers, your network, your database, and every API you call. For each one, ask: when it fails, what does the user actually see? An error? A degraded feature? Nothing?
BackupA copy of your data that you can bring back. Servers hold state, but the data lives in the database. No backup plan means one corrupted table can delete months of orders, forever.
RecoveryTwo honest questions: how much data can we lose (minutes of orders — or zero?) and how fast must we be back (5 minutes or 5 hours?). Your answers are the architecture — they decide replicas, queues and failover.
Dependency failurePayment gateways, email providers, map services — they go down without notice. Design for it: timeouts (never wait forever), retries with delay, a fallback (offer another payment option), and a queue so work is not lost when the provider comes back.
If you ignore it
One bad deploy — or one dead vendor — and the whole site is down. Worse: users learn that your system is "the one that is always down." That reputation is almost impossible to remove.
Real-world example
A hospital runs its critical rooms on backup generators. The power can fail; the patients do not feel it. The generator is boring until the single day it saves the hospital. That is exactly what redundancy is — boring by design.
Software example
A food delivery app: the ratings service is down. Drivers still deliver, orders still move. Only the star ratings are hidden for a while. The outage is small and quiet — because someone designed for it to be.
What an architect asks
  1. Which parts can fail — one by one?
  2. If each one fails, what does the user actually see?
  3. Which features must keep working at all costs, and which may go down?
  4. How much data can we lose, and how fast must we recover?
  5. Where are the single points of failure — and can I remove them?
INTERVIEW ANGLE

Reliability is not one number for the whole system. It is a number per feature: payments 99.95%, the marketing page 99%. Saying that out loud in an interview shows real experience.

02

Performance

How fast should it respond — and who decides?
What is it?
Performance is how quickly the system responds and how much load it can absorb. The trap: treating "fast" as a goal. It is not. It is a requirement — and requirements have numbers. "The product page loads in under 1 second for 95% of users" — that sentence changes the design. "It should be fast" changes nothing.
Why it matters
Users leave a web page that takes more than 2–3 seconds. In e-commerce, every extra second of page load measurably cuts conversions. Slow does not feel like "slow." It feels like "I'll try again later" — and later never comes.
Problem it solves
Most web apps die the same death: one slow database query on a hot path, or one long chain of synchronous calls. Performance design finds the bottleneck before launch, not at 2 a.m. during the outage.
Four things you design
Response timeSet a target per action, not per system. Checkout under 1s, search under 500ms, report generation under 30s. And decide what you measure: 95% of requests (p95), not the average — the average hides the users who suffer.
Slow databaseThe most common bottleneck in your world: N+1 queries, missing indexes, heavy joins on hot paths. The DB is also the most expensive part to fix at runtime — so it gets decided at design time: what is cached, what is denormalized, what is pre-computed.
Slow APIA checkout that waits on five services one after another takes the sum of all five. The fixes: call them in parallel where it is safe, cache what is stable, and never wait on a slow side-task in the request path.
Too many requestsA flash sale sends 50× the normal traffic. Design for it: rate limits to protect the core, a queue to absorb the spike, and a plan for what to switch off first (recommendations go, checkout stays).
If you ignore it
Launch day brings 3× the expected traffic. The site "works" for ten minutes, then every request waits 20 seconds, then it is down. You spent the whole weekend fixing a design you skipped on the whiteboard.
Real-world example
A coffee shop with one barista: ten customers are fine, fifty is a queue, one hundred is a riot. Performance is the barista's speed. Scaling is more baristas. The owner must know which problem he actually has before he spends money on the wrong fix.
Software example
An e-commerce product page: target under 1 second. Product data is cached (it changes rarely). Recommendations may be an hour old — nobody checks. But order creation is exact: no stale stock, no double charge. Different rules for different actions.
What an architect asks
  1. Which actions must be fast, and how fast exactly?
  2. For what share of users — the average, or the slowest 5%?
  3. Where is the real bottleneck — and have we measured it?
  4. Which reads can be cached or delayed without anyone noticing?
  5. Which operations must stay exact and synchronous?
INTERVIEW ANGLE

Asked "how would you make it faster?", a senior first answers: "which action, for which percentile?" That one question tells the interviewer you have measured real systems before.

03

Scalability

What happens when the users increase?
What is it?
Scalability is the ability to handle more load without a rebuild. Two levers: scale up (one bigger machine) and scale out (many small machines). Scale up is easy until it is not. Scale out is the shape of every system that keeps growing.
Why it matters
Growth surprises you. A product that works at 1,000 users can die at 10,000 — not because of a bug, but because the shape was drawn for 1,000. Scalability thinking means deciding where you can add machines instead of redrawing the system.
Problem it solves
The bottleneck moves as you grow: first the app server, then the database, then disk, then the network. Scalability is knowing where each one is sitting so you can act before the outage, not during it.
The 100 → 10,000 → 1,000,000 ladder
Press the buttons. Watch the shape change — not the ambition, the shape.
The shape at each rung

100 users — keep it simple

One box, one database, and you sleep well. The monolith takes a direct call to the DB. Every request is synchronous, and that is fine. The correct architecture at 100 users is simple — anything more is waste.

  • App: one server. State may even live in memory — nobody notices.
  • Data: one database, nightly backup, one restore drill a year.
  • Monitoring: a log file and a prayer. A simple uptime alert is enough.
  • Cost: small. That is a feature, not a compromise.

10,000 users — the app server chokes first

Add a second app server behind a load balancer — but only if the app is stateless (no session in memory). Then the database starts to hurt: cache the hot reads, add a read replica. Move slow work (emails, reports) onto a queue so the web tier stops waiting.

  • App: two+ stateless servers, a load balancer in front.
  • Data: write to one DB, serve some reads from a replica.
  • Cache: introduced for the hottest reads.
  • Async: queue + worker for background jobs. The request path gets shorter.

1,000,000 users — every layer is a pool

Many app servers that the cloud adds and removes by itself. A cache cluster in front of the data. A queue bus that absorbs every spike. And the database splits: read/write separated, then sharded by a key like customer or tenant.

  • App: an autoscaling pool. Stateless, always. State lives in the DB and the cache.
  • Data: sharded or heavily split. Per-tenant or per-region isolation.
  • Async: all slow work on the queue. The request path is short by design.
  • Discipline: everything measured. You never scale blind again.
If you ignore it
Two faces of the same failure. Face one: the launch-day crash — built for 1,000 users, hit by 100,000. Face two, quieter and deadlier: built for 1,000,000 on day one. The bill is 10×, the complexity is 10×, and the business has 2,000 users. Both are architecture failures.
Real-world example
A parking lot. Ten spots for a new shop is correct. Ten thousand spots is bankruptcy. But the lot must be drawn so it can be extended. That is scalability: not the size today, but the room to grow tomorrow.
Software example
An employee-management SaaS with 50 companies: one instance, one DB. At 500 companies, reporting queries start slowing down the CRUD app — reporting moves to a replica. At 5,000 companies, tenants get split across shards. Three different architectures — for the same product.
What an architect asks
  1. How many users today, in 1 year, in 3 years — and what is the spike factor?
  2. Which parts can scale by adding machines — and can I make them stateless?
  3. Where does state live, and what happens to it on a new machine?
  4. What do we measure before we scale, so we scale the right thing?
KEY TAKEAWAY

Scale is not a feature you design for on day one. It is a sequence of small decisions you take as load arrives. The architect draws the 100 → 10,000 → 1,000,000 path — and keeps every step cheap.

04

Security

How do we protect users and business data?
What is it?
Security is control: who can do what, and how hard it is for someone to do what they should not. Two foundations — authentication (proving who you are) and authorization (deciding what that person may do). Almost every "security incident" you will hear about is one of these two, missing or misplaced.
Why it matters
A data breach is not an IT incident. It is fines, lawsuits, a news story, and lost customer trust that marketing can't buy back. And breaches are rarely fancy: they are an endpoint that forgot to check the role, or a password stored in plain text.
Problem it solves
Trust crosses boundaries. The user's browser is untrusted. The internal service is untrusted. The "temporary" copy of card data is untrusted. Security design draws those boundaries and makes crossing them expensive.
Five things you design
AuthenticationWho is this? Identity plus proof: strong passwords stored as salted hashes (never plain text), sessions or short-lived tokens, and MFA where the data is valuable. Decide the session length and what "logged out" really means.
AuthorizationWhat may they do? Roles and permissions, checked on the server, on every request, for every endpoint. Hiding a button in the UI is not authorization — it is decoration.
Sensitive dataFind the crown jewels: card numbers, national IDs, salaries. Rules: encrypt in transit and at rest; store the minimum — a shop never needs the full card number, the payment gateway holds it; and log without leaking — never log what you are protecting.
Access controlLeast privilege: every service, account and human gets only what their job needs. Admin APIs are not public. The email-sending worker cannot delete orders. Network boundaries keep the database off the public internet.
Common mistakesChecks only in the UI · secrets in code or config files · "temporary" copies of sensitive data that become permanent · no audit trail, so nobody can say who changed a salary · unlimited login attempts · trusting any input that came from the client.
If you ignore it
Day one: a user opens the API and reads every other user's data by changing one ID. Now there is a breach, a legal team, and a company that must explain itself to the press. "We'll secure it after launch" is the most expensive sentence in software.
Real-world example
A bank. You show ID to open the account — authentication. You can only withdraw from your own account — authorization. The cash sits in the vault — encryption. Every cash movement is recorded — audit. None of it is optional, and none of it is "after launch."
Software example
A multi-tenant SaaS: tenant A must never see tenant B's data — not by mistake, not by a guessed URL, not by a tired developer. Every query is scoped by tenant, and the rule is enforced in one place, so no future endpoint can forget it.
What an architect asks
  1. Where are the trust boundaries — and who may cross them?
  2. If the whole database was stolen tonight, what could the attacker read?
  3. Which actions are irreversible — and what proof do they require?
  4. Can we answer "who did this, and when?" for any change?
  5. What do we deliberately not store — and why?
INTERVIEW ANGLE

For any feature, draw the data flow out loud: browser → API → DB → vendor. Then say: "here is the boundary, here is what we check, and here is what we never store." That mini-talk is the security answer.

05

Maintainability

How easy is the system to change?
What is it?
Software must change. The business changes. The team changes. The law changes. Maintainability is the cost of that change: how long it takes, how risky it is, and how many people are brave enough to touch it. Architecture is mostly about keeping this number low.
Why it matters
In year one, everyone can read your code. In year three, the original author works at another company, the rules have doubled, and a one-hour fix takes a week because nobody knows where the logic lives. That gap is where projects die.
Problem it solves
Change spreads. Logic that lives in three places needs three edits and two bugs. A module that touches everything becomes the place where "one small change" takes the system down. Maintainability design keeps change local.
Four things you design
Clean structureA layout you can explain in one breath: who calls whom, where data enters, where it leaves. If a new engineer needs a week to find where orders are created, the structure has already failed.
Clear responsibilitiesOne job per part. A component that "handles orders, billing and notifications" is three jobs wearing one coat — change billing and you risk orders. Responsibility is the cheapest insurance in architecture.
Reducing tight couplingComponents that touch each other everywhere are one component with extra steps. Prefer clear contracts — an API, a message — so both sides can change their internals without breaking the other.
Technical debtShortcuts taken today, charged with interest every time you touch that code again. Some debt is fine — a prototype must be fast. The failure is not taking debt; it is taking it unknowingly and never repaying it. Name it, time-box it, schedule the payoff.
If you ignore it
Every release takes 3× longer. One person becomes the only one who can touch the core. Small changes cause outages. New hires are slow. And the business starts saying: "Why is this so hard? Maybe we should rebuild." Rebuilding is what unmaintainable systems pay at the end.
Real-world example
A restaurant kitchen. The grill station does only grill; desserts does only desserts. When the grill breaks, one line stops. Now imagine a kitchen where every chef does a little of everything: one person gets sick and dinner collapses. The kitchen layout is the architecture.
Software example
An employee-management system. A new payroll rule arrives (a tax change). If the rule lives in one module, it is a day of work with a clear test. If it is spread through 12 screens and reports, it is a month — and a bug in a report nobody opens.
What an architect asks
  1. Who will maintain this in 2 years — and how fast can they get up to speed?
  2. If we must replace the queue or the database, how many places break?
  3. Where are the contracts — and who owns them?
  4. Where is the duplicated logic, and who pays for it?
  5. What does the smallest change cost right now? If it is high, something is already wrong.
THE ARCHITECT'S REAL JOB

None of these five is optional, and none of them is free. A fast system that is unreliable is a liability. A secure one that nobody can change dies in three years. Architecture is not maxing out one pillar — it is choosing the balance the business can afford, and knowing which pillar you are deliberately sacrificing.

SECTION 03 — BEFORE ANY DIAGRAM

Questions I Should Ask Before Designing Any System

Twenty questions, in order. An architect who asks these in the first meeting will out-design a genius who starts drawing boxes. Read the "why it matters" — the question is only half the skill.

External customers, your own staff, or partners? Customers demand reliability and speed; staff will tolerate a slow page; partners demand a stable API. This answer sets the whole bar for quality — design for the wrong user and every other decision inherits the mistake.
If you build the wrong thing perfectly, you have failed. Ask: what does the business earn, save, or learn from this system? If nobody can answer in two sentences, stop and ask — the design target is wrong no matter how good the architecture is.
Size decides shape. 1,000 users and 1,000,000 users are different architectures (see the ladder in Section 2). Guessing wrong in either direction wastes money: under-sizing breaks you, over-sizing bankrupts you.
Average load sizes the system; peak load sizes the survival plan. Flash sales, salary day, a viral post — a 10× spike changes everything: queues, autoscaling, rate limits. Systems that die usually die at the peak, never at the average.
A system that is 95% reads is a caching problem. A system that is mostly writes is a database and queueing problem. Same word, "load" — opposite designs. This ratio is one of the cheapest and most powerful facts in the room.
99.9% is about 8.7 hours of downtime per year. 99.99% is about 53 minutes. The price difference between them is often 10×. The business must choose the number — not the engineer, not the interviewer's expectation.
The database is the heart. Ask: is data lost? How long until it is back? What does the app do in the meantime — fail fast, or serve read-only? The answers design your recovery plan: backups, replicas, failover, and the honest "we will lose N minutes of writes."
Payment, email, maps, SMS — none of it is under your control. Design the fallback for each: timeouts, retries with delay, a queue, and a degraded mode the user can live with. Every external dependency is a future outage you get to plan for now.
Card numbers, national IDs, salaries, health data. The list decides encryption, access rules, compliance (PCI-DSS, GDPR) and how hard a breach would hit you. Naming the crown jewels early makes "do we need PCI?" a 10-minute answer instead of a 3-month discovery.
Not everything. Name the hot actions and give them numbers. The rest is allowed to be 5× slower — and that is a design decision, not an accident. Trying to make everything fast is how budgets and designs both die.
Emails, reports, search indexes, analytics — all of it can wait from seconds to minutes. Moving it off the critical path is the cheapest performance win you will ever get, and the most common one architects miss.
A notification sent twice is annoying. A payment processed twice is a scandal. Decide per operation: at most once, at least once, or exactly once. That choice changes the whole write path — idempotency keys, deduplication, retries — so ask it before you draw the queue.
One team, one deployable. Five teams need clear boundaries or they will step on each other. The organization shapes the architecture as much as the load does — a famous truth, and the reason "microservices for 2 people" is a mistake.
If discount rules change weekly, that logic must live in one configurable place. If the workflow never changes, hard-code it confidently and stop worrying. Volatility decides where you invest in flexibility — and where you shouldn't.
An existing ERP, a payment vendor, a data warehouse. Every integration is a contract: who owns it, what breaks when it changes, and what happens when it is slow. Underestimated integrations are the number-one cause of "small" project overruns.
Cloud, on-prem, or hybrid. It decides how you scale (autoscaling or not), who patches things, how you fail over — and sometimes which technologies are even allowed in the building. A design drawn for the wrong room never fits.
The number that kills most architectures. 99.99% is expensive. Sharding is expensive. Redundant regions are expensive. A small budget is not a reason for a bad design — it is a constraint that makes the design honest. Name it in week one.
GDPR, PCI-DSS, data residency ("data must stay in this country"). These are not IT features you toggle on. They are architecture requirements with fines attached — and they change where data lives, not just how it is encrypted.
Everyone asks about the top; almost nobody asks about the bottom. At 1/10 load, is the system cheap to run — or are you paying for 10× you never use? Both ends are design answers, and the bottom one is usually where the waste hides.
Find the decisions that are hard to change later: data ownership, the boundaries between parts, the consistency rules, the tenant model. Those are the real architecture. Everything else is detail you can fix — so spend your thinking time where the regret would be deepest.
THE PATTERN

People, numbers, failures, money, law. An architect's first meeting is 80% listening. If you can work these twenty into your next project kickoff, you are already thinking differently — no new technology required.

SECTION 04 — CASE STUDY

Designing a Simple Online Shopping System

No technology yet. First the problem, then the decisions, then the shape. That is the order an architect works in — and the order you will repeat in interviews.

THE REQUIREMENTS — ALL OF THEM

  1. R1 Users can register.
  2. R2 Users can browse products.
  3. R3 Users can place orders.
  4. R4 Users can make payments.
  5. R5 Users can receive notifications (order status by email / SMS).

Before drawing anything, the architect reads those five lines and hears the risks hiding in each one:

  • R1 — Accounts mean passwords, and passwords mean a target. Sensitive data starts here.
  • R2 — Browsing is read-heavy. This is the part that must be fast and cheap.
  • R3 — The order is the promise. Losing an order is worse than a slow page.
  • R4 — Payment is external, exact, and expensive. One mistake costs real money.
  • R5 — Notifications are the least important — and the most common cause of blocking the main flow.

The architect's five lenses on this system

Reliability

Browsing (R2) must keep working even if payment (R4) has a problem. Orders (R3) must never be lost — write to the database first, notify later. Payment failures are expected: retry, offer a fallback, never crash the checkout. If email (R5) dies, the order still stands.

Performance

Product pages (R2) are hot and almost static → cache them. Checkout (R3+R4) must be short and exact → a few fast calls, never a long chain. Notifications (R5) leave the critical path entirely. Search may be a little slow; the order cannot be.

Scalability

Start with one deployable — a two-team shop does not need ten services. When load grows: app servers scale out (they are stateless), catalog reads go to the cache, the DB gains a read replica, and notifications already run on the queue. Every step is additive — none is a rewrite.

Security

Card data never touches our database — the payment gateway holds it. Passwords are salted hashes. Every order belongs to an authenticated user. Admin screens are a separate boundary. Login and payment attempts are rate-limited. Every order is logged: who ordered what, when.

Maintainability

Five responsibilities, five boxes: catalog, orders, payments, notifications, identity. Each owns one job. Payment sits behind a thin adapter — swap the gateway and only the adapter changes. Discount rules, which change often, live in the catalog module — one place, not five.

What this is NOT

Notice what is missing so far: no product list, no framework, no cloud region. The decisions above are the architecture. Technology is the last 10% — it fills this shape; it does not create it. That is the whole point of Day 1.

FOR YOUR STACK

The diagram below is, for you, SQL Server + Redis + RabbitMQ + ASP.NET Core. But look at what the decisions actually were: state vs stateless, sync vs async, who owns which data, where the external risk sits. The brands came last. That is the habit to build.

SYSTEM VIEW

Eleven boxes, one job each. Two are external — and you design around them, not with them. Note what is absent: no sharding, no service-per-team, no second region. Simple until proven otherwise.

Decisions made so far

# DECISION WHY
1 One deployable at the start, with clear modules inside Two teams, one product. The cost of separate services (deploy, monitor, trace) is not earned yet. Modules keep the door open to split later.
2 The order is written to the database before the notification is queued A lost notification is an email you send later. A lost order is a customer who paid and got nothing. The order is the promise.
3 Notifications run async, through the queue Email is slow and sometimes down. The checkout must not wait for it — or die with it.
4 Payment goes through a thin adapter to the gateway Gateways change contracts and go down. The adapter isolates the swap and the fallback (a second gateway, or "pay later").
5 Catalog is cached; stock and price are verified at order time Cached products may be a minute old — nobody notices. Stock and price at checkout must be exact. Cache the read, verify the write.

DELIBERATELY NOT DOING (DAY ONE)

  • No sharding. No per-service databases. No event sourcing.
  • No microservice per team. No Kubernetes. No second region.
  • Every one of these has a trigger — a number or a pain — and none of the triggers has arrived yet.
  • An architecture that has every answer before the questions are asked is not architecture. It is decoration.
INTERVIEW ANGLE

Interviewers do not want the fanciest shop design. They want to hear you say what you are not doing — and why. The sentence "I would not do X until I see Y" is the most senior sentence in this field. Say it often.

SECTION 05 — DECISION PATTERNS

Architecture Decision Examples

Five real decision patterns, in the format you will use in interviews and in life: Problem → Options → Pros → Cons → Decision → Why. The "why" is the architecture. The technology is just what the why happens to pick.

DECISION 01

One database, or many?

PROBLEM — A shop grows: catalog, orders and users all live in one SQL Server. Orders need strong consistency; the catalog is nothing but reads. Should the data split?

OPTION PROS CONS
A · One database, well-organized schemas Simplest to run; one backup, one restore drill; an order + stock update is a natural local transaction. One hotspot; a heavy reporting query can slow the checkout; one backup window for everything.
B · A database per module (catalog DB, orders DB) They scale and fail independently; teams can move independently. Cross-module consistency becomes messages and retries — hard; two backups; roughly double the operations.
DECISION

Start with A. Split only when a measured problem appears — and the first split is usually reporting to its own database or replica, not the catalog.

WHY

Order + stock consistency is the heart of the business. You do not pay the message-complexity tax before the load demands it. The split stays cheap later because the modules already have clean boundaries — which is the real asset.

DECISION 02

Send the email in the request — or through a queue?

PROBLEM — Order placed → confirmation email. The email provider takes up to 5 seconds and fails more often than anyone likes.

OPTION PROS CONS
A · Call the provider inside the request Dead simple; one code path; nothing extra to operate. Every checkout is 5 seconds slower; when the provider dies, the checkout dies with it.
B · Queue + background worker Checkout returns in milliseconds; provider failures are retried; spikes are absorbed. One more component to run; messages can be delayed — or lost, if designed badly.
DECISION

B. The email goes to the queue; a worker sends it and retries the failures.

WHY

An email that is ten seconds late is invisible to the user. A checkout that dies when the email provider sneezes is an outage. Move the slow, fallible thing off the critical path — this single rule pays rent every month.

DECISION 03

Cache the catalog — or hit the database every time?

PROBLEM — Product pages: 50,000 hits a day, and the data changes a few times a week. The database feels a little guilty.

OPTION PROS CONS
A · No cache, a fast database Always fresh; nothing to invalidate. The DB pays for reads that never change; the page gets slower as traffic grows.
B · In-process memory cache per server Fastest possible; zero network hop; zero new components. Every server keeps its own copy — after a price change, server 1 is new and server 2 is old for a while.
C · A shared cache (one copy for all servers) One consistent copy; clean invalidation; survives app restarts. Another component; it can fail (fall back to the DB — by design).
DECISION

C for a multi-server shop. A is fine for a single-instance app — pick the option that matches the shape, not the prestige.

WHY

With several app servers, a stale price on one of them is a support call and a trust problem. A shared copy makes invalidation one decision. And notice: the decision is about the shape (one shared copy) — the brand in your world is simply Redis, which you already know.

DECISION 04

Monolith or microservices — two teams, one new product

PROBLEM — The company loves microservices. The product is new, the team is two developers, and the first release is in six weeks.

OPTION PROS CONS
A · Modular monolith — one deployable, strict module boundaries One deploy, one trace, local transactions, a small operations bill; teams move fast. One release train; modules can creep into each other without discipline.
B · Microservices from day one Independent deploys; tech freedom per service; impressive on a slide. Network calls everywhere; distributed tracing; deploys multiplied; consistency problems arrive before product-market fit.
DECISION

A, with hard module boundaries — and a written trigger for extracting a service: different scale, different owner, or a release cadence the monolith cannot give.

WHY

Microservices buy independence. Two people on one product do not need independence yet — they need speed. The boundaries are the real asset; the process walls can wait for the day the team, scale, or cadence demands them.

DECISION 05

Multi-tenant SaaS: one shared database, or one per tenant?

PROBLEM — 100 companies (tenants) on one product. Tenant A must never see tenant B. (Yes — this is your Day 1 assignment. The decision, not the answer, is what you are practicing.)

OPTION PROS CONS
A · Shared DB, every table carries a tenant ID, every query scoped One backup; cheap per tenant; adding a tenant is instant; global reporting is easy. One noisy tenant can slow the others; the scoping rule must never be broken — it is a single line of defense.
B · A database per tenant Total isolation; per-tenant backup and deletion are easy; a noisy tenant cannot hurt anyone. 100 connections, 100 backups; migrations ×100; cost grows linearly with tenants.
DECISION

A at 100 tenants, with tenant scoping enforced in one place (a base data layer / global query filter). Written trigger: a large tenant that demands isolation moves to its own database — B for the whales, A for everyone else.

WHY

At 100 tenants, the shared model is cheaper and simpler, and isolation is a coding discipline you can guarantee in one enforced place. Per-tenant databases are the answer to a different scale — and the decision stays open because the trigger to revisit it is already written down.

THE MAIN LESSON — SAY THIS IN EVERY INTERVIEW

There is rarely one perfect technology. Every option above "works." The architect does not find the perfect one — the architect reads the problem and the constraints (team, budget, consistency, growth), chooses the option whose cost the business can pay, and writes down the trigger that will make them revisit it. That is the entire job.

SECTION 06 — HONEST EDITION

Common Beginner Mistakes

These are not "I wrote a bad loop" mistakes. They are the mistakes that cost senior developers the architect conversation. Read them slowly — you will recognize at least two of them in your own past.

01

Choosing technology before understanding the problem

It feels productive. Picking a tool is easy; questioning the problem is not. But the tool answers a question you may not even have yet — and you will drag it through every later decision.

Answer the 20 questions first. The technology is the last 10% of the decision — never the first.

02

Using microservices everywhere

It looks senior and it looks great on a slide. In reality it costs 5× the operations, and a two-person team cannot carry that bill while still shipping the product.

Modular monolith with clear boundaries. Split only when a real trigger arrives — and say the trigger out loud.

03

Ignoring failure scenarios

The happy path is the easy part and the fun part. Everything else feels like anxiety, so it gets skipped. Then the first real outage arrives as a surprise.

For every box in the diagram, ask: "when this one dies, what does the user see?" That single question doubles the quality of any design.

04

Ignoring cost

The architecture is "free" to the architect — the bill goes to the CFO. So the design floats, and one day reality invoices it: a $50k/month infrastructure for a $5k/month business.

Ask question 17 in every project. Name the rough monthly cost of your design before it is built, not in the post-mortem.

05

Treating security as an afterthought

It is invisible when it works, expensive to retrofit, so it is always "the last thing." That is exactly when it becomes the most expensive thing in the project.

Draw the trust boundaries in the first sketch. Decide what you never store before you store anything at all.

06

Designing for unrealistic scale

A million users sounds senior. It is also a sharding cluster, a queueing fabric, and a team of SREs — for a product with 3,000 users and no roadmap past the pilot.

Design for the real numbers and keep the path open. The 100 → 10,000 → 1,000,000 ladder is the answer: each rung paid for by the previous one's growth.

07

Overengineering

Event sourcing, CQRS, sagas — every one is a real tool for a real problem. And every one is a tax when the problem is not there. Complexity that nobody has asked for is just weight.

A tool earns its place with a measured pain. "In case we need it later" is not a requirement — it is a wish, and wishes do not pay the maintenance bill.

08

Copying an architecture from another project or company

Netflix's architecture assumes Netflix's team, budget, and 200 million users. Yours assumes your team, your budget, and your users. Copying the diagram imports all three assumptions silently.

Copy the principles — stateless apps, queued slow work, measured scaling. Never copy the box diagram without re-asking the 20 questions.

09

Designing without numbers

"It should be fast and available" is not a requirement — it is a feeling. Two competent engineers will build two different systems from it, and both will be right, and both will be wrong.

Attach a number to every quality word: fast = p95 under 300ms; available = 99.9%; scalable = 10× current load for 15 minutes. If there is no number, there is no design yet.

10

Not writing down the "why"

Six months later nobody remembers why the queue exists. A new lead "simplifies" it away, and the outage the queue was preventing becomes real — in production, on a Friday.

A one-page decision note: problem, options, decision, why, and the trigger to revisit. Ten minutes of writing that has saved at least one incident per team that uses it.

THE PATTERN IN ALL TEN

None of these is a lack of technical knowledge — you have twelve years of it. Every one of them is a skipped thinking step. That is why this 30-day program is about questions, decisions, and trade-offs — not about learning more tools.

SECTION 08 — CHECK

Self-Assessment: Did Day 1 Land?

Ten questions. No memorization — they test the thinking. Close the page, answer out loud, then open the model answer and compare the direction, not the words.

Q1A client says "the system must be fast." What do you ask next?
"Fast for which action? How fast, exactly — a number, and a percentile? For how many users, at what load? And what happens today when it is not?" Fast is not a requirement until it has a number and an action attached to it.
Q2What is the difference between reliability and performance, in one sentence each?
Performance: how quickly the system responds when it is working. Reliability: whether it keeps working at all when parts of it fail. One is about speed; the other is about survival.
Q3The payment provider is slow and sometimes times out. What do you design?
A timeout (never wait forever), a retry with delay, and a fallback — a second gateway or "pay later." If the payment runs asynchronously, the work goes through a queue so the provider's failure becomes a delayed job, not a failed order. And the user is always told the real state: paid, pending, or failed — never "unknown."
Q4Why is a monolith often the right first choice?
One deploy, one trace, local transactions, one backup, a small operations bill — and a team that moves faster inside one codebase. The costs only appear when independent scale or independent releases become a real need. So: keep the modules cleanly bounded from day one, ready to split — the boundaries are the asset.
Q5The boss says "we need 99.99% uptime." What is your first answer?
"That is about 53 minutes of downtime per year, and it costs roughly 10× more than 99.9% (8.7 hours). Which features actually need 99.99% — and what is the business willing to pay for the difference?" An architect negotiates the number with data, not with pride.
Q6What is the difference between authentication and authorization?
Authentication proves who you are — login, tokens, MFA. Authorization decides what that identity may do — roles, permissions, checked on the server for every request. You can have one without the other — and having only authentication is a classic breach.
Q7A feature works fine at 1,000 users. How do you know when it will break?
You cannot know by looking — you measure. Push it with a load test at 10×, watch where the response time bends, and find the first resource that saturates (CPU, database, connections). Then you have a number: it breaks here, at this load, at this component — and scaling becomes a plan instead of a fear.
Q8What is technical debt? Should you always avoid it?
Shortcuts taken now that cost extra every time you touch that code again. No — sometimes you take it on purpose: a prototype must be fast, and the "debt" is the plan to rebuild it later. The failure is taking debt unknowingly, or never repaying it. Name it, time-box it, schedule the payoff.
Q9Tenant A can see tenant B's data by changing the ID in the URL. Which pillar broke — and where?
Security — specifically authorization: the check was "is a logged-in user?", not "is this the user's tenant?". It broke at the query layer: data was fetched without a tenant scope. The fix is a single enforcement point — a global query filter or a base data layer — so no future endpoint can ever forget the rule.
Q10Name one decision that is cheap to change, and one that is hard to change.
Cheap: the UI framework, a helper library, the queue's message format (with care). Hard: how data is owned (which module owns which table), the consistency rules (what must be atomic), the tenant isolation model, public API contracts. The architect spends time on the hard ones — because those are the real architecture.

FINAL — CARRY THESE FOR 29 MORE DAYS

Architect Mindset for Day 1

Five rules. They are short on purpose. You will meet each one again — wearing a different costume — on every single day of this program.

01

Problem before technology

The tool is the last 10% of the decision. If you cannot state the problem in two sentences, you are not ready to pick a tool — no matter how much you love that tool.

02

Everything fails. Design for the bad day

Not "will it work?" but "when the disk dies, when the gateway sneezes, when the spike arrives — what does the user see?" The design that survives the bad day is the real design.

03

There is no perfect option. Choose the cost you can pay

Every option works. The difference is what it costs — money, complexity, team effort. The architect picks the affordable cost and writes down the trigger that will make them revisit it.

04

Numbers, or it did not happen

"Fast, reliable, scalable" are feelings. "p95 under 300ms, 99.9%, 10× for 15 minutes" are requirements. Attach a number to every quality word before you design anything at all.

05

Simple until proven otherwise

The best design is the smallest one that meets the real constraints — with a clear, cheap path to grow. Complexity is earned, one measured pain at a time. Never in advance.
