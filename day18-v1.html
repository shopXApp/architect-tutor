PART 1 — FIRST PRINCIPLES

Basic Understanding

Microservices are not a technology. They are an architecture style. The first step is to understand what they are — and what they are not.

1. What is a monolith?

A monolith is a single, unified application. All the code — user interface, business logic, data access — lives in one codebase, is built as one unit, and is deployed as one package. Examples: a single ASP.NET Core app with MVC, API, and background jobs; a Ruby on Rails application; a traditional n-tier .NET application.

2. What is a modular monolith?

A modular monolith is still a single application — but the code is organized into clear, independent modules with well-defined boundaries. Each module handles a specific business area (e.g., Orders, Customers, Inventory) and communicates with others through interfaces, not direct database calls. The modules are logically separated, even though they are physically together.

3. What is a microservice?

A microservice is a small, independent application that does one thing. It has its own codebase, its own database, and its own deployment. Microservices communicate with each other over the network — usually via HTTP APIs or messages. The whole system is a collection of these small services, working together.

4. What is the main difference between them?

ASPECT MONOLITH MODULAR MONOLITH MICROSERVICES
Codebase One One Many (one per service)
Deployment One unit One unit Independent per service
Database One shared One shared One per service (usually)
Communication In-process calls In-process calls Network calls (HTTP, messages)
Scaling Scale the whole app Scale the whole app Scale each service independently
Complexity Low Low-Medium High

5. Why did microservices become popular?

Microservices became popular because they promised solutions to problems that large monoliths face:

  • Independent deployment: Deploy one service without redeploying the entire application.
  • Independent scaling: Scale the busy service without scaling the whole system.
  • Team autonomy: Different teams can own different services, using different technologies and release cycles.
  • Technology flexibility: Each service can use the best technology for its job.
  • Resilience: If one service fails, it does not necessarily bring down the entire system.

6. What problems do microservices solve?

Microservices solve organizational and scaling problems that appear when a monolith grows too large:

  • Large codebase: A monolith with 100 developers becomes hard to understand, test, and deploy.
  • Different scaling needs: Some parts of the system need more resources than others.
  • Different teams: Multiple teams working on the same codebase creates conflicts and slows down releases.
  • Different technologies: Different parts of the system may need different databases, frameworks, or languages.
  • Single point of failure: A bug in one part of a monolith can bring down the entire system.

7. What new problems do microservices create?

Microservices do not solve problems for free. They trade one set of problems for another:

  • Network complexity: Services communicate over the network, which is slower and less reliable than in-process calls.
  • Data consistency: Transactions that span multiple services are hard to keep consistent.
  • Operational complexity: You now have many services to deploy, monitor, log, and debug.
  • Testing complexity: Testing interactions between services requires mocking or spinning up dependencies.
  • Debugging complexity: A single user request may touch many services — finding the problem is like finding a needle in a haystack.
THE FIRST RULE

Microservices are not a better monolith. They are a different architecture with different trade-offs. The question is not "are microservices better?" The question is: "are the problems microservices solve more painful than the problems they create?"

PART 2 — THE MOST IMPORTANT QUESTION

"Why shouldn't every application use microservices?"

Because for most applications, the problems microservices create are worse than the problems they solve. Here are ten situations where microservices are likely a bad choice.

  1. Small applicationSituation: The system has only a few features and a small codebase.Why bad: Microservices add overhead that a small system does not need. The simplicity of a monolith is a feature, not a bug.Better alternative: Monolith or modular monolith.
  2. Small development teamSituation: The team has fewer than 8–10 developers.Why bad: Microservices require operational maturity (CI/CD, monitoring, deployment) that small teams cannot provide. The team will spend more time fighting the architecture than building features.Better alternative: Monolith or modular monolith.
  3. Low trafficSituation: The system serves fewer than 100 requests per second at peak.Why bad: A single monolith server can handle this easily. Microservices add latency (network calls) that makes the system slower, not faster.Better alternative: Monolith. Optimize the database first.
  4. Simple business rulesSituation: The business logic is straightforward, with few changes expected.Why bad: Microservices shine when business areas are complex and change independently. If the business is simple, the architecture should be too.Better alternative: Monolith.
  5. Limited budgetSituation: The project has a tight budget for development and operations.Why bad: Microservices require more infrastructure (servers, networking, monitoring), more development effort (network handling, retries, timeouts), and more operational effort (deployment, debugging). All of this costs money.Better alternative: Monolith. Spend the budget on features, not architecture.
  6. Early-stage productSituation: The product is still finding its market fit. Features change frequently.Why bad: Microservices make it harder to change things that span multiple services. In the early stage, you want to change things quickly, not maintain service boundaries.Better alternative: Monolith. Pivot fast, then refactor later if needed.
  7. Low operational maturitySituation: The team does not have strong CI/CD, monitoring, or deployment practices.Why bad: Microservices require mature DevOps. Without it, deployments are slow, failures are hard to debug, and the system is unreliable.Better alternative: Improve operational maturity first. Then consider microservices.
  8. No need for independent scalingSituation: All parts of the system scale at the same rate.Why bad: The main benefit of microservices — independent scaling — is not needed. You are adding complexity for no benefit.Better alternative: Monolith. Scale the whole app vertically.
  9. Strong need for simple transactionsSituation: The system has many operations that update multiple parts of the data in a single transaction.Why bad: Distributed transactions (across services) are complex, slow, and prone to failure. If your business requires many multi-part transactions, microservices will make your life harder.Better alternative: Monolith with a single database. Use database transactions.
  10. Very tightly connected business logicSituation: Business operations frequently need data from many parts of the system, and that data must be consistent.Why bad: Microservices work best when business areas are loosely coupled. If every operation touches many services, you will spend all your time coordinating between them.Better alternative: Monolith or modular monolith with a shared database.
THE ARCHITECT'S JOB

An architect's most important skill is saying no to complexity. Microservices are complex. The default answer should be "no" — unless the business problem clearly justifies the cost. Most systems should not use microservices.

PART 3 — THE SAME SYSTEM, THREE WAYS

Business Example: Inventory and Order Management

One system, three architectures. See how the same business areas are organized differently.

THE BUSINESS AREAS

AREA RESPONSIBILITY TRAFFIC DATA
Authentication User login, permissions Medium Users, roles
Company Tenant/company management Low Companies, settings
Customer Customer profiles, addresses Medium Customers, contacts
Product Product catalog, pricing High (reads) Products, categories
Sales Order Order creation, management Medium Orders, order lines
Purchase Purchase orders to suppliers Low Purchase orders
Inventory Stock levels, movements Medium Inventory, transactions
Payment Payment processing Medium Payments, transactions
Notification Emails, alerts High Messages, templates
Reporting Sales reports, analytics High (reads) Report data, aggregates
Audit Audit logging Medium Audit logs

Design 1: Simple Monolith

How it worksAll business areas are in one codebase, one deployable unit, one database. Communication between areas is via direct method calls or shared database access.
AdvantagesSimple to develop, test, deploy, and debug. One codebase, one pipeline, one set of dependencies. Transactions that span multiple areas are easy — they are in the same database.
DisadvantagesHard to scale — the whole app must be scaled as one unit. Hard to deploy — a small change requires redeploying the entire app. Hard for large teams — many developers working in the same codebase creates conflicts.
When to useSmall systems, small teams, simple business logic, or when the system is still finding its feet. The default starting point for most applications.

Design 2: Modular Monolith

How it worksEach business area is a separate module with clear boundaries and interfaces. Modules communicate through interfaces, not direct database calls. But they are still deployed as one unit.
AdvantagesClear separation of concerns — each module has a single responsibility. Easier for teams — teams can own modules. Easier to test — modules can be tested in isolation. Easier to migrate — a module can be extracted into a service later.
DisadvantagesStill one deploy — a change to one module requires redeploying the whole app. Shared database — modules share a database, which can create coupling.
When to useWhen the monolith is growing, but microservices are not yet justified. The modular monolith gives you many of the benefits of microservices (clear boundaries, team ownership) without the operational complexity.
THE ARCHITECT'S SECRET

Modular monolith does NOT mean bad architecture. It is a legitimate, production-ready architecture that many large systems use successfully. It is often the best choice for systems that are too big for a simple monolith but not big enough to justify microservices.

Design 3: Microservices

How it worksEach business area is a separate service, with its own codebase, deployment, and database. Services communicate over the network (HTTP, messages).
AdvantagesIndependent deployment — deploy one service without affecting others. Independent scaling — scale only the services that need it. Team autonomy — teams own services end-to-end. Technology flexibility — each service can use the best tech.
DisadvantagesNetwork complexity — services communicate over the network, which is slow and unreliable. Data consistency — transactions across services are hard. Operational complexity — many services to deploy, monitor, debug.
When to useWhen the system is large, the teams are large, the business areas are independent, and the operational maturity is high. Only after the modular monolith has proven insufficient.
THE EVOLUTION PATH

Start with a simple monolith. When it grows, refactor into a modular monolith. When the modular monolith can no longer keep up with the scale or team needs, then consider extracting services into microservices. Most systems never need to leave the modular monolith stage.

PART 4 — THE UNDERRATED CHOICE

Modular Monolith: Why It Can Be the Best Choice

A modular monolith gives you many of the benefits of microservices without the operational nightmare. It is the architecture that most systems should aim for.

Clear business areas

Each module represents a business capability — Authentication, Customers, Products, Orders, Inventory. The modules are organized around what the business does, not technical layers (UI, API, database).

Separate responsibilities

Each module has a single responsibility. It owns its data, its business logic, and its interfaces. Other modules interact with it through those interfaces — not by reaching into its database or code.

Shared deployment

All modules are deployed together as one unit. This means:

  • Simpler deployment: One pipeline, one set of servers, one rollback plan.
  • Easier debugging: One log file, one place to look for problems.
  • Strong consistency: Transactions that span multiple modules can use the same database transaction.

Simple communication

Modules communicate through interfaces — method calls, not network calls. This means:

  • Fast: In-process calls are orders of magnitude faster than network calls.
  • Reliable: No network timeouts, retries, or failures.
  • Simple: No need to handle serialization, deserialization, or versioning.

Simple database access

All modules share the same database. This means:

  • Easy transactions: A transaction can span multiple modules without distributed transaction complexity.
  • Easy queries: Joins across module data are simple and fast.
  • Easy reporting: Reports can query data from multiple modules without complex data aggregation.

Easier debugging

With one codebase and one deployment, debugging is straightforward:

  • Set a breakpoint in one module, step into another.
  • View the call stack across modules.
  • Search the entire codebase for a problem.

Lower operational cost

One application means:

  • Fewer servers: One set of servers instead of many.
  • Simpler monitoring: One application to monitor.
  • Simpler logging: One log file to aggregate and search.
  • Simpler deployment: One pipeline to maintain.

Easier development for small teams

Small teams do not need the complexity of microservices. A modular monolith allows them to:

  • Work in a single codebase.
  • Avoid network complexity.
  • Focus on building features, not infrastructure.

Ability to move selected modules to services later

The modular monolith is not a dead end. If a module needs to be scaled independently or owned by a different team, it can be extracted into a microservice later. The clear boundaries make this extraction straightforward.

THE ARCHITECT'S MANTRA

"Modular monolith first, microservices later — if ever." Most systems will never need microservices. The modular monolith is the sweet spot for most applications.

PART 5 — THE REAL BENEFITS

Microservices Benefits

Microservices are not a magic bullet. But when used correctly, they provide real benefits.

  1. Independent deploymentBenefit: Deploy one service without redeploying the entire application. This allows faster, more frequent releases for individual features. Example: The Notification service can be updated to add a new email template without redeploying the Order service.Condition: The service must have a stable interface that other services depend on.
  2. Independent scalingBenefit: Scale only the services that need more resources. This can save money and improve performance. Example: The Product Catalog service can be scaled up during a Black Friday sale, while the Order service (which is not as busy) does not need to be scaled.Condition: The service must have independent resource needs.
  3. Failure isolationBenefit: If one service fails, it does not necessarily bring down the entire system. Other services can continue to function. Example: If the Reporting service fails, users can still place orders.Condition: Services must be designed to fail gracefully (timeouts, retries, circuit breakers).
  4. Team ownershipBenefit: Different teams can own different services. This allows teams to work independently, using the best practices and technologies for their service. Example: The Payment team can own the Payment service, using the best security practices and technologies for payments.Condition: The team must be mature enough to own a service end-to-end.
  5. Technology flexibilityBenefit: Each service can use the best technology for its job. Example: The Reporting service can use a columnar database optimized for analytics, while the Order service uses a relational database optimized for transactions.Condition: The team must be able to support multiple technologies.
  6. Smaller codebasesBenefit: Each service has a smaller, more manageable codebase. This makes it easier for developers to understand, test, and maintain the code. Example: A service with 5,000 lines of code is easier to understand than a monolith with 500,000 lines.Condition: The service boundaries must be clear and well-defined.
  7. Independent release cyclesBenefit: Different services can have different release cycles. A stable service can be released monthly, while a rapidly changing service can be released weekly. Example: The Authentication service (stable) can be released monthly, while the Product Catalog service (frequently updated) can be released weekly.Condition: The release process must be automated and reliable.
  8. Different performance requirementsBenefit: Different services can have different performance, availability, and durability requirements. Example: The Order service can be optimized for low latency, while the Reporting service can be optimized for high throughput.Condition: The requirements must be clearly defined and measurable.
THE CATCH

These benefits are only realized if the microservices are well-designed. Poorly designed microservices can be worse than a monolith — slower, less reliable, and harder to maintain. The benefits do not come for free.

PART 6 — THE REAL COSTS

Microservices Costs

Microservices introduce a lot of new complexity. Every item below is a problem you did not have with a monolith.

  1. Network communicationProblem: Services communicate over the network, which is slower and less reliable than in-process calls. Every network call adds latency and can fail.How an Architect manages it: Minimize network calls. Use caching. Design for failure (timeouts, retries, circuit breakers).
  2. Service failuresProblem: If one service fails, it can bring down other services that depend on it. A single point of failure can cascade into a system-wide outage.How an Architect manages it: Design for resilience. Use timeouts, retries, and circuit breakers. Implement graceful degradation.
  3. Distributed transactionsProblem: Transactions that span multiple services are hard to keep consistent. You cannot use a simple database transaction.How an Architect manages it: Avoid distributed transactions when possible. Use eventual consistency, sagas, or compensation logic when necessary.
  4. Data consistencyProblem: Data is spread across multiple databases. Keeping it consistent is hard. Reads may return stale data.How an Architect manages it: Accept eventual consistency where possible. Use change data capture (CDC) or event sourcing for synchronization. Implement conflict resolution.
  5. MonitoringProblem: You now have many services to monitor. You need to track the health of each service, its dependencies, and the interactions between them.How an Architect manages it: Implement centralized monitoring (metrics, logs, traces). Use dashboards to view the health of the entire system.
  6. LoggingProblem: Logs are spread across many services. Tracing a single user request requires correlating logs from multiple services.How an Architect manages it: Use structured logging with correlation IDs. Aggregate logs in a centralized system. Use distributed tracing.
  7. DeploymentProblem: You now have many services to deploy. Each service may have its own dependencies, configuration, and deployment process.How an Architect manages it: Automate deployment with CI/CD. Use containers for consistency. Implement blue-green or canary deployments.
  8. TestingProblem: Testing interactions between services requires mocking or spinning up dependencies. Integration testing is complex.How an Architect manages it: Use contract testing. Test each service in isolation with mocks. Implement integration tests in a staging environment.
  9. SecurityProblem: Each service is a potential attack surface. You need to secure each service individually.How an Architect manages it: Implement consistent security practices (authentication, authorization, encryption). Use a service mesh for mutual TLS.
  10. Version managementProblem: Services evolve at different rates. You need to manage backward and forward compatibility between service versions.How an Architect manages it: Use semantic versioning. Implement backward-compatible changes. Use API gateways for versioning.
  11. InfrastructureProblem: You need more infrastructure to run many services. Each service may need its own servers, load balancers, and databases.How an Architect manages it: Use containers and orchestration (Kubernetes) to manage infrastructure efficiently. Use serverless where appropriate.
  12. Service discoveryProblem: Services need to find each other. In a dynamic environment (e.g., cloud), service instances come and go frequently.How an Architect manages it: Use a service registry or service mesh. Implement health checks and automatic deregistration.
  13. Operational supportProblem: You need to support many services in production. This requires more operational maturity and more people.How an Architect manages it: Invest in DevOps. Automate everything. Implement on-call rotations and runbooks.
  14. DebuggingProblem: Debugging issues that span multiple services is hard. You need to trace requests across service boundaries.How an Architect manages it: Use distributed tracing. Implement centralized logging. Use correlation IDs to trace requests.
  15. Increased cloud costProblem: Running many services in the cloud can be more expensive than running a monolith. Each service may require its own resources (CPU, memory, networking).How an Architect manages it: Monitor and optimize resource usage. Use auto-scaling. Consider serverless for sporadic workloads.
THE ARCHITECT'S REALITY CHECK

Microservices are not a free lunch. They are a trade: you give up simplicity and operational ease in exchange for scalability and team autonomy. Only make that trade if the benefits clearly outweigh the costs.
