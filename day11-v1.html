SECTION 01 — THE REAL PROBLEM

Why Security Is Part of Architecture, Not a Checkbox at the End

Security bolted on at the end is like treating every other room of the house as the front door. The example that shows it: an e-commerce platform with four kinds of people.

If access is not designed correctly, here is what each careless default buys: Everyone sees everyone's orders because "users see orders." Admins edit every company's products because "admins are admins." Support reads full customer records including card fields because "support needs context." Products are visible only to logged-in users because someone protected the catalog "to be safe." The UI hides the admin button — and the API happily serves it to anyone who calls it directly. Each of these is not an attacker's invention; it is a default the team forgot to design.

THE LESSON

A page that hides what the user may not do is not security — it is decoration. Security is the set of rules the server enforces on every request: who you are, which tenant you belong to, what you may do to which resource, in which action. If those rules are not in the architecture by day one, the end of the project is when you pay for them — measured in data breaches, not in pages.

SECTION 02 — THE TWO QUESTIONS

Authentication vs Authorization

Two questions that are constantly confused — and the confusion is expensive.

Authentication

WHO ARE YOU?

The office: the receptionist checks your ID badge at the door. That is the whole job — proving you are who you claim to be. It does not say which floors you may enter.

The software: the user logs in (or the client proves itself), the identity provider verifies it, and issues a token. The user is now proved — identified — and nothing else is decided yet.

Authorization

WHAT MAY YOU DO?

The office: the badge reader on each floor decides whether your role unlocks it. The same badge gets you only into the floors you're allowed on.

The software: on every request, the API reads the token and checks: is this user allowed to do this action, on this resource, in this tenant — at this moment? Never once at login, never only in the UI.

Step by step: the user gives proof · the provider checks it · the provider issues a token (a signed statement of who this is) · every request to the API carries that token · and on every request the API checks the token's validity, then asks is the bearer of this token allowed to do this exact thing, on this exact resource, in this exact tenant? The first three steps are authentication. The last is authorization. A user can be authenticated to the system and still be unauthorized to the action — and a system that checks only login conflates the two into a data breach.

THE INTERVIEW SENTENCE

"Authentication answers who are you; authorization answers what may you do, on this request, on this tenant, right now. One is a gate; the other is an arena. A login is not a permission."

SECTION 03 — THE MECHANISM

OAuth 2.0 and OpenID Connect — Architect Level Only

No protocol syntax. Six things, plus the one reason you should not build this yourself.

WHY OAUTH EXISTSTo let an app access your data without knowing your password. The password lives with the identity provider; the app gets a token, not the secret. The provider remains the one place that sees credentials.
WHY OPENID CONNECT EXISTSOAuth is about delegating access, not about who the user is. OIDC adds identity on top of OAuth 2: the ID token says "this is the user" with the provider's signature, so the app and API can trust the identity itself.
ACCESS TOKENThe permission slip the client carries to the API — proof you are authenticated and may call certain endpoints, for a short time. The API checks it on every request.
ID TOKENThe identity statement: "this is who you are," signed by the provider. The app gets it too; the API usually uses the access token for authorization while the app uses the ID token to know the user.
REFRESH TOKENThe long-lived admission card that trades for a fresh access token when the short one expires — kept secret, used by the client only, revocable. A user does not re-login every hour.
AUTHORIZATION SERVERThe identity provider (Entra ID, AWS Cognito). It checks credentials, issues the tokens, revokes them, and remains the single source of truth for "who is allowed in." Everything downstream trusts the signature.
WHY "DO NOT BUILD YOUR OWN AUTH"

You see it in the enormity of what you avoid: password hashing and storage, account lockout, MFA, password-reset flows, session hijacking, session fixation, timing attacks, OAuth provider updates, and every new security patch on your custom stack — all of which the provider does for you and keeps current. One line of custom auth costs you ten years of security maintenance. Build your own only when you have an organization-level requirement so strong it outweighs all of that — and be ready to defend that sentence in front of the CIO, not at a whiteboard.

INTERVIEW ANGLE

"OAuth lets an app act on my behalf without my password. OIDC adds who I am on top of that. The provider is the one authority that sees credentials and vouches for everything else. I would use the provider I already have — and I would not build my own auth stack unless someone pays me to explain why every month is worth it."

SECTION 04 — THE TOKEN

JWT, in Plain English

A JWT is a signed statement about who you are — carried in JSON, encoded in Base64, and verifiable by anyone who has the signer's public key. Three parts: how it claims who you are, how it proves it, and what the API does with it.

WHAT IT CONTAINSThree parts, joined by dots: a header (algorithm), a payload (claims: user id, name, roles, tenant id, issuer, expiry), and a signature — the proof nobody can alter the payload without invalidating it.
WHY APIs USE ITNo lookup per request. The API validates the signature and reads the claims, using only the public key. No session store, no round-trip — which is exactly the stateless-server requirement from Day 2, now with a token that is the session.
SIGNATURE — WHY IT WORKSThe provider signs with a private key; your API checks with the public key. Anyone can verify; nobody can forge. Change one character in the payload and the signature no longer matches — a tampered token dies at verification.
WHAT THE API MUST VALIDATENot just "is a JWT present?" — signature valid · issuer is ours · audience is our API · not expired · and — the part people forget — the claims are sufficient for the requested action, on that tenant, at that moment.

FOUR "WHAT IF" SCENARIOS, EACH WITH THE API'S ANSWER

TOKEN EXPIRESAccess token = short life on purpose (5–60 minutes). On expiry the API returns 401; the client silently trades the refresh token for a fresh one. The expiry is the safety clock — it limits how long a stolen token is useful.
TOKEN IS MODIFIEDAttacker edits "role" from user to admin. The signature was computed over the original text — change a character and the signature fails verification. The token is rejected before any logic runs. This is the whole point of the signature.
TOKEN IS STOLENA short-lived access token bounds the damage (minutes), HTTPS protects it in flight. On suspicion, revoke the refresh token and log out — the provider's whole job. If a token cancels sessions, the provider cancels the token.
USER'S ROLE CHANGESOld token still has the old role. Two honest answers: short token lifetime so the stale claim dies naturally; and on a critical action, re-verify against the source of truth (the role service / a version claim). A role change that must take effect now cannot wait for expiry.
⇒ THE TOKEN IS A TRUSTED AS LONG AS ITS SIGNATURE, ITS CLOCK, AND ITS CLAIMS. IF ANY OF THE THREE FAILS, THE API MUST REMAIN STRONGER THAN THE TOKEN.
WHAT A JWT IS NOT

Not encryption. The payload is Base64, readable by anyone — do not put a card number in a JWT. Not a session. It is not revocable on its own — that is the provider's job, via the refresh token and the expiry. Not the answer. It is the way the API knows who you are; it does not decide on its own what you may do. The decision is the API's, every time.

SECTION 05 — THE IDENTITY PROVIDER

Microsoft Entra ID, From an Architect's Chair

For the .NET/Azure stack, Entra ID is the default answer to Section 3's entire problem. Five things it gives you — and the one that matters most in a multi-tenant app.

USER IDENTITYLogin, MFA, SSO for your employees and customers. Passwords, lockouts and password resets are their problem, never yours. The user proves themselves here and nowhere else.
APPLICATION IDENTITYRegistered apps and services get their own identity (service principals, managed identities). The app authenticates to other resources as itself — no stored secret.
ROLESAdmin, Manager, Support — mapped to your application's own authorizations. The IdP issues the role; the API enforces it per request and per tenant.
GROUPSPeople grouped by team or company, for assignment at scale. Membership decides what a user in the group may do — managed outside your database.
ACCESS CONTROLRBAC for the platform itself: who may read what (Key Vault, SQL, Blob) with least privilege — the Day 8 story, applied to user and app alike.
THE POINT THAT MATTERS FOR MULTI-TENANT

Entra ID issues the tenant id as a claim in the token, and — this is the critical habit — your API treats that claim as the only lawful tenant. The tenant id from the request body, the URL, the header: all untrusted. The IdP is the source of truth; the request is an untrusted suggestion. The difference between those two sentences is the difference between a tenant system and a data breach.

SECTION 06 — THE RULES

Role-Based Access

Role → Permission → Resource. Three words that design access — and why the naive version breaks in multi-tenant systems.

ROLE MAY DO MAY NOT DO REASON
Admin Manage company's users, products, prices, integrations. Touch other companies' data. Role is company-scoped, not universe-scoped.
Manager Approve orders, reports, some configuration. Delete users, alter billing, manage other companies. Manage the flow, not the crown.
Employee View and act on own company's data within their job function (e.g. warehouse, sales). Access company they don't belong to; permissions beyond the job. Least privilege — enough to do the job, and no more.
Support (internal, cross-tenant) Read-only access to selected customer data (and every read logged) — only the fields genuinely needed. Edit anything, see card numbers, query the entire tenant list. Support needs context, not the keys.

Why a simple role list is not enough — and five things that decide access

  1. The user — not just "Admin," but this user, in their company. A user can be Admin of A and Employee of B in the same system.
  2. The role — Admin, Manager, Employee, Support — the coarse gate.
  3. The company/tenant — the binding that turns "an admin" into "an admin of your company's data." Tenant checks beat role checks.
  4. The resource — orders, products, prices, users, integrations — a role is not blanket; it grants permissions per resource type.
  5. The action — read vs write vs delete vs export are different permissions on the same resource.
THE MULTI-TENANT ILLUSTRATION

A user is Admin of Tenant A and Employee of Tenant B. A well-designed system gives two answers for every one of her requests, per tenant: "may she manage users?" — yes on A, no on B. The role that the IdP issues is company's-bound, not global. If your authorization layer treats "Admin" as a global flag, you have already broken the tenant boundary. In multi-tenant systems, permission checks are tenant-scoped before they are role-scoped.

SECTION 07 — THE CRITICAL SECTION

Multi-Tenant Security — 10,000 Companies, 1 Million Users

One tenant must never see another tenant's data — not by URL, not by cache, not by job, not by report, not by mistake in a new endpoint written on a Friday. The boundary is not one filter; it is several, at different layers.

UNSAFE THINKING vs SAFE THINKING — TENANT DOORWAYS, NOT FEATURES

  • UNSAFE — Tenant id is read from the request URL (/api/orders?tenant=88) and trusted. Change the number, see another company.
  • SAFE — Tenant id comes from the token the IdP issued. The URL's tenant id is a hint at best, and the server validates it matches the token's tenant before anything happens.
  • UNSAFE — Every SQL query assumes the developer remembered WHERE TenantId = @t everywhere. One new endpoint without it is a breach.
  • SAFE — A global query filter adds the tenant scope everywhere, enforced by a base repository or SQL Row-Level Security — so you cannot write an unfiltered query, even by accident.
  • UNSAFE — Cache key products:hot shared across tenants.
  • SAFE — Cache key t:88:products:hot — tenant is in every key, as Day 5 taught.
  • UNSAFE — Background jobs query without a tenant scope ("sync all products"), so one bug exports every tenant to a blob.
  • SAFE — Every job is tenant-scoped by design, executed per-tenant, and the archives are tenant-prefixed.
  • UNSAFE — Reports query the same tables the app uses, with no tenant filter, and export a consolidated "everything" — that someone shares with the wrong customer.
  • SAFE — Reports are tenant-scoped by the same filters, generated per tenant, and the source of "everything" exists only where aggregation is genuinely needed and its own permissions.
  • UNSAFE — Logs print the full customer record for "debugging," including PII and card fields.
  • SAFE — Logs write tenant ids and operation names, never card numbers, PII fields, or tokens. The audit view is separate and restricted to support roles with data masked.
THE LAYERS THAT MUST AGREE

Tenant safety is not a filter you remember to write — it is five layers wearing the same coat: the IdP issues the tenant claim, the API validates it on every request, the data layer enforces it in every query, the cache carries it in every key, and background work is scoped per tenant. The day any one of the five is different, Tenant A sees Tenant B. If isolation lives only in the UI, Tenant B has already seen A.

SECTION 08 — THE VAULT

Secrets and Credentials

One sentence, and then one architecture: the code must contain nothing secret. Not passwords, not API keys, not connection strings, not tokens.

APPLICATION IDENTITY (Managed Identity / IAM Role)The platform vouches for the app itself. The app authenticates to SQL, Key Vault, Blob or Service Bus as itself — no password stored anywhere. Assign rights to the identity, then delete every connection string with the password inside. The app is the identity.
SECRET STORAGE (Key Vault / Secrets Manager)The small number of secrets that genuinely must live somewhere — third-party API keys, hard-to-rotate values and legacy credentials — go to the vault, referenced from the app at startup using its identity. Rotation is a vault operation, not a release. The code has nothing to fetch except the vault name.
THE "THEY ARE DIFFERENT" SENTENCE

Application identity = the proof of who the app is. Secret storage = the container for the exceptions. Most architectures need one identity and a few secrets. The smell is when you can copy a connection string out of your repository with a right-click and nothing about it requires access.

SECTION 09 — THE PERIMETER

API Security Controls

API security is not only about login. Login is where auth begins; what follows are the eight guards on every request — and why each one is necessary.

CONTROL WHAT IT DOES WHY IT MATTERS · SIMPLE EXAMPLE
HTTPS / TLS Encrypts everything on the wire — request and response. A token on plain HTTP is readable by anyone on the same network or a cafe wifi. One leak, one checkout, forever.
Authentication Verifies a valid, unexpired token from the right issuer. The token has an issuer and an audience, not just "a JWT in the header". Without that check, any token with "admin" in the payload is an admin.
Authorization Checks the role/permission per request, per action, per tenant. /admin/orders is not an Admin endpoint because the URL says it is — it is because the API checks IsAdmin and TenantId = token.tenant before coding.
Input validation Rejects unexpected types, ranges, formats before any business logic. Price field accepts a string that later parses: SQL injection. Discount field accepts a value over 100%: free products. Validate on the server; the client is always able to send anything.
Rate limiting Caps requests per client/IP/tenant. One client can hammer the login endpoint 50,000 times a minute, exhausting DB reads and slowly guessing passwords. Limit by identity where possible, IP where not.
Request size limits Caps payload size so a single request cannot consume memory. A 50 MB image upload as one request, × 100 concurrent, is the Out-Of-Memory restart from Day 4's bottleneck quiz. Stream, limit, and chunk.
Secure headers HTTP response headers that lock down the client — CSP, HSTS, X-Frame-Options. Strict-Transport-Security forces HTTPS; content-security headers stop script injection from runaway rendering. Cheap to set, hard to bypass.
Audit logging Who did what, when, on what tenant — without leaking sensitive fields. Who changed the price? Who changed the role? The day a breach happens, the audit log is the difference between "the door was open" and "we know exactly what happened".
THE POINT

Login is the front of a stadium. Eight guards check the rest of the entrances. The attacker almost never tries to beat your authentication — the attacker tries to exploit a door you stored a secret on, a missing limit, an unvalidated field, or a missing scope on an internal endpoint. Protect those, and most of the attack surface quietly closes.

SECTION 10 — THE ATTACKS (AT HIGH LEVEL)

Common Web Security Risks

High level, no exploit instructions. For each: what happens → the business impact → the simple prevention an architect builds in.

RISK WHAT HAPPENS BUSINESS IMPACT SIMPLE PREVENTION
SQL injection Input is joined into SQL, so a field becomes a command and reads/deletes the database. Full data breach, deleted data. Parameterized queries everywhere — never build SQL strings from user input, never log raw SQL with values.
XSS A user's input is rendered as code in another user's browser — browser executes attacker JavaScript. Sessions and tokens stolen, actions performed as the user. Output-encode by default everywhere a user's input is shown; content-security headers as a safety net.
CSRF An authenticated user's browser is tricked into making a request on another site. An unintended action performed as the user. Anti-CSRF tokens for state-changing requests, SameSite cookies, always re-authenticate for money-moving actions.
Broken access control The UI hides the admin button; the API serves it to any caller who asks. Privilege escalation to admin-grade data and actions. Server-side authorization on every request and every action — including back-office and service endpoints.
Sensitive data exposure PII, card fields, tokens, connection strings appear in responses, logs or error pages. RID/LDAP breach, fines, brand damage. Never log secrets or sensitive fields; mask sensitive data in responses and error pages; restrict sensitive data to encrypted stores with least privilege.
Insecure file upload Malicious content is uploaded as a file, served to users or stored next to secrets. Compromise of customers or the server itself. Validate type and content, store outside the app's directory, serve via a controlled URL, scan larger files, never execute uploads.
Brute-force login Hundreds of thousands of password attempts against one endpoint. Account takeover via slow guessing, DDoS of the login path. Rate limiting, lockout policies, MFA, and alerting on anomalous login patterns (not just on success).
Token theft A JWT or API key is leaked and used as the user. Full account compromise until the token expires. Short token lifetimes, HTTPS everywhere, refresh-token revocation, and monitoring of anomalous usage (impossible travel, unusual calls, impossible velocity).
THE PATTERN

Every one of these is a default you skipped, not a genius move by the attacker. The five with the worst track record for our stack: broken access control (hiding = decorating), SQL injection (parameterize everything), brute-force login (rate limit + MFA), sensitive data exposure (never in logs, never in responses), and CSRF (token + SameSite on money moves). Naming them with their fix, in order, is a small interview answer that reads as production experience.

SECTION 11 — THE PROTECTED DATA

Data Protection

Three states, three rules. This is the section that catches architects out because "encryption" covers everything until you say the wrong kind for the wrong thing.

Data in Transit

TLS / HTTPS

Encrypt the wire. TLS protects the token, the password, the card and the response — from end to end of the public internet and between services you control. Never let a token or a field travel on plain HTTP.

  • Enforce HTTPS at every endpoint.
  • Internal service-to-service is encrypted as well (TLS, not only network isolation), so a man-in-the-middle within the platform gets nothing.

Data at Rest

Protect Stored Data

Encrypt the data on the storage layer where practical (TDE, SSE), and limit access to it more than you rely on encryption: the real protection is not the cipher, it is the boundary — who may read it, and that the database lives behind private endpoints rather than any public endpoint.

  • Managed platform encryption (Azure Storage, SQL TDE).
  • Fields that must be exact and protected under heavy usage are tokenised (never the full card number; use payment-gateway tokens).
PASSWORDSNever encrypted or plain — hashed with a strong, slow, salted password algorithm (Argon2, BCrypt or PBKDF2 with high iteration). Encryption is reversible (any key leak unlocks everything); a strong password hash makes brute force expensive on every guess. A leaked password database should be worth nothing, not the keys to the kingdom.
FINANCIAL INFORMATIONNever store the full card number, CVV or bank secret. Use the payment gateway's token for charges and store the gateway's token + last-four for display. If your database is emptied, there is nothing to sell.
PERSONAL INFORMATION (PII)Find it, name it, limit it: the collection should be minimum needed, access restricted, retention time-bounded, deletion honoured, and every read of sensitive PII audited. GDPR and GDPR-like rules are architecture requirements, not features.
API SECRETSManaged secrets — the exceptions that genuinely must be stored — go to the vault (Section 8), referenced, rotated, and never committed, logged or baked into the image. Anything returned by an external service may be sensitive and stays out of logs even if it is not a "credential".
THE QUESTIONS TO ASK IN EVERY REVIEW

What is in the database that would be a problem if it were leaked, and is it at rest encrypted? · What leaves this database that is plaintext on the wire, and is it HTTPS? · If the codebase were published tomorrow, what would make it beyond a change of credentials? If the answer to the third is anything other than "a rotated password", a secret has leaked into config.

SECTION 12 — THE POSTURE

Zero Trust Thinking

Do not automatically trust something just because it is inside your network. A service inside the perimeter (or inside the cluster, or inside the same VPC) is not trusted until it is authenticated and authorized like anything else. Think of it as the shift from a castle moat to door-by-door verification.

USERSA user on the corporate network does not get a pass. The SSO flow, MFA, and permission checks apply everywhere — location is not proof, it is a signal at best.
APISAn internal API is not trusted because it is reachable only from the VNet. It authenticates callers and checks scopes like any external API — because a breach that reaches one API should not silently reach all of them.
SERVICESA worker calling another internal service does so with a service identity and a permission, not because they sit on the same subnet. The receiver verifies the caller's claim on every call (Section 13).
MACHINES / WORKLOADSPods, VMs, and jobs get their own identities (managed identity / IAM role), with least privilege, not blanket access because they run in the same cluster name.
CLOUD RESOURCESSQL, Key Vault, Blob, the queue — each is accessed with scoped permissions, private endpoints where relevant, and is never treated as "safe because it is ours".
AND THE ARCHITECTURE ITSELFBastion/jump boxes are not security; boundary controls, identity and least privilege are. A perimeter breach should not equal full access.
WHAT IT CHANGES — A MICROSERVICES EXAMPLE

Castled: the API on the "internal" network calls the DB fully — because it is authorised to reach it. Zero-trust: the order service authenticates to the inventory service, presents its own service identity, is authorised for stock.reserve only, and the inventory service rejects everything else. An attacker who reaches the order service does not reach the warehouse or the ledger — because inside ≠ authorized. That sentence is the answer to "why are internal calls also protected."

SECTION 13 — BETWEEN SERVICES

Service-to-Service Security

The morning a service inside your network is asked to do work by another service, the same two questions apply: who is asking, and may they ask it? Most systems never ask either.

  NO AUTHENTICATION SERVICE IDENTITY + PERMISSION
How it works Service A reaches Service B because it can find it on the VNet or the cluster's network. B answers because it is reachable. Service A gets a service token from the identity provider with a defined scope (e.g. create-payment); B validates the token and the required scope before doing work.
A breach of Service A Grants full access to every service it touches, on the strength of being inside the network. Grants only Service A's own scope. The inventory, the treasury and the user database say no.
Answer The network boundary is the security model. The receiver verifies the caller's claim on every call — an authenticated, scoped interaction, not an open door.

Concretely on Azure: the order workflow steps each require what they need — payment.create, stock.reserve, notify.send — and everything else returns 403. Managed Identity issues the token. The receiving service validates the issuer, the audience, the expiry and the scope — exactly like an external client — and can revoke the grant administratively. No pervasive network rule is used as the container's only permit. The caller's certificate is the permit, and it is scoped to the action the caller may take.

THE ONE-LINE RULE

Verify the caller on every connection — internal or external. Services authenticate each other with identity and scope, never because of the subnet they sit on. This is the discipline that stops one door becoming the only door.

SECTION 14 — WHEN IT BREAKS

Security Failure Scenarios

The failure drill. Eight scenarios, the architect's answer to each. Run the drill below, then read the walkthroughs.

FAILURE DRILL — WHAT DOES THE ARCHITECTURE DO?

1

JWT token is stolen

IMPACTAttacker acts as the user until the token expires — short if lifetimes are right, long if not.
RESPONSEShort token lifetime (minutes, not hours) bounds it by default. On suspicion or signal of anomalous use (impossible travel, unusual calls, impossible velocity) the provider revokes the refresh token and sessions at once — because the IdP is an authority, not a pile of state. If a token cancels a session, the provider cancels the token.
2

User role changes mid-session

IMPACTThe user's old token still says the old role — "Support" retains cross-tenant read privileges for up to a token lifetime.
RESPONSEShort token lifetime so an old role dies fast by expiry. For the critical few permissions (support access to PII, admin) the action re-verifies against the role service rather than the claim in the token, so the current role is the decision — not the cached one. There is no clean way around this with long tokens.
3

API key leaks

IMPACTThe external API the key serves is fully exposed until you stop believing it.
RESPONSEThe key lives in the vault, rotated, and never logged. On leak: revoke at the provider, rotate in the vault, redeploy nothing. Meanwhile the app had a managed identity for its own resources, so losing one external API is a contained problem, not a cascade of stored credentials. Alert on anomalous use coming from the leaked key path.
4

One tenant tries another tenant's data

IMPACTA curious script changes a tenant id from 88 to 92 in the URL.
RESPONSENo exception thrown, nothing readable: the URL tenant id never decided anything. The tenant id from the token is the one the query is scoped by (Section 5 and 7). On attempt, the request is denied, and — because it is a deliberate cross-tenant attempt — an audit log is written and alerted on. An attacker who lands on your platform should not find every tenant at one address.
5

Login attacked repeatedly

IMPACTTens of thousands of password guesses a minute against your login endpoint, grinding the database and probing accounts.
RESPONSERate limiting on the endpoint (by IP, and by identity where you have one, and by progressive difficulty), an alert on anomalous login patterns, MFA on all accounts, and a lockout policy that tightens as attempts rise. Brute force under a throttle gets one guess in a hundred of free attempts, and an hour's worth of slow, boring failure on every account you own.
6

Secret accidentally in logs

IMPACTA support engineer or text search of logs now has the credential — and so does the vendor hosting the log archive.
RESPONSEYour logging does not let it exist: tokens, connection strings, and sensitive fields are masked or omitted at the logging boundary. The byte value exists only in the vault, never in log traffic. If it sneaks through anyway, rotate the credential and alert — and treat the log store as sensitive data in its own right: encrypted at rest, limited access, retention bounded, and its own audit.
7

External identity provider is unavailable

IMPACTThe IdP is outside your control — new tokens cannot be issued, so logins fail for everyone at once with no workaround.
RESPONSEExisting valid tokens are honoured until expiry (the users already proven keep working for the lifetime). New logins are visibly and honestly failed ("sign-in unavailable"). Critical operations — payments, orders, inventory — are never held hostage to a token refresh they cannot perform, so the system degrades on the login path and keeps running for the users already inside. And it is your insurance: the IdP's SLA is a dependency you name and fail over from.
8

Service account has excessive permissions

IMPACTA small identity credential runs admin-everything: a breach of any one worker is a breach of the crown.
RESPONSELeast privilege on every service identity, written from the declared contract (payment.create, stock.reserve, notify.send) — not a convenience grant at platform level. The answer to Section 13 applied here: revoke the excessive permission without redeploying the app, using vault-side RBAC, and log what requested for each call. When the permission scope is precise, privilege degradation is another recovery plan.
THE PATTERN

Every one of the eight is contained the same way: a short evidence clock (short tokens, refreshed, checked on critical actions) · a density of brakes (rate limits, lockouts, MFA) · a write-everything-down habit (audit log, alert, revoke with the owner named) · and everything sensitive behind least privilege and a vault so nothing in code or logs is worth stealing. There is no magic architecture, just 11 controls above, and the discipline to use all 11, not a polite four.

SECTION 15 — CASE STUDY

The SaaS, Secured — Multi-Tenant E-Commerce

Same multi-tenant e-commerce SaaS. Security architecture, decision by decision: why this · what risk it reduces · what the trade-off is.

1 · AUTHENTICATION

Who proves you are?

DECISIONEntra ID (or Cognito in AWS) for login, MFA, SSO with OIDC for identity and OAuth 2 for access — never custom auth.
RISK REDUCEDHomegrown token systems, stored password funk, lockout logic — all removed.
TRADE-OFFThe IdP is a dependency (Section 14 #7 has the answer) — its SLA and failure path are designed around, not wished away.
2 · AUTHORIZATION

What may each user do, and whose?

DECISIONRole claims (Admin/Manager/Employee/Support) in the token, tenant id as a claim, and the API re-checks role + tenant on every request — the IdP states, the API decides.
RISK REDUCEDBroken access control hiding as decoration; role boundaries inside a company are structural, not only in colour.
TRADE-OFFA tiny latency and code signing tax per request — a fractional cent against a global breach if the answer were "it's hidden in the SPA".
3 · TENANT ISOLATION

One tenant's view of another is zero

DECISIONTenant id from the token only, never the request body or the URL as truth; global query filter + SQL RLS at the data layer; tenant in every cache key; jobs and reports scoped per tenant.
RISK REDUCEDCross-tenant leaks via URL tampering, cache collisions, background job overflows, shared report buckets.
TRADE-OFFA shared key must be carefully tenant-scoped (more keys), and each new service must prove it honours the filter — enforced by one owner and a test in CI, not by code review hope.
4 · API SECURITY

Eight guards at every entrance

DECISIONHTTPS (HSTS, CSP), token validation + auth on every endpoint, input validation, rate limiting by identity and IP, request size limits, secure headers, audit logging on every state change.
RISK REDUCEDBroken access control, SQL injection, brute force, token theft, unbounded payloads, missing sector audit.
TRADE-OFFConvenience: validation and limits are strict enough to say no to some legitimate requests, which you tune over weeks, not silence.
5 · SERVICE-TO-SERVICE

Between parts, verified always

DECISIONOrder flow steps call each other with Managed Identity + specific scopes (payment.create, stock.reserve, notify.send) and nothing else; everything else is 403; lack of scope is the default.
RISK REDUCEDLateral compromise from one compromised worker — one soul, crown jewels.
TRADE-OFFFive more tokens in the diagram, and a permissions register that is now part of the architecture's life — the permissions are in the runbook, not a developer's notebook.
6 · SECRET MANAGEMENT

The code has nothing to publish

DECISIONEvery secret in Key Vault; every Azure access via Managed Identity (app → SQL, app → Vault, worker → Service Bus); rotation is a vault operation, not a release.
RISK REDUCEDConnection string committed to repo, secrets leaking into CI logs, password aliases on the team's screenshots.
TRADE-OFFVault availability and setup — you connect to the vault, which means you already pay for a foundational trust object — reused across all services.
7 · DATA PROTECTION

If the database leaves you nothing to sell

DECISIONHTTPS everywhere (transit), TDE/platform encryption at rest, passwords hashed with a slow salted algorithm, full card numbers never stored — gateway tokens only, last-four for display, PII minimised and audited.
RISK REDUCEDPII exposure, credential leaks through config, plain reversible card numbers in storage.
TRADE-OFFYou say no to some product wants — no "store the card for 1-click", unless PCI is a business requirement and its cost is accepted and written.
8 · LOGGING & AUDITING

What can be proven

DECISIONStructured logs with correlation id; notification/store entries with tenant id; every state change audited (role change, price change, permission change, sensitive read); never log tokens, cards, PII fields or raw SQL with values. Retention time-bounded and access limited.
RISK REDUCEDThe first forensic question ("who did this, when?") is answerable; the last sensitive field never reaches the log archive.
TRADE-OFFThe log store itself becomes sensitive (Section 14 #6), so its retention, access and encryption are decided too — clean here, not a convenience dump.
9 · RATE LIMITING

When a crowd arrives, only some are welcome

DECISIONLogin: rate limit + lockout + MFA. Every API: per-tenant rate limit so one company cannot consume the shared pool, and per-IP uncapped so a botnet cannot become twenty companies. Alert thresholds on anomaly against normal per-tenant baselines.
RISK REDUCEDBrute force, background-jobs-run-amok, fake tenants as DDoS cover.
TRADE-OFFA small number of legitimate users hit the limit during a burst and get a short retry — a smaller, deliberate harm any user can count instead of a DDoS you cannot count at all.
10 · FAILURE HANDLING

When the things that protect you, break

DECISIONShort token lifetime so expiry is enforcement. Revocation in the IdP for revokeable suspicions. Login outage degrades the login path without losing in-flight users (Section 14 #7). Secrets rotate instantly per the vault. Support/PII access logged and alerted. Over-permitted identities revoked administratively per Section 14 #8.
RISK REDUCEDFrozen sessions revoking too slowly, leaked keys surviving, account recovery by luck.
TRADE-OFFAn IdP is a dependency, as is the vault — you accept its SLA and you rehearse its failure, and you say the dependency honestly in the diagram instead of quietly forgetting it.
THE LESSON

Notice what is not in the list: a custom auth layer, a "secret store," a shared cache key, a public SQL endpoint, a long-lived token, or an unlogged permission change. Ten decisions, each small and individually safe, each cheap next to the breach it prevents — and the final answer is the pattern: identity from the IDP, authorization and tenant scoping on every request, rate limits by tenant, secrets in the vault, state never in compute, and every permission change, suspicious read and sensitive operation logged and alerted. That is secure, and it is boring, and it is correct.

SECTION 16 — THE LAYER-WITH-LAYERS DIAGRAM

The Security Architecture Diagram

Every layer has a job; every layer checks or enforces one of the two questions. If any layer is empty, the layer below sees what should never have arrived.

USER → ENTRA IDAuthentication happens once with the provider (login, MFA, OIDC) — never in your code.
ENTRA → API GATEWAYThe token's claim travels only as a packet signed by the IdP; the gateway terminates TLS, caps rates and drops malformed or malformed-attacker traffic.
GATEWAY → APIOn every request: valid token? valid issuer? valid lifetime? valid role+tenant? valid action on this resource? If any is no, the answer state is done. This is authorization working, not an endpoint being hidden.
API ↔ SERVICE (A & B)Calls steps ensure each service identity holds only its action's scope — a compromise is a local breach, not a crown.
API → WATER DATARLS at the SQL layer + global query filter + RLS in the in-row SQL itself, plus a same-tenant cache key policy. Isolation enforced at three layers that must all agree.
ALL RESOURCES (via MANAGED IDENTITY + VAULT)The app signs in as itself to each resource; the vault hands any third-party exception credentials directly to the identity — they never touch the source repo.
AND THE RUNBOOKEvery authentication/re-auth, every authorization denial, every sensitive read, every role/permission change and the rate-limit pattern is logged and alerted on. The architecture always knows what the arbiter saw.
SECTION 17 — DECISIONS

10 Security Questions an Architect Should Ask

Q1

Who can access this system?

WHY IT MATTERSExternal users, internal support, partner integrations — each gets a different registration model and a different trust level. A system designed for consumers that support access locks external users out.
DECISIONList the actor types up front: customers, internal admin/support, partner APIs, internal services. Give each an access model and a reason.
Q2

How is identity verified?

WHY IT MATTERSThe identity provider is the foundation everything stands on; a fragile or homegrown one is a breach mortgage.
DECISIONUse the IdP (Entra/Cognito), OIDC for identity, OAuth for access, MFA for key accounts — no home-made authentication unless the reason can absorb on the CIO, not merely.
Q3

How are permissions checked?

WHY IT MATTERSThe only question is: which layer decided, on which field, and how we know?
DECISIONRole+tenant scoped permission on every request, in the API, validated by test and review — never by the UI.
Q4

How are tenants isolated?

WHY IT MATTERSOne tenant's global breach is a hundred tenants' data leak if no layer defends below the UI.
DECISIONTenant claim filtered everywhere: token as truth + global filter + RLS + cache keys + tenant-prefixed jobs/reports.
Q5

Where are secrets stored?

WHY IT MATTERSThe repo is the internet's history book — one commit is the source's deepest nest.
DECISIONIdentity authenticates to Key Vault of serious exceptions; vault authenticated with Managed Identity; rotation as architecture, not bash.
Q6

What happens if a token or credential is compromised?

WHY IT MATTERSSecrets leak in volume — the question is whether losing one is a week, an logout, or a breach.
DECISIONShort token life, refresh token revocable by provider, suspicious usage alerting, key rotation scrubbed into the runbook.
Q7

How are service calls protected?

WHY IT MATTERSOne worker's breach is the crown's breach if every internal service is trusted because it is inside.
DECISIONManaged identities with declared scopes; zero trust: no automatic calls that do not present identity and permission.
Q8

What data is sensitive?

WHY IT MATTERSWhat needs what protection, and who are you dangling support access over.
DECISIONThe four categories (passwords, financial, personal, api secrets) get their own stores, shapes and standpoint: only what's stored and only what's needed.
Q9

What should be logged — and never?

WHY IT MATTERSThe audit needs to prove action; the log archive must contain nothing to steal.
DECISIONAudit write-every change of state, mask/omit sensitive fields at the log boundary, retention and access limited.
Q10

How do we detect unusual access?

WHY IT MATTERSThe pattern-not-value approach: Suspicious tenant-switching, impossible travel, impossible velocity, and hourly account login galloping — the alarm should fire before support calls.
DECISIONBaseline normal per-scope and alert on divergence: a tenant that was 100 rps and is now 1000 rps overnight, or a user appearing in two countries within a minute — flag, rate-limit, alert, review.
THE POINT

Each of the ten questions has a possible decision the architect writes down, and a trade-off you sign for. "How are tenants isolated?" and "What happens if a token is stolen?" are the two that separate junior talk from architect talk in any interview. If you can have those two conversation-ready with numbers, you are production-ready for the rest of the conversation.

SECTION 18 — HONEST LIST

10 Security Mistakes

Each one is a default someone forgot to design.

01

Building custom authentication unnecessarily

Writing password storage, lockouts, resets and MFA yourself because it feels simple — and then maintaining it forever against the world.

Use the IdP's token, MFA, reset, and updates. Custom auth is a decision to pay, not a decision to be good at security.

02

Checking authorization only in the UI

The admin button is hidden in the frontend, so the developer assumes the endpoint cannot be called — while calling it directly works fine.

Role and permission checks on every request in the API, plus tenant scoping in every query. The SPA is the decoration.

03

Trusting the tenant ID from the client

Reading the tenant from GET /orders?tenant=88 and believing it, so switching the number accesses another company's data.

Tenant id from the token only, never body/query/header; scalar URL is a hint at best that must cross-check against the token claim.

04

Hardcoding secrets

A connection string or a third-party key committed to appsettings.json is a commit that never expires.

Managed identity for the platform's own services; Key Vault for the exceptions; rotate on loss as architecture, not a bash.

05

Giving too many permissions

A support account with blanket read access to PII because a card refusal blocked someone else.

Field-scoped access to selected PII (masked), read-only, with every read audited. Least privilege, every time.

06

Never expiring tokens

If the token lasts a month, a stolen token lasts a month, and role changes take a month to apply.

Short-lived access tokens (minutes) + refresh token revocable, and critical roles re-verified against the role service, not the claim.

07

Logging sensitive information

Booking payloads, tokens, card fields and stack traces with values meet every support analyst and every log vendor.

Mask or omit sensitive fields at the logging boundary; the log archive gets the same care as the database — encrypted, access-limited, boundary retention.

08

No rate limiting

A brute force, a botnet, or one busy tenant bbq's every tenant in the shared pool.

Per-identity, per-tenant and per-IP limits, anomaly thresholds on the endpoint table, and alarm baselines on divergence from normal.

09

Assuming internal services are automatically trusted

Services can call each other "inside" and each gets to ask anything, so one compromised service accesses all of them.

Zero trust, with service identities and declared scopes: order flow does payment.create, stock.reserve, notify.send — everything else is 403.

10

Ignoring security during architecture design

Security is "added later," and by then the tenant boundary, the vault story and the audit pattern are architectural choices to retrofit — painful, incomplete and ugly.

Security as one of the first architecture conversations, just like Day 1's five pillars: identity, tenant isolation, secrets and audit are made on day one — trying to add them later is architectural debt, never a feature.

SECTION 20 — SELF-TEST

15 Scenario Questions

Situations, not definitions. Answer out loud, then reveal.

Q1A user logs in successfully but cannot access the /admin API. Authentication or authorization problem?
Authorization. Authentication succeeded: the user is proven. The API (correctly) denied permission. If the question is "who is it," it is auth; if it is "what may I do," it is authz.
Q2The API gets a JWT in the header. What is the minimum integrated check?
Valid signature (from the issuer's public key) · issuer is our IdP · audience is our API · not expired · and claims sufficient for this action/tenant. Not "a JWT is present" — a valid and sufficient one.
Q3Why should a modern app avoid building its own authentication?
Because it costs: password hashing logic, lockout logic, reset flows, MFA, session reissues, security patches — all redone manually, forever, at the risk of leaks and outages. The provider does that free and keeps it current. Build custom auth only where the reason can be defended to the CIO at a whiteboard.
Q4OAuth vs OIDC — give me the sentence.
OAuth is delegate access: an app can call your API for you without your password. OIDC adds who you are on top: the ID token says this is the user, signed. OAuth grants access; OIDC proves identity — the API uses the access token for authZ, and may use the ID token to know the user.
Q5How does a revoked token actually happen in production?
The provider revokes the refresh token at suspicion — new access tokens stop being issued, existing access tokens expire in minutes. If a token cancels sessions, the provider cancels the token. That is why short-lifetimes matter and revoking is centralised.
Q6One user asks for another user's order by changing /orders/42 to /orders/43. What goes wrong, and how is it prevented?
This is broken access control: the URL identifies a resource; the check must be authorized by tenant on every request — user 42 is not authorized for order 43 unless the tenant id in the token matches. Never URL-driven tenant identification; data scope from the token's tenant id is the lawful filter, and query filters plus RLS enforce it independently of the endpoint.
Q7Side-by-side cache: tenant A and tenant B. How can a shared cache key leak, and what stops it?
A shared key like products:hot means whoever fills the entry first decides what everyone sees — a collision with no exception. Tenant in the key (t:88:products:hot) is the fix in Day 5. Tenant in the cache is not a feature — tenant in the key is a security control, like tenant in the query.
Q8A developer accidentally commits a connection string to GitHub. What does the architecture do?
The committed secret is already dead — its lifecycle is in Key Vault, which means rotate the secret there, in minutes, with no release needed. The codebase contains nothing else of brand value, because secrets are referenced by vault name and the platform's identity does the work. Review why it happened and enforce the commit hook.
Q9Why can you not fix authorization in the UI alone?
The UI is one client of many, and not the security model. Every request still calls the API, and the API must decide on the server, per request, per action, per tenant — on every endpoint, including internal ones. The SPA is one decoration. The rules live in the API and the data layer.
Q10What is zero trust, in one concrete example?
Do not trust because of location — identity and scope are both proved on every call. A worker in the same cluster or VNet has to present a service token with a defined scope (payment.create, stock.reserve) and the receiver checks issuer, audience, lifetime, scope each time — no bare handedness because of the address.
Q11Explain why passwords must be hashed, not encrypted.
Symmetric encryption is reversible: if the key leaks, every reverse is a clear password. A strong, slow, salted password hash makes brute force expensive per guess and produces no key to unlock everything — a leaked password database is dead weight, not a roadmap.
Q12If Azure Entra ID is down, what happens — and what is your answer before it happens?
Existing valid tokens are honoured until expiry — the users already approved can finish. New logins fail honestly ("sign-in unavailable"). Critical operations are never hostage to a refresh they cannot carry out, which means payment and order flows keep moving on existing users while the login path degrades — and the provider's SLA is a dependency you rehearse against, not neglect.
Q13A support engineer needs to access a customer's order data to help. How do you allow it with the least harm?
Give them read-only access to the fields they need (masked for sensitive ones), via a narrowly scoped claim, with every read audited — not read-write, not the full customer record, not the full tenant list, and never card numbers. The absolute maximum that can be seen is the answering-as-part-of-a-ticket minimum, and the audit log says who saw what and when.
Q14A teammate says "Rate limiting is security." 9/15 — defend it or correct it.
Defend by correcting the boundary: rate limiting is one security control, not security itself. It stops brute force, botnets and noisy tenants among the entry points — but it trusts the frontend never passes, the front door never forgets, and the system-wide security still needs auth, authz, tenant isolation, secrets, input validation, secure headers, audit, anomaly detection and data protection. The answer is a sentence, not the castle.
Q15The interviewer asks, "What is the little-known key security control of multi-tenant systems?" — one sentence.
Allow Access is not a filter you remember — it is five layers with the same coat: token claim as truth, authorization on every request and every action, a global query filter / row-level security in every data path, tenant-scoped cache keys, and jobs and reports scoped per tenant. If any one of the five are different, the coat comes off.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 11

Five rules. Not jargon — the questions you answer before you draw the box.

01

Identity is verified once, by the provider. Authorization decides on every request, by you.

Authentication and authorization are different chairs in the same meeting. An IdP vouches; the API and data enforce; the difference is how one user accidentally owns every resource.

02

Never trust the client. Never trust the URL. Verify the token.

The browser, the request body, the network — they are all allowed to suggest and never allowed to decide. The tenant id and the identity live in the signed token, everything else is decoration.

03

Multi-tenant isolation is five layers with the same coat.

Identity claim, query filter, RLS, cache key, job/job/reports. If isolation lives in the UI, tenant B has already seen tenant A at a URL you forgot about.

04

State never lives in the compute. Secrets live in the vault. Identity is a permission.

The code contains nothing to publish, the app is the identity, everything else is fetched by it. A related string that appears only in one of these rooms is the one façade to audit.

05

Rate limits, audit, alerts — the brakes are as important as the engine.

Because it is not "if" it breaks — it is "when." Brute force, stolen token, leaked key, IdP down, over-permitted identity: the numbers are the mitigation, the owner is the accountability, and written persistence beats every cleverness.
