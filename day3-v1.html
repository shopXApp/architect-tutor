SECTION 01 — THE FIRST RULE

Choose the Data Design Based on the Business Problem

The most expensive mistake in data architecture is picking a database because it is popular, then reshaping the business to fit it.

An architect does not start with "SQL or NoSQL?" — they start with "What does this business actually need from its data?" Eleven questions to answer first:

TYPE OF DATAStructured rows with strict columns (order lines, invoices), or flexible documents (user profiles, product catalogs with different attributes per category), or simple key-value pairs (sessions, caches)? The shape of data points to the shape of storage.
DATA RELATIONSHIPSHow many things are connected to each other? A customer → order → items → payment → invoice chain screams relational. Independent documents — blog posts, log entries — do not. Relationships decide joins; joins decide databases.
READ VS WRITE USAGE95% reads, 5% writes → a caching and replica strategy. Heavy writes (IoT sensors, click streams) → the write path must be optimized, perhaps with a document or time-series store. The ratio decides the architecture (Section 7).
DATA SIZE & GROWTH10 GB or 10 TB? 500 new records a day or 5 million? The current size is vanity; the growth rate is destiny. It decides when the first database cracks, whether partitioning enters the room, and when backups become a project of their own.
TRANSACTION NEEDSDoes a business operation span multiple tables and must either all succeed or all fail? If yes — that is the definition of a transaction, and it points toward ACID (Section 3). If no — eventual consistency and denormalization are on the table.
CONSISTENCY NEEDSAfter a payment, must the balance reflect it instantly (banking) or is a second of delay acceptable (social media likes)? The answer decides strong vs eventual consistency (Section 4) — and consistency decides the database.
REPORTING NEEDSWill someone run multi-year, multi-table reports with aggregations across millions of rows? If yes, the reporting query should not share a box with the checkout. Heavy reports drive a separate data store (Section 8).
SECURITYDoes the data contain PII, card numbers, health records, or salaries? Compliance rules (PCI-DSS, GDPR) can dictate encryption, retention, and even which database products are allowed in regulated industries. Ask before you draw.
AVAILABILITYIf this database goes down for 5 minutes, is it a nuisance (product catalog) or a regulatory incident (banking ledger)? The tolerance decides whether you need replicas, automatic failover, and — honestly — whether a cheaper option with a known risk is acceptable.
COSTThe number that kills architectures. Cosmos DB charges by RU; managed SQL Server charges by tier; self-hosted charges in engineer-hours. A design whose monthly bill is 5× the product's revenue is wrong — even if every box is technically perfect.
THE PATTERN — SAY THIS IN EVERY INTERVIEW

"I do not start with SQL or NoSQL. I start by asking: what data does this system hold, how is it connected, how often is it read and written, does it need transactions, how much can we tolerate being stale, and what is the cost?" The database choice is the output of these questions — not the input.

SECTION 02 — THE CHOICE

SQL vs NoSQL

Not "which is better." Which one matches the data?

In simple language: a relational (SQL) database stores data in tables with strict columns and enforces relationships and transactions between them. A non-relational (NoSQL) database stores data as flexible documents, key-value pairs, or graphs — and gives up some consistency or relationship enforcement in exchange for speed, scale, or flexibility.

Three options you will actually consider

THE SIMPLEST TEST

Ask: "Can I lose one field of one row and nobody cares?" If no — it is relational. Bank balance: losing one update means theft. Inventory: one lost decrement means overselling. If yes — maybe document or key-value. A user profile with an optional "favorite color" field: who cares?

INTERVIEW ANGLE

When asked "SQL or NoSQL?", answer: "What is the data? What are the relationships? What are the consistency needs?" — then walk through your reasoning. Saying "it depends" is not a cop-out if you follow it with the actual dependencies. That is senior architecture.

SECTION 03 — THE CONNECTED DATA

Relationships and Transactions

Relational databases are strong for systems where data is connected — where one piece of data cannot exist without another, and updating one thing means updating several things together.

The Order Example

Watch a single order flow through four tables:

Creating one order means: insert the order row, insert multiple item rows (one per product), decrement inventory for each product, and insert a payment row. Five operations. They must all succeed or none must — because an order with items but no payment is a promise broken, and an order with payment but no inventory is a lie to the customer.

This is what relationships mean: data that cannot exist independently. And it is what transactions solve: grouping multiple operations into one all-or-nothing unit.

ACID — in plain English

LETTERWHAT IT MEANSWHAT IT PREVENTS
A — AtomicThe whole thing succeeds or the whole thing fails. No middle ground. If the order inserts but the payment fails, the order is rolled back as if it never existed.Half-created orders: items exist but no payment, or vice versa.
C — ConsistentThe database moves from one valid state to another valid state. Foreign keys, unique constraints, and check rules are all enforced — the system cannot be in a "broken" state between operations.Orders pointing to non-existent customers; negative stock; duplicate invoice numbers.
I — IsolatedTwo transactions running at the same time cannot corrupt each other. If two customers buy the last item simultaneously, one succeeds and the other gets "out of stock" — never both, never neither.Double-spending: two orders both decrementing the same last item and both succeeding.
D — DurableOnce a transaction commits, the data is written to disk and survives a crash. The database does not "forget" your payment when the power goes out three seconds later."I paid but the order disappeared after the server restarted."
THE SIMPLEST ACID EXAMPLE

Transfer $100 from Account A to Account B. Atomic: both the debit and the credit happen, or neither does — never debit without credit. Consistent: the total money in the system stays the same. Isolated: if someone else transfers from A at the exact same millisecond, the database serializes them. Durable: once the transfer confirms, a power outage does not undo it. Without ACID, money disappears. With ACID, it does not.

WHAT GOES WRONG WITHOUT TRANSACTIONS

A customer places an order. The order row is created. The payment starts. The payment fails. Without a transaction: the order exists but the payment does not — a phantom order. The warehouse ships it, the customer never paid, the company loses money. Transactions are not a technical feature. They are a business guarantee written into the database engine.

SECTION 04 — THE SPREAD OF TRUTH

Consistency

When one part of the system changes data, how quickly should other parts see that change? The answer is not "immediately always." The answer is "it depends on what the data means."

STRONG CONSISTENCY REQUIRED

Bank balance

WHATAccount shows $500. User spends $100. The next page must show $400 — not $500, not "loading."
WHYA wrong balance means the user spends money they do not have, or sees money they do not own. Both are financial and regulatory failures.
ARCHITECT ANSWERRead from the write master immediately after writing. No replicas for balance queries. The user waits an extra 5ms — they already waited 3s for the page, nobody notices.
⇒ STRONG CONSISTENCY: READ FROM THE MASTER. THE USER WAITS. THE TRUTH IS CORRECT.
STRONG CONSISTENCY REQUIRED

Product stock

WHATLast item in stock. Two users check out simultaneously. Only one must succeed.
WHYIf both see "in stock" and both order, one order is broken. Overselling damages trust and costs real money in refunds.
ARCHITECT ANSWERStock checks and decrements run on the write master with row-level locks. The second transaction waits for the first, sees "zero stock," and fails cleanly.
⇒ STRONG CONSISTENCY: LOCKED DECREMENT ON THE MASTER. THE SECOND USER SEES "OUT OF STOCK."
EVENTUAL CONSISTENCY ACCEPTABLE

Social media likes

WHATPost shows 1,047 likes. I like it. My friend sees 1,047 for a few more seconds, then 1,048.
WHYBeing three seconds behind on a like count is invisible to the experience. Forcing every like through the master at 10,000 likes per second is expensive and unnecessary.
ARCHITECT ANSWERWrite to the master, read from a replica. The replica catches up within seconds. The user sees a slightly stale number — and does not care. Cost saving: enormous.
⇒ EVENTUAL CONSISTENCY: WRITE TO MASTER, READ FROM REPLICA. THREE SECONDS LATE IS FINE.
EVENTUAL CONSISTENCY ACCEPTABLE

Notification status

WHATThe notification system marks an email as "sent." The order confirmation page may show "pending" for a few seconds before it shows "sent."
WHYThe email is sent — the user gets it. The status is metadata about an event that already happened. Being wrong for seconds is not a user problem.
ARCHITECT ANSWERNotification status updates happen asynchronously (queue → worker → database). The read path does not wait for it. The truth catches up on its own.
⇒ EVENTUAL CONSISTENCY: THE STATUS CATCHES UP WHENEVER. THE EMAIL ALREADY ARRIVED.
THE PRACTICAL RULE

Money, inventory, and anything irreversible → strong consistency. Everything else → eventual. The cost difference is real: strong consistency requires reading from the write master (the bottleneck); eventual consistency lets replicas serve reads (cheap and scalable). The architect names the consistency per feature, not for the whole system.

INTERVIEW ANGLE

Say this: "I do not choose strong or eventual for the whole system — I choose per data type." Balance is strong, product catalog is eventual, stock is strong, order status is eventual, analytics is eventual. That sentence shows you understand that consistency is a spectrum, not a toggle.

SECTION 05 — MAKING IT BIGGER

Database Scaling

A database handles more traffic in six ways. Not all of them are created equal. An architect tries them in order — because each one costs more than the last.

MOVEPROBLEMSOLUTIONBENEFITLIMITATION
1. Better Queries Slow query scans every row. App waits. Users feel it. Rewrite the query: add a WHERE clause, remove a SELECT *, avoid N+1 loops.Free. Immediate. Often fixes 80% of database pain with a 10-minute edit. Requires understanding what the app actually asks for. Some queries are inherently slow and need structural change, not just a rewrite.
2. Indexes Database reads the whole table to find five rows. Add an index on the columns used in WHERE, JOIN, and ORDER BY.Near-free performance: a query goes from 3s to 30ms. The database engine does all the work. Every index slows writes (the index must update too). Too many indexes = writes crawl. Index on what you actually query, not what you think you might need.
3. More CPU / Memory The database is the bottleneck and queries + indexes are already optimized. Vertical scaling: move the database to a bigger machine. More vCPU, more RAM, faster storage.Zero code change. Boring, reliable, and often sufficient for years. The "scale up" lever. Hard ceiling (there is a biggest box you can rent). Price grows faster than power at the top end. Still one box that can fail (mitigated by standby failover).
4. Read Replicas The write master is overloaded — not just by writes, but by the reads that happen on the same box. Copies of the database that serve reads. The app sends writes to the master, reads to the replicas.Reads scale horizontally — add replicas as needed. The write master exhales. Replication is usually asynchronous and automatic. Replication lag → stale reads (a user reads their own just-written order from a replica that is 2s behind). The app must route reads and writes correctly. More databases to manage.
5. Partitioning One table is too large for efficient queries — even with indexes. The table is 100M+ rows and growing fast. Split the table by a key: by month (partition 1 = Jan, partition 2 = Feb), by tenant, or by range. The engine knows which partition to search.Smaller partitions = faster queries within each one. Old data can be moved to cheaper storage. The table is still one logical table to the app. Queries that span partitions are slower (they hit multiple partitions). Rebalancing partitions is manual. The partition key must be chosen carefully — a bad key makes things worse.
6. Sharding Even with replicas and partitioning, the write master cannot keep up. The data is too big for one box. Split the data across separate database servers: tenants A–M on Server 1, tenants N–Z on Server 2. Each shard is an independent database.No ceiling — each shard is its own database with its own capacity. The write load is distributed, not concentrated. Cross-shard queries become application problems (no JOINs across shards). Rebalancing shards is a project. Backups ×N. Failover ×N. Complexity explodes. Do it last.
THE ORDER MATTERS

Every move after #1 costs more operations, more money, and more complexity. An architect who jumps to sharding before fixing queries and adding indexes is like a doctor who prescribes surgery before checking the patient's temperature. Try 1, then 2, then 3, then 4. Stop when the problem is solved.

For a SaaS, the natural shard key is the tenant: move the noisy ones to their own database, leaving the rest shared. This is called "hybrid" sharding and it is the standard escape hatch for multi-tenant systems that outgrow a single write master.
SECTION 06 — THE TABLE OF CONTENTS

Indexing

An index is a table of contents for your data. Without one, the database reads every row until it finds what you need. With one, it looks up the page number and goes straight there.

Without Index

Full table scan

"Find the order for user john@example.com."

The database opens the Orders table, reads row 1: not John. Row 2: not John. Row 3: not John... row 50,000: found John.

50,000 reads for one answer. This happens every time a user logs in. Multiply by 10,000 concurrent users and the database is reading half a billion rows per minute.

With Index

B-tree lookup

"Find the order for user john@example.com."

The database opens the Email index, does a binary search through ~16 levels (log₂ of 50,000), and finds the exact row pointer.

16 reads for the same answer. That is not a small improvement — it is the difference between a site that works and a site that dies.

Three indexing examples

EXAMPLE 1 · LOGIN

Email lookup on the Users table

QUERYSELECT * FROM Users WHERE Email = 'john@example.com'
WITHOUT INDEXFull table scan on Users. 500K users → 500K row reads per login. Database CPU spikes at peak login time (morning, after lunch).
WITH INDEXEmail column indexed: ~19 levels (log₂ of 500K) → 19 reads. Login is instant regardless of table size.
⇒ COLUMN: Email (unique index). THE MOST COMMON AND CHEAPEST INDEX IN ANY SYSTEM.
EXAMPLE 2 · ORDER HISTORY

Orders by customer, newest first

QUERYSELECT * FROM Orders WHERE CustomerId = 123 ORDER BY OrderDate DESC LIMIT 10
WITHOUT INDEXFull scan, then sort all matching orders by date, then take 10. If the customer has 500 orders, it reads all of them and sorts every time.
WITH COMPOSITE INDEX(CustomerId, OrderDate DESC) → the index has the data pre-sorted for this customer. It jumps to the customer and reads the 10 newest directly.
⇒ COLUMN: (CustomerId, OrderDate DESC). COMPOSITE INDEX: TWO COLUMNS THAT WORK TOGETHER.
EXAMPLE 3 · PRODUCT SEARCH

Products by category, in stock

QUERYSELECT * FROM Products WHERE CategoryId = 5 AND Stock > 0 ORDER BY Name
WITHOUT INDEXScans all products, filters by category and stock, sorts by name. A hot category with 10K products makes this slow every page load.
WITH COVERING INDEX(CategoryId, Stock, Name, Id, Price) → the index contains everything the query needs. The database never touches the actual table — the answer is in the index.
⇒ COLUMN: (CategoryId, Stock, Name, Id, Price). COVERING INDEX: THE ANSWER LIVES ENTIRELY IN THE INDEX.
WHY INDEXES IMPROVE READSThey replace linear scans with tree lookups. A million rows go from 1,000,000 reads to ~20 reads. The difference is not incremental — it is exponential.
WHY TOO MANY INDEXES ARE HARMFULEvery INSERT, UPDATE, or DELETE must update every index on that table. 5 indexes = 5× the write work. The database spends more time maintaining indexes than answering queries. Balance is key: index the hot paths, not every column.
GOOD CANDIDATES FOR INDEXINGColumns used in WHERE clauses, JOIN conditions, ORDER BY, and foreign keys. Especially: email, customer ID, order number, date ranges, status fields that filter results. Index what your queries actually use — not what looks important.
INDEXES SHOULD MATCH ACTUAL QUERIESBefore adding an index, look at the slow-query log. Which queries are slow? What columns do they filter on? Add the index for that query. Then re-check the log. Do not add indexes proactively — add them reactively, one at a time, and measure.
FOR YOUR STACK

In SQL Server, the slow-query log is Query Store or Extended Events. The missing index recommendations are in execution plans. PostgreSQL has pg_stat_statements. Start there — do not guess. The database is telling you exactly which indexes it wishes it had. Listen to it.

SECTION 07 — THE RATIO

Read vs Write Workload

The ratio of reads to writes changes everything — which database you pick, where the bottleneck sits, and what you spend money on. The same "busy system" has three completely different architectures depending on this one number.

Read-Heavy: 95% Reads, 5% Writes

E-commerce browsing, news sites, social feeds

Users browse products, read articles, scroll feeds. Writes (adding to cart, posting a comment) are rare by comparison.

  • Architecture: Cache absorbs 90%+ of reads. Database sees only misses and writes. Read replicas fan out the remaining reads.
  • Bottleneck: Usually the cache (if it misses) or the database write master (if writes concentrate).
  • Money spent on: Cache cluster, CDN, read replicas. The write master is often overkill.

Write-Heavy: 5% Reads, 95% Writes

IoT sensor data, log ingestion, event tracking

Thousands of sensors write readings every second. Reads are rare (dashboards, alerts).

  • Architecture: Queue buffers writes. Time-series or document database ingests. The read path is separate and can be stale.
  • Bottleneck: Database write throughput. Disk I/O. The ingestion pipeline.
  • Money spent on: Write-optimized storage, ingestion queues, and batch processing. Not cache.

Balanced: 50% Reads, 50% Writes

Collaborative editing, real-time chat, trading systems

Every action writes data and someone immediately reads it. The system is constantly changing and constantly being read.

  • Architecture: The write master is the bottleneck. Sharding or partitioning enters earlier. Cache is less useful because data changes too fast.
  • Bottleneck: The write master. Always the write master.
  • Money spent on: A bigger write master, sharding, and distributed consensus mechanisms. This is the hardest pattern to scale cheaply.

E-commerce example — the ratio in action

ACTIONTYPEFREQUENCYARCHITECTURAL IMPLICATION
Product page viewRead~80% of all trafficCache the product. Serve from CDN where possible. DB sees only the first view of each product.
Search / browseRead~10%Search engine (ElasticSearch or SQL full-text). Not the main database.
Add to cartWrite~5%Lightweight write. Cache or lightweight DB. Cart data is temporary.
Checkout / orderWrite~3%Must be ACID on the write master. This is the 3% that matters — optimize it for correctness, not speed.
Payment confirmationWrite~2%External API call + write. Async (queue) if possible. The most expensive 2% of the system.
THE PATTERN

90% of traffic is reads that can be cached. 3% of traffic is writes that must be exact. 7% is somewhere in between. Design the architecture around those three buckets — not around the idea that "everything must be fast and consistent." It does not. And that is a feature, not a compromise.

SECTION 08 — THE REPORT

Reporting and Transaction Data

Heavy reports should not run against the main transactional database. Not because it is technically impossible — because it is economically stupid.

The bad way: reports on the transaction database

A report that scans 50 million rows takes the database CPU from 40% to 100%. For the next 3 minutes, every checkout is slower, every login is delayed, and if the traffic is peaching at that moment, the site tips over. The report is eating the checkout's lunch.

The right way: separate reporting

The main database replicates its data (asynchronously) to a separate reporting database. Reports run there — and nobody shopping notices. The business reason is as important as the technical one:

THE BUSINESS REASON

A report that slows the checkout loses real money during peak hours. The CFO does not care about CPU percentages — they care that revenue dropped 15% between 2pm and 3pm on Tuesday because the finance team ran their monthly report. Separate reporting means reports cost more infrastructure but the checkout never pays the bill. That is the architecture decision: pay for a reporting box instead of paying in lost revenue.

PRACTICAL APPROACH

Start simple: one read replica doubles as a reporting database. As reporting grows, move to a dedicated database (or a data warehouse like Azure Synapse / Snowflake). The ETL (extract-transform-load) pipeline copies data on a schedule — hourly, daily — so reports work on data that is a few hours old. For most business reports, that is perfectly acceptable. Real-time dashboards for operational data can read from a separate, optimized store.

SECTION 09 — THE MULTI-TENANT QUESTION

Multi-Tenant Database Design

A SaaS product serves 10,000 companies and 1 million users. Every company must see only its own data — never another company's. How do you store it?

Three approaches. Each has a different cost, different risk, and different scaling story.

 SHARED DB · SHARED TABLESSHARED DB · SEPARATE SCHEMASEPARATE DB PER COMPANY
What it looks like One database. One set of tables. Every row has a TenantId column. One database. One schema per company (e.g., dbo.company_a, dbo.company_b). Tables are structurally identical but physically separated by schema. One database per company. Company A has its own SQL instance. Company B has its own.

One noisy tenant can still affect others via resource contention.Each company scales independently. Noisy Company A does not affect Company B. Move big companies to their own server.

Best use case Startups, small SaaS, price-sensitive markets, 10–500 tenants. Use a global query filter (e.g., EF Core's global filter) to enforce TenantId everywhere. Mid-market SaaS where some tenants need their own tables for compliance, but not their own database. 500–2,000 tenants.Enterprise SaaS, regulated industries, large tenants with custom SLAs. 1,000+ tenants with automation. The "whale" strategy.

Recommendation for 10,000 companies / 1 million users

THE PRACTICAL ANSWER

Start with shared database, shared tables. Here is why: 10,000 separate databases is an operations nightmare that costs real money every month. The shared model is cheap, manageable, and correct — if you enforce tenant scoping in one place (a global query filter, a base repository, a database view). Use SQL Server's Row-Level Security (RLS) to add a hard guarantee at the database level — not just the application level.

Then add a trigger: when a single company generates >10% of total traffic or demands physical isolation for compliance, move them to a separate database. This is the "hybrid" model — shared for the 9,990 small companies, separate for the 10 whales.

INTERVIEW ANGLE

Do not say "separate database per company" for 10,000 tenants. That is the answer of someone who has never managed 10,000 databases. Say: "Shared tables with row-level security and a global tenant filter. One place enforces the rule. When a tenant outgrows the shared model, they graduate to their own database." That answer shows cost awareness, operational reality, and a growth path.

SECTION 10 — WHEN THINGS BREAK

Data Failure Scenarios

An architect does not design for the happy path. They design for the day everything goes wrong. Seven scenarios, seven responses.

SCENARIO 1

Database becomes slow

SIGNResponse times climb. p95 goes from 200ms to 2s. CPU is high but not 100%. Connections are saturated.
RESPONSECheck the slow-query log first (one bad query can cost more than the whole app tier). Add missing indexes. If writes are the bottleneck, scale the write master up. If reads, add a cache or read replica. Measure before buying servers.
⇒ SLOW QUERY LOG → INDEX → CACHE/REPLICA → SCALE UP. IN THAT ORDER.
SCENARIO 2

Database becomes unavailable

SIGNAll queries fail. The application throws connection errors. Everything stops.
RESPONSEIf there is a standby replica with automatic failover (SQL Server Always On, Azure SQL auto-failover): it takes 30–60s and the app reconnects. If not: manual restore from backup (hours of downtime). The architecture answer is always have a standby — even if it is a simple log-shipped copy on another server. For the app: a degraded mode ("browse only, cannot order") using cached data is better than a white error page.
⇒ STANDBY WITH AUTOMATIC FAILOVER + DEGRADED MODE IN THE APP. NO EXCUSES.
SCENARIO 3

One table becomes very large

SIGNQueries that used to be fast slow down. Indexes grow. Backups take longer. The table is 500M+ rows.
RESPONSEPartition the table by a natural key (date, tenant, region). Move old data to cheaper storage (archive table, blob storage). Create summary tables for historical queries. The app does not need to know — partitioning is transparent to queries that filter on the partition key.
⇒ PARTITION → ARCHIVE OLD DATA → SUMMARIZE. KEEP THE HOT TABLE SMALL.
SCENARIO 4

One company generates huge traffic

SIGNCompany X has 50% of all orders. Their reports slow down the shared database for everyone else.
RESPONSEThis is the trigger for tenant-level sharding: move Company X to its own database. The rest stay shared. Implement rate limiting per tenant to prevent any single tenant from monopolizing resources. Add tenant-level quotas. The architecture scales by graduating noisy tenants, not by rebuilding everything.
⇒ RATE LIMIT PER TENANT → GRADUATE NOISY TENANTS TO THEIR OWN DATABASE.
SCENARIO 5

Reports slow down the application

SIGNCheckouts slow down during report hours. The monthly sales report scans millions of rows on the transaction database.
RESPONSESeparate the reporting workload (Section 8): replicate data to a reporting database or data warehouse. Reports run there, not on the transaction database. If this is not feasible immediately, schedule reports during off-peak hours (2am, not 2pm). But the permanent fix is architectural separation.
⇒ REPORTING SEPARATION. PERMANENT FIX > SCHEDULING TRICKS.
SCENARIO 6

A transaction fails halfway

SIGNOrder is created, payment starts, payment times out. The order exists but is unpaid. The inventory was not decremented.
RESPONSEThe database rolls back the partial transaction (ACID). The order should not exist at all — it was never committed. The application catches the timeout and shows the user "payment pending — please try again." If the payment eventually succeeds via retry, a compensating transaction creates the order. For cross-service transactions (microservices), use the Saga pattern with compensating actions.
⇒ TRANSACTION ROLLS BACK → ORDER NEVER EXISTS → USER RETRIES. COMPENSATING ACTIONS FOR MICROSERVICES.
SCENARIO 7

Data is accidentally deleted

SIGNSomeone ran DELETE FROM Orders WHERE... and forgot the WHERE clause. Or a buggy migration drops a column.
RESPONSEThe immediate answer is a point-in-time restore from backup (RPO decides how much data is lost). But the architect designs to prevent this: soft deletes (IsDeleted flag instead of actual DELETE), database-level permissions that prevent DROP/DELETE for non-DBA accounts, audit logs of who ran what, and automated backups tested monthly (a backup you have not tested is a backup that does not exist). In SQL Server, temporal tables keep history of every change.
⇒ SOFT DELETES + PERMISSIONS + AUDIT LOGS + TESTED BACKUPS. ALL FOUR.
SECTION 11 — THE DECISIONS

10 Architecture Decisions

Ten real questions, ten decisions. Each in the format: Question → Options → Recommendation → Why → Trade-off. The pattern you will use in every architecture meeting and every interview.

DECISION 01

SQL or NoSQL for the core system?

QUESTION — The main system handles orders, payments, inventory, and users. Data is connected and transactions are mandatory.

RECOMMENDATION

SQL (SQL Server or PostgreSQL). The core is transactional with connected data — the exact pattern relational databases were built for.

WHY

Orders → items → payments → inventory is a chain of relationships where partial updates are unacceptable. ACID is not a nice feature here; it is the business requirement.

TRADE-OFF

Schema rigidity. Adding a new data type requires a migration. For the core, this is acceptable — core data does not change shape every week.

DECISION 02

One database or multiple databases?

QUESTION — Should orders, products, and users all live in one database, or should each have its own?

RECOMMENDATION

One database to start. The relationships between orders, products, and users mean cross-database joins would be required for many queries — which is slow and complex.

WHY

One database means one transaction, one backup, one set of connections. The cost of splitting (distributed transactions, eventual consistency) is not earned until traffic demands it. Separate databases add complexity before the complexity pays rent.

TRADE-OFF

One database is a single point of failure and a single bottleneck. But with a standby replica, read replicas, and proper indexing, these are managed risks — not show-stoppers.

DECISION 03

Read replica or not?

QUESTION — The database is at 70% CPU and 85% of queries are reads. Should we add a read replica?

RECOMMENDATION

Yes. A read replica offloads 85% of the current traffic from the write master. The replica catches up via asynchronous replication and serves reads at near-zero cost to the master.

WHY

When the read:write ratio is this skewed, the replica is the cheapest scaling move. The write master drops from 70% to ~15% CPU, buying years of headroom for write growth.

TRADE-OFF

Replication lag → some reads are 1–2 seconds behind. The app must route critical reads (order confirmation, balance) to the master and casual reads (product list) to the replica. Routing discipline adds code complexity.

DECISION 04

Shared tenant database or separate?

QUESTION — For 10,000 tenants, should data be in one shared database or separate databases per tenant?

RECOMMENDATION

Shared database, shared tables, with row-level security and a global tenant filter. One TenantId column enforces isolation at the database level.

WHY

10,000 databases is an operations cost the business cannot afford. Shared tables with RLS provide strong isolation (enforced by the database engine, not just the app) at one-tenth the cost. The trigger to graduate noisy tenants to separate databases is built in.

TRADE-OFF

One noisy tenant can slow everyone else. Mitigated by per-tenant rate limiting and the graduate-on-trigger strategy. Also: the TenantId must be correct on every query — RLS prevents mistakes but does not prevent the query itself from being slow.

DECISION 05

Cache or database for product data?

QUESTION — Products are viewed millions of times per day but change rarely. Should they come from the database or from cache?

RECOMMENDATION

Cache (Redis). Products are the definition of cacheable data: read-hot (millions of views), change-cold (a few price updates per day), and stale-tolerant (a price that is 30 seconds old causes no harm).

WHY

Every product view from cache is a query the database never sees. At 90%+ hit ratio, the database only handles cache misses and writes — a fraction of the original load. This is the cheapest performance gain available.

TRADE-OFF

Cache can go down (Section 6). The cache-down plan: serve from DB with rate limits, accept slightly stale data, and alert on hit ratio. Also: cache invalidation on price changes must be reliable — a wrong price in cache is a customer complaint.

DECISION 06

Main database or reporting database?

QUESTION — The finance team runs heavy monthly reports that slow the application. Should they share the database?

RECOMMENDATION

Separate reporting database, fed by replication from the main database. Reports run there, never on the transaction database.

WHY

Heavy reports and transactions compete for the same CPU, memory, and disk I/O. Separating them means reports cost more infrastructure but the checkout never slows down. The business reason: lost revenue during peak hours costs more than a reporting box.

TRADE-OFF

Reports work on slightly stale data (replication lag). For business reports, this is acceptable (hourly or daily data is fine). For real-time operational dashboards, a separate operational store is needed — but that is a different problem.

DECISION 07

Where should sessions live?

QUESTION — With multiple app servers behind a load balancer, where should user sessions be stored?

RECOMMENDATION

A shared cache (Redis). Not the database (too slow for every request) and not in-memory (lost when the server dies). Redis is fast (~1ms), shared across all servers, and expires cleanly.

WHY

Sessions are the definition of stateless-app data: every request needs them, they are temporary, and losing them means the user logs in again — which is an acceptable failure. Redis handles this natively with ASP.NET Core's distributed session provider.

TRADE-OFF

If Redis goes down, all users are logged out. This is acceptable because sessions are temporary — users simply log in again. Do not use Redis for permanent data.

DECISION 08

How should the system handle soft deletes?

QUESTION — Should the system actually DELETE rows, or mark them as deleted (IsDeleted = true)?

RECOMMENDATION

Soft deletes for core business data (orders, customers, products). Hard deletes for temporary data (cart items, session data, cache entries).

WHY

A deleted order cannot be restored from a backup without downtime. A soft-deleted order is one UPDATE away from being alive again. Also: audit requirements often mandate keeping a history of everything, even "deleted" things.

TRADE-OFF

Soft-deleted rows accumulate and slow queries if every query must filter WHERE IsDeleted = 0. Mitigated by: filtered indexes (only index active rows), periodic archiving of old soft-deleted data, and partitioning (active vs archived partitions).

DECISION 09

Should audit history be in the main database?

QUESTION — The system must keep a history of every change: who changed what, when, and what was the old value.

RECOMMENDATION

Separate audit tables in the same database for real-time access, with periodic archiving to cheaper storage. Or, for heavy audit loads, a separate audit database.

WHY

Audit data is write-heavy (every change writes an audit row) and read-rarely (only during investigations or compliance checks). Keeping it in the main database means audit writes compete with transaction writes. A separate table or database isolates the load.

TRADE-OFF

Audit data in the same database is easier to query and manage, but adds write load to every transaction. Separate audit storage means cross-database queries for audit investigations. For most systems, separate tables (same database) is the sweet spot.

DECISION 10

When should we shard?

QUESTION — At what point should the system be sharded across multiple databases?

RECOMMENDATION

Not until the write master is at 60%+ sustained CPU even after: indexes are optimized, cache is in place, read replicas are added, the master is scaled to the largest practical tier, and partitioning is in use. Then, and only then, shard by tenant.

WHY

Sharding is the most complex scaling move: it adds operational cost ×N, eliminates cross-shard JOINs, requires rebalancing, and changes the fundamental architecture. Every move before it is simpler and cheaper. Sharding is the last resort, not the first idea.

TRADE-OFF

Waiting too long to shard means the system degrades under load. Sharding too early means paying complexity costs for a problem that does not exist yet. The trigger (60% sustained on the biggest practical master) keeps the decision honest.

THE MAIN LESSON

Every database decision has a cost and a trade-off. There is no free option — only the option whose cost the business can afford and whose trade-off the architect can defend. The architect names both in every meeting, every interview, and every design document.

Step 2 — Transaction Requirements

Which operations must be atomic?

THE ANSWER

Checkout: create order + create order items + decrement inventory + create payment — all or nothing. This is the one non-negotiable transaction in the system.
Inventory update: decrement must be atomic. Two orders buying the last item cannot both succeed.
Company creation: create company + create admin user — transactional but rare, so complexity is low.
Everything else: can be eventual. Product updates, notifications, audit entries — they do not need ACID.

Step 3 — Database Choice

SQL or NoSQL for the core?

DECISION — SQL (SQL Server) for the core system.

WHY

Orders → items → payments → inventory is a chain of relationships where ACID is non-negotiable. The checkout transaction spans four tables and must be atomic. Relational databases are the only technology that guarantees this naturally.

SECONDARY STORE

Products (flexible schema, read-heavy, different attributes per category) → MongoDB or SQL Server with JSON columns. Audit history (write-heavy, append-only) → separate audit database. Notifications (temporary, fire-and-forget) → queue + lightweight store.

Step 4 — Tenant Strategy

DECISION

Shared database, shared tables, with row-level security. Every table has a TenantId. SQL Server's RLS enforces that a query from Company A cannot see Company B's rows — at the database engine level, not just in the application code. Step 10 — Main Risks

  • R1 — Cache down: the shield falls, the database meets the full read load. Mitigation: cache-down plan with rate limits and stale serving.

SECTION 14 — SELF-TEST

10 Scenario-Based Questions

No definitions. No memorization. Each question describes a real situation — and asks you to choose, explain, and defend. Say your answer out loud before opening the model answer.

Q1A system handles user profiles, product catalogs with different attributes per category, and order processing with payments. Which database(s) do you choose?
Two databases. SQL (SQL Server or PostgreSQL) for orders, payments, users — the data that needs ACID transactions and relationships. MongoDB (or SQL with JSON columns) for the product catalog — flexible schema, read-heavy, different fields per category. The rule: match the database to the data shape and consistency needs, not to one database for everything.
Q2The checkout must update inventory, create an order, and process payment. If any step fails, what must happen?
The entire operation must roll back — no order created, inventory not decremented, payment not processed (or refunded if it already went through). This is an ACID transaction: all or nothing. For the payment specifically, if it already charged, a compensating refund must fire. The database guarantees the rollback; the application must handle the refund.
Q3A product page shows stock = 1. Two users checkout simultaneously. What prevents both from buying the last item?
Row-level locking on the inventory row during the transaction. The first checkout acquires a lock, decrements stock to 0, and commits. The second checkout waits for the lock, reads stock = 0, and fails with "out of stock." This requires reading from the write master (strong consistency) — reading from a replica could show stale stock = 1 and cause overselling.
Q4The database is slow. What do you check first?
The slow-query log. One unindexed query on a hot path can cost more than the entire rest of the system combined. Then check: are the right indexes in place? Are there N+1 query patterns from the application? Is the write master overloaded with reads that should go to a replica? Is there a cache that could absorb reads? The answer is always measure first, fix the worst offender, re-measure.
Q5Should you index every column?
No. Every index slows writes (the index must update on every INSERT, UPDATE, DELETE). Index only the columns that are actually used in WHERE, JOIN, ORDER BY clauses — proven by the slow-query log, not by guessing. A table with 10 indexes is often slower for writes than a table with 3 well-chosen ones. Indexes are a trade-off: faster reads, slower writes.
Q6Heavy monthly reports are slowing down the checkout. What do you do?
Separate reporting from transactions (Section 8): replicate data to a reporting database and run reports there. Temporary fix: schedule reports during off-peak hours (2am). But the permanent architectural fix is separation — because reports will grow, and "schedule around peak" does not scale. The business reason: lost checkout revenue during peak hours costs more than a reporting box.
Q7For 10,000 tenants, should you use one database or one per tenant?
One shared database, shared tables, with row-level security. 10,000 separate databases is an operations cost the business cannot afford. Shared tables with RLS enforce isolation at the database engine level. Add a global query filter in the app as a second layer. The trigger: when a tenant exceeds 10% of traffic or demands physical isolation, graduate them to a separate database. Hybrid model — shared for the many, separate for the whales.
Q8The database write master is at 80% CPU. Read replicas are already in use. What is your next move?
Three options in order: (1) Scale up the write master — bigger machine, more vCPU/RAM. The simplest fix for write-bound workloads. (2) Partition tables — if one table is disproportionately large, partitioning reduces the data each query scans. (3) Shard by tenant — move the heaviest tenants to separate databases. This is the last resort because it is the most complex. Do not add more read replicas — they do not help with writes.
Q9The database goes down. What should have been in place already?
Three things: (1) Standby replica with automatic failover — the database fails over to the standby in 30–60s without manual intervention. (2) Tested backups with point-in-time recovery — if failover is not possible, restore from the latest backup + transaction logs. (3) Degraded mode in the application — serve cached data ("browse only, cannot order") instead of a white error page. The architect designs all three before the first user logs in.
Q10In an interview, someone asks: "How do you decide between SQL and NoSQL?" What is your answer?
"I do not start with the technology. I start with the data: What shape is it? How connected? How often is it read vs written? Does it need transactions? How stale can reads be? How much will it grow? What is the budget?" Then: "Structured + connected + transactions → SQL. Flexible schema + read-heavy → document. Sessions + cache → key-value. Global + low latency → distributed." The database choice is the output of these questions — never the input. And I always name the trade-off of my choice.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 3

Five rules. About data, not databases. The database is the tool — the data is the truth.

01

Start with the data, not the database.

What is the data? How is it connected? How often is it read and written? Does it need transactions? How stale can it be? Answer these first. The database choice follows — it does not lead.

02

Transactions are a business guarantee, not a technical feature.

ACID is not a database setting you toggle on. It is the guarantee that money does not disappear, inventory does not oversell, and orders are not half-created. When partial updates are unacceptable, the database must enforce the all-or-nothing rule.

03

Consistency is per data type, not per system.

Balance is strong. Product catalog is eventual. Stock is strong. Order status is eventual. Likes are eventual. The architect names the consistency per feature — and the cost difference between them is real money.

04

Scale the database in order — never out of order.

Fix queries → add indexes → scale up the master → add read replicas → partition → shard. Each step costs more than the last. Jumping to sharding before fixing a missing index is like ordering a heart transplant for a headache.

05

Every database decision has a cost and a trade-off.

Shared vs separate, SQL vs NoSQL, cache vs database, replica vs not — each choice saves something and costs something else. The architect names both, picks the affordable cost, and writes down the trigger to revisit.
