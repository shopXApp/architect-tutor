SECTION 01 — THE MINDSET

How an Architect Approaches Azure

The trap: starting with the service. The rule from Day 3, applied to a cloud catalogue: the requirement comes first; Azure follows. Ten questions before any service appears on the page.

WHAT PROBLEM AM I SOLVING?State it in one sentence. If you cannot, no service can save you.
WHAT WORKLOAD DO I HAVE?Stateless web API · long-running batch · event-driven bursts · data pipelines. Workload shape picks the compute.
HOW MUCH TRAFFIC?Peak RPS, concurrent users, growth. The numbers from Day 2 — Azure just names the tiers.
HOW IMPORTANT IS AVAILABILITY?99.9% or 99.99%? A number, not a slogan — it decides zones, regions, and the bill.
HOW QUICKLY MUST IT RESPOND?200 ms or 2 seconds changes caching, tiers, and whether a synchronous call is acceptable.
WHAT DATA IS INVOLVED?Relational and transactional → Azure SQL. Flexible and global → Cosmos. Files → Blob. The Day 3 questions, with product names.
WHAT SECURITY IS REQUIRED?Compliance, tenant isolation, secrets, who logs in. Entra ID, Key Vault, Managed Identity only make sense after this.
WHAT CAN FAIL?The same failure walk as always — but now you can also ask "what happens if the region fails?"
WHAT WILL IT COST?A managed service is a monthly commitment. Say the approximate bill out loud before you commit.
WHAT MAY CHANGE IN THE FUTURE?A workload that doubles quarterly, or an AI feature "next year", changes the choice today — without building for it today.
WHY "CHOOSE SERVICES FIRST" IS WRONG

Because a service is an answer to a question you have not asked yet. Choose AKS because "it is powerful" and you have paid for Kubernetes operations, for a workload that needed five App Service slots. Choose Cosmos because it is impressive and you are now managing eventual consistency for a pure transactional order system. The service list follows the requirement list — every time, in that order. An interviewer hears the difference immediately when you say: "before I name a service, let me name the problem."

THE ONE-LINE RULE FOR AZURE

Choose the simplest service that satisfies the requirement — and be ready to say what you rejected and why. That sentence is the whole of Day 8.

SECTION 02 — THE TOOLKIT

Core Azure Services, 90 Seconds Each

Twenty services, five groups. For each: what it does → when to use it → when NOT to → main benefit → main limitation. Cards, not a catalogue.

Compute

AZURE APP SERVICEHosts ASP.NET Core apps as managed web apps with built-in scaling, deploy slots, and HTTPS. Use: web APIs, websites, the classic request-driven app. Don't use: event-driven microbursts, or if you need full container control. Benefit: the least operations of any app host — deploy and forget. Limit: less control than containers; scaling is easy but not fine-grained.
AZURE FUNCTIONSEvent-driven code that runs only when something triggers it — a queue message, a timer, an HTTP call. Use: background jobs, integrations, webhooks, small event handlers. Don't use: a full stateful API with hundreds of endpoints, or long-running processes. Benefit: pay per execution, auto-scales to zero, tiny glue code. Limit: cold starts, execution time limits, awkward for big applications.
AZURE CONTAINER APPSRun containers without managing Kubernetes — scaling, revisions and ingress included. Use: containerised microservices, background workers, anything that wants containers without the cluster. Don't use: single-instance web apps (App Service is simpler) or teams needing full Kubernetes control. Benefit: container portability with managed scaling. Limit: still newer and less battle-tested than App Service for simple cases.
AKS — AZURE KUBERNETES SERVICEA managed Kubernetes cluster. Use: many services, custom infrastructure needs, existing Kubernetes investment, regulated workloads needing fine control. Don't use: because it sounds powerful. Benefit: full control, ecosystem, runs anything containerised. Limit: you operate Kubernetes — upgrades, nodes, monitoring, networking, and a team that understands it. The most expensive compute decision in this list.

Data

AZURE SQL DATABASEManaged SQL Server: automated backups, patching, high availability, and a familiar engine. Use: any relational, transactional data — orders, inventory, finance, tenants. Don't use: flexible schemas or global low-latency reads. Benefit: your SQL Server skills apply directly; the platform runs the DBA work. Limit: vertical scaling on one box; horizontal needs replicas and sharding you design.
AZURE COSMOS DBA globally distributed NoSQL database with multi-model APIs (document, table, graph). Use: globally distributed reads, flexible schemas, high write throughput, serverless-friendly. Don't use: complex relational queries or multi-table transactions — that is what SQL is for. Benefit: single-digit-millisecond reads worldwide, one click multi-region. Limit: RU-based pricing surprises, eventual consistency by default, and a data model you must design around.
AZURE BLOB STORAGECheap, massively scalable object storage for files. Use: images, documents, exports, backups, static assets — anything file-like. Don't use: transactional queryable data. Benefit: pennies per gigabyte, unlimited scale, CDN-friendly. Limit: not a database — no queries, no joins, and access patterns are all-or-nothing per blob.

Networking

AZURE APPLICATION GATEWAYA regional Layer-7 load balancer: routing, TLS, and WAF (web application firewall). Use: routing traffic to your app instances within a region, path-based routing, protecting apps from common web attacks. Don't use: global traffic or multi-region failover (that is Front Door). Benefit: one place for TLS, routing and WAF. Limit: regional — it cannot route across regions.
AZURE FRONT DOORA global entry point: routes users to the nearest healthy region, does global load balancing and failover. Use: multi-region apps, global users, WAF at the edge, CDN-like acceleration for dynamic APIs. Don't use: single-region apps where Application Gateway alone suffices. Benefit: global routing, regional failover, DDoS protection. Limit: costs real money and adds a hop for a single-region app.
API MANAGEMENTA gateway for APIs: a published front door with keys, rate limits, quotas, and developer portals. Use: exposing APIs to external partners, versioning, protecting and monetising APIs. Don't use: your own internal front-end talking to your own back-end — the ceremony is wasted. Benefit: subscription keys, throttling, analytics and a developer experience out of the box. Limit: cost and added latency; overkill for internal-only apps.

Messaging

AZURE SERVICE BUSThe enterprise message broker: queues and topics, sessions, transactions, duplicate detection, dead-letter queues. Use: business workflows needing reliability and ordering — order processing, payment events, anything with a retry/DLQ story. Don't use: fan-out of "something happened" to many listeners (Event Grid), or cheap high-volume job lists (Queue Storage). Benefit: the RabbitMQ you already know, managed, with the reliability semantics from Day 6. Limit: cost and throughput ceilings compared to cheaper options.
AZURE EVENT GRIDA push-based event router: "something happened" notifications to subscribers, from Azure and custom sources. Use: reacting to events — blob created, order placed, resource changed — across many subscribers. Don't use: work that must be reliably pulled by a worker with retries (Service Bus). Benefit: near real-time, huge fan-out, pay per event, almost nothing to operate. Limit: it carries news, not work — short retention, small payloads, no long-lived consumer pulling.

Security

MICROSOFT ENTRA IDAzure's identity service: the user directory and authentication provider. Use: login for employees, customers, and apps; SSO; MFA. Don't use: as a database of application data. Benefit: you never write passwords, sessions, or password-reset flows. Limit: identity modelling for complex custom user types can fight you.
AZURE KEY VAULTThe secrets safe: stores passwords, connection strings, certificates, and keys with access control and rotation. Use: every secret, always. Don't use: config that is not secret. Benefit: secrets leave your code and your config files forever. Limit: must be accessed correctly — it is a vault, not a config service.
MANAGED IDENTITYAn Azure identity for your own app to use when calling other Azure services — no password at all. Use: app → SQL, app → Key Vault, app → Blob, function → Service Bus. Don't use: when the identity must be known outside Azure. Benefit: the cleanest auth in the platform — nothing to store, rotate, or leak. Limit: Azure-internal only.

Monitoring

AZURE MONITORThe platform's telemetry home: metrics, logs, alerts, dashboards, for both Azure resources and your app. Use: infrastructure health, resource metrics, alerting on everything. Don't use: deep application-level insight — that is Application Insights' job. Benefit: one place for all platform signals. Limit: raw platform metrics do not tell you whether a business operation failed.
APPLICATION INSIGHTSApplication performance monitoring: requests, dependencies, exceptions, traces, and live metrics from your code. Use: every production .NET application. Don't use: for infrastructure metrics. Benefit: sees through the whole call: the request, the SQL it ran, the Redis call, the exception, and the queue it published to. Limit: telemetry volume costs money — sample intelligently.
SECTION 03 — THE CHOICE

Azure Compute Options

The most common interview trap on Azure is compute. The answer is almost never "the most powerful one."

OPTION BEST FOR ADVANTAGES LIMITATIONS
App Service Web apps and APIs — the classic request-driven .NET app. Least operations. Deploy slots. Auto-scaling. Built-in HTTPS. Perfect for a single deployable. Less control than containers. Scaling is coarse. Not for event-driven bursts.
Functions Event-driven work: queue triggers, timers, webhooks, small APIs. Pay per execution. Scale to zero. Trivial integration with Service Bus, Blob, Event Grid. Cold starts. Execution time limits. Awkward for large stateful applications.
Container Apps Containerised apps and workers that want scaling without the cluster. Container portability. Managed scaling and revisions. Runs background workers well. Newer platform. More moving parts than App Service for a plain web app.
AKS Many services, custom infra, existing Kubernetes investment, fine control. Full control. The entire Kubernetes ecosystem. Runs anything, anywhere, consistently. You operate Kubernetes — upgrades, nodes, monitoring, networking. A team and a budget, not a choice.
THE LESSON

Choose the simplest service that satisfies the requirement. AKS is not a prize for senior engineers. It is a monthly operations bill you accept only when the requirement genuinely needs it — many services, custom networking, a team that already lives in Kubernetes.

Five scenarios — which compute do you pick?

SCENARIO 1

A single ASP.NET Core web API with a SQL database, one team, standard traffic

CHOICEApp Service.
WHYOne deployable, request-driven, nothing exotic. App Service gives deploy slots, scaling and HTTPS with the least operations. Kubernetes here is paying for a control plane you will never use.
⇒ APP SERVICE. THE SIMPLEST THING THAT WORKS IS THE RIGHT THING.
SCENARIO 2

An order processor that must react to every Service Bus message within seconds, with bursts

CHOICEA worker on Container Apps — or a Function with a Service Bus trigger.
WHYEvent-driven, bursty, needs to scale with the queue. Functions scale per message and cost nothing when idle; Container Apps if you want the full control of a containerised worker.
⇒ FUNCTIONS OR CONTAINER APPS — NOT A WEB APP HOST.
SCENARIO 3

Twelve microservices, three teams, each deploying independently, custom networking

CHOICEAKS — or carefully considered, Container Apps.
WHYTwelve services with independent deploys and custom networking is exactly the scale where Kubernetes earns its bill — if the team knows it. Container Apps is the honest alternative when the team does not want to operate a cluster.
⇒ AKS IF THE TEAM LIVES IN IT; CONTAINER APPS IF NOT.
SCENARIO 4

A background job that sends daily emails and generates reports — once a night

CHOICEA Function on a timer, or a scheduled Container App job.
WHYRuns minutes a day. Pay-per-execution beats a permanently running server. A Function timer is the simplest; a Container App job if the job is heavy and containerised.
⇒ FUNCTIONS — DO NOT PAY FOR A SERVER THAT SLEEPS 23 HOURS A DAY.
SCENARIO 5

A small internal tool for 50 users on the company network

CHOICEApp Service (or even a single VM if there is a strong reason) — not containers, not Kubernetes.
WHYFifty users do not need autoscaling or a control plane. The cheapest, simplest host that runs the app is the answer. Over-engineering starts exactly here.
⇒ THE SMALLEST THING THAT RUNS IT. NOTHING MORE.
SECTION 04 — DATA

Azure SQL or Cosmos DB?

Same decision as Day 3, with product names attached. The seven deciding questions do not change.

  AZURE SQL COSMOS DB
Relationships Joins, foreign keys, relational integrity — the order → items → payment chain is native. Denormalise or assemble in code. Relationships are your problem.
Transactions Full ACID across tables. Money-safe. Atomic within a partition key only; multi-document transactions are limited.
Scale Vertical mostly; replicas for reads; sharding is your design. Horizontal by design — partition keys, unlimited throughput.
Global distribution Replicas and failover exist but are heavier to operate. One-click multi-region writes with single-digit ms reads.
Read/write patterns Excellent for both, with caching and replicas. Excellent for high write volume and hot reads by key.
Data structure Strict schema, migrations, reporting-friendly. Flexible documents — schemaless by design.
Consistency Strong by default. Eventual by default; strong is available at a cost.

Five business scenarios

1

Order processing with inventory and payments

CHOICEAzure SQL.
WHYACID transactions across orders, items, inventory and payments are non-negotiable. Cosmos cannot give you the same guarantee across documents.
2

A product catalog with different attributes per category, updated by many editors

CHOICECosmos DB (or SQL with JSON columns).
WHYFlexible documents match a catalog where electronics have voltage and books have ISBN. No migration per new category.
3

A global app with users in 15 regions and single-digit-millisecond reads

CHOICECosmos DB.
WHYMulti-region distribution is exactly what Cosmos was built for. SQL Server's geo-replication is heavier and costlier to operate.
4

An HR system with salaries, departments, and reporting — exact and auditable

CHOICEAzure SQL.
WHYComplex relationships, exact values, and audit queries. The report must add up; eventual consistency is unacceptable.
5

IoT sensor readings: millions of small writes, few reads

CHOICECosmos DB (or a time-series store).
WHYMassive write throughput with key-based reads is Cosmos's sweet spot. SQL would struggle and cost more for this shape.
THE DECIDING SENTENCE

Connected + transactional → Azure SQL. Flexible + global + write-heavy → Cosmos. And the honest note: most business systems put the transactional core in Azure SQL, and add Cosmos or Blob only where the shape demands it — not because it is a more impressive name.

SECTION 05 — THE PATH

Azure Networking — Who Does What

Three services, three jobs. They sound similar; they solve different problems — and the interview loves this exact question.

FRONT DOORGlobal. Routes each user to the nearest healthy region, fails over if a whole region dies, and can accelerate dynamic APIs with its edge network. When: multi-region apps, global users, or regional failover requirements. When not: a single-region internal app — Application Gateway alone is enough.
APPLICATION GATEWAYRegional. The front door inside one region: path-based routing to services, TLS termination, WAF for common web attacks, and scaling within the region. When: you need routing and a WAF inside your region. When not: cross-region failover — it does not do that.
API MANAGEMENTA developer-facing gateway: subscription keys, rate limits and quotas, versioning, and a developer portal. When: exposing APIs to external partners, monetising APIs, or controlling who calls what. When not: your own web app calling your own API — the ceremony is waste.
THE ONE-LINE DIFFERENCE

Front Door picks the region. Application Gateway routes inside it. API Management lets other developers in. Three doors, three keys, three purposes. If an interviewer asks "Front Door or Application Gateway?", the answer is "for what job?" — and then you name the three jobs.

SECTION 06 — SECURITY

A Secure Azure Architecture

The goal: application code contains no passwords, no secrets, no connection strings. Everything is either an identity or a reference to a vault.

AUTHENTICATION VS AUTHORIZATIONAuth: proving who you are — Entra ID issues a token after login. Authorization: deciding what that identity may do — the app checks the role and tenant on every request, on the server. Hiding a button in the UI is not authorization.
MANAGED IDENTITYThe app itself gets an identity in Entra ID. When the app calls SQL, Key Vault or Blob, Azure authenticates it — no password to store, rotate or leak. The most underused and most valuable Azure security feature for .NET apps.
KEY VAULTEvery secret lives in Key Vault: connection strings, API keys, certificates. The app fetches them at startup (or uses references) using its Managed Identity. Rotation is a vault operation, not a code release.
ROLE-BASED ACCESSRBAC everywhere: who may read Key Vault secrets, who may deploy, who may touch production SQL. Least privilege — every identity gets exactly the permissions its job needs, nothing more.
WHY SECRETS MUST LEAVE THE CODE

Code is copied, committed, reviewed, shared and leaked. A connection string in appsettings.json that is committed once is a credential that has left the building forever — even if it is later removed, the history keeps it. Key Vault + Managed Identity is not a convenience: it is the difference between a leak that matters and a leak that is just code.

SECTION 07 — MESSAGING

Service Bus vs Event Grid

Day 6 taught the difference between carrying work and carrying news. Azure names the two: Service Bus carries the work; Event Grid carries the news.

  SERVICE BUS EVENT GRID
Carries Work — a job that must be done: "send this email", "reserve this stock". News — a fact that happened: "order created", "blob uploaded".
Reliability Durable queues, retries, dead-letter queues, sessions, duplicate detection. The Day 6 story, managed. Built-in retries then dead-letter — but no long-lived consumer pulling work.
Consumers One worker (or a competing group) takes each message. Many subscribers each receive a copy of every event.
Example Order Service → Service Bus → Background Worker — exactly one worker must process the order flow. Order Created → Event Grid → Notification + Analytics + Audit — many services react to the same fact.
Choose it when Work must be done reliably, once, with retries and dead-lettering — payment processing, notifications, inventory. Many listeners must react fast — webhooks, fan-out, integrating Azure platform events.
THE ONE-LINE RULE

One consumer must do the job reliably → Service Bus. Many consumers must hear about it → Event Grid. And the common pattern: Event Grid tells, Service Bus does — the order event fans out to interested services, and each service that has real work to complete puts it on its own Service Bus queue.

SECTION 08 — MONITORING

Knowing the System Is Healthy

Day 6's rule, applied to Azure: asynchronous failure is invisible — instrument it or it does not exist. For a production .NET app, the monitoring stack is Application Insights inside Azure Monitor, and it answers five questions.

LOGSStructured logs with correlation ids — every request carries one id through the API, the SQL call, the Redis call and the queue message, so one order is traceable end to end in a single query.
METRICSRequests per second, response time (p50/p95/p99), error rate, dependency duration, queue depth, cache hit ratio. Numbers with thresholds, not vibes.
REQUEST FAILURES5xx rate, exceptions by type, failed dependencies. A rising failure rate on one endpoint is a deploy gone wrong — and it should page before customers do.
RESPONSE TIMEp95 and p99 per endpoint, not the average. The average hides the users who suffer; the p95 is the user experience, and a drift in p95 is the first sign of a bottleneck.
DEPENDENCY FAILURESEvery external call — SQL, Redis, Service Bus, the payment provider — tracked for duration, success rate and timeout. When the payment gateway is slow, you see which of your calls is slow and how much it costs your p95.
ALERTSAlert on symptoms, not just outages: error rate above 1%, p95 above the target, queue depth growing, DLQ depth above zero, cache hit ratio falling, DB CPU sustained. Every alert needs an owner and a runbook.
WHAT A PRODUCTION .NET APP MUST HAVE

Application Insights SDK wired into ASP.NET Core (it tracks requests, dependencies and exceptions for free) · a custom telemetry initialiser adding the tenant id and correlation id · structured logging to Azure Monitor Logs · dashboards for the five categories above · and alerts for: error rate, p95, queue depth, DLQ depth, DB DTU/CPU, cache hit ratio, payment gateway failure rate. If a metric has no alert, it is decoration.

THE INTERVIEW SENTENCE

"I know the system is healthy when I can answer three questions from a dashboard: how many requests failed in the last hour, what the p95 is per endpoint, and how deep the queues are — and when every one of those has an alert with an owner."

SECTION 09 — CASE STUDY

Multi-Tenant E-Commerce SaaS on Azure

Built step by step, from simplest to the full shape. For every service: why this · what problem it solves · what we rejected · the trade-off.

DIMENSION FIGURE DIMENSION FIGURE
Companies (tenants) 10,000 Concurrent users 10,000
Registered users 1,000,000 Peak requests/sec 5,000
Daily active 100,000 Clients Web + mobile
Features login · catalog · search · orders · payments · inventory · notifications · reports · audit · background processing
Constraints external payment provider · high availability · future AI features
STEP 1

The simplest shape that could work

CHOICEApp Service (one API) + Azure SQL + Blob for images + Application Insights.
WHYOne deployable, one relational database, files in Blob. This is the Day 6 "honest minimum" — and it already serves a lot of this traffic with the right tiers.
REJECTEDAKS, microservices, Cosmos, Service Bus — nothing has earned them yet.
TRADE-OFFOne deployable means one release train and a shared database — fine at the start, and the seams for splitting later are already the modules.
⇒ START BORING. THE FIRST ARCHITECTURE SHOULD EMBARRASS NOBODY AND COST LITTLE.
STEP 2

Scale and protect the request path

CHOICEApplication Gateway in front of App Service (auto-scaling, multiple instances, TLS, WAF). Add Front Door when a second region or global users arrive.
WHYThe API is stateless, so instances scale out cheaply. The gateway gives one entry, TLS and WAF — and the web tier becomes replaceable.
REJECTEDFront Door now — single region, the global door is not yet needed.
TRADE-OFFA gateway is an extra hop and an extra cost; it buys routing, WAF and clean scaling.
⇒ STATELESS APP + GATEWAY + AUTOSCALE. THE DAY 2 PLAYBOOK, WITH AZURE NAMES.
STEP 3

Add caching

CHOICEAzure Cache for Redis — catalog reads, sessions, permissions, dashboard aggregates — with TTLs, invalidation, and the cache-down plan from Day 5.
WHYThe catalog is read 50× more than written; the database is the bottleneck we protect. Redis is the shared copy across all app instances.
REJECTEDIn-process memory only — N servers would have N versions of the truth.
TRADE-OFFStaleness windows and a new failure mode — with the rate-limited fallback and hit-ratio alarms from Day 5.
⇒ REDIS FOR THE HOT, FORGIVABLE, CHANGE-COLD DATA. THE DAY 5 RULES, UNCHANGED.
STEP 4

Add messaging and background processing

CHOICEService Bus for the order flow — payment, inventory, notification, invoice — consumed by a worker (Container Apps or a Function per queue). Outbox pattern from Day 6: order + outbox row in one SQL transaction, a dispatcher publishes.
WHYThe checkout returns in ~40 ms; bursts become backlogs with numbers; failures retry then dead-letter with alerts.
REJECTEDEvent Grid for the order flow — it carries news, not work; the reliable-with-retries guarantee belongs to Service Bus.
TRADE-OFFEventual consistency and the whole Day 6 operational burden — queues, DLQs, idempotency, monitoring.
⇒ SERVICE BUS CARRIES THE WORK. EVENT GRID JOINS WHEN OTHER SERVICES NEED THE NEWS.
STEP 5

Secure the whole thing

CHOICEEntra ID for login (with tenant-scoped roles per company) · Key Vault for every secret · Managed Identity for app → SQL, app → Key Vault, worker → Service Bus · RBAC everywhere · private endpoints for SQL and Redis where the network demands.
WHYNo secrets in code, no passwords in connection strings, and the app authenticates to Azure as itself. Tenant isolation enforced at the data layer with RLS + global query filters (Day 3), with the tenant id in the cache key (Day 5).
TRADE-OFFVault and identity setup up front — paid back the first time a connection string would have leaked.
⇒ ENTRA + KEY VAULT + MANAGED IDENTITY + RBAC. THE CODE HOLDS NOTHING SECRET.
STEP 6

High availability, reporting, and the future

CHOICEAzure SQL zone redundancy and automatic failover · read replicas feeding a reporting database (Day 3's separation) · Front Door + a second region as the trigger arrives · Blob for report files and exports.
WHYWrites stay safe and single; reads and reports scale separately; the region story is added when the business actually needs it — not drawn on day one.
REJECTEDCosmos for the core (transactions), AKS (no need yet), multi-region active-active (cost not yet earned).
TRADE-OFFEach step is a written trigger away: second region at X% of traffic, sharding at Y% sustained writer CPU, AI features arriving as their own service behind the same gateway.
⇒ EVERY FUTURE MOVE HAS A TRIGGER. THE ARCHITECTURE GROWS ONLY WHEN A NUMBER DEMANDS IT.
THE LESSON OF THE CASE STUDY

Notice the order: boring first, then scale, then cache, then messaging, then security, then resilience. Each step was chosen because a requirement demanded it, and each step names what was rejected. That ordering — and that honesty — is what an interviewer is listening for, far more than the final diagram.

SECTION 10 — THE DIAGRAM

The Architecture, As Text

The shape of the design, drawn in text — the same way you would draw it on a whiteboard. Each connection has a job.

USERS → FRONT DOOROne global address; the user is routed to the nearest healthy region; TLS and DDoS protection at the edge.
FRONT DOOR → APPLICATION GATEWAYThe global door hands to the regional door: path routing, WAF, and traffic into the app instances.
GATEWAY → APP SERVICEThe stateless API scales out behind it. Sessions and cache live in Redis, so any instance serves any request.
APP → AZURE SQLThe transactional truth: orders, tenants, inventory. Accessed with Managed Identity, tenant-scoped queries.
APP ↔ REDISThe fast copy: catalog, sessions, permissions. Cache-down plan and hit-ratio alarms from Day 5 apply unchanged.
APP → SERVICE BUS → WORKERSThe order flow's slow work: payment, inventory, notifications. Outbox, retries, DLQ, idempotency — the Day 6 rules, managed.
WORKERS → PAYMENT PROVIDERThe external dependency, isolated behind the worker — its outages are backlogs, not checkout outages.
SQL → REPORTING DBDay 3's separation: replicas feed a reporting database; heavy reports never touch the transactional box.
ENTRA ID + KEY VAULTWho you are and what you may use. The app holds no secrets.
EVERYTHING → APP INSIGHTSOne place to trace a request, its SQL, its cache calls, its queue message, and its exceptions — end to end.
SECTION 11 — WHEN IT BREAKS

Failure Scenarios on Azure

Same drill as always — failure, impact, response — with Azure-specific failure modes added to the list.

1

Application instance fails

IMPACTNone to the user — one instance out of many.
RESPONSEApp Service restarts it, the gateway stops sending it traffic, the remaining instances absorb the load. The app is stateless, so nothing is lost. Alert: instance health, not a user complaint.
2

Database becomes unavailable

IMPACTCheckout stops; reads that miss the cache fail.
RESPONSEAzure SQL automatic failover to the secondary (~30s) with the app reconnecting. Degraded mode: cached catalog still served ("browse only"), order placement held or queued where possible, and the app tells the truth on screen. RTO decided by the business, tested quarterly.
3

Redis fails

IMPACTSessions and cached reads degrade.
RESPONSEThe Day 5 drill: rate-limited DB fallback, short local tier for the hottest keys, circuit breaker, hit-ratio alert fires first, warm-up before releasing the limiter. A slow minute, not an outage.
4

Service Bus is unavailable

IMPACTThe checkout still returns 40ms — the outbox rows simply wait, because the order is already safely in SQL.
RESPONSEThe dispatcher keeps polling; when the bus returns, messages publish and the backlog drains. Queue depth dashboard shows the truth; alert on depth + age, not on panic.
5

Payment provider is down

IMPACTCharges fail or time out — the gateway is external.
RESPONSETimeout, retry with backoff, dead-letter after N attempts, order state "payment pending", honest customer copy, a fallback payment option if the business offers one. Their outage is a backlog, never a lost order — the Day 4 rules, unchanged.
6

One tenant generates extreme traffic

IMPACTOne company's burst consumes shared capacity — everyone feels it.
RESPONSEPer-tenant rate limits and quotas, tenant-aware cache keys so one tenant's working set does not evict everyone else's, and the Day 3 graduation trigger: a tenant crossing the threshold moves to its own database (and its own Redis if needed).
7

An Azure region becomes unavailable

IMPACTEvery service in that region goes down together — this is the big one.
RESPONSEThe honest architecture answers in order: what is the RPO/RTO the business accepted? If multi-region is required, Front Door fails over to the second region, the database is geo-replicated, and the app is deployed to both regions with the data residency rules respected. If the business accepted single-region (and said so in writing), the response is a well-rehearsed recovery, not a surprise. Saying "we are single-region, and here is why" is a legitimate architect answer; not thinking about it is not.
THE PATTERN

Every scenario follows the same shape: what breaks → what the user sees → what recovers it → what alerts first. If you can walk all seven without pausing, you have passed the reliability part of any Azure interview.

SECTION 12 — THE BILL

Cost Thinking

An architect who cannot talk about money is a developer with a diagram. The rules are simple, and each one is a decision.

DON'T PICK THE MOST POWERFUL SERVICE AUTOMATICALLYAKS vs App Service is a monthly bill difference in the thousands, for the same workload. Power you do not use is not a feature.
COST SHOULD MATCH BUSINESS NEED99.99% availability costs roughly 10× 99.9%. If the business accepted 99.9%, you build to 99.9% and spend the difference on features.
SCALE ACCORDING TO ACTUAL USAGEAutoscaling, scale-to-zero Functions, and rightsizing tiers after measuring. A server that idles at 5% CPU at night is a monthly bill that sleeps.
MANAGED SERVICES COST MORE, BUT COST LESSAzure SQL costs more than a VM running SQL Server — and saves a DBA, patching, backups and failover. The comparison is total cost of ownership, not sticker price.
ARCHITECTURE DECISIONS ARE LONG-TERM COSTSSharding, multi-region, and microservices each add a permanent operational baseline. Every decision in this tutorial carries a monthly number — and you should be able to say roughly what it is.

Five examples where cheaper is better

1

App Service instead of AKS for a single API

WHYNo control plane, no node pool, no Kubernetes operator headcount. The same API runs at a fraction of the monthly cost.
2

Functions on a timer instead of an always-on worker

WHYA nightly report job that runs 20 minutes a day should pay for 20 minutes a day — not for a 24/7 server.
3

Blob + CDN instead of serving images through the API

WHYFiles out of the app and database entirely: cheaper storage, cheaper bandwidth via the CDN, and a lighter app tier.
4

Autoscale down at night instead of paying for peak 24/7

WHYA B2B app used 8am–8pm does not need peak capacity at 3am. Schedule the scale, keep the bill honest.
5

Single region + recovery plan instead of multi-region on day one

WHYMulti-region roughly doubles the infrastructure bill. If the business accepts a recovery-time target measured in hours, buy that instead — and write the decision down with the business.
THE COST SENTENCE FOR INTERVIEWS

"Every service I chose has a monthly number and a reason. I picked the simplest tier that meets the target, I autoscale to actual usage, and I named the trade-off where a cheaper choice means a slower recovery. Cost is a requirement, like latency — I design for it, not around it."

SECTION 13 — HONEST LIST

10 Azure Architecture Mistakes

Each one is a decision made for the wrong reason.

01

Using AKS without a real need

"It is the powerful one" — so a single API gets a Kubernetes cluster, a node pool, and an operations team it never needed.

Choose the simplest service that satisfies the requirement. AKS is earned by many services or a team that lives in Kubernetes.

02

Choosing services before requirements

Cosmos appears because it sounds impressive — before anyone asked whether the data is relational and transactional.

The requirement list comes first; the service list follows. Every service gets a sentence about the problem it solves.

03

Ignoring network design

The app is public, the database is public, the world can reach everything. One exposed SQL port away from a breach.

Private endpoints for SQL, Redis, and the broker; the gateway is the only public door; network isolation follows the trust boundaries.

04

Storing secrets in code

A connection string in appsettings, committed once, is a credential that has left the building forever.

Key Vault for every secret, Managed Identity for every call, RBAC for who may read what. The code holds nothing secret.

05

No monitoring

The app "works" — until the p95 drifts for three weeks and nobody noticed, because nothing alerted.

Application Insights on every .NET app, dashboards for requests/errors/dependencies, alerts with owners and runbooks.

06

No failure strategy

"Azure is highly available" is treated as a fact — so nothing is designed for the day a service or a region fails.

Azure services are highly available platforms; your application still needs failover, degraded modes and a tested recovery. The platform does not replace the design.

07

Ignoring Azure costs

The architecture is technically perfect and the monthly bill is five times the revenue.

Say the approximate bill out loud. Autoscale, rightsize, and choose the tier that meets the actual target.

08

Using Functions for unsuitable workloads

A stateful API with hundreds of endpoints becomes a maze of Function apps with cold starts and time limits.

Functions for event-driven bursts and glue. App Service for the request-driven application. Match the host to the workload shape.

09

Treating Azure services as automatically highly available

"Azure SQL has HA" — so the application has no degraded mode, no connection retry, no tested failover walkthrough.

The platform fails over the database; the application must survive the failover — retry logic, reconnects, and a runbook drill. Test the failover in staging, like everything else.

10

Overcomplicating a simple application

An internal tool for 50 users gets AKS, Cosmos, Event Grid and a saga — because the team wanted to "do architecture properly".

The simplest service that satisfies the requirement. Complexity is earned, one measured pain at a time — the Week 1 rule, still true.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 8

Five rules. Not about Azure — about why Azure follows.

01

The requirement comes first. Azure follows.

Workload, traffic, availability, data, cost, failure — answer those, then name the services. Naming services first is how over-engineered, over-priced systems are born.

02

Choose the simplest service that satisfies the requirement.

AKS is not a prize. Cosmos is not a prize. Every extra service is an extra bill, an extra failure mode and an extra thing to explain. The simplest correct answer is the senior answer.

03

The platform is highly available. Your application is not.

Azure SQL fails over; your app must survive the failover. The region can die; your design must know what that means. Azure removes the hardware problem, never the design problem.

04

No secrets in code. No identity without a role.

Key Vault for every secret, Managed Identity for every call, RBAC for every access. The moment a connection string leaves the vault, the security model has a hole.

05

Every service has a monthly number and a rejected alternative.

If you cannot say what a service costs and what you turned down instead, you have not decided — you have decorated. Cost and trade-offs are part of the architecture, not an afterthought.
