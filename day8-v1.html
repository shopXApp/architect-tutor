SECTION 01 — THE MINDSET

How an Architect Approaches Azure

The wrong way is to begin with "which Azure service should I use?" The right way is to begin with the same ten questions you learned in Week 1 — then let the answers point at a service.

WHAT PROBLEM AM I SOLVING?State the business value in one sentence. A service that solves the wrong problem perfectly is still wasted money.
WHAT WORKLOAD DO I HAVE?Always-on web API? Event-driven bursts? Long-running batch? Each maps to a different compute shape (Section 3).
HOW MUCH TRAFFIC?Numbers, not adjectives. 50 RPS vs 5,000 RPS vs spiky 100,000 RPS are three different architectures.
HOW IMPORTANT IS AVAILABILITY?99.9% = one region is fine. 99.99% = redundant across zones or regions. The difference is real money.
HOW FAST MUST IT RESPOND?Sub-second web? 5-second report? 30-second batch? Latency budget decides sync vs async and caching.
WHAT DATA IS INVOLVED?Structured and transactional? Flexible and global? Unstructured files? This is the SQL-vs-Cosmos-vs-Blob question (Section 4).
WHAT SECURITY LEVEL?PII? Payments? Regulated? The answer decides Entra ID, Key Vault, encryption at rest, and tenant isolation.
WHAT CAN FAIL?Walk the failure path before the happy path. Region, database, cache, gateway, a noisy tenant.
WHAT WILL IT COST?Every service has a meter. Estimate before building — cost is an architecture decision, not an afterthought (Section 12).
WHAT MAY CHANGE?Growth, new regions, AI features later? Choose a service that leaves a cheap path forward, not a rewrite.
WHY SERVICE-FIRST IS WRONG

Picking "AKS" or "Cosmos DB" first is a preference wearing a costume. It makes the business bend to fit the technology. When you start with the ten questions, the service is the output of your thinking — and you can always say which alternative you rejected and why. That sentence, spoken calmly, is what architect interviews hear.

SECTION 02 — THE TOOLBOX

Core Azure Services for a .NET Architect

Not the whole catalogue — the 19 you will actually reach for, each with what → when → when not → benefit → limitation.

Compute

Azure App Service

Compute · PaaS web + API
WHAT IT DOESHosts web apps and APIs; handles the server, patching, and scaling for you. Deploy your code, it runs.
WHEN TO USEAlways-on web/API workloads, the .NET default. Team wants to ship features, not run servers.
WHEN NOTCustom containers with specific tooling, or workloads needing full OS/network control — that is Container Apps or AKS territory.
MAIN BENEFITLowest operational overhead for a standard app; built-in autoscale, slots, easy TLS.
MAIN LIMITATIONLess control — fewer knobs for unusual requirements, and pricing is per-plan not per-container.
COST NOTECheap at small scale; watch the plan tier as you scale out.

Azure Functions

Compute · serverless, event-driven
WHAT IT DOESRuns small pieces of code in response to events (a queue message, a blob, an HTTP call). Scales to zero when idle.
WHEN TO USEBackground workers, webhooks, scheduled jobs, file processing — short, event-triggered work.
WHEN NOTLong-running work (cold starts and timeouts), or a large codebase that wants to be one app, not a thousand functions.
MAIN BENEFITPay per execution; zero idle cost; natural fit for queue → message → worker patterns (Day 6).
MAIN LIMITATIONCold starts, execution time limits, and many functions become hard to reason about as one system.
COST NOTECheapest for low, bursty traffic; expensive if always running hot.

Azure Container Apps

Compute · serverless containers
WHAT IT DOESRuns containers without you managing Kubernetes. Autoscales (even to zero), handles networking and revisions.
WHEN TO USEContainerized microservices, queue-driven workers, APIs that want richer control than App Service but not AKS.
WHEN NOTWhen you need full K8s ecosystem features, or a simple app where App Service is enough.
MAIN BENEFITThe sweet spot between App Service and AKS — containers, autoscaling, and no cluster to run.
MAIN LIMITATIONFewer Kubernetes features; some teams may find it less mature tooling than they would like.
COST NOTEPay per container usage; good middle ground.

Azure Kubernetes Service (AKS)

Compute · managed Kubernetes
WHAT IT DOESManaged Kubernetes: deploys and orchestrates containers, autoscales the cluster, handles control plane.
WHEN TO USEMany microservices, strict multi-tenancy, custom CNI / advanced networking, portability across clouds, mature DevOps on K8s.
WHEN NOTTwo apps and a database — the operational cost is not justified. When Container Apps or App Service satisfies the need.
MAIN BENEFITMaximum control and the whole Kubernetes ecosystem.
MAIN LIMITATIONYou now own cluster operations — upgrades, capacity, monitoring. The most expensive in people-hours.
COST NOTESteady cluster cost + node costs; you pay even when idle.

Data

Azure SQL Database

Data · managed relational
WHAT IT DOESManaged SQL Server: transactions, joins, constraints, backups and high availability handled for you.
WHEN TO USEOrders, payments, users, inventory — connected, transactional data (Day 3's core case).
WHEN NOTFlexible schemas per item, or global multi-region writes — those point to Cosmos DB.
MAIN BENEFITFull ACID, fine-grained scaling tiers, serverless option.
MAIN LIMITATIONScales up more than out; multi-region writes are complicated.
COST NOTEWatch DTU/vCore tiers; serverless for spiky dev workloads.

Azure Cosmos DB

Data · globally distributed NoSQL
WHAT IT DOESMulti-model NoSQL (document, key-value, graph) with global replication and low-latency reads.
WHEN TO USEGlobal apps, flexible schemas, massive read scale, per-region data.
WHEN NOTTight relational joins, strict multi-document ACID, or tight cost constraints (RU pricing can surprise).
MAIN BENEFITOne-click global distribution, single-digit ms everywhere.
MAIN LIMITATIONCost, eventual-consistency-by-default, no joins.
COST NOTERU is a metered, tunable and easy-to-miscalculate cost.

Azure Blob Storage

Data · object storage
WHAT IT DOESStores unstructured files — images, logs, exports, backups — at huge scale and low cost.
WHEN TO USEProduct images, invoice PDFs, audit archives, any file that is not a database row.
WHEN NOTTransactional structured data with relationships — that is SQL, not a file store.
MAIN BENEFITCheap, durable, effectively unlimited, works with CDN.
MAIN LIMITATIONNo query language, no joins — storage, not a database.
COST NOTETiers (hot/cool/archive) let you pay less for old data.

Networking, Messaging, Security, Monitoring

APPLICATION GATEWAYAn L7 load balancer for HTTP(S): routing, TLS, web-application firewall (WAF). Regional — protects the apps in one region.
AZURE FRONT DOORA global entry point and CDN: routes users to the nearest region, global failover, global WAF. Cross-region, not per-app.
API MANAGEMENTA gateway in front of your APIs: auth, rate limiting, versioning, developer portal. Governance, not throughput.
SERVICE BUSReliable messaging with queues, topics, DLQ, sessions. For commands that must not be lost (Day 6).
EVENT GRIDEvent routing — "this happened" fanned out to many subscribers. Fire-and-forget, high throughput, low ceremony.
MICROSOFT ENTRA IDIdentity provider: users, sign-in, SSO, conditional access. Authenticates the human.
KEY VAULTStores secrets, keys, and certificates, with access control and rotation.
MANAGED IDENTITYGives a service its own identity in Entra ID — no passwords, no connection strings in code.
AZURE MONITORThe umbrella for metrics, logs, and alerts across all your services.
APPLICATION INSIGHTSAPM for .NET apps: requests, dependencies, failures, traces. Lives inside Monitor.
THE GROUPING, MEMORIZED

Compute: App Service → Functions → Container Apps → AKS, in order of control. Data: SQL for truth, Cosmos for scale/flexibility, Blob for files. Network: Front Door (global), App Gateway (regional), APIM (API governance). Message: Service Bus for commands, Event Grid for events. Security: Entra (who), Key Vault (secrets), Managed Identity (how services authenticate). Monitor: Monitor (the dashboard), Insights (the app lens).

SECTION 03 — COMPUTE CHOICE

Comparing Azure Compute Options

The rule that will save you money: choose the simplest service that satisfies the requirement. AKS is not the default answer — it is the last answer.

OPTION BEST FOR ADVANTAGES LIMITATIONS
App Service Standard web apps & APIs; the .NET default. Lowest ops, autoscale, staging slots, fast to ship. Least control; less fit for unusual container or network needs.
Functions Event-driven, short, bursty work (workers, webhooks). Pay-per-execution, scales to zero, natural with queues. Cold starts, time limits, sprawl if overused.
Container Apps Containerized services without managing K8s. Containers + autoscale + no cluster ops; the sweet spot. Fewer K8s features than AKS.
AKS Many microservices, advanced networking, multi-cloud portability. Full control, whole K8s ecosystem. Highest ops cost; you own upgrades and capacity.

Your turn — which compute option?

SCORE: 0 / 5
1A standard ASP.NET Core e-commerce API, always running, 5,000 peak RPS. The team wants to ship features, not run infrastructure.
A plain .NET web app with steady traffic. App Service gives you everything with near-zero ops. AKS would add a cluster you have to run for no benefit. Container Apps is a candidate only if you are already containerized. Simplest that satisfies = App Service.
2A nightly report generator, plus a few queue-triggered email workers. Traffic is tiny and idle almost all day.
Short, event-triggered, mostly idle. Functions scales to zero and you pay per execution — an always-on App Service or a K8s cluster would bill you for 23 idle hours a day.
3You have ~8 containerized microservices with queue-driven workers. Your team does not want to manage Kubernetes.
You want containers but not cluster operations — that is exactly Container Apps. It gives autoscaling (including queue-depth scaling) and revision management without a Kubernetes control plane to babysit.
4A platform team running 40+ services with strict network policies, custom CNI, and a requirement to be portable across clouds.
Forty services, advanced networking, multi-cloud portability — now the control that AKS gives you is no longer overhead, it is the requirement. This is the rung where AKS genuinely earns its place.
5A small internal admin tool, used by 20 people, new team, tight budget, no containers yet.
Twenty users, tight budget: App Service on a low tier. Containerizing first would be ceremony with no payoff, and AKS for a 20-user tool would be one of the most expensive decisions on this page.
THE LESSON

AKS appeared once in five scenarios — and only when the requirement was 40 services + custom networking + portability, not when it was merely "lots of users." Traffic alone does not justify Kubernetes. Team size, control needs, and portability do.

SECTION 04 — DATA CHOICE

Azure SQL vs Cosmos DB

Same decision as Day 3, now in Azure terms. It is never "which is better" — it is "what does this data need?"

DECIDING FACTOR AZURE SQL COSMOS DB
Relationships Joins, foreign keys, related tables — its strength. Denormalize or do it in code; no real joins.
Transactions Full ACID across tables. ACID within one partition; cross-partition needs care.
Scale Scales up well, out via replicas/sharding with effort. Scales out effortlessly; autoscaled RU.
Global distribution Single write region; read replicas; multi-region writes are hard. One-click multi-region, multi-master.
Read/write pattern Balanced and write-heavy transactional workloads. Very read-heavy, high-throughput reads.
Data structure Fixed schema, strict columns. Flexible documents, evolving shape.
Consistency Strong by default. Eventual by default; strong comes at a cost.

Five business scenarios

AZURE SQL

Banking transactions & order ledger

WHYAccounts, transfers, order lines — connected, must be ACID, audited. Multi-document consistency is non-negotiable. Cosmos DB would force you to denormalise a money ledger, which is the last thing you want to denormalise.
COSMOS DB

Global e-commerce product catalog

WHYRead-heavy, millions of reads, users on three continents, flexible attributes per category. Single-digit ms reads near every user, global replication, and a flexible document shape — exactly Cosmos DB's pitch. The catalog is not the ledger.
AZURE SQL

Inventory with stock counts

WHYStock must be exact, decremented atomically, and consistent at checkout. Strong consistency + row-level locking = SQL. "Overselling is impossible" is a SQL sentence.
COSMOS DB

User activity feed for a social app

WHYMassive append + massive reads, schema-free event shapes, write-heavy, globally spread. Cosmos DB absorbs the write storm and serves reads near the user. A relational table would choke and require per-user sharding you must build yourself.
AZURE SQL + BLOB

SaaS with transactional core + file attachments

WHYThe transactional core (tenants, orders, permissions) is relational. Files (PDFs, images) do not belong in the database — they go to Blob Storage, which is cheaper and purpose-built. Two services, two jobs, correctly assigned.
THE DECISION RULE

Connected + transactional + strong consistency → Azure SQL. Flexible + global + read/write-heavy at scale → Cosmos DB. Files of any kind → Blob Storage. And a real system may use all three — the shop in this case study does.

SECTION 05 — NETWORKING

Front Door, Application Gateway, API Management

Three services, three different problems. The mistake is treating them as interchangeable.

  THE PROBLEM IT SOLVES KEY DIFFERENCE
Front Door "Users are spread across the world; route them to the nearest healthy region, cache static content at the edge, and fail over when a region dies." Global. The front porch of the whole system.
Application Gateway "Within one region, route /api/orders to one app and /images to another, terminate TLS, and block attack traffic with WAF." Regional, L7 routing and WAF for specific backends.
API Management "My APIs need authentication, rate limits, quotas per tenant, versioning, and a developer portal." API governance and policy, not traffic engineering.
ONE SENTENCE PER SERVICE (INTERVIEW)

Front Door gets traffic to the right region and protects you globally. Application Gateway routes traffic to the right app within a region and protects with WAF. API Management governs your APIs — auth, quotas, versioning. In a real system they can all appear in one request, each doing a different layer's job.

SECTION 06 — SECURITY

A Practical Secure Architecture

Four pieces: Entra ID knows who, Managed Identity lets services authenticate without passwords, Key Vault holds the secrets, RBAC decides who may do what.

ENTRA IDAuthenticates the human and issues a token. The app never stores passwords — it trusts the token. Great for SSO across services and organizations.
MANAGED IDENTITYGives an app its own identity so it can call Key Vault, SQL, Storage without a single secret in code. Access is granted to the identity, not to a password.
KEY VAULTThe one place secrets, keys and certs live — with access control, rotation, and an audit log. Code reads at runtime; developers never paste a secret into a repo.
RBAC (ROLE-BASED ACCESS)Assigns roles so each identity gets the least privilege. A worker that sends email cannot read the orders table. Least privilege = smaller blast radius.
WHY NO SECRETS IN CODE

A secret in source control is a secret that has already leaked — to every clone, fork, backup and laptop. It cannot be rotated safely, and everyone has it forever. Store secrets in Key Vault, authenticate with Managed Identity, and the only thing in code is the name of the secret, not the secret.

AUTHENTICATION vs AUTHORIZATION

Authentication = proving who you are ("this is Priya, and here is my token"). Authorization = what you may do ("Priya is an Admin, so she may approve refunds"). One verifies identity; the other decides permissions. In Azure: Entra ID handles authentication, and roles + policies handle authorization — you can be authenticated and still forbidden from a resource. Both, always. One is not enough.

SECTION 07 — MESSAGING

Service Bus vs Event Grid

One carries commands that must not be lost. The other announces things that happened. Knowing which is which is the whole answer.

  SERVICE BUS EVENT GRID
Message means A command: "do this exactly once." An event: "this happened, in case you care."
Delivery Guaranteed, with retries and DLQ, sessions, ordering. Push to subscribers; fire-and-forget, no DLQ of its own.
Consumers Usually one logical worker (scaled), pulling. Many subscribers, each reacts independently.
Use when Payments, orders, anything that must not be lost or duplicated. Notifications, analytics, "order created → inform N systems."
PLAIN ENGLISH

Service Bus is a courier with a signature required — the message cannot vanish, and failure is reported. Event Grid is a public announcement — everyone who is listening hears it, and if you miss it, that is on you. Commands → Service Bus. Events → Event Grid. They often work together: an event can land in Event Grid and trigger a Service Bus message for the part that must be processed reliably.

SECTION 08 — MONITORING

Knowing the System Is Healthy

An architect does not wait for a customer to report the outage. Signals, always on.

LOGSThe story of what happened — errors, warnings, structured events. In Application Insights: traces and exceptions. Answers "why did this fail?"
METRICSThe numbers over time — CPU, memory, RPS, queue depth, DTU. In Azure Monitor: charts and thresholds. Answers "where are we headed?"
REQUEST FAILURESFailed requests, exception rate, failed dependencies. The first sign a service is sick, often before users notice.
RESPONSE TIMEp95 latency per operation. A rising p95 with flat CPU means a dependency is slowing — the metric that finds hidden bottlenecks.
DEPENDENCY FAILURESCalls to SQL, Redis, Service Bus, the payment gateway — success rate and latency per dependency. Most outages are a dependency in disguise.
ALERTSThresholds that page a human: failure rate > X%, p95 > Yms, queue depth > N, DLQ > 0. Alerts are the monitoring that works while you sleep.
THE .NET PRODUCTION CHECKLIST

Watch all of: request rate and p95 per endpoint · exception rate · dependency success rate and latency (SQL, cache, gateway) · queue depth and DLQ · database DTU/CPU and connection pool · cache hit ratio · memory and GC. And every one of these has an alarm, not just a dashboard — a dashboard tells you what happened, an alarm tells you it is happening now.

MONITOR vs INSIGHTS

Azure Monitor is the umbrella — metrics, logs, alerts across every resource. Application Insights is the app-shaped lens inside it — your requests, dependencies, exceptions and traces, correlated into a single transaction trace. Build the dashboards in Monitor, read the app's behaviour in Insights.

SECTION 09 — THE CASE STUDY

Multi-Tenant E-Commerce SaaS on Azure

10,000 companies · 1 million users · 100K active · 10K concurrent · 5,000 peak RPS · web + mobile · payments · inventory · notifications · reports · audit · background processing · future AI. Build it simplest first.

S1

Assume the load is real, deploy for the happy path

Translate the marketing numbers: 1M registered → 100K DAU → ~50 RPS average → ~2,000 peak RPS, designed with headroom to the stated 5,000. The core is one logical app with clear modules — not yet many services.

WHY SIMPLE FIRSTDelivering working features quickly beats a distributed architecture nobody can operate. Complexity is earned in the later stages, stage by stage.
S2

Compute: App Service, scaled out

The web API is a standard ASP.NET Core app. It runs on App Service — managed, autoscaled by CPU/requests, with multiple stateless instances behind a load balancer (Day 2's stateless rule).

WHY APP SERVICE · NOT AKSOne team, one API, standard .NET. AKS would add cluster ops for zero benefit. Trade-off: less fine-grained control, but the team ships features instead of running nodes.
S3

Data: Azure SQL (core) + Cosmos DB (catalog) + Blob (files)

Orders, payments, inventory, tenants → Azure SQL (ACID, shared tables + row-level security, read replicas). Product catalog (flexible, read-heavy, global later) → Cosmos DB. Images and PDFs → Blob Storage with a CDN.

WHY SPLIT · NOT ONE DBEach data type gets the engine that fits it — the money stays ACID, the catalog scales reads, the files stay cheap. Trade-off: three stores to manage instead of one, but each does its job without contorting.
S4

Caching: Azure Cache for Redis

Hot reads — product pages, category tree, permissions, sessions — served from Redis with TTL and invalidation (Day 5). The cache-down plan: rate-limited fallback + a short local tier.

WHY REDIS · NOT JUST IN-MEMORYMultiple instances need one shared copy and one invalidation point. A per-server cache would give N versions of the truth.
S5

Messaging & background work

Payment and inventory commands flow through Service Bus to Azure Functions workers (idempotent, with DLQ). Order-created announcements fan out via Event Grid to email, analytics, and fraud detection.

WHY SERVICE BUS + FUNCTIONSCommands that must not be lost need a reliable broker; Functions gives pay-per-message workers that scale with queue depth. Trade-off: eventual results (a "confirming payment" state) in exchange for resilience.
S6

Security: Entra ID + Managed Identity + Key Vault

Customers sign in via Entra ID. The app uses Managed Identity to reach SQL, Redis and Storage with no secrets. Secrets live in Key Vault. RBAC enforces least privilege per role.

WHY THISNo passwords in code (Section 6). Tenant isolation is enforced in the data layer (global filter + RLS) — the key is a security boundary, and every query is scoped.
S7

Networking: Front Door + Application Gateway + APIM

Front Door at the global edge (CDN + global failover). Application Gateway routes within the primary region with WAF. API Management governs the API — auth, rate limits per tenant, versioning.

WHY THREE (LATER)They solve different problems (Section 5). For a single-region start, Front Door + APIM is enough; add App Gateway when intra-region routing and WAF are needed. Trade-off: cost and complexity of three hops.
S8

High availability & observability

Everything zone-redundant in the primary region; Azure SQL geo-replication and Cosmos multi-region for data; a warm standby region behind Front Door for the "region is gone" day. Application Insights + Azure Monitor alerts on p95, failure rate, hit ratio, queue depth, DLQ.

WHY THISDay 1's reliability, in Azure form. Trade-off: every extra nine and extra region is real money — the business buys the number, not the engineer.
S9

Future AI, without overcommitting now

Recommendations and search ranking later: keep events flowing to a data store the AI can read, expose a clean API, and pick a compute that can host an inference endpoint when the time comes.

WHY NOT BUILD IT NOWDay 1's rule — do not design for an unconfirmed future. Keep the seams (events, clean APIs) so AI slots in, but do not pay for ML infrastructure you do not yet need.
THE ARC

Nine stages, and every one starts simple and earns its complexity. At no point did the requirement "1 million users" justify AKS or a microservice-per-team architecture. The load justified App Service + Redis + SQL replicas — and that is the correct, honest answer in most interviews.

SECTION 11 — WHEN THINGS BREAK

Failure Scenarios

Each failure → business impact → architecture response. The response is what you built in advance, not what you improvise.

FAILURE BUSINESS IMPACT ARCHITECTURE RESPONSE
Application instance fails Nothing — one instance of many. Multiple stateless instances behind the gateway; health checks remove the dead one; autoscale replaces it.
Database becomes unavailable Orders and payments stop — the worst outage. Geo-replication + failover group; app degrades to read-only or "retry soon"; data never lost.
Redis fails Slower pages, hot keys hit the DB. Rate-limited fallback + short local tier + circuit breaker (Day 5's drill); alarm on hit ratio.
Service Bus unavailable Commands cannot be queued; work backs up. Producer-side outbox pattern — persist the message with the business change, drain when the bus returns. Nothing is dropped.
Payment provider down Checkout cannot complete. Order sits in PaymentPending; worker retries with backoff; user sees honest "confirming" status, never a silent charge.
One tenant generates extreme traffic Shared resources degrade for everyone. Per-tenant rate limits (in APIM), resource quotas, and graduate the noisy tenant to their own DB/Redis (Day 3's trigger).
Azure region becomes unavailable Whole region offline. Front Door fails over to the standby region; data replicated (SQL geo-replica, Cosmos multi-region); RPO/RTO bought in advance.
THE PATTERN

Every response was a decision made before the failure — a replica, a queue, a fallback, a rate limit. None of them are "we will figure it out when it happens." That is the difference between an architecture and a wish.

SECTION 12 — COST THINKING

How an Architect Thinks About Azure Cost

Azure bills what it bills, whether your design was elegant or not. Cost is a first-class architecture constraint.

DON'T AUTO-PICK THE MOST POWERFUL SERVICEAKS and Premium tiers are the most capable — and the most expensive. Capability you do not use is a bill you do not need.
COST SHOULD MATCH BUSINESS NEEDA 99.9% single-region design for an internal tool is correct. Paying for 99.99% multi-region for it is waste. The business defines the number; you match it.
SCALE TO ACTUAL USAGEFunctions scale to zero, serverless SQL pauses, autoscale shrinks the app pool at night. Provisioned-at-peak, paid-at-peak is the anti-pattern.
MANAGED SERVICES COST MORE, OPERATE LESSApp Service costs more per hour than a raw VM — but you do not pay engineers to patch it. Managed is buying time; weigh it honestly.
ARCHITECTURE DRIVES LONG-TERM COSTData egress, hot vs cool storage tiers, RU provisioning, multi-region replication — these are set by architecture and paid every month.
MEASURE BEFORE OPTIMISINGTag resources, read the cost analysis, find the top three spenders. Optimizing the wrong resource is as wasteful as optimizing none.

Five cases where cheaper is better

  • Internal admin tool — App Service low tier, not AKS. The difference pays for the whole team's coffee for a year.
  • Nightly report job — a Function that scales to zero, not an always-on VM burning idle hours.
  • Static marketing site — Blob Storage + CDN, not an app server at all. Static content is nearly free and faster.
  • Dev/test environments — serverless SQL + auto-shutdown by schedule, not production-priced mirrors running weekends.
  • Old audit data — move to cool/archive storage tiers. A third of the cost, and no one queries it daily anyway.
THE COST SENTENCE

"I choose the cheapest service that meets the requirement, scale it to actual usage, and treat every extra nine and extra region as a purchase the business must approve." Say that, and you have answered the cost question before it is asked.

SECTION 13 — HONEST LIST

Common Azure Architecture Mistakes

Ten ways Azure projects go wrong — and each one is a decision made too early or not at all.

01

Using AKS without a real need

Kubernetes feels like the "serious" answer. It is the highest-ops, highest-cost compute for a team that only needed an App Service.

AKS earns its place with 20+ services, custom networking, or real portability needs — not with a big user count.

02

Choosing services before requirements

Picking Cosmos DB or Functions as a "modern" default, then bending the business to fit.

Answer the ten questions first (Section 1); let the service be the output.

03

Ignoring network design

Everything on a public endpoint, no VNet isolation, no WAF — a breach waiting for a scanner to find it.

Private endpoints for data, WAF at the edge, and least-privilege network rules.

04

Storing secrets in code

Connection strings and keys committed to the repo — leaked to every clone and impossible to rotate.

Key Vault + Managed Identity; the only string in code is the name, never the value.

05

No monitoring

The system "works in demos", so nobody wired Application Insights. The first production outage is diagnosed by guesswork.

Lights on day one: request rate, p95, failures, dependencies; alerts on thresholds.

06

No failure strategy

Single region, single database, no fallback — and no plan for the day one of them is down.

Walk Section 11 before launch; every failure has a pre-decided response.

07

Ignoring Azure costs

Dev environments mirror production, storage never tiers, unused resources run all weekend. The bill arrives as a surprise.

Cost analysis from day one, tag everything, tier old data, autoshutdown dev.

08

Functions for unsuitable workloads

A long-running, chatty, or large-codebase workload forced into Functions — cold starts and timeouts and a thousand files.

Functions for short event-triggered work; App Service/Container Apps for long-running or cohesive apps.

09

Treating managed services as automatically highly available

"Azure handles HA" — but a single-region deployment with a single logical database still has a single point of failure.

Managed reduces your work; it does not remove the need for geo-replication, scaling rules, and a recovery plan.

10

Overcomplicating a simple application

Front Door + App Gateway + APIM + AKS + multi-region + Cosmos — for a 50-user CRUD app. The architecture outweighs the problem.

Simplest service that satisfies, then grow. An architecture smaller than the problem is almost always cheaper to run and easier to change.

SECTION 15 — INTERVIEW

15 Architect-Level Azure Interview Questions

Attempt each before revealing the model answer. These are the situations, not the definitions.

Q1Why App Service instead of AKS for a standard e-commerce API?
One team, one .NET API, steady traffic. App Service gives managed patching, built-in scaling and staging slots for near-zero ops. AKS buys cluster control the team does not need and pays for it in people-hours. I would revisit AKS only with 20+ services, custom networking, or portability as a hard requirement.
Q2When would you choose Cosmos DB over Azure SQL?
Flexible schemas, very read-heavy workloads, global multi-region reads/writes, and data without tight relational joins — a product catalog or an activity feed. I would not choose it for a money ledger, because ACID across tables and strong consistency matter more than scale there.
Q3What happens if an entire Azure region fails?
Front Door routes traffic to the standby region; data fails over — Azure SQL via its failover group and geo-replica, Cosmos via multi-region. The recovery is only as fast as the RPO/RTO the business paid for, which is why that trade-off is decided up front, not during the incident.
Q4Why use Service Bus instead of just calling a worker directly?
A direct call blocks the user and couples the caller to the worker's availability. Service Bus decouples them: commands queue safely, retry and dead-letter automatically, and workers scale independently with queue depth. The trade-off is eventual rather than immediate confirmation.
Q5Why use Managed Identity instead of a connection string?
A connection string is a shared secret that leaks and never rotates safely. Managed Identity gives the app its own Entra identity, grants it access to SQL/Storage/Key Vault, and removes the secret entirely. Nothing to paste, nothing to rotate, nothing to steal.
Q6How do you protect secrets in an Azure deployment?
Key Vault holds keys, secrets and certificates with access policies and rotation. Apps read them at runtime through Managed Identity — never from config committed to a repo. RBAC ensures only the identities that need a secret can read it.
Q7How would you reduce Azure cost on a running system?
Find the top three spenders in cost analysis first. Then: right-size compute (scale-to-zero where possible), tier cold storage, autoshutdown dev/test, review RU/DTU provisioning against actual usage, and question any capability — extra regions, Premium tiers — the business does not actually need. Optimise the real spend, not the easy win.
Q8How would you handle 10× traffic?
First, find what saturates — usually the database, not the app. The app tier scales out (stateless), cache absorbs reads, the queue buffers writes, and the database is the one to watch: replicas, then vertical, then partitioning, each with a trigger. The answer is never "add ten more app servers" if the DB is the ceiling.
Q9Where does API Management fit, and what does it actually add?
API governance, not traffic engineering: authentication at the API boundary, per-tenant rate limits and quotas, versioning, and a developer portal. It does not replace a load balancer — it sits on top of the API to enforce policy uniformly, which is exactly what stops one tenant from flattening everyone.
Q10What is the difference between Front Door and Application Gateway?
Front Door is global — nearest-region routing, global CDN, global failover, global WAF. Application Gateway is regional — L7 routing to specific backends, TLS, and a regional WAF. They stack: Front Door gets users to the right region, App Gateway routes within it.
Q11How does a multi-tenant SaaS stay isolated on Azure?
Shared tables with tenant scoping enforced in one data layer (global filter + row-level security), tenant in every cache key, per-tenant rate limits at the API layer, and a graduation trigger — a noisy or compliance-bound tenant moves to its own database or its own resources. Isolation is a boundary defended in depth, not a single checkbox.
Q12How does your architecture recover when the payment provider is down?
The order sits in a PaymentPending state; the worker retries with backoff and an idempotency key so a retry can never double-charge; the user sees an honest "confirming payment" status. No order is lost and no charge is ever duplicated — the two invariants that matter.
Q13What does "serverless" actually buy you, and when is it wrong?
Pay-per-execution and zero idle cost — ideal for bursty, event-driven work. It is wrong for long-running jobs (time limits, cold starts), for a large cohesive codebase better shipped as one app, and for steady always-hot traffic where per-execution can cost more than a reserved plan.
Q14How do you know your Azure system is healthy before users complain?
Alerts, not dashboards: request rate and p95 per endpoint, exception rate, dependency success rate and latency (SQL, cache, gateway), queue depth and DLQ, database CPU, cache hit ratio. A rising p95 with flat CPU is a slowing dependency; a falling hit ratio is an incoming DB spike. The alarm pages a human before the customer pages support.
Q15Walk through how you would explain an Azure cost decision to a CFO.
In business terms, not tier names: "we pay for App Service instead of a Kubernetes cluster because a smaller team ships faster and patches nothing; we run one region because 99.9% costs a third of 99.99%; we move old audit data to cold storage because nobody queries it daily." Each line maps a cost choice to a business outcome — cheaper where possible, premium only where it earns its keep.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 8

Five rules about Azure — which is to say, five rules about choosing anything from a catalogue.

01

The service is the output, never the input.

Ask the ten questions first; the requirement points at the service. If you start with the service, the business bends to fit the tool — and the tool never bends back.

02

Simplest that satisfies.

App Service before Container Apps before AKS. Cosmos only where SQL cannot reach. Every step up the power ladder must be justified by a requirement, not by ambition.

03

Managed buys time, not immunity.

A managed database still needs geo-replication. A managed app still needs scaling rules. Azure removes the labour; it does not remove the architecture decisions.

04

Secrets belong in Key Vault, identities in Entra, nothing in code.

Managed Identity means the connection string stops existing. That is not a nice-to-have — it is the difference between a secret and a string in a repo.

05

Cost is a decision you make, not a bill you receive.

Every tier, region and replica is a purchase. Match it to the business need, scale to actual usage, and say the price out loud before it appears on an invoice.
