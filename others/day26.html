PART 01 — THE MINDSET

Think Like a Production Architect

A system can fail even when every single component looks healthy. Each server says "I am fine." Each dashboard is green. And still, users cannot place an order. This happens because production failures live between components, not inside them.

Think of a busy restaurant. The kitchen is fine. The waiters are fine. The cash counter is fine. But the one person who prints the bill goes home sick. Suddenly nobody can leave, tables do not free up, new customers wait at the door, and the whole restaurant "stops working" — even though almost everything is still working. Production systems fail exactly like this.

The eight ideas you must be able to explain in simple words

DependencySomething your system needs from someone else — a cache, a database, a payment provider. You do not control it, but you die with it if you did not plan.
BottleneckThe narrowest part of the pipe. Everything else can be huge; the system moves only as fast as this one part. Usually it is the database, because it is the hardest thing to duplicate.
Cascading failureOne failure pushes extra work onto the next component, which then also fails, which pushes work further. Like one lane of a highway closing and the whole city jamming.
Sudden trafficLoad that arrives faster than you can add capacity — a campaign, a month-end report run, or thousands of retrying clients. Capacity added in minutes cannot beat traffic arriving in seconds.
Resource exhaustionRunning out of something finite: memory, threads, CPU, database connections, disk. Nothing "crashed" — the system simply has nothing left to work with.
Slow dependencyWorse than a dead one. A dead dependency fails fast and frees resources. A slow one holds your threads and connections hostage while pretending to still work.
Retry stormEveryone who failed tries again at the same second. The system that was already too slow now receives two or three times the traffic. Recovery becomes impossible.
Database overloadThe database is doing more work than it has CPU, memory or IO for. Queries queue, locks grow, everything slows down together — and the database cannot be scaled in 60 seconds.
THE CORE TRUTH OF DAY 26

Healthy components do not mean a healthy system. The system's health lives in the relationships: who depends on whom, how fast they answer, how much they retry, and what happens when one of them disappears. An Architect designs those relationships, not just the boxes.

Two sentences you should be able to say in an interview

One: "Most production outages are not caused by a component breaking — they are caused by the system's reaction to that component breaking." Two: "My job as an Architect is to make sure the reaction is small, controlled, and reversible."

PART 02 — THE CASE STUDY

The Main Incident: Redis Disappears at Peak

This one incident is the spine of the whole day. Everything after this — retry storms, circuit breakers, degradation, recovery — is a reaction to this exact situation.

THE SYSTEM — AS IT LOOKS ON A NORMAL DAY

COMPONENT WHAT IT DOES NORMAL BEHAVIOUR
.NET APIs Serve web and mobile clients for many companies (multi-tenant). 5,000 requests/second, 200 ms average
SQL database The single source of truth: orders, inventory, users, audit. CPU around 45%
Redis cache Holds dashboard data, lookups, sessions, and expensive query results. Absorbs roughly 80–90% of read traffic
Message broker Carries work that can happen later: emails, invoices, sync jobs. Queue depth near zero
Background workers Read from the broker and write results into SQL. Process messages in a few seconds
Reporting system Heavy queries over the same SQL database. Slow but tolerated
10:00 — THE TRIGGER

Redis becomes unavailable. Nothing else changed. No deployment, no traffic spike, no database problem. One cache node stopped answering. In a well-designed system this is a small event. In this system it is about to become a full outage.

The incident, step by step

  1. Redis stops answeringCache reads fail or hang. The API code was written as "try cache, otherwise read the database" — which sounds safe and is about to become the main problem.10:00:00 · nothing looks broken yet
  2. Traffic does not change — but its destination doesClients still send 5,000 requests/second. Before, about 4,000 of those were answered from memory. Now all 5,000 go to SQL. The database's read load grows several times in one second.10:00:05 · SQL read rate 5–10×
  3. Dashboards make it worseThe most-cached data is the most expensive to build: dashboard totals, tenant summaries, product lists. Every dashboard refresh is now a heavy query, repeated by thousands of users.10:00:20 · expensive queries dominate
  4. SQL CPU goes 45% → 95%The database is not broken; it is simply full. Once CPU passes roughly 80%, every query starts waiting for CPU time, so all queries get slower — including cheap ones.10:01 · everything slows together
  5. Response time grows 200 ms → secondsAPI calls hold their thread and their database connection while waiting. The API process is not "crashed"; it is just full of waiting work.10:02 · p95 climbs past 3s
  6. Timeouts beginLoad balancers, gateways and mobile clients give up. Users see errors or spinners. Note the cruel detail: the work still continues inside the database.10:03 · first 5xx / 504 errors
  7. Clients retry — the storm startsMobile apps retry automatically. Users press refresh. Internal services retry three times. Real traffic is still 5,000 RPS, but the system now receives 12,000–15,000.10:04 · load doubles or triples
  8. Background workers slow downWorkers use the same database. They cannot get connections or CPU. Messages stop being processed, the queue grows, invoices and notifications are delayed.10:05 · queue depth rising fast
  9. The system is declared "down"Technically, most services are running. Practically, nobody can complete a single business action. To the business, that is the same thing.10:07 · management escalation
THE ARCHITECT'S FIRST OBSERVATION

Redis failing was the trigger. The database becoming overloaded was the bottleneck. The retries were the amplifier. In the interview, name all three separately — most candidates only name the first one and stop there.

STAGE WHAT IT MEANS IN SIMPLE ENGLISH WHAT YOU WOULD SEE
1 · Redis fails The fast memory shortcut is gone. Every answer must now be re-calculated from the slow source. Cache errors, connection refused, hit ratio drops to 0
2 · Cache misses increase A "miss" means the answer was not in the cache. 10% misses is normal; 100% misses is a different system. Hit ratio 92% → 0%
3 · DB requests increase The database now receives every read that the cache used to absorb. This is often 5–10× more queries. Queries/second graph jumps like a wall
4 · DB CPU increases The database has a fixed amount of CPU. When it fills, it cannot say "no" — it just becomes slow for everyone. CPU 45% → 95%, waits and locks rising
5 · Queries slow down A query that took 20 ms now takes 2 seconds. Nothing changed in the query; only the queue in front of it changed. Slow query log explodes
6 · Requests stay open longer Each waiting API request keeps a thread and a database connection reserved. Waiting is not free — it costs resources. Active requests count climbing
7 · Connection pool fills The pool is a small fixed set of database connections shared by all requests. When all are busy, new requests just wait in line. "Timeout expired. The pool reached maximum size."
8 · Requests time out The caller gives up. The work often keeps running on the server — so you pay the cost and deliver nothing. 504 / 500 error rate rising
9 · Clients retry Apps, gateways and humans all try again — usually immediately, usually at the same moment. Request rate rises while success rate falls
10 · Traffic increases The system is now attacked by its own users. Real demand did not grow; duplicated demand did. 5,000 RPS in, 13,000 RPS measured
11 · DB overloaded Beyond this point, adding capacity slowly does not help. The database can no longer finish work faster than new work arrives. CPU pinned at 100%, everything queued
12 · System unstable APIs, workers, reports and notifications all fail together, because they all shared one exhausted resource. Every dashboard red, business stopped
THE POINT OF NO RETURN

Stages 1–5 are recoverable by reducing load. Stages 7–11 usually need rejecting load — turning traffic away, opening circuit breakers, disabling heavy features. Once retries are amplifying, a system almost never recovers on its own. Someone must take load away from it.

PART 04 — THE EMERGENCY

The First Five Minutes

In the first five minutes you are not solving the problem. You are stopping the bleeding. The goal is a system that is stable and partly working — not a system that is fully fixed.

05:00 INCIDENT DRILL TIMER — READ EACH MINUTE OUT LOUD AS IT PASSES
  1. Minute 0 → 1 · Confirm the shape of the failureThree questions only: Is it everything or one thing? When did it start? What changed just before? Look at four numbers: error rate, response time (p95), requests per second, and dependency health (Redis up/down, SQL CPU). Declare the incident and name one person as incident lead.OUTPUT: "Redis is down, SQL CPU 95%, error rate 12%, started 10:00."
  2. Minute 1 → 2 · Stop the things that add loadPause anything optional that touches the database: scheduled report jobs, bulk imports, data sync jobs, cache-warming loops, analytics exports. Freeze deployments and stop autoscaling more API instances — more API servers means more connections into an already overloaded database.OUTPUT: batch and reporting workload = 0
  3. Minute 2 → 3 · Put a shield in front of the databaseReduce the maximum database connections per API instance, shorten database timeouts (long waits help nobody), and open circuit breakers on the heaviest endpoints so they fail immediately instead of queuing. Failing in 50 ms is kinder to the system than failing in 30 seconds.OUTPUT: SQL receives less work than it can handle
  4. Minute 3 → 4 · Reduce the traffic itselfTurn on rate limits, especially per tenant. Switch off heavy dashboards and large reports behind a feature flag. Serve stale or reduced data where you can. Protect the critical paths — login, order creation, payment, inventory — and let the rest wait.OUTPUT: only valuable traffic reaches SQL
  5. Minute 4 → 5 · Watch the right five numbersSQL CPU, API p95 latency, error rate, queue depth, and connection pool usage. If CPU falls and latency falls together, your protection is working. If CPU falls but errors stay high, you are rejecting too much. Post a clear status update to the business every 10 minutes.OUTPUT: stable, degraded, communicated

What you must NOT do during an active incident

Do not restart everythingRestarting APIs throws away warm state and sends a fresh wave of connection attempts and retries at the database.
Do not deploy a "quick fix"Untested code during an outage adds a second unknown failure on top of the first one.
Do not scale out the API tierMore app servers = more concurrent queries hitting the same overloaded database. You are speeding towards the wall.
Do not increase timeoutsLonger waiting holds threads and connections longer. It hides the error and deepens the queue.
Do not debug root cause firstStabilise, then investigate. Root cause analysis while users are down is expensive curiosity.
Do not let everyone actFive people changing settings at once means nobody knows what helped. One incident lead, one change at a time, announced.
THE PRIORITY ORDER, MEMORISED

1. Protect the bottleneck. 2. Reduce load. 3. Keep critical business flows alive. 4. Communicate. 5. Only then look for the root cause. Saying this order in an interview is worth more than any tool name.

The four instruments — and what each one is for

Logs — what happenedIndividual events with detail. Best for the exact error text and the first occurrence. Weakness: too many lines during a storm. Search by correlation id, not by hope.
Metrics — how much and how fastNumbers over time: CPU, RPS, p95 latency, error rate, queue depth, hit ratio, pool usage. Best for finding when it started and what shape the failure has.
Traces — where the time wentOne request followed across services: 8 s total = 20 ms API + 7.9 s waiting on SQL. This is the fastest way to prove which dependency is the bottleneck.
Alerts — who gets woken upOnly for things a human must act on: error rate, latency, saturation (CPU/pool/queue). If everything alerts, nothing alerts.
THE ONE-LINE DIAGNOSTIC RULE

Ask: "What is everyone waiting for?" If every slow trace ends in the same place, that place is your bottleneck — no matter which component first triggered the incident. Trigger and bottleneck are usually different components, and you protect the bottleneck first.

PART 06 — CACHE FAILURE

Five Strategies When the Cache Dies

Most teams have exactly one strategy — "just read the database" — and that is the strategy that caused this incident. A real Architect chooses per endpoint, based on how expensive the query is and how important the feature is.

SAY THIS CLEARLY IN AN INTERVIEW

Falling back to the database is not automatically safe. It is only safe if the database can absorb the full uncached load. If the cache was absorbing 80% of your reads, then "fallback to SQL" means "multiply database load by five, instantly, with no warning". That is a decision, not a default.

STRATEGY ADVANTAGE DISADVANTAGE USER IMPACT WHEN TO USE
1 · Go straight to the database
"fallback read"		 Simple. Data is always correct and fresh. No code branches. Can instantly overload SQL and turn a cache incident into a total outage. Everything works — until it does not, then nothing works. Only for cheap, low-volume queries, and only with a concurrency limit in front of them.
2 · Return stale or limited data Very cheap. Keeps screens usable. Protects the database completely. Numbers may be minutes old; needs a second store or in-process copy. User sees data with a note: "updated 5 minutes ago". Dashboards, price lists, catalogues, tenant summaries — anything where being a little old is acceptable.
3 · Fail fast Protects the database instantly. Frees threads and connections. Keeps the rest of the system alive. The feature is simply unavailable; looks bad if applied to the wrong thing. Clear message in under a second: "Reports are temporarily unavailable." Expensive, non-critical endpoints during an outage. Always better than a slow failure.
4 · Temporarily disable expensive features Huge load reduction from one switch. Reversible in seconds. Requires feature flags built in advance; business must agree the list beforehand. Some screens hidden or greyed out; core actions still work. Heavy dashboards, exports, analytics, "recalculate everything" buttons.
5 · Use another cache source
local memory / second cluster		 Keeps most reads away from SQL even with Redis gone. Each server has its own copy, so data can differ between servers; more memory and more complexity. Mostly invisible — occasional small inconsistency. Very hot, read-only, small data: config, lookups, feature flags, tenant settings.

How an Architect combines them

The mature answer is a mix, decided per endpoint before the incident: cheap and critical reads fall back to SQL with a concurrency limit; hot lookups fall back to local memory; dashboards serve stale data; reports fail fast. One sentence for the interview: "My cache fallback policy is per endpoint, and its total worst-case load must still fit inside my database capacity."

CACHE STAMPEDE — THE HIDDEN KILLER

When the cache returns, thousands of requests discover the same missing key at the same moment and all run the same expensive query. Protect against it with a single-flight lock (only one request rebuilds a key, others wait or take stale data) and random TTLs so keys do not all expire together.

PART 07 — PROTECT THE BOTTLENECK

Protecting the Database When Redis Is Gone

The database is the one component you cannot duplicate in five minutes. Therefore the database is what you defend. Everything below is a way of saying: let less work reach SQL, and let it arrive in a controlled way.

PROTECTION WHAT IT DOES IN SIMPLE ENGLISH SPEED COST / RISK
Rate limiting Allow only N requests per second per client or per tenant. Extra requests get a polite "try later" instead of joining the queue. Immediate Some users rejected; needs sensible limits or you block real work.
Concurrency limits (bulkhead) Cap how many requests may talk to the database at once, per endpoint. Heavy reports can never take more than, say, 5 connections. Immediate Queues form inside the app; must be paired with fast timeouts.
Caching (restore / local) Bring any cache back — even a small in-memory one — so repeated reads stop hitting SQL. Immediate Slight staleness; memory pressure on app servers.
Query reduction Stop unnecessary calls: remove N+1 loops, batch reads, reduce dashboard refresh frequency, increase polling intervals. Immediate (config) / Long-term (code) Refresh intervals feel slower to users.
Read replicas Copies of the database used only for reads. Reports and dashboards read there; the main database keeps writing orders. Long-term Extra cost; replica data is a few seconds behind.
Request prioritisation Not all requests are equal. Checkout beats dashboard. Give critical paths their own connection budget and let the rest be shed first. Immediate (if built) / Long-term (to build) Requires classifying endpoints in advance.
Circuit breaking When an endpoint keeps failing, stop calling the dependency for a while and fail instantly instead. Immediate (if present) Feature goes dark while the breaker is open.
Timeouts Give up early so a thread and a connection are returned to the pool instead of waiting 30 seconds for a doomed query. Immediate Some long legitimate queries get cancelled.
Limiting expensive reports Queue them, allow one per tenant, restrict them to off-peak hours, or disable them entirely during an incident. Immediate Business users complain — get agreement in advance.
Temporary feature reduction Feature flags switch off heavy screens and non-essential background jobs with one click. Immediate (if built) Must be built and tested before the incident, not during it.
Immediate (today, in the incident)Rate limits · concurrency limits · short timeouts · circuit breakers · feature flags · stop batch and reporting jobs · block the noisy tenant.
Long-term (after the incident)Read replicas · separate reporting database · query and index optimisation · Redis high availability · capacity planning · load testing with the cache switched off.
THE MENTAL MODEL

Think of the database as a door in a crowded building. You cannot make the door wider during the fire. So you do three things: slow the crowd down (rate limit), let the important people through first (prioritise), and tell everyone else to wait outside (fail fast). The door survives, and the most valuable people get out.

PART 08 — THE AMPLIFIER

Retry Storm: When Trying Again Kills You

A retry is a request that the system has already failed to serve once. During an overload, retries are free extra traffic that you generate yourself, at the worst possible moment.

↓

↓
Timeout
↓

↓
More load
↓
More timeout
↓

Why it multiplies so fast

Retries multiply at every layer. The mobile app retries 3 times. The API gateway retries 2 times. The internal service calling another service retries 3 times. 3 × 2 × 3 = 18 attempts for one user action. Now imagine 5,000 users per second doing that. Real demand is 5,000 RPS; the database sees close to 90,000 attempts. The system is being attacked by its own retry policy.

Retry limitsMaximum 2 attempts, and only for operations that are safe to repeat. Never retry a request that already timed out doing heavy work — the work is probably still running.
Exponential backoffWait longer each time: 1s, 2s, 4s. Gives the sick system space to breathe instead of hitting it again immediately.
Random delay (jitter)Add a random 0–500 ms. Without it, all clients retry at exactly the same second and create a synchronised wave.
Circuit breakerAfter enough failures, stop calling entirely for a while. This is the only mechanism that reduces total attempts to near zero.
TimeoutsShort, layered timeouts so a failing call frees resources quickly instead of holding them while a retry is queued behind it.
Client-side limitsMobile and web clients must also back off, disable the button, and show "we are retrying in 10 seconds" instead of letting users hammer refresh.
RETRY IS NOT RECOVERY

Retry only helps when the failure is short and random — a dropped packet, a brief reconnect, one unlucky node. When the failure is overload, retry is the opposite of recovery: it takes a system that is already 20% short of capacity and pushes it 200% over. Retry when the system is healthy but the call was unlucky. Stop retrying when the system is saturated.

The rule of thumb table

SITUATION RETRY? WHY
Network blip, connection reset Yes — 1–2 times with backoff Failure is random and short; a second attempt usually succeeds cheaply.
HTTP 429 / 503 "too busy" Only after the delay the server asked for The server explicitly said it is saturated. Respect it or you make it worse.
Timeout on a heavy query No The work is probably still running on the database. A retry doubles the cost of the same request.
Validation error / 400 Never The request is wrong. It will be wrong forever.
Payment charge attempt Only with an idempotency key Without a key, a retry can charge the customer twice.
Background message processing Yes — with backoff and a dead-letter queue Nobody is waiting live, so slow retries are cheap and safe.
PART 09 — THE SAFETY SWITCH

Circuit Breaker, Explained Like Electricity

In your house, when something goes wrong with the wiring, a switch trips and cuts the power. It is annoying — but it prevents a fire. A software circuit breaker does exactly the same: it cuts the connection to a failing dependency to protect everything else.

  1. What problem does it solve?Without a breaker, every request keeps calling a dying dependency, waiting for a timeout, and holding a thread. Ten thousand slow calls consume your whole application. The breaker converts slow failure into instant failure.
  2. When does it open?When failures cross a threshold in a window — for example, "more than 50% of the last 100 calls failed or timed out". Percentages are better than counts, because they behave the same at 5 RPS and 5,000 RPS.
  3. What happens while it is open?No calls go to the dependency at all. Requests get an immediate fallback: stale data, a reduced answer, or a clear error message. Latency actually improves during this state — failing fast is fast.
  4. How does recovery happen?After a cool-down (say 30 seconds), the breaker goes half-open and allows a small number of trial calls. If they succeed, it closes and normal traffic returns. If they fail, it opens again for a longer period.
  5. Why does it protect downstream systems?It removes almost all load from the sick component so it can actually recover. A database at 100% CPU with 20,000 queued queries cannot recover while you keep calling it. Silence is the medicine.

Applied to our incident

Breaker on RedisWhen Redis stops answering, the breaker opens after a few failures. Now the app stops waiting 2 seconds per cache call and immediately uses its fallback plan. Without this, the cache failure alone would slow every request even before SQL got busy.
Breaker on SQL, per endpointThe dashboard endpoint's breaker opens when its queries start timing out, so dashboards fail instantly and stop consuming connections. Meanwhile checkout — a different breaker, a different budget — keeps working.
The mistake to avoidOne global breaker for the whole database. When it opens, your entire application dies at once, including payments. Breakers must be scoped per dependency and per operation class.
INTERVIEW SENTENCE

"A circuit breaker does not make my system more available on its own. It makes failure cheap, fast and contained — and that is what keeps the rest of the platform alive while one dependency is sick."

PART 10 — TIME BUDGETS

Timeout Design: Waiting Is Not Free

Every call that leaves your process must have a deadline. A call with no timeout is a promise to wait forever — and during an incident, waiting is what kills you.

Here is the physics. One API server can hold, say, 200 concurrent requests. At 200 ms per request it serves 1,000 requests per second. If a dependency becomes slow and each request now takes 8 seconds, the same server serves 25 requests per second. You did not lose any hardware. You lost 40× throughput just by waiting longer.

OPERATION TYPICAL BUDGET THINKING BEHIND IT
Cache call (Redis) 50–200 ms The cache exists to be fast. If it is slow, it has already failed its purpose — give up and move on immediately.
Database query (interactive) 1–3 s Must be shorter than the API timeout so the API can return a clean error instead of being cut off mid-flight.
Database query (report / batch) 30–120 s, isolated Allowed to be slow, but must run on its own connection budget or replica so it cannot starve checkout.
Public API request (end to end) 3–5 s Beyond this the user has already left or pressed refresh. Serving them after 8 seconds has almost no value.
External provider (payment) 5–10 s + idempotency Slower by nature. Never assume a timeout means "not charged" — you must be able to check the real status later.
Message processing (worker) 30–60 s then requeue A stuck consumer must release the message so another worker can try, otherwise the queue silently stops moving.

The three rules of timeout design

  • Timeouts must shrink as you go deeper. If the user gets 5 seconds, the service call gets 3, the database query gets 2, the cache gets 0.2. If an inner timeout is longer than the outer one, the outer caller gives up first and the inner work continues — you pay for work nobody receives.
  • A timeout must actually cancel the work. Returning an error to the user while the query keeps burning database CPU is the worst of both worlds. Pass cancellation down to the query.
  • Different operations deserve different budgets. One global 30-second timeout means your fast endpoints inherit the patience needed by your slowest report. That is how one bad report takes down a checkout page.
"WAITING LONGER" ≠ "RECOVERING BETTER"

Teams raise timeouts during incidents because errors "go away". They do not go away — they turn into slow requests holding resources, which is the invisible version of the same failure, plus resource exhaustion. A slow dependency with a long timeout consumes your entire thread pool and connection pool, and then your healthy features die too.

PART 11 — RESOURCE EXHAUSTION

Connection Pool Exhaustion

This is the single most common way a slow database turns into a completely dead application — and most developers never see it coming.

What is a database connection?An open line between your application and the database. Creating one is expensive (network handshake, authentication, memory on the database side), so applications keep them and reuse them.
What is a connection pool?A small fixed box of ready-made connections — often 100 per application instance. A request borrows one, runs its query, returns it. Like a shelf of shared telephones in an office.
What happens when queries are slow?Each request keeps its connection much longer. The number of connections has not changed, but each one is now occupied for 2 seconds instead of 20 milliseconds — so effective capacity drops 100×.
What happens when the pool is empty?New requests wait for a free connection. They pile up, then fail with "pool timeout". The application looks broken even for endpoints that would have been fast.
Slow DB
↓
Long requests
↓
Connections remain occupied
↓
Pool becomes full

The arithmetic worth memorising. Capacity = pool size ÷ query time. A pool of 100 connections with 20 ms queries serves 5,000 queries per second. The same pool with 2-second queries serves 50. Nothing broke. The maths simply changed.

How an Architect prevents it

  • Short query timeouts so a connection is never held hostage by one bad query.
  • Separate pools for separate workloads — checkout, dashboards and reports each get their own budget. A report flood then cannot starve orders. This is the bulkhead idea: separate watertight compartments in a ship.
  • Right-size the pool. Bigger is not better: 50 app instances × 200 connections = 10,000 connections, which will destroy the database itself. Total connections must fit what the database can serve.
  • Never hold a connection while calling something else (an external API, a cache, a message broker). Get data, close, then call.
  • Alert on pool usage, not just CPU. Pool saturation is the earliest honest signal that an outage is beginning — usually minutes before users complain.
PART 12 — THE SPREAD

Cascading Failure

A cascading failure is when the failure of one component creates the conditions for the next one to fail. It is a chain of dominoes, and every domino was "healthy" until the one before it fell.

Why the cascade happens: three shared things

  • Shared resources. APIs, workers and reports all use the same database and the same connection budget. Whoever exhausts it first takes down everyone.
  • Shared time. A slow dependency does not just slow one feature — it holds the threads that all features need.
  • Shared assumptions. Everybody assumed the cache would be there, so nobody measured what happens without it.
THE ARCHITECT'S DUTY

You cannot prevent components from failing. You can decide how far a failure is allowed to travel. Design so that the honest answer to "Redis is down" is "dashboards are stale and reports are off, orders and payments are fine" — not "the platform is down".

PART 13 — CHOOSING WHAT SURVIVES

Graceful Degradation

Graceful degradation means: when the system cannot do everything, it deliberately does the important things and drops the rest — instead of trying everything and failing at all of it.

A hospital in an emergency does not treat patients in the order they arrived. It treats them in the order of severity. Your platform must do the same with requests.

PRIORITY FUNCTION BEHAVIOUR DURING THE INCIDENT IF IT FAILS…
P1 · CriticalKEEP ALIVE Login / authentication Full connection budget, own bulkhead, cached tokens, never rate-limited below normal traffic. Nobody can do anything. Total outage.
P1 · Critical Order creation Highest priority. Write path protected; if reads are slow, accept the order and confirm details asynchronously. Direct revenue loss, per minute.
P1 · Critical Payment Protected, idempotent, never auto-retried blindly; status reconciled later. Money errors and customer trust damage.
P1 · Critical Inventory update Must stay consistent — this is the one place where correctness beats speed. Overselling, manual cleanup for weeks.
P2 · DelayableQUEUE IT Notifications (email, SMS, push) Keep accepting into the queue, slow the consumers down. Users get them 20 minutes late — acceptable. Annoyance, not damage.
P2 · Delayable Reporting refresh Serve last computed snapshot with a timestamp. Stop live recomputation. Managers wait. Business continues.
P2 · Delayable Analytics / audit aggregation Buffer events; process after recovery. Never drop audit writes — just delay them. Late insight, no operational impact.
P3 · DisposableSWITCH OFF Heavy dashboards Feature flag off, or serve a static "temporarily simplified" view. Users complain, revenue unaffected.
P3 · Disposable Large exports / bulk reports Reject immediately with "unavailable, try after 30 minutes". Zero business damage during one hour.
P3 · Disposable Recommendations, "related items", activity feeds Return empty or default content instantly. Slightly poorer experience.
THE GOAL OF DEGRADATION

During failure, the goal is not to keep everything working. The goal is to keep the most important business functions alive and make the loss visible, temporary and reversible. A platform that takes orders while its dashboards are frozen is having a bad hour. A platform that shows perfect dashboards while orders fail is having a disaster.

How to build it before you need it

  • Classify every endpoint P1 / P2 / P3 and store the classification in configuration, not in someone's head.
  • Give each class its own resource budget (connections, threads, rate limits) so P3 can never eat P1's capacity.
  • Build feature flags for every P3 feature, and test switching them off in production during quiet hours.
  • Agree the list with the business in writing. The middle of an outage is not the moment to negotiate whether reports can be disabled.
  • Design honest UI messages: "Showing data from 10:05" is trusted; a spinner forever is not.
PART 14 — THE OTHER QUEUE

Queue Backlog When Workers Slow Down

A message queue is a shock absorber: work goes in fast and is processed at a steady pace. But if consumers slow down while producers keep going, the buffer becomes a growing debt.

Queue depthHow many messages are waiting. Flat is healthy. A straight rising line means you are falling behind and will not catch up without a change.
Processing speedMessages consumed per second. Compare it to messages produced per second — the difference is your debt per second.
Message delay (lag)How old is the oldest waiting message? This is what the business actually feels: "invoices are 40 minutes late".
RetryFailed messages return to the queue. During an incident this can double the queue and hide new work behind old failures.
Dead-letter queue (DLQ)A side box for messages that failed too many times. It protects the main queue from being blocked by one poisonous message — but somebody must actually review it.
Consumer scalingAdding more workers. Only helps if the slow part is the worker. If the slow part is the database, more workers make everything worse.

The decision: which lever do I pull?

SITUATION DECISION REASONING
Workers are CPU-bound, database is healthy Scale consumers out The bottleneck is worker capacity. More workers genuinely drain faster.
Workers are waiting on an overloaded database Do NOT scale consumers — reduce them More consumers means more concurrent queries into the exact resource that is already the bottleneck. You would trade a queue delay for a total outage.
Queue is mixed: invoices + marketing emails Split queues, pause the non-critical one Critical work should never wait behind optional work. Priority queues exist for this exact hour.
Same message failing repeatedly Send it to the DLQ quickly One poisonous message can block a partition or consume all retry capacity.
Backlog is huge but downstream is recovering Drain slowly, with a rate limit Releasing 400,000 queued messages at full speed is a self-inflicted denial of service on a system that just came back.
Messages are stale and worthless (old notifications) Drop them, with business agreement Sending a "your order shipped" alert three hours late may be worse than not sending it. Time-to-live on messages is a legitimate design choice.
THE QUEUE IS A SYMPTOM, NOT A DISEASE

A growing queue rarely means "the queue is broken". It means something downstream is slower than the work arriving. Fix the downstream bottleneck, then drain the backlog under control. And remember the good news: a growing queue means work is delayed, not lost — that is exactly what the broker was bought for.

PART 15 — COMING BACK

Recovery: The Second Chance to Cause an Outage

Redis is back. The obvious move is to switch everything on again immediately. That is how teams cause a second, worse outage.

Why? Because at the moment of recovery: the cache is empty, so every request is still a cache miss; the queue is full of backlog waiting to hit the database; thousands of clients are retrying in a synchronised wave; and the database has not yet cooled down. Open the gates fully and you recreate the exact conditions of the first failure — this time with a backlog attached.

  1. Confirm the dependency is genuinely healthyNot "it responds to ping" — check latency, memory, replication and error rate for a few minutes. A flapping dependency that comes and goes is worse than one that stays down.
  2. Warm the cache before opening the doorsLoad the top keys — the most-requested dashboards, lookups and tenant summaries — in a controlled background job with a rate limit. Warm from the replica if possible, so warming does not hurt the primary database.
  3. Return traffic graduallyClose circuit breakers step by step: 10% → 25% → 50% → 100%, watching SQL CPU and p95 latency at each step. If a step degrades the numbers, go back one step and wait.
  4. Re-enable features in priority orderCritical first, then delayable, then heavy dashboards and reports last. Reports are what caused the pain — they return when everything else is proven stable.
  5. Drain the queue at a controlled rateDo not release the whole backlog. Limit consumer concurrency, drain the critical queue first, and watch database CPU as you go.
  6. Check downstream health tooExternal providers may also be recovering, and your backlog is about to become their traffic spike. Rate-limit outbound calls the same way you rate-limit inbound.
  7. Watch for at least 30 quiet minutes before declaring "resolved"Hit ratio back to normal, CPU below 60%, error rate near zero, queue depth falling, no rising retry rate. Only then close the incident and tell the business.
THE THUNDERING HERD ON RECOVERY

Empty cache + full retry queue + hungry backlog = a load spike bigger than your normal peak. Recovery must be as carefully rate-limited as the incident response was. A good Architect says: "I recover in steps and I measure between steps." A junior says: "I turned it all back on."

PART 16 — THE LONG GAME

Preventing the Whole Incident

Every prevention has a price. An Architect never presents a fix without naming the new complexity or cost it introduces — that is the difference between advice and engineering.

SOLUTION PROBLEM SOLVED BENEFIT NEW COMPLEXITY / COST
Redis high availability
replica + automatic failover		 A single cache node disappearing takes the whole cache layer with it. Failover in seconds; the incident becomes a blip instead of an outage. 2–3× cache cost; failover itself can misbehave; brief data loss on failover must be acceptable.
Monitoring Nobody knew what was happening for the first minutes. Cache hit ratio, SQL CPU, pool usage, queue depth and p95 on one screen. Tooling cost, dashboard maintenance, storage of metrics.
Alerts on the right signals Alerts fired late — after users complained. Alert on saturation (pool 80%, CPU 75%, hit ratio drop) not only on errors, so you act before failure. Alert tuning effort; false alarms erode trust if thresholds are careless.

Circuit breakers The app kept hammering a dying dependency. Failing dependency is isolated automatically, without a human. More states to reason about; wrong thresholds cause needless outages of good features.
Cache fallback policy "Just read SQL" multiplied database load by five. Per-endpoint decision: stale, local, limited or fail fast. More code paths; stale data must be visible and explainable to users.
Database protection
limits + bulkheads		 SQL accepted more work than it could ever finish. Database degrades gently instead of collapsing; critical paths keep capacity. Some requests are rejected during peaks — the business must accept this trade.

IF YOU CAN ONLY DO THREE THINGS

1. Timeouts + circuit breakers on every dependency (cheapest, biggest effect). 2. Per-tenant rate limiting and per-endpoint concurrency limits in front of SQL. 3. A load test with Redis switched off, so you know your real uncached capacity number. Everything else can wait for the next budget cycle.

PART 17 — CACHE DECISIONS

Redis Architecture Decisions That Matter

Not configuration — decisions. These are the seven cache questions an interviewer expects an Architect to have an opinion about.

DECISION WHAT IT MEANS SIMPLY WHEN IT MATTERS MOST
Cache-aside The application checks the cache first; on a miss it reads the database and stores the result. The cache is a helper, not the source of truth. Almost always the right default — but it is precisely the pattern that turns a cache outage into a database flood, so it must come with a fallback policy and a concurrency limit.
TTL (time to live) How long a cached answer is allowed to live before it is thrown away. Short TTL = fresher data, more database load. Long TTL = cheaper, staler. Add randomness so thousands of keys do not expire in the same second.
Cache invalidation Removing or updating a cached value when the real data changes. Critical for prices, stock and permissions. Prefer event-based invalidation on write for correctness-sensitive data; TTL alone is fine for tolerant data.
Cache warm-up Filling the cache with important keys before real traffic arrives. After a restart, a deployment, a failover, or a recovery. Without warm-up, "back online" means "100% cache miss at full traffic".
Cache failure behaviour What each endpoint does when the cache is unavailable: SQL fallback, stale copy, local memory, or fail fast. The single most important decision on this page. It is the difference between a degraded hour and a full outage.
Distributed cache One shared cache used by all application servers, instead of each server keeping its own copy. Needed when data must be consistent across servers (sessions, tokens, counters). The price is a network hop and a shared point of failure.
High availability Replica nodes and automatic failover so one dead node does not remove the whole cache layer. Whenever the cache absorbs a load your database cannot survive alone — which, at 80% hit ratio, is essentially always.
THE QUESTION THAT DEFINES YOUR DESIGN

"Is my cache an optimisation or a dependency?" If the system survives without it, it is an optimisation and a simple fallback is fine. If the system dies without it, it is a dependency — and a dependency needs high availability, a tested failure mode, and its own monitoring. Most teams believe they have the first and actually have the second.

PART 18 — LAYERED DEFENCE

Database Protection: Seven Layers

No single control saves a database. Protection works like a set of filters: each layer removes some load, so the layer behind it only ever sees what it can handle.

  1. Layer 1 — Limit incoming trafficAt the edge: per-tenant and per-user rate limits, request size limits, bot and abuse filtering, backpressure signals (HTTP 429 with Retry-After). Cheapest possible place to say no, because nothing has been spent yet.STOPS: floods, noisy tenants, retry storms
  2. Layer 2 — Protect expensive APIsIdentify the 5–10 endpoints that cost 10× more than the rest (dashboards, exports, search). Give them their own concurrency limit, their own breaker, and a strict timeout. They may starve — but only themselves.STOPS: one endpoint eating the whole database
  3. Layer 3 — Use caching properlyCache the expensive and repeated reads, with random TTLs, single-flight rebuilds, and a documented behaviour for when the cache is gone.STOPS: repeated identical work
  4. Layer 4 — Optimise queriesIndexes, no N+1 loops, no SELECT *, pagination instead of "load everything", pre-computed aggregates instead of counting millions of rows on every dashboard refresh.STOPS: self-inflicted CPU burn
  5. Layer 5 — Separate the reporting workloadReporting is a different animal: long, heavy, scan-based. Move it to a replica, a read-only copy, or a separate analytics store so it can never compete with checkout.STOPS: month-end reports killing operations
  6. Layer 6 — Scale database readsRead replicas for dashboards and lists, connection routing (writes to primary, reads to replica), and accepting a few seconds of lag where it does not matter.STOPS: read pressure on the write node
  7. Layer 7 — Monitor capacity continuouslyTrack CPU, IO, waits, slow queries, pool usage and headroom. Know your number: "we are safe up to X RPS with cache, and Y RPS without it." Review it every quarter and after every major release.STOPS: being surprised by your own growth
HOW TO PRESENT THIS ON A WHITEBOARD

Draw the database in the middle and seven rings around it. Then say: "Load must pass through all seven rings. Each ring removes some of it. My job is to make sure that whatever reaches the centre is always less than what the centre can serve." That single picture answers half of the database questions in an Architect interview.

PART 19 — THE RUNBOOK

Runbook: "Redis Unavailable, SQL Load Increasing"

A runbook is a short document that a tired engineer can follow at 3 AM without thinking. Short sentences. Clear order. No theory.

RUNBOOK · SEVERITY P1 · OWNER: PLATFORM ON-CALL

1 · DETECTION — HOW DO WE KNOW?

  • Primary alerts: cache hit ratio below 20% for 2 minutes · Redis health check failing · SQL CPU above 80% for 3 minutes · API p95 above 2 s · connection pool usage above 85%.
  • Confirming signals: error rate rising, request rate rising while success rate falls (retry signature), queue depth climbing.
  • Declare P1 immediately if two or more of these fire together. Name one incident lead and one communicator. Start an incident channel and a timeline log.

2 · IMMEDIATE ACTIONS — FIRST 5 MINUTES

  • Confirm Redis state (up / down / flapping). A flapping cache is treated as down — force the breaker open.
  • Freeze deployments and autoscaling of the API tier.
  • Stop all batch, import, sync and scheduled reporting jobs.
  • Enable "incident mode" feature flags: heavy dashboards off, exports off, recommendations off.
  • Reduce database timeouts and per-endpoint concurrency limits to the pre-agreed incident values.

3 · STABILISATION — STOP IT GETTING WORSE

  • Turn on aggressive rate limiting at the edge; apply stricter limits to the top-consuming tenants.
  • Open circuit breakers for P3 endpoints; keep P1 (login, order, payment, inventory) protected with a reserved connection budget.
  • Serve stale or reduced data where a fallback exists; return fast, honest errors where it does not.
  • Reduce background worker concurrency so workers stop competing with user traffic for the database.
  • Target state: SQL CPU below 70%, p95 under 1 s for P1 endpoints, error rate falling. Degraded but stable is a success.
  • Post the first business update: what is working, what is not, next update time.

4 · RECOVERY — RESTORE NORMAL OPERATION

  • Bring Redis back (failover to replica or rebuild the node). Verify latency and memory before trusting it.
  • Warm the top keys with a rate-limited job, reading from a replica where possible.
  • Close breakers in steps: 10% → 25% → 50% → 100%, watching SQL CPU and p95 between each step.
  • Re-enable features in priority order: P1 → P2 → P3. Reports and exports last.
  • Drain the message backlog with limited consumer concurrency; critical queues first.
  • Restore normal timeouts, limits and autoscaling only after 30 minutes of stability.

5 · VALIDATION — HOW DO WE KNOW WE ARE HEALTHY?

  • Cache hit ratio back above 85% · SQL CPU below 60% · p95 back to baseline (≈200 ms) · error rate under 0.1%.
  • Queue depth falling and oldest-message age returning to seconds.
  • Connection pool usage under 50% · no pool timeouts in the last 15 minutes.
  • Business check: place a real test order, run a real login, verify a payment and one notification end to end.
  • Only then declare "resolved" and schedule the review within 48 hours.

6 · PREVENTION — SO IT DOES NOT HAPPEN AGAIN

  • Redis high availability with tested automatic failover.
  • Documented per-endpoint cache fallback policy; no silent "always hit SQL" behaviour.
  • Permanent rate limits, bulkheads and breakers — not just incident-mode ones.
  • Load test with the cache disabled; publish the real uncached capacity number.
  • Move reporting to a replica or separate store.
  • Practise this runbook quarterly as a game day, including the recovery steps.
RUNBOOK QUALITY TEST

Give it to an engineer who has never seen this system. If they cannot execute the first five minutes without asking a question, the runbook is not finished. Runbooks are written for the worst night, not the best day.

PART 20 — AFTER THE FIRE

Post-Incident Review

The incident is over. Now comes the part that actually improves the system — if you run it as an engineering exercise and not as a search for someone to blame.

  1. What happened?A plain timeline with timestamps: 10:00 Redis unavailable · 10:01 SQL CPU 95% · 10:03 first timeouts · 10:04 retry storm · 10:09 incident declared · 10:22 stabilised · 11:05 recovered. Facts only, no interpretation yet.
  2. Why did it happen?Separate trigger (a Redis node died) from cause of the outage (no fallback policy, no limits in front of SQL, unbounded retries). The trigger is usually boring; the cause is architectural.
  3. Why was it not detected earlier?Were we alerting on symptoms (users complaining) or on saturation (hit ratio, pool usage, CPU)? How many minutes passed between the first bad metric and the first human action?
  4. What made it worse?Retries with no backoff · long timeouts · autoscaling the API tier · scaling consumers into an overloaded database · restarting services · five people changing things at once.
  5. What worked?Name it explicitly so it survives the next refactor: the queue preserved all messages, payments stayed idempotent, the incident channel worked, the replica held up.
  6. What did not work?Missing feature flags, unclear ownership, dashboards that did not show cache hit ratio, a runbook nobody had read.
  7. What should change?A short list of actions with an owner and a date. Maximum five. A review producing 30 actions produces zero improvements.
  8. How will success be measured?Concrete targets: "detection within 60 seconds", "system survives Redis loss at 5,000 RPS in a game-day test", "uncached capacity documented and load tested", "no unbounded retries anywhere in the platform".
BLAME CULTURE SAYS LEARNING CULTURE SAYS
"Who pushed the change?" "Why was the system able to fail so widely from one change?"
"The on-call engineer reacted slowly." "Our alerts fired 6 minutes late and the runbook was out of date."
"Someone forgot the timeout." "Timeouts are a default in our platform library from now on, so nobody can forget."
"It will not happen again." "We will reproduce it in a game day next month and prove it."
WHY BLAMELESS IS NOT SOFT

If people are punished for incidents, they hide information — and you lose the data that would have prevented the next one. A blameless review is not kindness; it is the only way to get the truth fast enough to fix the system. Blame the design, never the person.

PART 21 — THE DECISIONS

Twelve Architecture Trade-offs

Every one of these will appear in an Architect interview. There is no universally correct answer — there is only a defended answer with a stated context.

TRADE-OFF 01
Cache fallback vs fail fast
ProblemRedis is down. Should requests read the database instead, or fail immediately?
Option AFallback to SQL for everything — nothing visibly breaks.
Option BFail fast on expensive reads, serve stale data where possible.
BenefitsA keeps full functionality; B keeps the database alive and the platform stable.
RisksA can multiply DB load 5–10× and cause a total outage; B shows users missing features.
RECOMMENDEDHybrid, decided per endpoint: cheap+critical → fallback with a concurrency limit; expensive+optional → stale or fail fast. Why: the total worst-case fallback load must fit inside measured database capacity — that is an arithmetic constraint, not an opinion.
TRADE-OFF 02
Retry vs no retry
ProblemCalls are failing. Should the client try again?
Option ARetry aggressively so transient errors are invisible.
Option BNo retries; surface the error immediately.
BenefitsA hides short blips; B never amplifies an overload.
RisksA creates retry storms and duplicate side effects; B produces avoidable user-visible errors.
RECOMMENDEDBounded retries (max 2) with exponential backoff and jitter, only for idempotent operations, and disabled automatically when the circuit breaker is open. Why: retry helps random failures and destroys saturated systems — so make it state-aware.
TRADE-OFF 03
Single Redis vs highly available Redis
ProblemCache is a shared dependency for the whole platform.
Option AOne node — cheap and simple.
Option BPrimary + replica with automatic failover, or a managed HA tier.
BenefitsA saves money and operational effort; B turns a one-hour outage into a ten-second blip.
RisksA is a single point of failure for everything; B costs 2–3× and failover can itself misfire.
RECOMMENDEDHA — if the database cannot survive the full uncached load. Why: a cache that your system cannot live without is not a cache, it is a critical dependency, and critical dependencies get redundancy.
TRADE-OFF 04
Shared database vs separated reporting database
ProblemHeavy reports compete with order processing on the same server.
Option AOne database for everything — always consistent, simple.
Option BReplica or separate analytics store for reporting.
BenefitsA is cheap and always fresh; B removes the biggest, spikiest workload from the critical path.
RisksA means one big report can freeze checkout; B adds cost, lag and a second thing to operate.
RECOMMENDEDSeparate reporting. Why: reporting has completely different characteristics (long, scan-heavy, tolerant of lag). Mixing it with transactions guarantees that management's curiosity can stop revenue.
TRADE-OFF 05
More caching vs database scaling
ProblemRead load is growing faster than the database can serve it.
Option ACache more, cache longer.
Option BBuy a bigger database / add replicas.
BenefitsA is cheap and instantly effective; B raises the true floor of what the system can survive.
RisksA increases the blast radius of a cache outage and adds staleness; B costs real money every month.
RECOMMENDEDBoth, deliberately: cache for speed, but keep enough database capacity to survive a defined percentage of cache loss. Why: caching to hide an undersized database is borrowing capacity you must repay during the incident.
TRADE-OFF 06
Rate limiting vs accepting all traffic
ProblemDemand can exceed capacity at any moment.
Option AAccept everything, serve as much as possible.
Option BLimit per tenant/user and reject the excess quickly.
BenefitsA never rejects a paying customer; B guarantees predictable behaviour and fairness.
RisksA means everyone fails together when capacity is exceeded; B means some legitimate requests get 429s.
RECOMMENDEDRate limit. Why: serving 90% of users well beats serving 100% of users a timeout. Rejection is a choice; collapse is not.
TRADE-OFF 07
Strong consistency vs eventual consistency
ProblemShould every read see the very latest write?
Option AAlways read the primary — always correct.
Option BRead replicas and caches — a few seconds behind.
BenefitsA is simple to reason about; B scales reads almost without limit and survives cache/DB pressure.
RisksA concentrates all load on one node; B can show a user data that is slightly old.
RECOMMENDEDStrong consistency for money, stock and permissions; eventual consistency for dashboards, lists and search. Why: consistency is a per-use-case requirement, never a global setting.
TRADE-OFF 08
Synchronous vs background work
ProblemHow much must finish before the user gets a response?
Option ADo everything now: order, invoice, email, analytics.
Option BDo the minimum now, queue the rest.
BenefitsA gives immediate certainty; B gives short response times and a smaller failure surface per request.
RisksA means one slow step fails the whole action; B needs idempotency, monitoring and a story for delayed work.
RECOMMENDEDSynchronous only for what the user must trust immediately (payment authorisation, stock reservation); everything else queued. Why: the fewer dependencies inside a request, the fewer ways that request can die.
TRADE-OFF 09
One large database vs read replicas
ProblemRead traffic is 10× the write traffic.
Option AKeep scaling one powerful server up.
Option BPrimary for writes + replicas for reads.
BenefitsA is simplest and always consistent; B spreads read load and gives a failover candidate.
RisksA has a hard ceiling and a single point of failure; B adds lag, routing logic and cost.
RECOMMENDEDReplicas for lag-tolerant reads. Why: they solve the read-heavy problem and simultaneously improve availability — the same money buying two benefits.
TRADE-OFF 10
Automatic recovery vs controlled recovery
ProblemThe dependency is back. Who decides to resume full traffic?
Option ABreakers close automatically, everything resumes.
Option BA human ramps traffic in steps.
BenefitsA recovers in seconds with no staff needed; B avoids a second collapse from an empty cache and a full backlog.
RisksA can cause the thundering herd; B is slower and depends on a person being awake.
RECOMMENDEDAutomatic but rate-limited — breakers close in stages with a manual override. Why: automation should recover the system, not stampede it; humans keep the emergency brake.
TRADE-OFF 11
Feature availability vs system stability
ProblemKeeping a heavy feature alive is risking everything else.
Option ANever disable features; users hate missing functions.
Option BFeature flags switch off heavy features during pressure.
BenefitsA protects perceived product quality; B protects revenue-critical paths.
RisksA risks the entire platform for one report; B needs pre-agreed business rules and clear messaging.
RECOMMENDEDStability wins, with a pre-approved degradation list. Why: a temporarily missing dashboard is a conversation; a failed checkout is lost money and lost trust.
TRADE-OFF 12
Higher cost vs higher resilience
ProblemResilience is never free; budgets are finite.
Option AMinimum infrastructure, accept longer outages.
Option BRedundancy everywhere, multi-region, generous headroom.
BenefitsA maximises margin; B minimises downtime risk.
RisksA: one bad hour can cost more than a year of savings; B: paying constantly for a rare event.
RECOMMENDEDBuy resilience for the P1 path only, and calculate it: cost of one hour of downtime × expected hours per year vs annual cost of the protection. Why: resilience is a business investment, so present it in the business's own currency.
PART 22 — THE FIELD GUIDE

Fifteen Real Production Scenarios

Read each one and answer before reading the columns. In interviews these are asked as "what would you do if…" — and the expected shape of the answer is always the same four steps: symptoms → likely causes → immediate action → prevention.

SCENARIO SYMPTOMS ROOT CAUSE POSSIBILITIES IMMEDIATE ACTION RECOVERY & PREVENTION
1 · Redis unavailable Hit ratio 0, cache errors, SQL CPU spiking, latency up. Node crash, memory limit, network partition, failed patch, eviction storm. Open cache breaker, enable stale/local fallback, cut heavy endpoints, rate limit, stop batch jobs. Failover to replica, warm top keys, ramp traffic in steps. Prevent with HA, tested fallback policy, uncached load test.
2 · SQL CPU at 100% All endpoints slow together, pool timeouts, blocking and waits rising. Cache loss, missing index, a new bad query, report run, traffic spike, stale statistics. Kill the top expensive queries, stop reports/batch, apply concurrency limits, shed P3 traffic. Optimise or index the offending query; move reporting to a replica; alert on CPU > 75% and on new slow queries after deploys.
3 · API servers out of memory Restarts, out-of-memory kills, long GC pauses, latency saw-tooth pattern. Memory leak, huge result sets loaded into memory, oversized local cache, unbounded queues in code. Roll instances gradually (never all at once), cap page sizes, disable the endpoint that allocates most. Fix the leak, enforce pagination and streaming, set memory limits and alerts, load-test with realistic payload sizes.
4 · Message broker unavailable Publish failures, APIs slow if publishing is synchronous, workers idle. Broker node down, disk full, credentials expired, network issue. Make publishing non-blocking; buffer events locally (outbox table); never let a broker outage fail an order. Restore broker, replay the outbox in order with rate limiting. 9 · One tenant floods the system One tenant id dominates logs; other tenants slow; DB load skewed. Bulk import, broken integration loop, aggressive polling, a legitimate campaign. Prevent with per-tenant quotas, fair queuing, usage dashboards per tenant, and isolated resources for the largest accounts.
10 · Traffic suddenly 10× RPS spike, queues at the edge, latency climbing, autoscaling lagging behind. Marketing campaign, viral event, bot traffic, retry amplification, a partner's batch job. Rate limit and shed P3 traffic first; protect P1 paths; verify how much of the spike is retries rather than real users. Scale after protecting. Prevent with pre-warmed capacity for known events, queue- based buffering, and load tests at 3× expected peak.
11 · Connection pool exhausted "Pool timeout" errors while DB CPU may even look moderate; all endpoints affected. Slow queries holding connections, pool too small, connection leaks, too many app instances. Shorten query timeouts, cut concurrency on heavy endpoints, restart leaking instances one at a time. Prevent with separate pools per workload, right-sized totals, leak detection, and alerts on pool usage above 80%.
12 · Cache returns stale data Users see old prices/stock; support tickets; mismatch between screens. Missed invalidation on write, TTL too long, failed invalidation event, split-brain after failover. Invalidate the affected key ranges, shorten TTL for that data, disable caching for the critical field temporarily. Prevent with event-driven invalidation for money/stock data, versioned cache keys, and never caching values you cannot afford to be wrong.
13 · Background worker crashes Queue grows, no processing, repeated restarts, same message reappearing. Poison message, unhandled exception, memory issue, downstream dependency failure. Move the poison message to the DLQ, restart with limited concurrency, check the downstream dependency first. Prevent with idempotent handlers, retry limits, DLQ monitoring, and health checks that detect a stuck (not just dead) consumer.
14 · One region unavailable Total failure for users in that region; health checks failing; cross-region latency spikes. Cloud region incident, network partition, regional dependency failure. Fail over traffic to the healthy region, accept read-only or degraded mode if the database is not yet promoted. Prevent with defined RPO/RTO, replicated data, tested failover runbooks, DNS/traffic manager routing, and awareness of data residency rules.
15 · Monitoring itself fails Dashboards empty or frozen, no alerts, suspicious silence during peak hours. Metrics pipeline down, agent failure, storage full, credentials expired. Treat silence as an incident, not as good news. Switch to secondary signals: load balancer metrics, synthetic checks, direct database queries. Prevent with an independent watchdog (external synthetic monitoring), alerting on "no data received", and a second, simpler monitoring path.
THE PATTERN BEHIND ALL FIFTEEN

Notice the repetition: protect the shared resource, reduce or reject load, isolate the failing dependency, preserve the critical path, recover gradually, then remove the root cause. Learn the pattern and you can answer a scenario you have never seen before.

2 · Why not that one. "A dashboard aggregation that timed out is never retried — the original query is probably still running on the database, so a retry doubles the cost of a request that already failed."

3 · Retry storm prevention. "Max two attempts, exponential backoff with jitter, a retry budget capped at 5% of traffic, retries suppressed while the breaker is open, and 429 with Retry-After so clients back off instead of guessing."

4 · Redis down for 30 minutes. "Minute 0–1: breaker opens, hot lookups served from in-process memory. Minute 1: dashboards switch to stale snapshots with a visible timestamp, exports and reports are disabled. Throughout: orders, payments, login and inventory run normally at full speed because their uncached load fits our replica plus primary capacity. The user sees older numbers and two missing features — not an outage."

5 · What prevents SQL overload. "A hard admission limit: per-endpoint concurrency caps whose total is below measured primary capacity, plus per-tenant rate limits at the edge. Concretely, heavy reads are capped so they can never occupy more than 20% of the connection budget, and P1 writes hold a reserved 30%."

6 · Stale data. "Stale is acceptable for dashboards, catalogues and lists, always labelled with a timestamp. It is forbidden for stock, prices at checkout, permissions and balances — those read the primary or use event-driven invalidation. I do not cache values I cannot afford to be wrong."

7 · Why keep Redis. "Because without it the database needs roughly six times more capacity, which costs far more than an HA cache. Redis did not cause the outage — the missing limits did. Removing the cache would fix the symptom by making the system permanently more expensive."

8 · Recovery criteria. "Hit ratio above 85%, SQL CPU under 60%, p95 at baseline, error rate under 0.1%, pool usage under 50%, queue lag falling, plus a real test order completing end to end — sustained for 30 minutes."

9 · Two dependencies at once. "They are isolated by separate breakers and separate pools, so the effects add rather than multiply. Cache loss degrades reads; payment provider loss switches checkout to 'authorising, we will confirm shortly' with queued reconciliation. Both together means reduced service, not collapse — and if the combination exceeds capacity, load shedding by priority is the pressure valve."

10 · Priority. "Order creation and payment first, because they lose revenue per minute and can create data inconsistencies. The order was agreed with the business owner and is written in the runbook — I did not invent it during the incident."

11 · Tenant at 10×. "Per-tenant quotas and fair queuing contain it automatically: their excess gets 429s while other tenants are unaffected. Their heavy jobs are shifted to off-peak windows, and if the growth is legitimate we move them to dedicated capacity and price accordingly."

12 · Cost of resilience. "I size it against downtime cost. If an hour costs the business fifty thousand and we expect two per year, roughly a hundred thousand a year is justified. I spend it in order of cheapest impact first: timeouts, breakers and limits cost engineering days; Redis HA and replicas cost real money; multi-region I would defer unless the business quantifies the loss."

13 · Wrong breaker opening. "That is why thresholds are percentage-based over a window with a minimum request count, why breakers have fallbacks rather than hard errors, why every state change raises an alert, and why there is a manual override to force a breaker closed."

14 · Timeout numbers. "They come from measured p99 per dependency plus headroom, then divided down from the 3-second user budget. Doubling them would double resource holding time and halve effective capacity during a slowdown — waiting longer buys nothing the user values."

15 · Two million messages. "Split by value: critical business messages drain first at a controlled rate matched to database headroom; time-expired notifications are dropped with business agreement, because a shipping alert three hours late is noise; analytics events are drained last. Full-speed draining would be a self-inflicted denial of service."

Twenty-Minute Architect Challenge

One realistic brief. Twenty minutes. This is what a real Technical Architect interview round feels like — including the budget conversation.

THE BRIEF

"A production enterprise application is unstable during peak hours. The company runs Redis, SQL, message queues, background workers and several external services. Management wants zero downtime, but does not want unlimited infrastructure cost."

FACTOR REALITY
Traffic 1,200 RPS average, 6,000 RPS at peak (09:00–11:00 and 17:00–19:00)
Users 400 companies, 250,000 daily users, 3 tenants generate 60% of all load
Failure patterns Weekly: SQL CPU above 90% at peak · Monthly: Redis memory pressure and eviction storms · Occasionally: payment provider latency of 12 s · Daily: queue lag of 20+ minutes in the evening
Business priorities Orders and payments must never stop · Inventory must stay correct · Reports may be delayed · Notifications may be late
Budget constraint Infrastructure spend may rise by at most 25%; no multi-region this year
Availability target 99.9% for the order path; 99.5% acceptable for reporting

Your ten tasks: identify likely failure points · ask clarifying questions · find the main bottleneck · design protection layers · explain failure behaviour · explain recovery · explain monitoring · explain cost · explain trade-offs · recommend the most important improvements first.

RULES

Twenty minutes, spoken out loud, no notes. Spend the first two minutes asking questions, not answering. Finish with a prioritised list — an Architect who cannot sequence improvements is just a consultant with opinions.

Minutes 0–2 · Clarifying questions. "What does one hour of order downtime cost? What is the current cache hit ratio and what is our measured capacity without the cache? Are the three large tenants contractually entitled to unlimited usage? Which reports are run at peak, and by whom? Is the SQL instance CPU-bound or IO-bound at 90%? Do we already have feature flags and per-tenant limits, or must they be built?"

Minutes 2–5 · Failure points and the real bottleneck. "Four recurring failures, one root shape: everything ends at the SQL primary. Weekly CPU saturation at peak is the primary being asked for more than it can give. Redis eviction storms cause a sudden hit-ratio drop, which is the same overload with a different trigger. The evening queue lag is workers competing with users for the same database. The payment provider latency is separate but damaging because it holds request threads. So: the bottleneck is the SQL primary, the amplifier is uncontrolled load from reports, three big tenants and background workers, and the aggravator is the absence of isolation."

Minutes 5–10 · Protection layers, in cost order. "Free-to-cheap first, because the budget is 25%. Layer 1: per-tenant rate limits and quotas at the edge — the three large tenants get guaranteed capacity, not unlimited capacity. Layer 2: concurrency caps and breakers on the ten most expensive endpoints, plus a reserved connection budget for orders and payments. Layer 3: timeouts tightened everywhere and payment calls moved to an asynchronous confirmation flow so a 12-second provider cannot hold our threads. Layer 4: jittered TTLs, single-flight cache rebuilds and a memory policy review to stop eviction storms; plus in-process caching for the hottest lookups. Layer 5: workers get their own connection pool, reduced concurrency at peak, and a nightly window for heavy jobs. Layer 6: move reporting to a read replica — this is the one significant spend and it removes the single biggest source of peak CPU. Layer 7: publish the capacity numbers with and without cache and alert on saturation."

Minutes 10–13 · Failure behaviour after the change. "Redis lost: hot lookups served locally, dashboards stale with a timestamp, reports disabled, orders and payments unaffected — because their uncached load now fits the primary. SQL under pressure: P3 endpoints shed first, workers throttled, orders keep their reserved budget. Payment provider slow: breaker opens, checkout returns 'payment is being confirmed', reconciliation completes it. Queue backlog: critical queue drains first, notifications delayed, nothing lost."

Minutes 13–15 · Recovery and monitoring. "Recovery is staged: verify, warm, ramp 10/25/50/100, re-enable by priority, drain queues under a limit, 30 minutes of stability before declaring resolved. Monitoring adds the four signals they are missing today: cache hit ratio, connection pool usage, queue oldest-message age and per-tenant usage. Alerts move from error-based to saturation-based so we act five minutes earlier."

Minutes 15–17 · Cost. "Within the 25%: one read replica for reporting is the main line item, Redis moving to a highly available managed tier is the second, and a modest increase in primary size is the third if measurement justifies it. Everything else — limits, breakers, timeouts, flags, queue splitting — is engineering time, not infrastructure. I would present it as: roughly 20% more spend to remove the two most frequent outage classes, against a downtime cost of X per hour occurring weekly today."

Minutes 17–19 · Trade-offs stated openly. "Rate limiting will occasionally reject requests from our three largest customers at peak — that requires a commercial conversation and probably a paid tier. Reporting from a replica means reports are seconds behind, which the business has already accepted. Asynchronous payment confirmation changes the checkout experience slightly and requires reconciliation logic. And no multi-region this year means we accept that a regional outage is a multi-hour event — I would document that risk explicitly so it is a business decision, not an engineering oversight."

Minutes 19–20 · The prioritised recommendation. "In order: (1) timeouts, breakers and per-endpoint concurrency limits — days of work, removes the collapse mode. (2) Per-tenant rate limits — fixes the 60%-from-three-tenants problem. (3) Move reporting to a replica — removes the biggest peak CPU consumer. (4) Redis HA plus TTL and eviction fixes — removes the monthly trigger. (5) Worker isolation and queue splitting — fixes the evening lag. (6) Saturation-based monitoring and a quarterly game day — makes all of the above provable. If I can only do the first two this quarter, the platform is already dramatically more stable at almost no infrastructure cost."

20 Production Rules Every Architect Should Remember

Short enough to remember at 3 AM. Strong enough to answer most interview questions on their own.

# RULE WHY IT MATTERS
01 Healthy components ≠ a healthy system. Failures live in the relationships between components.
02 Every dependency will fail. Plan the day it does. Hope is not a failure strategy.
03 Protect the bottleneck before you debug it. Stabilise first, understand second.
04 Reduce load before you add capacity. Capacity arrives in minutes; overload arrives in seconds.
05 Fallback to the database is a decision, not a default. It multiplies load by one over the miss rate.
06 Fail fast beats fail slow. Slow failure consumes resources and delivers nothing.
07 Retry is not recovery. During overload, retries are the attack.
08 No timeout means no limit on damage. Unbounded waiting is unbounded resource loss.
09 A slow dependency is worse than a dead one. Dead fails cheaply; slow holds everything hostage.
10 Never let optional work compete with revenue work. Bulkheads exist so reports cannot kill checkout.
11 Shed load by priority, not by accident. Choose who fails, or the system chooses for you.
12 Degradation is designed before the outage, not during it. Feature flags are an architecture decision.
13 Recovery can cause the second outage. Empty cache + full backlog + retries = a new peak.
14 Warm the cache before you open the gates. "Back online" must not mean "100% cache miss".
15 A growing queue means delay, not loss — keep it that way. Never scale consumers into an overloaded database.
16 One tenant must never be able to hurt another. Quotas and fair queuing are multi-tenant hygiene.
17 Alert on saturation, not only on errors. Errors tell you it happened; saturation tells you it is coming.
18 Untested failure paths do not exist. Game days turn beliefs into facts.
19 Blame the design, never the person. Fear hides the data that prevents the next outage.
20 Resilience is a business investment — price it. Compare downtime cost per hour with protection cost per year.

One-Minute Interview Answer

"What would you do if Redis goes down and your database suddenly becomes overloaded?"

SAY IT LIKE THIS — ABOUT 60 SECONDS

"First I would separate three things: the trigger, the bottleneck and the amplifier. Redis failing is the trigger. The real problem is that all the read traffic the cache was absorbing now lands on SQL, so the database becomes the bottleneck. And the amplifier is retries — clients timing out and trying again, which multiplies the load we cannot serve.

In the first minutes I would not try to fix Redis. I would protect the database. Stop every optional workload — reports, exports, batch jobs. Freeze deployments and stop scaling out the API tier, because more instances mean more connections into a saturated database. Then apply per-tenant rate limits, tighten timeouts, cap concurrency per endpoint and open circuit breakers on the expensive reads, while reserving connection capacity for login, orders, payments and inventory.

At the same time I would degrade deliberately, using a list agreed with the business in advance: dashboards serve stale data with a timestamp, heavy reports are switched off, notifications keep queuing and are delivered late. The goal is for the honest status to be 'orders work, reports are off' rather than 'the platform is down'.

When Redis returns I would not open everything at once, because an empty cache plus a full backlog plus retrying clients is a bigger spike than our normal peak. I would warm the top keys from a replica, close breakers in stages while watching CPU and p95, re-enable features by priority and drain the queue under a rate limit.

Afterwards, the fix is architectural, not operational: a documented cache fallback policy per endpoint, permanent limits and breakers, Redis high availability, reporting moved off the primary, and a load test with the cache disabled so we actually know our uncached capacity. Redis failing should cost us a feature for an hour — never the business."

One Powerful Architect Statement

SAY THIS AND MEAN IT

"I do not design systems that expect everything to work. I design systems that expect things to break — and make sure that when one part breaks, the failure stops there: contained, visible, temporary, and never allowed to become the whole business going dark."

Redis will fail again. So will a database, a broker, a provider and a region. The difference between a Senior Developer and a Technical Architect is not that the Architect prevents those failures — it is that the Architect already decided, in advance and in writing, exactly how much of the system each one is allowed to take with it.
