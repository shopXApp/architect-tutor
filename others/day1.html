Day 1: Thinking Like a Technical Architect

Before you choose a technology, an architect first understands the problem. Today is not about learning new tools. Today is about changing the way you think about software systems.

You already know .NET, C#, SQL Server, Redis, RabbitMQ, Docker and Azure. Today we learn to decide when and why to use them — not just how.

Goal: Learn to think architecturally Focus: Decision making Level: Beginner-friendly, architect mindset

01What is Software Architecture?

In simple words: architecture is the set of important decisions about how a software system is built, connected, and kept healthy over time.

The core idea

Architecture is not about making code work. Code that works is the developer's job. Architecture is about making the system survive — survive more users, survive failures, survive attacks, and survive future change.

What a developer thinks
→
One feature at a time“How do I make this function work correctly?”
→
Clean code“Is this code readable and correct?”
→
Today“I need this to compile and pass tests now.”
→
Local scope“My part of the system works.”
What a tech lead thinks
→
A few features together“How do these features work as one flow?”
→
Consistency“Is the team following the same patterns and standards?”
→
The sprint“Can we deliver this in the next release?”
→
Team scope“Is the team unblocked and productive?”
What an architect thinks
→
The whole system“How does every part fit together, now and in 2 years?”
→
Trade-offs“What do we gain, what do we lose, and what does it cost?”
→
Failure“What happens when this part breaks at 2 AM?”
→
The business“Does this design match the company's money, growth, and risk?”
The shift: A developer asks “will it work?”. An architect asks “will it keep working — when users grow, when things fail, when attackers come, and when requirements change?”

02The 5 Things Every Architect Must Think About

These five qualities are the lens through which an architect evaluates every system. Remember them as: Reliability, Performance, Scalability, Security, Maintainability.

1 · Reliability

How do we make sure the system keeps working?

?
What is it?Reliability is the ability of the system to work correctly, even when something goes wrong.
!
Why it mattersUsers trust a system that works. One outage can lose customers, money, and reputation in minutes.
✓
Problem it solvesIt reduces downtime and prevents small errors from turning into total failure.
✗
When we ignore itOne failed component brings down everything (a “single point of failure”). No backup means permanent data loss.
Real worldAn airplane has two engines and multiple backup systems. If one fails, the plane still lands. A car has a spare tire.
SoftwareA payment service retries on failure and writes every transaction to a log, so a crash never loses a payment.
What an architect thinks about
  • Failures: Which parts can fail? Can the system still work if one part fails?
  • Backup: Is the data backed up? How quickly can we restore it?
  • Recovery: If the database crashes, how fast are we back online? Is recovery automatic or manual?
  • Dependency failure: If an external service (payment gateway, email provider) goes down, does our system break too, or can it keep working with a fallback?
2 · Performance

How quickly should the system respond?

?
What is it?Performance is how fast the system responds and how much work it can handle at once.
!
Why it mattersUsers expect a fast response (usually under 2–3 seconds). Slow systems feel broken, even when they work.
✓
Problem it solvesIt keeps the experience smooth and prevents people from leaving out of frustration.
✗
When we ignore itScreens freeze, checkout times out, and users abandon the cart.
Real worldA restaurant wants food served in about 20 minutes. Nobody waits 1 hour for a burger.
SoftwareAn e-commerce product page must load fast. If a product list runs a slow SQL query on every visit, the page is slow for every user.
What an architect thinks about
  • Response time: Which actions must be fast (searching, paying) and which can be slower (generating a report)?
  • Slow database: Which queries are heavy? Do we need indexes, caching, or separating read vs. write work?
  • Slow API: Do we call other services in a way that blocks? Can slow calls run in the background?
  • Too many requests: When many users arrive at once, does the system slow down for everyone? Can quick tasks (like reading a product) run separately from slow tasks (like processing an order)?
3 · Scalability

What happens when users increase?

?
What is it?Scalability is the ability to handle growth — more users, more data, more requests — without breaking or becoming too slow.
!
Why it mattersSuccess brings more users. If the system cannot grow, success becomes a problem.
✓
Problem it solvesIt lets the system grow smoothly instead of collapsing under load.
✗
When we ignore itThe system becomes slow, then stops working, exactly when it is most popular.
100 users
  • One server is often enough.
  • One database handles everything.
  • Simple is best — do not overbuild.
10,000 users
  • Add caching (Redis) for repeated data.
  • Run heavy work in the background (RabbitMQ).
  • Add a load balancer and more servers.
  • Add read replicas to the database.
1 million users
  • Split the system into independent services.
  • Use dedicated databases per area.
  • Distribute data across many servers (sharding).
  • Build queues, retries, and monitoring everywhere.
What an architect thinks about
  • Which parts of the system grow fastest? (Usually reads / browsing grow faster than writes.)
  • Can we add more servers to handle traffic (scale out) instead of buying one bigger server (scale up)?
  • Should we scale now, or is the current setup fine for the next year? (Do not scale before you need to.)
4 · Security

How do we protect users and business data?

?
What is it?Security is protecting the system, the users, and the data from people who should not have access.
!
Why it mattersA security breach can destroy trust forever, and cost the business huge fines and lawsuits.
✓
Problem it solvesIt makes sure only the right people see and change the right data.
✗
When we ignore itCustomer data leaks, accounts get stolen, and the business may not survive.
Real worldA bank has a locked door, a guard, and a key for only the vault. Not every employee can open the vault.
SoftwareIn a banking app, only you can see your own account. A customer support person can see limited details, not your password or your money.
What an architect thinks about
  • Authentication: How do we confirm WHO a user is? (login with username/password, MFA)
  • Authorization: What is this user allowed to DO? (roles and permissions)
  • Sensitive data: Which data must be encrypted? Passwords must be hashed, never stored as plain text. Payments and personal data need encryption both stored and in transit (HTTPS).
  • Access control: Users must only access their own company's data (in multi-tenant SaaS) and their own records.
  • Common mistakes: trusting the client/browser for security, storing secrets in code, forgetting to encrypt logs, leaving cloud storage public.
5 · Maintainability

How easy is the system to change?

?
What is it?Maintainability is how easily the team can understand, fix, and extend the system over time.
!
Why it mattersMost of a system's life is spent in maintenance, not in the first build. Hard-to-change systems slowly die.
✓
Problem it solvesIt keeps future changes cheap and safe, so the system can keep up with business needs.
✗
When we ignore itEvery small change takes weeks, breaks something else, and the team becomes afraid to touch code.
Real worldA well-organized kitchen has a clear place for everything. A messy kitchen means you cannot find anything and cooking takes forever.
SoftwareAn employee management system where one huge class does everything is impossible to change. If modules are separated, you can modify payroll without touching attendance.
What an architect thinks about
  • Clean structure: Is the code organized so a new developer can find things quickly?
  • Clear responsibilities: Does each component do one clear job?
  • Loose coupling: Can we change one part without breaking another? Are components too tightly connected?
  • Technical debt: What old shortcuts are we carrying? When do we plan to pay them back?

The five pillars together — a quick mental check

QualityOne-line questionFailure looks like…
ReliabilityWill it keep working?Outages, data loss
PerformanceIs it fast enough?Slow pages, timeouts
ScalabilityWill it handle growth?Crashes when popular
SecurityIs it protected?Breaches, stolen data
MaintainabilityIs it easy to change?Slow, risky changes

03Questions I Should Ask Before Designing Any System

Before choosing any technology, an architect asks questions. These 20 questions reveal what the system really needs — why they matter is just as important as the answers.

1
Who will use it?Customers, employees, admins, or other systems? The audience decides the UI, security, and access levels.
2
How many users?Hundreds or millions? This decides whether we need one server or a distributed system.
3
How many requests per second?Traffic volume tells us what must be fast and where we need caching or queues.
4
What are the most important features?We optimize and protect the important parts first. Everything else can be simpler.
5
What must be fast, and what can be delayed?Not everything needs instant response. Slow tasks (reports, emails) can run in the background.
6
How much money can the business spend?Budget decides between building, buying, or using a cloud service. Architecture always has a price.
7
How important is downtime?A trading system cannot stop. A blog can be down for an hour. Downtime tolerance decides redundancy level.
8
What happens if the database stops?We must know if we need a backup database, a read replica, or a manual restore plan.
9
What happens if an external service stops?If a payment provider is down, do we queue the order, retry, or show an error? Plan for dependency failure.
10
What data is sensitive?Passwords, payments, personal data need encryption and strict access. Knowing this prevents breaking the law.
11
What are the legal or compliance rules?Rules like GDPR or PCI-DSS decide where data lives and how it is protected. Ignoring them means fines.
12
Who should see what?Role-based access: managers, staff, admins each see different things. This shapes authorization from day one.
13
Is this one customer or many companies (multi-tenant)?Multi-tenant systems must isolate each company's data — a critical security and design decision.
14
How will usage grow in 1–2 years?Design for realistic growth, not fantasy. Building for a million users that never come is wasted money.
15
What are the peak times?Shopping sites spike on holidays, payroll on payday. We design for the peak, not the average.
16
Who will maintain this later?Can the team understand it in 2 years? Complexity has a long-term cost.
17
What happens if the data grows very large?Logs and orders grow forever. We must plan for search, archiving, and splitting data early.
18
What happens if a request fails?Do we retry, show an error, or warn the user? Failure handling must be designed, not left to chance.
19
How do we know the system is healthy?Monitoring and logs tell us when things break before users complain. An architect plans how we watch the system.
20
What happens if a single server or component fails entirely?This reveals “single points of failure.” If one piece takes down everything, we must fix that design.
Rule of thumb: Do not pick a database, framework, or cloud service until these questions have answers. Technology follows the problem, not the other way around.

04Mini Case Study: Online Shopping System

Requirements: users can register, browse products, place orders, pay, and receive notifications. We will NOT jump into technologies yet — first, the thinking.

Step 1 · Understand the problem

An online shopping system lets people create an account, look at products, buy them, pay online, and get updates by email/SMS.


The key insight an architect notices: the flows have different needs.

Step 2 · Key decisions before technology
FlowHow fast must it be?What happens if it fails?How much does it grow?
Browse productsVery fast (under 1s)Not critical — user can retryGrows the most (reads every second)
Place orderFast enoughMust not lose the orderGrows steadily
Make paymentFast but must be correctCritical — must never double-chargeGrows inside the orders
NotificationsCan be slow / delayedCan retry later safelyGrows a lot but can be queued
What this tells us
  • Browsing and payments should NOT compete for the same resources as slow tasks.
  • Notifications do not need to happen instantly — they can be sent later in the background.
  • Orders and payments are the parts we protect the most (reliability).
Step 3 · Thinking through each pillar
R
ReliabilityIf the payment provider is down, do not lose the order — save it and retry. Keep a log of every transaction so nothing is lost after a crash.
P
PerformanceCache the product catalog because it changes rarely but is read constantly. Keep orders and payments fast and separate from heavy reporting.
S
ScalabilityThe product browsing part will grow the most, so make it easy to add more servers for reading. Orders and payments can scale more slowly.
S
SecuritySensitive data is payment and personal details. Hash passwords, encrypt cards, use HTTPS, and let users see only their own orders.
M
MaintainabilityKeep catalog, orders, payments, and notifications as separate responsibilities so one can change without breaking the others.
Step 4 · A simple architecture (concept)

A simple, sensible shape looks like this — but the point is why each part exists, not the tool names:

Things users see (front-end)

  • Web/mobile app for browsing and buying.
  • Talks to APIs, never directly to the database.

Things that work in the back

  • Product service (reads fast, cached).
  • Order service (saves orders reliably).
  • Payment service (talks to payment provider, retries).
  • Notification service (sends emails/SMS in background).
  • User/account service (login and roles).
Important: Separating these responsibilities does not automatically mean microservices. It could start as modules in one application. That is a decision for later — the thinking comes first.

05Architecture Decision Examples

Every decision follows the same pattern: Problem → Options → Pros → Cons → Decision → Why.

Decision 1

Should I use one database or multiple databases?

Problem

The system has many different parts: users, orders, payments, and products. Do they all live in one place?

Options

A) One database for everything. B) A separate database for each major area.

✓ Pros of one database
  • Simple and cheap to run.
  • Easy to query across all data.
  • One backup and one team.
✗ Cons of one database
  • One part can slow down everything.
  • Harder to scale different areas independently.
  • One failure affects all data.
Decision

For a small to medium system, start with one database, but design the code so areas are clearly separated. Split later only when growth demands it.

Why

Simplicity first. Splitting too early adds cost and complexity without clear benefit. But a clean separation makes the future split easier.

Decision 2

Monolith or microservices?

Problem

Should the whole system be one application or split into many small services?

Options

A) One monolith. B) Many microservices.

✓ Pros of monolith
  • Simple to build, test, and deploy.
  • Easy to understand as one codebase.
  • Cheap for a small team.
✗ Cons of microservices (if too early)
  • Needs a lot of infrastructure.
  • Hard to debug across services.
  • Expensive and slow for a small team.
Decision

Start as a monolith (with clean modules). Split into services only when a specific part needs to scale or change independently.

Why

Microservices solve scaling problems, not early-stage problems. Most systems do not need them on day one.

Decision 3

Should I cache data in memory or fetch from the database every time?

Problem

The product catalog is read many times per second but changes rarely. The database is becoming the bottleneck.

Options

A) Always query the database. B) Add a cache (like Redis) in front.

✓ Pros of caching
  • Much faster reads.
  • Less load on the database.
  • Scales reads very well.
✗ Cons of caching
  • Adds complexity (stale data).
  • One more technology to run and monitor.
Decision

Cache data that is read often but changes rarely (products). Do not cache orders or payments, where correctness matters most.

Why

Cache fits “read a lot, change rarely.” It is wrong for data that must always be accurate.

Decision 4

Should notifications be sent immediately or in the background?

Problem

When an order is placed, the system sends an email. If the email server is slow, the whole order feels slow.

Options

A) Send email directly during the request. B) Put it in a queue and process it later (RabbitMQ).

✓ Pros of queuing
  • The user gets fast feedback.
  • Email failures can be retried.
  • Slow tasks do not slow fast ones.
✗ Cons of queuing
  • Slightly more infrastructure.
  • Delayed delivery (email arrives later).
Decision

Queue the notification and send it in the background. Keep the order response fast.

Why

Notifications can be delayed and retried safely. The user experience (fast order) is more important than instant email.

Decision 5

Should I store passwords myself or use an external authentication service?

Problem

The system needs login. Building secure login correctly is hard and mistakes are costly.

Options

A) Build login and password handling myself. B) Use a proven identity provider (Azure AD, Okta).

✓ Pros of a provider
  • Security handled by experts.
  • Adds MFA easily.
  • Less risk of mistakes.
✗ Cons of a provider
  • Ongoing cost.
  • Less control.
  • Dependency on a third party.
Decision

For most business systems, use a proven identity provider for authentication. Build custom authorization (roles/permissions) yourself.

Why

Authentication is a “solved problem” where mistakes are very expensive. Reuse the proven solution and focus your effort on your business rules.

There is rarely one perfect technology.

The architect chooses based on the problem, the constraints, and the trade-offs — not based on what is popular.

0610 Common Mistakes When Moving Toward Architecture

Honest, direct advice. Almost every architect has made some of these mistakes.

1
Choosing technology before understanding the problemYou pick “Kubernetes” or “microservices” before knowing the users, traffic, or budget. The problem must shape the technology, not the reverse.
2
Using microservices everywhereMicroservices add networking, monitoring, and debugging complexity. They are a solution to a scaling problem, not a default style.
3
Ignoring failure scenariosDesigning only the “happy path.” If the database, payment, or email service fails, nobody knows what happens.
4
Ignoring costA design can be technically beautiful but far too expensive to run. Every architect decision has a price tag.
5
Ignoring security until the endSecurity added later is fragile. Access control and data protection must be part of the design from day one.
6
Designing for unrealistic scaleBuilding for “millions of users” when you have 500. That over-investment wastes time and money now.
7
OverengineeringAdding queues, caches, and services that are not needed yet. Complexity is a cost, not a trophy.
8
Copying another project's architecture“We did this at my last job, so we'll do it here.” Different problems need different designs.
9
Forgetting the people who maintain itA design only you understand will fail the moment you leave. Architecture must be understandable by the team.
10
Not writing down decisionsIf you choose an option and don't record why, future teams will question (and often reverse) it without understanding the context.

08Self-Assessment: Check Your Understanding

Answer these 10 thinking questions honestly. If you cannot explain them in your own words, review that part of Day 1.

1
In your own words, what is software architecture — and how is it different from writing code?Tests whether you understand the shift from “making it work” to “making it survive.”
2
A user says the app is slow. List at least four different possible causes and how you would find the real one.Tests your performance thinking — database, API, network, or code, not just “add a cache.”
3
Imagine traffic suddenly becomes 10x. Which part of your system breaks first, and why?Tests whether you can reason about bottlenecks and scalability.
4
What is the difference between authentication and authorization? Give a concrete example.Tests a security fundamental you must be able to explain instantly.
5
Your database goes down at 2 AM. Walk through exactly what happens to your system and users, step by step.Tests whether you genuinely think about failure, not just design happy paths.
6
Explain reliability, performance, scalability, security, and maintainability in one sentence each — without jargon.Tests whether you can communicate architecture simply (a key architect skill).
7
When would you NOT choose microservices even though they are popular?Tests whether you choose based on the problem, not on trends.
8
A system must handle payments. List two ways to make sure a payment is neither lost nor charged twice.Tests reliability and correctness thinking for critical data.
9
For a multi-tenant SaaS, how do you make absolutely sure one company can never see another company's data?Tests your understanding of data isolation — the trickiest security risk in multi-tenant systems.
10
Pick any two design choices. Explain one you would accept, and one you would reject — and justify both.Tests your ability to make and defend a decision, which is the core of the architect role.

★Architect Mindset for Day 1

Five powerful rules to carry through the entire 30-day program.

1
The problem comes first, the technology second.Never pick a tool until you understand the users, the traffic, the money, and the risk. Technology is a means, not a goal.
2
Every decision is a trade-off.There is no perfect choice — only the best choice for this problem and these constraints. Always ask: what do we gain, and what do we lose?
3
Design for failure, not just success.The happy path is easy. An architect asks what happens when the database dies, the payment fails, or 10x traffic arrives.
4
Simple is a feature.Complexity has a real cost in money, time, and bugs. Start simple, and add complexity only when the problem truly demands it.
5
Be able to explain why.Anyone can choose an option. The architect is the person who can justify the choice — and justify rejecting the alternatives.
