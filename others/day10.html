SECTION 01 — THE REAL PROBLEM

Why Teams Use Containers

Not because containers are modern. Because the same application behaved differently on three machines, and everybody lost a week finding out why.

Directly on a server

The old shape

Your ASP.NET Core app is published to a Windows VM. IIS is configured by hand. The .NET runtime is whatever version was installed. A registry setting, a certificate and an environment variable were added "temporarily" in 2021.

  • Different environments: dev has .NET 8.0.3, staging has 8.0.7, production has an old hotfix. Same code, three behaviours.
  • Dependency conflicts: two apps on one server need different versions of the same native library. One of them loses.
  • "Works on my machine": nobody can reproduce the bug because nobody can reproduce the machine.
  • Deployment inconsistency: a checklist, a script, and one person who knows the missing step.
  • Difficult scaling: a new server means repeating the manual setup — and it will differ.
  • Difficult rollback: "put the old files back" is not a rollback; the config drifted with them.

Inside a container

The fix

The same app is packaged with its runtime, its dependencies and its startup rules into one immutable image. That image runs identically on your laptop, in CI, in staging and in production.

  • One artefact: the thing you tested is the thing that ships. Byte for byte.
  • No conflicts: each container carries its own dependencies; two apps with two library versions coexist happily.
  • Reproducible: "works on my machine" becomes "works in this image", and the image is portable.
  • Deploy = run this image: the same command everywhere; no checklist, no tribal knowledge.
  • Scaling: run the same image ten more times. Nothing to set up.
  • Rollback: run the previous image tag. Seconds, and genuinely the old behaviour.
THE ARCHITECT'S ONE-LINE SUMMARY

A container turns "a deployment" (a process, a checklist, a hope) into "an artefact" (a versioned, immutable thing you can run, copy, scale and roll back). That is the whole value — and it is a big one, entirely independent of Kubernetes.

SECTION 02 — THE VOCABULARY

What Is a Container?

Four words. Learn them as a pipeline, not as definitions.

IMAGEA read-only package containing your app, the .NET runtime it needs, and its dependencies. Think of it as a class: a definition, sitting still. It has a tag (orders-api:2.4.1) and never changes once built — build 2.4.1 today or next year and you get the same bytes.
CONTAINERA running instance of an image. Think of it as an object: created from the class, alive, doing work, and disposable. Ten containers from one image are ten identical processes — and killing one loses nothing, because the image is the truth.
DOCKERFILEThe recipe that builds the image: start from the .NET runtime base, copy the published output, set the entry point. Its value to an architect is not the syntax — it is that the build becomes written down and repeatable instead of living in someone's head.
REGISTRYThe library of images: Azure Container Registry, AWS ECR, Docker Hub. CI pushes a tagged image; every environment pulls the same tag. The registry is what makes "the thing we tested is the thing we ship" literally true across machines.
THE INTERVIEW SENTENCE

"An image is the immutable package; a container is a running copy of it. We build one image in CI, push it to a registry with a version tag, and every environment runs that same tag. Rollback is just running the previous tag."

SECTION 03 — THE COMPARISON

Containers vs Virtual Machines

A VM virtualises a machine. A container virtualises a process environment. That one difference explains every row below.

AREA CONTAINER VIRTUAL MACHINE
Startup Seconds or less — it is just a process starting. Tens of seconds to minutes — a whole operating system boots.
Resource usage Light. Shares the host OS kernel; megabytes of overhead. Dozens fit on one machine. Heavy. Each VM carries its own OS — gigabytes of RAM and disk before your app starts.
Isolation Process-level. Good, but a shared kernel means the boundary is thinner. Hardware-level. Stronger separation — the right answer when isolation is a compliance requirement.
Scaling Fast and granular — start ten more copies in seconds, autoscale on demand. Slow and coarse — provisioning a VM is a minutes-long operation.
Operating system Shares the host kernel. Linux containers on Linux hosts (Windows containers exist but are heavier). Full guest OS per VM — you can run any OS on any host.
Typical use Stateless apps and APIs, microservices, workers, CI jobs, anything you scale horizontally. Legacy applications, workloads needing a specific OS or kernel, strong isolation, stateful systems you do not want to containerise.
WHEN EACH IS APPROPRIATE

Container: your ASP.NET Core API, your background workers, anything stateless you want to deploy often and scale quickly. VM: a legacy Windows app that will never be re-platformed, a workload with a hard isolation requirement, or a database you have deliberately decided not to containerise. They are not rivals — a Kubernetes cluster is a set of VMs running containers.

SECTION 04 — .NET IN A BOX

Docker for an ASP.NET Core Application

The flow, and — more importantly — what changes about how you think when the app moves into a container.

What changes when you containerise

CONFIGURATIONConfig stops living inside the artefact. The same image runs in dev, staging and production — so anything that differs between them must come from outside at start-up. One image, many configurations.
ENVIRONMENT VARIABLESThe standard way to inject that config. ASP.NET Core reads them natively, so ConnectionStrings__Orders or ASPNETCORE_ENVIRONMENT arrive from the platform, not from a file baked into the image.
SECRETSNever in the image — an image is copied, shared and stored in a registry. Secrets come from the platform's vault at run time (Key Vault / Secrets Manager, or the orchestrator's secret object). Day 8's rule, unchanged: the artefact holds nothing secret.
LOGGINGStop writing log files to disk — the disk disappears when the container does. Write structured logs to stdout; the platform collects them into App Insights, CloudWatch or your log store. Correlation ids matter more than ever, because instances are anonymous and short-lived.
PERSISTENT DATAContainers are ephemeral: anything written inside one is gone when it restarts. Uploaded files go to Blob/S3, state goes to the database, sessions go to Redis. If your app writes to local disk today, that is the work item before containerising.
THE MENTAL SHIFTYou stop thinking about servers you maintain and start thinking about instances that come and go. Statelessness stops being a nice-to-have (Day 2) and becomes the entry requirement.
THE ONE THING THAT BREAKS FIRST

Almost every .NET app being containerised for the first time trips on the same three things: local file writes, in-memory session state, and config baked into the build. Fix those and the container part is nearly free. Ignore them and you will blame Docker for a design problem.

SECTION 05 — THE REAL QUESTION

"Why Do I Need Kubernetes?"

Containers solved packaging. They solved nothing about running forty of them, at 3 a.m., while one keeps crashing.

Put ten containerised services into production and a second set of problems appears — none of which Docker itself answers:

MANY CONTAINERSWhich machine does each one run on? Who decides, and who re-decides when a machine fills up?
SCALINGTraffic tripled. Who notices, who starts more copies, and who stops them again at midnight?
RESTARTING FAILURESA container dies at 02:14. Who restarts it — and what if it keeps dying?
TRAFFIC DISTRIBUTIONFive copies exist. Who spreads requests across them and stops sending traffic to the unhealthy one?
DEPLOYMENTVersion 2.4.2 must replace 2.4.1 across twenty containers without dropping a request.
ROLLBACK2.4.2 is bad. Who moves everything back — quickly, and without a spreadsheet?
SERVICE DISCOVERYThe orders service must call the pricing service. Containers move and get new addresses constantly. Who keeps the address book?
HEALTH CHECKSA container is running but not working — deadlocked, or waiting on a dead dependency. Who tells the difference and acts?

Doing all of that with scripts and human attention is container orchestration by hand. Kubernetes is the software that does it for you — and that is the honest, complete answer to "why Kubernetes".

BUT NOTICE THE TRAP

Every problem in that list is also solved by a managed platform — App Service, Container Apps, ECS Fargate all restart, scale, route and roll back for you. So the architect's question is never "do I have these problems?" (everyone does). It is: "do I have them in a shape that a managed platform cannot handle?" Sections 9–11 answer exactly that, and it is where the interview is won.

SECTION 06 — THE VOCABULARY

Kubernetes in Simple English

Kubernetes is a system that manages many containers for you. You tell it what you want ("five copies of this image, reachable here, restarted if they die"), and it keeps reality matching that description. Ten concepts is all an architect needs.

CLUSTERWhat: the whole system — a set of machines Kubernetes manages as one pool. Why: you stop thinking about individual servers and start thinking about capacity. Example: "our production cluster has 6 machines" — you never say which one your app is on.
NODEWhat: one machine (usually a VM) in the cluster that actually runs containers. Why: nodes are where CPU and memory really live — and nodes fail. Example: node-3 dies at 2 a.m.; Kubernetes moves its work to nodes 1, 2 and 4.
PODWhat: the smallest unit Kubernetes runs — usually one container (sometimes a main container plus a small helper). Why: Kubernetes schedules, restarts and scales pods, not containers. Example: one pod = one instance of your orders API.
DEPLOYMENTWhat: your declaration: "run 5 pods of image orders-api:2.4.1". Why: it maintains that number and manages version changes and rollbacks. Example: change the image tag to 2.4.2 and the Deployment replaces pods gradually.
SERVICEWhat: a stable internal address for a set of pods. Why: pods die and get new IPs constantly; callers need one name that keeps working. Example: the checkout pods call http://pricing and never know which pod answered.
INGRESSWhat: the entry point for traffic from outside the cluster, with routing and TLS. Why: without it, nothing on the internet can reach your pods. Example: /api/orders goes to the orders Service, /api/catalog to the catalog Service.
CONFIGMAPWhat: non-secret configuration held outside the image and injected into pods. Why: one image, many environments (Section 4's rule, implemented). Example: feature flags, timeouts, the environment name.
SECRETWhat: the same idea for sensitive values, handled with more care and normally backed by a real vault. Why: secrets must never be inside an image. Example: the database connection string injected at start-up — ideally sourced from Key Vault or Secrets Manager.
HEALTH CHECKWhat: two endpoints your app exposes — am I alive? (liveness) and am I ready for traffic? (readiness). Why: this is how Kubernetes tells "running" from "working". Example: readiness returns false while the cache warms, so no traffic arrives too early.
AUTO SCALINGWhat: rules that change the number of pods automatically. Why: traffic is not constant, and neither should your capacity be. Example: "keep CPU near 60% — between 3 and 30 pods." Cluster autoscaling adds machines when pods have nowhere to fit.
THE 20-SECOND INTERVIEW ANSWER

"A cluster is a pool of nodes. A Deployment says how many pods of an image should run. A Service gives those pods one stable address, and Ingress lets outside traffic in. ConfigMaps and Secrets inject configuration so one image works everywhere. Health checks tell Kubernetes whether a pod is really working, and autoscaling changes the pod count with load. Kubernetes' whole job is keeping reality equal to that declaration."

SECTION 07 — THE SHAPE

Kubernetes Architecture

How it keeps the application running

A POD CRASHES

One of three pods dies

WHAT HAPPENSThe Deployment notices reality (2 pods) no longer matches the declaration (3 pods) and starts a replacement from the same image. The Service immediately stops routing traffic to the dead pod.
USER IMPACTNone, if the other pods have capacity — in-flight requests on that pod fail and are retried by the client or the gateway.
THE CATCHOnly true if the app is stateless and health checks are honest. A pod that is "running" but deadlocked keeps receiving traffic unless liveness catches it.
TRAFFIC INCREASES

Peak hour arrives

WHAT HAPPENSThe autoscaler sees CPU (or a custom metric like queue depth) cross the target and increases the pod count. The Service starts routing to the new pods as they pass readiness.
THE CATCHPods scale in seconds; nodes take minutes. If the cluster has no spare capacity, new pods sit "Pending" while the cluster autoscaler provisions a machine. Plan headroom for spikes.
NEW VERSION

Deploying 2.4.2

WHAT HAPPENSYou change the image tag. The Deployment performs a rolling update: start a new pod, wait for readiness, remove an old one, repeat — so capacity never drops and no request hits a half-started pod.
THE CATCHRolling means both versions run simultaneously for a while. Your database schema and your API contract must tolerate that (Section 14).
A NODE FAILS

An entire machine disappears

WHAT HAPPENSEvery pod on that node is lost. Kubernetes detects the node is unhealthy and reschedules those pods onto the remaining nodes; the cluster autoscaler may add a replacement machine.
THE CATCHThe remaining nodes must have room. A cluster running at 95% capacity cannot absorb a node loss — spare capacity is the price of surviving one.
SECTION 08 — GROWING

Scaling: The Application vs the Cluster

Two different things, often confused in interviews — and the confusion causes real outages.

Scaling the application

More pods

More copies of your container. Fast (seconds), granular, and the everyday lever.

Limited by: the free CPU and memory already available in the cluster. When there is no room, new pods wait.

Scaling the cluster

More machines

More nodes for pods to run on. Slower (minutes), coarser, and directly a cost decision.

Needed when: pods are pending because the existing machines are full.

THE TRAP EVERY SENIOR HITS ONCE

Scaling from 10 to 50 pods multiplies your database connections by five. The app tier scales beautifully and the database falls over — the Day 2 lesson, wearing a Kubernetes hat. Always ask: "when the app scales, what downstream thing gets five times the load?" Connection pooling limits and a maximum pod count are not optional.

SECTION 09 — THE INTERVIEW TABLE

App Service vs Container Apps vs AKS vs ECS vs EKS

The single most useful table on this page. Learn the shape of it, not the wording.

PLATFORM EASE OF USE CONTROL OPERATIONAL EFFORT SCALING BEST USE CASE
Azure App Service Highest — deploy code or a container, done. Lowest — the platform decides most things. Very low. No cluster, no nodes, no upgrades. Automatic, instance-based, per plan. A .NET web app or API. The default answer for a single deployable.
Azure Container Apps High — containers without a cluster. Medium — revisions, ingress, scale rules, some networking. Low. Serverless containers; Kubernetes is hidden. Event- and HTTP-driven, can scale to zero. Containerised APIs and background workers, microservices without cluster ownership.
AKS (Azure Kubernetes Service) Lowest — you meet Kubernetes directly. Highest — full control of networking, scheduling, the ecosystem. High. Upgrades, node pools, add-ons, security, on-call expertise. Fully customisable — HPA, custom metrics, node autoscaling. Many services, custom infrastructure, a team that already runs Kubernetes.
AWS ECS (Fargate) High — AWS-native container running, no cluster to manage on Fargate. Medium — good control without Kubernetes concepts. Low with Fargate; moderate with EC2 launch type. Service auto scaling on metrics. AWS shops that want containers without Kubernetes. The ACA-equivalent answer.
AWS EKS Lowest — managed Kubernetes, same learning curve as AKS. Highest, plus the Kubernetes ecosystem. High — same operational reality as AKS. Fully customisable. AWS shops with real Kubernetes requirements or existing K8s workloads.
WHY AKS/EKS SHOULD NOT BE THE AUTOMATIC ANSWER

Because "powerful" is not a requirement. Kubernetes gives you control you must then exercise: version upgrades, node pool sizing, network policy, RBAC, ingress controllers, certificate rotation, cluster monitoring, and someone reachable at 3 a.m. who understands all of it. That is a permanent staffing and cash cost. A managed platform trades some control for someone else carrying that load — and for most .NET systems, that trade is correct. Choose AKS when you can name the specific control you need and the team who will operate it. Otherwise you have bought a platform team's workload to run one API.

SECTION 10 — THE HONEST SECTION

When NOT to Use Kubernetes

The section most tutorials skip and most interviews reward. Kubernetes solves real problems — and creates real operational complexity. If you are not buying the first, you are only buying the second.

1 · A small application

One API and a database. Kubernetes adds a control plane, manifests, ingress and node management to run something App Service runs with a deploy button.

2 · A small team

Under ~10 engineers with no dedicated platform person, Kubernetes work comes out of feature time — permanently. Somebody becomes the accidental cluster admin.

3 · Low or predictable traffic

Steady, modest load needs no sophisticated orchestration. Two instances behind a managed load balancer already survive an instance failure.

4 · Few services

Kubernetes shines at coordinating many moving parts. With two or three services, there is very little to coordinate.

5 · Simple deployment needs

If "replace the app and restart" at a known time is acceptable, you do not need rolling updates, canaries and pod disruption budgets.

6 · No advanced orchestration requirement

No custom schedulers, no sidecars, no service mesh, no operators — then you are paying for a toolbox to use one screwdriver.

7 · The team does not know Kubernetes

You will learn it during your first production incident. Managed platforms let the team ship while the skill is built deliberately, not under pressure.

8 · Tight budget

Control plane, node headroom, monitoring, and the engineer-time to run it. A comparable managed setup is usually dramatically cheaper end to end.

9 · Mostly stateful or legacy workloads

Databases and legacy Windows apps in containers add difficulty without benefit. Use managed data services; leave the legacy on a VM.

10 · A managed platform already meets every requirement

The decisive one. If Container Apps or ECS Fargate does everything on your list, Kubernetes is complexity with no matching problem.

THE SENTENCE TO REMEMBER

Kubernetes is not a scaling decision — it is an operating-model decision. You are not choosing "can it scale" (everything here scales). You are choosing whether your organisation will own and operate a platform. Say that in an interview and you sound like someone who has actually paid the bill.

SECTION 11 — THE OTHER SIDE

When Kubernetes Makes Sense

It is genuinely the right answer more often than the sceptics admit — when these conditions are actually true.

1 · Many services

Fifteen or more services with independent lifecycles need real scheduling, discovery and routing. Coordinating that by hand is worse than learning Kubernetes.

2 · Large production workloads

Hundreds of instances across many machines: bin-packing, node pools and resource governance genuinely save money at this size.

3 · Frequent deployments

Many deploys a day across many services makes rolling updates, automated rollback and canaries a daily necessity, not a luxury.

4 · Multiple environments

Dev, test, staging, several production tenants — one declarative definition applied everywhere beats maintaining parallel platform configs.

5 · Advanced scaling needs

Scaling on custom metrics (queue depth, per-tenant load), GPU pools, spot instances, or mixed workload classes on shared capacity.

6 · A large engineering team

Enough people that a platform team is justified — then Kubernetes becomes leverage for dozens of engineers instead of a tax on five.

7 · Strong container control required

Specific networking, sidecars, service mesh, mTLS between services, strict placement or compliance-driven isolation that managed platforms will not expose.

8 · Platform engineering / portability

You are deliberately building an internal platform, or you need the same substrate across clouds and on-premises. Kubernetes is the common denominator.

THE TEST

Count how many of those eight are true today — not aspirationally. Zero or one: use a managed platform. Two or three: managed platform, and write down the trigger to revisit. Four or more, plus a team that can operate it: Kubernetes is a defensible decision, and you can say why.
