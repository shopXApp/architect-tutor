SECTION 01 — THE PROBLEM

Start With the Real Problem

A system does not break because it has "users." It breaks because more of everything arrives at once. Same code. Same database. Different physics.

Watch what changes when the number after "users:" grows from 100 to 10,000 to 1,000,000. Six things grow — and each one quietly becomes a bottleneck in its own turn.

MORE REQUESTS100 users might generate 2 requests per second. 100,000 users can generate thousands per second. The application server, its thread pool, and its connection limits all feel this first.
MORE DATABASE QUERIESEvery page means queries. Multiply traffic by 100 and the database — the part that holds the truth and touches the disk — usually melts before anything else does.
MORE MEMORY USAGESessions in memory, in-process caches, connection pools, buffers for uploads. Memory does not degrade gracefully — it runs out, then the server restarts mid-request, losing the work in flight.
MORE NETWORK TRAFFICPages, images, JSON payloads — all cross the wire. Without planning, a 2 MB product image multiplied by a million views becomes terabytes and a very slow phone.
MORE CONCURRENT USERSConcurrency is the killer detail. 100 users spread over a day is relaxing. 1,000 users in the same second is a queue, a lock wait, and a cascade. Concurrency, not totals, decides the design.
MORE FAILURESAt 100 users a failure is a nuisance. At 1,000,000 the law of large numbers guarantees that something is failing right now — a disk, a node, a vendor. Reliability design (Day 1) is no longer optional.

Small system → Growing system → Large system

 SMALL — 100 usersGROWING — 10,000 usersLARGE — 1,000,000 users
What it looks like One app server, one database. Closed lunch breaks. Zero drama. A real product: daily spikes, a report that slows the app, the first 3 a.m. call. A platform: autoscaling pools, caches, queues, replicas — and something failing every day by design.
Breaks first Nothing. The box yawns. The app server’s CPU or the database’s disk — whichever the unmeasured query lives on. The database write master, then external dependencies, then whatever you forgot to monitor.
What you add first Nightly backup. That is enough. Load balancer + second stateless app server, cache for hot reads, queue for slow work. Everything from growing ×10 — plus read replicas, CDN, autoscaling, and real alerting.
Mindset "Keep it simple." "Measure, then fix the weakest part." "Assume failure; design the blast radius; automate recovery."
KEY TAKEAWAY

Growth does not break your whole system at once. It kills one weak part at a time, in a mostly predictable order: app server → database → network → external services. Your job today is learning to see which part is about to be next.

SECTION 02 — MEASURE FIRST

Understand Load Before Designing

Saying "our system has 1 million users" is marketing. An architect translates it into requests per second at peak — because that is the number the servers actually serve.

USERA registered account. A story about reach — not a load. Most of them are asleep right now.
DAILY ACTIVE USER (DAU)How many users actually show up per day. Typically 5–20% of registered users for e-commerce, 3×–5× that for social media.
REQUESTOne action: a page view, an API call, an image fetch. One user visit creates dozens of requests.
REQUESTS PER SECOND (RPS)The true unit of load. RPS = daily requests ÷ 86,400 seconds. Every sizing decision multiplies from this number.
CONCURRENT USERSUsers with a request in flight at the same moment. This strains thread pools, DB connections and memory — the dimensions that fail suddenly, not gradually.
PEAK vs AVERAGE TRAFFICTraffic is never flat. Lunch, campaigns, payday. Peak is typically 3–10× average. You size for peak; average decides your monthly bill.
RESPONSE TIMEHow long one request takes — and which fraction of users suffer: the p95 (worst 5%) matters more than the average. Average hides pain.
READ : WRITE RATIOReads scale cheaply with cache; writes must reach the database. 95% read → a caching design. 50% write → a database design. Same "load," opposite architectures.
THE DISTINCTION THAT WINS INTERVIEWS

1 million registered users does NOT mean 1 million users sending requests at the same time. It means: maybe 100,000 show up daily, 10,000 are active at peak hour, and the system must answer ~2,000 requests per second. Architecture is designed for the last number. This distinction alone separates senior answers from junior ones.

THE FORMULA CHAIN — MEMORIZE IT

Registered users × % daily active = DAU · DAU × requests-per-user-per-day = daily requests · ÷ 86,400 = average RPS · × peak factor (3–10) = peak RPS. Four multiplications that replace a week of guessing.

LIVE CAPACITY CALCULATOR — TRY THE ASSUMPTIONS

DAILY ACTIVE USERS—registered × active%
AVERAGE RPS—dau × reqs/day ÷ 86,400s
PEAK RPS — THE NUMBER YOU SIZE FOR—avg × peak factor
RULE OF THUMB: PEAK ≈ 3–10× AVERAGE. WITH 1M REGISTERED / 10% DAU / 50 REQ / ×8 → ROUGHLY 460 PEAK RPS. THE SYSTEM BELOW IS DESIGNED FOR 4× THAT HEADROOM.

Five worked calculations — step by step

Same formula, five industries. Notice how the shape of traffic changes the architecture more than the size of it.

EXAMPLE 1 · E-COMMERCE

Fashion shop

KNOWN1,000,000 registered users · 8% daily active · 60 requests per user per day · flash sales cause ×8 peaks.
STEP 1DAU = 1,000,000 × 0.08 = 80,000 users/day.
STEP 2Daily requests = 80,000 × 60 = 4,800,000.
STEP 3Average RPS = 4,800,000 ÷ 86,400 ≈ 56.
STEP 4Peak RPS = 56 × 8 ≈ 450.
⇒ DESIGN FOR ~500 RPS PEAK — SEVERAL APP SERVERS + CACHE ARE PLENTY. NOT A GOOGLE-SCALE PROBLEM.
EXAMPLE 2 · BANKING

Corporate banking portal

KNOWN40,000 corporate users · 30% daily · 120 requests/day each · salary days spike ×3.
STEP 1DAU = 40,000 × 0.30 = 12,000.
STEP 2Daily requests = 12,000 × 120 = 1,440,000.
STEP 3Average RPS ≈ 1,440,000 ÷ 86,400 ≈ 17; peak ≈ 50.
STEP 4Traffic is trivial. But every write must be exact, and downtime is measured in regulator phone calls.
⇒ TINY LOAD, HUGE CONSEQUENCES. THE ARCHITECTURE MONEY GOES INTO CONSISTENCY AND AVAILABILITY, NOT CAPACITY.
EXAMPLE 3 · FOOD DELIVERY

Lunch-time spike

KNOWN200,000 registered · 25% daily · 40 requests/day · lunch and dinner spikes ×15 average.
STEP 1DAU = 200,000 × 0.25 = 50,000.
STEP 2Daily requests = 50,000 × 40 = 2,000,000.
STEP 3Average RPS ≈ 23; peak ≈ 23 × 15 ≈ 350 — but for only 90 minutes, twice a day.
STEP 4Traffic collapses between meals. Paying for 350 RPS 24/7 is waste; autoscaling up at 11:30 and down at 14:00 is the design.
⇒ A SCHEDULE-SHAPED PROBLEM. AUTOSCALING AND QUEUE-ABSORBED SPIKES, NOT PERMANENT BIG MACHINES.
EXAMPLE 4 · SAAS

Multi-tenant business tool

KNOWN100 companies × 100 users = 10,000 users · 60% daily · 200 requests/day · modest ×4 peaks.
STEP 1DAU = 10,000 × 0.6 = 6,000.
STEP 2Daily requests = 6,000 × 200 = 1,200,000 → average RPS ≈ 14; peak ≈ 56.
STEP 3One beefy pair of servers handles this. The problems are elsewhere: tenant data isolation, per-tenant reporting, one noisy tenant hogging the pool.
⇒ SCALE IS NOT THE ISSUE AT ALL — ISOLATION AND PER-TENANT FAIRNESS ARE. THAT IS WHERE THE ARCHITECTURE GOES.
EXAMPLE 5 · SOCIAL MEDIA

A photo feed

KNOWN5,000,000 registered · 40% daily · 150 requests/day (feeds are read-hungry) · peaks ×3.
STEP 1DAU = 5,000,000 × 0.4 = 2,000,000.
STEP 2Daily requests = 2,000,000 × 150 = 300,000,000 → average RPS ≈ 3,470; peak ≈ 10,400.
STEP 3~95% of requests are reads of photos and feeds → CDN carries the bytes, cache carries the feed, the database only sees misses and writes.
⇒ THE READ : WRITE RATIO IS THE ARCHITECTURE: CDN + CACHE DO THE WORK; THE DB SERVES THE REST.
INTERVIEW ANGLE

When the interviewer says "1 million users," do this calculation out loud on the whiteboard, with clearly stated assumptions. Deriving 2,000 RPS from 1,000,000 users in four multiplications is the answer. Every diagram you draw afterwards just follows from it.

SECTION 03 — THE HUNT

Find the Bottleneck

"The whole system is limited by its weakest part." Strengthening anything else — even heroically — changes nothing.

Picture a wooden barrel: the water level is set by the shortest stave, never by the tallest. A second app server next to a dying database is a taller stave. Nobody notices.

APPLICATION SERVERSymptoms: CPU pinned at 100%, thread pool exhausted, slow everything. Checks: CPU%, thread/worker wait, GC pauses, connection pool usage.
DATABASESymptoms: DB CPU 95%, slow-query log exploding, lock waits, connection pool starved. Most common culprit in load growth — the part that owns state and touches disk.
NETWORKSymptoms: far users are slow, images crawl, everything is fine on the office LAN. Checks: payload sizes, geographic latency, bandwidth saturation.
EXTERNAL APISymptoms: your p95 tracks their p95; timeouts and retries cascade; random hangs at checkout. Checks: the partner's latency and error rates, not only yours.
FILE STORAGESymptoms: uploads or exports stall, memory balloons on large files (buffering in RAM), disk I/O saturation. Checks: streaming vs buffering, disk queue depth.
CACHESymptoms: hit ratio dropping, latency rising, DB load climbing in parallel — or an outage that re-exposes a database which was secretly never scaled at all. The cache is a shield; know what happens the day it falls.
THE DIAGNOSTIC LOOP

1) Measure response time — average and p95. 2) Watch which resource sits at 95–100% — CPU, connections, disk, a partner's latency. 3) Fix that and that only. 4) Re-measure: the bottleneck always moves — to the next component in line. An exhaustive "optimize everything" pass means nobody measured.

Your turn: spot the bottleneck

Five real-world-shaped scenarios. Read the metrics, pick the culprit, then read the reasoning. Answers lock on first click.

Lesson: a cache is a shield, and you must design for the day the shield falls — fallback reads, rate limiting, serving stale data, and an alarm on hit ratio, not only on uptime.
SECTION 04 — THE TWO LEVERS

Vertical vs Horizontal Scaling

When a machine is too slow you have exactly two moves: make the box stronger, or get more boxes. Everything in scaling is a variation of these two levers.

Vertical — “Scale Up”

One box, more muscle

Add CPU, RAM, faster disks to the same server. The code does not change at all — it just runs on a bigger machine.

Advantages: zero architecture change; one machine to run, monitor and back up; perfect when the team and the system are small.

Disadvantages: a hard ceiling (there is a biggest box you can rent); usually downtime to upgrade; price grows faster than power at the top end; one box still means one failure takes you down.

Horizontal — “Scale Out”

More boxes, same muscle

Add more servers behind a load balancer and let traffic spread across them. Capacity grows by adding machines, at roughly linear cost.

Advantages: almost no ceiling; fault isolation — one dead server is a slowdown, not an outage; cloud platforms can add and remove boxes automatically with demand (autoscaling).

Disadvantages: your app must be stateless (Section 8); more machines means more deploys, more logs, more monitoring; a load balancer becomes part of the life story.

REAL-WORLD ANALOGY — THE KITCHEN

Vertical: replace your cook with a stronger cook — one person with four arms and a jetpack. Works until dinner rush; impossible past human limits; tonight the superstar is sick, and the restaurant closes. Horizontal: hire more cooks and put one expeditor (the load balancer) at the pass handing out tickets. Each cook is ordinary; the kitchen survives any single flu and grows with bookings.

 VERTICAL (UP)HORIZONTAL (OUT)
What changesThe machine.The architecture — load balancing, statelessness, monitoring ×N.
Cost curveCheap at the bottom, steep at the top (big boxes are luxury items).Modest start, grows roughly linearly with load. Autoscaling can shrink the bill between spikes.
Failure impactThe one box dies → the system is down. Blast radius: everything.One server dies → the rest absorb the traffic. Blast radius: a fraction.
CeilingHardware limits, reached sooner than you think.Effectively none for stateless tiers; you add until the database calls for help.

WHY MODERN WEB SYSTEMS PICK HORIZONTAL

Three reasons: no ceiling, small blast radius, and cloud economics — paying for 20 machines during the spike and 4 machines at night. The nuance seniors add: scale the app tier out, scale the database writer up — then add replicas for reads (Section 7). Each tier gets the lever that fits its physics.

SECTION 05 — THE DOOR

The Load Balancer

A load balancer is one door with many rooms behind it. Users see a single address; the balancer decides which (healthy) server actually serves each request.

The flow is exactly this: User → Load Balancer → Server 1 / Server 2 / Server 3. Its four real jobs: distribute traffic evenly, health-check every server (a small "are you alive?" request every few seconds), remove a server that stops answering — automatically and silently — and be the single public entry point (including TLS).

LIVE DEMO — WATCH THE REQUESTS, THEN KILL SERVER 2

STATUS: ALL HEALTHY — THE LB SENDS EACH NEW REQUEST ONLY TO SERVERS THAT ANSWER THEIR HEALTH CHECK.
WHY IT IS NEEDED

Without the balancer, "add a server" is a lie — there is nobody to split traffic, nobody to notice a death, and the day one server dies, you are the failover mechanism. The LB is what turns "servers" into "capacity that heals itself."

The hidden trap: session data inside one server

Look what happens the second you add a balancer to a system that stores login sessions in server memory: the login lands on Server 1, the session lives only there, and the next request — routed to Server 2 — meets a stranger. The user is "logged out" every other click.

BROKEN — memory on one machine

Request 2 ≠ Server 1

Sessions, temp data, in-memory jobs, uploaded files — anything living inside one box's RAM or disk belongs to that box. Horizontal scaling turns it into roulette: 1 server in 3 remembers the user.

FIXED — shared session store

Any server can answer

Move the session to a shared place all servers can read — a cache or the database — or make requests self-describing with signed tokens. Now the LB's choice stops mattering: any server answers any request.

ABOUT "STICKY SESSIONS"

You can make the LB pin a user to one server. It is a bandage: it hides the state problem, breaks when the server dies, and ruins even distribution. Architects accept it briefly while migrating — never as the destination. The destination is stateless (Section 8).

SECTION 06 — THE SHIELD

Caching

Every read the cache answers is a read the database never sees. The fastest query in the world is the one you never run.

WHAT TO CACHEData read far more often than it changes and safe to serve slightly old: product catalog, configuration, prices (until change), user profiles, search suggestions, home pages.
WHAT NOT TO CACHEAnything where stale = wrong: account balances, stock counts at checkout, payment state, one-time tokens, and data so personal that serving the neighbor's copy is a breach.
CACHE HITLook in cache, answer found — ~1–5 ms. This is the shield catching an arrow.
CACHE MISSNot found → go to the database (~30–100 ms), then store a copy so the next read is a hit. Hits should be 90%+ of reads on cacheable data.
EXPIRATION (TTL)"This copy is trustworthy for 10 minutes." On expiry, the next read refreshes from the DB. A small random jitter on TTLs stops all keys from expiring at the same minute.
STALE DATAThe copy is older than the truth. Stale is free for product descriptions, dangerous for balances. The rule: cache what may be a little old; never cache what must be exact.

Two flows for a shopping product page:

WITHOUT VS WITH

Application → Database: every product view = a query. 50,000 day-views = 50,000 queries for data that changed twice. Database → Cache → Application: the app asks the cache first; the DB sees only misses. Same 50,000 views = maybe 200 queries.

INTERACTIVE — SAME PAGE, THREE MODES

~40 msPAGE LATENCY
~20%DB LOAD

90% of reads are answered by the cache in ~1–5 ms. The database only feels the misses and the writes — it idles at 20% while serving a busy shop. The cache is not a nice extra here; without it, this workload does not fit this database at all.

WHEN THE CACHE GOES DOWN

Every read storms the database at once (the "thundering herd"): DB 0 → 100% in minutes, and the site has effectively lost its load-bearing wall. Defenses an architect names in an interview: fall back to the database with rate limits so you degrade instead of dying; serve stale copies rather than nothing; alert on hit ratio, not only uptime; and restart gradually so the cache warms before traffic returns. See mistake #4 in Section 12.

SECTION 07 — THE HEART

Database Scaling

The database becomes the bottleneck first because it does three hard things nobody else does: it holds the single truth, it enforces consistency, and it touches disks. Everything on the app tier is replaceable; the database is the only irreplaceable box in the room.

So the game is simple: make the database do less real work. Five moves, in the order you try them:

MOVEWHAT IT DOESSIMPLE EXAMPLETRADE-OFF / NEW PROBLEM
1 · Indexing A "table of contents" so the DB finds rows without scanning every page. Find order by number: 3 s → 30 ms. The classic first-week fix — compute-free performance. Writes pay for index maintenance; the wrong index helps nobody. Free lunch — but you must order the right dish.
2 · Read replicas Copies of the master kept in sync, whose only job is serving reads. Product catalog + order history reads fan out over 2 replicas; the master exhales. Replication lag: a replica can be seconds behind → reading your own just-written data returns the old truth ("stale read").
3 · Separate read & write The app sends writes to the master, reads to the replica pool. "Place order" → master. "List orders" → replica. Two connection pools, one honest intent. Routing discipline in the app; every split-brain bug where a critical read secretly needs right-now data should stay on the master.
4 · Scale the writer up Give the single write master a bigger machine. 32 → 128 vCPU master. Boring, expensive-per-month — and very often sufficient for years. A ceiling exists; the cheque grows faster than the CPU; still one box that can die (mitigated by standby failover).
5 · Partitioning (sharding) Split the data by a key — tenant, region, customer range — across separate databases. SaaS: tenants A–M on DB1, N–Z on DB2. Each shard stays small and fast. Cross-shard queries become application problems; rebalancing tenants between shards; migrations ×N. Do it last, with a trigger.
THE NEW PROBLEMS, HONESTLY

The after-picture buys breathing room and sells you three new problems: stale reads (lag), routing complexity (the app must know its reads from writes), and more operations (three databases to patch, back up, watch). That is a fair trade at 10× the scale — and wasted complexity at 2×. Every scaling move is a trade, not an upgrade.

SECTION 08 — THE PRECONDITION

The Stateless Application

Stateless means: a server that can die between two requests of the same user, and nothing of value is lost. All per-user knowledge lives outside the box.

Remember the trap from Section 5: user logs in on Server 1, the session lives in Server 1's memory, and the load balancer sends the next request to Server 2 — which has never met this user. Three stateful servers behind a balancer make a broken system with leverage: a third of requests now fail instead of all of them.

Where does per-user state go instead of machine memory?

SHARED CACHESessions in a cache visible to every server (one key lookup, ~1 ms). Fast, expires cleanly, and if it dies the users simply log in again.
DATABASESessions as rows — durable, but it makes your bottleneck busier for something a cache does cheerfully. Acceptable at small scale.
SIGNED TOKENSThe request itself carries the claims (user id, roles) in a signed token. Zero lookups; the server verifies the signature and trusts it. Revoking early is the known hard part.
WHAT ALSO COUNTS AS "STATE" (PEOPLE FORGET)Uploaded files on local disk → move to blob storage. In-app long-running jobs → move to a queue + worker. In-memory counters/locks shared conceptually across instances → they lie on at least one machine.
FOR YOUR STACK

In ASP.NET Core this is everyday muscle memory: sessions pointed at a distributed cache, uploads straight to blob storage, background work on the queue, no machine-local assumptions. You have the tools; the discipline is a code review question: "if this instance dies mid-breath, what is lost?" If the answer is anything, you found hidden state.

SECTION 09 — THE SHORT WAY HOME

CDN and Static Content

Why should a user in Mumbai download a cat photo from a server in another hemisphere, when the same bytes can live ten minutes from the user? A CDN is exactly that: copies of your static files placed in many cities, plus a smart directing mechanism that serves each user from the nearest copy.

THE NUMBERS THAT MAKE THIS OBVIOUS

Mumbai user, origin in the US: ~300–400 ms round trip per resource, before the page even starts rendering. From an edge node in Mumbai: ~30–50 ms. And typically 60–80% of a page's bytes are static — images, CSS, JavaScript, fonts — meaning the majority of your traffic never needed to reach your servers at all.

IMAGESThe heavyweight champion of the web. Serve them resized, compressed and cached at the edge — the biggest single win most sites will ever see.
CSS & JAVASCRIPTDecides how fast the page becomes usable (first paint). If it crawls, the whole app feels broken even with a millisecond backend.
VIDEO & LARGE FILESStreaming video and downloadable installers are where origin bandwidth dies quietly and expensively. A CDN absorbs it for a fraction of the cost.
API RESPONSES — SOMETIMESPublic, safe, unchanging responses (a public product list, a menu) can sit at the edge for seconds-to-minutes. Personalized or write-nightmare data must not.

Use a CDN when…

Distance is the enemy
  • Users are geographically spread (any public product).
  • Static bytes are the bulk of every page (almost always true).
  • Spikes matter — a CDN is a shield for origins during launches.
  • You serve media, files, or mobile users on wobbly networks.

Skip it (for now) when…

Distance is not your problem
  • An internal app in one office / one country, on the LAN — the users are near the server.
  • Traffic is small: the saving is the price of a coffee.
  • Everything served is deeply personalized per request — the cache would hold one copy each.
  • You need hard guarantees that employees of company X never touch foreign edge nodes (compliance edge cases).
INTERVIEW ANGLE

Say the two numbers out loud: "60–80% of our bytes are static, and distance costs us 300 ms per resource — a CDN fixes the physics, not the code." That answer separates "we use Cloudfront because everyone does" from actual architecture.

SECTION 10 — THE BUILD

Putting Everything Together

A shopping platform, sized by the numbers: 1M registered · 100K daily active · 10K concurrent · 2,000 peak RPS — browsing, search, orders, payment, notifications. Watch the architecture grow only when a real problem forces it to.

V1 — The honest start

BASIC APPLICATION + DATABASE
PROBLEM
A new product, a small team, quiet traffic. Every hour spent on distributed machinery is an hour not spent on product.
CHANGE
One deployable web app + one SQL database. Nothing else. Sessions stay in-process memory — acceptable while there is exactly one process.
WHY
It is the cheapest architecture that is correct. Every later version is an addition to this shape — nothing here gets thrown away.
NEW TRADE-OFF
One box = one point of failure, a hard ceiling, and downtime on every deploy. All acceptable at these numbers — none acceptable at 2,000 RPS.

V2 — Multiple servers + load balancer

THE APP TIER BREAKS FIRST: CPU 100% AT EVERY SPIKE
PROBLEM
Flash-sale noon: app CPU pins at 100%, requests queue, and every deploy is a mini-outage because the one box must restart.
CHANGE
Load balancer + 3 app servers. The precondition lands here too: servers become stateless — sessions, temp data and uploads move to the shared store.
WHY
The app tier is replaceable, so horizontal scaling is nearly free: capacity ×3, no more deploy downtime, and one dead box is now a slowdown — never an outage (Section 5).
NEW TRADE-OFF
Everything memory-local had to be dragged out of the app (Section 8), and you now deploy and monitor three boxes instead of one.

V3 — Add caching

THE DATABASE BECOMES THE BOTTLENECK: CPU ~90%
PROBLEM
The catalog — 100,000 products, read millions of times per day, changed twice — is hammering the DB. App tier is fine; the query count isn't.
CHANGE
A cache in front of the read path. Product pages, category lists, hot searches and sessions live there; the database answers only misses and writes. Target hit ratio: ≥90%.
WHY
~50,000 product reads stop costing 50,000 queries. DB load drops to a fraction, and the cheapest milliseconds in computing (a memory lookup) are doing the most work (Section 6).
NEW TRADE-OFF
Data can be stale for the TTL window; someone must decide who updates the cache when the price changes; and a new failure mode appears — the day the cache dies, the DB meets the real storm for the first time.

V4 — Database scaling

WRITES + REPORTING ARE CHOKING THE ONE WRITER
PROBLEM
Cache absorbs catalog reads, but write traffic, cache misses, and the reporting team's monster queries still drive the single DB master to 80% at peak — and reads are collateral damage of writes on one box.
CHANGE
Read replica(s) + honest read/write separation in the app: writes to the master, ordinary reads and all reporting to replicas. Indexes reviewed on the hot paths (the free move first).
WHY
Reads and writes obey different physics: reads scale by adding copies (out), the single writer is grown by making it stronger (up — Section 7). Each gets the lever that fits.
NEW TRADE-OFF
Replication lag → stale reads (a user might not see their own just-placed order in a list for a second; the order page itself reads the master), routing complexity in the app, and two engines to patch, back up and monitor.

V5 — Background processing for slow work

THE CHECKOUT IS COUPLED TO THE SLOWEST THINGS ON EARTH
PROBLEM
A checkout request currently waits on: payment (3–7 s, external), confirmation email (flaky), invoice PDF, analytics pings, and partner webhooks. One vendor's bad afternoon becomes your outage — and a flash-sale write spike has nowhere to land.
CHANGE
A queue + workers. Notifications, PDFs, reporting feeds and webhooks become messages. Payment submits and confirms asynchronously; the user sees an honest "order received · confirming." Retries come with idempotency keys so they can never double-charge or double-send.
WHY
The request path shrinks to the essential one DB write → user-facing p95 plunges; spikes sit in the queue instead of on the DB; vendor slowness leaves the critical path entirely (Day 1, reliability — applied).
NEW TRADE-OFF
Consistency becomes eventual (the user waits seconds for "confirmed"), workers need dead-letter handling for poisonous messages, and "exactly once" is still a fairy tale you must engineer compensation for.

V6 — The final architecture

COMPOSED, MEASURED, AND CHEAP TO RUN BETWEEN SPIKES
PROBLEM
Two last gaps: static bytes still cost origin bandwidth and far-user latency; and the whole machine must rise and fall with demand — or the business pays for peaks 24/7.
CHANGE
CDN in front for all static content (+ short TTLs on safe public GETs); autoscaling policies on the app and worker pools; and the discipline layer — dashboards for RPS, p95, hit ratio, DB CPU, queue depth, plus alarms and a runbook.
WHY
Distance comes down to ~50 ms; ~60–80% of bytes never touch your servers (Section 9); capacity follows the demand curve instead of the spreadsheet. And you finally know the numbers, instead of hoping.
NEW TRADE-OFF
The complexity bill arrives as operations: fourteen boxes means dashboards, alerts, runbooks, and someone on call. The design is simple; keeping it simple is the ongoing cost.
CAPACITY SKETCH — HOW V6 ABSORBS 2,000 PEAK RPS

Of those 2,000, roughly 1,800 are reads. CDN + cache answer ~90% of them → the app pool sees a few hundred RPS of real work → each instance serves ~300–500 RPS comfortably → 4 instances idle, ~8 at peak, autoscale cap 20. Writes (~200 RPS) go to one write master that is scaled up; replicas carry reporting and ordinary reads. The queue dips and drains. That back-of-envelope arithmetic — said out loud — is the interview.

WHAT V6 DELIBERATELY DID NOT ADD

No microservices (the monolith's modules are clean; team count doesn't justify process walls yet). No sharding (writer at 20% utilization — the trigger is 60%+ sustained). No Kubernetes (managed app hosting suffices). No multi-region (trigger: cross-region latency complaints or a regional DR requirement). Each of these arrives with a written trigger, not with fashion.

SECTION 11 — ARCHITECT THINKING

What Should I Ask Before Saying a System Can Handle 1 Million Users?

Twenty-four questions. Ask them before anyone draws a box — and before you let anyone claim capacity. Each one changes the design or kills a fantasy.

Registered users are a story; DAU is the load. A system for 1M registered with 2% DAU is a 20,000-user system wearing a million-user coat — sizing for the coat wastes ten times the money.
The multiplier the whole chain hangs on. Confusing "visits" with "requests" (one visit = dozens of requests) is the most common 10× sizing error in existence.
Daily requests ÷ 86,400. This is your baseline sanity number. If nobody has computed it, every architecture drawn so far is decoration.
Peaks kill systems; averages bore them. The factor (3–10×), the shape (lunch vs flash sale), and the duration (90 minutes vs constant) each imply different cost and autoscaling decisions.
"Fast" is p95 checkout under 1 s, not vibes on a laptop. Miss p95 and you ship a system where 5% of users — often your paying power users — are silently suffering.
Separating "instant" (checkout page) from "can wait" (email, reports, PDFs) is how the queue enters the design. Without it you make everything synchronous — or worse, make the payment wait on the newsletter service.
10 GB and 10 TB are different lives: backup windows, index rebuilds, failover times, even "restore-and-pray" all change shape when data grows 10×. Growth rate is the number that decides when partitioning enters the room.
95% reads → cache and replicas do the heavy lifting. 50% writes → the write master is the star, and caching is a side dish. Same word "load," opposite architecture. Ask it in the first five minutes.
A handful of hot keys (the homepage, top products, the celebrity's post) can equal the load of the entire long tail. That 5% is what you optimize, cache, and protect — not the other 95%.
One unindexed query on a hot path can cost more than the entire app tier. The slow-query log is the single cheapest scaling tool in the building — spend one hour there before one dollar on servers.
Product description: minutes. Stock count: seconds. Balance: zero. The answer per feature decides the TTL policy and whether a given read can ever leave the master. Skipping this question produces "randomly wrong" data.
These two numbers design the backup, replica and failover strategy. Zero-loss write masters and five-minute recoveries cost real money; deciding them after the disaster means the business decided by accident.
Every write path must eventually pass one writer or a carefully partitioned set. Naming the trigger now (e.g., 60% sustained CPU on the top-tier machine) means sharding/arrival of the next lever is a planned operation, not a panicked rewrite.
99.9% ≈ 8.7 h/year. 99.99% ≈ 53 min/year and roughly 10× the money. Capacity without availability is a fast closed shop. The business owns this number — make it say it out loud.
Without a test you are narrating confidence. A load test finds the knee — the load at which the response time curve bends upward — and tells you which resource bends it. That answers half of this list empirically.
The cache dies at the worst time by definition. Decide now: fall back to DB with rate limiting, serve stale, alert on hit ratio, warm gradually after restart. Otherwise the "simple outage" interval includes the stampede after it.
Failover to a standby? Read-only degraded mode ("you can browse, you cannot order")? RTO minutes or hours? The design decision is which features are allowed to survive a heart attack — and that decision is made here, not in the incident channel.
Your real latency budget includes your vendors' p95, not just yours. Map each dependency: timeout, retry policy, degradation path, and a fallback provider if money is at stake. Unmapped dependencies are unknown outages on a timer.
Capacity for love is not capacity for bots: login floods, scrapers, coupon-hacking loops all look like "success traffic." Rate limits, auth throttles and bot defenses are part of capacity — budget them.
A "correct" architecture that spends $30k to serve $8k is wrong. Cost-per-request is the metric that keeps architectures honest — and autoscaling between spikes is usually its biggest lever.
Geography decides CDN value, region choice, and some laws. Users in one country: one region plus CDN. Users across oceans with "data must stay home" rules: that is a different architecture entirely — ask before assuming.
Load multiplies mistakes: a log line at 2,000 RPS leaks a database's worth of PII per month. High-traffic systems need stricter, not looser, discipline on what is logged, copied and cached — check regrettably-often caches for personal data first.
A design sized to exact current numbers is obsolete on arrival if growth is 20% monthly. The 12-month projection decides which one-time investments (statelessness, queues) you must buy now versus next year.
List the parts that survive 10× untouched (stateless app → yes; queue → yes) and the parts that die (write master; maybe the cache cluster). Now your scaling roadmap is two columns on a napkin instead of a mystery. This list, spoken calmly, is what "senior" sounds like.
SECTION 12 — HONEST EDITION

Common Scaling Mistakes

Ten ways smart engineers break their own sites. You will recognize some. That is the point.

01

Assuming registered users equal concurrent users

The million is on the slide, so the million goes into the spreadsheet. Machines are bought for a crowd that never shows up — or the opposite: nobody ran the math, and the actual crowd did show up.

Run the funnel from Section 2: registered → DAU → RPS → peak. Design for the peak, report the million to marketing.

02

Adding servers without fixing the database bottleneck

More app servers is the easy, visible fix — so it comes first. But each new app server sends more queries into the already-saturated database. You have scaled the crowd, not the kitchen.

Measure first (Section 3). If the DB is at 95%, the next dollar goes into indexes, cache and replicas — not into making the queue at its door longer.

03

Caching everything

"Cache it all" sounds like maximal performance. It is actually maximal staleness: balances, stock, and payment state are all data that must be exact — and cache invalidation of everything is a full-time job nobody budgeted for.

Cache what is read-hot and change-cold (Section 6). For everything else, accept the query. A slightly slower truth beats a fast lie.

04

Ignoring cache failure

The cache "just works," so nobody asks what happens when it stops. One day it stops — and the database, which was secretly never scaled to serve the real load, meets it for the first time (remember quiz scenario 5).

Design cache-down mode: DB fallback with rate limits, serve-stale, hit-ratio alarms, gradual warm-up. The shield is meant to fall someday — plan for it.

05

Keeping application state in memory "temporarily"

One era ago it was one server, so sessions in memory were fine. The temporary hack survives three years, then the load balancer arrives and a third of the users are suddenly strangers.

Statelessness is a precondition of scaling out (Sections 5 and 8) — the conversation happens before adding servers, in code review, not in the incident channel.

06

Using microservices "because the system is large"

Big traffic feels like it requires big architecture. But service splitting answers organizational scaling (many teams), while the bottleneck is usually database scaling. The day you split the monolith into twelve services sharing one DB, you still have one DB — plus eleven networks.

Scale the bottleneck, not the org chart. Extract a service when an independent scale or release need proves itself — with a trigger written down.

07

Optimizing before measuring

Tuning is fun; measuring is homework. So engineers guess the bottleneck — and they are wrong so reliably that "profile first" is practically a law. Famous last words: "I know where it's slow."

No optimization without a p95, a CPU chart, and a slow-query log. Ten minutes of measurement beats a week of confident wrongness.

08

Ignoring peak traffic

Averages look manageable on dashboards. Traffic, however, arrives in spikes — lunch, payday, a celebrity's post. The system sized for "average" is sized to fail exactly when the most users are watching.

Size for peak (Section 2), absorb spikes with queues and autoscaling, and always know your multiplier. The peak is the requirement.

09

Ignoring external dependencies

Dashboards only watch your own boxes. Meanwhile your p95 is secretly composed of their p95 — the payment provider's bad afternoon becomes your timeout storm, your thread-pool exhaustion, your outage.

Map every external call: timeout, retry with delay, queue where possible, fallback provider if money depends on it (Section 11, Q18). Their downtime is your design problem.

10

Designing for unrealistic numbers

"What if we have a billion users someday?" — and a year of architecture budget burns on machinery for a product that has not found its first thousand. Over-building is as much a failure of judgment as under-building, just more expensive.

Design for real numbers and stay honest about triggers. The V-versions in Section 10 are the pattern: each step is additive, each one earned by a measured problem.

THE PATTERN IN ALL TEN

Every mistake is a skipped measurement or a skipped why. Twelve years of technology does not protect you from the wrong bottleneck or the imaginary trillion users. Fifteen minutes of arithmetic does.

Model answers — study them only after attempting

Q01How would you design a system for 1 million users?
"Million registered" is marketing, so I first derive the load: DAU ~10% → 100K; ~50 requests each → 5M requests/day → ~58 avg RPS; peak ×8 ≈ 500–2,000 RPS. Then I walk the tiers: CDN for static bytes; load balancer in front of a stateless autoscaling app pool; cache in front of reads (≥90% hit ratio); one write master scaled up, reads on replicas; a queue absorbing payments-adjacent, notifications and spikes. I name the first bottleneck (the DB), the metric that proves it, and the trigger for the next version. I finish by stating what I did not build — microservices, sharding, multi-region — and what would make me reconsider.
Q02How do you estimate capacity?
The funnel: registered × active% = DAU; DAU × requests-per-day = daily requests; ÷ 86,400 = average RPS; × peak factor (3–10) = peak RPS. Then capacity per tier: requests-per-instance (from a benchmark or realistic 300–500 RPS for simple web work), × instances, ÷ headroom (keep boxes around 65% so one death is survivable). I sanity-check against the DB (writes per second it can absorb) rather than trusting the app math alone. Four multiplications + one benchmark beats a month of guessing.
Q03What happens when traffic suddenly becomes 10×?
If designed well: autoscaling adds app and worker instances (stateless, so minutes), the queue absorbs the parts that can't scale instantly, the cache shields the database from the read storm, rate limits keep abusive or runaway traffic from finishing the job, and the system degrades gracefully — recommendations off, checkout on. If designed badly: the write master melts first, then everything queues behind it. The difference is decisions made before the spike: statelessness, queues, cache-down plans. You do not architect during the incident.
Q04What becomes the bottleneck first?
Usually the database — the only irreplaceable box: it owns state, enforces consistency, and touches disk. Second place goes to the app tier if hidden state (sessions in memory, thread starvation) is present. But the honest architect answers with a metric, not a slogan: watch the resource approaching 95–100% — CPU, connections, disk queue — and fix that one. "The whole system is limited by its weakest part," and the weakest part is whatever your monitoring proves, measured per component, at peak.
Q05Why horizontal scaling?
Three reasons: no hard ceiling — you add boxes until the next bottleneck appears; fault isolation — one dead instance is degraded service, not an outage (a box is a fraction of capacity, not all of it); and economics — capacity follows the demand curve with autoscaling, so you stop paying for peak at midnight. The precondition is statelessness; the exception is the write database, which grows vertically for a long time because one writer simplifies the truth. Different tiers, different levers — that sentence is the senior nuance.
Q06How does caching help?
Every read the cache answers is a read the database never sees. Memory lookups cost ~1–5 ms, so a ≥90% hit ratio turns 50,000 catalog reads into a few hundred queries — the cheapest milliseconds in computing. It flattens latency (p95 drops), protects the DB from read storms, and buys capacity cheaper than any server upgrade. The discipline: cache read-hot, change-cold, stale-tolerant data; never balances, stock, or payment state. And the metric is hit ratio — a cache with a 40% hit ratio is a decorated database with extra steps.
Q07What happens if the cache (e.g., Redis) goes down?
The shield falls and every read storms the database at once: DB CPU can go 15% → 100% in minutes — the "thundering herd" (quiz scenario 5). The defenses I name: fall back to DB with rate limiting so you degrade instead of dying; serve stale copies rather than errors; alert on hit ratio, not only uptime; restart gradually with a single loader so the cache warms before traffic returns. The deeper lesson: the cache was absorbing load the DB could never serve, and that asymmetry must be known — measured, not discovered at 9 a.m. in the incident.
Q08How do you scale a database?
In order of cost: 1) fix indexing on hot queries (free compute); 2) cache so reads never arrive; 3) scale the write master up (bigger box, boring and honest); 4) read replicas + read/write separation so reads fan out; 5) partition/shard by tenant or region — last, because cross-shard queries become application problems. The named trade-offs: replication lag → stale reads; app routing complexity; more engines to run. A senior adds the trigger math: "at 60% sustained on the biggest available writer, sharding enters; before that, replicas and cache are the answer."
Q09Why do you need a load balancer?
Because "add a server" is meaningless without something to split traffic: it distributes requests evenly, health-checks every few seconds and silently evicts a dead instance (users notice nothing — demo on this page), terminates TLS, and gives you zero-downtime deploys via rolling restarts. It is what turns "a pile of servers" into capacity that heals itself. The corollary: it forces statelessness — sessions in one box turn "any request, any server" into roulette (Section 5). Without the balancer you cannot scale out; with it you cannot stay stateful.
Q10How do you identify whether scaling is actually required?
With metrics, never with vibes: p95 response time drifting up; CPU or connections sustaining >70%; queue depth growing instead of draining; hit ratio falling; the slow-query log filling. Then a load test at 2×/5× finds the knee — the load where latency bends upward — and tells you which lever, how much, and the date you need it by. Scaling decisions are a line on a graph, not a feeling in a meeting. If nobody can point at the graph, nobody should be buying servers yet.

Architect Mindset, Day 2

Day 5 rules. Five sentences you should be able to recite at a whiteboard in three months, half asleep.

01

Registered users are a story. The peak is the design.

Never let a total design a system. Four multiplications — DAU, requests, average, peak — turn the marketing number into the engineering number. The servers serve the last one.

02

Find the shortest stave.

The system is limited by its weakest part — and strengthening anything else changes nothing. Measure, find the resource at 95%, fix that, re-measure. That loop is the discipline.

03

Each tier gets its own lever.

App tier: out, because it is stateless and cheap to clone. Write master: up, because one writer keeps the truth simple. Reads: across replicas and the cache. Bytes: near, via CDN. Same question — different physics.

04

Add a component only to kill a measured bottleneck.

Load balancer, cache, replicas, queue — each entered Version 1→6 because a number was hurting. Every added box arrives with its trigger and its trade-off written down. Fashion is not a bottleneck.

05

Every shield is designed to fall someday.

Cache, load balancer, autoscaling — all shields. The question is never if they drop, but what your user sees the moment they do: degraded and honest, or a white error page with a logo.
