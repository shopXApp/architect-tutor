SECTION 01 - THE REAL PROBLEM

Application Servers Scale Out. The Database Often Does Not.

The classic shape is simple: Users -> Load Balancer -> Multiple APIs -> One Database. You can add API servers in minutes. The database is harder because it holds state, consistency, indexes, locks, connections and backups.

Fig. 13.1 - Scale-out APIs can increase pressure on the same database.
TRAFFIC GROWTH SIMULATION
100

One API instance and one modest database may be enough. Most time is spent building product value, not complex scaling.

API PRESSURE
DATABASE PRESSURE
TRAFFIC WHAT USUALLY HAPPENS WHY MORE API SERVERS MAY NOT FIX IT
100 requests/sec One database handles reads and writes comfortably. The database is not yet the bottleneck. Keep it simple.
1,000 requests/sec Indexes, connection pooling and query discipline start to matter. Adding APIs can create more simultaneous database connections and queries.
10,000 requests/sec Read traffic, hot tables, locks and slow queries become visible. APIs scale, but all of them still hit the same primary database.
100,000 requests/sec You need deliberate read/write separation, partitioning, maybe sharding, maybe NoSQL for some workloads. More APIs may make the database fail faster. The bottleneck moved down.
ARCHITECT INSTINCT

Before changing the database architecture, ask: Is the problem reads, writes, bad queries, locks, connections, data volume, tenant skew or reporting load? Each has a different fix. "Add servers" is not a database strategy.

SECTION 02 - BASICS

Vertical and Horizontal Scaling

Database scaling has two broad moves: make one server stronger, or spread work across multiple servers. The simple move is often the right first move.

APPROACH HOW IT WORKS BENEFIT LIMITATION WHEN TO USE
Vertical scaling Make one database server stronger: more CPU, memory, faster storage, larger managed tier. Simple. Minimal code change. Low operational complexity. Has a ceiling. Expensive at the top. Still one primary bottleneck. First step for growing systems, especially when you are not yet sure which scaling pattern is needed.
Horizontal scaling Use multiple database servers: replicas, partitions, shards, separate workloads. Can scale beyond one machine and isolate workloads. More complexity: routing, consistency, failover, cross-data queries and operations. When clear evidence shows one database cannot meet the read, write, data or availability requirement.
THE PRACTICAL ORDER

In real systems, the order is usually: good schema - good indexes - good queries - connection pooling - vertical scale - read replicas - partitioning - workload separation - sharding. Sharding is not the first chapter. It is the chapter after the simpler chapters have failed with evidence.

SECTION 03 - READ SCALING

Read Replicas: Scale Reads Without Touching Writes

Many high-traffic systems are read-heavy. Product pages, catalog browsing, search suggestions and order history reads may greatly outnumber writes. Read replicas let you send safe read traffic away from the primary database.

Fig. 13.2 - Read replicas reduce primary load but introduce possible stale reads.
  • Writes go to the primary because the primary owns the truth: create order, update inventory, change price.
  • Reads can go to replicas when the result can be a few seconds old: product catalog, category pages, reports, browsing.
  • Replication delay means a write may not appear instantly on the replica. This is called stale data.
  • Stale data is acceptable when the business can tolerate it. A product description being 3 seconds old is fine. A payment result being 3 seconds old may not be.
PRODUCT CATALOG EXAMPLE

Product catalog reads are perfect for replicas: many users browse the same products, product data changes less often than it is read, and seeing a price update a few seconds late may be acceptable if the checkout re-validates the final price against the primary before payment.

SECTION 04 - REPLICATION

Replication: Copies for Reads, Availability and Recovery Support

Replication means changes from the primary database are copied to one or more replicas: Primary -> Replica 1 -> Replica 2. It is one of the first horizontal moves.

Why replication is usedTo spread read traffic, keep another copy close to promotion, support backups, and improve availability when the primary fails.
Read scalingRead-only queries can hit replicas, reducing CPU and IO pressure on the primary.
AvailabilityIf the primary fails, a replica can be promoted to primary. Managed cloud databases often automate this within a region or zone.
Backup use caseBackups can be taken from a replica to reduce load on the primary, but the backup still must be stored independently.
Replication delayThe replica may lag seconds or minutes behind during load or failure. You must decide which reads can tolerate that.
FailoverFailover changes which database is the primary. The application must reconnect, retry safely, and avoid duplicate writes.
REPLICATION IS NOT BACKUP

If someone deletes all orders by mistake, replication faithfully copies the delete to every replica. A backup lets you restore to a previous point. Replication protects against server loss. Backup protects against data loss, human error and corruption. You need both.

SECTION 05 - PARTITIONING

Partitioning: Split a Large Table Into Manageable Pieces

Imagine an Orders table with 1 billion orders. Partitioning keeps it as one logical table but stores it in smaller pieces, usually inside the same database system.

PARTITION BY HOW IT WORKS BENEFIT RISK
Date Orders are separated by month, quarter or year. Great for historical data, archiving, reports by time range and deleting old data safely. Current month can become hot while old partitions are cold.
Tenant Orders are separated by TenantId ranges or tenant groups. Useful when tenants need different maintenance, retention or scale behavior. Not always right: one large tenant can create a hot partition; many small tenants waste structure.
Region Orders are separated by geography, for example US, EU, APAC. Supports data residency and region-local reporting. Cross-region customers and global reports become harder.

Why partition? To make large data easier to query, maintain, archive and scan. A query for last month's orders can touch one partition instead of scanning a billion rows.

INTERVIEW RULE

Do not say "partition by tenant" automatically because the system is multi-tenant. First ask: Are queries usually tenant-scoped? Are tenants evenly sized? Do we need tenant-level retention? Are hot tenants isolated elsewhere? Partitioning key choice is access-pattern choice.

SECTION 06 - SHARDING

Sharding: Put Different Data on Different Databases

Sharding means one logical dataset is split across multiple independent database servers. Each shard owns a subset of the data. It helps when one database cannot handle the total data or write load anymore.

Fig. 13.3 - Sharding distributes tenants or rows across separate databases.
  • Why it helps - each database handles only part of the data and part of the write load.
  • How data is distributed - by a lookup table (Tenant A -> DB1) or by a deterministic rule such as Hash(TenantId) -> shard number.
  • How requests find the shard - the application, gateway or data access layer uses tenant ID or shard key to route the request.
  • When one shard overloads - a large tenant, bad key distribution or a hot partition can overload one shard while others are idle.
  • Rebalancing is difficult - moving tenants between shards means moving data safely, updating routing, keeping writes consistent and avoiding downtime.
  • Cross-shard queries are hard - "all orders across all tenants" must fan out to many databases and merge results.
  • Cross-shard transactions are harder - a transaction touching two shards needs careful design, usually async workflow, not one big distributed transaction.
WHY SHARDING COMES LATE

Sharding solves a real scale problem but creates routing, operations, reporting, rebalancing and failure complexity. Usually consider it after indexing, query fixes, vertical scaling, read replicas, caching and partitioning have been evaluated with evidence.

SECTION 07 - COMPARE

Partitioning vs Sharding

They both split data, but not in the same way. Partitioning usually splits data inside one database system. Sharding splits data across multiple independent database servers.

PARTITIONING SHARDING
Data location Same database system, split into logical/physical partitions. Multiple separate database servers or databases.
Main purpose Manage large tables, speed bounded queries, simplify archiving. Scale beyond one database's capacity for data or write load.
Complexity Medium. The database engine often helps. High. The application/platform must route and operate shards.
Scaling benefit Better query and maintenance behavior; not always more total write capacity. More total capacity by adding shards.
Cross-data queries Usually easier because the database still sees all partitions. Harder; requires fan-out, aggregation and careful timeouts.
Typical use Large orders table, time-based reporting, archive/delete old data. Huge tenants, very high write throughput, data too large for one server.

Five scenarios

SCENARIO BETTER FIT WHY
Orders table has 1 billion rows and most queries ask for last 30 days. Partitioning by date The query naturally touches a time window, and old data can be archived by partition.
One database cannot handle total write throughput even after tuning. Sharding Writes need to be distributed across independent database servers.
EU and US data must stay in separate geographies. Region partitioning or regional sharding The driver is legal/data residency, not only performance.
10,000 tenants, but 20 tenants create 60% of traffic. Hybrid Keep most tenants shared; isolate hot tenants onto dedicated databases/shards.
Reporting needs all tenants every night, but OLTP queries are tenant-scoped. Partition or shard OLTP, separate reporting store Do not make production writes slow for cross-tenant reports.
SECTION 08 - INDEXING

Indexes: Make the Database Find Rows Without Scanning Everything

An index is like a sorted lookup structure. It lets the database find rows quickly without reading the whole table. Example query: SELECT orders WHERE CustomerId = ?.

CASE WHAT HAPPENS USER IMPACT
No useful index The database may scan many rows looking for matching CustomerId values. Slow API, high CPU, more IO, worse under load.
Index on CustomerId The database jumps to the relevant customers' orders faster. Lower response time and lower database pressure.
Primary indexThe index behind the primary key, for example OrderId. Great for fetching one order by ID.
Composite indexAn index over multiple columns, for example (TenantId, CreatedDate). Useful when queries filter by both.
Covering indexConceptually, an index that contains everything the query needs, so the database can answer from the index without going back to the table.
Index trade-offIndexes speed up reads but increase storage and write cost. Every insert/update may also update indexes.
TOO MANY INDEXES

An index is not free. Too many indexes slow writes, consume memory/storage and make query planning harder. An architect does not say "index everything". The architect says: index the queries that serve important access patterns, then monitor write cost.

SECTION 09 - QUERY PERFORMANCE

When an API Is Slow Because of the Database

You do not start by guessing. You follow the path: API -> Query -> Execution Plan -> Index -> Data Volume -> Locks -> Connections.

  1. APIWhich endpoint is slow? Is it all APIs or only order history, checkout, reporting? Use p95/p99 from observability, not one user complaint.SCOPE THE PROBLEM FIRST
  2. QueryWhich SQL statement or database call runs during that endpoint? One endpoint may run 20 queries. Find the expensive one.ONE SLOW ENDPOINT OFTEN HIDES ONE BAD QUERY
  3. Execution planThe database's explanation of how it will execute the query: scan, seek, join order, estimated rows. You do not need to be a DBA, but you must know that the plan tells you where the work is.PLAN TELLS YOU WHAT THE DATABASE THINKS
  4. IndexIs the needed index missing or unused? Does the query filter by columns that have no useful index?MISSING INDEXES ARE COMMON AND FIXABLE
  5. Data volumeDid a table grow from 10 million to 1 billion rows? A query that was fine at launch may die at scale.YESTERDAY'S GOOD QUERY CAN BE TODAY'S INCIDENT
  6. LocksIs another transaction holding rows or tables so this query waits? Slow can mean waiting, not computing.CHECK IF IT IS WORKING OR WAITING
  7. ConnectionsIs the API waiting for a database connection? If the pool or database max connections is exhausted, every query becomes slow before it starts.NO CONNECTION, NO QUERY
ARCHITECT ANSWER

"I would identify the slow endpoint, correlate it to the slow query, check the execution plan and index usage, then verify whether this is data growth, locking or connection exhaustion. Only after that would I choose tuning, indexing, read replicas, partitioning or architecture change."

SECTION 10 - CONNECTIONS

Connection Pooling: Reuse Expensive Connections

Opening a new database connection for every request is expensive: network setup, authentication, session state and server resources. A connection pool keeps ready connections and reuses them.

Fig. 13.4 - Pooling reduces connection overhead, but it must match database capacity.
SITUATION WHAT HAPPENS ARCHITECT THINKING
Pool too small Requests wait for a free connection even if the database could handle more. API latency rises before query starts. Increase carefully and monitor DB load.
Pool too large Too many concurrent queries hit the database, causing CPU, memory and lock pressure. More connections can make the database slower, not faster.
Database overloaded Connections are available, but queries are slow because the database is saturated. Do not just raise the pool. Find the workload causing saturation.
SECTION 11 - TRANSACTIONS

Transactions at Scale: Keep Them Small

A transaction keeps a set of database changes consistent. That is powerful, but a long transaction can hold locks, block other users and increase deadlock risk.

Example: Order -> Payment -> Inventory. It is tempting to wrap everything in one big transaction. But payment is an external call, inventory may be another service, and the database may hold locks while waiting for work outside itself.

Transaction durationThe longer a transaction stays open, the longer locks may be held and the more rows are protected from change.
LockingLocks protect correctness, but they can make other requests wait. Waiting requests become slow APIs.
ContentionMany users trying to update the same stock row, coupon or tenant balance compete for the same data.
DeadlocksTwo transactions wait for each other in a cycle. The database kills one so the other can continue.
DESIGN RULE

Keep the database transaction as small as practical: write the order record, reserve what must be reserved, commit, then use messaging/idempotency for follow-up steps. Do not hold a database transaction open while calling a payment provider.

SECTION 12 - DATABASE CHOICE

SQL vs NoSQL for Scale

Choose the database based on access patterns and business requirements, not popularity. SQL and NoSQL both scale, but they optimize for different shapes of data and queries.

DIMENSION SQL SERVER / POSTGRESQL MONGODB / COSMOS DB / DYNAMODB
Relationships Strong fit for relational data: orders, payments, customers, invoices. Good when data is document-shaped or access is mostly by key/document.
Transactions Strong multi-row and relational transactions. Often optimized for single-document or partition-key transactions; multi-item can exist but may be limited/costly.
Scale Scales well with tuning, replicas, partitioning and managed tiers; write sharding requires design. Often built for horizontal scale and high throughput if access pattern is known.
Query patterns Flexible queries and joins are strong. Works best when query patterns are known in advance and modeled into the document/partition key.
Flexible schema Schema changes are explicit and controlled. Flexible schema helps evolving product/catalog/profile data.
Global distribution Possible, often more complex for writes and consistency. Cloud-native NoSQL platforms often provide global distribution options more naturally.
PRACTICAL SAAS ANSWER

Use SQL for transactional truth: orders, payments, invoices, inventory movements. Use NoSQL where the access pattern fits: product search documents, event/audit feeds, globally distributed read models or flexible catalog attributes. Polyglot persistence is acceptable only when the operational cost is justified.

SECTION 13 - MULTI-TENANCY

Multi-Tenant Database Strategies

Multi-tenancy is not just a security topic. It affects cost, isolation, noisy neighbors, backup, restore, migration and scaling. Here are the four common options.

OPTION COST ISOLATION COMPLEXITY SCALING BEST USE CASE
1. Shared database, shared tables Lowest Lowest. TenantId must be enforced everywhere. Low to medium Scales until shared database/table pressure becomes high. Many small tenants, early SaaS, cost-sensitive platforms.
2. Shared database, separate schema Medium Better logical separation. Medium to high due to migrations and schema management. Limited by same database server. Moderate tenants needing some separation, not full database isolation.
3. Separate database per tenant Highest Highest. Easier tenant restore and isolation. High operational burden at 10,000 tenants. Good isolation, but provisioning and migrations become a product. Enterprise tenants, compliance, custom retention, very large tenants.
4. Hybrid approach Balanced Balanced. Most shared, important tenants isolated. High enough to need a routing catalog. Best practical path: move hot/regulated tenants out when needed. Large SaaS with many small tenants and some large enterprise tenants.
RECOMMENDATION FOR 10,000 COMPANIES

Start with a hybrid strategy: shared database/shared tables for most tenants, strict TenantId enforcement, indexes beginning with TenantId for tenant-scoped queries, and a tenant catalog that allows moving large or regulated tenants to dedicated databases later. This keeps cost sane while preserving an escape path.

SECTION 14 - FAILURE

Database Failure: Design the Response Before the Incident

A database incident is not one thing. Primary failure, replica failure, network failure, connection exhaustion and hot tenants all hurt differently. The architecture response must match the failure mode.

FAILURE BUSINESS IMPACT ARCHITECTURE RESPONSE RECOVERY
Primary database fails Writes stop; checkout/order creation may fail. Automatic failover to replica, retry-safe writes, circuit breaker to avoid storm. Promote replica, reconnect apps, validate data consistency and replay safe messages.
Read replica fails Read capacity reduced; some reads may slow. Route reads to other replicas or primary only for critical reads. Replace replica and watch primary load while degraded.
Network connection fails Temporary errors, timeouts, user retries. Short timeouts, retry with backoff, idempotent writes. Reconnect, verify connection pools recover and no duplicate writes occurred.
Maximum connections reached Requests wait or fail before queries run. Pool limits, backpressure, fix connection leaks, reduce unnecessary parallel queries. Kill idle sessions if needed, restart leaking app instance, tune pool/database limits.
Disk becomes full Writes fail hard; backups/logs may stop. Capacity alerts, automated expansion, log/archive cleanup policy. Add storage, clean safely, verify backups and transaction logs.
Query becomes extremely slow One endpoint slows or locks shared tables. Slow query monitoring, query timeout, kill runaway report, read/write separation. Add/adjust index, rewrite query, move report workload, review deployment.
One tenant generates huge traffic Noisy neighbor hurts other tenants. Per-tenant rate limits, tenant-level metrics, isolate hot tenant if persistent. Throttle, communicate, move tenant to dedicated database/shard if justified.
SECTION 15 - BACKUP AND RECOVERY

Backup, Restore, PITR, RPO and RTO

Backup is not a checkbox. The only backup that matters is one you can restore inside the business's recovery requirement.

BackupA copy of database data stored separately so you can recover after deletion, corruption or disaster.
RestoreThe act of bringing data back from backup into a usable database. Restore must be tested.
Point-in-time recoveryRestore to a specific moment, for example 10:14 AM, right before a bad script deleted rows.
RPORecovery Point Objective: how much data can we afford to lose? Example: if RPO is 5 minutes, losing 4 minutes is acceptable; 30 minutes is not.
RTORecovery Time Objective: how long can we afford to be down? Example: if RTO is 30 minutes, restore and failover must be rehearsed for that.
The blunt truthA backup without a restore test is a belief, not a recovery plan.
BUSINESS SCENARIO RPO THINKING RTO THINKING
Internal admin/reporting tool Can lose 1 hour of recent changes if data can be regenerated. Can be down half a day without customer impact.
E-commerce order platform Orders and payments cannot be lost; target minutes or near-zero for writes. Minutes to under an hour, depending on SLA and revenue impact.
Financial ledger / payment settlement Near-zero data loss. Every transaction matters. Very low, with strong failover and reconciliation procedures.
SECTION 16 - CASE STUDY

Multi-Tenant E-Commerce SaaS: Database Architecture

Requirements: 10,000 companies, 1 million users, 100,000 active users, 10,000 concurrent users, 5,000 peak requests/sec, billions of historical orders, catalog, orders, payments, inventory, reports, audit, Redis, messaging, Azure/AWS deployment.

THE DESIGN RULE

Do not jump directly to sharding. First design the database around business truth, access patterns, indexing, read/write separation, replication, partitioning and failure handling. Sharding is a later move if evidence says one database group cannot handle writes/data.

  1. Database selectionUse SQL Server or PostgreSQL as the primary transactional store for orders, payments, inventory movements and invoices. These are relational, need constraints, and need strong transaction semantics.WHY: CORE COMMERCE DATA IS RELATIONAL AND TRANSACTIONAL
  2. Schema approachShared tables with TenantId for most tenants, normalized core tables for orders/payments/inventory, plus carefully designed audit/event tables. Keep the data model explicit because correctness matters.WHY: COST-EFFICIENT FOR 10,000 TENANTS WITH A PATH TO ISOLATE
  3. IndexingIndex real access patterns: (TenantId, OrderId), (TenantId, CreatedDate), (TenantId, CustomerId, CreatedDate), product catalog keys, payment status lookups. Review indexes by slow-query data.WHY: TENANT-SCOPED QUERIES MUST NOT SCAN SHARED TABLES
  4. Read/write separationAll writes to primary. Safe reads such as catalog browsing, order history and reporting extracts go to read replicas or read models. Checkout re-validates critical data on primary.WHY: READS ARE HIGH VOLUME AND CAN BE STALE IN SOME PLACES
  5. ReplicationUse managed primary with zone-redundant replica/failover group where available. Add read replicas for scale and for backup/reporting offload.WHY: IMPROVES AVAILABILITY AND READ CAPACITY, BUT WATCH LAG
  6. PartitioningPartition historical orders and audit records by date first, because old data grows forever and reports usually use time windows. Consider tenant or region partitioning only when access and compliance require it.WHY: BILLIONS OF HISTORICAL ROWS NEED MAINTENANCE BOUNDARIES
  7. ShardingDo not start sharded. Add a tenant catalog early so the platform can later route selected tenants to dedicated databases/shards. Shard when write load, data size or tenant isolation evidence proves one database group is not enough.WHY: KEEP V1 OPERABLE, PRESERVE A FUTURE ESCAPE PATH
  8. Tenant strategyHybrid: shared for the long tail of small tenants, dedicated database for very large or regulated tenants. Track tenant load, storage, query cost and noisy-neighbor behavior.WHY: 10,000 DATABASES ON DAY ONE IS EXPENSIVE OPERATIONS
  9. Reporting strategyDo not run heavy reports on the OLTP primary. Use messaging/CDC/export jobs into a reporting database, warehouse or read model. Reports can be minutes behind if the business accepts it.WHY: REPORTS SCAN; CHECKOUT MUST NOT WAIT BEHIND SCANS
  10. BackupAutomated backups, point-in-time recovery, separate storage, periodic restore tests. Keep hot backups for fast recovery and longer archives for audit/compliance.WHY: REPLICATION DOES NOT UNDELETE DATA
  11. Disaster recoveryDefine RPO/RTO with the business. For core orders/payments, choose low RPO and rehearsed regional failover. For reporting, allow longer recovery because it can rebuild.WHY: NOT EVERY WORKLOAD DESERVES THE SAME DR COST
  12. Failure handlingRetry transient database errors with backoff, keep writes idempotent, use short timeouts, fail over managed databases, shed load under connection pressure, isolate noisy tenants and protect the primary from reports.WHY: DATABASE FAILURE MUST NOT BECOME DUPLICATE PAYMENTS OR LOST ORDERS
HOW THE DESIGN EVOLVES

Start with one well-designed SQL primary. Then add indexes and vertical scale. Then read replicas. Then partition historical tables. Then separate reporting. Then isolate hot tenants. Only then shard the write path if evidence still says the database layer cannot meet the requirement.

SECTION 17 - EVOLUTION

Three Stages of Database Architecture

The lesson: Do not build a billion-user architecture for a 10,000-user problem. Build the smallest database architecture that safely meets today's needs and has a clear next step.

STAGE 1 - SMALL SYSTEM

Architecture: One SQL database, good schema, basic indexes, backups, Redis for hot reads.

Why enough: Low traffic and low data volume. Simplicity beats imaginary scale.

Next limitation: Slow queries, missing indexes, database CPU during peaks.

STAGE 2 - GROWING SYSTEM

Architecture: Stronger DB tier, tuned indexes, connection pooling, read replicas, partitioned orders/audit, reporting copy.

Why enough: Reads are offloaded, old data is manageable, reporting no longer fights checkout.

Next limitation: Primary write pressure and hot tenants.

STAGE 3 - LARGE SCALE

Architecture: Hybrid tenant isolation, dedicated databases for large tenants, sharded write path if needed, regional replicas, strict DR.

Why enough: Workload is distributed and noisy tenants can be isolated.

Next limitation: Cross-shard reporting, rebalancing, operations complexity and cost.

SECTION 18 - DECISIONS

Ten Questions Before Changing Database Architecture

Before you add replicas, partitions, shards or new database technology, ask these. They prevent expensive solutions to the wrong problem.

QUESTION WHY IT MATTERS POSSIBLE DECISION TRADE-OFF
Is the database actually the bottleneck? App CPU, network, Redis or payment provider may be the real issue. Use traces/metrics before architecture change. Investigation takes time but avoids wrong fixes.
Is the problem reads or writes? Read pressure and write pressure scale differently. Read replicas for reads; sharding/workflow changes for writes. Wrong choice adds complexity without relief.
Can indexing solve it? Missing indexes are common and cheaper than topology changes. Add or adjust targeted indexes. Improves reads, may slow writes and increase storage.
Can caching solve it? Hot read data may not need a DB call every time. Cache product/catalog/session/reference data. Staleness and invalidation complexity.
Can read replicas solve it? Read-heavy workloads can often be offloaded cleanly. Route safe reads to replicas. Replication lag and read routing complexity.
Do we need partitioning? Large tables may need maintenance/query boundaries. Partition orders by date, region or tenant if access supports it. Wrong key creates hot partitions or hard queries.
Do we really need sharding? Sharding is costly and hard to undo. Shard only after evidence proves one database group cannot cope. Routing, rebalancing, cross-shard queries.
How will tenants be distributed? Uneven tenants create hot shards. Hybrid placement with tenant catalog and top-N monitoring. More operational tooling.
What happens during failover? Apps must reconnect and avoid duplicate writes. Managed failover, idempotent writes, retry with backoff. More code discipline and testing.
What is the recovery requirement? RPO/RTO decides cost and architecture. Choose backup frequency, PITR, regional replicas, restore drills. Lower RPO/RTO costs more.
SECTION 19 - MISTAKES

Ten Common Database Architecture Mistakes

1. Sharding too earlyYou inherit routing, rebalancing and cross-shard pain before you have proved a single database cannot work.
2. No indexing strategyShared multi-tenant tables become scans, and scans become incidents.
3. Too many indexesEvery write pays the price. Indexes are read accelerators and write tax.
4. Scaling APIs while DB remains bottleneckMore API servers create more database pressure and can make failure arrive sooner.
5. No read/write separationCatalog browsing and reports fight checkout on the same primary.
6. Ignoring replication delayUsers write data, then read from a lagging replica and think the write failed.
7. Poor tenant distributionOne tenant becomes 40% of traffic and harms everyone else.
8. Large transactionsLong transactions hold locks, create contention and increase deadlocks.
9. No backup testingBackup files exist, but nobody knows whether restore works inside RTO.
10. No disaster recovery planPrimary region fails and the team discovers the recovery steps during the incident.

SECTION 21 - TROUBLESHOOTING EXERCISE

Incident: Order API Jumped From 300 ms to 8 Seconds

Initial facts: Order API response time increased from 300 ms to 8 seconds. Database CPU is 95%. Investigate step by step. Start with observability from Day 12, then use the database flow from Section 9.

  1. Confirm scopeIs it only Order API? Only writes? Only one tenant? Did it start after a deploy, campaign or report?DO NOT FIX BEFORE YOU SCOPE
  2. Find the slow queryTrace slow requests, identify the database span and the exact query or procedure consuming time.API SLOWNESS IS A SYMPTOM
  3. Check plan, indexes and row countsIs the database scanning a huge table? Is a useful index missing? Did data volume cross a threshold?INDEX BEFORE SHARD
  4. Check workload mixHow much is read traffic, write traffic and reporting? Are reports running on the primary?SEPARATE WORKLOADS IF THEY FIGHT
  5. Check tenant distribution and connectionsIs one tenant flooding the system? Is the database at max connections? Are connection pools leaking or too large?LOAD SHAPE MATTERS
REVEAL ADDITIONAL INFORMATION GRADUALLY
  1. Clue 1: The slow query filters Orders by TenantId and CreatedDate, but the useful composite index is missing. Decide whether index creation is the first tactical fix and why.
  2. Clue 2: Read traffic is 80% of total traffic. Decide whether read replicas or routing safe reads away from the primary is the next scaling move.
  3. Clue 3: One tenant generates 40% of traffic. Decide whether to throttle, isolate or move that tenant, and what metric proves the need.
  4. Clue 4: Reporting queries run on the production database. Decide whether reporting should move to a replica, read model or warehouse before touching sharding.
  5. Clue 5: The database has reached its connection limit. Decide what to fix first: query/index, connection pool, reporting isolation, read routing or tenant throttling. Explain your order and why.
YOUR TASK

Write your answer as a prioritized incident plan: immediate mitigation, root cause proof, short-term fix, long-term architecture change. The interviewer is looking for order, not heroics.

  3. A product catalog is read 100 times more than it is written. How do read replicas help, and what is the risk?REPLICASSHOW STRONG-ANSWER CHECKLISTEN FORWrites to primary, safe reads to replicas, lower primary load, replication lag and stale reads, primary validation at checkout.
  4. Explain why replication is not backup using a deletion incident.RECOVERYSHOW STRONG-ANSWER CHECKLISTEN FORReplica copies deletes/corruption. Backup/PITR restores to before the mistake. Need both.
  5. You have 10 billion orders and most queries are by month. What partitioning strategy might fit?PARTITIONSHOW STRONG-ANSWER CHECKLISTEN FORDate partitioning, easier recent queries, archiving old data, warning about hot current partition.
  6. One shard has 70% of traffic while others are idle. What happened, and what can you do?SHARDINGSHOW STRONG-ANSWER CHECKLISTEN FORPoor key distribution or hot tenant. Need tenant metrics, throttling, move tenant, reshard/rebalance, future placement strategy.
  7. When should you reject sharding in an interview answer?TRADE-OFFSHOW STRONG-ANSWER CHECKLISTEN FORWhen reads can be solved by replicas, queries by indexes, reports by offload, data by partitioning. Shard only after evidence.
  8. A query filters by TenantId and CreatedDate. What index would you consider and what is the trade-off?INDEXINGSHOW STRONG-ANSWER CHECKLISTEN FORComposite index like (TenantId, CreatedDate), maybe includes selected columns if covering is useful. Read speed vs write/storage cost.
  9. The database reached max connections. Do you increase the connection pool?CONNECTIONSSHOW STRONG-ANSWER CHECKLISTEN FORNot automatically. Check connection leaks, slow queries holding connections, pool size, database saturation and request concurrency. Sometimes the right move is to reduce concurrency and fix the slow workload before raising limits.
  10. A manager wants one transaction around order creation, payment call and inventory update. What risk do you explain?TRANSACTIONSHOW STRONG-ANSWER CHECKLISTEN FORLong transaction, locks, blocking, deadlocks, external call inside transaction. Keep DB transaction small, use idempotency and messaging.
  11. Your reporting team runs heavy cross-tenant reports on the production primary. What architecture change do you recommend first?REPORTINGSHOW STRONG-ANSWER CHECKLISTEN FORMove reporting to replica/read model/warehouse. Protect OLTP. Accept reporting freshness trade-off.
  12. For 10,000 tenants, why not create 10,000 databases on day one?MULTI-TENANTSHOW STRONG-ANSWER CHECKLISTEN FOROperational cost, migrations, monitoring, backup, connection overhead. Hybrid is practical: shared long tail, isolate big/regulatory tenants.
  13. How would you choose between SQL Server/PostgreSQL and Cosmos DB/MongoDB for part of the platform?CHOICESHOW STRONG-ANSWER CHECKLISTEN FORAccess patterns, relationships, transactions, schema flexibility, scale/global distribution. Not popularity.
  14. Define RPO and RTO for order creation in plain English.RPO/RTOSHOW STRONG-ANSWER CHECKLISTEN FORRPO = how much order data can be lost; RTO = how long order creation can be down. Orders/payments usually need low RPO and low RTO.
  15. A primary database fails during checkout. What must your architecture do to avoid lost orders or duplicate payments?FAILURESHOW STRONG-ANSWER CHECKLISTEN FORFailover, retry with backoff, idempotency keys, durable messages/outbox if used, reconciliation, avoid blind retries that duplicate payments.
THE INTERVIEW PATTERN

Most database interview questions are traps against premature solutions. Before choosing replicas, partitioning or sharding, explain what evidence you need and which simpler option you would test first.

DAY 13 - CLOSE

The Database Architect Mindset

Five rules to carry into interviews and production reviews.

01

Find the real database problem.

Read pressure, write pressure, missing index, locks, connection exhaustion, reports and tenant skew are different problems. They deserve different fixes.

02

Use the simplest move that buys enough safety.

A better index can beat a shard. A read replica can beat a rewrite. Vertical scaling is not embarrassing when it is the cheapest safe step.

03

Shard late, but prepare early.

Do not shard before evidence. But design tenant IDs, routing boundaries and reporting separation so future sharding is possible.

04

Recovery is part of the database design.

Replication, backup, point-in-time restore, failover, RPO and RTO are not operations afterthoughts. They are architecture choices.

05

Design for growth, not fantasy.

Do not build a billion-user database architecture for a 10,000-user problem. Build a clean stage one and know exactly what triggers stage two.

The architect's database answer is not "SQL" or "NoSQL". It is the chain: data size, traffic shape, access pattern, scaling path, failure response and recovery promise.
