PART 1 — FIRST PRINCIPLES

Basic Understanding

Before you design an event-driven system, you must know what an event is, how it moves, and why it matters.

1. What is an event?

An event is a fact that happened. Something important occurred: an order was placed, a payment was completed, a user logged in, inventory ran low. The event does not say what to do — it says what happened.

REAL-WORLD EXAMPLE

A doorbell ring is an event. It does not open the door — it tells you someone is there. What you do next is up to you.

2. What is event-driven architecture?

Event-driven architecture is a way of building systems where components communicate by publishing and reacting to events, instead of calling each other directly. A component publishes an event ("OrderCreated") and any other component that cares can react to it — without the publisher knowing who, or even if, anyone is listening.

3. Why do businesses use events?

Because in a business, many things need to happen when one thing happens. When an order is created, you need to:

  • Charge the customer (Payment)
  • Reserve the stock (Inventory)
  • Prepare the shipment (Shipping)
  • Email the confirmation (Notification)
  • Update the sales report (Reporting)

With direct API calls, Order would have to call Payment, then Inventory, then Shipping, then Notification, then Reporting — tight coupling. With events, Order publishes "OrderCreated" and each of those components subscribes and reacts independently.

4. What is the difference between a normal request and an event?

Normal request (synchronous)Client calls Service A. Service A does the work right now and returns the result. The client waits. If Service A is slow, the client is slow. If Service A fails, the client sees the failure immediately.
Event (asynchronous)Service A publishes an event. The message is stored by a broker. Service B picks it up later and does its work. Service A does not wait. If Service B is slow, Service A is not affected. If Service B fails, the event can be retried.

5. What is synchronous processing?

Synchronous means waiting. The caller makes a request and waits for the response before continuing. Example: you click "Place Order" and the page waits until the order is saved and payment is processed before showing "Thank you".

6. What is asynchronous processing?

Asynchronous means not waiting. The caller sends a request and continues without waiting for the response. Example: you click "Place Order", the page shows "Thank you" immediately, and the order is processed in the background.

THE TRADE-OFF IN ONE SENTENCE

Synchronous is simpler and more predictable; asynchronous is more resilient and scalable — but harder to reason about and debug.

7. What is a publisher?

A publisher is the component that creates and sends the event. It decides what happened and announces it to the world (or at least to anyone listening). Example: the Order service publishes "OrderCreated".

8. What is a consumer?

A consumer (or subscriber) is the component that receives and reacts to the event. It listens for events it cares about and does its job when one arrives. Example: the Payment service consumes "OrderCreated" and processes the payment.

9. What is a message broker?

A message broker is the post office for events. Publishers send events to the broker, and the broker delivers them to the consumers. It stores the events temporarily, handles retries, and ensures that every event reaches every interested consumer. Examples: RabbitMQ, Azure Service Bus, Kafka.

10. What is a queue?

A queue is a line of messages. Events are placed at the end of the queue and consumed from the front, in order. Each event is delivered to one consumer (even if multiple consumers are listening, only one gets each event). Example: a queue for order processing where each order is handled by one worker.

11. What is a topic?

A topic is a category of events. Publishers send events to a topic, and all consumers that subscribe to that topic receive a copy of every event. Example: a "Orders" topic where Payment, Inventory, Shipping, Notification, and Reporting all receive every "OrderCreated" event.

12. Why should different business areas communicate through events?

Because it decouples them. Order does not need to know about Payment, Inventory, Shipping, Notification, or Reporting. It just publishes "OrderCreated". Each of those services decides independently whether and how to react. This makes the system:

  • Easier to change — you can add a new consumer without changing the publisher.
  • More resilient — if Payment is down, Order can still publish events and the others can still work.
  • Easier to scale — each service can scale independently based on its own load.

13. When should events NOT be used?

Events are not free. They add complexity, latency, and eventual consistency. Do not use events when:

  • The caller needs an immediate answer — if the client must wait for the result, use a synchronous request.
  • Strong consistency is required — if the next step must see the result of this step immediately, use a direct call.
  • There is only one consumer — if only one component cares, a direct API call is simpler.
  • The system is very small — events add overhead that is not justified for simple systems.
THE ONE-SENTENCE SUMMARY OF PART 1

An event is a fact. A publisher announces it. A broker delivers it. Consumers react to it. That is the entire architecture.

PART 3 — THE FLOW

Event-Based Design

Let's walk through the Order Management example step by step.

The OrderCreated event

The Order service publishes:

EVENT: OrderCreated { OrderId: "ORD-12345", CustomerId: "CUST-789", Items: [...], Total: 149.99, CreatedAt: "2026-02-17T14:30:00Z" }

Consumers of OrderCreated:

  • Payment — processes the payment for this order.
  • Inventory — reserves the stock for the items in the order.
  • Shipping — prepares the shipment for this order.
  • Notification — sends an email or SMS confirmation to the customer.
  • Reporting — updates the sales dashboard and reports.

What happens next

  • Order CreatedThe customer places an order. The Order service saves the order and publishes OrderCreated.PUBLISHER: ORDER SERVICE
  • Event publishedThe broker receives the event and stores it temporarily. It is now the broker's responsibility to deliver the event to all consumers.BROKER: RABBITMQ / AZURE SERVICE BUS / KAFKA
  • Payment processes paymentThe Payment service consumes the event, processes the payment, and publishes PaymentCompleted (or PaymentFailed).CONSUMER: PAYMENT SERVICE
  • PaymentSuccessfulThe Payment service publishes this new event. Inventory, Shipping, Notification, and Reporting may all consume it.NEW EVENT FOR THE NEXT STEP
  • Inventory reserves stockThe Inventory service consumes PaymentCompleted (or OrderCreated directly), reserves the stock, and publishes InventoryReserved.CONSUMER: INVENTORY SERVICE
  • InventoryReservedPublished by Inventory. Shipping may consume this to know it is safe to prepare the shipment.EVENT CHAIN: ORDER → PAYMENT → INVENTORY → SHIPPING
  • Shipping prepares shipmentConsumes InventoryReserved (or PaymentCompleted), prepares the shipment, and publishes ShipmentPrepared.CONSUMER: SHIPPING SERVICE
  • Notification informs customerConsumes OrderCreated (or PaymentCompleted or ShipmentPrepared), sends email/SMS, publishes NotificationSent.CAN CONSUME EARLY OR LATE IN THE FLOW
  • Reporting updates dashboardConsumes OrderCreated, PaymentCompleted, InventoryReserved, ShipmentPrepared to update reports and dashboards.REPORTING OFTEN CONSUMES MANY EVENTS
    • WHAT YOU SHOULD NOTICE

    Order does not call Payment. Order does not call Inventory. Order does not call Shipping. Order publishes an event and forgets. Each consumer does its job independently, at its own speed, and can fail and retry without affecting the others.

    The write path (create order) is synchronous and direct. Everything else is asynchronous and event-driven. This gives you the best of both worlds: immediate feedback for the user, and resilient, scalable background processing for the rest.
