PART 01 — START LIKE AN ARCHITECT

Understand the Product Before You Draw Any Box

When an interviewer says "Design WhatsApp", junior candidates immediately start drawing WebSocket clusters, Redis caches, and database shards. That is a major interview mistake. A Senior Solution Architect starts by asking: What is this product? Who uses it? What must never break?

WHY DRAWING BOXES FIRST HURTS YOU

If you pick technologies before understanding the requirements, you build the wrong thing. A banking chat system requires long message retention, legal auditing, and server-side search. WhatsApp requires privacy, minimal server storage, ephemeral delivery, and offline queuing. If you do not ask questions, you will design the wrong system.

1 · Functional Requirements (What the system does)

Functional requirements describe the capabilities visible to the user. We group them logically so we can see the scope of the interview:

ACCOUNT & IDENTITYUser registration with phone number verification, login on mobile and web, contact discovery (matching phone book contacts).
ONE-TO-ONE MESSAGINGSend and receive text messages between two users in real time with very low latency (under 100 milliseconds).
GROUP MESSAGINGCreate groups, add and remove members, send messages to groups with up to 1,000 or 10,000 members.
MESSAGE STATUS TICKSTrack lifecycle states: Sent (single grey tick), Delivered to device (double grey tick), and Read by user (double blue tick).
PRESENCE & ACTIVITYSee if a contact is Online, when they were Last Seen, and a real-time "User is typing..." indicator.
OFFLINE QUEUINGIf the recipient is offline, store the message safely, trigger a push notification, and deliver it automatically when they reconnect.
RICH MEDIA ATTACHMENTSSend images, short videos, voice notes, audio, and PDF documents with thumbnail generation and progressive download.
SAFETY & CONTROLSBlock and unblock contacts, report spam, delete for everyone (within a time window), and delete for me.

2 · Non-Functional Requirements (How well it performs)

Non-functional requirements describe the system qualities — speed, reliability, uptime, and capacity. Every single requirement forces an architectural decision:

REQUIREMENT TARGET NUMBER / BEHAVIOR ARCHITECTURAL IMPACT
Scale & Users 500M registered, 100M daily active, 20M concurrently connected. We cannot hold all connections on one machine; requires a distributed connection gateway tier separated from business logic.
Delivery Latency Message delivery < 100ms when both sender and receiver are online. HTTP polling is too slow and wasteful; forces persistent two-way connections (WebSockets) kept open in memory.
High Availability 99.99% uptime (~52 minutes downtime per year maximum). No single point of failure; every layer (gateway, broker, database) must be clustered with automatic failover.
Strict Reliability Zero message loss. A message must never disappear into thin air. Store-then-deliver: the server must persist the message to durable storage before telling the sender "we got it".
Message Ordering Messages must appear on the recipient's phone in the exact order sent. Requires conversation-based sequence numbers or single-partition message queues per conversation.
Data Retention Option A: Store permanently in cloud. Option B (WhatsApp style): Delete from server once delivered. Drastically changes storage costs. In WhatsApp, the server is a temporary buffer, not a permanent archive.
Security & Privacy End-to-End Encryption (E2EE) so even the server cannot read message content. The server handles encrypted binary blobs; search must happen locally on the phone, not on the server.
SENIOR ARCHITECT INTERVIEW TIP

In the first 3 minutes, clarify the retention model: "Are we designing a cloud-archive system like Telegram / Slack where servers store history forever, or an ephemeral store-and-forward system like WhatsApp where messages are deleted from the server immediately after delivery?" This single question proves you think about cost, compliance, and storage before drawing.

PART 02 — DEFINE REALISTIC SCALE

Estimate the System Scale With Simple Math

Never invent random large numbers during an interview. Start with simple baseline assumptions and multiply them cleanly so the interviewer can follow every step of your reasoning.

BASELINE ASSUMPTIONS TO STATE OUT LOUD

  • 500 Million total registered accounts.
  • 100 Million Daily Active Users (DAU) who open the app every day.
  • 20 Million peak concurrently connected users (users online at the same moment).
  • 40 messages sent per active user per day on average (combination of direct and group chats).
  • Average text message size: 100 bytes (text + sender ID + metadata).
  • Media: 5% of all messages carry an image, audio clip, or video (average size 200 KB).

1 · Messages Per Second (Throughput)

DAILY MESSAGES & AVERAGE RPS

100,000,000 active users × 40 messages/day = 4 Billion messages per day.

Seconds in a day = 24 × 3,600 = 86,400 seconds ≈ ~86,400 seconds (round to 100,000 for mental math).

Average message rate = 4,000,000,000 ÷ 86,400 ≈ ~46,000 messages per second (average RPS).

PEAK MESSAGE RATE (BURST TRAFFIC)

Traffic is never evenly distributed across 24 hours. Evenings, holidays, and breaking news create spikes.

Using a standard 2.5× to 3× peak multiplier:

Peak rate = 46,000 × 2.5 ≈ ~115,000 to 140,000 messages per second at peak.

2 · Concurrent Connections (The Gateway Load)

At peak hour, 20 Million users keep their app open and connected simultaneously. Each user holds one persistent TCP/WebSocket socket.

CONNECTION CAPACITY

A modern optimized Linux server can comfortably hold around 100,000 to 200,000 idle TCP connections (limited by RAM for socket buffers, file descriptors, and OS memory).

Servers required = 20,000,000 connections ÷ 100,000 per server = 200 Gateway Servers.

With N+1 redundancy and regional clustering: ~300 to 400 Gateway Servers globally.

3 · Daily and Yearly Storage Math

DATA TYPE VOLUME PER DAY DAILY STORAGE ANNUAL STORAGE
Text Messages 4 Billion messages × 100 bytes 400 GB / day ~146 TB / year
Media Files (5%) 200 Million files × 200 KB 40,000 GB = 40 TB / day ~14.6 Petabytes / year
WhatsApp Ephemeral Model Messages deleted from server upon delivery; only offline buffered (~5% offline) ~20 GB active buffer Disappears once delivered!

4 · Inbound Network Bandwidth

Text bandwidth: 46,000 msgs/sec × 100 bytes ≈ 4.6 MB/sec (modest).

Media bandwidth: (200,000,000 files × 200 KB) ÷ 86,400s ≈ ~460 MB/sec (~3.7 Gbps).

THE ARCHITECT'S SCALE CONCLUSION

"Text messages generate high IOPS (Input/Output Operations Per Second) and high connection concurrency, while media generates high storage and network bandwidth. Therefore, we must completely separate the media pipeline from the real-time text pipeline."

What to Combine Initially vs Split Later

START TOGETHER (CORE MONOLITH)User Profile, Contacts, Conversation metadata, and Reporting can initially live in a single service sharing one transactional database. This avoids distributed transactions and makes development fast.
SPLIT DAY ONE (DIFFERENT WORKLOADS)The Real-Time Connection Gateway and Message Ingestion must be separate from day one. Connection servers hold millions of idle sockets (memory-bound), whereas message ingestion performs CPU/IO-bound processing.
SPLIT ON GROWTH (SCALE PRESSURE)Presence (extremely high write frequency from heartbeats), Group Service (heavy fan-out computation), and Media Service (heavy bandwidth and file transcoding) must scale independently.
THIRD-PARTY ASYNC SPLITPush Notification Service must always be isolated behind a message queue. Third-party providers (Apple APNS and Google FCM) can be slow or fail; they must never slow down message ingestion.

PART 05 — SENDING A MESSAGE

User A Sends "Hello" to User B (Step by Step)

Walk this flow slowly during an interview. The interviewer wants to know: Where is the message validated? When is it saved? How does it cross from one server to another? What happens if delivery fails?

  1. CLIENT OUTBOXUser A types "Hello" and taps SendThe phone app generates a client-side temporary message ID, stores the message in local SQLite with status PENDING, and sends it over the existing WebSocket connection.
  2. GATEWAYGateway Server #04 receives the frameThe gateway checks the sender's token, validates authentication, and forwards the payload to the Message Service internally.
  3. VALIDATION & DEDUPEMessage Service validates the messageThe service checks: Are A and B blocked? Is A a member of this conversation? Has this client message ID been processed before? If valid, it assigns a server sequence number and timestamp.
  4. PERSIST FIRSTStore the message in durable storageThe message is written to the Message Database in state STORED. Rule: We never attempt delivery before persisting. If the server crashes 1 millisecond later, the message is safe.
  5. SENDER ACKSend Single Tick ACK back to User AThe Message Service notifies Gateway #04, which pushes an ACK to User A over WebSocket. User A's phone updates the clock icon to a Single Grey Tick (✓). User A knows the server is now responsible.
  6. LOCATE RECEIVERLookup User B's connection in Session RegistryThe service asks the Session Registry (Redis): "Where is User B?"
    Outcome 1 (Online): Redis returns Server #09.
    Outcome 2 (Offline): Redis returns NULL (not connected).
  7. ONLINE DELIVERYIf User B is Online: Route to Gateway #09The message is forwarded internally to Gateway #09, which pushes the message down the active WebSocket to User B's device.
  8. DELIVERY ACKUser B's phone sends Delivery ACKAs soon as User B's operating system receives the bytes and writes them to local storage, it sends a Delivery ACK back to the server. The message state updates to DELIVERED, and an event is forwarded to User A's gateway turning User A's tick into a Double Grey Tick (✓✓).
  9. OFFLINE FALLBACKIf User B is Offline: Queue & PushThe message is placed in User B's offline queue, and an asynchronous event is sent to the Push Notification Service (APNS/FCM) so User B's phone rings or shows an alert.
GOLDEN RULE OF MESSAGING ARCHITECTURE

"Store before Acknowledging; Acknowledge before Delivering." Never confirm receipt to the sender until the message is safely on disk. Never attempt network delivery without having a stored copy to retry if the network drops.

PART 06 — ONLINE USER VS OFFLINE USER

Handling the Online vs Offline Split

A messaging system must treat online and offline users as two completely different delivery pipelines. Online users receive messages in milliseconds down an open wire; offline users require storage, push notifications, and catch-up synchronization.

SCENARIO ONLINE RECIPIENT OFFLINE RECIPIENT
Detection Session Registry has an active user_id → gateway_server_id key with an unexpired heartbeat. Session Registry has no record, or the connection timed out and heartbeat expired.
Delivery Pipe Direct memory push through the existing TCP/WebSocket connection held on the target gateway. Third-party Push Notification (Apple APNS / Google FCM) to wake up device; message waits in offline queue.
Latency 20 to 80 milliseconds end-to-end. Delivered whenever user reconnects (minutes, hours, or days later).
Storage Lifetime Can be deleted immediately from server once Delivery ACK is received (WhatsApp model). Retained in offline inbox queue until delivered or until TTL expiration (e.g., 30 days).
Ticks Shown to Sender Single grey tick turns into double grey tick (✓✓) almost immediately. Remains on single grey tick (✓) until recipient turns phone on and app connects.
Catch-up Mechanism Not needed; streamed in real time. Sync Protocol: Upon reconnecting, client sends last_received_sequence_number; server pulls all messages with seq > last_seq and streams them in batches.

The Reconnection Catch-Up Flow (The Pull-on-Connect Pattern)

  1. User B switches phone out of Airplane ModeThe app establishes a fresh WebSocket connection to the closest gateway server.
  2. Authentication & Session RegistrationGateway authenticates User B and registers User B → Gateway #12 in the shared Redis Session Registry.
  3. Sync Handshake (The Catch-Up Request)User B's phone sends its current high-water mark: "My last received message sequence was 4,821."
  4. Drain Pending Offline QueueThe server queries the offline message store for all messages addressed to User B where seq > 4,821, sorted by sequence number.
  5. Chunked Stream DeliveryThe server pushes pending messages down the WebSocket in batches of 50 or 100 messages to prevent flooding the client's memory.
  6. Batch Delivery AcknowledgementUser B's phone saves the batch to local SQLite and returns an ACK. The server marks those messages as delivered and deletes them from the server buffer.
WHY NOT DELIVER MESSAGES INSIDE THE PUSH NOTIFICATION?

Push notifications (APNS/FCM) have strict payload limits (usually 4 KB), can be dropped by mobile operating systems, and do not guarantee delivery or ordering. The push notification should only say: "You have new messages". When the user taps it, the app opens its WebSocket and pulls the actual encrypted messages directly from our servers.

PART 07 — REAL-TIME CONNECTIONS

How Phones Keep a Fast, Open Line to the Server

In a chat app, you cannot wait 5 seconds to know if your friend said "Yes" or "No". The server needs a way to push bytes to the phone the millisecond they arrive. Let us compare the three ways to do this in plain English.

TECHNIQUE HOW IT WORKS IN SIMPLE ENGLISH ADVANTAGES & DISADVANTAGES SERVER LOAD & UX WHEN TO USE IT
Short Polling The phone asks the server every 2 seconds: "Any new messages for me?" Server responds "No", closes HTTP connection, phone asks again 2 seconds later. Simple to build.
Terrible waste: 99% of requests return empty. Burns mobile battery, floods servers with HTTP headers. 		Massive server CPU load. High latency (messages delayed by up to the polling interval). Never use for real-time chat. Good only for low-frequency dashboards.
Long Polling The phone sends an HTTP request. The server holds the connection open and waits. The moment a message arrives, the server responds and closes the connection. The phone immediately opens a new one. Faster than short polling; works through restrictive enterprise firewalls.
High overhead: each message forces a new TCP 3-way handshake and HTTP headers. 		Medium-heavy server load. Better UX, but connection churn creates CPU spikes during high message volume. Fallback mechanism when WebSockets are blocked by corporate proxies.
WebSocket (Persistent Bi-Directional) Starts as an HTTP request, then upgrades to a persistent, full-duplex TCP socket. The connection stays open 24/7. Both phone and server can send raw data frames anytime without headers. Ultra-low latency (<20ms). Minimal packet overhead (2 to 8 bytes header vs 1KB HTTP header). Saves battery and server bandwidth.
Requires connection gateway servers, heartbeats, and session routing.		 Lowest per-message server cost. Outstanding real-time UX (typing indicators, ticks feel instantaneous). The industry standard for all modern chat apps (WhatsApp, Slack, Discord).
WHAT ABOUT SSE (SERVER-SENT EVENTS)?

Server-Sent Events (SSE) is one-way: server pushes to client over HTTP, but client cannot send data back on the same connection (must make separate HTTP POST requests). In a messaging app where users are constantly sending messages, typing events, and ACKs back and forth, WebSocket is superior because it is truly bi-directional over a single socket.

PART 08 — CONNECTION MANAGEMENT

Managing 20 Million Concurrent WebSockets

Holding 20 million open TCP connections across hundreds of servers is one of the hardest distributed systems problems. An architect must answer: How do servers know who is connected where? What happens when a server dies? How do users reconnect without crushing the system?

1 · The Session Registry (The Global Phonebook)

When User A sends a message to User B, User A's connection server (Gateway #04) does not hold User B's connection. User B is connected to Gateway #09 on the other side of the data center. How does Gateway #04 find Gateway #09?

THE REDIS SESSION REGISTRY PATTERN

We maintain an in-memory, distributed key-value store (Redis Cluster):

Key: user_id:100234 → Value: { gateway_id: "gw-09.region-east", socket_id: "s-8821", connected_at: 1711200000 }

Lookup time: Under 1 millisecond. Gateway #04 queries Redis, discovers User B is on gw-09, and forwards the message internally across the fast datacenter network directly to gw-09.

2 · Heartbeats and Keep-Alive (Detecting Silent Drops)

Mobile phones move between cell towers, enter tunnels, or lose battery without cleanly closing the TCP connection. This creates "half-open connections" — the server thinks the user is online, but the wire is dead.

  • Ping-Pong Heartbeats: The client sends a tiny 1-byte "Ping" frame every 30 to 60 seconds. The gateway replies with a 1-byte "Pong".
  • Timeout Expiration: If the gateway sees no ping for 90 seconds, it marks the socket dead, closes the TCP connection, and deletes the entry from the Session Registry. User is now marked Offline.
  • Adaptive Interval: If the phone is on battery saver or backgrounded, it can stretch the heartbeat to 2–3 minutes to preserve battery life.

3 · What Happens When a Gateway Server Crashes?

Suppose Gateway #09 suddenly loses power or crashes. 100,000 users immediately lose connection. If 100,000 phones all reconnect in the exact same millisecond, they will crush the remaining gateways in a Thundering Herd stampede.

HOW TO PREVENT A RECONNECTION STAMPEDE

Every client must implement Exponential Backoff with Full Jitter:

  • Attempt 1: Wait random time between 1 and 3 seconds before reconnecting.
  • Attempt 2: Wait random time between 2 and 6 seconds.
  • Attempt 3: Wait random time between 4 and 12 seconds.

Jitter randomizes the retry time so 100,000 devices reconnect smoothly spread across 30 seconds instead of hitting the load balancer at the same microsecond.

PART 10 — MESSAGE ORDERING

Guaranteeing Messages Arrive in the Exact Order Sent

Imagine User A asks: 1. "Can you come?" followed by 2. "Never mind, I am sick." If User B receives message #2 before message #1, the conversation becomes completely confusing. Maintaining correct message ordering across distributed networks is a classic interview challenge.

Why Clock Timestamps Do Not Work (The Clock Drift Problem)

Candidates often say: "We just sort messages by timestamp." This will fail in production. Every phone and every server has slight clock drift (NTP time synchronization can easily be off by 50 to 500 milliseconds). If User A's phone clock is 2 seconds fast, their messages will jump out of order.

The Three Architectural Solutions

1. CONVERSATION SEQUENCE NUMBERS (RECOMMENDED)The server maintains an atomic monotonic counter for each conversation (chat room): seq: 1, 2, 3, 4.... When a message is written to storage, it is stamped with the next sequence number in that chat. The recipient phone renders messages strictly sorted by sequence_number, completely ignoring device clock differences.
2. CLIENT PREVIOUS-MESSAGE POINTER (CHATTREE)Each message sent by the client includes the ID of the message that came immediately before it: prev_message_id: "msg-101". The receiving client builds a linked list of messages. If a message arrives with an unknown previous ID, the client pauses rendering and requests the missing gap from the server.
3. CONVERSATION-PARTITIONED MESSAGE BROKERWhen messages are pushed into Kafka or Pulsar, the partition key is the Conversation ID: hash(conversation_id) % num_partitions. Because Kafka guarantees strict FIFO (First-In, First-Out) ordering within a single partition, all messages in that conversation are processed in exact arrival order by a single consumer thread.
WHAT ABOUT GROUP CONVERSATIONS?In a group with 10 people talking at once, the "true order" is defined as the order in which the messages successfully committed to the server database. The server acts as the central arbiter of truth and assigns the sequence numbers.
HOW TO EXPLAIN ORDERING IN 30 SECONDS

"We never rely on client timestamps for ordering because phone clocks drift. Instead, we use server-assigned monotonic sequence numbers per conversation, reinforced by partitioning message queues by Conversation ID. The client displays messages sorted by sequence number, ensuring identical message order on every participant's device."

PART 11 — DUPLICATE MESSAGES

Preventing Duplicate Messages (Idempotency)

The Scenario: User A types "Happy Birthday!" and taps Send. The server receives the message and saves it to the database. But before the server can return the ACK, User A drives into an elevator and the network drops. User A's phone thinks the message failed, so it automatically retries 5 seconds later. Does User B receive two "Happy Birthday!" messages?

WHY DUPLICATES ARE DANGEROUS

Duplicate messages cause confusion in personal chats, double-charges in conversational commerce, and explode push notification noise. The messaging pipeline must be idempotent.

Idempotent: Performing an operation once produces the exact same result as performing it 10 times.

Three Practical Approaches to Deduplication

APPROACH HOW IT WORKS TRADE-OFFS & RECOMMENDATION
1. Client UUID + Database Unique Constraint The client app generates a globally unique UUID (e.g., client_msg_id: "550e8400-e29b...") before sending. The database table has a UNIQUE CONSTRAINT (conversation_id, client_msg_id). 100% reliable guarantee.
Database constraint checks can become an indexing bottleneck at 100,000 writes/sec if not partitioned correctly.
2. Redis Bloom Filter + Deduplication Cache (Fast Path) Before hitting the database, the Message Service checks an in-memory Redis cache with a 10-minute TTL: SETNX dedup:msg_id "1" EX 600. If key exists, it is a duplicate and is discarded immediately. Microsecond execution time; absorbs 99.9% of retries without database load.
If Redis node restarts without persistence, duplicate window opens briefly.
3. Client-Side Message ID Deduplication (Defense in Depth) Even if the server accidentally delivers a duplicate down the WebSocket, the recipient's phone checks its local SQLite table: INSERT OR IGNORE INTO messages WHERE msg_id = ?. The user never sees two identical bubbles on their screen.
Wastes bandwidth down the wire, so server deduplication is still required.
THE ARCHITECT'S PREFERRED DESIGN

Layered Defense: We generate client_message_id on the phone. The server checks an in-memory Redis deduplication window (Option 2) for ultra-fast filtering, backed by a unique key in the partitioned message storage (Option 1). Finally, the client phone applies local deduplication (Option 3). This prevents duplicate database rows, duplicate push notifications, and duplicate chat bubbles.

PART 12 — RETRY & FAILURE HANDLING

Why Blind Retries Cause Catastrophic Cascading Failures

When a network glitch or database slowdown occurs, systems that blindly retry everything immediately end up multiplying the traffic by 5× or 10×. This turns a minor 2-second hiccup into a full 3-hour global outage.

1 · Exponential Backoff with Jitter (The Golden Formula)

If an attempt fails, never retry immediately. Wait progressively longer intervals, and add a random number (jitter) so millions of devices don't synchronize their retries:

BACKOFF FORMULA

Wait_Time = Min(Max_Interval, Base_Interval × (2 ^ attempt_count)) + Random_Jitter

Example: Attempt 1 = 1s ± 0.3s; Attempt 2 = 2s ± 0.6s; Attempt 3 = 4s ± 1.2s; Max cap = 30 seconds.

2 · Acknowledgements (ACKs) and Unacked Timers

When Gateway #09 pushes a message to User B, it starts an unacked timer (e.g., 5 seconds). If User B's phone does not send a Delivery ACK within 5 seconds, Gateway #09 assumes User B just lost network, cancels the push, and routes the message into the Offline Queue + Push Notification path.

3 · Dead-Letter Queues (DLQ)

What if a message payload is corrupted (e.g., malformed JSON or illegal character) and crashes the worker thread every time it is read? Without a circuit breaker, the worker will consume the message, crash, restart, re-read the message, crash again — forever (a Poison Pill).

DEAD-LETTER HANDLING RULE

Every message has a retry counter header: retry_count. If retry_count > 3, the consumer thread removes the message from the main queue and drops it into a Dead-Letter Queue (DLQ). Alerts fire for engineers to inspect the payload, while healthy messages behind it continue processing without delay.

PART 13 — MESSAGE STORAGE

PART 14 — CONVERSATION STORAGE & PARTITIONING

Sharding: Slicing Billions of Messages Across Nodes

You cannot store 140 Terabytes of messages per year on a single database disk. You must shard (partition) the database across dozens of database nodes. The choice of Partition Key makes or breaks the entire system.

Comparing the Three Partitioning Strategies

PARTITION STRATEGY HOW IT WORKS PROS, CONS & VERDICT
By User ID
hash(user_id)		 Every user has their own mailbox table. When A sends a message to B, the server writes two copies: one to A's partition and one to B's partition. + Reading a user's inbox is fast.
− Double write on every message; synchronizing chat state between two partitions is difficult.
By Conversation ID (Recommended)
hash(conversation_id)		 All messages for a given chat (direct or group) live together on the exact same database shard, sorted by sequence_number. + One single write per message!
+ Fetching chat history requires reading only one single partition.
− Risk of Hot Shards if a celebrity group has 100,000 members.
By Geographic Region
country_code / region		 European users go to EU database shards; US users go to US shards. + Complies with data residency laws (GDPR).
− Cross-border chats (user in London chatting with user in New York) require cross-region coordination.

How to Defeat the "Hot Shard" Problem (Celebrity Group Chats)

Suppose a popular news channel or football team group chat has 50,000 members and produces 1,000 messages a minute. If all messages hit one shard, that database node's CPU and disk will hit 100%.

COMPOUND PARTITION KEY (SALTING BY TIME)

Instead of partition_key = conversation_id, use a Compound Bucketed Key:

partition_key = conversation_id + ":" + YYYY-MM (e.g., "grp-991:2026-03")

Messages for March 2026 live on one shard; messages for April automatically move to another shard. For hyper-active mega-groups, we can add a secondary random salt (0 to 3) to spread the write load across 4 separate database nodes.

PART 15 — GROUP CHAT FAN-OUT

Delivering One Message to 10,000 Group Members

One-to-one messaging is simple: 1 message in = 1 message out. Group messaging is vastly harder: 1 message sent to a group of 10,000 members means 10,000 deliveries and 10,000 potential push notifications. This multiplication is called Fan-Out.

APPROACH HOW IT WORKS ADVANTAGES & DISADVANTAGES BEST SUITED FOR
Fan-Out on Write (Push Model) When User A posts to the group, the Group Worker copies the message into the individual inbox/queue of all 10,000 members immediately. + Reading is instantaneous: each user reads only their local inbox.
− Terrible write amplification: 1 post creates 10,000 database writes and 10,000 WebSocket events. 		Small groups (<100 members), family chats, work teams.
Fan-Out on Read (Pull Model) The message is stored only once in the group conversation table. When member B opens the app, member B queries: "Give me new messages in Group G since my last visit." + Super-fast write: exactly 1 database write regardless of group size!
− High read load when 10,000 users all open the app after a notification. 		Mega channels, public announcement groups, broadcast lists.

The Hybrid Fan-Out Architecture (The Industry Standard)

FIG 3 — HYBRID GROUP FAN-OUT: WRITE ONCE TO DISK, BROADCAST BATCHES TO GATEWAYS BY SERVER ID
CRITICAL EFFICIENCY TRICK: GATEWAY COALESCING

If 500 members of a 10,000-person group happen to be connected to Gateway #04, the Fan-Out worker does not send 500 separate network requests to Gateway #04. It sends one single internal request with the message payload and an array of 500 socket IDs: { msg: "...", sockets: [s1, s2, ... s500] }. Gateway #04 receives it once and pushes it down the 500 local sockets. This reduces inter-server network traffic by 99.8%!

PART 16 — PRESENCE (ONLINE / OFFLINE)

"Is This User Online?" (The Presence Engine)

Presence sounds simple: a user connects, mark them Online; they disconnect, mark them Offline. At 100 million active users, presence generates more write traffic than messages themselves. Let us see why and how to design it cleanly.

1 · Why Presence is Ephemeral (Short-Lived)

  • Presence data is transient. If a user was online 3 minutes ago, storing that in permanent disk storage is completely useless. Only the last_seen timestamp needs durability.
  • Because mobile connections flap frequently (phone locks, enters an elevator, switches to Wi-Fi), presence status changes dozens of times per hour per user.
  • Therefore, Presence MUST live in an in-memory key-value store (Redis / Memcached) with automatic TTL.

2 · Heartbeat and Lease Expiration

REDIS PRESENCE PATTERN

When User A connects, Gateway sets: SET presence:user_123 "ONLINE" EX 60 (expires in 60 seconds).

Every 30 seconds, User A's phone sends a heartbeat ping. Gateway renews: EXPIRE presence:user_123 60.

If User A drops their phone in water or loses signal, the key automatically vanishes from Redis after 60 seconds. No cleanup scripts or background garbage collection needed!

When marking offline, we write: SET last_seen:user_123 "1711200450" (persisted).

3 · The Presence Fan-Out Trap (Do Not Broadcast!)

INTERVIEW RED FLAG: NEVER BROADCAST PRESENCE

Suppose User A has 500 contacts in their address book. When User A goes online, should the server broadcast "User A is Online" to all 500 contacts? NO!

If 20 million users are going online and offline, 500 broadcasts each would equal 10 Billion presence events per second. The network would melt.

THE SOLUTION: PULL / SUBSCRIPTION ON VIEW

We only send User A's presence to User B if User B has currently opened the chat screen with User A. When User B opens the chat with User A, User B subscribes to User A's presence channel. When User B leaves the chat, they unsubscribe. This cuts presence traffic by over 98%.

PART 17 — TYPING INDICATORS

"User is Typing..." (Ephemeral Signaling)

When someone starts typing, you see three bouncing dots. Junior engineers treat this like a chat message and try to save it to the database. An architect recognizes that typing indicators are ephemeral signaling events.

CHARACTERISTIC CHAT MESSAGE TYPING INDICATOR
Durability Must be written to disk; zero data loss allowed. Never saved to disk. Memory only; if dropped, nobody cares.
Lifetime Permanent (or retained until delivered). Expires automatically in 3 to 5 seconds.
Delivery Guarantee At-least-once with ACK confirmation. Best-effort (Fire-and-forget). No ACKs, no retries.
Offline Handling Queue message, send push notification. Discard immediately. Never send a push notification saying "User is typing..."!

Client-Side Throttling (The Key to Cost Control)

If a user types 60 words per minute, their fingers press keys 5 times a second. The client app must throttle typing events: when the first keystroke occurs, send a { type: "TYPING_START", conversation_id: "c1" } frame, and suppress all further events for the next 4 seconds. When the user stops typing for 3 seconds, send { type: "TYPING_STOP" }.

PART 19 — PUSH NOTIFICATIONS

Waking Up Devices When the App is Closed

When User B locks their phone, puts it in their pocket, or kills the app, the operating system terminates the WebSocket connection. The only way to reach User B is via Apple Push Notification service (APNS) or Google Firebase Cloud Messaging (FCM).

  • STEP 1Message persisted in offline queueThe Message Service confirms User B is offline and writes the message to User B's pending delivery queue.
  • STEP 2Emit Notification Event to Message BrokerThe service emits an asynchronous event PushNotificationNeeded { recipient: User_B, conversation: C1 } into Kafka/RabbitMQ. Crucial: This never blocks the sender's ACK.
  • STEP 3Worker fetches device token & preferencesThe Notification Worker pulls the event, queries User B's device push tokens (iOS / Android), and checks if the chat is muted.
  • STEP 4Dispatch to APNS / FCM GatewayThe worker calls the Apple/Google push APIs over HTTP/2. If the third-party API is slow (e.g., takes 800ms), only the background worker waits.
  • STEP 5Device wakes up & establishes WebSocketThe mobile OS displays the alert banner. When the user taps it, the app opens, connects to our closest WebSocket gateway, and drains the pending message queue.
    • CHALLENGE HOW THE ARCHITECT SOLVES IT
    Muted Chats & Do-Not-Disturb The notification worker checks Redis user settings before calling APNS/FCM. If muted, the notification is silently suppressed while the message remains safely in the offline queue.
    Notification Collapse (Badge spam) If 50 messages arrive in a busy group chat, we use the APNS/FCM collapse_key (thread ID). The phone displays one single summary: "50 new messages in Family Group" instead of chiming 50 individual times.
    Push Provider Outage (FCM/APNS down) Notifications are retried with exponential backoff and dropped if older than 24 hours. The messages themselves are safe in the server database; when the user manually opens the app, all messages load immediately.
    PART 20 — SCALING EACH LAYER

    Scaling Components Independently

    Never try to scale the whole system with a single magic command. Different services have completely different performance bottlenecks: some are memory-bound, some are CPU-bound, and some are disk-I/O bound.

    COMPONENT BOTTLENECK HOW IT SCALES AUTOSCALING TRIGGER
    WebSocket Gateways Memory (RAM) & File Descriptors (holding 100k open sockets per server). Horizontally add more gateway instances behind a TCP/Layer-4 load balancer (AWS NLB / HAProxy). Completely stateless except for socket handles. Active socket count > 120,000 per node, or RAM utilization > 70%.
    REST / HTTP APIs CPU & Network (Registration, profile uploads, authentication). Stateless container clusters (Kubernetes / ECS). Easily scale from 20 to 200 nodes during traffic rushes. CPU utilization > 65%, or HTTP p95 response time > 250ms.
    Message Service CPU & Message Queue IOPS (validation, deduplication, routing). Scale consumer worker pools partitioned by Conversation ID. Increase partition count in Kafka/Pulsar. Consumer group lag (messages pending in queue) > 5,000.
    Message Storage Disk Write IOPS & Storage Capacity. Add more storage nodes to the NoSQL cluster (Cassandra / ScyllaDB). Hash-ring automatically rebalances ranges. Disk write latency > 10ms, or storage capacity > 75%.
    Presence Service In-Memory Key Evictions & Network PPS (packets per second from heartbeats). Redis Cluster sharded by hash(user_id) with read replicas for status lookups. Redis operations/sec > 80,000 per shard, or memory > 70%.
    Media Processing CPU & Bandwidth (creating image previews, transcode audio). Asynchronous worker queue reading from S3 bucket events. Auto-scales aggressively on upload spikes. Media queue depth > 500 items.
    KEY TAKEAWAY: SEPARATE STATEFUL FROM STATELESS

    Stateless tiers (API servers, fan-out workers, notification processors) can be booted up or killed in 10 seconds based on CPU. Stateful tiers (WebSocket gateways holding active connections, Redis session registries, Cassandra storage) require careful connection-draining and data rebalancing. Never mix stateful socket handling with stateless business logic in the same process.

    From One City to Multiple Continents

    Light travels through fiber-optic cables at ~200 km per millisecond. If your servers are only in Virginia (USA), a user in Singapore will experience a 220 millisecond round-trip delay on every single packet. For real-time messaging, we must bring edge servers close to the user.

    FIG 5 — MULTI-REGION ARCHITECTURE: CONNECT LOCALLY, ROUTE INTERNALLY OVER DEDICATED FIBER

    1. Local Edge Connection: Alice's phone connects to the London gateway (15ms). Bob's phone connects to the Tokyo gateway (20ms).

    PART 22 — CONSISTENCY REQUIREMENTS

    Where Strong Correctness is Mandatory vs Where Delay is Fine

    CAP Theorem in Simple English: In a distributed network, network splits will happen. You must choose between Consistency (everyone sees the exact same data at the same second) or Availability (the system keeps working even if some data is slightly delayed).

    DATA DOMAIN CONSISTENCY MODEL WHY — WHAT IS THE BUSINESS IMPACT OF BEING WRONG?
    Message Identity & Content Strong Consistency A message body must never be corrupted, lost, or silently changed. What was sent is what must be stored.
    Conversation Sequence (Ordering) Strong Consistency Sequence numbers must increment strictly (1, 2, 3...) per chat. Gaps or re-orderings break human conversations.
    Group Membership & Permissions Strong Consistency If an admin removes a user from a private group, that user must be blocked from sending or receiving messages immediately.
    Online / Offline Presence Eventual Consistency (Delay OK) If User B went offline 5 seconds ago, but User A still sees "Online" for a few seconds, nobody is harmed.
    Last Seen Timestamp Eventual Consistency A timestamp being 10–20 seconds delayed has zero impact on user experience.
    Typing Indicators Best-Effort (No Guarantees) If a "User is typing..." packet drops due to network congestion, it is completely ignored. Zero business risk.
    Analytics & Usage Metrics Eventual Consistency (Hours delay) Business dashboards and BI reports can process data via batch pipelines hours later.
    PART 23 — SECURITY & PRIVACY

    Protecting User Data (The Security Architecture)

    Messaging platforms are prime targets for state actors, hackers, and spammers. An architect must explain security in practical layers: the transport pipe, the data at rest, and End-to-End Encryption.

    ENCRYPTION IN TRANSIT (TLS 1.3)Every WebSocket frame, HTTP API call, and internal microservice communication is encrypted with TLS 1.3 using modern ciphers. Man-in-the-middle attacks on coffee shop Wi-Fi are impossible.
    END-TO-END ENCRYPTION (E2EE)The Signal Protocol: messages are encrypted on the sender's phone using the recipient's public key. The server only sees random scrambled ciphertext. Even if the server database is completely leaked, zero message content can be read by anyone.
    ENCRYPTION AT RESTAll databases, S3 media buckets, and backup archives are encrypted with AES-256 keys managed in Hardware Security Modules (AWS KMS / Cloud HSM).
    TOKEN AUTHENTICATION (JWT / OPAQUE)Clients use short-lived cryptographic access tokens (15-min expiry) paired with securely stored refresh tokens. If a token is stolen, it can be revoked immediately in the Session Registry.
    RATE LIMITING & ANTI-SPAMToken bucket algorithms at the gateway level: max 20 messages/sec per user; max 5 new chats/min to unknown numbers. Spammers attempting bulk broadcasts are throttled and banned automatically.
    CONTACT PRIVACY (HASH MATCHING)The client does not upload plain-text phone contacts. It uploads SHA-256 salted hashes of phone numbers to match friends without exposing the user's raw address book to the server.
    E2EE IN AN INTERVIEW: KEEP IT ARCHITECTURAL

    Do NOT try to write cryptographic math on the whiteboard. Explain the architectural implications: "Because WhatsApp uses E2EE, the server cannot perform server-side message search, content moderation, or server-side virus scanning. Search must run locally in SQLite on the phone, and moderation relies on client-side user reports where the user voluntarily forwards the decrypted snippet to the trust team."

    PART 24 — FAILURE SCENARIOS

    Sixteen Ways the Messaging Network Fails

    Seniority in a System Design interview is proven when components break. Walk through these 16 realistic production disasters using the 4-part structure: What Happens → User Impact → Immediate Response → Long-Term Prevention.

    FAILURE EVENT WHAT HAPPENS & USER IMPACT IMMEDIATE SYSTEM RESPONSE LONG-TERM PREVENTION
    1 · WebSocket Gateway node crashes 100,000 active sockets drop instantly. Users see "Connecting..." at top of chat. Heartbeat monitor marks node dead in Session Registry. Clients reconnect to healthy gateways using Exponential Backoff with Jitter. N+1 gateway server redundancy; keep gateway processes simple and memory-isolated so they rarely crash.
    2 · Message Database node fails Write attempts for that partition throw database connection errors. NoSQL replica quorum (e.g., write consistency QUORUM) completes writes on surviving replica nodes automatically. Multi-AZ replication factor of 3; automated failover and periodic chaos testing.
    3 · Message Broker (Kafka) partition down Group fan-out or offline push queues stall for that conversation. Kafka partition leader election promotes an in-sync replica (ISR). Producers retry with exponential backoff. Cluster replication factor = 3; minimum in-sync replicas = 2; monitor partition lag.
    4 · User disconnects mid-flight Message was received by gateway, but client dropped before receiving ACK. Message is safely in DB. When user reconnects, client re-sends. Server deduplicates by client_message_id and returns ACK. Idempotent message handling and client outbox queues.
    5 · Flapping network (Subway / Tunnel) Phone rapidly connects, disconnects, reconnects every 3 seconds. Presence debouncing: delay broadcasting "Offline" for 30 seconds. Coalesce reconnection state syncs. Client-side connection hysteresis (wait 5s stable connection before initiating full sync).
    6 · Duplicate message transmission Network retry causes the server to receive the exact same payload twice. Redis deduplication cache (SETNX) detects existing key and discards duplicate payload immediately. Unique constraints in database storage and client-side message ID deduplication.
    7 · Delivered ACK is lost in transit Receiver got the message, but server never received the Delivery ACK. Server periodically re-attempts delivery. Recipient sees existing ID, discards payload, and re-emits Delivery ACK. Client storage treats message_id as primary key with INSERT OR IGNORE.
    8 · Apple APNS / Google FCM outage Offline users do not receive push notification banners on their lock screen. Notification workers buffer alerts in retry queue. Messages remain safe in database; delivered when user opens app. Multi-provider fallback (SMS fallback for critical account alerts); queue alerts with TTL.
    9 · Entire Cloud Region goes dark A major power outage takes down the Virginia data center. Global DNS / Anycast BGP reroutes incoming client traffic to the nearest backup region (e.g., Ohio / Frankfurt). Multi-region active-active deployment with cross-region asynchronous database replication.
    10 · Viral Mega-Group Spike (100k msgs/min) A sports final causes 10,000 members to post simultaneously, creating 100M fan-outs. Dynamic rate-limiting on group (slow mode: max 1 msg per user per 10s); switch from push fan-out to pull-on-read. Dedicated heavy-group queue partitions to prevent viral groups from starving direct 1-to-1 chats.
    11 · Message ordering arrives jumbled Packet delay over mobile cell network causes message #3 to arrive before message #2. Client checks sequence_number. Client buffers message #3, requests missing sequence #2 from server, renders in order. Monotonic conversation sequence numbers stamped by server during database write.
    12 · Media Storage (S3) upload failure User fails to upload image attachment due to S3 API slowdown. Client retries chunked upload using resumable multi-part upload protocol. Text chat continues uninterrupted. Multi-region bucket replication; CDN direct upload fallbacks.
    13 · Redis Session Registry cache failure Redis cluster restarts; gateway mapping table is emptied. Gateways lazily re-register their local connected sockets to Redis during regular heartbeat cycles (within 30s). Redis Cluster with persistent AOF (Append-Only File) and active replica nodes.
    14 · Slow Consumer thread in message queue A bug causes notification workers to process messages 10× slower than normal. Queue depth alarm triggers autoscaler to spin up 50 additional worker containers automatically. Dead-letter queues; poison-pill timeouts; strict latency SLOs on consumer loops.
    15 · New Year's Eve Global Traffic Spike (5× peak) Midnight countdown triggers massive burst of "Happy New Year!" texts and media. Non-essential features (typing indicators, presence updates) are automatically degraded or shed to protect message delivery. Pre-warmed compute capacity; automated load-shedding circuit breakers; capacity planning.
    16 · Malicious client message flood (DDoS) A compromised phone script attempts to send 5,000 messages per second. Gateway token-bucket rate limiter immediately throttles connection (HTTP 429 / socket close); account flagged for review. Device attestation (SafetyNet / App Attest), CAPTCHA challenges, IP reputation filtering.
    PART 25 — ARCHITECTURE TRADE-OFFS

    An architect never says: "Technology X is the best." An architect says: "We chose Option A over Option B because we gain X, and we deliberately accept the sacrifice of Y." Here are the 10 core decisions you must defend in an interview.

    OPTION B — BY CONVERSATION IDAll messages in a chat share the same shard.
