PART 1 · THE FOUNDATION

Reading and Writing Are Different Jobs

Before any technical word, let's agree on one thing: a customer placing an order and a manager reading a report are doing two different things. Treating them the same is where most systems start to break.

1 · What is a read operation?

A read is when someone looks at data. The system gives them information and does not change anything. Examples: a customer browsing products, a manager opening a sales dashboard, a report showing last month's orders. Nothing in the database changes because of a read.

2 · What is a write operation?

A write is when someone changes data. The system must record something new or update something that exists. Examples: a customer placing an order, a clerk updating stock, a payment being marked as paid. After a write, the world is different from before.

3 · Why are they sometimes handled differently?

Because they have different rules:

WRITES MUST BE CORRECTIf an order is placed, the database must record it exactly. You cannot "almost" save an order. You cannot "lose" half of a payment.
READS MUST BE FASTWhen 10,000 users open a dashboard at 9 a.m., each one wants their page in less than a second. The shape of the data for reading is not the same as the shape for writing.
READS CAN BE SLIGHTLY OLDA dashboard from 10 seconds ago is usually fine. An order from 10 seconds ago, saved incorrectly, is never fine.

Think of a restaurant. The waiter taking an order (write) must write it down correctly — no mistakes allowed. The menu on the wall (read) is a display, designed to be easy to read, and does not change when a customer orders. Two different objects, two different jobs.

4 · What problems appear when both use the same design?

  • Slow reads. The database is shaped for saving orders (rows, foreign keys, rules). A dashboard that wants "sales per region per month" has to do heavy work every time someone looks at it.
  • Blocked writes. While a big report is running, the database is busy. New orders may slow down or wait in line.
  • Scaling pain. You cannot add more "read power" without also adding more "write power" — because they share one machine.
  • Risky changes. Adding an index to speed up the dashboard may slow down order creation. One change affects both sides.

5 · What does "separating read and write" actually mean?

It means the system decides: the place I write to and the place I read from may not be the same thing. At its simplest, it may be a different code path inside the same application. At its most advanced, it may be two completely different databases, with data flowing from one to the other.

6 · When is separation useful?

  • When many more people read than write (10 reads for every 1 write is common).
  • When readers and writers have different needs (a dashboard wants a summary; an order wants exact data).
  • When heavy reports slow down the main system.
  • When the system must grow a lot in the future.

7 · When is separation unnecessary?

  • Small systems with a few users and no heavy reports. Separation adds complexity — do not pay that price if the problem is small.
  • Systems where every read must be perfectly up-to-date (for example, a banking balance check). Separation usually means a short delay — not acceptable here.
  • When writes are the bottleneck, not reads. Separation helps reads, not writes.

8 · What extra complexity does separation introduce?

  • Two things to keep in sync. If you have a write database and a read database, data must flow from one to the other. That flow can break, lag, or lose information.
  • Two places to monitor. You watch both sides now — twice the dashboards, twice the alerts.
  • Two places to understand. A new developer must learn both shapes of the data.
  • Eventual consistency. "The dashboard will catch up" is a real phrase — and it means the user may see something old for a moment. You must decide if that is acceptable.
THE ONE SENTENCE TO REMEMBER

Writes must be correct. Reads must be fast. They can be slightly old. If you remember this, every decision in this tutorial follows naturally.

PART 2 · THE EXAMPLE WE WILL USE

The Enterprise Order Management System

Let's work with one example all day. An e-commerce platform that sells products, takes orders, processes payments, ships goods, and reports on everything. The system has:

  • Customers who browse products and place orders.
  • Clerks who update inventory and manage shipping.
  • Managers who read dashboards and reports every morning.
  • Reports that summarize millions of orders.

Some things must be instant and correct (an order, a payment). Other things can be slightly delayed (a dashboard from 10 seconds ago, a report from yesterday).

How it works at first — one path for everything

In the early days, the system is simple. A customer opens the website, the API talks to one database, and the same database answers both the customer's order and the manager's dashboard. There is one source of truth, one shape of data, one set of rules.

FIG. 16.1 · STAGE ONE — ONE PATH FOR EVERYTHING

What goes wrong as the system grows

Day one, this works fine. Year three, problems appear:

Reports slow down ordersEvery morning the manager runs a big sales report. The database works hard for ten minutes. During those ten minutes, a customer's order takes 8 seconds instead of 0.3 seconds. The customer leaves.
Dashboard shape fights order shapeAn order is stored as rows of products, customers, prices. A dashboard wants one row: "sales by region last month". The database must rebuild that answer every time the manager opens the page — slow.
More users, one machineTen thousand managers open their dashboards at 9 a.m. All those reads hit the same database that is also saving orders. The machine cannot do both at full speed.
Changes break both sidesAdding an index to speed up the dashboard slows down order creation. Adding a rule to orders slows down reports. Every improvement has a cost on the other side.

This is where the architect steps in. The question is no longer "does it work?" but "can it keep working when ten times more people use it?"

THE MOMENT TO ACT

The architect does not wait for the system to fail. The moment a report takes more than a few seconds, or a dashboard is sluggish at peak time, that is the signal: reads and writes are starting to fight each other. The fix is to stop treating them as the same job.

PART 3 · THE THREE OPTIONS

Three Ways to Handle Reads and Writes

There are three levels of separation, each more complex but more powerful. None is always right — the choice depends on scale, consistency needs, and team capacity.

Option 1 · One database, one modelHow it works. The application writes and reads from the same tables. No special handling. When to use. Small systems, low traffic, simple requirements. When not. When reports slow down orders, or when reads outnumber writes by a lot.
Option 2 · One database, separate logicHow it works. Same database, but the code that writes and the code that reads are written separately — different classes, different methods, sometimes different teams. When to use. Medium systems, where shape matters but one database is still enough. When not. When the database itself is the bottleneck.
Option 3 · Separate read and write models, syncedHow it works. Two stores. The write side saves data correctly. A process copies (syncs) it to a read side shaped for fast reading — different tables, different database, maybe even different technology. When to use. Large scale, heavy reporting, heavy dashboards. When not. When you cannot accept even a small delay between write and read.
Complexity grows with each stepOption 1 is a beginner's design. Option 2 is the professional middle ground. Option 3 is what large platforms use — at a price. The architect's job is to know when to step up, not to start at step three.

Side-by-side comparison

Advantages Simple. One source of truth. No sync to worry about. Still simple. Can optimize reads without touching writes. One database to maintain. Reads and writes scale independently. Reports cannot slow down orders. Read side can be a different technology (search engine, cache, document store).

THE ARCHITECT'S FIRST QUESTION

Before choosing any option, ask: "How important is it that every read sees the very latest write?" If the answer is "critical" (banking, medical), you stay close to Option 1 or 2. If the answer is "a few seconds of delay is fine" (dashboards, reports, catalogs), Option 3 becomes the natural choice.

THE WORD YOU MAY HEAR

Option 3 is often called CQRS — Command Query Responsibility Segregation. That is a big name for a simple idea: the thing you write to and the thing you read from are different. The name is less important than the thinking behind it.

PART 4 · THE ARCHITECTURE

Two Paths, Two Purposes

Let's draw what Option 3 actually looks like. The system splits into two sides — each optimized for its own job, with data flowing between them.

The write path — correctness first

When a customer places an order, the request travels a short, careful path. The system must save exactly, confirm, and move on. Speed matters, but correctness matters more.

FIG. 16.2 · THE WRITE PATH — CORRECTNESS FIRST

The read path — speed first

When a manager opens a dashboard, the request takes a different path. It is shaped for speed. The data may have been prepared ahead of time, in a form that is easy to read. A short delay — seconds — is usually acceptable.

FIG. 16.3 · THE READ PATH — SPEED FIRST

Why the two sides have different needs

NEED WRITE SIDE READ SIDE
Must be Correct — every order, every payment, exactly right Fast — 10,000 managers opening dashboards at 9 a.m.
Data shape Normalized — many small tables with rules and links Denormalized — one big table shaped for the screen
Can be old? No. An order saved incorrectly is a disaster. Yes, by seconds. A dashboard from 10 seconds ago is fine.
Traffic pattern Steady — orders arrive throughout the day Spiky — managers all open dashboards at the same time
Scaling direction Vertical or careful horizontal (single writer) Horizontal (many read replicas, many caches)

Where caching helps

The read side is where caching pays off. Products rarely change — a cache can serve them instantly. A manager's dashboard from a minute ago is still valid — a cache can show it until a newer version arrives. The write side never caches the source of truth — every order goes to the database before the customer sees confirmation.

CACHE ON THE READ SIDEProducts, user profiles, dashboard summaries, reports. Cache hits make the system feel instant.
NO CACHE ON THE WRITE PATHOrders, payments, inventory updates. Every write hits the database. No shortcuts.
CACHE IS A PERFORMANCE TOOLIt makes reads faster. It does not replace the read model. It sits in front of it.

Where background processing comes in

The "sync" between the write database and the read model is almost always a background job — not part of the customer's order flow. When an order is saved, the write side records it and replies. A background worker picks up the change and copies it to the read model. This is why the dashboard may be a few seconds behind — the copy is not instant.

What happens when read data is slightly behind

This is called eventual consistency — the data will become consistent, but not immediately. In practice, the delay is usually:

  • Milliseconds to seconds with a good design.
  • Acceptable for most reads — a dashboard from 5 seconds ago is not a problem.
  • Not acceptable for some reads — "did my order go through?" must be answered from the write side.

The architect's job is to know which reads can wait and which cannot. A customer's order confirmation reads from the write side. A manager's dashboard reads from the read side. Same system, two different answers.

THE DESIGN AT A GLANCE

Write path: short, strict, correct. Read path: fast, shaped, slightly delayed. Sync: background work, never in the customer's way. Cache: sits in front of the read side, never in front of writes.

PART 5 · THE TWELVE DECISIONS

Questions Every Architect Must Answer

Before choosing an option, the architect works through these twelve questions. Each one reveals something important about the system.

  1. Why not use one database for everything?Because one database must serve two masters. The shape that is best for saving orders (rows, rules, foreign keys) is not the shape that is best for reading a dashboard (summaries, aggregates). When both sides fight for the same machine, both lose.SIMPLE ANSWER: ONE DB IS EASY UNTIL IT BECOMES A BOTTLENECK
  2. Why not always separate reads and writes?Because separation costs complexity. Two stores, sync between them, eventual consistency to explain to users. If the system is small, one database is the right answer. Do not pay for a feature you do not need.SIMPLE ANSWER: COMPLEXITY IS A TAX — PAY IT ONLY WHEN YOU NEED TO
  3. When is separate read processing useful?When reads outnumber writes by a large margin (10:1 or more). When readers need a different data shape than writers. When reports or dashboards must not slow down the transaction side.SIMPLE ANSWER: WHEN READ TRAFFIC IS HEAVY AND DIFFERENT
  4. When is immediate consistency required?When the business cannot tolerate even a brief delay. Banking balances. Stock levels during a sale. Medical records. In these cases, the read must come from the same place as the write — or the user sees the wrong number.SIMPLE ANSWER: WHEN "SLIGHTLY OLD" IS UNACCEPTABLE
  5. When is slightly delayed data acceptable?When the user will not act on the data in the next few seconds. Dashboards. Reports. Catalogs. Recommendations. A product list from 10 seconds ago is the same list the user sees — and is served much faster from the read side.SIMPLE ANSWER: WHEN THE USER WON'T NOTICE
  6. How does reporting affect the main database?Heavy reports scan millions of rows. They consume CPU, memory, and I/O. If they run on the write database, new orders slow down. Reports should run on a read replica or a dedicated analytics store.SIMPLE ANSWER: REPORTS ON THE WRITE DB SLOW EVERYTHING DOWN
  7. How can dashboards be made faster?By pre-building the answers. Instead of asking the database to sum a million rows every time a manager opens the page, a background job prepares the summary and stores it. The dashboard reads the prepared answer in milliseconds.SIMPLE ANSWER: PRE-SHAPE THE DATA BEFORE IT IS READ
  8. How does read-heavy traffic affect architecture?It pushes you toward separation. One database cannot serve a million reads per hour and keep writes fast. The answer is usually: read replicas, a separate read model, and a cache in front.SIMPLE ANSWER: READ-HEAVY = TIME TO SEPARATE
  9. What happens if the read database is unavailable?The dashboards and reports stop working. The write side keeps taking orders. This is an important property: the core business keeps running. A broken dashboard is bad; a broken order system is a disaster.SIMPLE ANSWER: READ-SIDE FAILURES ARE USUALLY TOLERABLE
  10. What happens if synchronization fails?The read side stops receiving updates. Dashboards show old data. This is visible to users (the numbers look stale) but does not lose any orders. The sync must alert when it fails, and retry or skip bad records.SIMPLE ANSWER: THE READ SIDE GETS OLD — BUT THE WRITE SIDE KEEPS WORKING
  11. How do you recover missing read data?By re-running the sync from the write database. Because the write database is the source of truth, the read side can always be rebuilt. This is why separation is safe: the truth is never in the read side.SIMPLE ANSWER: REBUILD FROM THE WRITE DB — IT HOLDS THE TRUTH
  12. How does this design affect cost and maintenance?Two stores cost more than one. Sync infrastructure adds operational work. Monitoring must cover both sides. The team must understand the design. The payoff is scale and performance — if the business needs it. If it does not, the simpler design wins.SIMPLE ANSWER: MORE POWERFUL · MORE EXPENSIVE · WORTH IT ONLY WHEN NEEDED
THE DECISION IN ONE PARAGRAPH

Start with one database. Watch the system. When reports start slowing orders, or dashboards are sluggish at peak, separate the code first (Option 2). If the database itself becomes the bottleneck, separate the stores (Option 3). Each step is a response to a measured problem — not a guess about the future.

PART 6 · EIGHT SCENARIOS

Real Situations, Real Decisions

Eight systems, eight decisions. For each, we ask: should reads and writes be handled the same way, or separated?

Scenario 1 · Banking Transaction System

SITUATIONCustomers transfer money. Every balance check must show the exact current amount. A transfer must be recorded correctly.
DECISIONKeep reads and writes together. Option 1 or 2 at most.
WHYA balance shown to a customer must be the true balance. Eventual consistency is not acceptable — showing 100 when the account has 50 causes real harm.
ARCHITECT THINKSUse one database with strong consistency. Read replicas only for reports (internal, not customer-facing). Never show a stale balance on the customer screen.

Scenario 2 · Social Media Feed

SITUATIONMillions of users scroll a feed. Each user posts a few times a day but reads thousands of times. A feed from 2 seconds ago is fine.
DECISIONSeparate read and write models. Option 3.
WHYRead traffic is enormous (100 reads per 1 write). A post can be pre-built and cached. The feed does not need to be exactly up to date.
ARCHITECT THINKSWrite side stores posts. Read side builds each user's feed in the background. A cache sits in front. Millions of reads do not touch the write database.

Scenario 3 · Product Catalog

SITUATIONCustomers browse millions of products. Products change rarely. Search and filtering must be fast.
DECISIONSeparate read and write stores. Option 3, with a search engine.
WHYProduct data rarely changes — a few seconds of staleness is invisible. A search engine (Elasticsearch, Solr) is far better at product search than a transactional database.
ARCHITECT THINKSWrite side: product database (transactional). Read side: search index, synced in background. Cache in front for popular products.

Scenario 4 · Hospital Appointment System

SITUATIONPatients book appointments. Doctors see their schedule. A double-booked appointment is a real problem.
DECISIONKeep reads and writes together for booking. Option 1 or 2.
WHYWhen two patients try to book the same slot, the system must see the real-time state. A stale read would allow a double booking. Booking is the write path and must read from the same place it writes.
ARCHITECT THINKSBooking: one database, strong consistency. Analytics and reports: can use a read replica. Schedule views for doctors: may use a read model with a short delay, but must reconcile.

Scenario 5 · E-commerce Dashboard

SITUATION10,000 merchants open their sales dashboard every morning. Each dashboard summarizes millions of orders.
DECISIONSeparate read and write models. Option 3.
WHYSumming millions of orders every time a dashboard opens is too slow. The summaries can be pre-built in the background. A dashboard from 30 seconds ago is acceptable.
ARCHITECT THINKSWrite side: orders database. Background job: builds summaries per merchant. Read side: pre-built summaries. Cache: merchant's own dashboard.

Scenario 6 · Inventory System

SITUATIONStock levels must be accurate during a sale. If 100 items are in stock, the system cannot sell 101.
DECISIONKeep reads and writes together for the sale moment. Option 1 or 2.
WHYWhen a customer clicks "buy", the system must check the real stock level. A stale read causes overselling. The inventory write must be strongly consistent.
ARCHITECT THINKSSale path: one database, atomic checks. Catalog views: can use a read model with a small delay. Analytics: read replica.

Scenario 7 · Reporting System

SITUATIONExecutives run heavy reports that scan years of data. Reports take minutes to run.
DECISIONSeparate reporting from the transaction database. Option 3, with a dedicated reporting store.
WHYHeavy reports must never slow down orders. The reporting system can use a technology built for analytics (column-store, data warehouse). Data is a few minutes old — acceptable for reports.
ARCHITECT THINKSWrite side: transactional database. Sync: background ETL. Read side: data warehouse or column-store. Reports run only on the read side.

Scenario 8 · Audit System

SITUATIONEvery action in the system is recorded for compliance. Audits are run occasionally. Audit data is never modified.
DECISIONAppend-only write side; separate read model for search. Option 3.
WHYAudit writes are fast (just append). Audit reads are rare but may scan large ranges. A separate read-optimized store (search engine or document store) makes audits fast without slowing down writes.
ARCHITECT THINKSWrite side: append-only log (immutable). Sync: stream to read side. Read side: indexed for search. Compliance: read side can be rebuilt from the write side if ever questioned.
THE PATTERN

Whenever a read must be exactly current (banking balance, inventory at checkout, appointment availability), keep reads and writes together. Whenever a read can be slightly old (dashboard, feed, report, search), separation is worth the cost. The architect's job is to put each read on the right side.

Fifteen Questions an Architect Must Answer

These are not definitions. They are decisions. For each question, we show four layers: what the interviewer is checking, a simple answer, a strong architect answer, and a common wrong answer.

    STRONG ARCHITECT ANSWEROnly when the scale, consistency, or traffic pattern demands it. A small internal tool stays on one database. A large e-commerce platform with millions of dashboard views may need separation. The decision is driven by numbers, not fashion.

    COMMON WRONG ANSWER"Consistency is lost." It's not lost — it's delayed. And it's a deliberate trade-off, not a failure.
  5. What is the downside of separating reads and writes?TRADE-OFF ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you see the full picture — not just the benefits.
    SIMPLE ANSWERIt's more complex and costs more.
    STRONG ARCHITECT ANSWERThree downsides: (1) Two systems to keep in sync — sync can fail or lag. (2) Two places to monitor and understand. (3) Eventual consistency — some reads will be briefly old. The complexity is worth it only when the problem is big enough.
    COMMON WRONG ANSWER"There's no downside — separation is always better." Every architectural choice has a cost.
  6. How would you explain this architecture to a business stakeholder?COMMUNICATION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you can translate technical decisions into business language.
    SIMPLE ANSWERWe have two systems: one for taking orders, one for showing reports. They talk to each other.
    STRONG ARCHITECT ANSWER"Think of it like a restaurant. The kitchen takes orders (write side) — it must be correct. The menu on the wall shows what's available (read side) — it must be easy to read. They're two different things, and they don't interfere with each other. When the kitchen is busy, the menu doesn't slow down. When many people read the menu, the kitchen doesn't slow down."
    COMMON WRONG ANSWERTechnical jargon: "CQRS with eventual consistency and a message broker." Stakeholders don't care about the mechanism — they care about the outcome.
  7. When is eventual consistency acceptable?DECISION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you can judge when a short delay is safe.
    SIMPLE ANSWERWhen the user won't notice or act on the delay.
    STRONG ARCHITECT ANSWERWhen the read is informational, not actionable in the next few seconds. A dashboard from 10 seconds ago is fine. A report from 5 minutes ago is fine. A product catalog from 30 seconds ago is fine. A banking balance from 10 seconds ago is not fine — the user might act on it.
    COMMON WRONG ANSWER"Eventual consistency is always acceptable." It's not. Banking, inventory at checkout, and appointment availability cannot tolerate it.
  8. How do you decide between Option 1, Option 2, and Option 3?DECISION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you have a clear decision framework.
    SIMPLE ANSWERStart simple, add complexity only when needed.
    STRONG ARCHITECT ANSWEROption 1 (one database, one model) for small systems. Option 2 (one database, separate logic) when reads are heavy but one database is still enough. Option 3 (separate models and stores) when the database itself is the bottleneck or when read traffic is enormous. Each step is a response to a measured problem.
    COMMON WRONG ANSWER"I always use Option 3 because it's the most scalable." That ignores cost, complexity, and team capacity.
  9. What happens if synchronization between the write and read sides fails?FAILURE ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you think about failure modes.
    SIMPLE ANSWERThe read side stops getting updates. Dashboards show old data.
    STRONG ARCHITECT ANSWERThe write side keeps working — orders are still taken. The read side becomes stale. The sync system must alert when it fails. Users may notice that dashboards are "old." The fix is to repair the sync and let it catch up. Because the write database is the source of truth, no data is lost.
    COMMON WRONG ANSWER"The system stops working." It doesn't — the write side keeps working. Only the read side is affected.
  10. How do you handle read-heavy traffic?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you know the standard patterns.
    SIMPLE ANSWERAdd read replicas and a cache.
    STRONG ARCHITECT ANSWERThree layers: (1) Cache in front of the read side — popular items served instantly. (2) Read replicas — multiple copies of the read data. (3) A separate read model shaped for the access pattern — pre-built summaries, search indexes, etc. The choice depends on the traffic pattern and consistency needs.
    COMMON WRONG ANSWER"Add more servers." Horizontal scaling alone doesn't solve the shape problem — you need the right data shape too.
  11. When should you NOT separate reads and writes?DECISION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you know when to keep things simple.
    SIMPLE ANSWERWhen the system is small or when every read must be exactly current.
    STRONG ARCHITECT ANSWERWhen the system has low traffic, when the team is small, or when reads must be strongly consistent (banking balances, inventory at checkout). Separation adds complexity — pay for it only when the problem justifies it.
    COMMON WRONG ANSWER"Never — separation is always good." That ignores cost and complexity.
  12. How does separating reads and writes affect cost?TRADE-OFF ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you consider the business impact of your design.
    SIMPLE ANSWERIt costs more.
    STRONG ARCHITECT ANSWERTwo stores cost more than one. Sync infrastructure adds operational cost. Monitoring must cover both sides. The team needs to understand the design. The payoff is performance and scale — but only if the business needs it. For small systems, the simpler design is cheaper and sufficient.
    COMMON WRONG ANSWER"It costs the same." It doesn't — two systems are always more expensive than one.
  13. How do you test a system with separate read and write models?TESTING ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you think about testing the new failure modes.
    SIMPLE ANSWERTest both sides and the sync between them.
    STRONG ARCHITECT ANSWERThree layers of testing: (1) Write side — does it save correctly? (2) Read side — does it return the right data? (3) Sync — does data flow correctly, and how long does it take? Also test failure modes: what happens when sync is slow or broken?
    COMMON WRONG ANSWER"Test it the same way as a normal system." The sync and eventual consistency are new things to test.
  14. What's the difference between a read replica and a separate read model?THINKING ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the difference between replication and projection.
    SIMPLE ANSWERA replica is a copy of the same data. A read model is a different shape of the data.
    STRONG ARCHITECT ANSWERA read replica is a copy of the write database — same tables, same shape. It helps with read scale but doesn't change the data shape. A read model is a different representation — pre-built summaries, search indexes, denormalized views. A replica helps with scale; a read model helps with speed and shape.
    COMMON WRONG ANSWER"They're the same thing." They're not — a replica is a copy, a read model is a transformation.
  15. How do you monitor a system with separate read and write sides?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you think about operational visibility.
    SIMPLE ANSWERMonitor both sides and the sync between them.
    STRONG ARCHITECT ANSWERThree things to monitor: (1) Write side — is it saving correctly? (2) Read side — is it serving correctly? (3) Sync — is it keeping up? The key metric is sync lag: how far behind the read side is. If lag grows, alert. Also monitor read-side errors, write-side errors, and sync failures.
    COMMON WRONG ANSWER"Monitor the same way as a normal system." The sync is a new failure point that needs its own monitoring.
WHAT THE INTERVIEWER SCORES

Not whether you know the terms. Whether you understand the trade-offs, can explain to non-technical people, know when NOT to use it, and think about failure modes. A strong architect says "it depends" — and then explains what it depends on.

The 500,000-User E-commerce Problem

Here is a real scenario. Read it, think about it, design a solution — then click to see a suggested answer.

THE PROBLEM

An e-commerce company has 500,000 registered users. Order creation is moderate — about 5,000 orders per day. But product browsing, search, dashboards, and reports generate very high read traffic. The transaction database is becoming slow. Dashboards take 8 seconds to load. Reports time out. Product search is sluggish during peak hours.

Your task: Design an improved architecture. Explain:

  • What stays together
  • What should be separated
  • Why
  • How data moves
  • How consistency is handled
  • How failures are handled
  • How the design scales

CLICK TO SEE SUGGESTED ARCHITECTURE

DESIGN YOUR SOLUTION FIRST — THEN CLICK HERE
SUGGESTED ARCHITECTURE: Option 3 — Separate read and write stores.

What stays together: The order creation path. Orders must be exact — the write database handles them. Inventory checks at checkout must be exact — same database.

What separates: Product catalog, search, dashboards, and reports. These are read-heavy and can tolerate a short delay.

Why: The transaction database is the bottleneck. Read traffic is overwhelming it. Separation allows reads to scale independently.

How data moves: Orders are written to the transaction database. A background process syncs order data to a reporting store (data warehouse). Product data is synced to a search index (Elasticsearch). Dashboards are pre-built from the transaction database and cached.

How consistency is handled: Orders and inventory: strongly consistent (write database). Product search: eventually consistent (search index, 10-second delay). Dashboards: eventually consistent (pre-built, 30-second delay). Reports: eventually consistent (data warehouse, 5-minute delay).

How failures are handled: Write side keeps working even if read side fails. Sync failures alert the team. Read side can be rebuilt from the write side. Cache failures fall back to the read model.

How the design scales: Write side: vertical scaling or careful horizontal (single writer). Read side: horizontal scaling (many search nodes, many cache instances, many read replicas). Each side scales independently.
THE KEY INSIGHT

The transaction database was doing two jobs: saving orders (write) and serving searches, dashboards, and reports (read). By separating the read side, each side can be optimized for its own job. The write side stays fast for orders. The read side scales for searches and reports. The system grows without one side hurting the other.

PART 11 · THE CLOSE

Ten Rules for the Technical Architect

If you remember nothing else from today, remember these ten rules. They are simple, practical, and they will guide every decision you make about read vs write design.

Rule 1Writes must be correct. Reads must be fast. Reads can be slightly old. This single sentence drives the whole decision. If you remember nothing else, remember this.
Rule 2Start simple. Option 1 (one database) is the right answer until you have a measured reason to change. Complexity is a tax — pay it only when the problem justifies it.
Rule 3Measure before you separate. Do not separate reads and writes because "it's modern." Separate them because reports slow down orders, or dashboards are sluggish at peak. The numbers tell the story.
Rule 4Know which reads cannot wait. Banking balances, inventory at checkout, appointment availability — these must be exact. They live on the write side, always. A stale read here causes real harm.
Rule 5Know which reads can wait. Dashboards, reports, catalogs, feeds — these can be seconds or minutes old. They are candidates for the read side. Eventual consistency is a feature, not a bug, here.
Rule 6Reports never run on the write database. Heavy reports slow down orders. Reports belong on a read replica or a dedicated reporting store. This is non-negotiable at scale.
Rule 7The write side is the source of truth. If the read side breaks, it can be rebuilt from the write side. If the write side breaks, the business stops. Protect the write side at all costs.
Rule 8Sync is background work. Never put sync in the customer's order flow. When an order is saved, reply to the customer. Then, in the background, sync to the read side. This is why eventual consistency works.
Rule 9Monitor the sync. Sync lag is the key metric. If the read side is 30 seconds behind, that's fine. If it's 30 minutes behind, alert. Monitor sync health like you monitor the database itself.
Rule 10Explain it simply. The restaurant analogy works: the kitchen (write) must be correct, the menu (read) must be easy to read. They are two different jobs. Stakeholders understand this. Use it.

The one-line interview answer

"I separate reads and writes when the read pattern is fundamentally different from the write pattern — when reads are heavy, when they need a different shape, and when a short delay is acceptable. I keep them together when every read must be exactly current, or when the system is small enough that one database serves both well."

Memorize that sentence. It covers the whole day. In an interview, say it — then fill in the details with the specifics of the system you are discussing.

DAY 16 — CLOSE

The Architect Who Decides

Five rules from today. If you remember nothing else, these carry you through any read vs write conversation.

01

Correctness before speed.

A customer's order must be exact. A dashboard can wait. If you confuse these two, you build a system that is fast at the wrong things and broken at the right things.

02

Measure before you separate.

Do not separate reads and writes because "that's what modern systems do." Separate them because the numbers say the single database is the bottleneck. The decision comes from data, not from fashion.

03

The write side is the source of truth.

If the read side breaks, you can rebuild it. If the write side breaks, the business stops. Protect the write side. Every decision flows from this.

04

Eventual consistency is a trade-off, not a failure.

It is a deliberate choice: the read side may be slightly behind, but the system scales. The architect's job is to decide which reads can tolerate this and which cannot.

05

Explain it to a stakeholder.

If you cannot explain the architecture in a restaurant analogy, you do not understand it. "The kitchen takes orders, the menu shows what's available" — stakeholders understand this. Technical jargon does not help them.

A technical architect is not the person who knows the most patterns. A technical architect is the person who knows when to use which pattern — and can explain why to someone who has never written a line of code. Read vs write design is the perfect example: the choice is simple, the reasoning is deep, and the explanation must be clear.
