PART 1 — START LIKE AN ARCHITECT

Why You Should Not Start Drawing Microservices

Most candidates lose the interview in the first five minutes. They hear "design an Uber-like system" and immediately start naming services: Auth Service, Trip Service, Payment Service. This is the wrong move. Architecture is the expensive-to-change decisions — not the box names.

THE TRAP

If you start with boxes, you have already assumed: microservices (instead of one modular app), separate databases (instead of one), and network calls (instead of function calls). Each assumption costs you later. Senior architects question the assumptions first.

Functional Requirements (what the system must do)

These are the features. The interview expects you to enumerate them and prioritize. If you skip one, the interviewer will catch it.

  • User registration — rider and driver signup, identity check, document upload for drivers.
  • Login & authentication — phone, email, social, OTP.
  • Driver registration & onboarding — background checks, vehicle documents, approval flow.
  • Driver availability — driver going online / offline, accepting or rejecting trips.
  • Driver location updates — frequent GPS pings to the backend.
  • Search for nearby drivers — given a rider location, who is close?
  • Ride request — rider asks for a car to a destination.
  • Driver matching — pick the best driver for the request.
  • Ride acceptance — driver confirms the request.
  • Trip start — driver begins the trip, meter starts.
  • Trip completion — driver ends the trip at destination.
  • Fare calculation — base + distance + time + surge + tax.
  • Payment — charge the rider, pay the driver.
  • Notifications — push, SMS, email at every key moment.
  • Ride history & receipts — past trips, invoices, support.
  • Ratings & reviews — both sides rate each other.
  • Support & safety — emergency button, trip sharing, dispute resolution.

Non-Functional Requirements (how the system must behave)

These decide the architecture more than features do. Every one of them changes a design choice.

SCALEHow many riders, drivers, rides? Affects every capacity decision.
CONCURRENCYHow many rides are happening right now? Affects matching, payments.
LOCATION FREQUENCYHow many GPS pings per second? Affects the location pipeline.
RESPONSE TIMEHow fast must "find a driver" be? Affects matching and caching.
AVAILABILITY99.9% or 99.99%? Affects redundancy, regions, and cost.
SCALABILITYCan we add 10× capacity without rewriting? Affects partitioning and statelessness.
SECURITYWho can see location? Who can charge? Affects auth, audit, encryption.
ACCURACYHow exact must location be? How strict must fare be? Affects data quality and consistency.
RELIABILITYWhat happens when one service dies? Affects retries, fallbacks, queues.
PRIVACYGDPR-style rules on location history? Affects retention policies and region isolation.
WHY EACH MATTERS

If you say "the system must be fast" but cannot say how fast in milliseconds, your design is a wish. Numbers, or it didn't happen. This is the single most common mistake in system design interviews.

PART 2 — DEFINE REALISTIC SCALE

Turning "Millions" into Real Numbers

Interviewers expect you to do rough back-of-the-envelope math. You do not need precision. You need the right order of magnitude. Here are the assumptions and the simple arithmetic.

ASSUMPTION NUMBER REASONING
Total registered riders 50,000,000 Total signups in the platform's history.
Total registered drivers 5,000,000 About 10% the size of the rider base.
Daily active riders (DAU) 10,000,000 20% of registered come back each day.
Active drivers (peak hour) 1,000,000 20% of total drivers are working in the busiest hour.
Concurrent rides at peak ~500,000 About half the active drivers are mid-trip at the same time.
Daily ride requests ~30,000,000 3 trips per active rider per day on average.
Peak hour requests ~6,000,000 About 20% of daily traffic happens in the busiest hour.
Peak requests per second ~1,700 6,000,000 ÷ 3,600 seconds = ~1,700 RPS.
Location updates per driver ~1 / 3 seconds Background GPS pings while online.
Peak location updates per second ~333,000 1,000,000 drivers × ⅓ update = 333k pings every second.

What the numbers tell you

  • API traffic (~2,000 RPS peak) is high but ordinary — a few hundred application servers handle it.
  • Location traffic (~333,000 pings/sec) is 100× bigger — it cannot use the same pipeline. It needs a different storage, a different queue, and different scaling rules.
  • Storage for location is huge but mostly short-lived — keep it fast, throw it away later.
  • Network bandwidth for location is the single biggest cost. A single ping is small, but millions per second add up.
INTERVIEW TIP

Always show your math. Say "6 million requests in the peak hour, divided by 3,600 seconds, gives me about 1,700 requests per second, so I plan for 2× that to be safe." Interviewers love seeing the numbers, even if the assumptions are off by 20%.

PART 3 — CORE BUSINESS AREAS

What Parts Should the System Have?

A "business area" is one well-defined job the system does. Do not start with 12 of them. Start with the fewest that could work, then split as you grow. Here is a mature set, and the rule for when each becomes its own service.

AREA MAIN JOB KEY DATA NOT ITS JOB DEPENDS ON
Authentication Verify who the user is. User ID, hashed password, OTP, tokens. Storing user profiles. Identity provider (in-house or external).
Rider Manage rider profile, history, payment methods. Rider profile, saved cards, addresses. Real-time location of rider. Auth, Payment.
Driver Manage driver profile, onboarding, vehicle, documents. Driver profile, vehicle info, ratings. Live location (that's location service). Auth, Document storage.
Driver Availability Online/offline, ready/not-ready status. Driver ID, status, current trip ID. GPS coordinates. Location, Ride.
Location Ingest, store, query driver positions in real time. Driver ID, lat/long, timestamp, status. Trip logic, payment. High-throughput in-memory store.
Ride Manage a ride from request to completion. Ride ID, rider ID, driver ID, state, route. How drivers are matched (that's matching). Matching, Location, Trip, Pricing.
Matching Find the best driver for a request. Search index, request parameters. Storing rides. Location, Driver Availability.
Trip The actual journey — start, route, end, distance, time. Trip ID, polyline, distance, duration. Pricing logic. Ride, Location.
Pricing Compute fare, apply surge, apply discounts. Tariff tables, surge rules, promo codes. Processing the charge. Trip data.
Payment Charge the rider, pay the driver, refund if needed. Payment ID, status, amount, references. Computing the fare. Pricing, external payment provider.
Notification Send push, SMS, email at the right moment. User ID, channel, template, status. Computing the message. Ride events.
Rating Collect and process ratings after a trip. Rating ID, score, comment, role. Trip logic. Trip data.
Reporting Aggregates, dashboards, exports. Daily rides, revenue, driver hours. Real-time queries. Data warehouse.

Which areas can start together?

At small scale, you can have one modular app with all these as code modules inside one process. As you grow, the areas most likely to break first become their own services:

  • Location — because of volume, not logic. It will need its own scaling, its own storage, and its own network.
  • Matching — because it is on the hot path of every ride. Latency matters here.
  • Payment — because of security, audit, and external dependencies.
  • Notification — because it can absorb spikes and never block the user.
THE RULE

Combine areas that change together. Split areas that scale differently or fail differently. Location and payment fail for different reasons and scale at different rates — they should be separated early.

PART 4 — HIGH-LEVEL ARCHITECTURE

A Simple Picture Before a Fancy One

A good architecture diagram has only what the picture needs. Boxes, arrows, and one label per box. No clever names, no clustering for the sake of clustering.

What each major component is for

API LAYEROne front door. Auth, rate limiting, routing, version handling. Keeps every other service clean.
LOCATIONThe fastest-changing data. Lives in memory, not the main database. Designed for hundreds of thousands of writes per second.
MATCHINGThe brain of the ride. Sits on the hot path. Must answer in under a second.
RIDEThe state machine. From "requested" to "completed". Holds the truth about who, what, when.
REAL-TIMEWebSocket gateway that pushes updates to rider and driver apps. Without it, polling kills your servers.
MESSAGE BROKERAsync glue between services. Notifications, receipts, analytics, fraud checks.
CACHEHot reads: session tokens, frequently used driver profiles, surge configuration, city rules.
SQL DBThe system of record. Riders, drivers, rides, payments, trips. ACID matters here.
LOCATION DBShort-term store for driver positions and trip breadcrumbs. Throwaway after the trip ends.
NOTIFICATIONWorkers that send push, SMS, email. Slow and batch-friendly. Should never block the user.
DESIGN RULE

Don't add a component because it is popular. Add it because removing it would break something. Every box must justify its existence.

PART 5 — RIDE BOOKING FLOW

The Whole Flow, Step by Step

This is the moment a rider taps "Confirm". Follow the steps. Notice which ones must be instant and which can wait.

  1. Rider opens the app, requests a ridePickup, drop, payment method. Frontend sends to the API. Synchronous (sync) — the user is waiting.SYNC
  2. API validates, asks matching for nearby driversMatching calls Location for drivers inside a radius. Sync — the rider is staring at a spinner.SYNC
  3. Matching picks a driver and sends the requestPush to the driver's app via the real-time channel. The driver has 10–15 seconds to accept.REAL-TIME
  4. Driver accepts (or rejects, or no response)If accepted, ride state moves to "DriverAssigned". Push to rider. If timeout, retry the next driver.REAL-TIME
  5. Driver arrives at pickupState moves to "DriverArrived". Rider gets a notification.REAL-TIME + EVENT
  6. Trip startsDriver taps "Start trip". State moves to "TripStarted". Meter and pricing engine are now live.SYNC
  7. Driver and rider moveGPS pings update Location. Real-time channel shows the car moving on the map.REAL-TIME
  8. Trip endsDriver taps "End trip". Fare is calculated. State moves to "Completed".SYNC
  9. Payment is attemptedCharge the saved card. Receipt is generated and queued. Driver payout is recorded.SYNC CORE + ASYNC TAIL
  10. Ride is closed, ratings and history updatedReceipt, ratings request, support records. All happen in the background.ASYNC
THE RULE OF THREE

Three categories of work. Sync — the user is waiting, you must answer now. Real-time push — the user needs to know without refreshing. Async — nobody is waiting; process when you can, but never lose the work. The architecture must let each category scale and fail on its own.

PART 6 — DRIVER LOCATION TRACKING

The Hardest Data in the System

A driver on the road generates a GPS ping every few seconds. Multiply that by one million active drivers and you have hundreds of thousands of pings every second. That data cannot live in the same database as your riders and payments. It is too much, it changes too fast, and it is mostly throwaway.

Why location needs a different storage approach

  • Volume — ~333,000 writes per second at peak. A normal transactional database can do a few thousand writes per second per node.
  • Half-life — a driver position is interesting for a few minutes (while a rider looks for a car). After the trip, it is history.
  • Read pattern — "who is near this point right now?" — a geographic query, not a primary key lookup.
  • Failure tolerance — if a ping is lost, the next one comes in three seconds. A dropped location update is not a disaster.

A practical approach

  • Fast in-memory store for the current position of every online driver (Redis-style).
  • Geo index that lets you ask "who is inside this rectangle?" in milliseconds.
  • Short-lived persistence for the trip itself — breadcrumbs of where the car went.
  • Long-term storage only for the final trip polyline, kept for receipts and disputes.
DO NOT

Do not write 333,000 pings per second to your main transactional database. Do not index geospatial columns on the same table where you store payments. Do not keep raw GPS pings for years — the privacy risk alone is enough to lose you a country.

INTERVIEW TIP

When the interviewer asks "how do you handle millions of location updates?", the strong answer is: "they never touch the main database. They go to a dedicated, in-memory, geo-aware store with a short TTL, and only the trip's final polyline is written to long-term storage."

PART 7 — FINDING NEARBY DRIVERS

"Who Is Close to This Rider?"

The matching service asks this question thousands of times per second. Speed matters more than perfect accuracy. The system should answer in under 200ms, ideally under 100ms.

The core ideas

  • Geo indexing — drivers are placed in a grid or a quadtree, so the system only looks at the cells inside the search radius, not every driver in the city.
  • Grid or area-based grouping — divide the city into small cells (e.g., 500m squares). Drivers belong to one cell; queries only scan a few nearby cells.
  • In-memory data — driver positions live in memory; disk seeks would kill latency.
  • Update cheaply — when a driver moves, just update their position; if they cross a cell boundary, move them to the new cell.
  • Filter unavailable drivers — never include drivers on a trip, drivers who went offline, or drivers in the wrong vehicle category.

The four trade-offs

GOAL WHAT IT COSTS WHAT YOU GIVE UP
More accuracy More cells to scan, more index updates. Slower, more CPU, more memory.
More speed Coarser cells, fewer scans. Some faraway drivers included, some close ones missed.
Lower cost Smaller machines, fewer replicas. Lower peak capacity, slower failover.
Lower complexity No exotic data structures. Worse performance at scale.
THE TRADE

You do not need to find the single closest driver. You need to find any one of the closest drivers in under a second. Once you accept that, the algorithm gets dramatically simpler — and that is the architect's win.

PART 8 — DRIVER MATCHING

How the System Picks One Driver

Matching is a ranking problem, but the architect's job is to design the flow, not the algorithm. Here is the flow and the few rules that matter.

The decision factors (in order of importance)

  • Distance / ETA — closer is better, but "estimated time of arrival" usually beats raw distance (a driver 1 km away on a highway beats one 500 m away in traffic).
  • Driver availability — must be online, on shift, and not already on a trip.
  • Vehicle type — must match what the rider asked for (sedan, SUV, premium).
  • Driver status — not on break, not flagged by safety system.
  • Reliability score — cancellation rate, on-time rate, ratings.
  • Business rules — driver quotas, new-driver boost, surge-zone priority.

The flow

  1. Matching starts when the ride service creates a requestIt calls the matching service with pickup point, vehicle type, and rider preferences.
  2. Matching gets a shortlist of nearby driversFrom the location service, filtered by availability and vehicle type.
  3. It ranks them and sends the request to the top onePush notification through the real-time channel. Driver has 10–15 seconds.
  4. If the driver does not respond, try the next oneRepeat up to a small number (e.g., 3–5 drivers). After that, tell the rider "no cars nearby".
  5. If the driver accepts, lock the rideSet ride state to "DriverAssigned" and update driver availability to "on trip". See Part 9 for the lock.
WHAT IF TWO DRIVERS ACCEPT AT THE SAME TIME?

The system must allow only one winner. This is the double-booking problem, covered in Part 9. The architect's answer is: the first accepted response wins, the system must be fast enough to reject the loser gracefully, and the loser must be told "ride already taken".

PART 9 — PREVENTING DOUBLE BOOKING

One Driver Cannot Be in Two Rides

Imagine two riders requesting a ride in the same second. The same driver is a great match for both. Both requests reach the system. Only one of them can win. This is the most common failure in ride-booking systems that don't have proper locks.

The defense layers

  • Driver state flag — when a ride is offered, mark the driver as "reserved" for that ride for a short window (10–15 seconds). Other matching calls will skip reserved drivers.
  • Atomic state change — the moment a driver accepts, the system performs a single conditional update: "set driver status to on-trip only if it is currently free". The database ensures only one update succeeds.
  • Database constraints — a unique active-ride-per-driver constraint, or a check that rejects updates to a driver who is already on a trip.
  • Short-lived reservation — use a short-lived lock that auto-expires if the driver never accepts, so a stuck request doesn't keep a driver frozen forever.
  • Idempotent accept endpoint — the "accept ride" call carries a ride ID. The server accepts only the first one. The second arrival is acknowledged as "ride already taken".

Trade-offs

PROS OF LOCKINGStrict correctness. No double-booking ever. Predictable behavior under load.
CONS OF LOCKINGLock contention can slow matching. Locks must expire or they leak. A buggy lock can freeze a driver.
PROS OF EVENTUAL CONSISTENCYFaster, no contention. Resolves the conflict only at accept time.
CONS OF EVENTUAL CONSISTENCYCan let the same driver be offered twice. Needs a strong "winner" logic at the moment of accept.
RECOMMENDED

Use a short-lived reservation when a request is sent, and a conditional atomic update at accept time as the final word. Two layers. If the reservation fails, no big deal — the accept-time check will catch it. If the accept-time check is the only line of defense, you have no early filter and matching wastes work.

PART 10 — REAL-TIME COMMUNICATION

Pushing Updates to Rider and Driver

The driver is moving. The rider is watching. Both apps need updates in real time without refreshing. This is the part that decides whether the system feels alive or feels broken.

The three options

OPTION HOW IT WORKS SPEED SERVER LOAD RELIABILITY
Polling App asks "anything new?" every few seconds. Slow (3–10s lag) High (many wasted calls) Simple
Long polling App asks, server holds the connection until something changes. Fast High (many held connections) Reasonable
WebSockets Open, persistent connection both ways. Instant Lower per update Best, with reconnect logic
RECOMMENDED

WebSockets (or a managed equivalent) for live driver location, ride status, and chat. Always have reconnect logic and an offline queue — phones lose network in tunnels and elevators. The system must catch up when the device reconnects.

What the real-time channel carries

  • Rider → server — new ride request, cancellation, chat message, payment confirmation.
  • Server → rider — driver assigned, driver approaching, driver arrived, trip started, driver location updates, trip completed.
  • Driver → server — accept, reject, arrived, start trip, end trip, location pings.
  • Server → driver — new ride request, ride cancelled, surge updates.
PART 11 — RIDE STATE MANAGEMENT

The State Machine That Keeps Everything Honest

A ride is a journey through well-defined states. Clear states prevent illegal moves like "completed ride goes back to searching". The state machine is the contract between every service that touches a ride.

Why this matters

  • Prevents illegal transitions — a completed ride cannot go back to searching.
  • Enables audit — every state change is a recorded event.
  • Makes distributed services safe — every service asks "what is the current state?" before acting.
  • Defines recovery paths — if a driver disconnects mid-trip, the system knows the ride is still in "TripStarted" and waits for the next event.
INTERVIEW TRAP

If your design has no explicit states, you are letting the system invent them. That is how you end up with two services both thinking the ride is in different states, and the rider sees a driver who never arrives. State is the truth. Name it.

PART 12 — PRICING

How the Fare Is Built

Pricing is business rules + math. The architect's job is to keep the rules separate from the trip processing, so that marketing can change promotions without breaking the trip flow.

The components of a fare

  • Base fare — the flat fee to start a trip.
  • Distance — per-kilometer charge based on the actual route.
  • Time — per-minute charge for slow traffic or waiting.
  • Surge — a multiplier when demand is high.
  • Taxes & fees — city, country, or platform fees.
  • Discounts & promos — codes, loyalty credits, partner discounts.

When the fare is calculated

  • Estimate — when the rider requests, show a price range. Use historical data and distance.
  • Final fare — at trip end, recompute exactly using the actual distance and time. The estimate can be off; the final cannot.
WHY PRICING IS SEPARATE

Promotions change weekly. Surge changes every few minutes. Tax rules change by city. The pricing service isolates all of this from the ride flow. If marketing can change a promo without a code deploy, your pricing is in the right place.

PART 13 — PAYMENT

The One Flow You Must Get Right

Payment is where the system touches real money. Errors here are visible, expensive, and embarrassing. The architect must design for idempotency, retries, and failure.

The flow

  1. Ride completesPricing service produces the final fare with a unique fare ID.
  2. Payment service is calledWith ride ID, fare ID, payment method ID. This call is idempotent — calling it twice has the same effect as calling it once.
  3. External provider is calledThe provider charges the card and returns success or failure.
  4. If success, mark ride as paid, queue receiptThe rider gets a push and an email. Database record updated.
  5. If failure, retry with backoffTry a few more times. If still failing, ask the rider for a new payment method or support contact.
  6. If timeout, do not retry blindlyAsk the provider for the charge status. Otherwise you may double-charge.

Idempotency, in simple English

"Idempotent" means: doing the same thing twice has the same result as doing it once. Imagine your payment service sends a charge to the bank, but the response is lost in the network. The service retries. Without idempotency, the rider is charged twice. With idempotency, the system uses a unique charge ID and the bank recognizes it as the same operation.

THE THREE RULES OF PAYMENT

1. Every charge has a unique ID. 2. Retries send the same ID. 3. The provider answers the same way for the same ID. This is the difference between a system that scales and a system that gets headlines.

PART 14 — MESSAGING AND BACKGROUND WORK

What Should Never Block the User

A ride request is on the hot path. The user is waiting. Anything that does not have to happen right now should be queued and processed in the background. The system absorbs spikes better, and the user gets a faster response.

Candidates for async processing

  • Notifications — push, SMS, email. The user does not need them instantly; 5–10 seconds is fine.
  • Receipts — generate a PDF after payment and email it later.
  • Analytics events — every ride produces dozens of events. Stream them to a warehouse.
  • Driver statistics — accept rate, cancellation rate, online hours. Computed nightly.
  • Rating processing — recalculate driver scores after each rating.
  • Reporting — daily, weekly, monthly reports.
  • Fraud checks — analyze patterns out-of-band, then flag if needed.
  • Driver payouts — compute weekly payouts, then transfer.
RULE OF THUMB

If the user is staring at a spinner while this work happens, it is in the wrong place. Move it to a queue. The only work that stays sync is the work the user is waiting for.

PART 15 — DATA STORAGE

One Database Is Never Right for Everything

Different data has different shape, different access pattern, and different life span. Putting everything in one place either starves the slow queries or kills the fast ones.

MAIN TRANSACTIONAL DBRiders, drivers, rides, trips, payments. ACID matters. Schema is fixed. Strong relationships. Use a relational database.
FAST TEMPORARY STOREDriver positions, availability flags, short matching locks. In-memory. TTL-based. Throwaway data.
LONG-TERM STORAGETrip history, finalized polylines, audit logs. Cheap storage, batch analytics, regulated retention.
SEARCH INDEXCity, place, address search. Built for fuzzy text and geo. Not the source of truth — a copy optimized for read.

Why one database hurts

  • Location writes are 100× more frequent than ride writes. Putting them in the same database overwhelms it.
  • Long-running analytics queries lock tables and slow down live traffic.
  • Regulated data may need to be in a specific region. Mixing it with global data prevents that.
  • Different backup needs — you back up transactions every minute, GPS breadcrumbs every hour, and analytics nightly.
PART 16 — CACHING

When Cache Helps and When It Lies

Cache is the fastest query. It is also the easiest place to serve stale, wrong, or malicious data. Treat it as a hint, not a source of truth.

What to cache

  • Driver availability summary per cell (number of free drivers per area).
  • Frequently accessed rider profile (name, default payment method).
  • Pricing configuration per city (tariff, surge rules).
  • City configuration (time zone, currency, support contacts).
  • Popular pickup places (airport terminal, train station — searched 1000× a minute).

What NOT to cache

  • Live driver positions — too frequent, too short-lived; the dedicated location store handles this.
  • Active ride state — must be authoritative; caching risks showing wrong state to the user.
  • Payment status — must come from the payment system, period.

Three rules for any cache

  • Have a TTL — every cache entry expires. No exceptions.
  • Have a fallback — when the cache is down, the system still works (slower, but correct).
  • Have invalidation — when the source data changes, push an invalidation or update.
PART 17 — SCALING

Why Location Traffic Scales Differently From API Traffic

A normal API call (login, request ride) is request-response: one request, one response, then the connection is free. A location ping is fire-and-forget: the driver app sends pings continuously whether or not anyone is asking. This is why one set of rules does not work for both.

How each layer scales

  • API — stateless, scales horizontally. Add more servers behind a load balancer.
  • Location processing — needs a separate ingestion path (e.g., a message queue + workers) that absorbs bursts and writes to the in-memory store.
  • Matching — stateless from the outside, but pulls heavily from the location store. Scale by partitioning cities.
  • Ride service — scale by region and by city. One city's traffic is independent of another's.
  • Database — primary for writes, read replicas for reads, sharding for very large datasets.
  • Real-time gateway — scale by connection count, not by request rate. Each open WebSocket uses memory.
  • Notifications — workers, queues, and a third-party delivery service.
THE INSIGHT

Location traffic and API traffic look similar in dashboards but are fundamentally different shapes. One is request-response, the other is streaming. The architecture must reflect that, or the same infrastructure will be optimal for neither.

PART 18 — GEOGRAPHIC SCALING

From One City to Many Countries

Geographic scaling is not just "add more servers". It changes latency, availability, and regulation. Each country has its own rules about data residency (where data must live) and privacy.

The growth path

  1. One city, one data centerSimple. All in one place. Works until 100k+ users.
  2. Multiple cities, one regionPartition the database by city. Location service partitioned by city. Each city's traffic is independent.
  3. Multiple regionsReplicate read traffic. Pin writes to the home region for each city. Plan for cross-region outages.
  4. Multiple countriesRegion-per-country for data residency. Local payment providers. Local language and currency. Local support.

The trade-off

CENTRALIZEDEasy to operate, one source of truth, one place to deploy. But: high latency for far users, single regional outage takes down everyone, hard to satisfy data residency.
REGIONALLow latency, isolated failures, meets data residency. But: hard to keep consistent, more complex ops, more expensive.
RECOMMENDED

Start centralized. As you grow into a second country, split by region for that country alone. Don't pre-split for countries you don't have. Complexity is earned.

PART 19 — FAILURE SCENARIOS

What Will Break, and What You Will Do About It

The interviewer is not trying to trick you. They want to know that you have thought about the system on a bad day. Walk the failure path before you walk the happy path.

SCENARIO WHAT HAPPENS USER IMPACT IMMEDIATE RESPONSE LONG-TERM FIX
Location service down Driver pings not stored. Riders see no cars nearby. Show "looking for drivers", widen search radius, retry. Redundant in-memory store, partitioned by city.
Matching service down No new ride requests get assigned. Riders stuck on "searching". Queue requests; serve them when matching is back. Standby matching instance, automatic failover.
Payment provider down Charges fail or time out. Riders cannot complete payment. Allow cash or "pay later", retry in background. Backup provider, circuit breaker, retry queue.
Database down No reads, no writes. App effectively dead. Failover to replica, read-only mode, queue writes. Multi-region replication, tested failover runbook.
Message broker down Async work stuck in producers. No notifications, no analytics, no reports. Buffer locally, replay when broker is back. Redundant broker cluster, monitoring on broker lag.
WebSocket gateway down Apps cannot receive real-time updates. Users see stale screens. Apps reconnect, fall back to polling for short period. Multiple gateway regions, sticky session fallback.
Driver loses network Driver app goes offline. Active trip may stall. Rider sees "driver connection lost", safety check triggered. Reconnect logic, heartbeat, on-trip timeout.
Rider loses network Rider app goes offline. Cannot see updates. Driver sees "rider disconnected", trip continues; reconnect syncs state. Idempotent state replay on reconnect.
Driver disappears after assignment Driver does not arrive or accept. Rider waits forever. Timeout the assignment, try the next driver, refund the rider. Strict assignment TTL, automatic re-matching.
Duplicate ride request Rider double-taps "request". Two rides created. Idempotency key per request; second one is rejected. Idempotency layer in the API.
Duplicate payment Payment service retries after timeout. Rider charged twice. Use unique charge ID; provider is idempotent. Idempotency contract with payment provider.
Two drivers accept Race condition on accept. One driver gets a ghost ride. First accept wins; second is told "ride taken". Atomic state transition, short-lived reservation.
No driver accepts Search times out. Rider sees "no cars nearby". Suggest waiting, change pickup, increase fare (surge). Better search radius, supply incentives, driver re-engagement.
Regional outage An entire cloud region is down. All users in that region offline. Failover to another region, restore from backups. Multi-region active-passive, tested recovery.
Peak demand (concert, holiday) Request rate 10× normal. Slow or failed requests. Auto-scale, shed low-priority work, queue notifications. Capacity planning, surge pricing, queue-based load shedding.
Surge miscalculation Price spike or wrong surge. Riders overcharged or drivers underpaid. Cap surge, allow overrides, fast refund path. Surge rules review, anomaly detection, refund automation.
PART 20 — CONSISTENCY AND ACCURACY

Where the System Must Be Right Now, and Where It Can Wait

Not everything needs the same level of correctness. The architect decides per use case, and pays only for what is needed.

Needs strong correctness (right now)

  • Driver assignment — one driver per ride, never two.
  • Ride state — the user must see the right state.
  • Payment — money is real. Mistakes are public.
  • Final fare — the rider must be charged exactly what the rules say.

Can tolerate temporary delay (eventual is fine)

  • Analytics counts — off by a few percent is fine for a dashboard.
  • Reports — a few minutes late is normal.
  • Some notifications — arriving 30 seconds later is fine.
  • Driver statistics — recomputed nightly is acceptable.
THE DECISION

Strong consistency costs money, latency, and complexity. Eventual consistency is cheaper and faster. Choose by business impact: if the user is staring at the screen waiting, it must be strong. If the user is not, eventual is fine.

PART 21 — SECURITY

Practical Security, Not Theory

The architect's job is to make the system hard to misuse, not to install every possible control. Practical security is the small set of decisions that eliminate the most common risks.

  • Rider and driver authentication — strong password, phone OTP, token-based sessions (short-lived access + long-lived refresh).
  • Authorization — a driver cannot read another driver's trips. A rider cannot read another rider's payment. Always check ownership.
  • Location privacy — driver location is shared with the matched rider only during the trip. Never expose raw positions to the public.
  • Secure communication — TLS everywhere. Internal calls are signed.
  • Payment protection — never store full card numbers. Use a tokenized provider. PCI-DSS scope is the provider's, not yours.
  • API protection — rate limit, throttling, anomaly detection. Block credential stuffing.
  • Audit logging — every state change, every payment, every admin action is logged and tamper-evident.
  • Trip safety — emergency button, trip sharing, continuous driver check-in.

PART 23 — COST THINKING

Where the Money Goes

Senior architects think about cost as part of the design, not after. A correct design that breaks the bank is a failed design.

The big cost areas

  • Server processing — application servers scale with request rate.
  • Location processing — the largest single cost. 333k pings/sec is not free.
  • Network traffic — moving GPS data to the cloud costs real money.
  • Real-time connections — each open WebSocket uses memory and bandwidth.
  • Database — storage, IOPS, replicas, backups.
  • Storage — long-term trip history, audit logs.
  • Monitoring — metrics, logs, traces add up at scale.
  • External services — payment, SMS, maps, push notifications.

Eight ways to control cost

  1. Throttle location pings when not neededSlow down pings when the driver is idle for minutes. Speed them up only when a rider is being matched or during a trip.
  2. Use server-side batchingCombine multiple pings into a single network call where possible.
  3. Sample analytics eventsYou don't need every GPS ping in analytics. Sample 1 in 10.
  4. Pick the right tier of databaseHot data on fast disks, cold data on cheap storage.
  5. Right-size real-time connectionsDisconnect idle WebSockets. Reconnect on demand.
  6. Negotiate provider feesPayment and SMS fees add up. Volume is leverage.
  7. Cache aggressivelyEvery cached read is a database read you don't pay for.
  8. Delete what you don't needGPS breadcrumbs, debug logs, old sessions. Set retention policies.

FINAL — 15 THINGS TO REMEMBER

The Day 23 Cheat Sheet

Memorize these. They are the difference between a developer answer and an architect answer.

01

Ask before you draw.

Five clarifying questions before the first box. Always.

02

Show the math.

333,000 location pings per second, 2,000 ride requests per second, 500,000 concurrent rides. These are your design constraints.

03

Separate fast, business, and background data.

Three storage tiers. In-memory for location, SQL for transactions, warehouse for analytics. Never one database for all three.

04

Location is a pipeline, not a database call.

333k writes per second goes to a queue, gets batched, lands in an in-memory store. Never the transactional DB.

05

Match by area, not by city.

Grid or quadtree. Query only nearby cells. The single closest driver does not matter; an available one nearby does.

06

Two layers prevent double-booking.

Short-lived reservation when offering, atomic state change on accept. The database is the final word.

07

Real-time means WebSockets, with a fallback.

Polling when disconnected. Reconnect logic that catches up. Never trust a single connection.

08

The ride is a state machine.

Name the states. Reject illegal moves. The state machine is the contract between services.

09

Pricing is a separate service.

Marketing will change promos weekly. Surges change every minute. Tax rules change by city. Isolate all of it.

10

Idempotency is the payment rule.

Unique charge ID, retries send the same ID, the provider answers the same way. No idempotency, no scale.

11

Async is for everything the user is not waiting for.

Notifications, receipts, analytics, payouts. If the user is staring at a spinner, it should be sync; otherwise, queue it.

12

Cache config, not state.

Cache city rules, surge tables, profiles. Never cache active ride state or payment status.

13

Geographic scaling is a regulator question, not just a latency one.

Some countries require their data to stay in their country. Plan for that before you expand.

14

Cost is part of the design.

Throttle idle pings, sample analytics, right-size real-time connections. The largest cost is location, not API.

One-Minute Interview Answer

"I'd start by separating three concerns: fast-changing data, business transactions, and background work. Live driver location is fast-changing — hundreds of thousands of GPS pings per second — so it lives in an in-memory geo store with a short TTL, never the main database. Rides, payments, and profiles are business transactions in a relational database with strong consistency. Notifications, receipts, and analytics are background work that runs through a message broker so the user is never blocked. Matching sits in front of the location store: it asks for nearby available drivers, ranks them, offers the ride, and uses a short-lived reservation plus an atomic state change to prevent double-booking. Real-time updates go over WebSockets with a polling fallback. The ride itself is a strict state machine — Requested, Assigned, Arriving, Arrived, TripStarted, Completed — and only legal moves are allowed. For payment, every charge has a unique ID and the provider is idempotent, so retries never double-charge. Finally, scaling is geographic: the system is partitioned by city, regions are isolated for data residency, and the location pipeline is sized separately from the API because the traffic shapes are completely different. That's the shape — the trade-offs are consistency versus latency, simplicity versus scale, and centralized versus regional, and each is chosen by business impact, not by what is popular."

One Powerful Architect Statement

"A large real-time system earns its reliability by separating fast-changing data, business transactions, and background work into three independent pipelines — so each can scale on its own clock, fail on its own terms, and recover without taking the customer with it."
