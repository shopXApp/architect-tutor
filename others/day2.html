SECTION 01 — FOUNDATION

Start with the Real Problem

The interview question is "design a system for 1 million users." The wrong answer starts with technology. The right answer starts with a question: what actually changes as users grow?

What changes as users grow

Think of a restaurant. One table is easy. Ten tables need more waiters. A hundred tables need a bigger kitchen, multiple chefs, and a reservation system. The food is still the same — but everything around it must change shape.

SMALL SYSTEM

100 Users

One server handles everything comfortably. The database is fast. Deploys are simple. If one thing slows down, nobody really notices.

  • ~1–5 requests/second
  • One machine, one DB
  • Response time is fast naturally
  • Failure affects very few people
GROWING SYSTEM

10,000 Users

The database starts to sweat. Some queries are slow. Memory fills up. Requests queue. One slow request blocks others. You start noticing the shape of traffic.

  • ~50–200 requests/second
  • DB becomes the bottleneck
  • Need caching, indexing
  • One server is now a risk
LARGE SYSTEM

1,000,000 Users

Every single assumption you made at 100 users is wrong. You need multiple servers, intelligent routing, database replicas, caches, queues, CDN, monitoring. Failure is not a question of if — it is a question of which part next.

  • 1,000–10,000 requests/second
  • Every layer is a potential bottleneck
  • Stateless apps, distributed state
  • Partial failure is normal

The six things that change

What changesAt 100 usersAt 10,000 usersAt 1,000,000 users
RequestsA trickle. One server is bored.Noticeable. Slow queries begin to hurt.A firehose. Every component is under pressure.
Database queriesFast. No tuning needed.Slow queries appear. Indexes matter.DB is usually the first thing to collapse without design.
Memory usageMinimal. Plenty of headroom.Sessions, caches, connection pools fill up.Memory must be designed — every byte has a cost.
Network trafficNegligible.Bandwidth begins to matter for images, files.CDN, compression, and efficient protocols become critical.
Concurrent usersMaybe 10 at a time.Hundreds at a time. Thread pool pressure.Thousands simultaneously. Async becomes essential.
FailuresRare. Affects few people.Occasional. Need graceful degradation.Constant somewhere. Design assumes parts always fail.
THE ARCHITECT'S FIRST MOVE

Before drawing any diagram, an architect asks: what is the actual load? Where will it break first? What is the cheapest fix for that specific problem? — not "which technology should we use?"

SECTION 02 — LOAD ESTIMATION

Understand Load Before Designing

The single most common mistake in architecture interviews: someone hears "1 million users" and immediately starts designing for 1 million simultaneous requests. That is almost never the reality.

The vocabulary you need

→Load Concepts — Plain English
REGISTERED USERS
People who have an account. Most of them are not using the app right now. On a typical SaaS product, maybe 10–20% visit on a given day.
DAILY ACTIVE USERS
People who actually use it today. Usually 10–30% of registered users. For a social app it is higher; for a payroll tool it is much lower.
CONCURRENT USERS
People actively using the system at the same exact moment. Typically 5–15% of daily active users during peak hours. This number drives server sizing.
REQUESTS PER SECOND
Each user action (page load, search, button click) sends 1–10 HTTP requests. Concurrent users × actions per minute ÷ 60 = RPS. This is what you actually design for.
PEAK TRAFFIC
The highest load in a day, week, or year. A food delivery app peaks at dinner time. A tax software peaks in March. Design for the peak, not the average.
AVERAGE TRAFFIC
The normal, quiet load. Useful for cost estimation and baseline capacity. Not useful for scaling decisions — those are made at the peak.
RESPONSE TIME
How long the user waits for an answer. The target is not the same for every action — a product page should load in <1s; a report can take 30s. Measure at p95 (95th percentile), not the average, which hides the slow users.
INTERVIEW TRAP — THIS WILL BE ASKED

1 million registered users does NOT mean 1 million users are sending requests at the same time. A shopping platform with 1M registered users might have 80,000 active today, 8,000 online right now, and 2,000 requests per second at peak. Those four numbers are completely different design problems. The interviewer wants to know if you know this distinction.

5 Calculation Examples — Step by Step

You will be asked to estimate in interviews. Here is the thinking pattern — use it every time.

EXAMPLE 1 — E-COMMERCE: HOW MANY CONCURRENT USERS?
1Registered users1,000,000
2Daily active users (10% of registered — typical e-commerce)100,000
3Active during peak 2-hour window (50% of daily)50,000
4Concurrent at any single moment (10% of peak window active)5,000
→ Design for ~5,000 concurrent users, not 1,000,000
EXAMPLE 2 — E-COMMERCE: HOW MANY REQUESTS PER SECOND AT PEAK?
1Concurrent users at peak5,000
2Average actions per user per minute (browse, search, add to cart)3
3Total requests per minute (5,000 × 3)15,000
4Requests per second (15,000 ÷ 60)250 RPS
5Add 3× safety margin for flash sales and spikes750 RPS
→ Design infrastructure to handle ~750 requests/second at peak
EXAMPLE 3 — FOOD DELIVERY: HOW MUCH DATA STORAGE?
1Daily active users100,000
2Average orders per active user per day1.2
3Total orders per day (100,000 × 1.2)120,000
4Average order record size (order + items + address)2 KB
5Storage per day (120,000 × 2KB)240 MB
6Storage per year (240MB × 365)~87 GB
→ Orders DB needs ~87 GB/year — manageable on a single well-tuned SQL Server for several years
EXAMPLE 4 — BANKING: HOW MANY SERVERS DO I NEED?
1Target peak RPS1,000
2One ASP.NET Core server handles (well-written, async, no blocking)~300 RPS
3Servers needed to handle peak (1,000 ÷ 300)~4
4Add 2 extra for redundancy and rolling deploys+2
5Total servers6
→ Start with 6 app servers. The DB capacity is a separate calculation — and usually the harder one.
EXAMPLE 5 — SAAS: WHAT IS THE READ/WRITE RATIO?
1Users browse reports and dashboards (read)80% of requests
2Users create/update/delete records (write)20% of requests
3Read/write ratio4 : 1
4Decision: reads can use a read replica or cache; writes still go to primary DB✓
→ A 4:1 read/write ratio is a strong signal to add a cache and a read replica — before adding more app servers
INTERVIEW PATTERN

In an interview, always estimate in this sequence: Registered → Daily Active → Concurrent → RPS → Storage. Showing this chain tells the interviewer you have done this before. Making up a final number without showing the chain tells them you have not.

SECTION 03 — BOTTLENECK ANALYSIS

Find the Bottleneck First

Before adding any infrastructure, find where the system will slow down first. The whole system is limited by its weakest part — just like water through a pipe narrows to the smallest section.

→Common Bottleneck Locations
APPLICATION SERVER
CPU-heavy processing, blocking I/O, synchronous waits, memory leaks, connection pool exhaustion. First place to look when response time rises steadily.
DATABASE
Missing indexes, N+1 queries, too many connections, large table scans, lock contention, no read replicas. The most common bottleneck in .NET + SQL Server systems.
NETWORK
Too much data per response (large JSON, no compression), too many round trips, high latency between services, bandwidth limits. Common when you have many services calling each other.
EXTERNAL API
Payment gateway slow, SMS provider timing out, third-party data feed latency. You cannot optimize what you do not own — so you design around it. (Timeout, retry, queue, fallback.)
FILE STORAGE
Disk I/O limits, slow image uploads/downloads, large file reads on hot paths. Move files to blob storage (Azure Blob) and serve through CDN.
CACHE
Cache too small (constant eviction), wrong eviction policy, cache misses on every request (cold start), cache going down with no fallback — suddenly everything hits the DB at once.
THE RULE

"The whole system is limited by its weakest part." Adding 10 more app servers does nothing if the database is at 100% CPU. Find the bottleneck first. Fix that. Measure again. The bottleneck will simply move somewhere else — and that is progress.

5 Scenarios — Identify the Bottleneck

Read each scenario. Try to identify the bottleneck before you open the answer.

ANSWER BOTTLENECK: DATABASE — specifically the search query The app server is nearly idle (15% CPU). The database is saturated (90% CPU). The app server is not the problem — it is waiting for the DB. Likely cause: a LIKE '%keyword%' query doing a full table scan on a products table with no full-text index, or a missing composite index on searchable columns. Fix: add a full-text index, or move search to a dedicated search engine (Azure Search, Elasticsearch). Do NOT add more app servers — they will all just queue at the same DB bottleneck.
ANSWER BOTTLENECK: EXTERNAL API — the restaurant availability or payment provider Neither the app server nor the DB is saturated — yet the response time is terrible at peak hours. The bottleneck is almost certainly an external dependency: the restaurant POS system, the payment gateway, or the mapping API — all of which are also at their peak at dinner time. Fix: add a timeout (never wait more than 1–2 seconds for a vendor), move non-critical vendor calls off the request path into a queue, and implement a fallback. Do NOT scale hardware — you are waiting for someone else's server.
ANSWER BOTTLENECK: APPLICATION SERVER — likely CPU-bound synchronous processing, OR a shared downstream resource App server CPU at 80% with only 20% DB load means the CPU work is happening in the app: heavy computation, PDF generation, synchronous operations, or serializing large objects. Adding more servers doesn't help because either: (a) they share a resource that is now the new bottleneck (a connection pool, a lock, a queue), or (b) the problem is a shared state component you have not noticed yet. Profile the app — find the hot code path. Then decide: offload it to a background job, cache the result, or make it async.
ANSWER BOTTLENECK: FILE STORAGE I/O — blocking the request thread during upload A synchronous file upload is blocking the web server thread pool. While the upload is happening, no other request can be served by that thread. At enough concurrency, the thread pool is exhausted. Fix: make the upload fully async (ASP.NET Core async file streaming to Azure Blob), accept the upload and return immediately, then process it in the background. The API call should be: "I received your file. Processing will complete in a moment." — not: "wait here while I read 20 MB off a slow disk."
ANSWER BOTTLENECK: CACHE FAILURE causing a "thundering herd" to the database This is called a thundering herd or cache stampede: when the cache goes down, every request that was previously answered from cache now hits the database simultaneously. The database was never designed to handle that load — it was always protected by the cache. The real bottleneck here was the database's capacity, hidden until the cache was removed. Fixes: (1) add a fallback in-process cache, (2) implement circuit breaker — if cache is down, return degraded data instead of hitting DB, (3) Redis cluster/HA so the cache itself doesn't go down.
SECTION 04 — SCALING STRATEGY

Vertical vs Horizontal Scaling

When the system is under pressure, you have two levers. Understanding when to pull each one is a core architect decision — and a guaranteed interview question.

⬆ VERTICAL SCALING — Make one machine bigger
  • What: Upgrade CPU, add RAM, faster disk on the same machine
  • Analogy: Hire one really experienced chef who can cook faster
  • Pros: Simple — no code changes, no network complexity, no session problem
  • Cons: Expensive — big machines cost disproportionately more
  • Cons: There is a physical ceiling — you can only buy so much machine
  • Cons: Single point of failure — one machine, one outage
  • Cost curve: Linear, then suddenly exponential at the top
  • Use when: The bottleneck is a single component that is hard to distribute (e.g., SQL Server, a stateful service)
  • Don't use when: You need high availability — one big machine still fails as one
↔ HORIZONTAL SCALING — Add more machines
  • What: Run multiple identical smaller machines behind a load balancer
  • Analogy: Hire more chefs, each handling separate tables simultaneously
  • Pros: Near-unlimited scale — just add machines
  • Pros: High availability — one machine fails, others keep serving
  • Pros: Cost scales linearly and stays predictable
  • Cons: Requires stateless application design — sessions can't live in memory
  • Cons: Consistency is harder — multiple machines, shared DB, race conditions
  • Cons: More operational complexity — deploy, monitor, route across many machines
  • Use when: The app tier is the bottleneck and the app is (or can be made) stateless
  • Don't use when: The bottleneck is the database — more app servers just create more DB pressure
FactorVertical ScalingHorizontal Scaling
Speed to add capacitySlow — need to resize/restart serverFast — spin up a new instance in minutes
Cost per unitHigh at the top endLinear and predictable
CeilingHard ceiling — maximum machine sizeEffectively unlimited
Code changes neededNone — transparent to the appApp must be stateless or externalize state
Failure impactTotal — one machine, one outagePartial — other machines keep running
Best forDatabases, early-stage systemsWeb/API tiers, mature systems with load
WHY MODERN SYSTEMS PREFER HORIZONTAL

Horizontal scaling aligns with cloud economics (pay per small machine, not one giant machine), enables zero-downtime deploys (take down one server at a time), provides built-in high availability (other servers keep running when one dies), and allows autoscaling — the cloud adds machines during a spike and removes them afterwards. Vertical scaling is still used — especially for databases — but it is always a starting point, never the end game.

INTERVIEW ANSWER PATTERN

"I would start with vertical scaling for the database (simpler, no code change) and horizontal scaling for the stateless app tier (multiple instances behind a load balancer). As the database reaches its vertical ceiling, I would move to read replicas and eventually sharding — but only when measured load demands it."

SECTION 05 — TRAFFIC DISTRIBUTION

Load Balancer

A load balancer is the traffic cop that stands in front of your servers. Without it, horizontal scaling is impossible — because users do not know which server to talk to.

What it actually does

→What a Load Balancer Does — Five Jobs
DISTRIBUTES TRAFFIC
Sends each incoming request to a server — round-robin (take turns), least connections (pick the least busy), or IP hash (same user goes to same server). This is the main job.
HEALTH CHECKS
Every few seconds, pings each server ("are you alive?"). If a server doesn't respond, the LB removes it from rotation automatically. Users never see the failed server — they hit a healthy one.
SSL TERMINATION
Handles HTTPS encryption/decryption at the edge, so app servers get plain HTTP internally. Offloads CPU-intensive crypto from the app servers.
ENABLES ROLLING DEPLOYS
Take Server 1 out of rotation, deploy new code, health-check passes, put it back. Repeat for all servers. Zero-downtime deployment is only possible because of the load balancer.
RATE LIMITING / DDoS PROTECTION
Reject or throttle requests from a single source that is sending too many. Protects the servers behind it from being overwhelmed by a single bad actor.

The Session Problem — and How to Solve It

Here is the classic trap with horizontal scaling:

THE SESSION PROBLEM

User logs in. Server 1 creates a session and stores it in memory. Next request goes to Server 2 — which has no memory of this session. The user is logged out. Adding servers without solving this problem makes login unreliable in proportion to the number of servers.

SolutionHow it worksTrade-off
Sticky Sessions (Affinity)LB always sends same user to same server (via IP or cookie)Simple but breaks HA — if that server dies, the user loses session. Not truly stateless.
Centralized Session StoreSession data lives in Redis. Every server reads/writes the same store.Redis becomes a dependency — if it goes down, all sessions are gone. Add Redis HA.
JWT Tokens (Stateless)Session info is in a signed token carried by the client. No server stores it.Tokens can't be invalidated before expiry without a server-side check. Keep them short-lived.
ARCHITECT RECOMMENDATION

Use JWT with short expiry (15–60 min) + refresh tokens stored in Redis. This gives you stateless app servers (any server handles any request), while keeping the ability to revoke sessions (invalidate the refresh token). This is the pattern used in most serious ASP.NET Core systems with horizontal scaling.

SECTION 06 — CACHING

Caching

The fastest database query is the one you never make. Caching stores a pre-computed answer close to the consumer so the same work is not repeated for every request.

The core idea — a shopping example

"Show me the product page for iPhone 15."

Without CacheWith Cache
Request → App → DB Query (200ms) → Serialize → Response

Every single user triggers the same DB query. At 500 RPS on product pages, that is 500 × 200ms of DB time per second. The DB is doing the same work, repeatedly, for identical data.		 Request → App → Cache hit? Yes → Return in 2ms → Response

The product data is fetched from DB once (on cache miss), stored in Redis for 5 minutes. For the next 5 minutes, all product page requests are served from memory in 2ms. The DB sees a tiny fraction of the traffic.
→Caching Concepts — Plain English
CACHE HIT
The answer is already in cache. Return it immediately. No DB call. This is what you are designing for.
CACHE MISS
Not in cache. Go to the DB, get the data, store it in cache for next time, return it. Slightly slower than normal but happens once per cache window.
EXPIRATION (TTL)
How long the cached data is valid. After TTL, the next request is a cache miss and the cache refreshes. Product prices: maybe 5 minutes TTL. User profile: 30 minutes. Homepage hero banner: 1 hour.
STALE DATA
The cached data is older than reality. A product price updated in the DB is still the old price in cache for up to 5 minutes. This is an explicit trade-off: speed for freshness. You decide what is acceptable per use case.
CACHE INVALIDATION
Removing or updating cached data when the source changes. Hard problem. Best approach: short TTL (let it expire naturally) + explicit delete on write (remove the key when the product updates).

What to cache — and what NOT to cache

✓ GOOD CANDIDATES FOR CACHE
  • Product catalog data — changes rarely, read millions of times
  • User profile / preferences — stable, read on every page
  • Homepage content, banners, featured items — static for hours
  • Reference data — country lists, category trees, config values
  • Aggregated stats — dashboard totals, report summaries (with acceptable delay)
  • API responses from slow external services (with short TTL)
✗ BAD CANDIDATES FOR CACHE
  • Real-time stock levels during checkout — must be exact
  • Payment transaction results — must be exact, never stale
  • User's own orders in real-time — freshness matters
  • Per-user, per-second data — the cache key space explodes
  • Sensitive PII without encryption and access control
  • Data that changes every request — caching it is pointless

What happens when the cache goes down?

CACHE FAILURE — THE THUNDERING HERD

When cache goes down, every request that was previously a cache hit now becomes a DB query simultaneously. If the DB was never designed to handle that load (because the cache was always protecting it), the DB collapses under the sudden traffic. The cache failing causes a full site outage — even if the cache itself is not critical data.

StrategyWhat it does
In-process fallback cacheKeep a small in-memory cache inside the app. If Redis is down, serve from memory for a short time. Buys time for Redis to recover without a DB stampede.
Circuit breakerIf cache calls are failing, stop calling it. Return a degraded response ("data may be slightly out of date") rather than stampeding the DB.
Redis HA / ClusterRedis Sentinel or Redis Cluster — so the cache itself has redundancy and does not go down cleanly.
Staggered TTLsDon't expire all keys at the same time. Add a small random jitter to TTL values so cache misses are spread out over time, not all at once.
SECTION 07 — DATABASE SCALING

Database Scaling

The database is usually the last thing you can scale horizontally — and the first thing to become a bottleneck. Understanding how to relieve database pressure without immediately jumping to sharding is a sign of real architect experience.

Why the database bottlenecks first

App servers are stateless and can be cloned. Databases are stateful — they hold the truth. Every write must go to one place. Every read must see consistent data. You can't just "add more databases" the way you add app servers.

The escalation ladder — in order

1IndexingDO THIS FIRST — ALWAYS
What
Database index — like the index at the back of a book. Instead of reading every row to find what you need, the DB jumps directly to the right page.
When to use
Any column you filter on (WHERE), join on, or sort by (ORDER BY) in a frequently-run query. Missing index on a large table = full table scan = the most common cause of slow queries in SQL Server.
Trade-off
Indexes slow down writes (the index must be updated too) and consume disk space. Add them deliberately, not everywhere.
Example
Orders table with 50 million rows. Query: "give me all orders for user ID 12345." Without an index on UserID, SQL Server reads 50 million rows. With an index, it reads ~200 rows in milliseconds.
2Read ReplicasSEPARATE READ AND WRITE TRAFFIC
What
A copy of the database that continuously receives changes from the primary ("write") database. Read traffic goes to replicas. Write traffic goes to primary.
When to use
When you have a high read/write ratio (80% reads or more) and the primary DB is saturated despite indexing. Typical: reporting, dashboards, product listings, user profiles.
Trade-off
Replication lag: writes go to the primary, but replicas may be a few milliseconds (or seconds) behind. A user who just created an order may not immediately see it in a read that goes to a replica. Design around this: writes always read-back from primary; dashboards read from replica.
Example
E-commerce: product browsing (millions of reads) goes to replica. Order creation (writes) goes to primary. The primary DB CPU drops by 70%.
3Partitioning (Sharding)LAST RESORT — USE WITH CARE
What
Split the data itself across multiple database servers. Each server holds a subset of the data (e.g., customers A–M on shard 1, N–Z on shard 2). No single server holds everything.
When to use
When you have genuinely huge data volumes (billions of rows) or write throughput that exceeds what one primary DB can handle — even after vertical scaling and caching. This is rare at typical enterprise scale.
Trade-off
Cross-shard queries are expensive or impossible. "Give me all orders" now requires asking every shard. Transactions across shards are complex. The shard key decision is extremely hard to change later. Most systems at 1 million users do NOT need sharding.
Example
A multi-tenant SaaS: shard by tenant ID. Each tenant's data lives entirely on one shard. Cross-tenant queries are rare by design — so the trade-off is acceptable.
THE ORDER MATTERS

Indexing → Caching → Read Replicas → Vertical Scale → Sharding. Most systems at 1 million users need only the first three. Jumping to sharding before exhausting the others is overengineering — and will cost you dearly in operational complexity.

SECTION 08 — STATELESS DESIGN

Stateless Application Design

Making your application stateless is the single most important thing you must do before horizontal scaling works. Without it, adding servers creates problems instead of solving them.

What "stateless" means

Stateful AppStateless App
Session storageSession lives in server memory (RAM)Session lives externally — Redis, DB, or JWT
User contextServer "remembers" who you are between requestsEvery request carries its own identity (JWT token)
Load balancerMust send same user to same server (sticky)Any server can handle any request — LB is free to route to healthiest
ScalingAdding servers causes login and session bugsAdd any number of servers — each is identical
Server failureUser loses session and must log in againNext request goes to a different server — user notices nothing
Local cacheEach server has its own in-memory cache — may be out of syncCache is external (Redis) — all servers see the same data

Where state must go instead

→State Belongs in External Storage
USER SESSION
Redis (fast, ephemeral, shared across all servers). OR: JWT token (the state travels with the user, no server needs to store it).
SHOPPING CART
Redis for active carts (fast reads/writes). Database for completed orders. Never in server memory — the cart must survive server restarts and load balancer routing changes.
UPLOADED FILES
Azure Blob Storage, AWS S3 — shared, durable, accessible from any server. Never on the local disk of an app server.
TEMP COMPUTATION
Background jobs or queues (RabbitMQ). The request accepts the work, puts it on the queue, and returns immediately. A worker picks it up regardless of which server it runs on.
APPLICATION CONFIG
Environment variables, Azure App Config, or a config service. Never hardcoded per server — all servers must behave identically with the same config.
INTERVIEW PHRASE TO USE

"My application servers are stateless — any server can handle any request from any user. State lives in external systems: Redis for sessions and cache, SQL Server for persistent data, Azure Blob for files. This means I can add or remove servers without any impact on users."

SECTION 09 — CONTENT DELIVERY

CDN and Static Content

Why should a user in Mumbai download a product image from a server in West Europe, if the same image can be served from a server 20 km away from them?

What a CDN does

A CDN (Content Delivery Network) is a distributed network of cache servers spread around the world. A file is stored once on your origin server, then automatically copied ("cached") to CDN servers ("edge nodes") around the world. When a user requests that file, the CDN serves it from the closest edge node — not from your origin.

→CDN — When to Use, When Not To
GOOD FOR
Images, CSS, JavaScript, fonts, HTML templates, videos, PDF files, downloadable content. Anything static that does not change per user and can be cached. This category is often 60–80% of your total bandwidth.
NOT FOR
Dynamic API responses that are unique per user (order history, personalized content). Anything that changes in real-time. Authenticated pages that should not be cached publicly.
COST BENEFIT
CDN bandwidth is significantly cheaper than origin server bandwidth. More importantly, it offloads your servers and network — a CDN cache hit never touches your origin server at all.
WHEN UNNECESSARY
All users are in one geography (internal enterprise tool). Content is entirely dynamic and user-specific. Very low traffic where latency is not a concern. Early-stage product with no global audience.
INTERVIEW ANSWER

"All static assets — images, JS, CSS — are served from CDN. This reduces origin server load by ~70% and cuts latency for global users from hundreds of milliseconds to single digits. The origin only handles API requests and page rendering. Static content that never changes gets a very long Cache-Control header (1 year) with a content-hash in the filename so we can deploy new versions without cache issues."

SECTION 10 — PUTTING IT TOGETHER

Full System Design — 6 Versions

Now we combine everything. Same system, growing under load. Each version solves the problem created by the previous version's scale. Watch the pattern: problem → change → why → new trade-off.

Version 1 — Basic Application + Database

~100 USERS~5 RPS1 SERVER

Design: One ASP.NET Core application server, one SQL Server database. All requests go to one machine. All data in one database. Simple deployment, simple monitoring.

Why it works here: At 100 users the load is minimal. The simplest design is always the right design for small load — complexity has a cost too.

The problem that will appear: When users grow to thousands, this single server becomes a single point of failure and a performance ceiling. One deploy = full downtime. One hardware failure = full outage.

New trade-off introduced: None — this is the baseline. Enjoy it while it lasts.

Version 2 — Multiple App Servers + Load Balancer

~5,000 USERS~100 RPS3 APP SERVERS

Problem from V1: Single server is at CPU capacity. One deploy takes the site down. One hardware failure = total outage.

Change: Add a load balancer in front. Run 3 identical ASP.NET Core instances. Sessions moved to Redis (required for stateless routing). SSL termination at the LB.

Why: Any server can now handle any request. Rolling deploys are possible (take one server out, deploy, put it back). One server can die and the other two keep serving.

New problem: The database is now receiving 3× the connection pressure. All three app servers share one database. The DB becomes the new bottleneck.

New trade-off: Sessions must be stored externally (Redis). Added operational complexity of a load balancer and Redis. But gained HA and zero-downtime deploys.

Version 3 — Add Caching Layer

~20,000 USERS~400 RPSCACHE HIT 80%

Problem from V2: DB is overloaded. 80% of queries are reads for the same product pages, category lists, and reference data. The same SQL queries fire hundreds of times per second for identical data.

Change: Add Redis caching for hot data. Product catalog: 5-min TTL. User preferences: 30-min TTL. Reference data (categories, brands): 1-hour TTL. Cache-aside pattern — app checks cache first, falls back to DB on miss.

Why: 80% cache hit rate means 80% fewer DB queries. DB load drops dramatically. Response time for cached items falls from ~200ms to ~2ms.

New problem: Stale data for up to 5 minutes (for product data). Cache failure causes thundering herd to DB. Cache warming needed after deploys (cold start problem).

New trade-off: Speed vs freshness. Cached product prices may be up to 5 minutes old. Acceptable for browsing — NOT acceptable for checkout (checkout always re-reads live stock and price).

Version 4 — Database Scaling (Read Replicas)

~100,000 USERS~1,000 RPSREADS SPLIT

Problem from V3: Caching helped a lot, but cache misses and write traffic still hit the primary DB hard. Reporting queries and analytics are competing with live transaction queries. The primary DB is the bottleneck again.

Change: Add one or two SQL Server read replicas. Route: order creation and payment → primary. Product reads, user profiles, reporting, dashboards → replica. All writes still go to primary.

Why: The primary DB now only handles writes and the most critical reads. The replica absorbs the large volume of read traffic. Reporting queries can run on replica without affecting live transactions.

New problem: Replication lag (typically milliseconds to seconds). A user who just placed an order might query the replica and not see it immediately. Handle this: after a write, redirect the next read for that user to the primary for a short window.

New trade-off: Consistency vs scale. Replica reads may be slightly stale. Acceptable for product browsing and reports. Never acceptable for financial data — those always go to primary.

Version 5 — Background Processing for Slow Tasks

~200,000 USERS~2,000 RPSASYNC QUEUE

Problem from V4: Some operations are slow and holding up the request thread: sending confirmation emails, generating invoices, updating search indexes, sending SMS, processing images, generating reports. These make the user wait — and they block the thread pool during peak load.

Change: Move all slow, non-critical work to a message queue (RabbitMQ / Azure Service Bus). The API accepts the request, writes the event to the queue, and returns immediately ("Order placed — confirmation email coming shortly"). A separate worker pool processes the queue asynchronously.

Why: The web request path becomes short — just write to DB and enqueue the event. The user gets a fast response. Slow work runs at its own pace, with retries on failure, without blocking web threads.

New problem: Eventual consistency — user places order, email arrives a few seconds later. If queue is down, events must not be lost (use persistent queues + dead-letter queues). Workers must be idempotent — the same message processed twice must produce the same result.

New trade-off: Simplicity vs speed. The request path is now simpler and faster. But the system is now distributed — you have more components to monitor, and debugging becomes harder (trace requests across services).

Version 6 — Final Architecture for 1 Million Users

1M REGISTERED100K DAILY ACTIVE2,000 RPS PEAK10K CONCURRENT

Everything together: CDN for all static assets → Load Balancer → 6–8 stateless app servers (autoscaling) → Redis cache + Redis sessions → Primary SQL DB (writes + critical reads) + 2 read replicas (read traffic + reporting) → RabbitMQ/Service Bus queue → Worker pool for async tasks (email, SMS, reports, search index updates) → Azure Blob for files → Monitoring and alerting on every layer.

Costs are justified because: We added each component only when a measured bottleneck demanded it. We did not start here on Day 1 — we arrived here through five iterations driven by actual growth.

What would change this further (1M → 10M): Separate the monolith into domains if team size demands it, consider sharding the DB by tenant or region, add a dedicated search service for product search, implement multi-region deployment for latency and availability, add a proper API gateway layer.

The architect's honest statement: This architecture works for the given load. If traffic suddenly grows 10×, the app servers autoscale, the cache absorbs the read spike, and the main risk is the primary DB write throughput — which would be the next planned upgrade. We know where the next bottleneck is before it happens.

SECTION 11 — ARCHITECT THINKING

What Should I Ask Before Saying a System Can Handle 1 Million Users?

Twenty questions. Each one changes the design. In an interview, asking these tells the interviewer more than any answer could.

These three numbers are completely different design problems. Designing for registered users as if they are all concurrent is the most expensive and common mistake in system sizing. The chain registered → active → concurrent → RPS is the calculation you must always perform before drawing the first box.
Average load is for cost planning. Peak load is for capacity planning. A system that handles the average but collapses at the peak is not a working system — it is a scheduled outage. Ask when the peak is (dinner time, salary day, sale events) and design for 2–3× that peak for safety margin.
Not all actions need the same speed. Product page: under 1 second. Search: under 500ms. Report generation: 30 seconds acceptable. Payment status: instant. Each target changes the design — caching for fast reads, queues for slow operations, synchronous paths only for critical exact operations.
A 90:10 read-heavy system screams for caching and read replicas. A 50:50 write-heavy system (trading platform, messaging) needs to focus on write throughput, queueing, and consistency. The same "1 million users" can mean completely different architectures depending on this ratio.
A system with 10 GB of data and one with 10 TB need fundamentally different storage strategies, index strategies, and backup strategies. Growth rate matters too — a system that will have 10× the data in 2 years needs to be designed with that growth path already modelled.
99.9% = ~8.7 hours/year. 99.99% = ~53 minutes/year. These are not minor differences — achieving 99.99% costs roughly 10× more than 99.9% and requires redundancy at every layer (load balancer, app, DB, network). The business must choose this number, not the engineer.
Does the entire site go down? Or can you serve read-only from cache? Can you accept writes into a queue and replay them when DB recovers? Answering this defines your recovery plan: RTO (how fast do you recover) and RPO (how much data can you lose). These drive the need for replicas, failover clusters, and backup strategies.
Payment gateways, SMS providers, email services, mapping APIs, identity providers. Each one is a potential outage that is outside your control. For each: what is the timeout, what is the retry strategy, what is the fallback? External dependencies are often the actual cause of incidents that look like your system's failures.
Predictable traffic (monthly payroll run, end-of-day reports) allows scheduled scaling. Unpredictable spikes (a product goes viral, a news link sends traffic) require autoscaling, rate limiting, and queue-based load shedding. The architecture is different for each — you can't plan for a viral moment if you have designed for a flat curve.
All users in one country: one region, CDN for static assets. Users spread globally: multi-region deployment (latency), CDN everywhere, data residency compliance per region. A banking app with users only in the UK needs a very different geographic architecture than a global SaaS product.
Card data (PCI-DSS), health records (HIPAA), personal data (GDPR), financial records (SOX). Each classification adds compliance requirements that change the architecture: where data can live, how it is encrypted, who can access it, what audit logs are required. Ignoring this until after launch is expensive.
A $5,000/month budget and a $50,000/month budget are completely different design constraints. High-availability with multiple regions costs money. Managed services cost money. Autoscaling costs money at peak. An architect who designs without cost constraints is not designing — they are dreaming.
One team of five people does not need microservices. Five teams of ten people might — because team boundaries need to map to deployment boundaries. Conway's Law: the architecture will mirror the organization structure. Understanding the team size determines how the system should be split (or not split).
Design for today + a clear growth path to tomorrow. Not for 10 years from now. If the product is expected to grow 3× in a year, the architecture needs a defined plan for each scale milestone — not a full-scale rewrite at each milestone.
Payment processing: must be exact. Stock quantity at checkout: must be exact. Product description on a browsing page: can be 5 minutes old. Dashboard totals: can be a few minutes delayed. Distinguishing these unlocks a huge set of architectural options (caching, read replicas, async processing) that are only safe for the "eventually consistent" category.
1 hour of downtime for a company that processes £50,000 of orders per hour has a direct financial cost. For a social platform it is reputational. Understanding the actual cost of failure helps the business decide how much to invest in reliability — and helps you prioritize which failures to design against first.
Nightly payroll runs, monthly billing, bulk report generation. Batch workloads compete with live traffic for DB and CPU resources. They need to be designed separately — either scheduled at low-traffic times, or run on separate infrastructure that does not share resources with the live system.
At 1 million users, "something is slow" is not actionable. You need: request traces to find which service is slow, metrics to know when to scale, alerts to know before users complain, and logs to debug what happened. Observability is not optional at scale — it is how you find bottlenecks before they become incidents.
RTO (Recovery Time Objective): how long until you are back up? RPO (Recovery Point Objective): how much data can you afford to lose? A banking system might require RTO 15 min and RPO 0 seconds. A product catalogue app might accept RTO 4 hours and RPO 1 hour. These numbers directly determine backup frequency, replication, and failover design.
The most important question. All the previous nineteen questions produce assumptions. Before spending money on infrastructure, measure: load test the system, watch what saturates first, then fix that specific thing. Optimizing the wrong thing — even brilliantly — makes no difference. Measure. Then design. Always.
SECTION 12 — HONEST EDITION

Common Scaling Mistakes

These are not junior mistakes. Senior engineers and technical leads make every one of them. The difference after today is that you will see them before they become incidents.

01

Assuming registered users equal concurrent users

The number "1 million users" feels real and urgent. The brain skips the calculation and assumes the worst — that all of them want something right now. This leads to massively over-engineered and over-expensive architecture from day one.

Always complete the chain: registered → daily active → peak concurrent → RPS. The final number is what you design for. Show this calculation in every interview and every design review.

02

Adding more app servers when the bottleneck is the database

Adding servers is easy and feels like progress. But if the DB is already at 90% CPU, six new app servers will not help — they will create six times more pressure on the already-maxed DB. The site will not get faster; it will get worse.

Identify the bottleneck first. If the DB is the bottleneck, fix the DB (indexes, cache, replica). Only then consider adding app servers — when the app tier is actually the constraint.

03

Caching everything indiscriminately

Caching feels like a free win. So engineers cache user-specific data, stale financial data, per-request unique data — and then users start seeing wrong prices, other users' data, or ghost orders that should not exist.

Cache only data that is: read many times more than written, safe to be slightly stale, shared across users (not user-specific sensitive data). Cache with explicit TTL and intentional invalidation on write.

04

Ignoring what happens when cache fails

The cache is "just a performance optimization" — so nobody plans for it failing. Then Redis goes down for 3 minutes during peak sale and the database, which was sized assuming 80% cache hits, instantly collapses under full load.

Design the fallback: in-process L1 cache, circuit breaker that degrades gracefully, Redis HA, and staggered TTLs to prevent stampede. The cache is now part of the critical path — treat it accordingly.

05

Keeping application state in server memory

It works perfectly on one server. Then you add a second server and users start getting mysteriously logged out. Session data on Server 1 is invisible to Server 2. The fix is always the same — but it is always discovered by the first outage after horizontal scaling.

Externalize all session state to Redis or use stateless JWT from day one, before you have more than one server. Retrofitting this on a running system is painful and risky.

06

Jumping to microservices because the system is "large"

Large systems do not need microservices — large teams may need them. A well-structured monolith serving 10 million users is a success story. Splitting it into 30 microservices because it "feels more scalable" adds network calls, distributed tracing complexity, and service coordination overhead that a team of 4 cannot manage.

Scale justifies microservices only when the load on a specific part demands independent scaling, or when team boundaries require independent deployment. Not before.

07

Optimizing before measuring

An engineer "knows" the DB is slow — so they spend two weeks adding caching. The real bottleneck was a synchronous email call that blocked the thread pool. Two weeks wasted, problem still present, customers still complaining.

Measure first. Load test. Watch CPU, memory, DB connections, response time per endpoint, thread pool saturation. Find the actual bottleneck. Fix that one. Repeat.

08

Designing for average traffic instead of peak traffic

The system handles 500 RPS easily all day. Then a flash sale starts, traffic hits 4,000 RPS for 20 minutes — and the system is down for the most commercially important period of the month. Average performance is the worst metric for capacity planning.

Design for peak × 2–3 safety factor. Know when the peak is. Have a tested plan for load shedding (what to switch off first) if the peak exceeds design capacity anyway.

09

Ignoring external API dependencies as a risk

The payment gateway has 99.9% uptime — that's fine, right? But 99.9% means 8.7 hours per year down. And when it is down at dinner time on a Friday, your entire checkout is down too, even though your system is perfectly healthy. The external vendor's SLA is the ceiling for your own availability, unless you design around it.

For every external dependency: define timeout, retry policy, fallback behaviour (second vendor, queue-and-retry, graceful degradation message to user). The design must assume every external service will fail at the worst possible time.

10

Designing for unrealistic scale — the "we might get on the news" fallacy

The team designs for 10 million users on day one because "what if we go viral?" The result: Kubernetes clusters, 15 microservices, event sourcing, CQRS — for a product with 200 users and no confirmed market fit. The operational complexity kills velocity and the company burns its budget on infrastructure before the product is proven.

Design for 3× your realistic near-term load, with a clear and cheap path to 10×. The architecture for "maybe someday" should not cost the same as the architecture for "definitely now."

THE THREAD RUNNING THROUGH ALL TEN

Measure first. Fix the actual bottleneck. Add complexity only when load demands it. Every mistake above is a variation of "we skipped one of those three steps."

SECTION 14 — INTERVIEW PREPARATION

10 Technical Architect Interview Questions

Read the question. Write or say your answer out loud. Then open the model answer. Compare your direction — not your exact words.

IQ 01"How would you design a system for 1 million users?"
First clarify: "1 million registered, or 1 million concurrent?" Then walk through the estimation chain to arrive at realistic concurrent users and RPS. Then outline the progressive architecture: (1) start with one server + DB for small load, (2) add LB + multiple stateless app servers as the app tier saturates, (3) add caching for read-heavy traffic, (4) add read replicas when the DB becomes the bottleneck, (5) add async queue for slow work. At each step explain the trigger that causes the change and the trade-off it introduces. End with: "At 1 million registered users and the numbers I calculated, this is the design — and this is where the next bottleneck will appear if we grow 10×."
IQ 02"How do you estimate capacity for a new system?"
Start from what you know: registered users × activity rate = daily active. Apply peak factor and session duration to get concurrent users. Multiply by actions per minute ÷ 60 = RPS. Then estimate per-server capacity (based on similar systems or load tests) and divide. Add 2–3× safety margin for unexpected spikes. For storage: daily writes × record size × 365 × retention years. Show the calculation explicitly — the interviewer wants the thinking, not just the final number.
IQ 03"What happens when traffic suddenly becomes 10×?"
First layer of response: autoscaling adds app servers automatically (if the app is stateless and autoscaling is configured). Second layer: the cache absorbs the read spike (if the cache hit rate is high and the cache is healthy). Third layer: the load balancer rate-limits to protect the system from accepting more than it can handle. Fourth layer: the primary DB write throughput is the likely breaking point — for a planned 10× scenario, I would pre-scale the DB tier (bigger primary, more read replicas) and ensure the queue is absorbing non-critical writes. Fifth: have a runbook — which features can be disabled first (recommendations off, detailed analytics off) to protect core checkout.
IQ 04"What becomes the bottleneck first as you scale?"
The order is almost always: (1) the database — specifically slow queries and connection count; (2) the app server — usually CPU or thread pool exhaustion from blocking calls; (3) external dependencies — payment and notification vendors that are slow or unreliable under load; (4) network/bandwidth — once you're serving millions of large responses; (5) the cache — when it becomes a bottleneck from too many connections or when it fails and the DB gets stampeded. But — always measure first. The actual bottleneck in your specific system may be different from the general pattern.
IQ 05"Why do you prefer horizontal scaling over vertical?"
Vertical scaling has a hard ceiling (maximum machine size), is expensive at the top, and still has a single point of failure. Horizontal scaling has no practical ceiling, scales cost linearly, enables zero-downtime deploys (rolling), and provides HA (other servers keep running when one dies). However — horizontal scaling requires stateless application design, which is a non-trivial engineering requirement. I prefer horizontal for the app tier once the app is stateless. For the database I use vertical scaling first, then read replicas, before considering horizontal DB scaling (sharding).
IQ 06"How does caching help scalability?"
Caching breaks the linear relationship between traffic and DB load. Without cache, 2× traffic = 2× DB queries. With an 80% cache hit rate, 2× traffic = only 40% more DB queries. This is not just a performance optimization — it is the mechanism that makes 1 million users manageable on a reasonably-sized database. Cache also reduces response time dramatically (2ms vs 200ms for the same data), which improves user experience and reduces server thread occupancy. The trade-off is data freshness — and the architect must decide which data can be slightly stale and which cannot.
IQ 07"What happens if Redis (your cache) goes down?"
If the cache goes down unexpectedly and there is no fallback, every request that was previously a cache hit now hits the database simultaneously — a thundering herd. If the database was never sized for that load (because the cache was protecting it), the DB collapses, causing a total outage. My mitigation: (1) Redis HA (Sentinel or Cluster) to prevent clean failure, (2) in-process L1 cache as a short-term fallback, (3) circuit breaker pattern — if cache is unreachable, degrade gracefully (serve slightly stale or simplified responses) rather than hammering the DB, (4) staggered TTLs to prevent mass simultaneous expiry.
IQ 08"How do you scale a database?"
In strict order: (1) Add proper indexes — this is free and often 10–100× improvement on slow queries; (2) Add caching — serve hot reads from cache, dramatically reducing DB load; (3) Add a read replica — separate read and write traffic, replicas absorb reporting and browse queries; (4) Vertical scale the primary — bigger machine, more RAM, faster disk — simple with no code change; (5) Connection pooling tuning; (6) Query optimization — fix N+1, reduce large joins; (7) Sharding — only when genuinely needed, because it adds significant complexity. Most systems at 1 million users need only steps 1–4.
IQ 09"Why do you need a load balancer?"
Three reasons: (1) Traffic distribution — without it, multiple servers are pointless because users don't know which server to call; (2) High availability — health checks detect a failed server and route around it in seconds, giving users a seamless experience even during a partial failure; (3) Zero-downtime deploys — take one server out of rotation, deploy to it, health-check passes, put it back, repeat. Without a load balancer, a deploy means downtime. Secondary benefits: SSL termination (offloads crypto from app servers), rate limiting, and DDoS protection at the edge.
IQ 10"How do you know whether scaling is actually required?"
By measuring. Specifically: (1) Application server CPU consistently above 70–80% during normal load (not just brief spikes); (2) Response time at p95 exceeding the defined SLA; (3) Database connection pool exhaustion or query wait time increasing; (4) Error rate increasing — timeouts, 500s, circuit breaker triggers; (5) Thread pool saturation. If none of these are happening, you do not have a scaling problem — you have a performance anxiety problem. Scale when measured pain appears, not when the user count reaches a round number.

FINAL — DAY 2 PRINCIPLES

Architect Mindset, Day 2

Five rules. Short on purpose. You will use each one in every system design conversation for the rest of your career.

01

Understand the load before drawing any box

Registered users are not concurrent users. The RPS is not the user count. Calculate the chain every single time — registered → active → concurrent → RPS. The diagram you draw from the wrong number is the wrong diagram, no matter how good it looks.

02

Find the bottleneck before adding infrastructure

Adding servers to a database bottleneck makes things worse. Adding cache to a CPU bottleneck does nothing. Measure first — CPU, memory, DB query time, thread pool saturation, external API latency. Then fix the actual constraint. The bottleneck will move when you fix it. That is progress, not failure.

03

Every component can fail — design the failure, not just the success

The cache will go down. The payment gateway will time out. One app server will crash. Design the failure scenario for every component: what does the user see, does the system degrade gracefully, does it recover automatically? The happy path is the easy part. The failure path is the architecture.

04

Simple first, complex only when load demands it

The right architecture for 100 users is one server and one database. The right architecture for 10 million users is fundamentally different. Do not design 10 million from day one — design 100 with a clear, cheap path to 10 million. Complexity is earned, not assumed.

05

Name your trade-offs before someone else names them for you

Caching introduces stale data. Read replicas introduce replication lag. Async queues introduce eventual consistency. Know your trade-offs. State them out loud in the design review and in the interview. An architect who hides trade-offs is not an architect — they are a salesperson. An architect who names them earns trust.

"Do not start by choosing technologies. Start by understanding the load, finding the bottleneck, and then choosing the simplest solution that can handle the expected growth."
