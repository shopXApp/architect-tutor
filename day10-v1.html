SECTION 01 — THE REAL PROBLEM

Why Teams Move to Containers

Before any technology: the six problems that make "it works on my machine" a deployment strategy. A simple .NET API shows all six at once.

DIFFERENT ENVIRONMENTSDev has .NET 8, staging has .NET 8 Service Pack 2, prod has .NET 6. The same code behaves differently in each — and the difference is invisible until 2 a.m.
DEPENDENCY CONFLICTSService A needs OpenSSL 1.1, Service B needs 1.0. On one server they fight; in containers each gets its own copy and the fight disappears.
"WORKS ON MY MACHINE"The honest translation: the machine is part of the application. Any environment difference — SDK, fonts, region settings, timezone — is an unshipped dependency.
DEPLOYMENT INCONSISTENCYDev deploys with a script, ops deploys by hand, the CI pipeline deploys a third way. Three deployments, three results, one ticket.
DIFFICULT SCALINGOne machine, one app, one instance. To run two copies you copy the whole machine's configuration — and pray you remember every difference.
DIFFICULT ROLLBACKUninstalling version 2 means restoring files, config, and the runtime state of the machine. Rollback becomes archaeology instead of one command.
THESIS

Containers solve packaging: the code, the runtime and the libraries travel as one unit, so "it runs on my machine" becomes "it runs anywhere a container runtime exists." That is the whole win — and it is a big one. Everything else in this page is about a different problem.

SECTION 02 — THE FOUR WORDS

What Is a Container?

Four words, one flow. No commands needed.

WORD PLAIN ENGLISH WHY IT MATTERS
Dockerfile The recipe: "put the compiled app here, add the runtime there, expose this port, run this command." A text file the build reads. It is code. Versioned, reviewed, reproducible — the environment becomes part of the repository instead of tribal knowledge.
Image The packaged result of the recipe: the app + its runtime + its libraries, frozen as read-only layers. Never changes once built. Immutable = testable. The image you tested in CI is exactly the image that runs in production — the mismatch problem is gone by construction.
Registry The library where images are stored and versioned (Azure Container Registry, Docker Hub, ECR). One copy, many machines. Pull the same version anywhere: local, staging, prod, another region.
Container A running instance of an image — a process with its own filesystem view, network and resource limits. Start one, or fifty, from the same image. This is where scaling and healing happen: containers are cheap to start, replace and duplicate.
THE ONE-LINE TEST

Image = what it is. Container = what is running. You can have a hundred containers from one image, and — because the image is immutable — every one of them is identical. That identity is the entire point.

SECTION 03 — THE RIGHT TOOL

Containers vs Virtual Machines

They look similar. They are different tools for different problems.

AREA CONTAINER VIRTUAL MACHINE
Startup Seconds — the host OS is already running. Minutes — a whole OS must boot.
Resource usage Light — they share the host kernel; no duplicated OS per unit. Heavy — each VM runs its own full OS, doubling memory for the same workload.
Isolation Process-level — kernel is shared, so isolation is weaker at the security boundary. Strong — a separate kernel per VM; a breach of one does not reach the host's kernel.
Scaling Cheap and fast — adding a unit is milliseconds and a few megabytes. Slower and costlier — each unit is an operating system.
Operating system Shares the host's kernel (each container is a package of app + libraries, not an OS). Each VM owns a complete guest OS.
Typical use Applications, APIs, workers, microservices — where you want many small cheap units. Legacy apps needing a full OS, different OS families side by side, hard isolation requirements.
THE RULE

VMs give you strong isolation at high cost per unit. Containers give you cheap light units at slightly weaker isolation. For .NET services: containers, almost always. For "this legacy app needs Windows Server 2016 and nothing else will do": a VM, gladly. The choice is the trade, not the trend.

SECTION 04 — THE .NET VIEW

Docker for an ASP.NET Core Application

No Dockerfile required to think about it. The flow and the five things that change — that is what an architect reasons about.

CONFIGURATIONConfig leaves the image. The image is immutable; the environment provides the values — via environment variables, config files mounted from outside, or a platform's config service. Never bake a URL or a flag into the image.
ENVIRONMENT VARIABLESThe standard injection channel: ASPNETCORE_ENVIRONMENT, connection strings (references, not values), feature flags. One image, many configurations — that is the point.
SECRETSNever in the image, never in the layers, never in the repo. Secrets arrive at runtime — environment variables, mounted secrets, or the platform's secret store (Day 8's Key Vault). The image is public by design; it must contain nothing secret.
LOGGINGOne container is ephemeral — its filesystem disappears with it. Logs go to stdout/stderr and are collected by the platform, not written to a local file you will lose when the container restarts.
PERSISTENT DATAThe container has no memory. Anything that must survive a restart — files, uploads, the database itself — lives outside on a volume or in a service (Blob, Azure SQL, Redis). The rule from Day 8, now inside the container world: state never lives in the unit of compute.
WHAT ACTUALLY CHANGES

Nothing about your C# logic changes. What changes: the environment is now code (the Dockerfile), the unit is disposable (restart any container, any time), and everything you were not supposed to do anyway — hardcoded config, local files, machine-specific state — becomes physically impossible. That is the quiet win architects like.

SECTION 05 — THE REAL QUESTION

Why Do I Need Kubernetes?

Containers solved packaging. Containers did not solve management. The moment you run forty of them in production, eight ordinary questions appear — and that is the entire case for orchestration.

MANAGEMENT NEED WHAT HAPPENS WITHOUT IT
Many containers Forty units deployed by hand, in a sequence that only one person remembers.
Scaling Traffic rises; somebody manually starts five more containers and hopes the load balancer notices.
Restarting failed containers A container dies at 3 a.m.; it stays dead until a human looks at the dashboard.
Traffic distribution Every new container needs a load-balancer entry — by hand, again.
Deployment Replacing version 1 with version 2 is a manual sequence with a window of downtime.
Rollback Version 2 is buggy; restoring version 1 is another manual sequence — if the old image was even kept.
Service discovery Service A needs Service B's address; containers get new addresses when they restart. Someone must maintain the map.
Health checks "Is the container running?" is a different question from "is it actually serving requests?" Nobody asked the second one.
THE BRIDGE

Each question alone has a manual answer. Together, they are a full-time job — and the answers must be repeated, automated and reliable. That is what orchestration is: the automation of these eight questions. Kubernetes is the most famous orchestrator; it is not the only one, and it is not the answer to a system that has not asked these questions yet.

SECTION 06 — THE TEN WORDS

Kubernetes in Simple English

No internals. Ten concepts, each with a job and an example — enough for any architect conversation.

CONCEPT WHAT IT DOES WHY IT MATTERS SIMPLE EXAMPLE
Cluster The whole managed system — one control plane plus the machines that run your work. The unit you pay for and the boundary of a region. "We have one cluster in West Europe."
Node A machine (VM) inside the cluster that runs containers. Node count = capacity. A dead node means work moves to the others. 3 nodes, each with 4 vCPU.
Pod The smallest unit of work: one or a few containers that run together on a node. Pods are ephemeral — they are born, die, and are replaced. The orchestrator counts pods. 4 pods running the API, each = 1 container.
Deployment The declaration: "I want 4 replicas of this image, version 3." It is the desired state. The cluster's job is making reality match it — automatically. "Keep 4 API pods running; roll out v3 when I say so."
Service A stable address in front of a set of pods, so callers stop chasing pod addresses. Pods come and go; the Service name stays. That name is the contract. http://orders-api always works.
Ingress The front door: routes external traffic by URL path to Services. One public entry, clean routing — the Day 8 gateway idea, native to the cluster. /api/orders → orders Service.
ConfigMap Non-secret configuration injected into pods as env vars or files. Config leaves the image; the image stays immutable. API URLs, feature flags.
Secret Same as ConfigMap, for things that must not be readable. Secrets are mounted, not baked — and never in the image. DB passwords pulled from the platform vault.
Health check Two probes: "is the process up?" and "is it serving requests?" The second probe is what actually saves you — a process can be alive and useless. Liveness = startup OK. Readiness = DB reachable.
Auto scaling Adjust pod count on a signal — CPU, memory, queue depth, or requests. This is the answer to "what happens when traffic 10×s" inside the cluster. 4 pods → 40 pods when CPU crosses 70%.
THE ONE SENTENCE

Kubernetes is a loop: you declare the desired state (Deployment, Service, scaling rule), and the cluster continuously compares it to reality and repairs the difference. A dead pod is replaced. A new version is rolled out. Traffic is routed. That loop is the entire product.

SECTION 07 — THE LOOP

How Kubernetes Keeps the App Running

POD CRASHES

What happens in the next 30 seconds

DETECTThe readiness probe fails → the Service stops sending traffic to that pod. The liveness probe fails → the orchestrator kills it.
REPLACEPods are declared, not owned: "4 replicas" stays true, so a new pod starts from the same image on the same node (or another one).
⇒ HEALING IS AUTOMATIC — IF THE HEALTH CHECK IS HONEST. A POD WITH NO READINESS PROBE IS A POD YOU CANNOT PROTECT.
TRAFFIC INCREASES

Scaling the application

SIGNALCPU or memory crosses the threshold (say 70%), or queue depth rises.
ACTIONMore pods. 4 → 10 → 50. Each carries the same immutable image; the Service distributes across them.
⇒ APP SCALING = MORE PODS (CHEAP, FAST). CLUSTER SCALING = MORE MACHINES (THE EXPENSIVE PART).
NEW VERSION

Rolling deployment of v2

ACTIONThe Deployment is updated to image v2; pods are replaced gradually, health-gated.
GATEA pod that fails its readiness probe halts the rollout — the bug never reaches all traffic.
⇒ DEPLOY AND ROLLBACK BECOME ORDINARY OPERATIONS, NOT EVENTS.
NODE FAILS

The machine dies

DETECTHeartbeats stop; the node is marked unhealthy.
ACTIONSIts pods are recreated on healthy nodes — one cluster, no single machine matters. Replicas across nodes are why 3 nodes beat 1 big node.
⇒ NODE FAILURE IS A NON-EVENT — IF REPLICAS ARE SPREAD AND THE APP IS STATELESS (DAY 2'S RULE, STILL TRUE).
SECTION 08 — TWO LEVERS

Scaling the App vs Scaling the Cluster

Two different levers, two different bills. Architects confuse them constantly — and the bill teaches the difference.

Scaling the application

More pods

Add containers from the same image: 2 pods → 10 → 50. This is the cheap lever — seconds to start, fine-grained, and it is exactly what the autoscaler does when CPU rises.

Scaling the cluster

More machines

Add nodes — bigger or more VMs — so the pods have somewhere to land. This is the expensive lever: machines cost money whether they are busy or not, and node pools are monthly commitments.

SIMULATOR — 10,000 REQUESTS PER MINUTE AT THE API

CAPACITY—req/min at current pods
SHORTFALL—req/min unserved
SCALES TO—pods the autoscaler would create
CLUSTER NODES—at ~10 pods per node
THE WORKED EXAMPLE

2 pods → 10 → 50. Each pod handles ~500 req/min. At 1,000 req/min: 2 pods, done. At 10,000: 20 pods needed — the autoscaler adds them in minutes. At 100,000: 200 pods — and now you need the machines to hold them, which is the cluster-scale decision. Pods are where traffic is absorbed; nodes are where capacity is paid for. Know which lever you are pulling — in the design and in the interview.

SECTION 09 — THE COMPARISON

App Service vs Container Apps vs AKS (vs ECS/EKS)

The most asked comparison in interviews. Five platforms, one table — and the rule that ends the argument.

PLATFORM EASE OF USE CONTROL OPERATIONAL EFFORT SCALING BEST USE CASE
Azure App Service Highest — deploy a container (or plain code) and go. Low — the platform decides a lot. Lowest — nearly serverless for the team. Autoscale by rules; coarse but simple. APIs, web apps, one or a few deployables, small to mid teams.
Azure Container Apps High — containers without a cluster. Moderate — container-level control, no Kubernetes API. Low-to-moderate. Scale to zero and per-revision scaling built in. Containerised services and background workers that want scaling without Kubernetes.
AKS Lowest — a learning curve and a cluster to babysit. Highest — full Kubernetes control. Highest — upgrades, nodes, networking, monitoring. Everything: pods, nodes, custom autoscaling. Many services, platform-engineering needs, teams that live in Kubernetes.
AWS ECS High — AWS's simpler container service. Moderate. Low-to-moderate. Good, service-level. The AWS equivalent of Container Apps: containers on AWS without EKS.
AWS EKS Lowest (Kubernetes). Highest. Highest. Full. Same as AKS, on AWS.
WHY AKS/EKS MUST NOT BE THE DEFAULT

Because the choice is not "how powerful" — it is how much operations can the team afford. Kubernetes is a platform you operate: upgrades, node failure, networking, monitoring, capacity. If the requirement can be satisfied by a managed platform — and for most applications it can — the cluster is not an upgrade, it is a second job. Power you are not using is cost you are still paying. The interviewer is listening for exactly this sentence.

THE DECISION RULE

Try App Service first. Reach for Container Apps when you need containers without the cluster. Reach for AKS when you need Kubernetes itself. Each step up must be justified by a requirement, not by ambition.

SECTION 10 — THE HONEST SECTION

When NOT to Use Kubernetes

Kubernetes solves real problems — and it creates real operational complexity. List the problems you have; if the list does not match the second column below, the complexity is not justified. Ten situations where the answer is "no thank you":

SITUATION WHY KUBERNETES IS OVERKILL WHAT TO USE INSTEAD
Small application (1–2 services) You have one deployable and one database. Orchestration manages many; you do not have many. App Service.
Small team (2–5 engineers) The team must now run the platform, not the product. Every hour on node upgrades is an hour off features. App Service or Container Apps.
Low traffic No scaling problem → autoscaling buys nothing. You are paying for a control plane to manage two pods. One or two App Service plans.
Few services Service discovery and orchestration solve "many things, many addresses." With three services, the map fits on a napkin. App Service + simple config.
Simple deployment A rolling deploy via the platform's slots is already smooth. The cluster adds ceremony, not capability. Deploy slots, CI/CD to App Service.
No advanced orchestration need No custom schedulers, no node tuning, no platform team. The extra control has no buyer. Managed containers.
No team member knows Kubernetes You have bought a platform nobody can operate — the worst version of an investment. Start managed; learn later if needed.
Regulated environment with strict isolation Multi-tenant cluster security, network policies and audit trails are real work. A per-service managed host may be simpler to prove compliant. Isolated App Service plans / VMs.
Budget-constrained The cluster bill runs 24/7 for capacity used 4 hours a day. Serverless Functions, scale-to-zero.
Monolith, one deployable, modest scale Everything the cluster offers is available from the platform, cheaper. App Service with autoscale.
THE HONEST TRADE

Kubernetes buys: automated healing, fine-grained scaling, rollouts, and a portable platform. It charges: a team that knows it, a monthly bill for idle capacity, and a permanent operational tax — upgrades, node pools, networking, monitoring, incident complexity. Both sides of the ledger are real. The mistake is counting only the first column.

SECTION 11 — WHEN IT EARNED ITS BILL

When Kubernetes Makes Sense

Eight cases, each with the reason. Each one is a queue in a different costume: the requirement exists, so the complexity is payment for it.

1

Many services

REASON20+ services with independent deploys. Orchestration, service discovery and rollout coordination stop being nice and become load-bearing.
2

Large production workloads

REASONHigh traffic, many replicas, aggressive autoscaling — the fine-grained control near the platform's ceiling becomes worth its cost.
3

Frequent deployments

REASONTen releases a day. Rolling updates, canaries and instant rollbacks are exactly what the orchestration loop provides.
4

Multiple environments that must match

REASONSame cluster machinery (or the same charts) across dev / staging / prod means environments cannot drift — the mismatch problem from Section 1, solved again.
5

Advanced scaling needs

REASONCustom metrics (queue depth, response time), per-service scaling, scheduled bursts — beyond what a simple autoscale rule offers.
6

Large engineering team

REASONTwenty engineers, five squads, one product: shared infrastructure with per-team boundaries is a real coordination problem that the cluster's namespaces and quotas answer.
7

Strong container control required

REASONCustom images, sidecars, init containers, node-level tuning — the platform's abstractions are too coarse for the requirement.
8

Platform engineering requirements

REASONThe company has made Kubernetes its internal standard — every team ships the same way, with the same tooling, retrained once. That is an organizational decision, and it is a legitimate one.
THE PATTERN IN ALL EIGHT

Each case is a measured requirement: many services, high deploys, big team, hard scaling. Not "someday maybe." If you can point at the trigger — "we have 12 services and 3 squads" — the cluster is justified. If the trigger is "it is powerful," it is not.

SECTION 12 — BEFORE PRODUCTION

What an Architect Must Consider

Thirteen concerns, one line each. Not implementation — the checklist you use before anyone says "ship it."

HEALTH CHECKSLiveness (is it alive?) and readiness (can it serve?). A pod with no readiness probe is a pod you cannot protect.
LOGSStructured, with correlation ids, to stdout. Ephemeral containers lose local files; the platform collects streams, not files.
MONITORINGMetrics per pod and per service: request rate, p95, errors, resource use — plus the platform metrics for the cluster itself.
SECRETSMounted from the platform's store, never in the image. The image is public by design.
CONFIGURATIONConfigMaps/secrets for what varies; nothing environment-specific baked into the image.
NETWORKINGIngress rules, service-to-service routing, and network policies where the security model demands east-west isolation.
STORAGEWhat is ephemeral (fine) vs what must persist (a volume or an external service — Day 8's rule: state never lives in the unit of compute).
SCALINGAutoscale rules with sane minimums and maximums. The minimum protects latency; the maximum protects the bill.
SECURITYLeast privilege on the image, no root, resource quotas per namespace, and the platform's managed identities for service-to-service calls.
DEPLOYMENTStrategy chosen per service, health-gated, with the rollout failure handled automatically.
ROLLBACKThe old image is kept, versioned, and one command away. Tested, not assumed.
BACKUPContainers need no backup — but the data behind them does. This is Day 3/8's backup story: the cluster is disposable; the data is not.
COSTCluster capacity is a 24/7 bill. Right-size nodes, scale to zero where possible, and know what idle costs per month.

1

A container crashes

IMPACTNone — other replicas serve.
RESPONSEProbe fails → pod replaced from the same image in seconds. Honest health checks are the difference between "recovered silently" and "half traffic lost until someone looks."
2

A pod crashes

IMPACTSmall — one replica gone. The Service keeps routing to the rest.
RESPONSEDesired state says "4 replicas"; the cluster counts 3 and starts a fourth. The loop repairs it, automatically, every time.
3

A node fails

IMPACTCapacity drops by a node's worth; its pods go down with it.
RESPONSEWorkloads are rescheduled on healthy nodes. This is why replicas are spread across nodes — and why a cluster of several small nodes beats one big one. Alert on node health.
4

Traffic becomes 10×

IMPACTLatency grows; pods saturate.
RESPONSEAutoscaler adds pods on the signal. If pods are finite, the next lever is nodes — and the third is asking why the database is not the bottleneck (Day 2, still true inside the cluster).
5

New deployment has a bug

IMPACTEscalating errors on the new version.
RESPONSERollout halts on failed health gates; the cluster keeps old pods serving. One command rolls back to the previous image. This is why rollback is designed before release day, not during it.
6

Container can't reach the database

IMPACTThe pod is alive and useless — the classic readiness trap.
RESPONSEThe readiness probe fails, so the Service stops routing to the pod; surviving pods carry on; the app retries the connection. Liveness would only restart the loop — readiness is what protects the user.
7

Redis becomes unavailable

IMPACTDegraded reads for the app.
RESPONSEThe Day 5 story, unchanged: rate-limited DB fallback, serve-stale, hit-ratio alarm, warm-up. The cluster restarts pods fine — it cannot fix a cache outage for you.
8

External API fails

IMPACTPayment or notification failures.
RESPONSEThe Day 4 rules: timeout, retry with backoff, dead-letter, honest state to the user. The cluster restarts pods; the design handles the dependency.
THE PATTERN

The cluster handles container and node failures beautifully — and handles nothing else. Database outages, cache outages, vendor failures: all still your design's job. Every failure scenario on this page was already covered by Days 2–8. Containers changed the machinery, not the rules.

SECTION 14 — THE RELEASE

Deployment Strategies

Three ways to ship version 2 of a .NET API. Watch the traffic move.

one at a time each new pod must pass health before the next
HOW IT WORKS BENEFIT RISK SUITABLE WHEN
Pods are replaced gradually — one per wave, health-gated. No extra capacity needed. Zero downtime if probes are honest. Old and new versions run together briefly; a subtle bug can hit some users before the rollout is stopped. The default for most services. A bug is fully rolled back in one command.
HOW IT WORKS BENEFIT RISK SUITABLE WHEN
Two full environments; traffic flips entirely to the new one. Instant switch, instant rollback. No mixed-version state during the release. Double the running capacity for the release window. The "switch" needs a fast DB-compatible version pair. Big-bang risks: a new UI, a major API change, a release you want to watch in full before committing.
HOW IT WORKS BENEFIT RISK SUITABLE WHEN
A small slice of traffic hits the new version; watch real metrics; widen gradually. Real-world validation before full exposure. A bug affects the smallest possible audience. Slower rollout. Needs good metrics and the discipline to act on them — a canary nobody watches is just a v2 that 10% of users see. High-risk, high-value changes where real traffic is the only honest test.
THE CHOICE, IN ONE LINE

Rolling for routine releases · blue-green when the switch must be atomic and reversibility perfect · canary when the cost of being wrong is highest. The platforms (App Service slots, Container Apps revisions, Kubernetes rollouts) all implement these — the architect chooses the strategy, the platform executes it.

SECTION 15 — CASE STUDY

The SaaS, Three Ways

The same multi-tenant e-commerce SaaS. Three deployment options, honestly compared — then a reasoned recommendation that is not "AKS because it scales."

DIMENSION OPTION A · APP SERVICE OPTION B · CONTAINER APPS OPTION C · AKS
Architecture App Service plan running the API (and a second plan or Function for workers). Container Apps environment: API + worker, each its own app/revision. A cluster: deployments, services, ingress, workers as separate workloads.
Benefits Least operations. Slots for blue-green. Autoscale. Your team ships features, not infrastructure. Containers without the cluster; scale-to-zero; per-revision rollouts; background workers first-class. Full control; fine-grained autoscaling; canaries; the standard platform if the team lives in K8s.
Risks Coarse scaling; platform limits hit sooner at very high traffic; less control over the image environment. Newer platform; some Kubernetes-style control pleasantly missing. You operate it: upgrades, nodes, networking, monitoring, capacity. A team and a monthly bill.
Operational effort Low — deploy and go. Low-to-medium. High — platform engineering is a job now.
Cost Predictable; scale rules control the bill directly. Per-use friendly; scale to zero saves at night. Cluster nodes run 24/7; idle capacity is a monthly number.
Select it when The API and a few workers are the whole story, and the team is small. You want containers and real background workers, without operating a cluster. Many services, many squads, frequent deploys, custom scaling — or Kubernetes is already the company standard.
THE RECOMMENDATION — WITH THE REASON

Start with Option A and keep B in the pocket. At this scale — one ASP.NET Core API, background workers, Redis, Service Bus, Azure SQL — the honest architecture needs capability, not a control plane. App Service gives autoscaling, slots, and a cost that matches traffic; the workers are the one thing it does not do brilliantly, which is exactly where Container Apps earns its place. AKS enters on a written trigger, not on ambition.

Triggers, written now: 1) the platform's autoscale ceiling is hit and measured — not predicted. 2) three or more independent deployables with separate release cadences. 3) a need for canary or custom-metric scaling that the platform cannot express. 4) the company standardises on Kubernetes. Until one fires, the cluster is a bill with a control plane attached.

INTERVIEW ANGLE

Say it like this: "For these requirements I would use App Service with Container Apps for the workers. Kubernetes would solve a problem I do not have yet — and I can name the triggers that would make me revisit it." That answer is the whole day.

SECTION 16 — DECISIONS

10 Questions Before Choosing Kubernetes

Q1

How many services do we have?

WHY IT MATTERSOrchestration solves many-things coordination. One or two deployables do not have the problem.
POSSIBLE DECISION1–3 services → managed platform. 15+ with independent releases → the conversation changes.
Q2

How much traffic, and how spiky?

WHY IT MATTERSAutoscaling is only valuable when scaling is actually needed.
POSSIBLE DECISIONModest traffic → platform autoscale. Big spikes with custom metrics → cluster.
Q3

How often do we deploy?

WHY IT MATTERSFrequent deploys are where rollouts, canaries and instant rollback pay rent.
POSSIBLE DECISIONWeekly → slots/revisions are enough. Ten a day → rollouts and health-gated deploys become valuable.
Q4

Does the team know Kubernetes?

WHY IT MATTERSAn unoperated cluster is the most expensive way to run a service.
POSSIBLE DECISIONNo → managed, and learn when the platform stops being enough.
Q5

What level of control is actually required?

WHY IT MATTERSSidecars, init containers, node tuning, custom schedulers — each has a buyer; if none exist, the control has no value.
POSSIBLE DECISIONNo exotic needs → managed containers. Realised needs → cluster.
Q6

Can a managed platform solve the problem?

WHY IT MATTERSThe question is not "is Kubernetes powerful" but "is anything missing from the simpler option."
POSSIBLE DECISIONIf nothing is missing, nothing is justified.
Q7

What is the operational cost — honestly?

WHY IT MATTERSUpgrades, nodes, networking, monitoring, incident complexity — a permanent tax per month.
POSSIBLE DECISIONWrite the tax down. If the bill exceeds the benefit, the answer writes itself.
Q8

What happens when the platform team is unavailable?

WHY IT MATTERSCluster ownership needs a grown-up on call. A cluster nobody can run is a vendor with no phone number.
POSSIBLE DECISIONNo owner → managed platform, today.
Q9

What breaks at 10× — and would K8s have fixed it?

WHY IT MATTERSUsually the answer is the database or a vendor — and the cluster fixes neither (Day 2, still true).
POSSIBLE DECISIONIf the 10× bottleneck is not the compute, don't buy compute.
Q10

Is Kubernetes the company standard?

WHY IT MATTERSA platform decision can be organisational: one shared way to ship, one onboarding, one security model.
POSSIBLE DECISIONIf it is the standard, the argument is over — the question becomes how well you use it.
THE MAIN LESSON

All ten questions are requirement questions, not technology questions — and that is the point. Kubernetes is justified by service count, deploy frequency, team size and control needs. When those numbers exist, the platform is the answer. When they do not, it is the question nobody asked.

SECTION 17 — HONEST LIST

10 Container & Kubernetes Mistakes

01

Using Kubernetes because it is fashionable

"Senior architects use AKS" — so a two-service app gets a cluster, a node pool, and an operations bill nobody budgeted.

Requirement first. The ten questions, answered out loud, before the cluster appears.

02

Running databases inside containers without a reason

The database is state; the container is disposable. State in a disposable unit means data loss on restart — and a DB you must now back up, patch and operate yourself.

Managed database service (Azure SQL, Cosmos, managed Postgres). Containers for compute; managed services for state.

03

Ignoring operational complexity

The diagram shows six boxes and a cluster; the calendar shows a team that now upgrades nodes and argues about networking.

Count the complexity honestly before committing — it is a permanent tax, not a setup cost.

04

No health checks

A pod with a dead readiness probe keeps serving traffic to a broken process — the cluster thinks everything is fine.

Liveness (is it alive) and readiness (can it serve). A readiness probe that checks the database is worth its weight.

05

No resource limits

One hungry pod can starve the node, and "no limit" is an invitation to a noisy neighbour — or a whole node going down.

Requests and limits on every pod, per namespace where teams share a cluster.

06

No monitoring

The cluster restarts pods silently — beautiful — until the tenth restart in a minute is an outage nobody's dashboard saw.

Application metrics + platform metrics + restarts and crash-loop alerts. A restart is a signal, not a secret.

07

No rollback plan

Version 2 is bad, and the "plan" is a conversation about how to get version 1 back.

Tag every image, keep the previous one, and one-command rollback — tested in staging before release day.

08

Hardcoding secrets

In the image, in the chart, in the repo. The image is public by design — a secret in it is a secret published.

Secrets mounted at runtime from the platform's vault. The image contains nothing secret, ever.

09

Ignoring networking

Services reach each other "somehow" — until a redeploy changes an address, or everything is exposed because nobody wrote an ingress rule.

Ingress first (one public door), service-to-service names, and network policies where isolation is required.

10

Ignoring cloud cost

The cluster runs 24/7 and the workload peaks 4 hours a day. The gap is a monthly line item.

Scale pods to zero where possible, rightsize nodes, schedule the idle, and name the idle cost out loud.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 10

Five rules. Not about containers — about the difference between solving a problem and paying for prestige.

01

Containers solve packaging. They solve nothing else.

Different environments, dependency drift, inconsistent deploys — solved. Scaling, failure, traffic, and the database: not solved. Do not sell containers as a scaling strategy.

02

The image is immutable. The container is disposable.

Config arrives at runtime, secrets arrive at runtime, state lives outside. Everything that made deployments unpredictable becomes impossible by design.

03

Kubernetes is a loop, not a feature.

Declare the desired state; the cluster repairs the difference. But the loop is only as good as your probes — and it fixes nothing about your database, your cache or your vendor.

04

Pods are cheap. Nodes are a bill.

Scaling the app is adding containers. Scaling the cluster is adding machines — a 24/7 cost. Know which lever you are pulling, always.

05

AKS is not a prize. It is a second job.

Every cluster needs an owner, a budget and a reason. If you cannot write the trigger that justifies it, the answer is the managed platform. That restraint is the senior answer.
