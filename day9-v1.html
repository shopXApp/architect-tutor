SECTION 01 — THE MINDSET

Cloud Architecture is Not a Service Count

The trap of the cloud round: "how many managed services can you name?" The question that matters is the same one from Week 1: what does the requirement need, and what is the simplest thing that delivers it?

BUSINESS NEEDOne sentence for the value. The cloud serves it; it does not define it.
TRAFFICPeak RPS, concurrency, growth. The Day 2 numbers — AWS just names the tiers.
PERFORMANCEWhat must be fast, what may wait, and what the p95 budget is.
AVAILABILITYThe number, not the slogan — it decides AZs, regions and the bill.
SECURITYWho may do what, where secrets live, and what data leaves the boundary.
SCALINGWhat scales out, what scales up, and the triggers — same rules as always.
COSTA monthly number per design, said out loud. Cost is a requirement.
OPERATIONAL EFFORTEvery service you pick is a bill of operations — patching, monitoring, waking up.
FUTURE GROWTHWhat may change in 12 months, and what trigger flips the design.
THE TWO SENTENCES THAT FRAME THE DAY

Azure is not automatically better because you know Azure. AWS is not automatically better because it is popular. The architecture decides the service — and the cloud decides nothing. An interviewer testing you on AWS is testing the same thing they tested on Azure: can you read a requirement, name the simplest service that fits, and defend the trade-off?

SECTION 02 — THE TOOLKIT

AWS Core Services, 90 Seconds Each

Service cards. What, when, when-not, benefit, limitation — no CLI, no configuration.

Compute

EC2A virtual machine you operate. Use: legacy apps, custom OS or networking needs, anything requiring full server control. Don't use: modern web apps — newer options are less work. Benefit: total control. Limit: you patch, back up and babysit it.
ECSRuns containers without Kubernetes — EC2 instances or Fargate (serverless containers). Use: containerised services and workers, the AWS answer to Azure Container Apps. Don't use: a single simple web app, or when you need Kubernetes' ecosystem. Benefit: containers with managed orchestration. Limit: its own learning curve, less ecosystem than EKS.
EKSManaged Kubernetes — the AWS twin of AKS. Use: many services, custom infrastructure, a team that lives in Kubernetes. Don't use: because it is powerful. Benefit: the whole Kubernetes world, managed control plane. Limit: you operate the cluster — the same bill as AKS.
LAMBDAEvent-driven code that runs per invocation. Use: queue triggers, webhooks, short glue jobs, bursts that scale to zero. Don't use: long-running or stateful workloads. Benefit: pay per execution, scale to zero. Limit: cold starts, time limits, not for big applications.
ELASTIC BEANSTALKThe managed platform for a single deployable — AWS's App Service. Use: a request-driven .NET web app, one deployable, low operations. Don't use: containers needing fine control or event-driven bursts. Benefit: least operations, deploy and forget. Limit: less control; the platform makes opinionated choices.

Storage

S3Object storage — files, images, backups, exports. Use: anything file-like, static assets, the source of truth for content. Don't use: transactional data. Benefit: pennies, unlimited scale, versioning, web-friendly. Limit: not a database — no queries, no joins.
EBS (HIGH LEVEL)Block storage for EC2 instances — a disk attached to one machine. Use: the OS disk and data needing low-latency random access on one instance. Don't use: shared or durable application storage that must survive the machine. Benefit: fast, familiar. Limit: tied to one machine and one AZ.

Database

RDSManaged relational databases — Postgres, MySQL, SQL Server. Use: the transactional core: orders, inventory, finance, tenants. Don't use: flexible schemas or global key-based scale. Benefit: the DBA work is done; your SQL skills apply. Limit: scales vertically; horizontal is your design.
AURORARDS's high-performance engine — MySQL/Postgres-compatible with a scale-out storage layer. Use: relational workloads needing more throughput and faster failover than standard RDS. Don't use: SQL Server migrations — Aurora is MySQL/Postgres only. Benefit: better performance and 15 read replicas. Limit: engine lock-in to the MySQL/Postgres family.
DYNAMODBKey-value / document NoSQL with single-digit-millisecond reads at any scale. Use: key-based access patterns, massive throughput, flexible schemas, global tables. Don't use: relational queries or multi-table transactions as the core pattern. Benefit: scales horizontally by design, no partition to manage. Limit: you design the access pattern first — no joins, no ad-hoc queries.

Networking

VPCYour private network — subnets, routing, security groups, and the boundary between public and private. Use: every architecture. Don't use: the default "everything public" setup. Benefit: the isolation boundary that makes everything else safe. Limit: you design it — and a wrong VPC design is expensive to undo.
APPLICATION LOAD BALANCER (ALB)Layer-7 load balancer inside the VPC: routes by path, health-checks, TLS, and spreads across AZs. Use: in front of containers or EC2 within a region. Don't use: global routing (that is CloudFront) or DNS-level failover. Benefit: clean routing and automatic instance health. Limit: regional only.
CLOUDFRONTThe global CDN and edge: serves static and dynamic content from the nearest location, with WAF. Use: global users, static assets, API acceleration, TLS at the edge. Don't use: a single-region internal app. Benefit: distance stops mattering — and it is a DDoS shield. Limit: cost and an extra hop for local apps.
API GATEWAYA managed API front door: auth, throttling, versioning, and a developer surface. Use: exposing APIs to external consumers, tying to Lambda, controlling who calls. Don't use: your own front-end calling your own API. Benefit: keys, quotas, analytics out of the box. Limit: cost and latency for internal-only traffic.

Messaging

SQSThe durable queue — work that must be processed reliably with retries and DLQs. Use: background jobs, order processing, decoupling spikes. Don't use: fan-out to many listeners (SNS) or event integration (EventBridge). Benefit: the simplest reliable queue, exactly-once-ish with your idempotency. Limit: nearly-ordered, not globally ordered; no built-in fan-out.
SNSPub/sub notification — one message, many subscribers (queues, Lambda, email, SMS). Use: "something happened, tell everyone who cares." Don't use: guaranteed work processing. Benefit: fan-out in one call. Limit: it does not guarantee processing.
EVENTBRIDGEEvent routing between AWS services and your apps, with rules, filtering and schedules. Use: integration between systems, reacting to AWS events, scheduled orchestration. Don't use: plain queue work. Benefit: the hub that wires services together declaratively. Limit: another routing layer; think about it as the bus, not the workhorse.

Security

IAMUsers, groups, roles, policies — who may do what, everywhere. Use: every access decision, always, least privilege. Don't use: as an application user directory for customers. Benefit: one model for human and machine access. Limit: the most common AWS security failure is an over-broad IAM policy.
SECRETS MANAGERThe vault for connection strings, API keys, credentials — with rotation. Use: every secret. Don't use: non-secret config. Benefit: secrets leave code and repos; rotation is a toggle, not a release. Limit: still your responsibility to use it everywhere.
KMSKey management and encryption: creates and controls the keys that encrypt your data at rest. Use: encrypting S3, RDS, DynamoDB, and your own data. Don't use: as a secrets store. Benefit: encryption you can actually manage and rotate. Limit: key policies matter — a lost key is lost data.

Monitoring

CLOUDWATCHMetrics, logs, alerts, dashboards for AWS resources and your app. Use: infrastructure health and alerting on everything. Don't use: deep per-request tracing (X-Ray). Benefit: one home for platform signals. Limit: platform metrics do not tell you whether the business operation succeeded.
X-RAY (HIGH LEVEL)Distributed tracing — one request's journey through services, queues and databases. Use: when a call spans many components and you need to see the whole path. Benefit: the correlation story from Day 6, managed. Limit: sampling and configuration overhead — pair it with CloudWatch, do not replace it.
SECTION 03 — THE MAP

Azure to AWS — The Translation Table

The single most useful table on this page. These are not exact replacements — the note under each row says what differs. Use it to translate, then think.

AZURE AWS MAIN PURPOSE THE DIFFERENCE THAT MATTERS
App Service Elastic Beanstalk Managed host for one deployable Similar job, different style: Beanstalk is a platform around a deployable, App Service is a more polished app-focused product. Both are "least operations" — pick by team, not by feature list.
Functions Lambda Event-driven serverless code Nearly the same. Lambda has longer history and a bigger ecosystem; Azure Functions has richer binding integration with the Azure stack. Both pay per execution and scale to zero.
AKS EKS Managed Kubernetes Same product, two clouds. EKS is slightly more mature; AKS is more integrated with Azure services. The decision is operational familiarity, not superiority.
Container Apps ECS / Fargate Containers without Kubernetes The middle ground on both clouds. Fargate is the AWS equivalent — containers with managed scaling, no cluster to operate.
Azure SQL RDS / Aurora Managed relational database The big difference: Azure SQL is a SQL Server product; RDS supports SQL Server, Postgres and MySQL, Aurora only MySQL/Postgres. If your data is SQL Server, RDS SQL Server is your AWS home — Aurora is not an option.
Cosmos DB DynamoDB NoSQL, key-based, global scale Both are key-value/document with horizontal scale. Cosmos has multi-model APIs and tunable consistency; DynamoDB is single-model, spreadsheet-of-scale, and its access patterns must be designed first. Neither is a relational database.
Blob Storage S3 Object storage Closest match on the whole table. Both: files, images, exports, static assets. S3 has versioning and a broader ecosystem; Blob has tighter Azure integration.
Service Bus SQS Durable queue for work SQS is simpler; Service Bus has richer semantics — topics, sessions, transactions. SQS + SNS together cover much of Service Bus's ground, but with a different shape.
Event Grid EventBridge Event routing and integration Both carry news. EventBridge adds rules, filtering and event buses — closer to "the wiring hub" than Event Grid's more notification-style push.
Front Door CloudFront Global edge / CDN CloudFront is content + edge acceleration; Front Door adds global HTTP routing and origin failover. For global apps both work; the routing nuance differs.
API Management API Gateway API front door API Gateway is deeper into the AWS service mesh (auth integrations, Lambda), API Management is a fuller developer-portal product. Same job, different depth.
Key Vault Secrets Manager Secrets store Same job. Both support rotation; both should be the only home for secrets in their cloud.
Entra ID IAM / Cognito Identity Not the same thing. Entra ID is a full identity provider; AWS IAM is about permissions inside AWS; Cognito is the customer-facing auth service. Map by job: IAM for who-may-do-what-in-AWS, Cognito for app login, or keep Entra ID and federate.
Application Insights CloudWatch / X-Ray Monitoring and tracing CloudWatch is metrics and logs (like Azure Monitor); X-Ray is distributed tracing (closer to App Insights' trace view). Use both — it is the same two-layer monitoring story.
NEVER SAY "IT'S THE SAME THING"

In an interview, the sentence that wins is: "they are the closest equivalent, but the difference that matters is…" — and then one honest difference. Saying "SQS is just Service Bus" loses the point. Saying "SQS is the durable queue, Service Bus adds topics, sessions and transactions — for the order flow I would pick by which semantics my workflow needs" wins it.

SECTION 04 — THE CHOICE

AWS Compute Choices

The same lesson as Day 8, with AWS names: more control usually means more responsibility.

OPTION CONTROL OPERATIONAL EFFORT SCALING COST MODEL SUITABLE WORKLOAD
EC2 Total You patch, back up, and babysit Manual — you build it Per instance-hour, always on Legacy, custom OS or network needs
Elastic Beanstalk Little (platform-managed) Least Easy, built-in Instance-hours, simple One deployable web app
ECS / Fargate Moderate Moderate Managed scaling Per task or per vCPU-hour Containers, background workers, microservices
EKS High High — you run the cluster Autoscaling you configure Cluster + node-hours Many services, Kubernetes-native teams
Lambda Little Almost none Scale to zero, per invocation Pay per execution Event-driven bursts, glue, queue triggers

Five scenarios — which compute?

SCENARIO 1

A single ASP.NET Core API with RDS, one team, standard traffic

CHOICEElastic Beanstalk — the AWS App Service.
WHYOne deployable, request-driven. The platform handles scaling and health. EKS here is paying for a cluster nobody asked to operate.
⇒ BEANSTALK. THE SIMPLEST THING THAT WORKS.
SCENARIO 2

A queue-driven order processor with bursts, reacting to SQS messages

CHOICELambda (SQS trigger) — or an ECS/Fargate worker for longer processing.
WHYBursty and event-driven. Lambda scales with the queue and costs nothing idle; Fargate when the work is longer than a Lambda's execution window.
⇒ LAMBDA OR FARGATE — NOT A SERVER.
SCENARIO 3

Twelve microservices, three teams, independent deploys, Kubernetes-native team

CHOICEEKS — the one case where the cluster earns its bill.
WHYIndependent deploys, custom networking, and a team that already lives in Kubernetes. If the team does not, ECS/Fargate is the honest answer.
⇒ EKS ONLY WHEN THE TEAM LIVES IN IT.
SCENARIO 4

A nightly job that generates reports and sends emails

CHOICELambda on a schedule — or EventBridge scheduling a Fargate task.
WHYRuns minutes a day. Pay per execution beats an always-on instance.
⇒ DO NOT PAY FOR A SERVER THAT SLEEPS.
SCENARIO 5

A legacy Windows service with a custom driver, running on one machine

CHOICEEC2 — the only answer here.
WHYCustom OS-level requirements that no managed platform accepts. EC2 is the correct choice when the workload truly needs it — and only then.
⇒ EC2 IS NOT WRONG. IT IS JUST RARELY THE FIRST ANSWER.
SECTION 05 — DATA

RDS / Aurora or DynamoDB?

The Day 3 decision, AWS-flavoured. Six questions decide it.

  RDS / AURORA DYNAMODB
Transactions Full ACID across tables. Money-safe. Transactional within a single item, or limited transactions within one partition key.
Relationships Joins, foreign keys — the order → item → payment chain is native. Denormalise or assemble in code.
Scale Vertical, plus read replicas; sharding is your design. Horizontal by design — throughput scales with partitions.
Access patterns Any query you can express. You design the key first: single-digit-ms reads only on the patterns you planned.
Global distribution Replicas and failover exist; heavier to operate. Global tables — multi-region reads and writes built in.
Operational effort RDS and Aurora are both managed; Aurora adds performance and fast failover. Nothing to manage; you pay for provisioned capacity.

Five scenarios

1

Order processing with inventory and payment records

CHOICERDS (or Aurora) with a SQL engine.
WHYACID across the order chain is non-negotiable. DynamoDB's single-item transactions do not cover it.
2

A product catalog with different attributes per category

CHOICEDynamoDB (or a SQL JSON column).
WHYFlexible documents match a catalog where categories differ. Key-based reads on product id are the hot pattern.
3

A global app needing fast reads in 15 regions and multi-region writes

CHOICEDynamoDB global tables.
WHYMulti-region replication is built in. RDS replicas can read globally but write like a SQL database.
4

An HR system with salaries, departments and auditable reporting

CHOICERDS / Aurora.
WHYRelationships, exact values, and reports that must add up. Eventual consistency is not acceptable.
5

Millions of sensor writes per minutes, read by device id

CHOICEDynamoDB.
WHYMassive key-based write throughput is its design. RDS would struggle and cost more for this shape.
THE DECIDING SENTENCE

Connected + transactional → RDS/Aurora. Key-based + massive scale + flexible → DynamoDB. And the honest note for your stack: if the data is SQL Server-shaped, RDS SQL Server is the AWS home — Aurora is MySQL/Postgres only, and "it performs better" does not mean it takes your T-SQL.

SECTION 06 — THE PATH

AWS Networking

The flow, and why each layer exists. Same three-jobs lesson as Azure, different names.

VPCYour private network: subnets, routing, security groups. Public subnets hold the load balancer and web tier; private subnets hold the database, cache and queues. The lesson: the database does not need to be reachable from the internet.
PUBLIC VS PRIVATE RESOURCESPublic: what users must reach — the load balancer, maybe the API. Private: everything that only your app talks to — RDS, DynamoDB (via VPC endpoints), the cache, queues. If a resource is private, no attacker can reach it even with a leaked credential.
APPLICATION LOAD BALANCERThe regional door: routes by path to instances, health-checks them, spreads across AZs, terminates TLS. In the case of one unhealthy instance, the user never notices.
CLOUDFRONTThe global door: static content and API acceleration from the nearest edge, WAF, DDoS protection. Used when users are far from the region — or when you want the origin protected from the internet.
API GATEWAYThe developer door: throttling, keys, versioning, and the natural front for Lambda-based APIs. Overkill for an internal web app; the right tool for a public API surface.
THE ONE-LINE DIFFERENCE

CloudFront reaches the user. ALB routes inside the region. API Gateway lets external developers in. VPC keeps everyone else out. Four answers to four different questions — and the interview is deciding which question you have.

SECTION 07 — SECURITY

AWS Security — Identity → Permission → Secret Protection

The Day 8 security story, AWS-named. The chain: an identity (IAM role) carries permissions (policies), and secrets live in a vault (Secrets Manager), encrypted with keys (KMS) — none of it in code.

IAM — USERS, GROUPS, ROLES, POLICIESThe permission model. A role is an identity that a service assumes: the ECS task assumes a role that grants it exactly: read Secrets Manager, write DynamoDB, send to SQS. A policy states the permissions in plain JSON. Least privilege is the whole game.
ROLES OVER ACCESS KEYSAn access key is a credential that lives forever and gets copied. A role is an identity the platform grants to a service, with no key to leak. Rule of thumb: services use roles; humans use federated login; nobody uses long-lived keys.
SECRETS MANAGERThe vault: connection strings, API keys, passwords — stored, encrypted, rotated on a schedule, and fetched at startup (or refreshed periodically) by the app. Rotation is a vault operation, not a release.
KMSKey management and encryption. Secrets Manager uses KMS to encrypt secrets; S3, RDS and DynamoDB use KMS keys for encryption at rest. You control the keys, you control the data.
WHY NO SECRETS IN CODE

The practical example: a connection string in an appsettings file, committed once, is a credential that is now in the git history, in the CI logs, in the backups, and in any screenshot ever taken. Even if you remove it today, the history keeps it alive. Secrets Manager + IAM roles + KMS exists so that the worst possible leak contains nothing worth stealing — and any architect interview is listening for exactly that sentence.

SECTION 08 — MESSAGING

SQS, SNS and EventBridge

Day 6's two questions, three AWS answers: SQS carries work. SNS tells many. EventBridge wires systems together.

  SQS SNS EVENTBRIDGE
Job Carries work — one consumer processes reliably, with retries and DLQs. Carries news — one message, many subscribers. Wires systems — routes events with rules, filters, and schedules.
Order created → The worker queue: payment, inventory, notification — the reliable path. Fan-out to inventory, notification, analytics — "everyone who cares." The integration hub: "order created" triggers workers, cross-service patterns, scheduled jobs.
Reliability Retries, DLQ, visibility timeout — the Day 6 story. Best-effort delivery to subscribers; durability is the receiver's job. Targeted delivery with retries per rule.
When to use One consumer must do the job reliably. Many consumers must hear about the fact. Multiple systems must react to events, or events need routing rules.
Simpler alternative A direct API call — when the caller needs the answer now, or the work is a quick read. A queue over a two-second lookup is ceremony, not architecture.
THE ONE-LINE RULE

Work → SQS. News → SNS. Integration → EventBridge. And when the answer is needed now — a direct call. One order event can do all three at once; the trick is knowing which lane is which.

SECTION 09 — STAYING UP

AWS Reliability and Scaling

Four problems, four mechanisms — the Day 2 playbook with AWS names.

PROBLEM MECHANISM WHAT IT ACTUALLY DOES
More application traffic Auto Scaling Adds or removes instances on CPU, request count or queue depth. Stateless app → the fleet grows and shrinks with demand, and the bill follows the traffic, not the forecast.
Server failure Multiple AZs + ALB health checks The load balancer routes around an unhealthy instance — usually before humans notice. One AZ down → the other carries on. The app's statelessness is what makes this free.
Database failure RDS Multi-AZ + read replicas Multi-AZ gives a synchronous standby that takes over in ~a minute (the failover drill, Day 8, AWS edition). Read replicas carry the read load and keep reports off the writer.
Queue backlog SQS depth + autoscaling workers Workers scale on queue depth: 100 messages → 2 workers, 10,000 → 20. The backlog is a number with a drain rate, not an incident.
THE ARCHITECT'S READING

Every mechanism in this table is reactive to a metric. That is the real point: none of it works without the metric. Auto Scaling needs CPU or depth; Multi-AZ needs a tested failover; the ALB needs health checks. The architecture is the metric, the mechanism, and the tested recovery — in that order. Same as Week 1, same as Day 8, now with AWS names.

SECTION 10 — THE CHOICE OF CLOUD

Eight Situations: Azure / AWS / Either

The interview question you cannot dodge in 2026. The lesson in front of every row: cloud choice is a business and architecture decision, not a technology preference.

1 · MICROSOFT ENTERPRISE

An enterprise with Exchange, Active Directory, Office 365, and a large Microsoft licensing estate

CHOICEAzure.
WHYThe existing identity and licensing estate is the asset. Entra ID, SQL Server managed, and the Microsoft support relationship make Azure the path of least resistance — and lowest total cost.
2 · HEAVY .NET

A pure .NET shop with SQL Server everywhere

CHOICEAzure (with AWS as a correct alternative for RDS SQL Server).
WHYThe tooling, templates and team familiarity are Azure-side. AWS runs .NET fine and RDS supports SQL Server — but the friction and the team's edges favour Azure.
3 · AWS-NATIVE TEAM

A team of 20 engineers who have spent a decade in AWS

CHOICEAWS.
WHYExperience is the cheapest infrastructure you will ever buy. The time-to-delivery advantage of a team that does not have to relearn the catalogue dwarfs any service-level nuance.
4 · SPECIFIC MANAGED SERVICE

"We need [a specific service] — the best implementation of it"

CHOICEThe cloud that has it — AWS for Lambda-scale serverless, Azure for Fabric or Cognitive services, either for most.
WHYOne genuinely differentiated service can tip a choice, if it is on the critical path. Then the rest of the design follows that cloud.
5 · MULTI-CLOUD

A business strategy of not being locked to one vendor

CHOICEEither — but designed for portability.
WHYContainers and managed databases are portable; deep platform integrations are not. The honest truth: multi-cloud is a business decision with a real engineering cost — say it out loud.
6 · COST-SENSITIVE

A startup that must make every dollar count

CHOICEEither — with simple, cheap choices and autoscaling-to-zero where possible.
WHYAt this size the cloud matters less than the architecture. Lambda/Functions pay-per-execution and rightsized tiers beat any brand preference.
7 · GLOBAL SAAS

A consumer product with users on every continent and a single codebase

CHOICEEither — both handle global well. DynamoDB global tables vs Cosmos multi-region; CloudFront vs Front Door.
WHYThe requirement is geography, and both clouds support it. Pick the one the team can operate, then build the region story from the Day 8/9 checklist.
8 · COMMITTED

The company already has three years of tooling, pipelines and spend in one cloud

CHOICEThe cloud you are in.
WHYMigrating to the "better" cloud is a re-platforming project with real cost and real risk. Unless there is a specific, named failure in the current cloud, the honest architect says: stay, and fix the architecture instead.
THE LESSON

Cloud choice is a business and architecture decision, not a technology preference. Azure is not better because you know it, AWS is not better because it is popular. The four inputs are always: existing estate, team experience, required services, and cost — in that order.

The Same SaaS, on AWS

The Day 8 system, redesigned on AWS. For every service: why this · what problem it solves · why not another AWS service · could Azure solve it?

DIMENSION FIGURE DIMENSION FIGURE
Companies (tenants) 10,000 Concurrent users 10,000
Registered users 1,000,000 Peak requests/sec 5,000
Daily active 100,000 Clients Web + mobile
Features login · catalog · search · orders · payments · inventory · notifications · reports · audit · background processing

STEP 1

The simplest shape that could work

CHOICEElastic Beanstalk (one API) + RDS (SQL Server or Postgres) + S3 for images + CloudWatch.
WHYOne deployable, one relational database, files in S3. The Day 8 honest minimum, AWS-named.
REJECTEDEKS, microservices, DynamoDB, SQS — nothing has earned them yet.
COULD AZURE?App Service + Azure SQL + Blob + App Insights — identical design, different names.
⇒ START BORING. THE FIRST ARCHITECTURE ON ANY CLOUD SHOULD COST LITTLE.
STEP 2

Scale and protect the request path

CHOICEALB in front of an auto-scaling Beanstalk (or ECS) fleet, two AZs, health checks. Add CloudFront when users are far away or a second region arrives.
WHYThe API is stateless, so the fleet scales out on CPU or request count; the ALB routes around unhealthy instances. The web tier is replaceable.
REJECTEDCloudFront now — single region; the global edge is not yet needed.
COULD AZURE?Application Gateway + App Service autoscale — the same shape.
⇒ STATELESS FLEET + ALB + AUTOSCALE. DAY 2, AWS-NAMED.
STEP 3

Add caching

CHOICEElastiCache (Redis) — catalog, sessions, permissions, dashboard aggregates — TTLs, invalidation, cache-down plan from Day 5.
WHYThe catalog is read 50× more than written; the database is the component we protect. Redis is the shared copy across the fleet.
REJECTEDIn-process memory only — N instances, N versions of the truth.
COULD AZURE?Azure Cache for Redis — the same service family, same rules.
⇒ THE DAY 5 RULES, WITH ANOTHER BRAND.
STEP 4

Add messaging and background processing

CHOICESQS for the order flow (payment, inventory, notification, invoice) consumed by a Fargate worker or Lambda per lane. Outbox pattern, unchanged from Day 6: order + outbox row in one RDS transaction, a dispatcher publishes.
WHYThe checkout returns in ~40 ms; bursts become backlogs with numbers; failures retry then dead-letter (via a DLQ) with alerts.
REJECTEDEventBridge for the order flow — it routes news; the reliable-with-retries story belongs to SQS. SNS joins later when multiple services need to hear about orders.
COULD AZURE?Service Bus + workers — richer semantics (sessions, transactions), same decision logic.
⇒ WORK → SQS. NEWS → SNS. INTEGRATION → EVENTBRIDGE.
STEP 5

Secure the whole thing

CHOICECognito (or Entra ID federated) for login · IAM roles for every service call · Secrets Manager for every secret · KMS for encryption at rest · VPC with private subnets for RDS, ElastiCache and SQS · tenant isolation in the data layer (RLS + global filters, Day 3) and tenant id in cache keys (Day 5).
WHYNo secrets in code; every service is an identity with a policy; the database is unreachable from the internet.
REJECTEDLong-lived access keys — roles replace them everywhere.
COULD AZURE?Entra ID + Managed Identity + Key Vault + private endpoints — the same four ideas, four different names.
⇒ IAM + SECRETS MANAGER + KMS + VPC. THE CODE HOLDS NOTHING SECRET.
STEP 6

High availability, reporting and the future

CHOICERDS Multi-AZ (or Aurora for more throughput) · read replicas feeding a reporting database (Day 3) · CloudFront and a second region when the trigger arrives · S3 for report files and exports · AI features arriving as their own service behind CloudFront.
WHYWrites single and safe; reads and reports separate; the region story added when the business needs it.
REJECTEDDynamoDB for the core (transactions), EKS (no need yet), global tables (cost not earned).
COULD AZURE?Azure SQL zone-redundant + replicas + Front Door — the identical progression.
⇒ SAME TRIGGERS, SAME ORDER — DIFFERENT BRAND NAMES.
THE LESSON OF THE CASE STUDY

Compare this walk with Day 8's. The decisions are the same; only the names changed. That is the point of Day 9: you are not learning a second architecture. You are learning to translate the first one — and the day you can do both, the cloud question in any interview is already answered.

SECTION 12 — THE DIAGRAM

The Architecture, As Text

The same shape, AWS-drawn. Every connection has a job.

USERS → CLOUDFRONTGlobal edge: static assets served nearby, API traffic accelerated, WAF and DDoS at the front door.
CLOUDFRONT → ALBThe global door hands to the regional door: path routing, TLS, health-checked instances across AZs.
ALB → API FLEETStateless instances scale behind it. Sessions and cache live in ElastiCache, so any instance serves any request.
API → RDSThe transactional truth, in a private subnet, reached only by the app's IAM role.
API ↔ ELASTICACHEThe fast copy. The Day 5 cache-down plan and hit-ratio alarms apply unchanged.
API → SQS → FARGATEThe slow work: payment, inventory, notification. Retries, DLQ, idempotency — Day 6, managed.
WORKERS → PAYMENT PROVIDERThe external dependency behind the worker. Its outages are backlogs, not checkout outages.
RDS → READ REPLICADay 3 separation: reporting reads scale off the writer, and heavy reports never touch the transactional box.
COGNITO + IAM + SECRETSWho you are, what you may do, what you may read. The code holds nothing.
EVERYTHING → CLOUDWATCH + X-RAYMetrics and logs in one place, and the full path of one request across every service.
SECTION 13 — WHEN IT BREAKS

Failure Scenarios on AWS

Same drill as Day 8 — failure, impact, response — with the AWS mechanisms named.

1

EC2 / container instance fails

IMPACTNone to users — one of many.
RESPONSEThe ALB health check stops sending it traffic; Auto Scaling replaces it. Stateless app → nothing is lost.
2

Application becomes unhealthy

IMPACTErrors on one path; the fleet keeps serving the rest.
RESPONSEALB drains the bad instance; CloudWatch error-rate alarm fires first; a rollback via the deploy pipeline is the fix — the health check is what buys the time to do it calmly.
3

Database becomes unavailable

IMPACTCheckout stops; reads that miss cache fail.
RESPONSERDS Multi-AZ fails over to the standby (~a minute) with reconnects. Degraded mode: cached catalog still served ("browse only"), the app tells the truth on screen. RTO decided by the business, tested quarterly.
4

Queue grows rapidly

IMPACTBacklog with a number — the site itself is fine.
RESPONSEWorkers autoscale on queue depth; SQS absorbs the spike. Alert on depth and age of oldest message; the drain rate is a number you can state to the business.
5

External payment provider fails

IMPACTCharges fail or time out.
RESPONSETimeout, retry with backoff, DLQ after N attempts, "payment pending" state, honest customer copy. Their outage is a backlog — never a lost order. Day 4, unchanged.
6

One tenant creates extreme traffic

IMPACTOne company's burst consumes shared capacity.
RESPONSEPer-tenant rate limits, tenant-aware cache keys so one tenant's working set does not evict the rest, and the Day 3 graduation trigger: a tenant crossing the threshold moves to its own database.
7

One Availability Zone becomes unavailable

IMPACTAn AZ dies; the fleet and database are down half.
RESPONSEMulti-AZ is why you spread: the ALB routes to the surviving AZ, Auto Scaling replaces instances there, RDS Multi-AZ fails over. This is the reason AZs, not the reason regions — and it is the cheapest resilience step you can take.
8

Application receives 10× traffic

IMPACTAutoscaling absorbs it — up to a point.
RESPONSEFleet scales on CPU/request count; the cache shields the database; SQS absorbs bursts. The limit is the database writer — and that is where the next trigger (replicas, then sharding) lives. The Day 2 ladder, AWS-named.
THE PATTERN

What breaks → what the user sees → what recovers it → what alerts first. Walk all eight without pausing and the reliability question in any cloud interview is done.

SECTION 14 — THE BILL

Cost Thinking on AWS

Same Day 8 rules, AWS-flavoured. No prices — decisions.

A SIMPLER SERVICE IS BETTERBeanstalk over EKS for one API. Lambda over an always-on worker for a nightly job. The savings are monthly and permanent.
MANAGED SERVICES REDUCE EFFORTRDS costs more than EC2 running Postgres — and costs less, once you count patching, backups, monitoring and the 3 a.m. call. Compare total cost of ownership, not the sticker.
MORE SCALE INCREASES COST — BY DESIGNAutoscaling means the bill follows traffic. That is good: you pay for the peak only while it is the peak.
OVERENGINEERING CREATES COSTGlobal tables, a second region, and Kubernetes are each a monthly line item with no user-visible benefit at today's scale. Each one must be earned by a number.
ARCHITECTURE REDUCES COSTCaching cuts database load, queues flatten spikes into steady drain, and scaling to zero kills the idle bill. The cheapest capacity is capacity you did not provision.
THE COST SENTENCE

"Every choice has a monthly number and a reason. I pick the simplest service that meets the target, I autoscale to actual usage, and I name the trade-off where cheaper means slower recovery. Cost is a requirement — I design for it, not around it." Same words as Day 8. That is the point.

SECTION 15 — HONEST LIST

10 AWS Architecture Mistakes

Each one is a decision made for the wrong reason — most of them the same wrong reasons as Azure.

01

Choosing services before requirements

DynamoDB appears because it scales — before anyone asked whether the data is relational and transactional.

Requirement list first, service list second. Every service gets one sentence about the problem it solves.

02

Using EKS without a real need

"It is the powerful one" — one API gets a cluster, a node pool and an operations team it never needed.

Beanstalk or ECS for most workloads. EKS is earned by many services or a Kubernetes-native team.

03

Ignoring IAM

One broad policy on everything — the most common AWS security failure is a permission that could do anything.

Least privilege: roles per service, policies per job, no long-lived keys, code review on IAM like code.

04

Putting everything in public networks

The database is one port scan away from the world because it is in a public subnet.

VPC with private subnets for RDS, ElastiCache, SQS. The ALB is the only public thing; everything else is reached from inside.

05

No failure strategy

"AWS is reliable" is treated as a fact — so nothing is designed for the day an AZ or a service dies.

The platform is highly available; your application is not. Failover, degraded modes, tested recovery — the Week 1 rule.

06

Ignoring cost

The architecture is perfect; the monthly bill is five times the revenue.

Say the bill out loud. Autoscale, rightsize, and choose the tier that meets the actual target.

07

Assuming managed services solve every problem

RDS has HA, so the application needs no retry logic — until the failover happens mid-transaction.

The platform fails over; the application must survive it. Reconnects, retries, a runbook, a staging drill.

08

Using Lambda for unsuitable workloads

A stateful API with hundreds of endpoints becomes a maze of Lambda functions with cold starts and time limits.

Lambda for events and glue. Beanstalk or ECS for the request-driven application. Match the host to the workload.

09

Treating DynamoDB like a relational database

The relational data lands in DynamoDB, then the team discovers there are no joins and no ad-hoc queries — and the access patterns were never designed.

DynamoDB requires the access pattern first. Transactional connected data belongs in RDS/Aurora. Choose by data shape, not by "it is fast."

10

Copying the Azure architecture directly into AWS

"Service Bus → SQS, Cosmos → DynamoDB" — and the differences (sessions, transactions, access patterns) arrive as surprises.

Translate the decision, not the diagram. Re-ask the requirement question per service, then name the closest AWS service and the difference that matters.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 9

Five rules. Not about AWS — about the fact that both clouds answer the same questions.

01

The requirement decides. The cloud follows.

Load, data, availability, cost, team, estate — those six answers pick both the service and the platform. Neither brand is a default.

02

Translate the decision, never the diagram.

SQS is not "Service Bus with a different name" — it is a different set of semantics. Re-ask the requirement per service, then name the closest service and the difference that matters.

03

More control means more responsibility.

EC2 over Beanstalk, EKS over ECS — each step up the control ladder is a step up the operations bill. Choose the rung the requirement demands, not the one that impresses.

04

The platform fails over. The application must survive it.

Multi-AZ, Multi-Region, managed databases — all platform promises. Your application still needs reconnects, degraded modes and a tested recovery. Azure and AWS both remove hardware problems; neither removes design problems.

05

Know both clouds, defend one choice.

The strongest answer in a multi-cloud interview is: "I could build this on either. Here is what I would pick here, and the trade-off, and the one place I would choose differently on the other cloud." That sentence is the whole day.

Day 9 done. You did not memorise the AWS catalogue — you learned to translate the architecture you already own, and to pick a cloud like an architect: by requirement, not by preference. Day 10 stays behind the curtain until the assignment is yours.
