SECTION 01 — THE REAL PROBLEM

Why “User → API → Database” Gets Slow

A database is a careful accountant: it reads from disk, checks constraints, respects locks, joins tables, and never lies. That care costs milliseconds. When every one of 5,000 requests per second asks the same accountant the same question, the queue is not a bug. It is arithmetic.

Why response time improves: a cache lookup is memory against a hash table — single-digit milliseconds, no disk, no query planner, no lock waits. The tail improves most: p95 drops because the database queue shortens.

Why database pressure drops: reads that never reach SQL cost SQL nothing. The connection pool stops being the bottleneck, and the writes that matter finally get the I/O they need. Day 2 called the cache “the shield” — this is the shield doing its job.

WHAT CACHING IS NOT

Not a replacement for the database. The cache is a copy. It can be evicted, restarted, emptied by a deploy, or corrupted by a bad key. The database is the truth; the cache is a fast memory of the truth. If your design breaks when the cache is empty, you did not build a cache — you built a second database with worse guarantees.

And it is not free. It buys milliseconds with three new problems: stale data, invalidation complexity, and a new thing that can die. Sections 5–8 pay for those problems.

SECTION 02 — THE SELECTION

What Is Good Data to Cache?

One sentence: cache what is read far more often than it changes, and safe to serve slightly old. Three tests — hot, cold-changing, forgivable.

Ten practical candidates

Product catalog pagesviewed 50K/day · edited twice
Category & navigation treereads:thousands · writes:weekly
Config / feature flagsevery request needs it
Master dataunits, tax slabs, cities
User session & claimsper request · shared across servers
Roles & permissionsexpensive joins · rarely changed
Dashboard aggregatesminutes to compute, seconds to serve
Search suggestionspure CPU · same 200 prefixes
Exchange / pricing rateschanges on a schedule anyway
HTML fragments / rendered blockssame markup, every visitor

And what should usually stay out

Account balances and anything you must never be wrong about

A 2-second-stale balance lets a customer overdraw. Money reads go to the source of truth (Day 3's strong-consistency rule).

Stock at the moment of checkout

Cached “in stock” is how you oversell. Read the live row, lock, decrement.

Payment status

Pending/failed/success drives whether you ship. Cache it and you ship on a lie.

One-time tokens, password reset codes, CSRF nonces

They must be single-use and expire. A copy is a replay hole.

Data that is unique per user and rarely re-read

A 30 MB user export cached once = cache memory wasted and eviction pressure for the real hot keys.

Anything written as often as it is read

If it changes every second, you will spend your invalidation budget chasing it and still serve old values.

Highly sensitive personal data, when not needed

Every cache copy is another place PII can leak, be logged, or outlive the delete request. Ask whether it is needed at all.

The slow query nobody has indexed yet

Caching a 4-second query hides the fact that a missing index would make it 40 ms. Fix first, cache second (Section 14, mistake #10).

THE ARCHITECT'S SHORTLIST

Take your top 10 endpoints by traffic. Mark each: hot? changes how often? what breaks if it is 60 seconds old? The cache list writes itself — and it is usually three to five items, not thirty.

SECTION 03 — THE THREE SHAPES

Cache Strategies

Three ways to arrange “app, cache, database.” The difference is who writes what, and in what order.

How it works

The lazy cache

Read: look in cache; if empty, query the database, store the result, return it. Write: save to the database, then delete the cache entry. The cache is populated on demand, by the reads.

Good use case

Read-mostly app data

Product pages, catalog, config, permissions, dashboard aggregates — anything where reads dominate and a second of staleness is fine.

BENEFIT RISK
Only what is actually read is stored — cache memory is used for the hot set. Simple to add to an existing app. Cold data never costs cache RAM. A cold cache = every request misses (this is the stampede, Section 7). The window between “DB updated” and “cache deleted” returns stale data. Two callers can both miss and both fill.

How it works

The tidy cache

The write goes to the cache and the database as one logical operation. A read after the write always sees the new value — the cache is never allowed to be behind.

Good use case

Freshness matters, writes are modest

Reference data consumed by many readers with rare but important updates: price lists, published content, tenant feature settings — where “slightly old” would create support tickets.

BENEFIT RISK
No stale reads after a commit. Reads are always fast — no miss penalty on the hot path. Predictable behaviour makes it easy to reason about. Every write costs a cache write — slower writes, and a cache outage can block writes if the code treats it as required. If you write data nobody reads, you pay for nothing.

How it works

The deferred cache

Write hits the cache and returns. A background job flushes the change to the database in batches, seconds later. The database sees smooth, merged traffic instead of spikes.

Good use case

Write storms with forgiving data

View counts, like counters, activity scores, telemetry, last-seen timestamps — write-heavy metrics where a lost second of data is acceptable and the DB would otherwise be crushed.

BENEFIT RISK
Writes return instantly. The database is protected from bursts — thousands of updates on one key collapse into one write. Data loss if the cache dies before the flush. Long window where the database disagrees with reality. Ordering and dedup become your problem. Not for money, not for orders.
WHICH ONE DOES A TYPICAL .NET APP USE?

Cache-aside, almost always. Because it fits reality: most business apps are read-heavy, the database is already the source of truth and is already written correctly by existing code, and you can add a cache read in one layer without changing every write path. You accept staleness in exchange for simplicity. Write-through appears for a few “freshness must be exact” lookups; write-behind is rare and mostly for counters and telemetry — the places where losing a second is cheaper than paying for the write.

SECTION 04 — THE TOOL, NOT THE TUTORIAL

Redis, From an Architect's Chair

You do not need Redis commands to be dangerous with Redis. You need six facts about what it is — because every one of them is a design consequence.

WHAT IT ISAn in-memory store of keys and values, served over the network with one-thread-fast handling. It holds copies — strings, hashes, sets, sorted sets, tiny JSON — and it forgets by design unless you tell it to remember.
WHY IT IS FASTData lives in RAM (no disk), the key is a hash lookup (no query planner, no joins), and there is one small command per call. One to five milliseconds is normal. That speed is also the trap: it makes people cache things they should have fixed.
KEY / VALUEYou ask for an exact key; you get that value or nothing. There is no WHERE, no search — which means the shape of your key is the shape of your access pattern (Section 10). Design keys like an API, not like a filename.
EXPIRATIONEvery key can carry a TTL. The cache self-cleans. Expiry is not a feature you may skip — it is the only thing standing between “cache” and “a slowly filling box that one day dies” (Section 5).
MEMORY-BASEDRAM is finite and expensive. Eviction policy decides what gets dropped when it fills. Big values are the classic mistake — a 5 MB blob per tenant is not caching, it is squatting (Section 14, mistake #7). Budget it, set maxmemory, measure it.
DISTRIBUTED + AVAILABILITYOne Redis serves all your app servers, which is why it beats a per-server memory cache (Section 9). For availability you get replicas, failover, and optional persistence — and the honest architect's note: treat Redis as something that can vanish (Section 8). Persistence is for recovery, not for being a database.
INTERVIEW ANGLE

Asked “why Redis?”, the junior answers “it's fast.” The architect answers: “fast, shared across servers, and it expires by itself — which lets me put a copy of hot data between users and the one thing I cannot scale cheaply: the write database. And I assume it can vanish, so my app still works when it does.”

SECTION 05 — THE CLOCK

Cache Expiration — TTL, Time To Live

TTL is the answer to a question you must never skip: “How wrong is this copy allowed to be?” You set the clock once, and every future request inherits that decision.

DATA TTL WHY THAT NUMBER
Product master data 1 hour Changes a few times a day. If a description is 30 minutes old, no human is harmed. Long TTL = the cache absorbs nearly all traffic.
Dashboard / aggregate 1 minute The query costs minutes of work, but a manager expects “as of a minute ago”. 60 seconds also means 60 users share one computation.
User session 30 minutes Not freshness — safety. Sliding expiry is the logout timer. A session that lives 30 days is a security hole, not a cache.
Stock level shown on a page seconds, if at all Minutes of staleness become overselling. The checkout path does not read this cache.
Feature flags / config 30–60 s You want a flag flip to propagate on its own — with no deploy, no manual purge, and no 24-hour lag.
WHY TTL IS NOT OPTIONAL

Without expiry the cache becomes a second database that nobody maintains: entries never leave, memory grows until eviction becomes random, and stale data stops being “a minute old” and becomes “six months old”. Expiry is the self-cleaning mechanism. Set a TTL on every key — the only safe default is “shorter than the pain of being wrong”.

SECTION 06 — THE FAMOUS PROBLEM

Cache Invalidation

“When the original data changes, how do we update or remove the cached copy?” — the sentence that has ended more cache projects than performance ever justified.

The example: price is ₹100 in the database and ₹100 in the cache. Marketing changes it to ₹120. The update lands in SQL. Now two sources of truth disagree — and which one a customer sees depends on luck. That is the whole problem.

  • T = 0s — DB price = 120 · cache price = 100. Both “correct”, neither agreed.
  • T = 3s — Customer A (cache hit) sees ₹100 and buys. Your margin is gone, or the order is cancelled at fulfillment.
  • T = 8s — Customer B arrives after the invalidation and sees ₹120.
  • T = 60s — Cache TTL expires anyway; the next read refreshes it. Everything converges. That is why TTL is the safety net under every strategy below.
APPROACH HOW ADVANTAGE RISK
1 · Delete after update
the classic		 Write the DB in a transaction, then remove the key (or a version prefix). Next read refills it. Never writes a half-built object. One rule: DB first, delete second. Works even if the delete fails — TTL catches it. The next reader pays the miss. If the delete is forgotten in a new code path, staleness lasts until TTL. Mitigate: a single “save + invalidate” method all writers must use.
2 · Update after write Write the DB, then overwrite the cache with the new value. No miss for the hot key — the reader never pays the refill cost. Concurrent writers can interleave and leave the older value in cache. You must rebuild the exact same object shape in two places, or you cache a subtly wrong document.
3 · Short TTL Do nothing. Let the key die in 30–60 seconds. Zero coupling between write paths and cache. Impossible to forget. Perfect for data where “wrong for a minute” is acceptable. You pay staleness on every change, and the DB carries 1/TTL of the read traffic forever. For a hot key that can be a real load.
4 · Event-based invalidation The write publishes ProductChanged(id) to a queue/bus. A subscriber deletes keys — in one app or across many services. Scales to multiple caches, multiple services, multiple regions. New consumers add themselves without touching the writer. Decouples the write path from cache plumbing. Now correctness depends on a message that can be late, lost, or duplicated. You need the TTL net anyway — plus monitoring on consumer lag.
HOW AN ARCHITECT COMBINES THEM

Delete-after-write for correctness, short TTL as the insurance policy, events when many things must forget at once. And one more trick worth saying in the interview: version the key instead of deleting it — bump product:v41 → v42 and every old entry becomes unreachable garbage that expires on its own. No delete to forget, no race on the delete.

INTERVIEW ANGLE

“Do you update or delete the cache?” — the strong answer is delete, with reasons: no half-built objects, no read-modify-write races, and the miss path is the same code that built the entry in the first place. Then add: “and every key still has a TTL, because deletes fail.”

SECTION 07 — THE CLIFF

Cache Stampede

One popular key expires. For one second, the shield has a hole the size of your busiest page.

SIMULATOR — EXPIRE THE HOT KEY AND WATCH THE DATABASE

Product tenant:88:product:456 is the homepage feature. 10,000 requests/second read it. It just expired.

Baseline: cache is warm, hit ratio 100%, the database is a rumour. Now expire the key with no defenses.
Verdict: —

Why it is dangerous: the database is sized for ~5% of your reads, not 100%. A stampede is a sudden, perfectly-timed 20× load spike — on the component with the least headroom. It turns a 2-second cache blip into a site-wide outage, and the outage feeds itself: retries, health-check restarts, and a cold cache after every restart. Day 2 called this the thundering herd; here is the shape of it:

The five defenses, ranked by honesty

  1. Single-flight / distributed lock on refill. One reader wins the right to rebuild; the rest wait a few ms and read the finished value. This alone turns 10,000 queries into 1. In .NET: a Redis lock or an in-process Lazy<Task> per key (plus the lock for other servers).
  2. Stale-while-revalidate. Mark the entry “logically expired” but keep it for a grace window: the reader gets the old value now, and one background job refreshes it. Users never wait; the DB never stampedes. Perfect for dashboards and catalogs.
  3. Jitter the TTL. 3600 ± 300 seconds instead of exactly 3600. Prevents synchronized mass expiry across thousands of keys after a warm or a deploy.
  4. Pre-warm after deploy / after a flush. A startup or scheduled job loads the known hot keys before traffic arrives, so the first user is never the one paying.
  5. Rate-limit the miss path. Cap concurrent rebuilds per key. If the flood still comes, the limiter fails some readers with a short retry instead of killing the database.
THE POINT

A stampede is not “many misses.” It is many misses for the same key at the same instant. Every defense above makes those ten thousand requests into one.

SECTION 08 — THE INTERVIEW QUESTION

What Happens When Redis Goes Down?

This is asked in almost every architect interview, because the answer shows whether you have ever carried a pager. Run the drill.

FAILURE DRILL — USER → API → REDIS → DATABASE

RATE-LIMIT DB FALLBACK (shed load) LOCAL IN-MEMORY FALLBACK CACHE CIRCUIT BREAKER (stop calling for 30s) ALERT ON HIT RATIO + LATENCY
Standing order: Redis is healthy, nothing to see. Kill it and decide, as the architect, what the application does.
THE QUESTION THE WEAK ANSWER THE ARCHITECT ANSWER
Should the application stop? “Redis is required, so the app is down.” One cache outage becomes a full outage — you made a copy of your data load-bearing. No. For read paths, degrade to the database (with limits) or serve stale. The cache must be a removable component. The exception: features that genuinely need Redis (a queue, a lock, a session) — say which they are.
Should it use the database? “Yes, just fall through to SQL.” That is a stampede on purpose: 5,000 rps onto a box built for 400. Yes, but on a budget: a cap on concurrent rebuilds, a short per-instance memory cache for the worst keys, and a circuit breaker so you are not paying 200 ms of timeouts on every request.
How to avoid DB overload? Pray it is short-lived. Rate-limit the miss path · serve stale where acceptable · shed non-critical pages (recommendations, exports) first · keep a short-TTL local cache as the emergency tier · fail fast with a friendly message instead of a long queue.
Redis comes back — then what? “Everything returns to normal.” It doesn't. The cache is empty, so the first 60 seconds after recovery is the worst moment of the incident. Plan the warm-up: pre-warm hot keys, keep the DB rate limiter engaged while the cache refills, then release it. Recovery from a cache is a two-step event — restore, then refill.
Monitoring & alerts Alert on “Redis up/down” via a port check. Alert on hit ratio (falling = your real load is about to move to SQL), eviction rate, latency of cache calls (a slow Redis is worse than a dead one — timeouts eat threads), DB CPU, and connection errors. The hit-ratio alarm is what turns an outage into a warning.
THE SENTENCE THAT PASSES THIS QUESTION

“I design the app so Redis is an optimisation, not a dependency. If it dies, I want a slow minute instead of an outage: fall back to the database with a concurrency cap, serve stale where the business allows, keep a short-TTL local tier, and warm before removing the limiter. And I alarm on hit ratio, not on ping — because hit ratio is the leading indicator of the database burning.”

SECTION 09 — WHY NOT JUST MEMORY?

Local Cache vs Distributed Cache

IMemoryCache in the app process is the fastest cache you will ever have — and it is a lie the moment you run more than one instance.

Local cache (in-process)

User → Server A → its own memory

No network hop. Sub-millisecond. Zero infrastructure, zero cost, cannot go down separately.

  • The problem: Server A and Server B each hold their own copy. A price changes → A's copy is new, B's is old. Users on different servers see different data, and “sometimes the price is wrong” is the hardest bug to reproduce.
  • Also: every deploy empties it (cold cache on every release), memory competes with your app, and no entry can be shared.

Distributed cache (Redis)

Server A / B / C → one Redis

One shared copy for the whole fleet, visible to every service, with expiry, eviction, and — crucially — one place to invalidate.

  • Why it wins with N servers: consistency of the copy, shared warm-up, invalidation is one call, and cross-service use (sessions, locks, rate counters) becomes possible.
  • The cost: +1–2 ms per lookup, a new component that needs patching, monitoring, and a failure plan (Section 8).
THE ANSWER IS USUALLY “BOTH, IN ORDER”

A two-tier read: 5 seconds in local memory, then Redis, then the database. The tiny local window absorbs a 10,000-rps key with almost no Redis traffic, and five seconds of difference between servers is tolerable for master data. Do not reach for this until you have measured Redis round-trips as a real cost — otherwise it is just one more way to be stale.

CITATION LOCAL DISTRIBUTED
Speed sub-ms ~1–2 ms + network
Consistency across servers no — one copy per process yes — one copy for the fleet
Survives a deploy no yes
Sessions / locks / counters cannot share designed for it

SECTION 10 — THE SMALL THING THAT SAVES YOU

Cache Key Design

A cache key is an API contract. Four properties: unique, predictable, consistent, tenant-aware. Get it wrong and two different answers fight over one slot.

KEY BUILDER — COMPOSE IT, THEN BREAK IT ON PURPOSE

—
INCLUDE TENANT SEGMENT INCLUDE LANGUAGE INCLUDE VERSION (bump = force refresh)

Why the tenant segment is not decoration

SINGLE KEY, TWO TENANTS

How one line of code leaks a customer list

THE CODEcache.Get("customers:list") → if miss, SELECT * FROM Customers WHERE TenantId = @t → cache the rows under customers:list.
THE ACCIDENTTenant 88 fills the entry first. Tenant 92 arrives, finds customers:list populated, and gets 88's data. Nothing throws. Nothing is slow. The bug is silence.
THE FIXPut the tenant in the key — t:88:customers:list — and, better, make it impossible to forget: one key-builder helper in the data layer, plus tenant scoping enforced in the query itself (Day 3's global filter + RLS).
⇒ IN MULTI-TENANT SAAS, THE KEY IS A SECURITY CONTROL. TREAT IT LIKE ONE — REVIEW IT, TEST IT, COVER IT IN A TEST THAT QUERIES WITHOUT A TENANT AND ASSERTS IT FAILS.
UNIQUE — NO COLLISIONSInclude everything that changes the answer: tenant, culture, currency, price-list, plan, user-role variant. If a segment can change the bytes, it belongs in the key.
PREDICTABLE — YOU CAN FIND IT AGAINFixed order, fixed separators, lower-case entity names: t:{tenant}:{entity}:{id}:{culture}:v{n}. Predictable keys are the only keys you can invalidate, count, and debug at 3 a.m.
CONSISTENT — ONE BUILDERNever hand-write keys in a controller. One helper in the infrastructure layer, used by every service, is the difference between “we have a caching strategy” and “twelve people invented twelve caches”.
SHORT & FLAT — SIZE MATTERSKeys live in memory too. Serialising an entire filter object into a key costs RAM and makes audit impossible. Hash the filter, keep the readable parts: t:88:orders:search:9f2c1a.
THE VERSION TRICK, ONCE MORE

Store the current version of a data family in one key (t:88:product:ver → 41). To invalidate everything at once, set it to 42. Old keys become unreachable and expire on their own — no KEYS product:* scan in production, which is a genuinely dangerous command at scale.

SECTION 11 — WHEN THE COPY DISAGREES

Cache Consistency — Five Situations

Every one of these is a decision, not a bug report. Name your answer before the incident names it for you.

SITUATION 1

Database updated, cache not updated

WHAT IT LOOKS LIKEA new writer path (a bulk-import job, a support tool, a second service) changed the row and never touched the cache. Users see old data until TTL.
ARCHITECT THINKINGAsk who is allowed to write this table? Every writer must go through one owner that invalidates. If you cannot enforce that, shorten the TTL — staleness bounded to 60 s is a policy; staleness “until somebody notices” is an accident. Also: is a stale read ever harmful? Then this data must not be cached on the critical path at all.
SITUATION 2

Cache updated, database update fails

WHAT IT LOOKS LIKEYou wrote cache-then-database. The database rolled back. The cache now holds a value that never existed — and it is “fresh”, so it survives.
ARCHITECT THINKINGNever let the cache be written before the truth commits. Order matters: DB commit → cache delete. This is why “update the cache” (write-through-by-hand) is riskier than “delete it”: deleting a wrong value costs one miss; caching a lie costs the trust of every reader.
SITUATION 3

Cache expires in the middle of a request

WHAT IT LOOKS LIKEOne page reads four keys; key two expires between the first and second read. The page mixes data from two generations — old price, new tax.
ARCHITECT THINKINGAccept it for independent things; design around it for things that must agree. Options: one composite key per page (price, tax, and stock stored together, refreshed together), a version segment in every key of the family so all readers land on the same generation, or serve stale on expiry so a mid-request death never happens.
SITUATION 4

Two users update the same record

WHAT IT LOOKS LIKEBoth read at v1, both write, last one silently overwrites the first. Now the cache holds the loser's view of the world.
ARCHITECT THINKINGThis is not a caching problem — it is a concurrency problem the cache merely exposes. Optimistic concurrency (row version on the update; reject on mismatch) is the fix; “cache-aside, delete after commit” handles the copy. Do not let a cache become the accidental source of truth just because it is quicker to read.
SITUATION 5

Different services cache different copies

WHAT IT LOOKS LIKEOrder, Pricing, and Reporting each cached the product, each with its own TTL. A campaign changes the price: for 25 minutes, three services tell three truths, and the invoice disagrees with the page.
ARCHITECT THINKINGPick an owner. Either the owning service publishes ProductChanged and everyone invalidates on it (events), or the data is cached once in a shared namespace with a shared key format and a shared version. What you must not do is let “we each cache a little” become the consistency strategy. And in the money path — invoice total, checkout price — recompute from the source and never read a shared copy.
THE ONE-LINE RULE

The cache may be wrong for a bounded time, and it may never be the only record of something true. Every design decision in this section exists to make that sentence actually hold.

SECTION 12 — CASE STUDY

The MFGPLUS Dashboard — 5 Minutes to 2 Seconds

A manufacturing SaaS dashboard: open work orders, machine status, defect counts, month-to-date output. It takes 5 minutes to generate. 400 plant users open it every few minutes. The database never recovers.

1 · The current problem

2–5 · What to cache, under what key, for how long

QUESTION DECISION REASONING
2 · Why caching helps Turn N expensive computations into one per refresh window, served from memory. The expensive part is not the read — it is the computation. Caching a computed result has the highest return of any cache you will ever build.
3 · What is cached The whole rendered dashboard payload per tenant (and per user-scope when filters differ). Not the raw tables. One key, one lookup, one invalidation. Row-level caching here would need 40 keys and 40 staleness windows for the same page.
4 · Cache key t:{tenantId}:dash:plant:{plantId}:scope:{userId|0}:v{n} Tenant-first (isolation), scope segment so “my open orders” never leaks to the plant view, version segment for instant global refresh.
5 · TTL 60 s logical TTL + 5 min stale grace (stale-while-revalidate) Managers want “about a minute ago”. The grace window is what prevents the stampede every 60 seconds — and it means the request that finds the key expired is served the old number while a single job rebuilds.

6–8 · Refresh, changes, and failure

6 · REFRESH

Who pays for the five minutes

BACKGROUND JOBA scheduled generator recomputes each active dashboard every 60 s and overwrites the key. Users almost never hit the expensive path at all.
SINGLE-FLIGHTIf the job is late, exactly one reader may rebuild (Redis lock with a 6-minute lease); everyone else gets the stale copy. Never four hundred.
IDLE TENANTSOnly regenerate for tenants with an open session in the last N minutes. A dashboard nobody is looking at should not be burning the database on a timer.
⇒ THE PAGE COST IS “ONE HEAVY QUERY PER MINUTE PER ACTIVE TENANT”, NOT “PER USER”.
7 · ON DATA CHANGE

When a work order closes

DECISIONDo nothing. Let the 60-second window run out.
WHYA dashboard is a lagging indicator by nature. Invalidating on every event means a busy shift regenerates constantly — the stampede is back, self-inflicted. Add a “refresh” button that triggers a throttled rebuild for the one person who really needs it now.
8 · WHEN REDIS DIES

The honest plan

BEHAVIOURThe dashboard must not fall back to running the five-minute query per user — that is a self-inflicted outage. Instead: serve the last-known result from a short in-process memory copy (it will be minutes old, and say so on screen).
THE UI HONESTY“Data as of 14:32 · cache unavailable.” One line of text buys the entire team the right to degrade instead of failing.
IF NO COPY EXISTSReturn “temporarily unavailable, retry in a minute” — a deliberate, cheap, friendly 503 with a rate limit in front of the DB path. A slow answer and a wrong answer are both worse than a clear one.

10 · How the design scales

  1. More tenants: work is per active dashboard, not per user. A 10× user increase is nearly free; a 10× tenant increase is what you must budget for — so the generator is a queue of jobs, spread out, not a cron firing everything at :00.
  2. More dashboards per tenant: same pattern, more keys; keep the key convention so “invalidate this plant” stays one command.
  3. Redis too small: shrink the payload (cache the aggregate, not the row grid), add a second instance for the heaviest tenants, and keep local memory as tier one.
  4. The next real step is not a bigger cache — it is a reporting database or warehouse feeding the cache (Day 3). When the generator runs every minute, it should not be pointed at the transactional box at all.
INTERVIEW ANGLE

Tell this story in five beats: expensive computation · shared by many · staleness acceptable → cache the result with tenant-scoped key, 60 s TTL + stale grace + single-flight, degrade honestly when Redis dies, and the DB frees up. Numbers first, brand names last.

SECTION 13 — DECISIONS

10 Questions to Ask Before Adding Redis

Ask all ten before the word “Redis” enters the room. Each has an option you will reject, and a trade-off you will sign for.

D01

Do we actually need caching?

OPTIONS — index / rewrite query · scale DB up · add cache · do nothing.

RECOMMENDATION

Fix the query first. Add cache only when the work is inherently expensive (aggregation, external call, rendering) or when read volume far exceeds write volume.

WHY

A cache over a bad query makes the bad query invisible — and you will still pay for it on every miss. Measure: if a new index gets you 90% of the way, keep your failure modes at zero.

TRADE-OFF

Skipping the cache means the expensive computation stays in the request path. Accept that only if it is genuinely cheap at your numbers.

TRIGGER TO ADD IT

DB CPU sustained >60%, or a hot read repeated >50× per second on the same rows.

D02

What data should be cached?

OPTIONS — everything · hot+cold-changing+forgivable · only sessions/config.

RECOMMENDATION

Three-to-five named items from your top-10 traffic list. Write them down, one line each: what it is, its TTL, who invalidates it.

WHY

Every cached item is a permanent consistency obligation. A short list you can reason about beats a broad one nobody can.

TRADE-OFF

Un-cached reads keep hitting SQL — that is fine; it is the part you scaled on purpose.

EXCLUDE

Money, stock at checkout, payment status, one-time tokens, per-user data read once.

D03

How long should it live?

OPTIONS — no TTL · seconds · minutes · hours · invalidate-only.

RECOMMENDATION

A TTL on everything, chosen from the pain of staleness: master data 1 h, dashboards 1 min, sessions 30 min — plus jitter.

WHY

TTL is the only mechanism that repairs a cache after you have forgotten an invalidation path. “Invalidate only” means one missed code path equals staleness forever.

TRADE-OFF

Short TTL → more misses → more DB load. Long TTL → older data. Pick the boundary of the acceptable, not the maximum.

ASK THE BUSINESS

“How wrong may this be?” If the answer is “zero”, it does not belong in a cache at all.

D04

What happens on a miss?

OPTIONS — query DB inline · return loading · compute async · reject.

RECOMMENDATION

Inline query for cheap data with single-flight; for expensive computation, serve stale and refresh in the background.

WHY

An unprotected inline miss is a stampede waiting for its TTL. The word “inline” is not a plan; “one reader rebuilds, the rest wait or get stale” is.

TRADE-OFF

Waiting readers add latency to a few requests. Rebuilding in one place costs a lock and a little code. Both cheaper than a melted database.

COLD START

After deploy or flush: pre-warm the hot keys, and keep the DB limiter engaged during refill.

D05

What happens when Redis fails?

OPTIONS — app fails · fail open to DB · fail open with limits + local tier · fail closed.

RECOMMENDATION

Degrade: rate-limited DB fallback + short in-process cache for the worst keys + circuit breaker. Fail closed only where the cache is genuinely load-bearing (e.g. auth tokens with no DB alternative).

WHY

Naive fail-open converts a cache outage into a database outage — the second is far worse. Naive fail-closed makes the optimisation a dependency.

TRADE-OFF

Degrading means some users see slower or older data during the incident. Choose that deliberately, and write it in the runbook.

PROVE IT

Take Redis away in a test environment and watch what breaks. If “everything” breaks, you do not have a cache.

D06

How will stale data be handled?

OPTIONS — ignore it · bound it with TTL · invalidate on write · version-stamp and show it.

RECOMMENDATION

Bound it, invalidate the ones that matter, and display the age where users make decisions (“as of 14:32”).

WHY

Staleness is not a defect to eliminate; it is the price you agreed to. Making it visible converts a trust-destroying bug into an accepted product behaviour.

TRADE-OFF

Showing “as of” invites questions from users who wanted live data — that is the negotiation, not the bug.

HARD RULE

Any screen where a stale value changes money or a physical action must read the source.

D07

Local cache or Redis?

OPTIONS — IMemoryCache only · Redis only · both, two tiers.

RECOMMENDATION

Redis as the shared source of copies; a 2–5 second local layer only when you have measured that Redis round-trips matter, or as the emergency tier when Redis is gone.

WHY

With N servers, local-only means N versions of the truth and per-instance cold caches. Redis gives one shared copy, one invalidation point, and cross-service reuse.

TRADE-OFF

The local tier adds its own staleness window and another thing to explain. Keep the window tiny and the list of keys short.

WHEN LOCAL ALONE IS FINE

One instance, or data where 10 minutes of divergence between servers is harmless (static reference lists).

D08

How do we protect the database from the cache?

OPTIONS — nothing · connection caps · miss-path rate limit · queue the rebuild · circuit break.

RECOMMENDATION

All of the cheap ones: cap concurrent rebuilds per key, cap total DB read concurrency when the cache is degraded, circuit-break a sick dependency, and put a queue in front of expensive generation.

WHY

The cache's job is to protect the database. If the cache's failure is the worst load the database ever sees, the design has the polarity reversed.

TRADE-OFF

Shedding load means refusing some requests during the incident — the deliberate, smaller harm.

MEASURE

DB CPU at cache-cold. That number is your real capacity, not the pretty one.

D09

How do we handle tenant-specific data?

OPTIONS — rely on the query filter · put tenant in the key · both · separate Redis per big tenant.

RECOMMENDATION

Tenant in the key and tenant scoping in the query — enforced in one data-layer helper — plus per-tenant key counts and memory visible in the admin console.

WHY

In SaaS, a shared key is a cross-tenant leak with no exception thrown. The key is a security boundary; treat it like one and test it.

TRADE-OFF

More keys, more memory, and no accidental cross-tenant cache reuse. That is the point.

NOISY TENANT

If one tenant evicts everyone, give them their own Redis or their own DB (Day 3's graduation trigger).

D10

How will we know it is working?

OPTIONS — nothing · Redis INFO once a day · hit ratio + latency + evictions · cost per request.

RECOMMENDATION

Dashboards and alerts for hit ratio (by key family), cache call latency, eviction rate, memory, DB CPU, and error rate on the miss path. A cache without a hit-ratio number is a guess with a monthly bill.

WHY

Hit ratio is the leading indicator: it falls before the database does. Evictions rising tells you the cache is undersized before users notice. Without these, you cannot prove the win to anyone.

TRADE-OFF

You must instrument the read path (a decorator around the cache client) and carry the metrics forever. Cheap — and it's the only way to defend the design later.

TARGET

Pick a number per key family — 90% for catalog, 99% for config — and alarm on sustained drop.

THE MAIN LESSON

Every caching decision buys latency and database headroom and pays with staleness, invalidation work, and a new failure mode. Say the purchase price out loud. That is the whole interview.

SECTION 14 — HONEST LIST

10 Caching Mistakes

Each one is a trade you accepted without reading it.

01

Caching everything

It feels like performance work. Every entry is an invalidation obligation and a memory cost, and half of them are never read twice.

Cache the shortlist from Section 2. If you cannot name the hit ratio, delete the cache.

02

No expiration

“We'll invalidate manually.” Then a writer appears who does not know about the cache, and staleness is unbounded.

TTL on every key. No exceptions. Jitter on the bulk of them.

03

Poor cache keys

Keys hand-built in twelve places, inconsistent order, no tenant — collisions become “random” wrong data.

One key builder in infrastructure. Fixed segment order. Tenant and culture included.

04

Ignoring stale data

Nobody decided how old is acceptable, so the answer is “until a customer complains”.

Write the acceptable staleness per item, show “as of” in the UI, and keep money/stock out of the cache.

05

No Redis failure plan

It has never been down, so no one has decided what down means. It will be, during a launch.

Rate-limited fallback, local tier, circuit breaker, and a drill in staging. Run Section 8 as a test.

06

Relying on the cache as the source of truth

Business state lands in a copy with no schema, no constraints, and eviction. One flush deletes the truth.

Database first, cache second. If losing every key would hurt, that data is not a cache — it is a database.

07

Huge objects in the cache

The whole 8 MB result set under one key. Memory explodes, evictions start, serialization eats your latency win.

Cache the aggregate or the page, not the row dump. Compress, trim fields, cap size per key family.

08

No monitoring

The cache “is there”, so nobody looks. Hit ratio drops quietly for weeks and the DB takes the load.

Hit ratio, evictions, cache latency, DB CPU — four numbers, always on screen.

09

Ignoring tenant isolation

One key, two tenants, one very public data breach. No exception is thrown; the fix is found by an auditor.

Tenant in the key, tenant in the query, and a test that asserts a key built without a tenant fails.

10

Using cache to hide a bad query

A 4-second query becomes a cached 2 ms read, and now nobody will ever fix the query — including on the miss.

Index and rewrite first, cache second. Keep the miss path fast, or you have built a time bomb with a TTL.

SECTION 16 — CHECK

Self-Test: Ten Caching Scenarios

Decisions and failures, not definitions. Answer out loud, then reveal.

Q1The catalog page is slow. Do you add Redis?
Not yet. I ask what the query costs and why. If it is an N+1 or a missing index, fix that — free, and it also fixes the miss path. If the read is genuinely expensive or just enormous in volume, caching is the right lever. I would want the numbers first: DB CPU, QPS on that query, and read:write ratio.
Q2Product price changed in the database 30 seconds ago but the page still shows the old one. Walk me through your response.
First, is that within policy? If TTL is 60 s and the price is a display value, it is working as designed — and I would add “price updated 14:32” to the UI. If the checkout price is stale, that is a defect: checkout must read the source, and the cache must be invalidated by the same code path that writes, not by an extra step someone forgot. Then I check whether a writer exists that bypasses the owner.
Q3Every day at exactly 03:00 the database spikes and the site crawls for 40 seconds. What happened?
Synchronized expiry — a nightly job (or the same TTL set on everything) means all keys die in the same second, and the whole fleet stampedes the DB on cold refill. Fixes: jitter the TTLs, pre-warm hot keys after the flush, and single-flight the rebuild so ten thousand misses become one query.
Q4Redis is down for 12 minutes at peak. Describe what your system does.
It degrades, it does not die. Reads that can be stale serve the last local copy; the rest fall through to SQL but through a rate limiter and a circuit breaker so we do not stampede a box built for 8% of traffic. Write paths are unaffected because the DB is the truth. When Redis returns, we keep the limiter on while the cache warms, then release it. And on-call knew at minute one, because we alarm on hit ratio, not on ping.
Q5You have six API servers and sessions in IMemoryCache. What breaks, and what is the fix?
Whichever server created the login is the only one that recognises the user; the load balancer sends the rest to strangers, so the user is logged out at random. Sticky sessions are a bandage that breaks on deploy. Fix: a shared store — sessions in Redis (ASP.NET Core's distributed cache) or self-contained signed tokens.
Q6Design a cache key for a per-tenant, per-language product page. Why each segment?
t:{tenantId}:product:{id}:{culture}:v{ver}. Tenant first, because a shared key is a cross-tenant leak. Culture, because the copy differs. Version, so a bulk price change bumps ver and orphans every stale entry at once instead of scanning keys. Fixed order and one builder method so no controller invents its own shape.
Q7Which of these would you cache, and which would you refuse: account balance, category tree, exchange rate set hourly, stock at checkout, user permissions?
Category tree: yes, long TTL. Exchange rates: yes, but the TTL is the update interval. Permissions: yes, with invalidation on role change, because it is read on every request. Account balance: refuse. Stock at the moment of ordering: refuse — read the live row with a lock. The pattern: cache where “a minute old” is a shrug, refuse where it is a liability.
Q8Your cache hit ratio is 41%. Is the cache working?
No — you are paying for memory, complexity, and staleness and getting little back. Either the TTL is far too short, eviction is chewing the working set (memory too small), or the data is not actually hot (unique per user, changes constantly). The fix is to pick fewer, hotter keys with longer TTLs, or remove the cache and fix the query.
Q9Dashboard generation takes five minutes and hundreds of users refresh at 9 a.m. What is the architecture?
Cache the result, not the rows. A scheduled generator produces the payload per active tenant every 60 s into Redis under a tenant-scoped key; readers get it in milliseconds. Serve stale during rebuild, single-flight any on-demand refresh, throttle the “refresh now” button, and stop generating for idle tenants. And the generator should read a replica or warehouse, not the OLTP box.
Q10Write-through or cache-aside for a reference dataset that changes twice a month and must never be wrong?
The “never wrong” clause is the deciding word. Cache-aside with a delete-after-commit and a long TTL gives speed with a small stale window; write-through removes that window at the cost of write complexity. For data that changes twice a month and is used for legal calculation, I would go further: don't rely on a cache for correctness — version the dataset, load it explicitly, and let the version number be the invalidation. Then the cache is only a performance detail.

FINAL — CARRY THESE FORWARD

Architect Mindset, Day 5

Five rules. Not about Redis — about copies, clocks, and failure.

01

A cache is a copy, and a copy must have an expiry date.

Every key gets a TTL. TTL is not a performance knob; it is the mechanism that forgives every invalidation path someone forgets to write. A cache with no expiry is a slow leak with a friendly name.

02

You are not buying speed. You are trading freshness for it.

Ask how wrong the data may be before asking how fast it must be. If the answer is “not at all”, the data does not belong in a cache — it belongs in a transaction on the source of truth.

03

Assume the cache can vanish in the middle of your busiest minute.

Then design the app so that minute is slow, not fatal: fall back with limits, serve stale, break the circuit, warm before you relax. If losing Redis loses the product, you built a database with no guarantees.

04

A thousand misses for one key is one query.

Single-flight, stale-while-revalidate, jittered TTLs, pre-warm. The cache's job is to protect the database — including from its own behaviour.

05

The key is a contract: unique, predictable, tenant-safe, one builder.

In multi-tenant SaaS the key is a security control, and hit ratio is the metric that tells you whether the whole idea is working. Measure it or delete it.
