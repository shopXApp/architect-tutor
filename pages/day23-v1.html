PART 01 — START LIKE AN ARCHITECT

Do Not Draw Microservices on Minute One

The most common interview mistake is opening with "I will create 12 microservices." That is a solution looking for a problem. An architect starts with who uses the system, what must be true, and how big it is. The boxes come last — and only the boxes that earn their place.

WHY NOT START WITH SERVICES?

If you split the system before you understand it, you turn simple in-program calls into network calls that can fail, lag, and disagree with each other. Every service boundary is a promise to operate distributed databases, retries, timeouts and monitoring. Draw that cost on the whiteboard only when a real constraint — traffic volume, team independence, failure isolation — pays for it.

The order an architect actually follows

  1. Functional requirements — what the system must DOList the user-visible features: register, request a ride, pay, rate. No technology words yet.
  2. Non-functional requirements — what the system must BEHow fast, how available, how consistent, how big. These are the constraints that shape architecture.
  3. Scale in real numbersRegistered users mean nothing. You need peak updates per second and concurrent rides.
  4. The core flow end to endOne rider, one driver, one ride — happy path first, then every way it can break.
  5. The data and its personalityFast-moving location data behaves nothing like payment records. That difference drives the whole design.
  6. The simplest design that survives itA modular "monolith" (one deployable application with clear modules) plus a specialized location store is a perfectly senior starting point — with a path to split later.

Plain English: functional requirements are the things users can do — the functions of the product. Group them by who uses them.

Non-functional requirements (the qualities)

Plain English: non-functional requirements say how well the features must work — the "-ilities". Each one below quietly decides part of your architecture, so the table shows the architecture impact. Always attach numbers; "fast" and "reliable" are feelings, not requirements.

REQUIREMENT WHAT IT MEANS IN SIMPLE ENGLISH HOW IT CHANGES THE ARCHITECTURE

PART 02 — DEFINE REALISTIC SCALE

Turn Marketing Numbers Into Engineering Numbers

"50 million users" tells you almost nothing. You must walk the funnel: registered → daily active → online at peak → requests per second. Here is the whole calculation with easy interview math.

OUR ASSUMPTIONS (STATE THESE OUT LOUD)

Registered riders 50,000,000
Registered drivers 5,000,000
Daily active riders 10,000,000 (20% of registered)
Drivers online in the peak hour 1,000,000
Rides per day ~20% of active riders take a ride = 2,000,000 rides/day
Coverage Multiple cities, multiple countries

1 · Location updates per second (the big one)

A moving driver app sends its location every 4 seconds. During the peak hour, 1 million drivers are online.

THE MATH

1,000,000 drivers ÷ 4 seconds = 250,000 location updates every second at peak.

Average across the whole day is far lower (maybe 40–60k/s) — but you design for the peak, and spikes inside the peak (stadium exit) can multiply a single city 5–10×.

Each update is tiny — driver id, latitude, longitude, timestamp, maybe heading and speed: roughly 100 bytes.

NETWORK MATH

250,000 × 100 bytes = 25 megabytes/second of raw inbound data (~200–250 Mbit/s, more with encryption overhead). Not enormous in bandwidth — enormous in write rate. This is why the bottleneck is processing, not network pipes.

2 · Ride requests per second

2 million rides/day. Ride requests cluster into the evening peak: assume 15% of the day's rides happen in the busiest hour.

THE MATH

2,000,000 × 15% = 300,000 requests in the peak hour.

300,000 ÷ 3,600 seconds ≈ ~83 new ride requests/second on peak average.

Traffic is never smooth — apply a burst multiplier of ~4× → design for ~350 requests/second globally, with a single hot city owning a large share.

83 requests/sec looks small next to 250k location updates/sec. That contrast is the most important number on the whiteboard — it tells you where the architecture's center of gravity is: location ingestion, not ride booking.

3 · General API traffic

Riders open the app, move maps, see ETAs, check history. Assume ~100 API calls per active rider per day:

THE MATH

10,000,000 × 100 = 1 billion API calls/day.

Concentrate ~20% into 4 peak hours: 200,000,000 ÷ 14,400s ≈ ~14,000 requests/second, with headroom for bursts → design around 25–30k RPS for the API layer.

4 · Concurrent rides

Assume ~15% of online drivers are on a trip at any peak moment:

THE MATH

1,000,000 × 15% = ~150,000 concurrent trips.

Each trip streams driver position to one rider. That is 150,000 small real-time fan-out streams — handled by persistent connections, not by the rider refreshing the database.

5 · Database workload

  • Writes: ~83 rides/sec peak average, ~350/sec at burst. Each ride creates a handful of records (ride, trip events, payment). Comfortable for a well-indexed SQL database — but location writes (250k/sec) must never hit it.
  • Reads: history, profiles, pricing config — typically 10–50× the writes; served with replicas, caching, and read-optimized stores.
  • Storage growth: 2,000,000 rides/day × ~2 KB of trip record = ~4 GB/day ≈ 1.5 TB/year of core history, before GPS breadcrumbs, replicas and analytics copies.

6 · The scale summary to draw on the board

WORKLOAD PEAK SIZE MAIN VICTIM IF UNDER-DESIGNED
Location updates ~250,000 / sec In-memory geo store + ingestion tier
General API calls ~25–30,000 / sec API servers, cache, database replicas
New ride requests ~350 / sec (burst), highly regional Matching + driver reservation logic
Live trip streams ~150,000 concurrent Real-time connection gateway
Payments Hundreds/sec, but zero tolerance for error Payment service + idempotency + reconciliation
RULE OF THUMB TO QUOTE

"Location traffic is write-heavy, massive and disposable; ride traffic is small, transactional and permanent. Those two workloads cannot share a home — that one fact dominates the entire design."

PART 03 — CORE BUSINESS AREAS

Slice the Business Before You Slice the Software

A business area (also called a domain) is a part of the business that owns one kind of responsibility and one kind of data. Even in a monolith, drawing these boundaries keeps code clean — and they become the natural service boundaries if and when you split.

Rider Rider profile, preferences, payment-method references, history views. Rider profile, saved places, settings. Driver availability or matching. Authentication.

What to combine first, what to split later

COMBINE AT THE STARTOne deployable application with clear modules: Rider + Driver profiles + Authentication + Rating, and Ride + Trip + Pricing in the same transactional boundary. A small team ships faster, and one database gives free consistency.
SPLIT OUT FIRST (DAY ONE)Location ingestion and the real-time gateway — their traffic profile (250k writes/sec, persistent connections) is so different they cannot sensibly share scaling or deployment with booking.
SPLIT WHEN GROWTH FORCES ITMatching (hot, latency-critical, per-city), Payment (different risk/compliance rules and release cadence), Notification (spiky, fan-out heavy), Pricing (business changes rules weekly — isolate the churn).
SPLIT BY TEAM / REGION LATERReporting/Analytics moves to its own warehouse early as a consumer; Driver onboarding and fraud may become independent as teams grow. Split on measured pain or organizational need — never on fashion.
THE INTERVIEW LINE

"I would start as a modular monolith for all transactional areas, with Location and the real-time gateway separate from day one because their workload is categorically different. Matching and Payment are the next splits, triggered by load and compliance — and each split is driven by a measured bottleneck, not a guess."

PART 04 — HIGH-LEVEL ARCHITECTURE

The Minimum Set of Boxes That Earn Their Place

Read the diagram top to bottom: apps at the edge, an API gateway, the transactional services in the middle, the special high-speed location lane on the right, messaging connecting async work, and three kinds of storage at the bottom. Nothing is here because it is fashionable — every box answers a "why do we need it?" below.

FIG 1 — HIGH-LEVEL ARCHITECTURE: THE BOOKING LANE AND THE LOCATION LANE SHARE ALMOST NOTHING

Why do we need each component?

RIDER & DRIVER APPSThe two user surfaces. The driver app is also the system's biggest sensor — it produces the location stream. They are the only parts users see, so they must keep working in weak networks (queue and retry).
API LAYER / GATEWAYOne front door: authenticates every call, enforces rate limits (a stolen token cannot flood matching), routes to services, and hides internal topology. Stateless, so we add copies horizontally during spikes.
AUTHENTICATIONIssues and checks identity for two populations with different risk (drivers carry background checks). Centralizing it means every other service can simply trust a verified token.
RIDER / DRIVER SERVICESOwn profiles, vehicles, documents, history. Classic transactional data — durable, modest traffic, strong consistency.
LOCATION INGEST + GEO STORE250k updates/sec must be absorbed and immediately queryable. Workers validate and write to an in-memory geographic store — memory, because disk cannot keep up; geographic index, because the only question is "who is near this point". Data expires in seconds.
MATCHINGTurns "find me a ride" into one concrete, reserved driver: queries the geo store, ranks candidates, dispatches offers in waves with timeouts, and performs the atomic reservation. Isolated because it is hot, latency-sensitive and city-scoped.
RIDE / TRIP SERVICESThe system of record and the state machine for money-making events. Every transition is durably stored; this data is never ephemeral.
PRICINGIsolated because business users change fare and surge rules constantly. Versioned configuration means the price quoted at request time is the rule set the final fare can be explained against.
PAYMENTWraps an external provider with retries, idempotency keys, timeouts and reconciliation — the provider WILL be slow or fail; this service makes that survivable. It never sees raw card numbers (tokenization).
NOTIFICATIONPush/SMS/email fan-out for offers and ride updates. Spiky and non-critical, it consumes events so a push outage never blocks a ride.
MESSAGE BROKERThe backbone for background work: ride events fan out to notification, receipts, ratings, analytics and fraud without the booking transaction waiting for them. Also buffers spikes and retries.
REAL-TIME GATEWAYHundreds of thousands of persistent socket connections live here, separate from request/response APIs, so a traffic surge of sockets never starves booking requests (and vice-versa).
TRANSACTIONAL DATABASEThe durable truth: accounts, rides, trips, payments. Strong correctness, constraints, auditability — partitioned by region/city as it grows.
CACHEAbsorbs hot reads (city config, pricing rules, session/profile fragments) so spikes do not hammer the database. Never the source of truth.
LONG-TERM / ANALYTICS STORETrip history, heat maps, finance and ML features live in a warehouse fed by events — big scans and aggregations that must never run against the live booking database.
MONITORINGA ride platform fails in weird, distributed ways. You need city-level dashboards, alerts on matching time and location lag, distributed tracing and business metrics (cancellations, no-driver rate), not just CPU graphs.
WHAT IS DELIBERATELY NOT ON THIS DIAGRAM

No machine-learning platform, no service mesh, no multi-region saga engine. Components are added when a measured problem needs them. In an interview, drawing popular boxes you cannot justify invites the question "what breaks if we remove it?" — and if you cannot answer, you lose credibility.

PART 05 — RIDE BOOKING FLOW

One Ride, End to End

Walk this flow slowly in the interview and label each step: does the user wait for it (immediate), can it run later (background), is it an event, or is it money/state that must be instantly correct? That labeling is what separates an architect answer from a feature list.

  1. IMMEDIATERider opens the appThe app authenticates, loads profile/payment and city pricing config (cacheable, fast).
  2. IMMEDIATERider sets pickup and sees the mapThe Location service answers "available cars and ETA near this point" from the in-memory geo store — read-only, sub-500ms, no ride exists yet.
  3. MUST BE CORRECTRider requests a rideA Ride record is created in state Requested with a unique request id. The rider must get a quick acknowledgement ("searching…"), even though matching is still running.
  4. IMMEDIATEFind nearby driversMatching queries the geo store in expanding rings: nearest available drivers of the right vehicle type, excluding drivers with open offers.
  5. IMMEDIATESelect suitable driversRank by ETA/distance, rating, cancellation rate, and business rules. Pick a first wave (often one, sometimes a handful).
  6. EVENTSend ride request (offer) to driver(s)Offer pushed through the real-time gateway with a countdown (e.g. 10–15s). A short-lived offer record holds the driver id and expiry.
  7. MUST BE CORRECTA driver acceptsThe accept does an atomic compare-and-set: only succeeds if that driver is still free and the ride is still open. All other offers are instantly revoked; other riders' offers to that driver fail.
  8. EVENTRide confirmedRide moves to DriverAssigned. Rider receives driver details and live location; drivers not chosen get "ride taken". Event: RideConfirmed.
  9. EVENTDriver drives to pickupLive location streams driver → rider via the real-time gateway; ETA updates. Rider state: DriverArriving.
  10. EVENTDriver arrives and marks arrivalState DriverArrived; rider notified; waiting-time meter may start.
  11. MUST BE CORRECTDriver picks up rider and starts tripState TripStarted, timestamp captured. From here the trip breadcrumb stream is archived (it becomes billing evidence).
  12. EVENTRoute tracking during tripPeriodic location points accumulate; rider sees progress; safety features (share trip) read the same stream.
  13. MUST BE CORRECTDriver ends the tripState TripCompleted; distance and time totals are locked from the archived breadcrumbs.
  14. IMMEDIATEFare calculatedPricing computes the final fare server-side from trip totals and the rule/surge snapshot. The rider should see this within seconds.
  15. MUST BE CORRECTPaymentPayment creates an idempotent charge through the provider; success/failure is recorded exactly once; retries reuse the same charge id.
  16. BACKGROUNDRide finalized & receiptReceipt generation, notifications, ratings prompt, driver earnings, analytics and fraud checks run off the event stream.
  17. BACKGROUNDRide completedFinal state is immutable; driver returns to the available pool the moment they choose; rating and any refund/correction happen as follow-ups, never by reopening the ride.
CATEGORY STEPS WHY IT MATTERS
Needs an immediate response Map/cars display, ride request acknowledgement, nearby search, driver accept/reject, fare shown at end. Users wait with their thumb on the screen; latency directly cancels rides.
Can happen in the background Receipts, rating prompts, analytics, driver stats, fraud scoring, reporting, marketing. Nobody's trip fails because an analytics row is 30 seconds late.
Where events are useful Every state change emits one event: RideRequested, DriverAccepted, TripStarted, TripEnded, PaymentSucceeded. Many services react without the ride transaction knowing or waiting for them.
Must be instantly correct Ride creation, driver reservation/accept, state transitions, fare totals, charge result. Mistakes here are visible, financial, or create dangerous double work.
TIP — THE ACK PATTERN

The rider's "request ride" tap should NOT block until a driver accepts. The API acknowledges immediately ("searching"), matching proceeds, and the result arrives over the socket. A request that holds the connection for 20 seconds is both slow and fragile.

PART 06 — DRIVER LOCATION TRACKING

Location Is a Stream, Not a Row

This is the heart of the system. ~250,000 tiny updates arrive every second; each one replaces the previous one; nobody ever queries "the history of driver D's updates at 18:42" — except while on a trip. That personality demands a different home from normal business data.

The write path (driver phone → system)

  1. The driver app batches and sendsEvery ~4 seconds while moving (it can slow to 15–30s when stationary, and stop when offline). It sends lat/long, heading, speed and the app's online/on-trip state. Weak network? The app retries briefly; old points are worthless, so it drops stale ones rather than flooding catch-up.
  2. Location ingest tier absorbs the floodMany stateless ingest workers behind a load balancer. They do only cheap validation (sanity checks on coordinates, auth, de-duplicate) — no database writes, no business logic. Scale this tier by CPU independently of everything else.
  3. Write straight into the in-memory geo storeEach update overwrites that driver's current position key. No history, no disks in the hot path. The store is sharded (partitioned) by city/geographic cell so no single machine holds a million dots.
  4. Attach availability stateEach dot is tagged: available / on offer / on trip / paused. Matching only ever sees dots tagged available — driver availability rides on top of location rather than living in a separate slow table.
  5. Heartbeats expire stale dotsEvery position has a TTL (time-to-live — an automatic expiry, e.g. 15–20s). If a driver's app dies or loses network, the dot vanishes on its own; an offline driver is never offered a ride. Reconnect simply starts writing again.

The read paths (who reads positions)

  • Matching reads nearby available dots — high volume, tiny radius, must be milliseconds.
  • Rider maps read car dots around a pickup (throttled and slightly fanned-out so ten thousand riders opening the app in one district do not each trigger raw queries).
  • Live trip tracking reads one named driver repeatedly and streams it to exactly one rider.

Driver moving while a rider is requesting

Positions are seconds-old the moment they are read — the design accepts this. Matching works with small uncertainty by: searching a slightly larger radius, re-checking the driver is still available and near at accept time, and computing ETA with current road data. If a driver has moved too far or gone offline by the time the offer lands, their accept is rejected and matching continues with the next candidate.

Four storage personalities, clearly separated

KIND OF DATA EXAMPLE HOME LIFETIME
Fast in-memory, current value Where every online driver is right now + status. RAM geo store, sharded by city, TTL expiry. Seconds; overwritten constantly.
Geographic search index "Available drivers within 2 km of this point." Same in-memory store with a grid/geohash index. Rebuilt continuously from the stream.
Trip breadcrumbs (billing evidence) Positions during an active trip. Appended to durable trip storage (often via the broker). The life of the account / legal period.
Long-term history Completed trips, distance, heat maps. Transactional DB then warehouse. Years.
WHY A DIFFERENT STORAGE APPROACH?

A normal relational database is built to durably save rows and answer questions about history — writing 250,000 throwaway rows per second into it would burn the disk, the transaction log, and replication, and still be slower than RAM. Location data is write-heavy, short-lived, spatial and replaced-not-appended. Use memory for the present; persist only what a fare or a court case might need later.

FAILURE INSTINCT TO MENTION

If the in-memory geo store loses a node, its dots go dark and matching simply treats those drivers as offline — drivers' apps reconnect to healthy nodes (often routed by consistent partitioning), positions rebuild in seconds, and no permanent data is lost because nothing permanent lived there. Designing the store to be disposable is what makes this failure cheap.

PART 07 — FINDING NEARBY DRIVERS

"Which Available Drivers Are Close to This Rider?"

Answered millions of times per minute. The trick is to never scan every driver: divide the map into small areas so each search touches only a handful of cells, and keep the answer in memory.

FIG 2 — GRID / GEOHASH GROUPING: DRIVERS ARE STORED UNDER THE CELL THEY CURRENTLY OCCUPY

The idea in simple terms

  • Grid or area-based grouping: slice the world into small squares (often called a geohash — a short text code for a rectangle, e.g. gcpvj2). Every driver's position is stored under the code of the cell they are in.
  • Location indexing: instead of computing the distance to a million drivers, the system opens the rider's cell and its eight neighbours. All drivers outside are ignored without a single calculation.
  • In-memory location data: the cell → drivers mapping lives in RAM on nodes partitioned by region, so a lookup is microseconds, not a disk query.
  • Updating position: when a driver crosses a cell boundary, the driver id is removed from the old cell's set and added to the new one — a couple of in-memory set operations.
  • Removing unavailable drivers: TTL expiry removes dead dots; accepting an offer or starting a trip flips the dot's status so searches skip it; finishing a trip makes the driver available again instantly.
  • Ring expansion: search 1 km; if too few drivers, search 2 km, then 4 km — with per-country/city caps and fare implications shown to the rider ("drivers far away, higher fare?").

The four-way trade-off

LEVER PULLING TOWARD ACCURACY PULLING TOWARD SPEED / COST
Accuracy Exact distance math, tiny cells, fresher updates (every 2s), live road ETA for every candidate. More CPU per search, more updates/sec, more machines.
Speed Coarser cells, precomputed nearest lists, cap candidates to 20, throttle map reads. Slightly worse picks; occasionally offers a driver a few hundred meters farther.
Cost Slow update frequency when stationary; fewer, bigger geo nodes; batch map fan-outs. Dots are slightly older; empty suburb searches less precise.
Complexity A proven in-memory data store with spatial queries, one sharding scheme, TTL built-in. Building a custom spatial engine "for control" is a classic résumé-driven trap.
THE PRAGMATIC ANSWER

Cell-based in-memory index, cells sized so a search touches a few hundred dots at most, ring-expansion for sparse areas, and accept-time re-validation to forgive stale positions. Perfect nearest-driver optimality is not the goal — best driver reachable within seconds is.

PART 08 — DRIVER MATCHING

From Candidate List to One Confirmed Driver

We deliberately stay at architecture level — ranking algorithms (the math that scores drivers) are a pluggable rule inside the Matching service. The architect's concern is the lifecycle, races, timeouts and fallbacks.

Factors that influence the pick

DISTANCE & ETAStraight-line distance for the first cut; road ETA (traffic-aware) for the final ranking — ETA beats raw distance.
AVAILABILITY & STATUSOnly dots tagged available, no pending offer, not over daily driving limits, inside the city service area.
VEHICLE TYPEThe rider selected UberX / XL / premium / accessibility — filter before ranking.
DRIVER QUALITYRating, recent cancellation/acceptance rate, completion rate — protects service quality.
BUSINESS RULESSurge priority, scheduled rides, fleet partners, fairness/rotation so the same driver is not spammed, driver destination filters.
CONTEXTCity rules, airport zones, ride duration estimate vs driver's remaining shift, fraud signals.

The matching lifecycle

  1. Matching startsThe Ride record (Searching) triggers the matching engine for that city's shard. It snapshots the request's needs: location, vehicle, pricing tier.
  2. Build the candidate listGeo search with ring expansion; apply filters; rank; cap to a small list.
  3. Dispatch in wavesWave 1: the single best driver (or a small first group depending on market tightness) receives an offer with a 10–15s expiry. No answer or reject → wave 2 to the next drivers, expanding the radius. Waves balance driver experience against match speed.
  4. Reserve while offeringAn offered driver is marked "on offer" so they are not simultaneously offered to another rider — a short-lived reservation with an automatic expiry (Part 9).
  5. Acceptance is atomicThe first valid accept wins; the ride moves to DriverAssigned, all sibling offers are revoked, the winner's status becomes assigned.
  6. Two drivers trying to acceptBoth accept clicks race to one compare-and-set. The database/store executes one winner; the loser gets "ride already taken" and stays available.
  7. No driver acceptsAfter the final wave: notify the rider, mark NoDriverFound, suggest a retry, different tier, later time, or surge adjustment. Nothing is half-booked; no driver is stuck.
  8. Timeouts self-healEvery offer, search and reservation carries an expiry handled by a sweeper, so a crashed node can never leave drivers or rides locked forever.
ARCHITECTURE, NOT ALGORITHM

Say this: "The ranking function is a versioned component behind an interface. The architectural guarantees are: only available drivers are offered, an offer reserves the driver for seconds, acceptance is a single atomic compare-and-set, every wait expires, and failure ends in a clean state rather than a stuck ride." That answer covers ML-based matching later without redesigning the platform.

PART 09 — PREVENTING DOUBLE BOOKING

One Driver Cannot Belong to Two Rides

The scenario: rider A and rider B tap "request" within the same second; driver D is the nearest for both; both offers/requests are in flight. The system must guarantee that D ends the race on exactly one ride.

FIG 3 — A COMPARE-AND-SET ON DRIVER STATUS SERIALIZES THE RACE

The five mechanisms (and what each term means)

  1. Atomic state change (compare-and-set)Atomic means "all-or-nothing, indivisible" — no other request can see it half-done. A compare-and-set says: change driver D's status from AVAILABLE to RESERVED(ride=A) only if it is still AVAILABLE. The store executes this as one operation; A's succeeds, B's sees the changed value and fails.
  2. Short-lived reservations with TTLThe "offer" holds the driver for 10–15 seconds only. If the driver's app crashes or the matching node dies, the reservation expires and the driver is free again. Locks that never expire are how whole cities freeze.
  3. Database constraints as the final wallA unique rule in the transactional database: at most one active ride per driver (and one active ride per rider). Even if a bug slips past the in-memory logic, the database rejects the second insert. Constraints are the last line of defense, not the only one — they are slower than the in-memory reservation.
  4. Optimistic version numbersEach driver record carries a version. To update it you must present the version you read; if someone else changed it first, your write is rejected and you retry with fresh data. (Optimistic = don't lock first; check at write time. Pessimistic = lock the row up front.)
  5. Idempotent ride request + compensationIf the rider's app retried the request (network blip), duplicate requests carry the same client-generated id and collapse into one ride. If a reservation must be undone (ride cancelled, offer timed out), a compensating action releases the driver back to available.
APPROACH HOW IT WORKS GAIN COST / TRADE-OFF
Pessimistic lock Lock the driver row before offering. Simple mental model, strictly safe. Contention at hot spots; a forgotten lock blocks the driver; database round-trips slow matching.
Optimistic CAS / version Offer optimistically; verify-and-flip status at accept. Fast, no long locks, scales well. Losers must retry; logic must handle failed flips (it does — next wave).
In-memory reservation + TTL Hot reservation state in the geo/matching store, auto-expiring. Microsecond speed; self-healing; fits the location lane. Must be sharded carefully; DB constraint still backs it for durability.
DB unique constraint One active ride per driver enforced at insert. Absolute last-line guarantee, auditable. Not fast enough to be the primary matcher; returns an error you must handle.
RECOMMENDED COMBINATION

In-memory TTL reservation while offering (speed) → atomic compare-and-set at accept (correctness under the race) → unique constraint in the transactional database when the ride is persisted (durability and audit) → sweeper that expires abandoned reservations. Three layers, each cheap, none carrying the whole guarantee alone.

PART 10 — REAL-TIME COMMUNICATION

Both Apps Must Know Things the Instant They Happen

Driver location moving on the rider's map, "driver accepted", "driver arriving", trip started, trip ended, cancellation, price changes — these are pushed to the apps, not pulled repeatedly by them.

The three approaches, compared honestly

APPROACH WHAT IT MEANS SIMPLE? FAST? SERVER LOAD RELIABILITY NOTES
Polling App asks "any update?" every few seconds. Very simple. Slow — updates up to one interval late; battery/network heavy. Enormous: 1M drivers'/riders' apps × a request every 3–5s = hundreds of thousands of mostly-empty calls/sec. Works through almost any network/proxy; easy fallback.
Long polling App asks, server holds the request open until there is news, then app asks again. Medium. Near-instant when an update exists. Lower wasted calls, but holding millions of open HTTP requests is expensive and reconnect churns. Good fallback where persistent connections are blocked.
Persistent connection (WebSocket / real-time) One open two-way socket per online app; events flow both ways immediately. More moving parts (gateway cluster, connection routing). Instant; ideal for moving dots and offer countdowns. Lowest per-update cost once connected; one connection serves everything. Must handle reconnects, missed-message catch-up, and scale the connection gateway horizontally.

How a ride platform uses them

  • Persistent sockets are the default for both apps, terminating at a dedicated real-time gateway cluster, partitioned by region. The business services publish events; the gateway fans them to the right sockets.
  • Push notifications (mobile OS push / SMS) are the fallback when the socket is dead (app in background, network switched). "Your driver arrived" must arrive even if the socket does not. Critical: offers to drivers are sent over BOTH socket and push so backgrounded apps still ring.
  • Reconnect is a first-class feature: on reconnect the app sends "last seen event version"; the server replays anything missed. The ride's true state always lives server-side — the socket is just a pipe, never the source of truth.
  • Connection affinity: a given user's socket lands on a gateway; services don't need to know which — they publish to an internal channel (driver id / ride id) and the gateway mesh routes it.
WHY NOT JUST POLL?

Polling at ride-platform scale means paying for millions of requests that return "nothing new", while still being up to one interval late. One socket replaces hundreds of polls. Keep polling only as an emergency fallback for hostile networks — say that in the interview and you show pragmatism rather than dogma.

PART 11 — RIDE STATE MANAGEMENT

A Ride Is Always in Exactly One Legal State

A state machine is just a list of allowed situations (states) and the legal moves between them (transitions). It is the cheapest way to prevent impossible situations like charging for a ride that never started, or completing a cancelled ride.

FIG 4 — THE RIDE STATE MACHINE. SOLID ARROWS ARE THE HAPPY PATH; DASHED ARROWS END IN CANCELLED.
STATE WHAT IT MEANS
Requested Ride record created; not yet searching (validation/payment pre-check).
Searching Matching is actively offering drivers in waves; countdowns running.
DriverAssigned One driver has accepted and is reserved; rider got details.
DriverArriving Driver en route to pickup; live ETA streamed.
DriverArrived Driver marked arrival at pickup; waiting-time rules may begin.
TripStarted Rider picked up; billing clock/distance running; breadcrumbs archived.
TripCompleted Driver ended the trip; totals locked; fare being calculated/charged.
Cancelled / NoDriverFound Terminal failure states with reason codes and any cancellation fee policy.

Invalid transitions the system must reject

  • Completed → Searching (a finished ride never re-enters matching — create a new ride).
  • Cancelled → TripStarted (a dead ride cannot start; a driver tapping "start trip" on a cancelled ride gets an error).
  • TripStarted → DriverAssigned (cannot un-assign mid-trip; rerouting is a separate support flow).
  • Requested → TripStarted (skipping assignment/arrival hides fraud and breaks billing).
  • PaymentDone twice (terminal state; duplicates rejected — links directly to Part 13).

How the architect protects the state

  1. One transition rule, enforced server-side only: a table of (current state, event) → next state. Any event not in the table is rejected. Apps never decide state.
  2. Optimistic concurrency: updates are "set state = X where id = ? and state = Y and version = n". Two drivers' devices ending the same trip cannot apply twice.
  3. Append-only event history: states change by appending immutable events (Requested at t0, Assigned at t1…). You can reconstruct any ride, audit disputes, and feed analytics — the current state is just the fold of that history.
  4. Idempotent commands: "driver arrived" delivered twice (socket + push retry) must produce one transition, not two.
  5. Sweepers for stuck states: a ride in Searching for 60s, or assigned with no movement for 5 minutes, triggers automated timeouts and notifications.
WHY THIS MATTERS SO MUCH

Every other hard problem — double booking, duplicate payment, driver disconnect, retries — is ultimately an illegal state change arriving late or twice. The state machine is where those problems go to die. In an interview, drawing it early demonstrates maturity faster than any technology choice.

PART 12 — PRICING

Quote Before, Bill After — Never the Reverse

Pricing is business policy in code: it changes every week, varies by city, and moves money at scale. That is why it lives in its own component with versioned rules instead of being hardcoded inside the ride flow.

What makes up a fare

  • Base fare — a fixed pickup charge per city and vehicle type.
  • Distance charge — per km/mile of the actual route.
  • Time charge — per minute, including slow traffic and waiting after arrival.
  • Surge / dynamic pricing — a multiplier or fee when demand exceeds nearby supply, by area and time.
  • Taxes, tolls and airport fees — pass-through costs with legal rules per jurisdiction.
  • Discounts and promotions — applied predictably, with explicit audit of which promotion was used.

When fare is calculated — two different moments

MOMENT WHAT IS CALCULATED DATA NEEDED PROMISE LEVEL
Before requesting (estimate) Estimated range or upfront price using expected route & current surge. Pickup/drop-off, road-distance service, city config, live surge, vehicle type. Estimate (or upfront-guaranteed, which the business hedges with route models).
After trip ends (final fare) Exact fare from actual distance + time + tolls, using the rule snapshot. Archived trip breadcrumbs/totals, toll records, the pricing rules in force. Billable truth; drives the charge.

The architectural rules

  • Separate pricing from ride processing: the ride service should ask Pricing "what is the fare?" and never implement fare math itself. Business users then change rules without touching the transactional core.
  • Version and snapshot rule sets: the estimate records which pricing version and surge level applied. The final fare is computed against that snapshot — a rule changed mid-trip cannot silently rewrite the deal.
  • Server is the only calculator: phones send raw facts (locations, timestamps); fares are never computed on devices where they can be tampered with.
  • Handle surge cleanly: surge is computed per small area from live supply/demand, cached for very short windows, and shown/accepted before the rider books.
  • Prevent incorrect charges: validate totals inside plausible bounds (e.g. reject a $50,000 fare from a GPS glitch), cap waiting charges per policy, log every input, and route anomalies to a review queue rather than charging.
SIMPLE SUMMARY

Pricing = versioned city rulebook + live inputs + an audit trail. Estimate is a prediction; final fare is a calculation from evidence; the charge is a separate, idempotent step.

PART 13 — PAYMENT

Money Moves Exactly Once, Even When Everything Retries

The payment provider is an external system over the internet. It WILL be slow, fail, timeout, or send its confirmation late. The architecture around it assumes that from day one.

  1. STATERide completedTrip state terminal; distance/time totals locked.
  2. IMMEDIATEFare calculatedPricing returns the final fare with rule version and fare breakdown stored on the ride.
  3. MUST BE CORRECTPayment request createdA payment intent with a unique idempotency key (e.g. ride id + fare version) is stored in state PENDING.
  4. EXTERNALCall the payment providerCard data is never on our servers — a tokenization provider handles cards; we send token + amount + key over HTTPS.
  5. EVENTProvider confirms success or failureConfirmation may come as the direct response OR later as a webhook (an async server-to-server callback). Both paths carry the same key.
  6. MUST BE CORRECTRecord the result exactly onceSuccess → payment SUCCEEDED, ride finalized. Failure/decline → FAILED, retry policy or alternate payment / debt flow.
  7. BACKGROUNDRide finalization & receiptReceipt, driver earnings, invoice, analytics events fan out from PaymentSucceeded.
  8. BACKGROUNDReconciliationA scheduled job compares our ledger against provider settlement reports and fixes the rare mismatches (including webhooks that never arrived).
IDEMPOTENCY — IN VERY SIMPLE ENGLISH

An idempotent operation gives the same result whether you call it once or ten times. Imagine pressing an elevator button repeatedly: the elevator still comes once. Every payment request carries a unique key (the same key on every retry). The provider keys on it: the first call charges; the second, third and fourth calls with the same key return the existing result and never create a second charge. That is the entire trick that prevents double charging across retries, timeouts and duplicate messages.

SITUATION WHAT GOES WRONG HOW THE ARCHITECTURE HANDLES IT
Need to retry A network blip failed the call; retry could double-charge. Retry with the same idempotency key and exponential backoff (wait 1s, 2s, 4s…); retries are safe by design.
Duplicate payment request Rider app double-taps; queue delivers twice; failover re-runs the job. Key derived from ride id (plus fare version); unique constraint in payment table; duplicates collapse to the first transaction.
Provider down Charges cannot be made for minutes. Payment stays PENDING; rider is not blocked from leaving; queued retries + reconciliation; alerting; graceful messaging ("receipt on its way").
Timeout — did it charge? The provider may have charged but the response was lost. Never blindly charge again: poll the transaction status by key, or wait for the webhook. Unknown → reconcile; never assume failure.
Late confirmation / webhook Success arrives seconds or minutes later. Webhook handler is itself idempotent; arriving twice or out of order still produces one SUCCEEDED transition.
Refund needed Cancellation policy, overcharge, support case. Refund is its own idempotent transaction linked to the original charge; ledger keeps both records; never delete or rewrite the original.
THE MENTAL MODEL TO STATE IN THE INTERVIEW

Distributed systems promise "at least once" delivery — assume every request may arrive multiple times. Money flows require "effectively once" outcome. Idempotency keys + unique constraints + a reconciliation backstop convert at-least-once delivery into exactly-once effect.

PART 14 — MESSAGING & BACKGROUND WORK

Everything That Can Wait, Should Wait

Asynchronous processing simply means: instead of doing task B while the user waits, publish an event ("ride ended") and let background workers do B later through a message broker — a central post office that safely holds events until consumers process them.

BACKGROUND TASK TRIGGER EVENT WHY IT MUST NOT BLOCK THE MAIN FLOW
Notifications (push/SMS/email) Accepted, arriving, ended, receipts. A slow SMS vendor must not delay confirming the ride; retries happen in the background.
Receipt & invoice generation PaymentSucceeded. Rendering PDFs and emails is slow and irrelevant to the charge completing.
Analytics & heat maps All lifecycle events. Heavy aggregation belongs in the warehouse; coupling it to booking adds latency and blast radius.
Driver statistics & ratings RideCompleted, RatingSubmitted. Averages and quality scores can be seconds/minutes old without harming anyone.
Fraud checks Request, accept, payment events. Most fraud scoring runs async; a slow rules engine never freezes the street. High risk can still synchronously block specific actions.
Surge & supply computation Location + request streams. Multiplier calculation is continuous and batchy; readers fetch a recent cached value.
Settlement / earnings / reporting TripCompleted, PaymentSucceeded. Finance pipelines run on schedules; correctness matters, immediacy does not.
Timeout sweepers / cleanup Scheduled timers. Expiring stale offers and unlocking abandoned reservations keeps the system self-healing without user involvement.
THE DECISION RULE

If the user is staring at a spinner waiting for the answer (match result, charge result), keep it synchronous and fast. If the work satisfies another consumer (marketing, finance, data science, a messaging vendor), make it event-driven. The broker also acts as a shock absorber during spikes: producers keep moving while consumers catch up — with retries and a dead letter queue (a quarantine area for messages that repeatedly fail) so nothing is silently lost.

PART 15 — DATA STORAGE

Three Data Personalities, Three Homes

One database cannot be simultaneously a 250k-write/second in-memory stream, a strict financial ledger, and a multi-petabyte analytics warehouse. Match each dataset to the storage built for its workload — this is called polyglot persistence, used deliberately, not for show.

HOME DATA THAT LIVES THERE WHY THIS HOME
Main transactional database (durable, SQL-style) Riders, drivers (identity/vehicle/docs), rides, ride state transitions, trips (summary + billing breadcrumbs), payment intents & ledger, promotions used, ratings. Strong correctness, transactions (all-or-nothing multi-row changes), enforced constraints (one active ride per driver), auditability. Partitioned by region/city as it grows; read replicas for history and reporting reads.
Fast temporary storage (in-memory + cache) Current driver positions with TTL, availability status, live offers & reservations, matching wave state, sessions, short-lived surge values, hot config. Microsecond reads/writes, native spatial queries, millions of tiny overwrites/sec, automatic expiry. Losing it is harmless — it rebuilds from the driver stream within seconds.
Long-term storage (warehouse / object & search) Completed-trip history, raw event archive, financial settlement records, supply/demand datasets, reports, ML training data, document/photo object storage. Designed for huge scans and aggregations across years of data, immutable event logs, cheap storage. Fed asynchronously from the event stream; never touched by the live booking path.
WHY ONE DATABASE IS NOT IDEAL FOR EVERYTHING
  • Access patterns conflict: spatial circle queries vs ledger joins vs full-table aggregations need different engines and indexes.
  • Scale units conflict: location grows with online drivers; history grows forever; payments barely grow but demand the strictest guarantees.
  • Failure blast radius: a report query scanning a billion rows must never slow the database that assigns rides.
  • Lifecycle conflicts: location data dies in seconds; payment records live for years under legal retention.
BUT DO NOT OVER-SPLIT TOO EARLY

Day one: one transactional database for all durable data (schema organized by the business areas), one in-memory geo store, one warehouse pipeline. Extra specialized stores are added when a measured workload proves the need. Polyglot persistence is a response to pressure, not a starting lineup.

PART 16 — CACHING

Cache the Hot, Stable, Forgiving Reads

A cache is a small fast copy of data you would otherwise fetch slowly. It protects the database during spikes and shaves latency — but every cached value is a promise that stale data is acceptable.

WHAT TO CACHE WHY & TYPICAL TTL
City / surge / pricing configuration Read on every estimate and request; changes rarely. Short TTL (seconds to a few minutes) plus push-invalidation when operations changes a rule.
Driver availability summary for map views Pre-aggregated "cars in this view" counts per cell, refreshed every few seconds — far cheaper than raw queries per watching rider.
Frequently accessed rider/driver profile fragments Name, photo, rating, vehicle description shown on the match screen; TTL minutes; invalidate on profile edit.
Sessions / tokens / rate-limit counters Checked on every API call; must be fast by definition; naturally TTL-based.
Popular areas / ETA tiles / map metadata City-center ETAs and zone polygons are requested millions of times; compute once, serve many.

What must NOT be cached as truth

  • Wallet balance, payment status, final fare — money decisions read the ledger, not a copy.
  • The active ride state for state-transition decisions — the state machine checks the durable record; a stale "assigned" in cache can create double work.
  • Driver reservation/offer ownership for the final accept decision — the atomic compare-and-set is performed against the authoritative store.
  • Authentication/verification changes — a banned driver's revoked token must take effect quickly (short TTL + active invalidation).

The three cache questions you must always answer

EXPIRATIONEvery key gets a TTL matched to how stale it may be (seconds for supply, minutes for profile, longer for static config). No TTL = silent stale data forever.
CACHE FAILUREIf the cache dies, services fall back to the database — but with throttling, so a cache outage cannot stampede the DB into a second outage. The system degrades slower, not catastrophically.
STALENESSDecide per item: a 3-second-old "cars near you" is fine; a 3-minute-old surge multiplier may overcharge. Where staleness costs money, invalidate on change or skip caching.
STAMPEDE PROTECTIONWhen one hot key expires, let a single process refresh it while others reuse the old value briefly (or lock/refill in the background) — never let thousands of requests miss simultaneously.
KEEP IT IN ITS PLACE

Caching is a supporting actor in this architecture — the stars are the geo store and the state machine. If your answer to every scaling question is "cache it", the interviewer will find the one place caching cannot help (the atomic accept) and the design collapses.

PART 17 — SCALING

Scale Each Lane by Its Own Traffic Curve

Horizontal scaling means adding more identical servers behind a load balancer (versus vertical scaling — buying one bigger machine). Stateless services scale horizontally almost for free; stateful stores need partitioning.

COMPONENT HOW IT SCALES TRIGGER TO ADD MORE
API layer Stateless instances behind load balancers; autoscale by CPU and request queue length. p95 latency / CPU target.
Location ingest Many stateless workers; drivers are routed to workers/partitions by city cell so each dot lands in one shard. Incoming update lag (seconds-behind gauge).
In-memory geo store Sharded by geography (city → cells → partitions); replication for failover; hot districts get more partitions. Per-shard dot count and search latency.
Matching One matching engine "owns" each city shard and its reservations; add shards by splitting cells; stateless web tier around it. Match latency, time-to-assign, offer queue.
Ride / trip service Horizontally scalable app tier; transactional DB partitioned by city/region (rider/driver id affinity), read replicas. Write latency, queue depth, DB CPU.
Real-time gateway Connection servers scale by socket count (tens of thousands each); split from request API tier entirely. Connection count, memory per node.
Notifications Queue consumers scale independently per channel (push/SMS/email); vendor rate limits respected. Queue backlog / age.
Payment Modest volume — scale worker concurrency to provider rate limits; protect with queues and idempotent workers; multi-provider failover. Pending-payment age, provider errors.

Why location traffic and API traffic scale differently

  • Location is a flood of tiny writes from drivers only, geographically clustered, hitting a stateful sharded in-memory store. Its bottleneck is write throughput + memory; its partition key is place.
  • Normal API traffic is a balanced request/response mix from riders worldwide, mostly reads, hitting stateless servers, caches and database replicas. Its bottleneck is CPU + database reads; it scales by adding identical nodes anywhere.
  • They must therefore be separate deployments that scale independently: a concert that 10×'s location traffic in one district should force-scaling of that city's location shards — without touching the payment service in another country.

The partitioning hierarchy to draw

GEOGRAPHIC PARTITIONING

Country → City → Grid cells → Store partitions. Drivers, offers and reservations for a cell live in one partition with a single owner, which makes the accept decision naturally serialized and fast. Riders and drivers are registered globally (a replicated profile store) but matched locally. Each lane — API, ingest, gateway, matching — autoscales on its own metrics.

PART 18 — GEOGRAPHIC SCALING

From One City to Many Countries

The growth path is not "bigger servers". It is replicate the whole stack per region, keep local traffic local, and share only what must be global.

Stage 1 — One city

One deployment: all services, one geo store (a handful of partitions), one transactional database. Simple, strongly consistent, cheap. Matching ownership per cell already follows the sharding model so the architecture doesn't need redesign later.

Stage 2 — Many cities in one country

Deploy the location, matching and gateway lanes per city/region behind a smart routing layer that directs a phone's traffic to its region (based on GPS or home city). The transactional database is partitioned (sharded) by region with read replicas. Rider/driver profiles and auth stay a national service replicated across regions; rides stay in their region.

Stage 3 — Multiple countries

Independent regional stacks (EU, US-East, SEA…) each owning the full hot path. Cross-region traffic is limited to: identity/profile replication, payments orchestration, global analytics, and ops tooling. Each region fails over inside itself (multi-AZ / paired failover region).

CONCERN HOW REGIONAL ARCHITECTURE ANSWERS IT
Data locality & latency Location writes, searches and matching never cross an ocean; milliseconds stay milliseconds.
Regulatory requirements Data residency laws (e.g. trip/PII data stays in-country) become a deployment boundary; regional stacks and regional payment providers plug in naturally.
Availability A regional outage is contained; other countries keep running. Profiles replicated so users traveling still authenticate; they match on the local region.
Independent scaling New Year's Eve scales one country's lanes; capacity and cost follow local demand.
CENTRALIZED (ONE GLOBAL STACK) REGION-BASED (REPLICATED STACKS)
+ Simplest data model, one set of services, cheapest at small scale. + Low latency, fault isolation, residency compliant, independent scaling/cost.
− Cross-continent latency on every location write; one regional outage becomes global; regulators may forbid it; can't scale hot lanes independently. − More deployment/ops surface; data replication and conflict handling needed for global identity; features must be rolled out region by region.
RECOMMENDED PATH

Start centralized for the first city, but build the geographic partition key (city/region) into every hot-path store from day one. Then regionalize the hot lanes (location, matching, gateway, ride DB) as you cross borders — while keeping identity, payments orchestration and analytics as shared, replicated services. That key costs nothing early and saves a rewrite later.

Sixteen Ways the Street Goes Wrong

Interviewers score seniority on the failure walk. For each scenario know four things: what happens, user impact, immediate response, long-term prevention.

THE FOUR-COLUMN HABIT

PART 20 — CONSISTENCY & ACCURACY

Where "Now and Correct" Is Worth Paying For

Strong consistency means all readers immediately see the latest committed value. Eventual consistency means copies may be seconds or minutes old and converge later. Choosing is a business decision: what does staleness cost?

PART OF THE SYSTEM REQUIREMENT WHY — BUSINESS IMPACT OF BEING WRONG
Driver assignment / reservation Strong (atomic) Two riders getting the same driver is a visible, trust-destroying incident.
Ride state transitions Strong + event history Billing, support disputes and cancellations depend on one authoritative timeline.
Payment & ledger Strongest; idempotent; reconciled Real money; regulators and customers require exact, auditable balances.
Final fare Strong, derived from evidence A fare that changes after the receipt is a support and legal problem.
Auth/token revocation Near-strong (seconds) A banned driver retaining access is a safety incident.
TEMPORARY DELAY ACCEPTABLE HOW MUCH DELAY IS HARMLESS
Analytics dashboards & heat maps Minutes to hours; decisions are strategic.
Business/finance reports Daily/hourly batches are normal finance practice.
Some notifications Seconds late is fine; critical ones get push/SMS fallback.
Driver ratings / statistics Aggregates refreshed in minutes; never used for the live accept decision.
Map car dots outside matching 2–5 seconds old by design; visual, not transactional.
THE ARCHITECT'S CHOICE RULE

Ask "what is the cost of this value being wrong for 30 seconds?" Double charge or double booking → strong, synchronous, transactional. Dashboard tile or rating average → eventual via the event pipeline. Most systems don't choose one consistency model — they put strong guarantees around a small core and let the wide, cheap periphery converge over time.

PART 22 — ARCHITECTURE TRADE-OFFS

Ten Decisions, With What Each One Costs You

For every decision, say what you picked, what you rejected, what you gained, what you sacrificed, and the future condition that would flip your choice. Never present an option as simply "correct".

D1 Polling vs real-time communication

OPTION A — POLLINGDead simple, firewall-friendly, but huge empty request volume and up-to-interval latency.
OPTION B — PERSISTENT SOCKETSInstant updates, low per-message cost, but a whole gateway tier with reconnect/routing complexity.
GAINSub-second driver dots and offer countdowns; massive server-load reduction at scale.
SACRIFICEOperational complexity; must engineer reconnect, fan-out and fallback.
RECOMMENDED & WHYSockets for the live experience, push/SMS and occasional long-polling as fallbacks. The 250k/sec location world makes polling financially and technically absurd; the fallback keeps hostile networks working.

D2 Centralized vs geographic systems

OPTION A — ONE CENTRAL STACKCheapest and simplest early; one data model.
OPTION B — REGIONAL STACKSLocal latency, fault isolation, data residency; duplicated ops.
GAIN (B)Millisecond matching everywhere; one country's outage stays in that country; compliance.
SACRIFICE (B)Deployment multiplicity; identity replication; region-by-region releases.
RECOMMENDED & WHYBuild central for the first city with a region key already in every hot-path record; regionalize hot lanes as you cross borders. Reversible early, nearly impossible late.

D3 SQL vs specialized location storage

OPTION A — EVERYTHING IN SQLTransactions, constraints, one operational model.
OPTION B — IN-MEMORY SPATIAL STORE FOR LOCATION250k writes/sec and circle queries in RAM; data ephemeral.
GAIN (B)The only design that survives the location flood; geographic queries become microseconds.
SACRIFICE (B)A second technology to run and shard; two stores to keep straight.
RECOMMENDED & WHYHybrid: SQL remains the durable truth (rides, payments, accounts); in-memory geo store owns only ephemeral positions. The workloads are categorically different — this is the day-one split.

D4 Direct API calls vs events

OPTION A — DIRECT SYNCHRONOUS CALLSSimple to reason about; immediate answer or failure.
OPTION B — EVENT-DRIVEN VIA BROKERDecoupled, elastic, retriable; eventual and harder to trace.
GAIN (B)Receipt/analytics/notification failures never touch a ride; spike buffering.
SACRIFICE (B)Eventual behavior, ordering/dedupe discipline, broker operations.
RECOMMENDED & WHYSynchronous for anything the user awaits or money depends on; events for fan-out and background work. Critical state changes are written durably first, then published (outbox pattern) so a broker hiccup never loses them.

D5 Single database vs partitioned data

OPTION A — ONE DATABASETransactions across everything; easiest coding.
OPTION B — SHARD BY REGION/CITY + READ REPLICASHorizontal write capacity and containment.
GAIN (B)A hot city can't exhaust global DB capacity; smaller failure domains.
SACRIFICE (B)No cheap cross-shard transactions; routing and migration tooling needed.
RECOMMENDED & WHYStart single, schema with region/ride keys, shard on measured write/CPU pressure. Rides are naturally region-scoped so cross-shard transactions are rare — the easy kind of sharding.

D6 Strong vs eventual consistency

OPTION A — STRONG EVERYWHEREAlways correct; slower, more coupled, costlier.
OPTION B — EVENTUAL AT THE EDGESAvailable and cheap; stale reads where tolerable.
GAINSpend the expensive guarantee only where business damage is real.
SACRIFICETwo consistency models in one system; reconciliation logic.
RECOMMENDED & WHYStrong for reservation/state/payment/fare; eventual for maps, analytics, stats, notifications. Decide per data element by cost-of-staleness, not fashion.

D7 Centralized vs regional matching

OPTION A — GLOBAL MATCHEROne pool, uniform algorithms.
OPTION B — MATCHER PER CITY/CELL SHARDSingle owner per area; local decisions.
GAIN (B)Microsecond reservation races resolved locally; scales with city demand; failures contained.
SACRIFICE (B)Drivers near borders need hand-off rules; algorithm rollout is distributed.
RECOMMENDED & WHYRegional/cell ownership. Matching is latency-critical and inherently spatial; a single global matcher is a giant lock and a giant single point of failure. Border hand-off rules are a known, solvable case.

D8 Cache vs direct database access

OPTION A — READ THE DB EVERY TIMEAlways fresh; DB pays for every read and every spike.
OPTION B — CACHE HOT READSSub-millisecond, shields the DB; stale risk.
GAIN (B)Spike survival and cost reduction on config/profile/ETA reads.
SACRIFICE (B)TTL, invalidation, stampede and cache-failure planning.
RECOMMENDED & WHYCache stable, hot, forgivable data with short TTLs; never cache money or the reservation decision; always design the cache-dead fallback. A supporting tactic — not the architecture.

D9 One large service vs separate business services

OPTION A — MONOLITH/MODULAR MONOLITHFast to build; one deploy; local transactions.
OPTION B — MICROSERVICESIndependent scaling, deploys and teams; distributed complexity.
GAINA chosen split lets location/matching/payment scale and fail independently — which they must.
SACRIFICENetwork failure, data consistency, ops overhead, slower early delivery.
RECOMMENDED & WHYModular monolith for transactional areas at start; extract Location/gateway first (different workload), then Matching and Payment (load and compliance). Split along the seams the traffic numbers dictate.

D10 Build payments vs external provider

OPTION A — BUILD IN-HOUSEFull control, per-transaction fee avoided.
OPTION B — USE A PAYMENT PROVIDERTokenized cards, global rails, compliance handled.
GAIN (B)No PCI card-data environment, faster country expansion, fraud/risk tooling, banks handled for you.
SACRIFICE (B)Per-transaction fees, dependency on an external system, less control of uptime.
RECOMMENDED & WHYExternal provider behind your own idempotent payment service (optionally two providers for failover). Building card processing is a compliance business, not a ride business; encapsulating it keeps the door open to switch later.
PART 23 — COST THINKING

Scale Creates a Real Electricity Bill

An architect spends the company's money on purpose. The major cost areas are predictable — and so are the levers that reduce them without weakening safety-critical paths.

COST AREA WHAT DRIVES IT IN A RIDE PLATFORM
Server processing API, matching, gateway and ingest instances running 24/7 plus autoscaling headroom.
Location processing The biggest custom compute line — 250k updates/sec through ingest + in-memory geo clusters with RAM-heavy nodes.
Network traffic Ingress from apps, cross-AZ replication, fan-out to phones, map/ETA data.
Real-time connections Millions of idle-but-open sockets consume memory on gateway servers around the clock.
Databases High-availability instances, replicas, backups, geo store RAM, warehouse clusters.
Storage & analytics Trip breadcrumbs, event archives, logs, warehouse growth (petabytes over years).
Monitoring High-cardinality metrics, log ingestion, tracing, alerting — quietly expensive at scale.
External services Payment provider per-transaction fees, SMS (notably costly in some countries), maps/ETA/routing APIs, push infrastructure.

Ten practical cost levers

  1. Adaptive location frequency4-second updates while moving; slow to 15–30s when stationary or cruising without demand; pause entirely when the app is backgrounded/offline. This single rule can cut ingest volume by tens of percent.
  2. Right-size the geo store with cell shardingRAM is the priciest part of that tier — partition so sparse rural cells share nodes and only dense districts get dedicated capacity; expire dots aggressively.
  3. Aggregate before fanning out map dotsThousands of riders watching the same block should read one precomputed "cars in cell" snapshot, not trigger per-rider queries and per-rider streams.
  4. Autoscale aggressively, but on the right metricScale ingest by lag and gateway by connection count; scale in at night per region. Idle peak-sized fleets 24/7 are pure waste; regional deployments scale by local daytime.
  5. Push instead of polling; batch on the wireSockets already slash request volume; coalesce small updates into batched frames and compress them to cut network and connection cost.
  6. Cache pricing/city/ETA dataEvery cache hit avoids API, database and maps-API calls — external routing/maps calls are often metered per request, so caching ETA tiles directly saves cash.
  7. Choose storage tier by data ageHot breadcrumbs in fast storage for days; compressed cold storage for months; sampled/aggregated data for years; delete what policy doesn't require. Tiering cuts the warehouse bill dramatically.
  8. Make SMS a fallback, not the defaultUse free push as the primary channel; SMS only for critical delivery failures; vendor-shop by country.
  9. Sample and retain metrics/logs intelligentlyFull-resolution metrics for 7 days, aggregated after; log levels dropped in steady state; tracing a fraction of requests. Keep full fidelity on payments and matching.
  10. Graceful degradation over over-provisioningDuring rare mega-spikes, throttle receipts/analytics/nonessential pushes and read slightly-older map data instead of carrying 10× fleet every day of the year. Buy peak capacity as burst capacity, not baseline.
NEVER CUT HERE

Don't reduce cost by weakening the atomic accept, payment idempotency/reconciliation, backup testing, security controls or monitoring of money and matching paths. Cost optimization protects the same revenue engine more cheaply — it never gambles with correctness or safety.

  10. 10 · Real-time: persistent sockets on a dedicated gateway tier scaled by connection count; channel routing by ride/driver id; versioned catch-up on reconnect; push/SMS for background/dead sockets; long-poll fallback for hostile networks.
  11. 11 · State: Requested→Searching→DriverAssigned→DriverArriving→DriverArrived→ TripStarted→TripCompleted→(PaymentDone)→RideCompleted; Cancelled/NoDriverFound terminal; one server-side transition table, optimistic versions, append-only event log, idempotent commands, timeout sweepers.
  12. 12 · Data: transactional SQL (accounts, rides, payments — constraints, region sharding + replicas); RAM geo store (ephemeral); event log/warehouse (history, analytics); object storage for documents. One DB initially, split on measured pressure.
  13. 13 · Cache: city/pricing config (short TTL + invalidation), sessions, profile fragments, per-cell car counts, ETA tiles; never cache money, active ride state or accept decisions; cache-dead fallback throttled to protect the DB; single-flight hot keys.
  14. 14 · Messaging: broker for notifications, receipts, ratings, stats, fraud, surge computation, settlement; durable outbox so state changes and events can't diverge; retries with backoff; DLQ; critical confirmations stay synchronous.
  15. 15 · Pricing/payment: isolated versioned Pricing; estimate from expected route + surge snapshot; final fare server-side from archived totals; plausibility gates. Payment intent with idempotency key → tokenized provider → direct or webhook confirmation, both idempotent; timeout = unknown → poll/reconcile; refunds as linked idempotent transactions; ledger reconciliation job.
  16. 16 · Scaling/geography: stateless tiers autoscale per own metrics; geo store and matching shard by country→city→cell; region key present from day one; as borders open, replicate the hot stack per region, keep identity replicated globally; paired failover regions.
  17. 17 · Failures/security: TTLs, sweepers, circuit breakers, queues, graceful degradation, multi-AZ + regional failover, reconciliation. Security: strong driver verification, short-lived tokens, TLS everywhere, least privilege, tokenized cards, rate limiting, fake-GPS/fraud scoring, location minimization, audit logs.
  18. 18 · Cost/trade-offs: adaptive update frequency, aggregated map dots, aggressive autoscale/scale-in, push over SMS, storage tiering, sampled logs; never cut correctness, reconciliation or monitoring. Trade-offs explicitly named (see Part 22): sockets vs polling, regions vs central, SQL vs geo store, sync vs events.

"Two workloads dominate the design: a massive, disposable, spatial write stream handled in sharded memory, and a small, permanent, money-correct transaction core handled with a state machine, atomic reservations and idempotent payments. Everything else — notifications, analytics, receipts — is decoupled by events so it can lag without hurting a ride, and the whole platform is partitioned by geography so one city's concert never takes down another city's evening."

Model Answer Guide

  1. 1M simultaneous updates: load balancers spread them across many stateless ingest workers; updates are tiny and stateless until they reach the geo store shard owning that driver (consistent partitioning → one cell, one writer). Slight arrival jitter is harmless; batching at the edge and adaptive frequency keep peak under the sized 250k/s; per-shard lag metrics trigger autoscale. No transactional DB is anywhere in this path, so the burst cannot corrupt business data.
  2. Two riders, one driver: both offers create TTL reservations; the first accept that lands the atomic compare-and-set (AVAILABLE→ASSIGNED with version check) wins; the second fails the flip and its rider moves to the next wave. The unique active-ride constraint in SQL is the durable backstop. The driver is never presented as available after reservation.
  3. Matching fails mid-search: ride state stays Searching durably (in the DB/outbox, not matcher memory); standby matcher for the city shard takes over ownership; every offer and search has a TTL swept automatically, so nothing stays locked; affected riders see "retrying" then continued waves or a clean NoDriverFound. Design the matcher to rebuild its working set from the durable event/log store.
  4. Payment timeout: timeout means unknown, never failure; payment stays PENDING keyed by idempotency key; poll provider status, await webhook, bounded retries; reconciliation with settlement closes ambiguity. Never issue a fresh charge; the trip remains completed regardless.
  5. Accept then network loss: the accept only counts when the server commits the atomic transition; if the driver's request never arrived, the offer simply expires after TTL and matching continues. If it committed, the ride is Assigned server-side and will be there when the driver reconnects (state sync); a grace window + SMS/push covers the driver, and re-matching only triggers after the grace timer with no heartbeat.
  6. Driver crosses regions mid-trip: trip ownership stays pinned to the originating region for billing/state continuity (the ride is an agreement under that city's rules); location shards hand the live dot to the new region for map streaming, forwarding events back to the owning region. Matching never reassigns an active trip; drivers searching after ending simply register in the new region.
  7. Database down: multi-AZ synchronous replicas fail over automatically (seconds); during the window, the API serves a declared degraded mode — live location and existing trip tracking continue (they run on the geo lane/sockets), new bookings are queued or politely failed rather than half-created; no booking decision is made from cache. Restored nodes replay durable outbox events.
  8. 10× traffic: in order: (1) split hot geo/matching shards finer for the dense districts, (2) autoscale stateless ingest/API/gateway on lag and socket count, (3) throttle background consumers and lengthen map-dot TTLs, (4) admission-control new searches with honest wait messaging, (5) regional capacity burst. Because the architecture is already sharded by geography and stateless at the edges, this is capacity allocation, not redesign.
  9. Cut cost: adaptive location frequency (largest lever), per-cell aggregated map dots, scale-in per region overnight, push-over-SMS, storage tiering and log sampling, cache metered ETA/maps responses, right-size geo RAM with sparse-cell sharing. Keep budgets for payment reconciliation, backups, and core monitoring untouched.
  10. Why not polling: one poll every 3–5 s across ~1M+ connected apps means hundreds of thousands of requests per second, most returning "nothing new", while updates still arrive a full interval late and phones burn battery. One socket per app removes both problems; polling remains only as a degraded fallback on hostile networks.
  11. Why not one database: three irreconcilable workloads: 250k overwrite-writes/s of disposable spatial data, strict small transactions with constraints, and years of analytic scans. One engine either over-provisions forever or lets analytics scans and GPS floods starve payments; separate stores also give independent failure domains and scaling. Start with one SQL for the durable core — but the geo stream never enters it.
  12. Why a broker: so a notification vendor, receipt renderer or analytics pipeline can be slow or down without touching the booking transaction; to absorb spikes; to retry safely with DLQ; and to give new consumers (fraud, ML) history without changing core services. Critical state is still committed synchronously with a durable outbox, so broker downtime loses nothing.
  13. Stadium hot cell: matching/geo shard for that cell saturates first. Pre-split dense venues into finer cells (dynamic shard splitting), route drivers/riders by sub-cell, widen search rings into adjacent cells for supply, apply surge and admission control, and pause nonessential per-request work. Geo partitioning exists precisely to make this a local event.
  14. Duplicate/out-of-order webhooks: handlers are idempotent on the payment key and perform guarded transitions (e.g. only PENDING→SUCCEEDED accepted); duplicate SUCCEEDED returns the stored result; a late FAILED after SUCCEEDED cannot move state backward — it raises an anomaly for reconciliation. Money effects happen once; ordering is made irrelevant.
  15. Stale surge: multipliers are computed continuously and cached with very short TTLs plus push invalidation when they change; every ride snapshots the multiplier the rider accepted, and the final fare is computed against that snapshot — stale reads affect displays briefly, never charges; plausibility checks flag impossible deltas; audit rows make overcharges refundable and undercharges explainable.
  16. Fake GPS: stream fraud checks per driver: movement-velocity sanity (teleports), jitter/accuracy signatures, cross-checks of cell transitions, device attestation and sensor data; suspicious dots are quarantined from matching and queued for review; repeat offenders blocked. Works asynchronously for risk scoring, synchronously for clear fraud.
  17. Cancellation states/fees: before DriverArrived cancellation is a legal Searching/Arriving→Cancelled transition with policy-ruled fees (often free, driver released instantly); after arrival a waiting window applies; after pickup (TripStarted) the rider cannot self-cancel into nothing — the trip must end and fare rules apply (minimum charge). The state machine rejects illegal skips; fee decisions are Pricing's, refunds Payment's.
  18. Split-brain after failover: reservations are TTL-based and single-writer per shard; on failover the new owner refuses to act until old locks are expired or fenced (fencing token/epoch — every write includes an owner generation the store rejects when stale). Worst case the old owner accepts a duplicate that the unique SQL constraint rejects; riders never see two drivers because assignment commits once.
  19. Heavy report vs live traffic: reports never touch the booking database — events replicate into a warehouse where scans are free to run; live SQL keeps only transactional hot data with replicas reserved for operational reads. Add query workload isolation and scheduled report slots. This is why analytics is a consumer, not a tenant of the core.
  20. Data residency law: deploy a regional stack in-country (the rollout model already assumes this): location, rides, trips and PII stay inside the region with local storage and local payment provider; only non-identifying aggregates and replicated identity references cross borders, with documented legal basis. The region partition key built from day one turns compliance into deployment configuration rather than a rewrite.

"How would you design an Uber-like ride booking system?"

"First I'd confirm the peak numbers, regions and availability target. ONE POWERFUL ARCHITECT STATEMENT

A real-time platform is three systems wearing one logo: a heartbeat that moves at the speed of the street, a ledger that must never be wrong, and the paperwork that can catch up later. Keep them in separate homes and each one scales, fails and heals — on its own terms.

Fast-changing data, money-grade transactions, and background processing do not share databases, scaling curves, or failure budgets. The whole of Day 23 is learning to draw that seam before you draw anything else.
