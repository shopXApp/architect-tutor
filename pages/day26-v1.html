PART 01 — MINDSET

Think Like a Production Architect

A system can fail even when every single part looks healthy. Each server says "I am fine." Each database says "I am running." And yet users cannot log in. This happens because a real system is not a list of parts — it is a chain of parts waiting for each other.

The eight ideas you must feel, not just know

DependencySomething your system needs from someone else. Your API needs the database. The database needs the disk. Like a restaurant that needs the market to open. If the market closes, the kitchen is "healthy" but nobody eats.
BottleneckThe slowest, most limited part. Ten fast checkout counters and one door — the door decides how many customers get in. Making the counters faster changes nothing.
Cascading failureOne failure pushes extra work onto the next part, which then also fails, and so on. Like one lane of a highway closing: the other lanes jam, then the exit ramps jam, then the whole city jams.
Sudden traffic (spike)Many more requests than normal in a short time. A promotion, a news article, a scheduled job at 9:00 AM. The system did not change — the demand did.
Resource exhaustionYou run out of something limited: memory, CPU, threads, database connections, disk. Nothing "crashed" — you simply have no seats left in the bus.
Slow dependencyThe worst kind of failure. A dead service returns an error instantly and you move on. A slow service makes you wait, holding your memory and threads while doing nothing.
Retry stormMany clients get errors, all retry at the same second, and the load doubles or triples. It is like everyone pressing the elevator button harder when the lift is already full.
Database overloadThe database is usually the hardest part to scale quickly. When protection layers above it disappear, all the pain lands there — and the database is where the money lives.
THE CORE TRUTH

Healthy components do not mean a healthy system. Health is a property of the whole chain, under real load, at the worst moment. An architect designs for the chain, not for the boxes.

Why "everything is green" is a dangerous dashboard

Most monitoring shows whether a machine is up. Very few show whether the system is useful . During the incident you will read about today, every server was up, Redis was "restarting", SQL was "running", and the business was losing orders every second. The right questions are:

  • Can a user complete the most important action right now? (place an order, pay, log in)
  • How long does it take? Slow is a form of down.
  • What percentage of requests fail? A 4% error rate at 5,000 req/sec is 200 angry users every second.
  • What is close to full? CPU, connection pool, queue depth, memory, thread pool.
PART 02 — THE CASE STUDY

The Main Incident

One enterprise platform. Many companies (tenants) use it. Everything is normal until 10:00 AM, when the cache disappears.

THE SYSTEM — AS IT LOOKS ON A NORMAL DAY

COMPONENT WHAT IT DOES (SIMPLE ENGLISH) NORMAL BEHAVIOUR
.NET APIs The doors of the system. They receive every request from web and mobile. 5,000 requests per second, 200 ms response
SQL database The book of truth. Orders, inventory, customers, money. CPU around 45%
Redis cache A fast memory store that keeps copies of answers so SQL is not asked again. Serves ~85–90% of dashboard reads
Message broker A queue — a waiting line for work that can be done a little later. Queue nearly empty
Background workers Programs that pick work from the queue: emails, stock sync, invoices. Messages processed in seconds
Reporting system Heavy queries for management: sales by month, big exports. Slow but tolerated

10:00 AM — Redis becomes unavailable

Redis stops answering. It does not matter yet why (a node restarted, memory filled, network broke). What matters is what the rest of the system does next, because nobody told the APIs to behave differently.

TIME WHAT HAPPENS WHAT THE NUMBERS SAY
10:00:00 Redis stops responding. API calls to the cache start failing or hanging. Cache hit ratio 88% → 0%
10:00:20 Every dashboard read now goes to SQL. The same 5,000 req/sec, but now the database sees maybe 8× more queries than usual. SQL CPU 45% → 78%
10:01 Queries start queuing inside SQL. Each one takes longer because they compete for the same CPU and memory. SQL CPU 95%, query time 40 ms → 900 ms
10:02 API requests stay open waiting for SQL. Each open request holds a database connection and a thread. Connection pool usage 30% → 100%
10:03 New requests cannot get a connection. They wait, then time out. API p95 200 ms → 8 s, errors 0.1% → 22%
10:04 Mobile apps and integrations retry automatically. Effective traffic becomes 9,000+ req/sec of mostly repeated work. Incoming traffic +80%, all of it painful
10:05 Background workers also use SQL. They slow down, so the queue starts growing. Queue depth 200 → 60,000 messages
10:06 Emails and notifications are delayed. Reports time out. Users say "the system is down." Business impact: orders failing
THE UNCOMFORTABLE PART

Redis failing was a small technical event. The outage was created by our own design — no cache-failure behaviour, no limits, long timeouts, unlimited retries and no way to shed low-value traffic. The cache did not cause the outage. The missing plan for a cache failure did.

STAGE IN SIMPLE ENGLISH WHY IT MAKES THINGS WORSE
1 · Redis fails The fast helper that answered most questions is gone. Nothing absorbs read traffic any more.
2 · Cache misses A "miss" means the answer was not in the cache, so we must ask the database. Misses go from 12% to 100% instantly — not gradually.
3 · More DB requests The database suddenly gets many times more queries than it was sized for. Capacity planning assumed the cache existed.
4 · CPU rises The database machine is doing far more work per second. Above ~85% CPU, waiting time grows very fast, not linearly.
5 · Queries slow Every query, even cheap ones, becomes slower because they queue. Now even healthy features feel broken.
6 · Requests stay open The API is waiting for an answer, holding memory, a thread and a connection. Waiting is not free — it consumes capacity.
7 · Pool fills The pool is the fixed set of database connections the app may use. All are busy. Now even a tiny, fast query cannot start.
8 · Timeouts Requests give up after waiting too long, and users see errors. Work already done is thrown away — pure waste.
9 · Clients retry Mobile apps, browsers and partner systems automatically ask again. The failing system is punished for failing.
10 · Traffic grows Real traffic did not increase; duplicate traffic did. Load can double or triple within a minute.
11 · DB overloaded The database can no longer serve even critical writes like orders. Now the business, not just the dashboard, is affected.
12 · System unstable Workers slow, queues grow, notifications stop, reports fail. Recovery becomes harder because everything is tangled.
THE LESSON IN ONE LINE

A system-wide outage is usually one failure plus four missing protections: no fallback behaviour, no timeout discipline, no limit on retries, and no way to shed low-value work.

PART 04 — EMERGENCY

The First Five Minutes

In the first five minutes you are not solving the root cause. You are stopping the bleeding. Fixing comes later; survival comes now.

  1. Minute 0 → 1 · Confirm what is really happeningLook at four numbers only: error rate, response time (p95), traffic, and saturation (CPU, pool, queue depth). Confirm Redis is truly unreachable and confirm SQL CPU. Declare the incident and name one person as incident lead so five people do not act at once.SAY: "cache hit ratio is zero, SQL CPU 95%, p95 8 seconds — this is a cache-loss cascade."
  2. Minute 1 → 2 · Stop what makes it worsePause anything optional that touches the database: scheduled reports, bulk exports, data sync jobs, marketing batch mails, non-urgent background workers. Ask client teams to stop automatic retries. Cancel any deployment in progress. Do not restart everything hoping it helps.GOAL: remove work the business will not miss for ten minutes.
  3. Minute 2 → 3 · Protect the database directlyReduce database timeouts (so stuck requests release their connections quickly), open circuit breakers on the heaviest endpoints so they fail fast, cap the maximum concurrent requests per API instance, and if available, move read-only traffic to a replica. The database must be given room to breathe.GOAL: shrink the queue in front of SQL.
  4. Minute 3 → 4 · Reduce the traffic you can afford to loseTurn off heavy dashboards and analytics widgets. Serve a "temporarily simplified view". Apply rate limits per tenant and per endpoint. Keep login, order creation, payment and inventory fully alive. This is load shedding — deliberately refusing low-value work to save high-value work.GOAL: 100% of orders, 0% of big reports.
  5. Minute 4 → 5 · Watch the right signals and communicateTrack SQL CPU and wait time, connection pool usage, API error rate and p95, queue depth, and cache status. Post a short status message to the business: what is affected, what still works, next update time. Silence during an incident creates a second incident made of phone calls.GOAL: see improvement within 2–3 minutes, or escalate the next lever.

What you should NOT do during an active incident

Do not restart everything

Restarting API servers empties in-memory state and dumps a fresh wave of cold requests onto an already dying database.

Do not increase timeouts

It feels helpful. It is the opposite: longer waits hold connections longer and make the queue deeper.

Do not enlarge the connection pool

More connections to an overloaded database means more competition and slower queries for everyone.

Do not deploy a "quick fix"

Untested code during an outage adds a second unknown. Use switches and configuration you already have.

Do not hunt the root cause first

Stabilise, then investigate. Understanding why Redis died does not help the customer at 10:04.

Do not let five people act at once

Parallel uncoordinated changes make the system unexplainable. One lead, one change at a time, announced.

PART 05 — DIAGNOSIS

Find the Real Bottleneck

Everything looks broken during an incident. Your job is to find the one place where the pain starts. Everything else is an echo.

SUSPECT SIGNAL THAT PROVES IT SIGNAL THAT CLEARS IT
Redis Cache hit ratio drops to zero; cache calls error or time out; Redis memory or connection count at limit. Hit ratio normal and cache latency under a few milliseconds.
SQL CPU above 85%, query duration rising, blocking/locks, connection pool full, long-running queries visible. CPU normal and query time flat while APIs are still slow → look elsewhere.
API layer CPU or memory high on API servers, thread pool starvation, garbage-collection pauses, while SQL is calm. API CPU low and requests are just waiting → the wait is downstream.
Network Latency between services rises, packet loss, DNS failures, timeouts on all dependencies at once. Same-region calls fast and stable.
Message broker Publish calls slow or failing, broker memory/disk full, consumers disconnected. Publish fast, queue depth stable.
Background workers Queue depth growing steadily, message age increasing, worker CPU pinned or workers crashed. Queue drains as fast as it fills.
External provider Only the endpoints that call the provider are slow; provider latency chart spikes; their status page reports issues. Internal-only endpoints slow too → it is not them.

The four sources of truth

LogsWritten sentences about events. Good for what error. Look for a sudden change in error type and the first minute it appeared — the first error is usually closest to the cause.
MetricsNumbers over time. Good for how much and how fast: CPU, latency, error rate, hit ratio, queue depth, pool usage. Metrics show the shape of the failure.
TracesA map of one request through all services with timings. Good for where the time is spent. A trace showing 7.6 s inside a SQL call ends the argument immediately.
AlertsAutomatic warnings when a number crosses a line. Good alerts fire before users complain: cache hit ratio, DB CPU, pool saturation, queue depth, error budget burn.

PART 06 — CACHE FAILURE

Five Strategies When the Cache Dies

There is no single correct answer. There are five behaviours, each with a price. An architect picks different behaviours for different endpoints.

READ THIS BEFORE STRATEGY 1

"If Redis fails we just read from the database" is the most common wrong answer in interviews. It is only safe if the database can carry the full uncached load at peak — and in most enterprise systems it cannot, because the cache is exactly why the database looks comfortable.

STRATEGY ADVANTAGE DISADVANTAGE USER IMPACT WHEN TO USE
1 · Go straight to the database
"cache is optional" 		Simplest. Data is fresh and correct. No feature is lost. Can kill the database instantly at high traffic. This is exactly how today's incident happened. None — until the database dies, then total outage. Low traffic endpoints, cheap queries, or when DB is sized for full load without cache.
2 · Return limited or stale data
older copy, smaller page		 System stays fast and alive. Very cheap protection. Data may be minutes old; wrong for money, stock levels or permissions. Sees slightly old numbers, usually with a "data as of 09:58" note. Dashboards, product catalogues, lists, counts, anything advisory.
3 · Fail fast
immediate clear error		 Protects the database completely. Frees threads and connections instantly. The feature is visibly unavailable. Feels harsh to users. Clear message: "Reports are temporarily unavailable." Expensive, non-critical endpoints during heavy load.
4 · Temporarily disable expensive features
feature switch		 Removes the biggest load with one config change. Predictable. Needs switches built in advance; you cannot invent them mid-incident. Some screens hidden or simplified; core work continues. Heavy dashboards, exports, analytics, bulk operations.
5 · Use another cache source
local memory / second cluster		 Absorbs a large share of reads even without Redis. Each server has its own copy → inconsistency; more memory; more complexity. Mostly invisible; occasional small differences between servers. Read-mostly, slow-changing data such as settings, catalogues, lookup lists.

How an architect actually chooses

  • Classify every read as critical, useful, or decorative — before the incident.
  • Critical reads (inventory for checkout, price at payment) → go to the database, but with a short timeout and a request limit.
  • Useful reads (dashboards, lists) → stale copy from local memory, or fail fast with a friendly message.
  • Decorative reads (recommendations, "people also bought", activity feeds) → switch off entirely; nobody loses money.
  • Always add a limiter in front of the database path, so cache loss cannot translate one to one into database load.
PART 07 — PROTECTION

Protecting the Database

When the cache is gone, the database becomes the last thing standing between you and a full outage. Protect it like it is the business — because it is.

TECHNIQUE WHAT IT MEANS IN SIMPLE ENGLISH SPEED
Rate limiting Allow only N requests per second per user, per tenant, or per endpoint. Extra requests get a polite "try again shortly". Immediate if built; long-term if not
Concurrency limits Cap how many requests may be inside an expensive operation at the same time — like a nightclub with a door counter. Immediate
Caching The primary shield. Includes a small in-process cache so one dead Redis is not total cache loss. Long-term design
Query reduction Fewer and cheaper queries: no N+1 loops, fetch only needed columns, page results, add missing indexes. Long-term (but one bad query can be fixed now)
Read replicas Copies of the database used only for reading. Reads move off the main writer so orders keep working. Long-term to build, immediate to switch
Request prioritisation Checkout beats browsing. Payment beats reporting. Give critical traffic its own pool and its own quota. Long-term design, immediate benefit
Circuit breaking After too many failures, stop calling the struggling component for a while and fail fast instead. Immediate if built
Timeouts Give up after a set time so resources are released. Short timeouts are database protection, not user cruelty. Immediate (config)
Limit expensive reports Queue them, restrict to off-peak, cap row counts, or point them at a separate reporting store. Immediate to disable; long-term to separate
Temporary feature reduction Turn off the heavy 10% of features that create 80% of database work. Immediate with feature switches
IMMEDIATE VS LONG TERM — SAY THIS IN INTERVIEWS

Immediate levers (minutes): shorten timeouts, open circuit breakers, rate limit, disable heavy features, stop batch jobs, route reads to replicas, reduce retries.
Long-term fixes (weeks): highly available Redis, in-process fallback cache, separate reporting database, query and index work, capacity planning, per-tenant quotas, load testing with the cache disabled.

Why it multiplies so fast

Retries stack across layers. If the mobile app retries 3 times, the gateway retries 2 times, and the service retries 2 times, one user action becomes up to 12 requests. At 5,000 requests per second, that is a self-inflicted denial of service. Worse, every retry arrives at almost the same moment, because everyone timed out at the same moment — this is called synchronisation.

CONTROL SIMPLE EXPLANATION PRACTICAL RULE
Retry limits Try again only a small number of times, then stop and report the failure. Two retries maximum, and only at one layer.
Exponential backoff Wait longer between each attempt: 1s, 2s, 4s. Gives the system time to breathe. Double the wait each time, with a ceiling.
Random delay (jitter) Add a small random amount to each wait so clients do not all return together. Backoff without jitter still creates waves.
Circuit breaker When failures are widespread, stop retrying at all for a while. Retry is pointless when the dependency is down.
Timeouts Fail quickly so the retry decision happens early and cheaply. Timeout must be shorter than the caller's patience.
Client-side limits Mobile and partner clients must not retry reads automatically without backoff. Publish retry rules in your API contract.
Retry budget Allow retries only up to a small percentage of total traffic (e.g. 10%). Best protection against storms at scale.
RETRY IS NOT RECOVERY

Retrying helps only for short, random, isolated failures — a dropped packet, one bad node. When the dependency is overloaded, every retry steals capacity from the requests that might still succeed. In an overload, the kindest thing you can do is send less traffic.

Retry only what is safe to repeat

Never retry blindly on writes. Repeating "create order" or "charge card" can duplicate money. Retries are safe when the operation is idempotent — meaning doing it twice has the same result as doing it once, usually achieved with a unique request key that the server remembers.

PART 09 — CIRCUIT BREAKER

Circuit Breaker, Explained Like a Fuse Box

In your home, when there is an electrical fault, a fuse trips. It does not try "one more time". It cuts the connection to protect the house, and you reset it later. A circuit breaker in software does exactly this.

  1. What problem does it solve?It stops you from repeatedly calling something that is clearly broken or overloaded. Without it, every request waits for a timeout, holds resources, and adds load to the sick component. The breaker converts slow failure into fast failure.
  2. When does it open?When failures cross a threshold in a window — for example, more than 50% of the last 100 calls failed or timed out. Timeouts count as failures; slowness is failure.
  3. What happens while open?Calls are not attempted at all. The caller immediately gets a fallback: stale data, a reduced response, or a clear error. Response time drops from 8 seconds to 5 milliseconds, and threads and connections are freed.
  4. How does recovery happen?After a cool-down period the breaker moves to half-open and lets a small number of trial calls through. If they succeed, it closes and normal traffic resumes. If they fail, it opens again with a longer cool-down. This is gradual recovery built into the code.
  5. Why does it protect downstream systems?The struggling component suddenly receives almost no traffic, which is exactly what it needs to recover. A breaker is a gift to the thing it is protecting, not a punishment.
BREAKER ON WHEN IT OPENS FALLBACK BEHAVIOUR
Redis calls Cache calls failing or slower than ~50 ms repeatedly. Skip the cache entirely for a while (do not wait on it), use in-process cache, and apply a strict limit on the database path.
SQL — heavy read endpoints Query timeouts or DB CPU above threshold. Return stale/limited data or "temporarily unavailable" — never queue more work.
SQL — critical writes Only on hard errors, with a much higher threshold. Fail with a clear retry-later message and keep the request in a durable queue if business allows.
Payment provider Provider latency or error rate spikes. Show "payment temporarily unavailable", never double-charge, reconcile later.
COMMON MISTAKE

Putting a single circuit breaker around the whole database. Then one failing report endpoint blocks order creation too. Breakers must be per dependency and per operation class — that is the bulkhead idea: separate compartments so one flooded room does not sink the ship.

PART 10 — TIMEOUTS

Timeout Design

A timeout is a promise: "I will not wait longer than this." Without that promise, one slow dependency can consume every thread, connection and megabyte you own.

Why waiting is expensive

While a request waits, it still holds a thread, a chunk of memory, a database connection, an open socket and a place in the queue. A server that can handle 500 concurrent requests handles 2,500 requests per second at 200 ms — but only 62 per second at 8 seconds. The server did not get slower; it got fuller. Waiting quietly destroys capacity.

CALL SENSIBLE STARTING POINT REASONING
Cache (Redis) 50–200 ms, plus a fast connect timeout A cache exists to be fast. If it is slow, it has already failed — skip it.
Database query 1–3 s for normal queries; separate longer limit for reports Long DB timeouts are the main cause of pool exhaustion.
Internal service call 1–2 s Must be shorter than the caller's own timeout, or you waste work.
API request (overall) 5–10 s hard ceiling Beyond this the user has already left the page.
External provider (payment) 3–10 s, plus a status-check path Never assume failure on timeout — verify, or you double-charge.
Message processing Bounded per message, with retry and dead-letter One poisonous message must not block the consumer forever.
THE TIMEOUT BUDGET RULE

Timeouts must shrink as you go deeper. If the user waits 5 seconds, the API should wait 3 for the service, the service 2 for the database, and the cache 0.1. If an inner call is allowed more time than the outer one, the outer caller gives up while the inner work continues — you pay for work nobody receives.

Waiting longer is not recovering better. Increasing a timeout does not make the dependency faster; it only makes your system hold more broken requests at once. Short timeouts plus a good fallback beat long timeouts plus hope.

PART 11 — CONNECTION POOL

Connection Pool Exhaustion

This is the quiet killer inside almost every enterprise incident, and almost nobody explains it well in interviews. Learn it properly.

What is a connection?An open line between your application and the database, used to send a query and receive an answer. Creating one is slow and the database can only support a limited number.
What is a pool?A small fixed set of ready-made connections that requests borrow and return. Like a rack of 100 shopping trolleys shared by all customers.
What goes wrong?If each customer keeps a trolley for 20 minutes instead of 2, the rack empties. New customers stand at the door — even those who only need one item.
Why slow queries hurt twiceA slow query is not only slow itself; it keeps a connection locked, so fast queries that would have finished in 5 ms never even start.

How an architect prevents it

  • Short database timeouts. The fastest way to return connections to the pool.
  • Separate pools for separate workloads. Reports get their own small pool so they can never starve checkout. This is bulkheading.
  • Concurrency limits at the API. Reject early rather than queue inside the pool.
  • Never hold a connection while calling something else. No external HTTP call inside an open transaction.
  • Keep transactions short. Read, decide, write, commit — do not think while holding locks.
  • Alert on pool usage, not just on CPU. Pool saturation above 80% is an early warning that arrives minutes before users notice.
  • Do not "solve" it by enlarging the pool. More connections against an overloaded database makes every query slower.
PART 12 — CASCADE

Cascading Failure

A cascading failure is a row of dominoes. Each falling piece pushes the next. The first domino is small; the last one is the business.

Why cascades happen

  • Shared resources. Reports, dashboards and orders use the same database and the same pool, so pain spreads.
  • Unlimited waiting. Nothing gives up, so pressure accumulates instead of being released.
  • Amplification. Retries turn one failure into many requests.
  • No prioritisation. A background report competes equally with a paying customer's checkout.
THE ARCHITECT'S JOB

You cannot prevent components from failing. You can decide how far the damage travels. Design deliberate cut points — timeouts, breakers, bulkheads, limits and fallbacks — so the chain stops at domino two instead of domino six.

PART 13 — DEGRADATION

Graceful Degradation

Graceful degradation means the system gets weaker on purpose instead of dying by accident. Like a hospital during an emergency: the operating theatre stays open, the gift shop closes.

PRIORITY FUNCTION BEHAVIOUR DURING THE INCIDENT MAY IT BE SLOW / STALE?
P0 — Critical Login & authentication Must work. Give it a reserved connection pool and its own rate limit. Slow yes, wrong never
P0 — Critical Order creation Must work. Accept the order even if confirmation email is delayed. Slow yes, lost never
P0 — Critical Payment Must work and must never double-charge. Idempotency keys mandatory. Slow yes, duplicated never
P0 — Critical Inventory update Must be correct at checkout; display counts may be approximate. Display stale ok, reservation no
P1 — Delayable Notifications & emails Queue them. Delivery in 30 minutes is acceptable; losing them is not. Delay acceptable
P1 — Delayable Reporting Serve last generated snapshot with a timestamp, or queue the request. Stale acceptable
P1 — Delayable Analytics & audit aggregation Buffer events; process after recovery. Never drop audit records. Delay acceptable
P2 — Disposable Heavy dashboards Replace with a simple summary or a maintenance message. Turn off
P2 — Disposable Large exports / bulk downloads Block during the incident; offer scheduled delivery later. Turn off
P2 — Disposable Recommendations, activity feeds, non-critical jobs Disable silently. Users rarely notice; the database certainly does. Turn off
THE GOAL DURING FAILURE

The goal is not to keep everything working. The goal is to keep the most important business functions alive and to make the loss of everything else predictable, visible and temporary. A system that serves 100% of orders and 0% of reports is a success. A system that serves 40% of everything is an outage.

How to build this before the incident

  • Write the priority table with the business, not alone. They must agree which screens can disappear.
  • Put a feature switch on every P1 and P2 feature so it can be turned off in seconds without a deployment.
  • Design the degraded screen in advance: a clean "simplified view, data as of 09:58" beats a spinning wheel.
  • Practise it. Turn on degraded mode in production for five minutes during a quiet hour, on purpose.
PART 14 — QUEUES

Queue Backlog

A queue is a waiting line for work. It is a shock absorber — but if the workers slow down, the line becomes a second problem hiding behind the first.

Queue depthHow many messages are waiting. Rising depth means you are producing faster than you consume. It is the earliest honest warning in the whole system.
Processing speedMessages handled per second. During our incident it fell because every worker also waits on the same overloaded database.
Message delay (age)How old the oldest waiting message is. Depth of 60,000 matters only in relation to speed: at 100/sec that is ten minutes of lateness.
RetryFailed messages go back to the queue. During an outage this makes the line grow even without new work — a queue-level retry storm.
Dead-letter queueA side box for messages that keep failing, so one bad message does not block everything. It must be monitored, or it becomes a graveyard nobody visits.
Consumer scalingAdding more workers. Powerful — and dangerous: more workers means more database pressure. Scale consumers only when the bottleneck is the workers, not the database.

The decision an architect must make

OPTION CHOOSE IT WHEN RISK
Scale consumers up The database is healthy and workers are the bottleneck (worker CPU high, DB calm). If the DB is the bottleneck, this accelerates the outage.
Reduce incoming work Producers are generating avoidable messages (analytics events, re-sync jobs). Some data must be regenerated later.
Delay non-critical messages Mixed queues: split critical (order events) from optional (marketing). Requires separate queues built in advance.
Pause processing entirely Workers are actively harming the database and the messages are safe to hold. Backlog grows; you must have capacity to drain it later.
A QUEUE IS NOT A FIX, IT IS A DELAY

A queue moves pain from "now" to "later" and turns a spike into a flat line. That is valuable — but the work still has to be done, and draining a backlog after recovery can create a second overload. Always plan the drain rate, not just the buffer.

PART 15 — RECOVERY

Recovery — The Second Chance to Fail

Redis is back. The instinct is to open everything immediately. Do not. Recovery is the moment when many teams cause outage number two.

SHOULD ALL TRAFFIC RETURN AT ONCE? NO.

An empty Redis is functionally the same as a broken Redis: every request is a miss and goes to SQL. If you open the gates while the cache is cold, you recreate exactly the condition that caused the outage, this time with a backlog of retries and queued messages added on top.

  1. Confirm the dependency is genuinely healthyRedis reachable, memory normal, no failover in progress, latency low and stable for a few minutes. A flapping dependency is worse than a dead one.
  2. Warm the cache before opening trafficLoad the most valuable keys first: tenant settings, dashboard aggregates, catalogues, permissions. Warming is usually 20 keys that carry 80% of the reads — know that list in advance.
  3. Release traffic graduallyClose circuit breakers step by step, or raise rate limits in stages: 10%, 25%, 50%, 100%, watching SQL CPU at each step. If CPU jumps above target, step back one level.
  4. Re-enable features by priority, not alphabeticallyCore first, then delayable, then heavy dashboards and reports last. Reports come back only when SQL CPU has been stable for a while.
  5. Drain the queue at a controlled speedDo not unleash 60,000 messages at a recovering database. Increase consumer count in steps and watch database load, not queue depth alone.
  6. Check downstream healthNotifications, external integrations and reporting may have their own backlog, duplicates or stuck records. Verify data correctness, not just green charts.
  7. Declare recovery only on business signalsOrders per minute back to normal, payment success rate normal, error rate under target, p95 back to baseline, queue age near zero. "The servers are up" is not recovery.
SAY THIS IN THE INTERVIEW

"Recovery is a controlled operation, not a switch. I warm the cache, release traffic in stages, restore features by business priority, and drain the queue at a rate the database can absorb — because a cold cache plus full traffic is the same as no cache at all."

PART 16 — PREVENTION

Preventing the Same Incident

Every improvement buys safety and costs something. An architect always names all three: the problem solved, the benefit, and the new complexity or cost.

SOLUTION PROBLEM SOLVED BENEFIT NEW COMPLEXITY / COST
Redis high availability A single cache node is a single point of failure. Automatic failover; outage becomes seconds instead of an hour. More nodes to pay for and operate; failover itself can misbehave; brief blips remain — so you still need fallback logic.
Monitoring (four signals) Nobody saw the problem before customers did. Detection in seconds; clear evidence for diagnosis. Tooling cost, dashboard maintenance, data storage.
Meaningful alerts Alerts fired on symptoms only, or too late. Warning before impact: hit ratio, DB CPU, pool, queue age. Alert fatigue if tuned badly; needs ownership and review.
Timeout policy everywhere Requests waited forever and consumed capacity. Failures become fast and cheap; capacity is preserved. Some legitimate slow operations now fail; needs per-operation tuning.
Circuit breakers Sick dependencies kept receiving traffic. Automatic protection and automatic gradual recovery. Extra library, thresholds to tune, risk of opening too eagerly.
Cache fallback (in-process cache) Cache loss went straight to 100% database load. Absorbs a large share of reads even with Redis gone. Memory per server; possible inconsistency between servers.
Database protection layers The database had no defence of its own. Overload is refused politely instead of accepted fatally. Some users get rejected during peaks; needs clear messaging.
Rate limiting (per tenant) One company or one script could flood the platform. Fair sharing; noisy tenants are contained. Quota management, customer conversations, edge cases for big clients.
Query & index optimisation Each query cost more CPU than necessary. Higher headroom on the same hardware; cheaper than scaling. Engineering time; indexes slow writes and use storage.
Load testing with the cache off Nobody knew the real uncached capacity. You learn the true limit in a test, not in an outage. Test environment cost, effort to keep tests realistic.
Capacity planning Sizing assumed the cache always exists. Known headroom and known trigger points for scaling. Higher baseline infrastructure spend.
Disaster recovery plan No answer for losing a whole region or a database. Defined RPO/RTO, tested restore, business confidence. Significant cost and regular drills; standby capacity mostly idle.
SEQUENCE MATTERS

If you can only do three things this quarter: 1) timeouts and retry policy, 2) circuit breakers plus feature switches for heavy features, 3) monitoring and alerts on cache hit ratio, DB CPU and pool usage. These are cheap and prevent most of the damage. Highly available Redis is important, but it never removes the need for a cache-loss plan.

PART 17 — CACHE ARCHITECTURE

Redis Architecture Decisions

Not configuration — decisions. Seven choices, and when each one actually matters.

DECISION WHAT IT MEANS WHEN IT MATTERS
Cache-aside The application looks in the cache first; on a miss it reads the database and puts the result in the cache. The cache is a helper, not the source of truth. Default for almost everything. Matters most because it defines what happens on a miss — and a total cache failure is simply 100% misses.
TTL (time to live) How long a cached copy is allowed to live before it is thrown away. Short TTL = fresher but more database load. Long TTL = cheaper but staler. Also spread TTLs randomly so thousands of keys do not expire in the same second.
Cache invalidation Removing or updating a cached copy when the real data changes. Critical for prices, stock and permissions. Wrong invalidation shows customers old prices — a business incident, not a technical one.
Cache warm-up Filling the cache with important data before real traffic arrives. After a restart, a deployment, a failover, or recovery from exactly the incident in this tutorial.
Cache failure behaviour What each endpoint does when the cache is unreachable: database, stale, fail fast, or disabled. The single most important decision on this page — and the one most teams have never written down.
Distributed cache One shared cache used by all servers, so everyone sees the same value. Needed for sessions, locks, counters and anything that must be consistent across instances — and it is why cache loss hits every server at once.
High availability More than one node with automatic failover, so a single failure is survivable. When the cache has become load-bearing — that is, when the database cannot survive without it. Then HA is not optional.
THE QUESTION THAT REVEALS SENIORITY

"Is your cache an optimisation or a dependency?" If the system survives without it, it is an optimisation. If the database melts without it, the cache is now a critical dependency and must be designed with the same care as the database: high availability, monitoring, alerts, capacity, and a documented failure plan.

PART 18 — LAYERS

Database Protection Strategy — Seven Layers

Think of it as castle walls. Every layer removes some load before it reaches the last, most precious room.

LAYER WHAT IT DOES WHAT IT COSTS YOU
L1 · Limit incoming traffic Refuse excess requests at the edge, before they consume anything expensive. Per user, per tenant, per endpoint. Some users are refused; needs a fair, well-communicated policy.
L2 · Protect expensive APIs The heavy 10% of endpoints get concurrency caps, breakers and switches of their own. Requires knowing which endpoints are expensive — measure them.
L3 · Caching Answers most reads without touching the database at all. Staleness, invalidation complexity, a new dependency to protect.
L4 · Optimise queries Makes every remaining query cheaper — the highest value per pound spent. Engineering effort; indexes slow writes.
L5 · Separate reporting Removes the single biggest source of unpredictable heavy load from the hot path. Data is slightly delayed; extra storage and pipeline to maintain.
L6 · Scale database reads Read replicas absorb read traffic so the writer stays free for orders. Replication lag, routing logic, extra cost.
L7 · Monitor capacity Tells you how much headroom is left, so you scale before the incident. Requires discipline and regular capacity reviews.
PART 19 — RUNBOOK

Production Runbook: "Redis Unavailable, SQL Load Rising"

Print this. Put it where the on-call engineer can find it at 3 AM. It must be usable by someone who is tired and frightened.

DETECTION — HOW DO WE KNOW?

  • Alert: cache hit ratio below 50% for 1 minute, or Redis health check failing.
  • Alert: SQL CPU above 80% for 2 minutes, or average query duration above 3× baseline.
  • Alert: connection pool usage above 80%.
  • Alert: API error rate above 2% or p95 above 1 second.
  • Alert: queue age above 5 minutes.
  • Human signal: support tickets saying "slow" or "spinning".

IMMEDIATE ACTIONS — FIRST 5 MINUTES

  • 1. Declare the incident. Name an incident lead and a communicator.
  • 2. Confirm Redis status and SQL CPU. Note the start time.
  • 3. Turn on degraded mode: disable heavy dashboards, exports and reports.
  • 4. Stop batch jobs, scheduled syncs and non-critical background workers.
  • 5. Reduce database command timeout; open circuit breakers on heavy read endpoints.
  • 6. Apply or tighten rate limits, especially on the noisiest tenants and endpoints.
  • 7. Ask client teams / partners to pause automatic retries.
  • 8. Post the first status message with a next-update time.

STABILISATION — STOP IT GETTING WORSE

  • Route read traffic to replicas where possible.
  • Verify SQL CPU is trending down and pool usage is falling. If not, shed more traffic.
  • Kill individual long-running queries only if they are clearly report queries.
  • Confirm P0 functions still work with a real end-to-end test: login → add to cart → order → payment.
  • Begin restoring Redis in parallel (failover, restart, new node) — but never at the cost of stabilisation.
  • Update stakeholders every 10–15 minutes, even if nothing changed.

RECOVERY — RESTORE NORMAL OPERATION

  • Confirm Redis is stable for at least 3–5 minutes.
  • Warm the top keys (settings, catalogues, dashboard aggregates, permissions).
  • Close circuit breakers gradually; raise rate limits in stages 10% → 25% → 50% → 100%.
  • Re-enable features by priority: P1 first, heavy P2 dashboards and reports last.
  • Drain the message backlog by increasing consumers step by step while watching SQL.
  • Restore timeouts and configuration to their normal documented values.

VALIDATION — HOW DO WE KNOW WE ARE HEALTHY?

  • Cache hit ratio back near baseline; SQL CPU under 60%; pool usage under 50%.
  • API p95 back to ~200 ms; error rate under 0.5%.
  • Queue age near zero; dead-letter queue reviewed and empty of new items.
  • Business signals: orders per minute normal, payment success rate normal, no duplicate charges.
  • All feature switches returned to their normal state and recorded.
  • Only then: close the incident and schedule the review within 48 hours.

PREVENTION — SO IT DOES NOT HAPPEN AGAIN

  • Highly available Redis with tested failover.
  • In-process fallback cache for the top read paths.
  • Documented timeout and retry policy across all services.
  • Circuit breakers and per-tenant rate limits as standard.
  • Reporting separated from the transactional database.
  • Load test at peak traffic with Redis disabled, at least twice a year.
  • Runbook rehearsal (game day) with the on-call team once a quarter.
PART 20 — LEARNING

Post-Incident Review

The review is where an incident becomes an asset. Run it within 48 hours, while memory is fresh and emotions have cooled.

  1. What happened?A factual timeline with timestamps and numbers. No opinions, no adjectives. "10:00 Redis unreachable. 10:03 SQL CPU 95%. 10:06 error rate 22%."
  2. Why did it happen?Two answers are needed: the trigger (Redis node failed) and the real cause (the system had no defined behaviour for cache loss). Triggers are random; causes are design.
  3. Why was it not detected earlier?Which alert should have fired and did not? Usually the answer is "we alerted on servers, not on cache hit ratio or pool saturation."
  4. What made it worse?Retries, long timeouts, reports running at peak, no feature switches, five people changing things at once. This list becomes your highest-value backlog.
  5. What worked?Name it and protect it. Perhaps the payment idempotency prevented double charges, or the queue meant no orders were lost. Keep what saved you.
  6. What did not work?Missing runbook, unclear ownership, dashboards nobody trusted, slow communication with the business.
  7. What should change?A small number of concrete actions, each with an owner and a date. Five real actions beat twenty wishes.
  8. How will success be measured?Define the proof: "next load test with Redis off keeps SQL CPU below 70% and orders succeeding", "detection time under 60 seconds", "no incident longer than 15 minutes from this cause".
BLAMELESS, ON PURPOSE

If people fear the review, they hide details — and the details are the whole value. Ask "what allowed a reasonable person to make that decision?" instead of "who did it?". A single person can never bring down a well-designed system; if one action did, the design is the finding.

PART 21 — TRADE-OFFS

Twelve Production Architecture Decisions

Click each decision. Every one follows the same shape: problem · option A · option B · benefits · risks · recommendation · why. This shape is what interviewers listen for.

01Cache fallback vs fail fast+
PROBLEM

Redis is unavailable. Should requests silently go to the database, or fail immediately?

OPTION A — FALLBACK TO DATABASE

Every miss becomes a database query. Nothing visibly breaks.

OPTION B — FAIL FAST

Return an error or a reduced response immediately without touching the database.

BENEFITS

A keeps features complete and data fresh. B guarantees the database survives and frees resources instantly.

RISKS

A can destroy the database in under two minutes at peak. B makes features visibly unavailable and can frustrate users.

RECOMMENDED

Mixed, decided per endpoint: fallback with a strict concurrency limit for critical reads; stale-or-fail-fast for heavy, non-critical reads.

WHY

The correct behaviour depends on business value, not on technology. One global rule is always wrong somewhere.

02Retry vs no retry+
PROBLEM

A call failed. Should the caller try again?

OPTION A — RETRY AUTOMATICALLY

Improves success rate for short, random glitches.

OPTION B — DO NOT RETRY, REPORT THE FAILURE

Keeps load predictable and honest.

BENEFITS

A hides transient network faults from users. B prevents amplification during overload.

RISKS

A causes retry storms and can duplicate writes. B surfaces errors that would have healed by themselves.

RECOMMENDED

Retry only idempotent operations, at one layer only, maximum two attempts, with exponential backoff plus jitter, disabled automatically when the circuit breaker is open, and capped by a retry budget.

WHY

Retries are useful against randomness and harmful against overload. The controls tell the difference for you.

03Single Redis vs highly available Redis+
PROBLEM

One cache node means one failure takes the cache away completely.

OPTION A — SINGLE NODE

Cheap, simple, easy to reason about.

OPTION B — REPLICATED / CLUSTERED WITH FAILOVER

Survives node loss automatically.

BENEFITS

A saves money and operational effort. B turns a 45-minute outage into a 20-second blip.

RISKS

A is a single point of failure for a load-bearing component. B costs more, and failover itself can be slow, partial or confusing.

RECOMMENDED

Highly available Redis and a cache-loss fallback plan.

WHY

HA reduces the frequency of failure; the fallback reduces the impact. You need both, because failover is never instant and never certain.

04Shared database vs separated reporting database+
PROBLEM

Heavy reports compete with customer transactions for the same CPU.

OPTION A — ONE SHARED DATABASE

Always fresh data, one place to manage.

OPTION B — SEPARATE REPORTING STORE OR REPLICA

Analytical load is physically isolated from orders.

BENEFITS

A is simple and cheap. B protects revenue-critical paths from unpredictable queries.

RISKS

A means one manager's export can slow every customer. B introduces delay, cost and a pipeline to maintain.

RECOMMENDED

Separate reporting, starting with a read replica, later a purpose-built store.

WHY

Reporting load is unbounded and unpredictable; transactional load is bounded and precious. Never let the first threaten the second.

05More caching vs scaling the database+
PROBLEM

Read load is too high for the current database.

OPTION A — CACHE MORE AGGRESSIVELY

Cheap, fast to implement, dramatic effect.

OPTION B — SCALE THE DATABASE (bigger box or replicas)

Raises true capacity, no staleness.

BENEFITS

A gives the best performance per pound. B removes the hidden dependency and keeps data fresh.

RISKS

A deepens the cache dependency — exactly today's incident. B is expensive and slow to deliver.

RECOMMENDED

Cache for speed, but size the database so it can survive the uncached load of your most important traffic, with the rest protected by shedding.

WHY

Caching is an accelerator, not a foundation. The foundation must hold when the accelerator is removed.

06Rate limiting vs accepting all traffic+
PROBLEM

Traffic can exceed capacity. Do we refuse some of it?

OPTION A — ACCEPT EVERYTHING

Nobody is ever told "no".

OPTION B — RATE LIMIT AND SHED LOAD

Some requests are politely refused to protect the rest.

BENEFITS

A feels customer-friendly. B keeps the system predictable and available for the majority.

RISKS

A means overload turns into a total outage where everyone is refused. B needs fair policy and clear messaging.

RECOMMENDED

Rate limit, with priority tiers so critical operations have their own reserved capacity.

WHY

Refusing 5% deliberately is far better than failing 100% accidentally.

07Strong consistency vs eventual consistency+
PROBLEM

Must every reader see the newest value immediately?

OPTION A — STRONG CONSISTENCY

Always the latest truth, at the cost of coordination.

OPTION B — EVENTUAL CONSISTENCY

Slightly old values are acceptable for a short time.

BENEFITS

A is essential for money, stock reservation and permissions. B allows caching, replicas and enormous scale.

RISKS

A limits throughput and availability. B can show a customer a product that just sold out.

RECOMMENDED

Strong where money and commitments happen; eventual for display, search, dashboards and counts.

WHY

Consistency is a per-operation decision, never a system-wide slogan.

08Synchronous vs background work+
PROBLEM

Should the user wait for every step of an order to complete?

OPTION A — DO IT ALL SYNCHRONOUSLY

Simple to build and easy to reason about.

OPTION B — QUEUE THE NON-ESSENTIAL STEPS

Respond as soon as the essential part is safe.

BENEFITS

A gives immediate confirmation of everything. B keeps responses fast and survives spikes and downstream failures.

RISKS

A means one slow email service can break checkout. B adds queues, delay, duplicate handling and monitoring.

RECOMMENDED

Synchronous for payment authorisation and stock reservation; background for invoices, emails, analytics and external syncs.

WHY

The user needs certainty about their money and their goods — nothing else.

09One large database vs read replicas+
PROBLEM

Reads dominate the workload and threaten the writer.

OPTION A — ONE BIGGER DATABASE

Simple, consistent, no routing logic.

OPTION B — WRITER PLUS READ REPLICAS

Reads are spread; the writer is protected.

BENEFITS

A avoids lag and complexity. B adds read capacity cheaply and gives an isolation boundary for reports.

RISKS

A has a hard ceiling and one failure domain. B has replication lag, which shows stale data if used carelessly.

RECOMMENDED

Replicas for reporting and tolerant reads; writer for anything that must be exactly current.

WHY

Most read traffic tolerates a second of lag. The few reads that do not are easy to name.

10Automatic recovery vs controlled recovery+
PROBLEM

When the dependency returns, should traffic resume automatically?

OPTION A — FULLY AUTOMATIC

Fast, no human needed, works at 3 AM.

OPTION B — HUMAN-CONTROLLED, STAGED

Traffic released step by step with checks.

BENEFITS

A minimises downtime. B avoids a second overload from a cold cache and a queued backlog.

RISKS

A can flood a fragile system and cause flapping — repeated up-down cycles. B is slower and depends on people.

RECOMMENDED

Automatic but gradual: half-open circuit breakers, staged rate limits, warm-up first; with a human able to hold or roll back.

WHY

Speed matters, but an uncontrolled return is how a 10-minute incident becomes a 60-minute one.

11Feature availability vs system stability+
PROBLEM

Under stress, do we keep every feature on, or turn some off?

OPTION A — KEEP EVERYTHING AVAILABLE

No feature is ever "missing".

OPTION B — DEGRADE DELIBERATELY

Sacrifice heavy features to protect core ones.

BENEFITS

A avoids difficult conversations. B keeps revenue flowing during trouble.

RISKS

A risks losing everything including checkout. B requires prior business agreement and switches built in advance.

RECOMMENDED

Degrade, using a priority table agreed with the business and reviewed twice a year.

WHY

Every minute of full outage costs more than a day of missing dashboards.

12Higher cost vs higher resilience+
PROBLEM

Resilience is not free. How much should we buy?

OPTION A — MINIMUM SPEND

Single instances, no standby, no spare headroom.

OPTION B — REDUNDANT EVERYTHING, MULTI-REGION

Survives almost anything.

BENEFITS

A maximises margin. B maximises availability and customer trust.

RISKS

A means one bad hour can cost more than a year of savings. B can double infrastructure spend for risks that may never occur.

RECOMMENDED

Buy resilience where an outage is expensive: HA for the cache and database, plus cheap software controls (timeouts, breakers, limits, switches) everywhere. Keep exotic multi-region for the tier that truly needs it.

WHY

The best resilience is mostly design discipline, not hardware — and design discipline is almost free. Present the cost of downtime per hour and let the business choose the level.

PART 24 — TOUGH SCENARIO

The Interviewer Speaks

SCENARIO — READ IT AS IF SAID ACROSS THE TABLE

"At 10 AM, Redis becomes unavailable. Within three minutes SQL CPU reaches 98%. API response time increases from 200 ms to 8 seconds. Clients start retrying. Background jobs are delayed. Management says the system is effectively down."

# QUESTION
1 What is happening?
2 What would you check first?
3 What would you stop?
4 How would you protect SQL?
5 How would you handle retries?
6 Which features would you disable?
7 How would you recover?
8 How would you prevent this in the future?

Rules: speak for 6–8 minutes. Structure your answer as diagnose → contain → protect → recover → prevent. Say numbers. Say trade-offs. Do not open the model answer until you have finished.

1 · WHAT IS HAPPENING

This is a cache-loss cascade, not a database problem. Redis was absorbing most read traffic. When it disappeared, every read became a database query, so SQL received several times its designed load. Above roughly 85% CPU, query time grows sharply, so requests stay open, connections stay busy, the pool fills, and requests time out. Clients then retry, which adds duplicate load, and background workers using the same database slow down, which grows the queue. One component failed; our missing protections turned it into an outage.

2 · WHAT I CHECK FIRST

Four numbers in sixty seconds: cache hit ratio and Redis reachability; SQL CPU, query duration and blocking; connection pool usage; API error rate, p95 and traffic. I also compare request count with unique users to see how much of the traffic is retries rather than real demand. In parallel I confirm no deployment or schema change happened at 09:55.

3 · WHAT I STOP

Everything optional that touches the database: scheduled reports, bulk exports, data sync jobs, analytics processing, non-critical background workers, and any deployment in progress. I also ask client and partner teams to pause automatic retries. I do not restart servers and I do not increase timeouts.

4 · HOW I PROTECT SQL

Shorten database command timeouts so connections return quickly; open circuit breakers on the heaviest read endpoints so they fail fast; cap concurrency per API instance; apply rate limits per tenant and per endpoint, tightest on the noisiest; route tolerant reads to replicas; and reserve pool capacity for P0 operations — login, order creation, payment and inventory. The aim is to shrink the queue in front of SQL, not to add capacity we cannot add in three minutes.

5 · HOW I HANDLE RETRIES

Reduce retry counts to at most one or two, at a single layer, with exponential backoff plus jitter, and disable retries automatically wherever the breaker is open. Apply a retry budget so retries cannot exceed a small share of traffic. Retries are safe only for idempotent operations; for payments I rely on idempotency keys and a status check rather than retrying the charge.

6 · WHICH FEATURES I DISABLE

P2 first: heavy dashboards become a simple summary, large exports are blocked with a 'scheduled for later' message, recommendations and activity feeds are switched off. Then P1: reports serve the last snapshot with a timestamp, notifications and analytics are queued. P0 stays fully alive. All of this is a configuration switch, not a deployment.

7 · HOW I RECOVER

Only when Redis has been stable for several minutes. Warm the top keys first — tenant settings, dashboard aggregates, catalogues, permissions — because a cold cache with full traffic recreates the outage. Then release traffic in stages, 10, 25, 50 and 100 percent, through half-open breakers, watching SQL CPU at each step and stepping back if it rises above target. Re-enable features by priority, heavy reports last. Drain the message backlog by increasing consumers gradually while watching the database. Declare recovery on business signals: orders per minute, payment success rate, error rate and p95.

8 · HOW I PREVENT IT

Highly available Redis with tested failover; an in-process fallback cache for the top read paths so cache loss is partial rather than total; a documented timeout and retry policy; circuit breakers and per-tenant rate limits as standard; feature switches for every P1 and P2 feature; reporting separated onto a replica or reporting store; alerts on cache hit ratio, database CPU, pool usage and queue age; and twice-yearly peak load tests with Redis switched off so we know our real uncached capacity. Finally, a blameless review with five owned actions and measurable success criteria.

CLOSING LINE

"The technical trigger was a Redis node. The architectural cause was that we had no defined behaviour for losing the cache. That is what I would fix first, and it costs almost nothing."

45-Minute Architecture Exercise

THE PROBLEM — ONLY THE PROBLEM

"Design a resilient enterprise application where Redis, the database, the message broker and external services can each fail independently — without the whole system going down."

DIMENSION FIGURE DIMENSION FIGURE
Peak traffic 5,000 requests/second Concurrent users 100,000
Tenancy Multi-company (shared platform) Availability target 99.9%
Workload heavy dashboards · heavy reports · orders · inventory · payments · notifications

Your design must cover: 1 failure points · 2 bottlenecks · 3 timeouts · 4 retry policy · 5 circuit breakers · 6 cache failure strategy · 7 database protection · 8 queue protection · 9 graceful degradation · 10 monitoring · 11 recovery · 12 disaster recovery · 13 trade-offs. Suggested time: 10 min questions and failure map, 25 min design, 10 min trade-offs and recovery.

1 · FAILURE POINTS

Cache node or cluster; the write database; the read replicas; the message broker; background workers; each external provider; the network between zones; and the monitoring system itself. For each I write one line: what happens, what the user sees, what we do automatically.

2 · BOTTLENECKS

The write database first, because it is the hardest to scale quickly. Then the connection pool, then the cache as a load-bearing dependency, then worker throughput. The stateless API tier is the easiest to scale and therefore rarely the true limit.

3 · TIMEOUTS

A shrinking budget: user request 5 s, API to service 3 s, service to database 2 s (reports get a separate longer path), cache 100 ms, external providers 3–10 s with a status-check path. No call anywhere without a timeout.

4 · RETRY POLICY

One retrying layer only, maximum two attempts, exponential backoff with jitter, retries only on idempotent operations, retries disabled while a breaker is open, and a global retry budget of about 10% of traffic. Payments use idempotency keys and reconciliation instead of blind retries.

5 · CIRCUIT BREAKERS

Per dependency and per operation class: cache, heavy database reads, critical database writes (high threshold), each external provider. Fallbacks defined for every breaker — stale data, reduced response, or a clear message. Half-open recovery gives automatic, gradual return.

6 · CACHE FAILURE STRATEGY

Highly available Redis, plus a small in-process cache on each API instance for slow-changing data. On cache failure: critical reads go to the database behind a concurrency limit; dashboards serve stale data with a timestamp; heavy analytics endpoints fail fast; and TTLs are jittered so keys never expire together. The cache is treated as a critical dependency with its own monitoring and alerts.

7 · DATABASE PROTECTION

The seven layers: edge rate limits and per-tenant quotas; concurrency caps and breakers on expensive endpoints; caching; query and index discipline with short transactions; reporting moved to a replica or reporting store; read replicas for tolerant reads; and capacity monitoring with alerts at 70% CPU. Separate connection pools per workload so reporting can never starve checkout.

8 · QUEUE PROTECTION

Separate queues by priority (order events vs marketing), an outbox so events are never lost if the broker is down, retry limits with dead-letter queues that are monitored, idempotent consumers, and consumer autoscaling that is aware of database load rather than queue depth alone.

9 · GRACEFUL DEGRADATION

P0 login, orders, payment, inventory — always on, with reserved capacity. P1 notifications, reporting, analytics — delayed. P2 heavy dashboards, exports, recommendations — switched off. Every P1/P2 feature has a runtime switch and a designed degraded screen. The priority table is signed off by the business.

10 · MONITORING

Traffic, errors, latency and saturation for every component; cache hit ratio and latency; database CPU, query duration, blocking and pool usage; queue depth and message age; per tenant usage; end-to-end traces; synthetic user journeys running continuously; and a heartbeat alert if metric data stops arriving.

11 · RECOVERY

Stability check, cache warm-up of the top keys, staged traffic release through half-open breakers, feature restoration by priority, controlled queue drain, then validation on business signals before declaring the incident closed.

12 · DISASTER RECOVERY

Defined RPO and RTO agreed with the business — for example RPO 5 minutes, RTO 1 hour. Asynchronous replication to a second region with a warm standby, tested failover twice a year, documented fail-back and data reconciliation, and backups whose restore is actually tested rather than assumed.

13 · TRADE-OFFS I WOULD STATE OUT LOUD

Stale dashboards in exchange for a surviving database. Rejected requests in exchange for stable service for the majority. Slightly higher cost for HA cache and replicas in exchange for shorter outages. Eventual consistency for display data, strong consistency for money. Warm standby rather than active-active, because the cost of active-active is not justified by a 99.9% target.

1–3 · RETRIES

I retry idempotent reads and idempotent event processing, because a repeat is harmless and most failures there are transient. I do not retry payment authorisation or order creation without an idempotency key, because a repeat can duplicate money. Storms are prevented by four things together: two attempts maximum at one layer, exponential backoff with jitter, retries disabled while the breaker is open, and a retry budget capping retries at about 10% of traffic.

4 · REDIS DOWN FOR 30 MINUTES

The system runs in degraded mode for 30 minutes and that is acceptable by design. The in-process cache absorbs slow-changing reads, dashboards serve stale data with timestamps, heavy analytics is off, and the database serves only critical paths behind a limiter. Orders and payments continue. We are slower and less rich, but we are trading and not losing data.

5 · WHAT PROTECTS SQL

Layered, not single: edge rate limits, per-tenant quotas, concurrency caps on expensive endpoints, breakers on heavy reads, short database timeouts, separate pools per workload, reporting on a replica, and P2 features switched off. Any one of these can be bypassed; all of them together mean cache loss cannot translate one-to-one into database load.

6 · STALE DATA DURING A SALE

Acceptable for browsing counts, unacceptable for reservation. Prices and stock are validated against the database at checkout, so the worst case is a customer sees an item as available and is told at checkout that it has gone — annoying but honest. Money-critical values are never served from a long-lived cache, and invalidation is event-driven with short jittered TTLs.

7 · WHY NOT REMOVE REDIS

Because a database large enough to serve 5,000 requests per second of uncached reads costs far more than a cache cluster, scales less smoothly and still has a hard ceiling. The cache is the cheapest capacity we own. The correct answer is not to remove it but to stop pretending it cannot fail.

8 · HOW WE KNOW WE RECOVERED

Business signals plus technical signals held for a sustained period: orders per minute and payment success rate at baseline, error rate below 0.5%, p95 back to about 200 ms, cache hit ratio normal, database CPU under 60%, pool under 50%, queue age near zero, DLQ reviewed. Green servers alone never close an incident.

9 · TWO SIMULTANEOUS FAILURES

Because protections are per dependency, a second failure degrades a second area rather than multiplying. If cache and broker both fail, reads degrade and events are written to the outbox for later publishing, while orders continue. If cache and database both degrade, we drop to the smallest possible surface — login and order capture only — because that is the business floor we agreed.

10 · PRIORITY OWNERSHIP

The priority table is owned by the business, not by engineering, and reviewed twice a year. Login, orders, payment and inventory are P0. Engineering implements switches; the business decides what may go dark. Decided in advance, never during the incident.

11 · ONE TENANT AT 10×

Their quota absorbs it: they are throttled with clear 429 responses and their bulk work is moved to a separate queue and schedule, while other tenants see no change. We then contact them and, if the growth is genuine, sell them dedicated capacity. Fairness is enforced by architecture, not by trust.

12 · COST OF RESILIENCE

I would spend roughly this way: software controls — timeouts, breakers, limits, switches, idempotency — near zero cost and non-negotiable; HA cache and read replicas — moderate, justified by the cost of one hour of downtime; multi-region warm standby — significant, and justified only because a 99.9% target and regulatory expectations require it. Active-active everywhere is not justified and I would say no.

13 · BREAKER OPENS AT NORMAL PEAK

That is a tuning fault, and it is an incident of its own. Thresholds are set from observed p99 plus margin, with a minimum request volume before the breaker can trip, and we alert on breaker state changes so false opens are detected and corrected quickly.

14 · REPLICA LAG OF 90 SECONDS

Anything that must reflect the user's own last action breaks — order status right after checkout, updated profile, stock reservation. Those reads go to the writer or use read-your-own-writes routing. Everything else tolerates lag. We alert when lag exceeds a threshold and automatically stop routing sensitive reads to lagging replicas.

15 · SLOWNESS RATHER THAN ERRORS

Slowness is the dangerous case, so we convert it into failure deliberately: short timeouts, breakers that count timeouts as failures, and health checks that measure latency rather than mere liveness. A dependency that is 'up but 8 seconds slow' is treated as down.

16 · WHO FLIPS THE SWITCHES

On-call engineers, within seconds, via configuration — no deployment, no approval chain during an incident. Every flip is logged and announced, and there is a documented default state so nothing is left switched off after recovery.

17 · TWO MILLION MESSAGE BACKLOG

Check message age and business impact first. Split the queue: process order-critical messages first, discard or resample pure analytics events if the business agrees, and drain the remainder at a rate the database tolerates, scaling consumers in steps. Communicate the expected drain time in hours, honestly.

18 · MONITORING DOWN

Treated as an incident in its own right. We rely on an independent secondary check — synthetic transactions from outside, direct health endpoints, and cloud-native metrics — and we have heartbeat alerts that fire when metric data stops arriving, because silence is the most dangerous alert of all.

19 · PROVING IT WORKS

Peak load tests with the cache disabled; controlled failure drills where we kill a cache node, a worker and a broker node; runbook game days with the on-call team; and continuous synthetic journeys in production. Each drill has a written expected behaviour, and any surprise becomes a backlog item.

20 · BUDGET CUT BY 30%

I keep everything free or cheap that prevents cascades: timeouts, retries policy, breakers, limits, switches, monitoring and alerts. I keep HA on the cache because it is small money protecting large money. I cut the standby region to a colder, slower recovery tier, reduce over-provisioned headroom in favour of autoscaling, and shorten metric retention. I state clearly which risk increases and by how much, and ask the business to accept it in writing.

CLARIFYING QUESTIONS I WOULD ASK FIRST

The database, triggered by two things at once: a cache hit-ratio dip at peak, and unthrottled bulk imports from three tenants at 09:15. PROTECTION LAYERS I WOULD ADD

Per-tenant rate limits and a scheduled off-peak window for bulk imports; concurrency caps and circuit breakers on the ten most expensive endpoints; separate connection pools for reports, workers and user traffic; short database timeouts; feature switches for dashboards and exports; an in-process fallback cache with jittered TTLs; reports moved to a read replica; and a strict retry policy across clients and services.

At peak stress the system sheds in a defined order: recommendations and activity feeds off, exports blocked, dashboards simplified with stale data and a timestamp, reports served from the last snapshot. Orders, payments, inventory and login keep reserved capacity and remain fully functional. Users are told what is temporarily reduced.

RECOVERY

Mostly automatic: breakers half-open and close as latency falls, rate limits step back up, features re-enable by priority, and workers scale their drain rate with database load in mind. A human confirms on business signals. No mass restart, no cold-cache flood.

MONITORING

Alerts that fire before customers notice: cache hit ratio below 70%, database CPU above 70%, query duration above 2× baseline, pool usage above 80%, queue age above 3 minutes, p95 above 800 ms, plus per-tenant request rate so the 09:15 imports are visible as they start. Add synthetic checkout journeys every minute and a heartbeat alert on the metrics pipeline.

COST

Roughly 80% of this is engineering work, not infrastructure: limits, breakers, timeouts, switches, pools, retry policy, alerts. The infrastructure additions — one read replica and a second cache node — fit comfortably inside the 15% ceiling, and the replica also removes reporting load, which buys back headroom. Nothing here requires a bigger database.

TRADE-OFFS I WOULD STATE

Bulk imports become slower and scheduled, which three tenants will notice and must accept. Dashboards may show data a few minutes old at peak. Some requests will be throttled with clear messages. Reports on a replica are slightly delayed. In exchange, peak-hour instability disappears and the availability target becomes achievable. "Zero downtime" is not purchasable at this budget; 99.9% with graceful degradation is, and I would put that in writing.

Week 1: per-tenant rate limits and move bulk imports off peak; short database timeouts; retry policy fix. Week 2–3: separate connection pools; circuit breakers and feature switches on the ten heaviest endpoints; the alert set. Month 2: read replica for reporting; in-process fallback cache; second cache node. Month 3: load test at peak with the cache disabled, a game day, and a documented runbook. Cheapest and highest impact first — that ordering is the answer they are really testing.

ONE-MINUTE INTERVIEW ANSWER — "REDIS IS DOWN AND THE DATABASE IS OVERLOADED. WHAT DO YOU DO?"

"First I would confirm the shape of the problem: is Redis really down, and is the database slow because of extra load or because of one bad query? The likely story is simple — Redis is gone, every read now goes to SQL, and the database is doing work it was never sized for.

My first goal is not to fix Redis. My first goal is to stop the database from dying, because if SQL dies we lose orders and payments too. So I reduce load: turn off heavy dashboards and big reports, apply rate limits on the most expensive endpoints, shorten database timeouts so slow requests release their connections quickly, and open the circuit breaker on the endpoints that are hammering SQL so they fail fast with a clear message instead of queuing up.

At the same time I stop the retry storm — retries are multiplying the load, so I cut retry counts, add backoff with random delay, and ask client teams to stop automatic retries for read endpoints. I protect the critical business functions: login, order creation, payment and inventory stay up; notifications, analytics and reporting can wait.

Then I bring Redis back — but I do not open all traffic at once. I warm the most-used keys, release traffic gradually, and watch SQL CPU, latency, error rate and queue depth. Recovery can cause a second outage if you rush it.

Afterwards, prevention: highly available Redis, sensible timeouts everywhere, circuit breakers, rate limits per tenant, a separate reporting path, and a load test that runs with the cache switched off — so we already know what happens before it happens."

ONE POWERFUL ARCHITECT STATEMENT

"I do not design systems that never break. I design systems that break in one place, quietly, on purpose — where the failure is contained, the important business still runs, and recovery is a planned step rather than a lucky escape."
