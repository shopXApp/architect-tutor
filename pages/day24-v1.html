PART 01 — START LIKE AN ARCHITECT

Understand the Product Before You Draw the Pipes

A messaging app looks simple — "just send text from A to B". But the product promises are brutal: arrive in a blink, in order, exactly once, even if B is offline for a week, even if the network dies mid-send. If you draw servers before you understand those promises, you will design a chat demo, not WhatsApp. Architects start with what it must do, what it must be, and how big it is.

WHY PRODUCT FIRST?

Every product promise becomes an architecture burden. "Works offline" means a pending-message queue and push notifications. "Never lose a message" means store-before-acknowledge and retries. "Groups of 10,000" means fan-out engineering. "Read receipts" means a reverse acknowledgement pipeline. List the promises first and the boxes almost draw themselves.

The order an architect follows

  1. Functional requirements — what users can DORegister, chat one-to-one and in groups, send media, see ticks, block, delete. No technology words yet.
  2. Non-functional requirements — what the system must BEHow many users, how fast a message arrives, how available, how durable. These constraints shape everything.
  3. Scale in real numbersRegistered users mean nothing. You need concurrent connections and messages per second at peak.
  4. One message end to endA sends "Hello" to B — happy path first, then offline B, dead network, duplicate send, lost acknowledgement.
  5. The data and its personalityPermanent messages, temporary presence, expiring typing signals — three personalities, three handlings.
  6. The simplest design that survives itA connection layer, a message service with durable storage, and a queue for offline/push delivery. Split later on measured pain.

Say: "Before I draw — can I confirm peak concurrent connections, whether groups can reach thousands of members, the delivery-time target, and whether history must sync to new devices?" Four questions that prove you design from promises, not from habit.

PART 02 — DEFINE REALISTIC SCALE

From 500 Million Accounts to Messages Per Second

Registered users are a vanity number. Walk the funnel: registered → daily active → messages/day → messages/second → peak → fan-out → storage. Easy numbers, said out loud.

OUR ASSUMPTIONS (STATE THESE OUT LOUD)

Registered users 500,000,000
Daily active users (DAU) 100,000,000
Concurrently connected 20,000,000 open connections at peak
Messages per active user per day ~40 (sent + received, text-heavy with some media)
Group share ~35% of messages go to groups; average group fan-out ~15 deliveries per send
Coverage Global — users in every timezone

1 · Messages per second

THE MATH

100,000,000 users × 40 messages = 4,000,000,000 (4 billion) messages/day.

4,000,000,000 ÷ 86,400 seconds ≈ ~46,000 messages/second on average.

Evenings peak at ~3–4× the average → design for ~150,000–200,000 sends/second at global peak, with single-region bursts higher.

2 · Real delivery load (fan-out multiplier)

A "send" is not a "delivery". One group message to 15 members means 15 deliveries. With ~35% of sends being group messages at ~15× fan-out:

THE MATH

Blended multiplier ≈ (65% × 1) + (35% × 15) ≈ ~6 deliveries per send.

46,000 sends/s × 6 ≈ ~275,000 deliveries/second average, and over 1 million/sec at peak. This is the number the connection and queue tiers feel.

3 · Concurrent connections

20 million open sockets at peak. If one connection server comfortably holds ~50,000–100,000 sockets, that's roughly 200–400 connection servers globally — before redundancy and regional split. Memory per socket (buffers, session state) is the sizing unit, not CPU.

4 · Storage per day and per year

THE MATH — TEXT CORE

Average stored message ≈ 500 bytes (200–300 bytes of text + id, sender, conversation, sequence, timestamps, status).

4,000,000,000 × 500 bytes = ~2 TB/day of message records (logical; ×3 with replication ≈ 6 TB/day raw).

Per year: 2 TB × 365 ≈ ~730 TB/year logical — under 1 PB for the text core, very manageable with tiering.

THE MATH — MEDIA DOMINATES

Assume 10% of messages carry media at ~200 KB average (photos, voice notes, compressed video).

400,000,000 × 200 KB = ~80 TB/day of media — 40× the text core. Media needs object storage, CDN caching, thumbnails, and expiry/retention policies. Media is the storage bill; text is a rounding error.

5 · Network traffic

Roughly: 4B sends/day × ~1 KB wire size (payload + encryption + protocol overhead) ≈ 4 TB/day inbound; deliveries multiply by ~6× ≈ ~25 TB/day outbound, plus media downloads (cached at CDN edges), presence/typing chatter, and history syncs. Design for tens of TB/day with regional peering — and note that fan-out, not sends, drives the pipe.

RULE OF THUMB TO QUOTE

"Sends are thousands per second; deliveries are millions per second; media is terabytes per day. Three different numbers, three different scaling stories — size each lane from its own number."

THE INTERVIEW LINE

"One modular core for identity, conversations, groups and status; the socket layer and media separate immediately because their resource profile is alien to everything else; message storage, presence and notifications earn independence as their load curves diverge."

The Minimum Boxes That Earn Their Place

Read top to bottom: apps hold one open pipe each into a dedicated connection layer; the message service stores then routes; offline users are served by queues plus push; media bypasses the message database entirely. Every box below answers "why do we need it?" — nothing is fashionable filler.

WHAT IS DELIBERATELY NOT HERE

No ML platform, no service mesh, no blockchain identity. Every box answers a measured load or a product promise. If you can't say what breaks when a box is removed, it doesn't belong on the whiteboard.

PART 05 — SENDING A MESSAGE

User A Sends "Hello" to User B

One message, every step, with the labels that matter: validated where, stored where, delivered how — and what changes when B is offline or delivery fails.

  1. APPUser A types "Hello" and taps sendThe app creates a client message id (a unique id made on the phone, e.g. random UUID) and shows the message immediately as "sending" (clock icon). The phone keeps a copy — it owns retrying until the server confirms.
  2. PIPEApp → connection / APIThe message travels over A's open socket (with auth token attached) to the connection layer, which forwards it to the message service.
  3. VALIDATEMessage service validatesIs the sender authenticated? Is the conversation real and is A a member? Is B blocking A? Is it spam-shaped (rate limits)? Rejects fail fast with an error — never stored, never delivered.
  4. DEDUPEDuplicate check by client idIf this client id was already processed (A's network died and the phone retried), the service returns the original result without storing again. Retries are safe by design.
  5. STORE FIRSTAssign sequence + store durablyThe message gets the next sequence number in that conversation (…4821, 4822…) and is written to the message store. Only after the write succeeds does the server acknowledge A ("stored" — first tick). The database write happens before any delivery attempt.
  6. ROUTEDelivery startsThe router table answers "where is B right now?" — which connection server holds B's socket, if any. Then one of two paths:
  7. ONLINE PATHB is online → push down the socketThe message is pushed instantly to B's connection server and down B's socket. B's app stores it locally, renders it, and sends back a delivery acknowledgement ("ack" — a tiny "got it" reply), which flips A's ticks to delivered.
  8. OFFLINE PATHB is offline → queue + pushThe message waits in B's durable offline queue; a push notification ("A: Hello") is queued to Apple's/Google's service. When B reconnects, queued messages stream down in sequence order and B acks each.
  9. READ PATHB opens the chat → read ackB's app sends a read acknowledgement; A's ticks turn blue. In groups, one ack per member; the sender sees "read by 47".
  10. RETRY PATHIf delivery fails → retry with backoffNo ack within the timeout? Retry — after 1s, then 2s, 4s… (backoff: waiting longer between attempts so a struggling system can recover). Retries are idempotent: B's app dedupes by message id, so a redelivered message never appears twice.
QUESTION ANSWER
Where is it validated? In the message service — auth, membership, blocks, rate limits — before anything is stored.
Where is it stored? In the partitioned message store under (conversation id, sequence number), plus the client id for dedupe.
How does delivery start? Router-table lookup for B's live socket; online → push now, offline → durable queue + push notification.
B online? Sub-second push, delivery ack flips the ticks, read ack turns them blue.
B offline? Queued durably, push wakes the phone, full catch-up in order on reconnect.
Delivery fails? Bounded retries with backoff, then the message waits in the queue; repeated poison failures go to a dead-letter area for inspection — never silently dropped.
PART 06 — ONLINE USER VS OFFLINE USER

The Two Fates of Every Message

This split is the soul of messaging architecture. Online delivery is a fast memory lookup and a socket write. Offline delivery is durable patience: store, queue, notify, and wait — for minutes, days, or weeks.

User B is online

  1. Router lookupThe ephemeral store answers "B lives on connection server #214" in microseconds.
  2. Instant pushThe message service hands the message to server #214, which writes it to B's socket. Target: tens to low-hundreds of milliseconds.
  3. Device ackB's app persists the message locally first, then acks. Only the ack advances status to delivered — the server never assumes a socket write arrived.
  4. Read ack laterWhen B opens the chat, a second ack marks it read. Two separate signals, two separate tick states.

User B is offline

  1. Stored durably firstThe message is already safe in the message store (Part 5, step 5) — offline changes nothing about storage.
  2. Kept pending in B's queueA durable per-user (or per-device) offline queue holds the message reference in order. Queues survive server restarts; they are the reason "your week-old messages arrive when you land".
  3. Push notification sentA notification event goes to the phone maker's push service ("A: Hello"). Push is a wake-up tap, not the message — the real content arrives over the socket after reconnect (safer for privacy and size).
  4. Reconnect catch-upB reconnects → authenticates → announces "last message I have is #4821" → server streams #4822… in order → B acks each → presence flips online. Missed knowledge is repaired by replay, not by guessing.
  5. Expiry and limitsQueues have retention policies (e.g. hold up to N days / M messages, then summarize or expire per product rules) so a dead account can't grow a queue forever.
WHY STORE BEFORE CONFIRMING?

The server acknowledges the sender ("stored ✓") only after the message is durably written. That ordering is the entire reliability contract: once the sender sees a tick, the message can survive any crash, any offline peer, any reconnect — because it lives on disk, not in someone's memory. Confirm-then-store would lose messages on every server failure; it's the difference between "usually works" and infrastructure.

PART 07 — REAL-TIME CONNECTIONS

Why Chat Needs an Always-Open Pipe

A message can arrive at any millisecond, and users expect it instantly. The app can't afford to "check for mail" every few seconds — with 20M users that means hundreds of millions of empty checks per hour. Compare the three classic approaches honestly.

APPROACH HOW IT WORKS ADVANTAGES DISADVANTAGES
Polling App asks "any new messages?" every N seconds; server answers yes/no. + Dead simple; works through any proxy/firewall; no connection state on servers. − Latency up to N seconds; battery drain; enormous empty request volume at 20M users.
Long polling App asks; server holds the request open until a message arrives or a timeout hits; app immediately re-asks. + Near-instant delivery; far fewer empty responses than polling. − Holding millions of open HTTP requests is expensive; reconnect churn on mobile networks; still request/response shaped.
WebSocket / persistent connection One long-lived two-way socket per device; either side sends the instant there is data; heartbeats detect death. + Instant both ways; lowest per-message cost; natural home for acks, presence, typing. − Servers must hold millions of idle sockets (memory); needs reconnect, routing and heartbeat engineering.
COMPARE ON POLLING LONG POLLING PERSISTENT SOCKET
Server load at 20M users Crushing — millions of requests/min, ~99% empty. Heavy — millions of held requests + reconnect storms. One socket each; cost is mostly idle memory.
User experience Seconds late; stale ticks; battery drain. Good when connected; hiccups on network flips. Instant send, instant ticks, live presence/typing.
When to use it Rarely-changing data; hostile networks as last-resort fallback. Fallback where raw sockets are blocked; simple low-scale products. Default for real-time messaging at any serious scale.
THE PRAGMATIC STACK

Persistent sockets as the default transport, mobile push as the wake-up channel for backgrounded/offline devices, and polling only as a degraded fallback (e.g. syncing missed history after a long outage). Say that trio in the interview: it shows you choose by context, not by loyalty.

SOCKETS ARE NOT THE TRUTH

The socket is a pipe, not a database. Every important fact — message content, order, status — lives server-side in storage. If the pipe dies mid-sentence, reconnect + replay from storage repairs everything. Architects who treat the connection as reliable storage design systems that lose messages on every tunnel and elevator.

PART 08 — CONNECTION MANAGEMENT

Holding 20 Million Pipes Without Dropping Them

Connections are state: each socket lives on exactly one server, phones move between networks constantly, and servers die. Managing that at scale needs deliberate routing, heartbeats, and a shared map of who lives where.

  1. Distribute connections across many serversPhones connect through load balancers to a fleet of connection servers (hundreds globally). Each server holds tens of thousands of sockets; sizing is by memory (buffers + session state per socket), and new servers join the pool with no reshuffling of existing sockets.
  2. Keep a shared router tableA fast shared store maps user id → connection server + socket handle + version. When the message service must reach B, it reads this table instead of broadcasting to hundreds of servers. Entries carry a TTL and a version so stale mappings die fast.
  3. Heartbeats detect silent deathPhones send tiny heartbeats every ~30–60s; missed beats mean the socket is dead even if nobody closed it (tunnels, dead batteries). The server then frees the socket, clears the router entry, and flips presence to offline with a last-seen stamp.
  4. Reconnect is a first-class flowOn reconnect the phone authenticates, gets placed (possibly on a different server), re-registers in the router table with a new version, and announces its last received sequence per conversation — the server replays the gap. Old router entries are fenced by version so late writes from the dead socket can't hijack routing.
  5. Server failure sheds, then healsIf a connection server dies, its ~50k phones notice (heartbeat failure) and reconnect to healthy servers with jittered backoff (random delays so they don't stampede at once). No messages are lost — content lives in the message store and queues, never in connection memory.
  6. Multiple devices multiply everythingPhone + web + tablet each hold a socket and a router entry. Delivery fans out to all of a user's devices; a read on one marks read everywhere via status sync events.
WHY CONNECTION STATE IS HARD

Because it changes constantly (every network flip), lives in server memory (dies with the server), and must be globally readable in microseconds (every delivery needs it). The answer is a shared, versioned, TTL-expiring router table in fast storage — connection servers stay dumb pipes, and all "who is where" knowledge lives in one replaceable place that rebuilds itself from reconnecting phones.

PART 09 — MESSAGE DELIVERY

Sent, Stored, Delivered, Read — Four Facts, Not Feelings

Each tick is a recorded event driven by an acknowledgement (a small "got it" reply). The sender's UI is just a mirror of these server-side facts.

FIG 3 — THE DELIVERY STATE FLOW: EACH TICK IS EARNED BY AN ACK
STATE MEANS TRIGGERED BY
Sent Left the sender's phone; nothing is guaranteed yet. Phone queued it to the socket.
Stored ✓ Validated, sequenced and durably written. Survives any crash from here on. Server ack after the store write.
Delivered ✓✓ On the recipient's device storage (not necessarily seen). Device delivery ack.
Read (blue) Recipient opened the conversation containing it. Read ack from the app.

What happens when things go wrong

  • Stored but delivery fails: the message waits safely; the sender sees one tick; retries continue with backoff and the offline queue holds it until B returns. Nothing is lost, nothing is half-shown.
  • User disconnects mid-delivery: unacked messages stay pending; on reconnect the server replays from the last acked sequence. The app dedupes by id, so replays never double-render.
  • User opens the message days later: read status simply arrives late — acks have no expiry pressure; the sender's ticks update whenever the truth arrives. History paging shows the same states.
  • Delivery ack is lost: the server, unsure, redelivers; B's app sees an already-known id and drops the duplicate but re-sends the ack. At-least-once delivery + idempotent receive = exactly-once effect.
DESIGN RULE

Status transitions are idempotent and monotonic (they only move forward: stored → delivered → read). A duplicate or out-of-order ack can never move a message backward or create a second copy. Guard every transition with "only if currently in the earlier state".

PART 10 — MESSAGE ORDERING

"Hi. How Are You? Where Are You?" — In That Order, Always

If three messages arrive shuffled, conversations become nonsense. Ordering is one of the hardest guarantees in distributed systems, because speed wants many parallel paths and order wants exactly one.

What can go wrong

A sends three messages quickly. Without design, message 1 might travel through server X while 2 and 3 go through server Y; a retry delays #1; B's phone renders 2, 3, then 1 — "How are you? Where are you? Hi." Worse in groups: two members' replies can interleave differently on different phones, so two people literally see different conversations.

FIG 4 — PARALLEL DELIVERY WITHOUT SEQUENCE NUMBERS SHUFFLES CONVERSATIONS

How the architect keeps order

  1. Sequence numbers per conversationEvery message in a conversation gets the next integer: 4821, 4822, 4823… Apps render strictly in sequence order and can detect gaps ("I have 4821 and 4823 — resend 4822"). The number is the order; nothing else is.
  2. Single logical writer per conversationAll messages of one conversation flow through one sequencing owner (one partition leader / one queue). Parallelism happens across conversations, never inside one. This is the core trade: per-chat serialization buys global parallelism.
  3. Partition by conversation idPartitioning (splitting data across machines by a key) uses the conversation id as the key, so one chat's messages and its counter live together on one partition — sequencing is a local increment, fast and contention-free.
  4. Timestamps are for display, not orderPhone clocks lie (wrong timezones, manual changes). The server stamps an authoritative time for "sent at 14:02", but ordering and gap detection use sequence numbers only.
  5. Gap repair on the clientApps buffer out-of-order arrivals briefly and request missing sequences explicitly. The server supports "give me #4800–#4900" cheaply because storage is keyed by (conversation, sequence).
TRADE-OFF WHAT YOU GAIN WHAT YOU SACRIFICE
Per-conversation sequencing Perfect order inside every chat; simple mental model; cheap gap repair. One hyperactive group is bottlenecked by its single writer (mitigate: batching, fast in-memory counters, Part 14).
Global ordering (all chats, one counter) Total order across everything (rarely needed). One global lock for billions of messages/day — unbuildable. Rejected.
Timestamp-only ordering No sequencer needed. Clock skew shuffles chats; ties are unresolvable. Rejected as the ordering mechanism (kept for display).
THE ANSWER TO MEMORIZE

"Order is per conversation, assigned by a single logical writer as incrementing sequence numbers, stored under (conversation, sequence), with clients repairing gaps by number. Timestamps are decoration." Say that and the ordering question is over.

PART 11 — DUPLICATE MESSAGES

The Network Fails, the Phone Retries, the Server Sees It Twice

Duplicates are not a bug to hope away — they are guaranteed by retries, reconnects and lost acks. The architecture must make receiving the same message twice completely harmless.

How duplicates happen — and why they're dangerous

  • Sender retry: A sends "Hello"; the ack is lost in a tunnel; the phone resends. Server sees two identical sends.
  • Delivery retry: B receives the message but its ack is lost; the server redelivers. B sees it twice.
  • Reconnect replay: B reconnects and the server replays messages already received before the drop.
  • Why dangerous: double-rendered messages destroy trust ("did I send that twice?"), double notifications annoy, and duplicate processing (two sequence numbers for one send) breaks ordering and history.

Three practical approaches (use all three — they guard different doors)

  1. 1 · Client-generated unique message id + server dedupeThe phone creates one id per send and reuses it on every retry. The server keeps a dedupe record (id → result) and returns the stored result for repeats instead of reprocessing. This is the primary defense — it converts "send twice" into "send once, confirm twice".GUARDS: SENDER RETRIES AND DOUBLE-TAPS
  2. 2 · Idempotent receive on the deviceIdempotent means "doing it twice has the same effect as once". B's app stores received ids; a redelivered message matches an existing id, is dropped from rendering, but still re-acks (so the server stops retrying). GUARDS: DELIVERY RETRIES AND REPLAYS
  3. 3 · Idempotent processing with unique constraintsThe message store enforces uniqueness on the client id (and on (conversation, sequence) assignment), so even two racing server workers can't create two rows. The loser returns the winner's result. GUARDS: RACES INSIDE THE BACKEND
PREFERRED APPROACH — AND WHY

Client-generated ids with server-side dedupe as the backbone, idempotent device receive as the second layer, unique constraints as the backstop. The client id is preferred because it survives every failure mode (retry, reconnect, failover) without coordination, costs one tiny lookup, and keeps the sender's "send" operation safe to repeat forever. Dedupe records can expire after days/weeks since retries don't span months.

PART 12 — RETRY AND FAILURE HANDLING

Retry With Manners, or Don't Retry at All

Retry means trying again after failure. Done blindly, retries multiply a small fire into an inferno (retry storm: every client hammering a sick server simultaneously). Every retry in the system needs four properties below.

MECHANISM WHAT IT MEANS IN SIMPLE ENGLISH MESSAGING EXAMPLE
Acknowledgement A tiny "got it" reply that stops retries. No ack within timeout = assume failure. Server ack → sender stops; device ack → server stops; read ack → ticks turn blue.
Backoff + jitter Wait longer between attempts (1s, 2s, 4s…); add randomness so millions of clients don't retry in lockstep. 50k phones reconnecting after a dead server spread over ~30s instead of one second.
Bounded retries Every retry loop has a max count or max age — then it parks, not spins. Undeliverable message waits in the offline queue for reconnect instead of retrying every second for a week.
Dead-letter handling Messages that fail repeatedly move to a quarantine area (dead letter queue) for inspection, alerting, and manual or delayed reprocessing. A poison message (corrupt payload crashing a worker) is quarantined after N tries instead of crashing every worker forever.
Duplicate detection Every retried operation carries its original id so repeats collapse safely. Client message ids (Part 11); idempotent ack processing.
Reprocessing from storage Recovery replays from durable state, never from memory. After a crash, workers resume from queue offsets and "last acked sequence", not from what they remember.
Connection retry Phones re-establish dead sockets with backoff and resume exactly where they left off. "Last sequence I have is #4821" → server replays the gap, nothing more.
WHY BLIND RETRY MAKES IT WORSE

Imagine the message store slows down. Without discipline, every sender retries instantly, every retry adds load, the store slows further, timeouts cascade — a death spiral called congestion collapse. The cures: backoff with jitter, bounded attempts, circuit breakers (stop calling a failing dependency for a while and fail fast instead), load shedding (serve "queued, will send" rather than dying), and queues that absorb the spike while humans fix the cause.

PART 13 — MESSAGE STORAGE

What a Message Row Carries, and Where Billions of Them Live

Message storage is write-heavy (200k/sec at peak), ordered, and queried in exactly one dominant pattern: "give me conversation X, messages after sequence N". That pattern picks the storage more than any fashion does.

What gets stored per message

IDENTITYMessage id (server), client message id (dedupe key), conversation id, sender id.
ORDER + TIMESequence number within the conversation; server timestamp (authoritative display time).
CONTENTText body (or encrypted blob); message type (text/image/video/voice/doc/system).
STATUSStored/delivered/read state — per recipient in groups.
MEDIA REFERENCEPointer to the object-store file + thumbnail id — never the bytes themselves.
LIFECYCLEExpiry/disappearing-message deadline, delete flags, edit history pointer, report hash.

Relational (SQL) vs NoSQL for messages

COMPARE ON RELATIONAL (SQL) NOSQL (WIDE-COLUMN / DOCUMENT)
Message volume 4B rows/day needs aggressive sharding; single-primary writes top out fast. Built for massive partitioned writes; linear scale by adding nodes.
Query pattern Fine for key lookups, but range scans across shards need care. "Partition = conversation, rows ordered by sequence" is the native shape of wide-column stores.
Relationships Joins, constraints, transactions — ideal for users, groups, rosters, blocks. Weak joins; relationships handled in application code.
Scaling Scale up, read replicas, then painful manual sharding. Horizontal by design; add nodes, rebalance automatically.
Cost & ops Cheaper and simpler at small scale; sharded-SQL ops get expensive. More cluster to operate, but cheaper per billion writes at scale.
RECOMMENDED SPLIT

NoSQL wide-column/document store for the message firehose (partition key = conversation id, clustering = sequence number), relational database for the transactional core (users, groups, rosters, blocks, settings), plus object storage for media and in-memory stores for ephemeral data. Each workload gets the engine shaped like its queries — that's the whole decision.

PART 14 — CONVERSATION STORAGE AND PARTITIONING

One Global Message Table Cannot Survive This

Partitioning means splitting data across many machines by a key; sharding is the same idea applied to databases (each machine owns a "shard"). The key you choose decides what stays fast — and what becomes a distributed headache.

PARTITION BY WHAT STAYS FAST WHAT GETS HARD (TRADE-OFF)
Conversation id (recommended for messages) One chat's history + sequence counter live together; ordering is a local increment; "messages after #N" is one partition read. A mega-active group concentrates writes on one partition (hot partition) — needs batching and fast counters.
User id "All my chats" upkeep and per-user quotas are local. One conversation's messages scatter across two users' partitions; ordering and history reads need coordination.
Geography / region Local latency, data residency, regional failure isolation. Cross-region chats (A in Berlin, B in Tokyo) need an owner region and replication.
Time buckets (month/week) Beautiful for cold archiving and retention expiry (drop whole old partitions). Terrible as the primary key — every active chat would span buckets; use for tiering, not for live reads.

When one group becomes extremely active

A 10,000-member group during a live match can produce thousands of messages per minute — all landing on one conversation partition. The design absorbs it by: keeping the write path tiny (append + counter increment), batching status updates, fanning out delivery asynchronously (Part 15), caching the roster, and rate-limiting per-sender floods. The partition stays a fast append log; all expensive work (10,000 deliveries, 10,000 ticks) happens downstream in parallel. If one group still saturates a partition, split storage cells further (sub-partition by time within the conversation) while keeping a single logical sequencer.

PARTITIONING MANTRA

Partition by the key your hottest query uses (conversation id), replicate for survival, tier by age for cost, and never let a hot key's delivery work block its write path.

PART 15 — GROUP CHAT

One Message In, Ten Thousand Deliveries Out

Groups are harder than 1:1 chat because a single send explodes into thousands of deliveries, thousands of acks, and per-member read states. The central decision is when that explosion happens: at send time or at read time.

FIG 5 — FAN-OUT ON WRITE VS FAN-OUT ON READ

The two approaches in plain English

  • Fan-out on write means: when the message is sent, immediately write a copy (or delivery task) into every member's inbox/queue. Reads are then trivial — "show my inbox" — because the work already happened.
  • Fan-out on read means: store one copy in the group's ordered log; each member reads "all messages after my last seen sequence" when they open the chat or reconnect. The send is cheap; reads do the work.
COMPARE ON FAN-OUT ON WRITE FAN-OUT ON READ
Write load 1 send → 10,000 inbox writes. Spiky and heavy. 1 send → 1 log append. Constant and tiny.
Read load Inbox reads are instant and simple. Every open/reconnect scans the group log for "after my sequence".
Storage 10,000 copies of one message (or 10,000 queue tasks). One copy + tiny per-member pointers.
Latency Online members get pushes immediately either way; history instant. Online pushes still instant; history needs a log read (fast when keyed by sequence).
Complexity Simple reads; heavy write pipeline with partial-failure handling (9,998 of 10,000 delivered?). Simple writes; needs per-member cursors and efficient range scans.
WHEN EACH IS USEFUL

Fan-out on write suits small groups and the live push moment (online members should get the message instantly — that push is a write-time fan-out over sockets). Fan-out on read suits large groups, history, and offline catch-up (one ordered group log, members pull their gap). Production messaging blends both: push live to online sockets at send time, persist one copy in the group log, and let offline members pull their missing range on reconnect. Per-member delivered/read states are tracked separately either way.

PART 16 — PRESENCE

"Is This User Online?" — Asked a Billion Times a Day

Presence is the live answer to "online now?". It flips every time a phone enters a tunnel, and it's read every time anyone opens a chat. That makes it the textbook case for ephemeral (short-lived, disposable) data.

The states and their triggers

SIGNAL WHAT IT MEANS HOW IT'S COMPUTED
Online An active socket with fresh heartbeats exists for the user. Socket connected + heartbeat within timeout window.
Offline No live socket (app closed, network dead, phone off). Socket closed or heartbeats missed past the timeout.
Last seen "Was here at 14:02" — the only presence fact worth persisting briefly. Timestamp of the last heartbeat/disconnect, cached with TTL.
Multiple devices User is online if any device is connected. OR across per-device flags; each device heartbeats independently.

Why presence is temporary data

  • It changes constantly — every network flip rewrites it. Writing that churn to a durable database would burn writes on facts that expire in seconds.
  • Stale is acceptable — "online" that's 30 seconds old harms nobody; message routing uses the live socket attempt anyway, not the presence flag.
  • Loss is harmless — if the presence store dies, phones re-heartbeat and it rebuilds in seconds. Nothing billable or historical lived there.
  • So it lives in fast memory with TTL: each flag auto-expires; heartbeats refresh it. Privacy settings ("hide my last seen") are enforced at read time from profile settings.

Scaling presence reads

Presence is read far more than written (every chat open checks the peer). The pattern: connection servers publish heartbeat events; an in-memory presence store holds current flags; reads are local cache hits; updates propagate as lightweight events only to watchers (contacts with the chat open), not broadcast to the world. Nobody polls the database for "is A online?" — that question never touches disk.

PART 17 — TYPING INDICATOR

"Typing…" Is Not a Message. Don't Store It Like One.

The typing indicator is the perfect teacher: it looks like chat, but its data personality is the opposite of a message. Treating it like a message would be an expensive, pointless mistake.

TYPING SIGNAL PROPERTY WHAT IT MEANS FOR THE DESIGN
Temporary data True for ~5 seconds, then a lie. Never written to durable storage — memory only.
Frequent updates Every keystroke burst re-sends "typing". Throttle on the phone (e.g. at most every few seconds) and let the server just forward.
Expiration Auto-clears after seconds, with an explicit "stopped typing" event. No cleanup jobs; TTL does it.
Low importance Losing one typing event is invisible — the next keystroke re-sends it. No retries, no queues, no acks.
Failure tolerance If the forwarding path hiccups, the indicator just doesn't show. Nobody files a support ticket over a missing "typing…".
THE LESSON THIS TEACHES

Different data gets different handling. Messages: durable, ordered, acked, retried. Presence: in-memory with TTL, heartbeat-refreshed. Typing: fire-and-forget over the live socket, expires in seconds, zero persistence. An architect who routes all three through the same pipeline either loses messages or pays message-grade costs for keystroke gossip. Name the personality, then pick the pipe.

PART 18 — MEDIA MESSAGES

Photos Travel First Class on a Separate Plane

Media is ~80 TB/day — 40× the text core. It must never flow through the message database, the sequencer, or the socket pipes as bulk bytes. The chat carries a reference; the bytes live elsewhere.

  1. UPLOADUser uploads the fileThe app requests an upload slot and PUTs bytes directly to object storage (a simple giant file store: put file in, get file out by key) — resumable for big videos on flaky networks.
  2. PROCESSMedia processing (async)Virus/malware scan, generate thumbnail + preview, transcode video variants, strip metadata if policy requires. The chat message can reference the file before all variants finish.
  3. REFERENCEChat message carries only a pointerThe message stored in the conversation holds a media id + thumbnail + size — a few hundred bytes. Ordering, dedupe and ticks work exactly like text.
  4. SECURE ACCESSReceiver fetches via signed URLThe app gets a short-lived signed URL (a download link with an expiry and permission baked in) and downloads from the nearest CDN edge (a CDN — content delivery network — is a global network of cache servers that keeps popular files close to downloaders).
  5. EXPIRELifecycle + cost controlOriginals retained per policy; untouched originals can drop to cold storage; disappearing-message media is deleted on schedule; dedupe identical files by content hash (one viral video stored once).
CONCERN HOW THE ARCHITECTURE ANSWERS IT
Why not the message DB? 200 KB–50 MB blobs would explode row sizes, wreck cache efficiency, slow backups, and make every history page a multi-GB scan. Databases store pointers; object stores store bytes.
Access control Signed expiring URLs + membership check at issue time; a leaked link dies in minutes; blocked/removed members get no new URLs.
Cost CDN absorbs repeat downloads (group of 500 downloads once per edge, not 500 origin reads); compression/transcoding shrinks bytes; lifecycle tiers age cold files down; hash-dedupe kills viral duplicates.
Reliability Resumable uploads, checksums, replicated object storage; a failed thumbnail never blocks the message — degrade to "file" view.
PART 19 — PUSH NOTIFICATIONS

The Tap on the Shoulder for Sleeping Phones

When the receiver is offline or the app is backgrounded, the socket is gone — so the phone maker's push service (Apple/Google) delivers a small wake-up. Push is a notification about a message, never the message itself.

  1. STOREMessage storedThe message is durable and sequenced (nothing about push can change that).
  2. EVENTNotification event queuedA "B needs a nudge" event goes to the notification queue with conversation, sender and preview rules.
  3. PROVIDERPush provider deliversThe notification service sends to Apple/Google with B's device token. Providers throttle, delay, or drop — that's normal and expected.
  4. WAKEUser taps / app wakesThe app reconnects its socket and pulls the real messages in order. Even if the push never arrived, reconnect sync delivers everything — push accelerates, storage guarantees.
RULE WHY
Never block storage on push Push providers are slow, rate-limited third parties. The sender's tick must not wait for Apple. Queue the nudge; confirm the store.
Notification failure → retry, then give up gracefully Retry with backoff (token refresh, transient errors); invalid tokens are pruned. Ultimate fallback is always reconnect sync — no message depends on a push.
Dedupe notifications Collapse "5 new messages" into one push; id-keyed sends prevent buzz-storms from retries.
Respect user preference + privacy Muted chats, quiet hours, and "hide preview" are enforced before sending; with end-to-end encryption the push carries no readable content — just "new message".
PART 20 — SCALING

Scale Each Lane by Its Own Curve

Horizontal scaling = adding more identical servers behind a load balancer. Every lane below scales horizontally — but on different metrics, because idle sockets, message writes and video bytes are different resources.

COMPONENT HOW IT SCALES TRIGGER TO ADD MORE
API layer Stateless instances behind load balancers; autoscale on CPU/queue. p95 latency, CPU.
Real-time connections Add connection servers; each holds tens of thousands of sockets. Size by memory; router table stays shared and fast. Sockets per server, memory, heartbeat lag.
Message processing Stateless validators + per-conversation sequencer partitions; add partitions as conversations grow; workers behind queues absorb bursts. Sequencer queue depth, store-ack latency.
Message storage Add NoSQL nodes; data rebalances by conversation partitions; hot conversations get dedicated throughput. Write latency, partition heat, disk.
Presence In-memory cluster, shard by user id; add RAM nodes; TTL bounds every entry. Memory, event publish lag.
Notification Queue consumers scale per provider; respect vendor rate limits with pacing. Queue backlog age.
Media Object storage scales itself; add transcode workers; CDN edges absorb downloads. Upload queue, transcode lag, egress cost.
Search Per-user index shards; heavy indexing runs off-peak; much search stays on-device. Index lag, query latency.

Why connections and processing scale differently

  • Connections are about holding state while idle: 20M sockets mostly silent, cost = memory + heartbeat CPU. They scale by adding socket-holders and partitioning the router table. A quiet midnight still holds 20M sockets.
  • Message processing is about burst throughput: near-zero at 4 a.m., 200k sends/sec at 8 p.m. It scales by adding workers and sequencer partitions that can shrink again after the peak.
  • Sharing one fleet for both means sizing for the worst of both worlds. Separate tiers let sockets stay put while workers breathe with the day.
PART 21 — GLOBAL ARCHITECTURE

From One Region to Every Timezone

Global users punish centralization: a Berlin-to-Tokyo round trip on every send kills the "instant" promise. The path is regional stacks with local hot paths and a thin global brain.

Stage 1 — One region

Everything in one place: connection fleet, message service, stores. Simple, strongly consistent, cheap — but distant users feel the latency and one regional disaster is a global outage. Fine for launch; include a region key in routing and storage from day one.

Stage 2 — Multiple regions

Deploy full hot stacks per region (EU, US, Asia…): users connect to the nearest region (by latency-based routing); their live traffic — sockets, sends, presence — stays local. A global layer owns identity/directory, configuration, abuse signals and cross-region analytics.

CONCERN HOW REGIONAL ARCHITECTURE ANSWERS IT
Data locality & latency Sends, socket pushes and presence never cross oceans; sub-second delivery worldwide.
Regional routing DNS/anycast + latency probes send each phone to its best region; travelers re-home automatically on reconnect.
Cross-region chats Each conversation has an owner region (usually the creator's); the other region forwards sends there for sequencing, then delivers locally. One extra hop, only for cross-region chats.
Replication Identity and directory replicate globally; messages replicate to the owner's region plus the recipient's region for fast history reads; media replicates via CDN origin strategy.
Availability & failure A region down = its users fail over to the paired region (reconnect + replay); other regions unaffected; queued cross-region traffic drains on recovery.
WHY GLOBAL ADDS COMPLEXITY

Every region boundary creates questions a single region never asks: who sequences a chat whose members span continents? Where does history live when both travel? What if two regions both accept writes during a network split (split-brain)? The answers — owner regions, versioned replay, idempotent everything, declared RTO/RPO — are all solvable, but each is real engineering. Go global for latency and survival, with eyes open about the cost.

PART 22 — CONSISTENCY

Strong Where It Hurts, Eventually Everywhere Else

Strong consistency = everyone immediately sees the latest truth. Eventual consistency = copies converge within seconds/minutes. The business impact of being briefly wrong decides which you buy — strong costs latency and availability.

NEEDS STRONG CORRECTNESS WHY — COST OF BEING WRONG
Message identity (dedupe) A retried send processed twice = duplicate messages and broken sequence. The client-id check must be authoritative.
Message ordering per conversation Two sequencers minting #4822 = a forked conversation. One logical writer per chat.
Conversation membership Sending to someone just removed (or missing someone just added) is a privacy and correctness failure.
Group permissions / admin actions "Admin removed the spammer" must take effect now — a racing send from the removed user must be rejected.
Account info, blocks, devices A block must stop messages immediately; a revoked device must lose access now.
SMALL DELAYS ACCEPTABLE HOW MUCH DELAY IS HARMLESS
Online status / last seen Seconds to a minute — nobody's safety depends on a fresh green dot.
Typing indicator Seconds — it expires on its own anyway.
Some notifications Seconds late is fine; reconnect sync is the real guarantee.
Read receipts in huge groups Aggregates ("read by 47") can lag seconds behind reality.
Analytics / trending / reports Minutes to hours; strategic, not operational.
THE DECISION RULE

"What breaks if this is 30 seconds stale?" Duplicate messages, shuffled chats, messages to removed members, unblocked harassers → strong. Green dots, typing bubbles, dashboards → eventual. One system, two guarantees, chosen per data element by business damage.

PART 23 — SECURITY

Private Conversations at Planetary Scale

Messaging holds humanity's most sensitive content. The architecture protects identity, the pipe, the stored bytes, and the humans — with abuse controls that work even when content itself is unreadable to the server.

AUTHENTICATIONPhone-number + one-time-code signup; short-lived access tokens with refresh; new-device linking verified from an existing device; instant revocation on report of theft.
AUTHORIZATIONAuthentication proves who you are; authorization decides what you may do: members can read their chats only; group admins manage rosters; services use scoped credentials; least privilege everywhere.
ENCRYPTION IN TRANSITTLS on every hop — sockets, APIs, push callbacks, service-to-service. No plaintext message bytes on any wire, ever.
ENCRYPTION AT RESTStored messages, media and backups encrypted on disk with managed keys, rotation, and per-region key boundaries for residency.
SECURE MEDIA ACCESSSigned expiring URLs, membership-checked at issue; encrypted objects; no public buckets; preview data minimized.
RATE LIMITINGPer-user/device/IP limits on sends, OTPs, group creates, contact syncs — messaging's immune system against spam floods and credential-stuffing.
ABUSE PREVENTIONBehavioral signals (send velocity, new-account bursts, report counts), hash-matching of known-bad media, forwarding limits on viral content — all without reading private chats.
BLOCKINGBlock lists enforced at send time in the message service (blocked sender's message is rejected before storage) and at media-URL issue; instant effect, no grace window.
MESSAGE PRIVACYMinimal metadata retention, disappearing messages with enforced deletion (including media + backups windows), screenshot/report flows that reveal only reported content.
AUDIT LOGGINGAppend-only, tamper-evident logs of auth events, admin actions, permission changes and safety decisions — shipped to separate storage for forensics and compliance.
END-TO-END ENCRYPTION — HIGH LEVEL ONLY

End-to-end encryption (E2EE) means only the sender's and recipients' devices hold the keys — servers relay locked boxes they cannot open. Architecturally: key exchange and device verification live in Auth; the message service stores and routes opaque ciphertext blobs; ordering, dedupe and ticks work on metadata (ids, sequences), never on content; push previews carry no readable text; abuse-fighting shifts to metadata, behavior and user reports; backups need their own key story. The trade-off is explicit: maximum privacy in exchange for server-side features (search, scanning, preview) becoming harder or impossible.

PART 24 — FAILURE SCENARIOS

Sixteen Ways Chat Breaks (and the Calm Response to Each)

Seniority is scored on the failure walk. For each: what happens, user impact, immediate response, long-term prevention.

FAILURE WHAT HAPPENS / USER IMPACT IMMEDIATE RESPONSE LONG-TERM PREVENTION
1 · Connection server fails ~50k sockets drop at once; those users look offline; sends stall. Phones detect dead heartbeats and reconnect with jittered backoff to healthy servers; router table versions fence the dead entries; replay from last acked sequence. Stateless socket tier, versioned router table, autoscaled headroom, chaos-tested reconnect storms.
2 · Message store partition down Sends to affected conversations fail; history unreadable for those chats. Fail over to replicas; senders see "sending…" not false ticks; queued retries with backoff until the partition heals. Replicated partitions, tested failover, conversation-keyed isolation so one hot partition can't take all chats.
3 · Message broker fails Offline queues, push triggers and fan-out tasks stall; live socket delivery still works. Live path continues (store + direct push); broker cluster fails over; producers buffer/spill to disk briefly. Clustered durable broker, critical acks never broker-only, DLQ + replay tooling, capacity headroom.
4 · User disconnects mid-chat Messages in flight lack acks; peer's ticks freeze at one tick. Unacked messages stay queued; reconnect replays the gap; dedupe drops repeats; ticks catch up. Store-before-ack, idempotent receive, gap-repair protocol as the standard reconnect flow.
5 · Unstable network (flapping) Rapid connect/disconnect; duplicates and reordered arrivals threaten. Debounce presence (don't flap the green dot), batch replay, client-side buffering and reordering by sequence. Backoff reconnect, sequence-based rendering, presence hysteresis (grace period before "offline").
6 · Duplicate message arrives Same text twice would confuse and erode trust. Client-id dedupe on send path; received-id check on device; duplicate re-acks but never re-renders or re-sequences. Unique constraints, dedupe retention windows, duplicate-rate dashboards.
7 · Delivered but ack lost Server redelivers a message B already has; sender's ticks lag. Redelivery collapses by id on device; fresh ack sent; ticks advance. Harmless by design. At-least-once + idempotent receive as the documented contract; ack-loss metrics.
8 · Push provider fails Offline users aren't woken; they discover messages late. Queue and retry pushes with backoff; SMS/email fallback for critical alerts only; messages wait safely regardless. Multi-provider strategy where possible, token hygiene, reconnect sync as the real guarantee (push is acceleration).
9 · Region goes down Regional users can't connect; cross-region chats partially stall. Latency routing shifts users to paired region; reconnect + replay; owner-region duties fence over with epoch tokens. Paired regions, owner-region design, split-brain fencing, quarterly failover drills, declared RTO/RPO.
10 · One group explodes (viral event) Thousands of msgs/min; fan-out queues grow; member phones buzz nonstop. Async fan-out absorbs it; throttle per-sender floods; collapse notifications; partition keeps appending (cheap). Blended fan-out, hot-partition throughput planning, slow-mode/flood controls, notification collapsing.
11 · Ordering breaks (sequencer fault) Two messages share a sequence or a gap appears; clients show "waiting for message". Clients hold rendering at the gap and request the missing sequence; single-writer fencing prevents double-minting; repair job reconciles. One logical sequencer per conversation, fencing/epochs on failover, gap-repair protocol, order-violation alerts.
12 · Media storage fails Uploads/downloads fail; chats show placeholders; text unaffected. Retry with backoff; serve thumbnails from CDN cache; degrade to file-icon; message text/reference still delivers. Replicated object storage, multi-CDN, resumable uploads, text/media failure isolation.
13 · Cache fails Sessions, rosters, presence read-through to backing stores; latency spikes. Fall back to databases with throttling (no stampede); single-flight refresh on hot keys; presence degrades to last-known. Cache clusters with replication, TTL discipline, cache-dead runbooks, load tests with cold caches.
14 · Processing slows (overload) Store-ack latency climbs; senders stare at clocks; retries add fuel. Shed load (accept + queue with "sending" state rather than failing), autoscale workers, circuit-break slow dependencies. Queue-buffered ingestion, autoscaling on ack latency, backpressure, capacity headroom for 3–4× peaks.
15 · Global traffic spike (New Year) Worldwide 5–10× minute-bursts; every lane saturates at once. Pre-warmed capacity, degrade typing/presence freshness first, collapse notifications, pace non-critical work; honest "sending…" states. Regional time-spreading (midnight moves across zones), load-tested peaks, graceful-degradation switches, event playbooks.
16 · Poison message / abuse flood Crash-looping payload or spam flood degrades workers and trust. Quarantine to dead-letter after N failures; rate-limit/abuse-block the source; alert; keep the pipeline moving. Schema validation, size caps, per-sender limits, behavioral abuse scoring, DLQ review tooling.
THE FOUR-COLUMN HABIT

Detect (heartbeats, TTLs, queue-age metrics) → contain (partitions, regions, queues) → degrade gracefully (queued beats failed, stale beats wrong) → recover (failover, replay, reconcile) → prevent (redundancy, idempotency, drills). Walk every failure in that order.

PART 25 — ARCHITECTURE TRADE-OFFS

Ten Decisions, Each With a Price Tag

For every decision: what you pick, what you reject, what you gain, what you sacrifice — and the future condition that would flip you. Never present an option as simply "correct".

D1 WebSocket vs polling

OPTION A — POLLINGSimple, stateless servers; seconds of delay and crushing empty-request volume at 20M users.
OPTION B — PERSISTENT SOCKETSInstant both ways, cheap per message; needs socket fleets, routing, reconnect engineering.
GAIN (B)Sub-second delivery and ticks; battery-friendly; natural acks and presence.
SACRIFICE (B)Memory-heavy tier + router table + heartbeat/reconnect logic to build and operate.

OPTION A — SQL EVERYWHERETransactions, joins, one operational model.
OPTION B — NOSQL FOR THE FIREHOSEPartitioned appends at 200k/sec; weak joins.
GAIN (B)Linear write scaling shaped exactly like the access pattern (conversation → sequence range).
SACRIFICE (B)A second storage technology; relationships handled in code.
RECOMMENDED & WHYHybrid: NoSQL for messages, SQL for the transactional core (users, groups, blocks). One engine can't be both a 200k-write firehose and a constraint-guarded ledger.

D3 Fan-out on write vs fan-out on read

OPTION A — WRITE-TIME FAN-OUTCopy to every inbox at send; instant reads, brutal writes.
OPTION B — READ-TIME FAN-OUTOne group log; members pull their gap; cheap writes, pricier reads.
GAINBlending gives instant live pushes AND cheap history.
SACRIFICETwo mechanisms to build: live push fan-out + group log with per-member cursors.

D4 Centralized vs regional architecture

OPTION A — ONE GLOBAL STACKSimplest model, cheapest to start.
OPTION B — REGIONAL STACKSLocal latency, isolation, residency; duplicated ops.
GAIN (B)Sub-second delivery worldwide; one region's outage stays local; compliance.
SACRIFICE (B)Owner-region routing, replication, split-brain fencing, region-by-region releases.
RECOMMENDED & WHYCentral at launch with a region key in routing and storage from day one; regionalize the hot path as you go global. The key costs nothing early and saves a rewrite later.

D5 Strong vs eventual consistency

OPTION A — STRONG EVERYWHEREAlways current; slower, costlier, less available.
OPTION B — EVENTUAL AT THE EDGESFast and available; briefly stale reads.
GAINSpend the expensive guarantee only where staleness causes real damage.
SACRIFICETwo models in one system; reconciliation and careful per-field choices.
RECOMMENDED & WHYStrong for identity/dedupe, per-chat order, membership, permissions, blocks; eventual for presence, typing, aggregates, analytics. Decide per field by "cost of 30 seconds wrong".

D6 Direct processing vs message broker

OPTION A — DIRECT CALLS ONLYSimple to trace; a slow consumer blocks the producer.
OPTION B — BROKER IN THE MIDDLEDecoupled, buffered, retriable; eventual and operationally heavier.
GAIN (B)Offline queues, push triggers, fan-out tasks and retries survive crashes and spikes.
SACRIFICE (B)Broker cluster to run; ordering/dedupe discipline; harder tracing.
RECOMMENDED & WHYDirect synchronous path for store + live socket push (the user is waiting); broker for offline queues, retries, push, fan-out and all background consumers. The live blink stays direct; everything patient goes through queues.

D7 Shared vs partitioned data

OPTION A — ONE SHARED STORESimple queries, cross-chat transactions.
OPTION B — PARTITION BY CONVERSATIONHorizontal scale, local ordering.
GAIN (B)200k writes/sec spread over hundreds of partitions; hot chats isolated; order is local.
SACRIFICE (B)No cheap cross-partition transactions; hot-partition planning for mega-groups.
RECOMMENDED & WHYPartition by conversation id — the access pattern ("chat X after seq N") is inherently partition-local, which makes this the easy kind of sharding. Cross-chat transactions are vanishingly rare in messaging.

D8 Synchronous vs asynchronous processing

OPTION A — SYNC EVERYTHINGImmediate answers; every dependency's outage is your outage.
OPTION B — ASYNC WHERE POSSIBLEResilient and elastic; delayed effects.
GAINPush vendors, transcoders and analytics can be slow or down without touching the send tick.
SACRIFICEEventual side effects; queue/backpressure engineering.
RECOMMENDED & WHYSync: validate → dedupe → store → ack → live push. Async: offline queueing, push, media processing, read-receipt aggregation, search indexing, safety. The rule from Part 12: the user waits only for the tick.

D9 Media in database vs object storage

OPTION A — BLOBS IN THE DBOne system, transactional with the message.
OPTION B — OBJECT STORE + CDNBytes outside, reference inside.
GAIN (B)80 TB/day flows through cheap storage + edge caches; the message DB stays small and fast; independent lifecycle/expiry.
SACRIFICE (B)Two systems to keep consistent (orphan-file cleanup); signed-URL access plumbing.
RECOMMENDED & WHYObject storage + CDN, decisively. Blobs in a transactional or NoSQL message store would wreck row sizes, caches, backups and history paging — for zero benefit.

D10 Centralized vs distributed presence

OPTION A — ONE PRESENCE SERVICESingle source of truth, simple reads.
OPTION B — DISTRIBUTED IN-MEMORY FLAGSSharded by user, TTL-expired.
GAIN (B)Heartbeat churn (millions/min) spread over RAM shards; reads are local; failures self-heal via re-heartbeat.
SACRIFICE (B)Briefly inconsistent views across shards; watcher fan-out to engineer.
RECOMMENDED & WHYDistributed ephemeral flags. Presence is high-churn, low-value, stale-tolerant data — the exact opposite of what deserves a centralized strongly-consistent service.
PART 26 — COST THINKING

Billions of Messages Have an Electricity Bill

An architect spends company money on purpose. The cost centers are predictable — and so are the levers that shrink them without touching the send tick.

COST AREA WHAT DRIVES IT
Persistent connections 20M idle sockets = memory on hundreds of servers, 24/7, even at quiet midnight.
Servers (compute) API, message workers, sequencers, transcoders, indexers + autoscaling headroom.
Message processing Validation, dedupe, sequencing, fan-out tasks at 200k sends/sec peak.
Databases HA instances, replicas, NoSQL clusters, in-memory presence/router stores.
Storage ~2 TB/day text (cheap) + ~80 TB/day media (the real bill) + backups.
Network traffic ~25 TB/day delivery fan-out + media downloads + cross-region replication.
Notifications Push volume (mostly free but metered at extremes), SMS fallback (expensive).
Media + CDN Object storage, transcode compute, CDN egress per GB.
Monitoring High-cardinality metrics, log ingestion, tracing at billions of events/day.

Ten practical cost levers

  1. Shrink per-socket memoryTune buffers and session state; 20M sockets × 1 KB saved = 20 GB of fleet RAM freed. Connection servers are bought by memory.
  2. Batch, compress and coalesce on the wireBatch queued messages per reconnect, compress payloads, coalesce presence/typing chatter. Less bandwidth, fewer wake-ups, lower egress.
  3. Let the CDN pay for mediaOne origin fetch per edge for viral content; aggressive edge TTLs; client-side caching. Origin egress is the expensive kind.
  4. Dedupe media by content hashThe same viral video forwarded a million times is stored once and referenced a million times. Transcode once, serve forever.
  5. Tier storage by ageHot partitions for recent chats; compressed cold archive for old history; drop to cheap object storage; enforce retention/expiry (disappearing messages delete for free).
  6. Collapse and pace notifications"5 new messages" in one push, not five; push over SMS always; prune dead tokens so vendors aren't paid to fail.
  7. Autoscale workers, not socketsProcessing breathes with the day (scale in at night); socket fleets follow regional daytime; transcode/index off-peak.
  8. Sample logs, aggregate metricsFull-resolution for days, aggregates after; trace a fraction of requests; keep full fidelity on the store-ack and payments paths only.
  9. Regionalize to cut cross-ocean pipesLocal traffic stays local; replicate only directory deltas and needed history — inter-region bandwidth is premium-priced.
  10. Degrade gracefully instead of over-provisioningAt rare 10× spikes: stale presence, collapsed notifications, paused indexing — instead of a permanent 10× fleet. Buy peaks as burst, not baseline.
NEVER CUT HERE

Don't economize on store-before-ack durability, dedupe/ordering guarantees, backup testing, abuse controls, or monitoring of delivery latency and queue age. Cost work makes the same promises cheaper — it never quietly drops a promise.

Model Answer Guide

  1. 20M simultaneous connects: load balancers spread SYNs across the socket fleet; phones reconnect with jittered backoff (never lockstep); auth is the bottleneck so token validation is cached and horizontally scaled; router table absorbs versioned registrations; replay is paced per user ("last sequence" pulls), not a flood. The system degrades to slower logins, never to lost data — storage, not sockets, holds truth.
  2. Double-minted #4822: damage: two messages claim one slot; clients gap-hold and show "waiting"; history forks. Fix: fencing — only the epoch-holding sequencer's writes are accepted; the loser's write is rejected by the unique (conversation, sequence) constraint and reassigned the next free number; clients repair by re-pulling the range. Prevention: single logical writer + epoch tokens on failover, order-violation alerts.
  3. Broker down 10 min: live socket delivery continues (store + direct push never needed the broker); offline queueing, push triggers, fan-out tasks and background consumers pause with producers buffering/spilling; on recovery, consumers drain in order with dedupe. Design rule proven: the tick path is broker-independent; the patient path waits.
  4. Duplicate on two devices: layers: (1) redelivery happened (lost ack or replay — normal); (2) device dedupe failed (received-id store missed — e.g. app reinstall wiped it); (3) per-device cursors diverged. Fix: server dedupe is per message, but receive dedupe must be per device with cursors synced across devices via status-sync events; on reinstall, full state re-sync before live rendering. Re-ack still sent so retries stop.
  5. Message DB unavailable: sends can't be stored → can't be acked: phones show "sending", outbox holds with backoff; live sockets stay up (presence/typing continue); history reads fail over to replicas or degrade gracefully; no false ticks are ever issued. Recovery: replica promotion, then queued outboxes drain with server dedupe collapsing the backlog. Partitioning means usually only some conversations are affected.
  6. 10,000-member live final: one group-log append per message (cheap); live pushes to online sockets via batched router lookups; offline members pull ranges later; pushes collapse to digests; per-sender flood limits + slow-mode; read states aggregate async. The partition appends thousands/min happily because delivery work is all downstream and parallel.
  7. 30 days offline, 50k queued: retention policy decides (e.g. hold N days/M messages, then summarize/expire per product rules); on return: paged catch-up (newest-first option + background backfill), collapsed single push ("47 new messages in…"), dedupe on replay, paced to avoid melting the phone; media downloads on demand (thumbnails first). Backlog age metrics warned ops long before.
  8. Mega-group vs everyone else: no — conversation-keyed partitioning isolates its writes to its partitions; its fan-out consumes shared worker/queue capacity, so fairness matters: per-conversation fan-out quotas, queue prioritization (small chats not starved), and push collapsing. Blast radius is bounded by design; monitor partition heat and fan-out lag per conversation.
  9. Post-outage recovery: phones re-home to paired region, authenticate, replay from last acked sequences; owner-region duties fence over (epoch tokens reject the dead region's late writes); cross-region queues drain; when the region returns it rejoins as replica, replays missed writes, and ownership fences back. RPO = seconds of async replication; nothing acked-and-stored is lost — it was durable before the outage.
  10. Why sockets, not polling: 20M users polling every 5s ≈ 4M requests/sec of ~99% emptiness, seconds-late delivery, dead batteries. One socket each: instant both ways, acks/presence/typing ride free, cost is idle memory. Polling survives only as a degraded fallback (hostile networks, history backfill).
  11. Two devices send at once: both sends reach the conversation's single sequencer, which serializes them — first writer gets #4823, second #4824. Per-device send cursors prevent each device from assuming contiguity; both devices receive both messages in sequence order like any other member. No conflicts because ordering is server-assigned, never client-assumed.
  12. Message racing a removal: the send is validated against membership at processing time: if removal committed first, the send is rejected (sender sees "you're no longer a member"); if the send sequenced first, it stays (it was legitimate then) and the removal only stops future sends. Strong consistency on membership makes this deterministic, not lucky. Either outcome is defensible because the order is total.
  13. Half the pushes dropped: users experience… nothing broken: messages are stored and queued; phones that open the app sync instantly; only the wake-up nudge is missing for some.   14. Presence store dies: everyone appears "last seen recently" (stale cache) rather than wrongly online/offline; routing is unaffected (router table is separate — or rebuilt alongside); heartbeats rebuild flags within a minute of recovery. Messaging continues fully — presence was never on the delivery path. Lesson: ephemeral stores fail soft by design.
  15. Spam flood 100k/s: gateway rate limits per account/device/IP shed it first; per-sender send quotas + new-account throttles; behavioral scoring quarantines; messages still validated cheaply and rejected pre-storage (no queue pollution); abuse blocks stop the accounts; DLQ + alerts for review. Legitimate traffic is protected by shedding spam at the edge, not in the core.
  16. Delete-for-everyone after read: honestly: the bytes were already rendered — deletion removes from devices that honor it (tombstone event propagates, media URLs revoked, server copy + backups purged per retention windows) but can't unsee. Policy: time-boxed window (e.g. 1 hour), tombstone ("message deleted") preserves order/gap integrity, screenshots/export caveats documented. Architecture delivers the honest version, not magic.
  17. Orphaned upload: no: uploads without a referencing message within TTL are garbage collected by a sweeper comparing object keys against message references; client retries reuse the same upload id (resumable); checksums verify. Orphan cleanup is a scheduled job, sized from upload-vs-reference metrics — media/DB consistency is eventual by design.
  18. Cut cost 40%: media/CDN first (fewer transcode variants, tighter edge TTLs, aggressive lifecycle tiers, hash-dedupe), then history tiering sooner, push collapsing harder, worker autoscale to queue age, sampled observability, regionalize to cut cross-ocean egress, burst capacity over baseline fleet.   19. Keep: one sequencer per chat, dedupe, store-before-ack, offline queues, blocks/abuse, backups. Complexity dies at the edges; guarantees live in the core.
  20. E2EE mandatory: survives: sockets, router, queues, sequencing, dedupe, ticks, fan-out, push plumbing, partitioning — all work on metadata. Breaks/changes: server-side content search and scanning (move to device + hashes), push previews (generic "new message"), media processing (client-side thumbnails or sealed processing), abuse controls (metadata/behavior/reports only), backups (own key story), web-client crypto.
