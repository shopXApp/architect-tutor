PART 1 — ACT LIKE AN ARCHITECT

Don't Draw Boxes Yet — Ask Questions First

The #1 mistake in system design interviews is drawing the first box within sixty seconds. A streaming platform looks completely different at 10,000 users versus 10 million. Architects extract numbers before they draw shapes.

Functional requirements — what the system must do

Account & accessUser registration, login, subscription tiers (free/paid), multiple profiles per account, device registration. These are the front door — small data, high consistency requirements.
DiscoveryBrowse the catalog, search, view detail pages, continue-watching rail, personalized home page. This is where most API requests land.
PlaybackWatch video, pause/resume, adaptive quality switching, captions, offline downloads. This is the "product" — everything else is a lobby for it.
Engagement loopWatch history, ratings, recommendations, "because you watched X". These feed the next session's discovery.

Non-functional requirements — the qualities that shape everything

QUALITY WHY IT MATTERS TO ARCHITECTURE
Number of users Sets database size and signup/auth throughput, not the hard part.
Concurrent viewers The hard number — sets CDN capacity and bandwidth, not server count.
Video startup time The single most important user metric. Forces edge caching + adaptive bitrate.
Response time (API) Metadata must feel instant — forces caching of catalog and home data.
Availability 99.9%+ means redundant API, failover DB, multi-region CDN.
Scalability Peak is bursts (new series launch) — forces stateless APIs and horizontal scale.
Security Subscriptions gate content: signed URLs, anti-sharing, content protection.
Storage Petabytes. Defines object storage over databases by itself.
Cost Video is bandwidth-dominant — the whole design bends to control CDN/egress cost.
THE THREE MUST-ASK QUESTIONS

1. How many concurrent viewers at peak? — shapes CDN/bandwidth.
2. Where are users located? — single region or global, shapes CDN distribution.
3. Is the catalog user-generated or curated/professional? — processing a 1,000-title curated library is very different from ingesting 10,000 user uploads an hour.

PART 2 — THE NUMBERS

Define the Scale (Back of the Envelope)

Every architecture decision downstream is a consequence of these estimates. State your assumptions aloud, then let the numbers steer.

Working assumptions

ASSUMPTIONS (state these to the interviewer)

Registered users: 50 million // total signups
Daily active users (DAU): 10 million // 20% of registered, reasonable for streaming
Concurrent viewers at peak: 2 million // peak evening, e.g. a popular new series
Average viewing session: 90 minutes // per active viewer per day
Average bitrate: 5 Mbps // HD, adaptive — could be 1–15 Mbps
Catalog size: ~20,000 titles, each averaging 2 hours // assume one 2-hour video ~3–5 GB at HD

Simple calculations

TRAFFIC & BANDWIDTH

Peak bandwidth: 2,000,000 viewers × 5 Mbps = 10 Tbps (terabits per second)
Daily video delivered: 10M DAU × 90 min × 5 Mbps = ~3.4 PB/day // this is why CDN is non-negotiable
API QPS (peak-heavy browsing): ~10M DAU × ~20 API calls/day ÷ 86,400 ≈ 2,300 avg, but peak browsing spikes it: ~5,000–10,000 QPS at launch moments // metadata only — tiny compared to video bytes

STORAGE

One 2-hour movie, 4 quality ladders: ~10 GB total across qualities // low 360p ~1GB, medium 720p ~2GB, high 1080p ~4GB, 4K ~8GB
20,000 titles × 10 GB = ~200 TB base // a lot, but cloud object storage handles it; growth is linear
Plus replicas + transcoding intermediates: budget 2–3× → ~400–600 TB actively managed
WHAT THESE NUMBERS WHISPER TO AN ARCHITECT

Bandwidth is 3.4 PB/day flowing while storage is only hundreds of TB. That single fact reshapes the whole design: delivery dominates storage in both difficulty and cost. Every decision — CDN over self-hosting, segments over whole files, edge caching over origin reads — stems from "we move more than we store."

PART 3 — THE SHAPE

High-Level Architecture

One clean diagram, then every major component explained in plain language. Notice the sharp divide: metadata on the left, video on the right.

FIG. 22.1 — HIGH-LEVEL ARCHITECTURE: CORE VS EDGE, CLEANLY SEPARATED

Every major component, simply

  • Clients (web/mobile/TV): Three different front ends; all speak to one API. Playback code lives here, choosing quality per device/network.
  • API Gateway: One entry point: authentication, rate limiting, routing. Stops abuse before it reaches anything expensive.
  • Core services: Auth, catalog, search, profiles, watch history. Small, frequent, consistency-sensitive.
  • Database + cache: Relational store for users/titles/history; cache in front for hot reads. No video bytes here, ever.
  • Video pipeline: Ingests a raw upload, transcodes it into multiple qualities and segments, writes the result to object storage.
  • Object storage: The "origin" of truth for every video file. Cheap, durable, scales to petabytes.
  • CDN: The delivery network — caches video near viewers so the origin rarely gets hit, and a user in Tokyo isn't pulling bytes from Virginia.
  • Search index: A purpose-built search store so "find a movie" never scans the main database.
  • Recommendation: Background service that precomputes "watch next" so the home page loads instantly.
  • Monitoring/logs: The observability backbone — you can't run 2M concurrent viewers you can't see.
PART 4 — THE PATENTED PIPELINE

Video Upload and Processing

What happens when a new movie arrives? This flow is the single most distinctive part of a streaming platform.

FIG. 22.2 — UPLOAD → PROCESS → MULTI-QUALITY → CDN READY

The flow, step by step

  1. Admin uploads a raw master (e.g., a 50 GB uncompressed studio file).
  2. Original is stored as-is — you keep the master forever so you can re-encode later.
  3. Processing (transcoding) converts it into multiple qualities and cuts each into small segments (a few seconds each).
  4. Processed files land in object storage, ready for the CDN to pull.
  5. Users pull only the segments they need, at the quality their network/device can handle.

Why multiple qualities?

  • Low (360p): for weak mobile signals, low data plans, tiny screens.
  • Medium (720p): the sweet spot for most phones and laptops.
  • High (1080p): TVs and fast home broadband.
  • Very high (4K): premium tiers, big 4K screens — biggest bandwidth, highest storage.

Adaptive streaming: the player continuously measures bandwidth and buffer, and switches segment quality on the fly — start fast in low quality, silently step up to HD as bandwidth allows, drop down if the network wobbles. Why it matters: a viewer on a shaky connection still gets smooth playback, never a frozen spinner. This per-segment switching is why you cut the video into segments in the first place.

THE ARCHITECTURAL INSIGHT

Transcoding is CPU-heavy, background work — a 2-hour movie doesn't encode in a millisecond. It belongs in an asynchronous worker pool, never in the upload request path. Upload returns "processing"; the pipeline emails/completes when the title is viewable. This separates a slow, expensive, retryable job from a fast, tiny, one-shot API call.

PART 5 — THE PLAY BUTTON

Video Streaming: What Happens on "Play"

The user's click is the whole business. Trace it precisely — and notice where the big bytes are not.

FIG. 22.3 — PLAY: API HANDS OFF A LOCATION, CDN DELIVERS THE BYTES
  1. User clicks Play. The app asks the API: "am I allowed, and where is this video?"
  2. Authorization: the API checks the account is entitled (subscribed, or owns/rents this title).
  3. Video location: the API returns metadata + a signed URL pointing at the CDN (or a manifest listing segments).
  4. CDN delivers: the player fetches segments directly from the CDN, at the right quality, as they're needed.
  5. Playback continues segment by segment, switching quality adaptively, buffering ahead.
WHY THE API NEVER SENDS VIDEO

An API server is built for thousands of small metadata requests. If it streamed 5 Mbps of video itself, a handful of concurrent viewers would saturate its network card and starve the login and catalog subsystems entirely. Separation is survival: the API says you may watch, the edge network does the delivering. Two different machines, two different jobs, two different scaling rules.

PART 6 — THE EDGE NETWORK

Why the CDN Is Non-Negotiable

A CDN (Content Delivery Network) is a network of thousands of servers spread around the world, each holding cached copies of content, so users download from a machine near them instead of from your single origin far away.

1. What it doesCaches copies of popular video segments in hundreds of edge locations. A viewer in Sydney gets segments from Sydney, not from Virginia.
2. Why it speeds deliveryDistance = latency. Serving from 50 km away instead of 15,000 km turns startup time from seconds into tens of milliseconds. TCP itself is faster on short, uncongested paths.
3. Why geography matters2M concurrent viewers spread globally means every region needs its own edge cache. One origin cannot serve the planet — the math of light-speed latency plus single-machine bandwidth breaks down instantly.
4. How it protects the coreThe origin only serves a segment once (a "cache miss"), then the edge serves the next 100,000 copies. Your object storage and datacenter see a trickle; the internet's edge absorbs the flood.
5. When CDN use growsMore viewers, more regions, more titles → more edge traffic. Cache hit ratio stays high for popular content; long-tail titles compress more at origin, so you pay more egress for old/obscure content that doesn't fit edge caches.
6. When CDN failsUsers served by that edge can't get video (or are rerouted to a farther, slower edge). A good design routes around failures: multiple CDNs or origin failover, health-checked at the app layer.
THE COST LAW OF STREAMING

CDN is usually the single largest line item in a streaming company's bill — more than servers, more than storage. Optimizations that increase cache hit rate (popular-content prewarming, regional catalogs, quality-aware caching) are literally revenue engineering, because every miss that round-trips to origin costs real egress money at YouTube/Netflix scale.

PART 7 — WHERE FILES LIVE

Storage Design: Never Put Video in a Database

The most frequent beginner mistake in this design is storing video in a relational database. Here is the decision, cleanly.

Database vs object storage for video

FACTOR DATABASE (BLOB in SQL) OBJECT STORAGE (S3/Blob)
Cost per GB Very expensive — high-perf SSD/engineered disks, backup overhead. ~50–90% cheaper, designed for massive data at rest.
Scale Petabytes in a DB = pain: sharding, migrations, connection issues. Virtually unlimited, scales horizontally with no thought.
Performance Retrieving a 5 GB video through SQL is slow and hammers the DB connection pool. Built for streaming large objects efficiently; pairs naturally with CDN.
Backup Backing up video blobs bloats backups 1000×, slows restore, inflates cost. Versioning + replication + cross-region replication built-in.
Management Video in DB is an anti-pattern to maintain and scale. Lifecycle policies auto-tier old/unused data to cheaper classes.

What goes where

  • Database (relational): Movie information (title, genre, cast, release year), user accounts, subscriptions, watch history, ratings, device registrations. Small, structured, related, transactional.
  • Object storage: The raw masters, every processed quality, every segment, thumbnails, captions. Large, immutable-ish, referenced by the DB via a pointer (object key/URL).
  • The link between them: the database stores metadata + a key to the object, never the object itself. The movie row knows where the 1080p manifest lives; storage holds the bytes.
THE ONE-LINE RULE

Structured, small, transactional → database. Large, binary, write-once-read-many → object storage. Say that in the interview and you have answered "why not store video in SQL Server?" permanently.

PART 8 — THE TRUTH LAYER

Database Design at Architecture Level

Keep tables minimal — this is about knowing what data is relational and which parts need consistency vs can lag.

DATA AREA WHAT IT HOLDS CONSISTENCY NEED NOTES
User Account, email, subscription tier, billing reference. Strong — payment-relevant. Profiles (viewer sub-accounts) hang off the user.
Subscription Plan, renew date, active/cancelled. Strong — gates all playback. Must be checked at play time — fast cached lookup.
Movie / Series / Episode Title, synopsis, cast, genre, release, object key pointers. Read-mostly; strong enough. Series has many episodes/episodes have seasons — natural hierarchy.
Watch history What, when, position, device per viewer. Eventual OK — a 1s lag is invisible. Massive write volume; append-mostly — a great fit for async capture.
Rating Thumbs up/down or stars per title per user. Eventual OK. Aggregates (avg rating) can be recomputed lazily.
Device Registered devices, last login, capabilities. Strong enough for account limits. Ties to "how many screens allowed".
STRONG VS EVENTUAL — THE LINE THAT MATTERS

Strong consistency for anything that gates money or entitlement: subscription status, account validity, a purchase. Eventual consistency for everything the user won't notice lagging by a second: watch history position, aggregate ratings, "recently watched". Putting high-cardinality, append-only data (watch history) on an async write path is what keeps the primary DB from melting under 2M concurrent viewers' heartbeat updates.

PART 9 — FIND THE TITLE

Search: Don't Scan the Main Database

"Find all movies with 'dragon' in the title, ranked by popularity" is a full-text query with ranking and typo tolerance — a very different beast from a point lookup by primary key.

Why the main DB strugglesRelational databases aren't optimized for relevance-ranked, typo-tolerant, partial-text matching across 20K titles. As traffic grows, such queries scan and strain the same database serving account and playback lookups.
A separate search storeA dedicated search engine (Elasticsearch-style) maintains a specialized index — a pre-built, inverted structure optimized for fast text search and ranking. Queries hit it, never the primary database.
Indexing & updatesNew titles and metadata edits flow to the search index asynchronously via a feed/queue. Search may lag a new title by seconds — invisible to users, enormous for decoupling.
Search failureIf search is down, browsing and catalog still work — the home page caches popular titles; users can still watch from their list. Search is degradable, not the whole product.
ARCHITECTURAL THEME RESTATED

This is the same "don't make the critical path share a home with bursty, expensive work" idea as reporting (Day 16) and videos-vs-API (Part 5). Search is read-heavy and self-contained — segregate it. You'll reuse this exact justification in the interview: same principle, different subsystem.

PART 10 — HOT DATA

Caching: What, Where, and What Not To

Caching is the cheapest performance win in the whole design — but only for the right data. Here's the architecture-level map.

WHAT TO CACHE WHY
Movie details Changed rarely, read constantly. Prime cache material.
Popular movies / home page rail The single highest-read, lowest-write data — cache aggressively, serve the home screen from memory.
User preferences & profile Needed on every request; small; changes rarely (but invalidate on profile edit).
Search results (hot queries) "dragon", "popular", actor names repeat a lot — cache top queries.
Recommendation rows Precomputed per user; cache until they're rebuilt in the background.
WHAT NOT TO CACHE WHY
Subscription / entitlement status Must be authoritative at play time — stale "paid" is a piracy hole.
Video bytes That's the CDN's job, not the API cache's.
Watch position during playback It's the "current" value — cache helps here, but a recoverable, slightly-stale cache with authoritative write-through is the right pattern, not a naive TTL.
Anything money-touching Billing, purchase state — read from source of truth.

The three caching questions

  • Expiration (TTL): how long may data be stale? Titles: hours. Home rails: minutes. Prefs: minutes. The TTL is your statement of acceptable staleness, get it from the business.
  • Failure: when cache dies, traffic hits DB directly — slower but alive. Design DB to survive the burst, and alert on cache-hit drop.
  • Updates/invalidation: when a title changes or profile updates, invalidate (delete) the entry, don't just wait for TTL — stale products lose trust fast.
PART 11 — "BECAUSE YOU WATCHED…"

Recommendation System, Architect's Eye

You don't need ML expertise to design the shape. Recommendations are "watch next": take what you watched, produce a ranked list of what to watch next. The architecture question is when, not how.

FIG. 22.4 — RECOMMENDATIONS: COMPUTED OFFLINE, READ INSTANTLY
  • User activity flows into a history/behavior store continuously (async, no impact on playback).
  • Background processing periodically (hourly/daily) recomputes each user's ranked list from their history.
  • Result is stored and cached, so the home page just reads a ready-made list — instant load.
  • Why background: recommendation ranking is expensive and non-urgent. Computing it inside the request path would spike home-page latency from 50 ms to 2,000 ms. Compute when things are quiet; read when they're busy.
PART 12 — GROW WITHOUT BREAKING

Scaling Every Major Area

Two tools: horizontal scaling (add more machines) and vertical scaling (make one machine bigger). Different subsystems prefer different tools.

AREA SCALING STRATEGY WHY
API (auth, catalog) Horizontal — stateless, add instances behind a load balancer. Each request is independent; no shared in-process state.
Database (primary) Vertical first, then read replicas + sharding. Writes have a single-writer ceiling; reads can fan out to replicas.
Search Horizontal — add index nodes. Search is naturally partitioning-friendly (shard by title domain).
Object storage Auto-scales; no action needed. The cloud service handles it internally.
Video processing Horizontal — add workers to the queue. Transcoding jobs are independent; more workers = faster backlog drain.
CDN Auto — it IS the horizontal scale; add regions. Capacity grows with points-of-presence, not your machines.
Background/recommendation Horizontal — parallel jobs. Batch jobs partition by user; scale by adding compute.
THE PATTERN

Stateless and read-mostly → horizontal. API, search, processing, caching.
Stateful and write-centric → vertical, then careful horizontal (replicas/sharding). The database.
Already-distributed services → scale their region count. The CDN and object storage.

PART 13 — THE LAUNCH NIGHT

Handling Peak Traffic: A New Series Drops

Midnight, a hugely popular series releases, and millions hit Play within minutes. What bends first, and how does the architecture survive?

  1. First to overload: the CDN's origin + metadata API.Everyone's first action is browsing/fetching the new title's metadata and its segments. The metadata API spikes; the first viewers miss the CDN cache and the origin is stampeded.
  2. CDN is the hero:Once the first thousand viewers fetch the segments, edge caches hold them. The next million are served from the edge. The spike is absorbed where it should be — near the viewers.
  3. API scaling:Stateless API scales horizontally under autoscaling rules — add instances when CPU/latency crosses a threshold. Bursts are the one thing load-balanced stateless services handle beautifully.
  4. Caching:Home page, new-title detail, top search results all prefetched into cache before launch ("prewarming"). The most popular thing in the world becomes a cache hit from the first request.
  5. Video processing:The new series was processed days ahead — upload and transcode happen before the release moment. On-demand transcoding at midnight would melt the worker pool; pre-processing means launch night only reads.
  6. Database protection:Watch-history writes flow async (queue), read replicas absorb catalog reads, and read-mostly paths are cached. The write path sees a calm, measured stream, not 2M heartbeats at once.
  7. Monitoring:Dashboards watch CDN hit-ratio, API p99, origin bandwidth, queue depth. An alert on cache-hit collapse or origin-everything is the first sign of a launch going sideways — long before users complain.
THE LAUNCH-NIGHT VERDICT

At the moment of spike, the design has already done its hardest work — videos are pre-processed, popular content is prewarmed at the edge, and the API is stateless. What's left is watching the metrics confirm what the architecture was built to survive.

PART 14 — WHEN IT BREAKS

14 Failure Scenarios

An architect who designs the failure library knows the system cold. Each failure: effect → user impact → immediate response → long-term prevention.

FAILURE WHAT HAPPENS / USER IMPACT IMMEDIATE RESPONSE LONG-TERM PREVENTION
1. API server fails Can't browse/login/start playback (though a session may continue buffered). Load balancer routes to healthy instances; auto-replace. Multiple instances, health checks, auto-scaling, blue-green deploys.
2. Database fails Catalog/search/history dead — possibly playback-start blocked. Failover to read replica promoted to primary. Replication + tested failover + connection retry + circuit breakers.
3. Cache fails Slower responses; DB hit by full read volume. Rebuild cache; temporarily throttle non-critical reads. Cache redundancy, graceful degradation, restart automation, alert on hit-ratio.
4. CDN (one region) fails Viewers in that region can't fetch video. Reroute to neighboring edge/origin; notify. Multi-CDN, origin failover, per-region health checks.
5. Video processing fails New upload stuck in "processing" — not viewable. Restart job; alert on stuck queue; retry with backoff. Idempotent jobs, dead-letter queue, worker auto-scaling.
6. Storage unavailable CDN misses can't reach origin → new/un-cached content breaks. Fail to replicated/secondary region bucket. Cross-region replication, eventual-consistency awareness, retry.
7. Search unavailable Search broken; browse/catalog still work (degraded). Healthy subset of search cluster; disable search UI gracefully. Multiple search nodes, fallback to catalog browse, monitoring.
8. Recommendation fails Home page missing "recommended" rail — can default to popular. Serve cached/popular fallback rows. Cached fallbacks, degrade-to-popular, offline recompute.
9. Network slow Adaptive bitrate drops quality; users see lower-res but continuity. Nothing to "fix" — monitor; users stay watching. Adaptive streaming is itself the mitigation; regional edge capacity.
10. One region fails Users in that region lose service. Traffic routed to neighboring region (higher latency, works). Multi-region active-active, data replication, global load balancing.
11. Very high traffic Slower API; possible throttling; video still flows via CDN. Scale APIs, throttle non-essential, serve degraded-but-working. Autoscaling, queue-based buffering, capacity planning (Day 14).
12. Duplicate processing job Wasted compute, possibly conflicting writes. Ignore idempotent duplicates; cancel redundant job. Idempotency keys on jobs; "exactly-once" claims avoided — design for "at-least-once + idempotent".
13. Watch history write storm Primary DB overloaded by concurrent position updates. Backpressure via queue; shed non-critical writes. Async write path, batching, eventual-consistency design.
14. Signed URL / auth leak Unauthorized access if tokens shared or too long-lived. Rotate/expire tokens immediately; revoke. Short TTL tokens, per-device binding, rate limiting, audit alerts.
PART 15 — STAYING UP

Availability and Recovery

Availability is purchased in five stages, each richer and each pricier. An architect knows the price of every stage.

BackupSnapshots of database and metadata; object storage already versioned/replicated. Backups protect against data loss, not downtime.
RecoveryThe plan to restore. RPO = how much data you may lose; RTO = how long you may be down. A backup you've never restored is a wish, not a plan.
Multiple regionsRunning in two+ geographic regions so one region's outage (or a natural disaster) doesn't kill the service. Video lives at the CDN everywhere; the core (API+DB) is what must replicate.
Health checksEach service exposes liveness/readiness; unhealthy instances are removed from traffic automatically. The fastest detection and the cheapest fix.
FailoverPrimary DB dies → replica promotes within minutes. Must be automated and drilled quarterly — an untested failover is a rumor.
Data replicationKeep copies in sync: async (faster, some lag) vs sync (safer, slower, costlier). Pick per data's money-relevance.
THE TRADE-OFF TRIANGLE

Higher availability → higher cost + more complexity. Each extra "nine" (99.9% → 99.99%) roughly doubles the engineering and infrastructure. The correct availability is the one the business will pay for, not the highest one you can draw. A streaming service's metadata must be up to start playback, but an already-streaming session surviving an API hiccup buys you enormous effective resilience — design those two tolerances separately.

PART 16 — KEEP IT HONEST

Security at Architecture Level

A paid streaming service's entire revenue is "only entitled users may watch". Security is the business model, not a bolt-on.

AuthenticationWho are you? Login issues a token the client presents. Managed identity (Auth0/Entra) is the sane buy — don't build your own OAuth (Day 20's "buy boring").
Authorization / subscription validationWhat may you do? At every Play, the API checks entitlement: active subscription? owns/rents this title? On the allowed number of screens? This is the gate, and it must be fast and authoritative.
Signed access links/tokensVideo URLs are short-lived signed tokens, not public links. A leaked URL expires in minutes and can be bound to device/IP/session.
EncryptionIn transit (TLS everywhere) for privacy; at rest (storage encryption) for protection; content protection/DRM only for genuinely premium content where it earns its complexity.
Anti-sharingLimit concurrent streams per account, device registration limits, anomaly detection (unusual login geography). Balance against user hostility — Netflix famously relaxed anti-sharing because it over-corrected.
API protection / rate limitingThrottle at the gateway per user/IP, block credential-stuffing, detect scraping. The API is where abuse lands first — protect it before the database.
PART 17 — THE BILL

Cost Thinking: Bandwidth Is King

Streaming cost is dominated by one line item — bandwidth — and every architecture choice either feeds it or starves it.

COST AREA WHY IT COSTS ARCHITECTURE LEVER TO CONTROL IT
CDN traffic The biggest cost — 3.4 PB/day at 5 Mbps × 2M viewers. Maximize cache hit-rate: prewarm popular content, warm regions, smarter edge caching.
Video storage Hundreds of TB × multiple qualities + replicas. Lifecycle tiers (hot vs cold/archive), drop rarely-used qualities for old titles.
Video processing Transcoding servers at encode time. Process once, batch, spot/cheap compute; avoid re-encoding unchanged content.
Servers (API) Stateless API fleet. Right-size autoscaling; cache to reduce compute; serverless for spiky parts.
Database Primary + replicas + storage. Read replicas for reads, async writes for history, cache aggressively.
Monitoring Log/metrics volume at scale. Sample logs, tiered retention (30d hot / archive cold).
Backup Redundant copies + restore capacity. Tiered backup, cross-region only for the data that truly must survive.

Cost-saving decisions (and when they backfire)

  • Adaptive bitrate — serve 4K only to those whose devices/plan justify it; prevents paying top-dollar bandwidth for viewers who can't see the difference. Trade: complexity in the player.
  • Region-aware content caching — a Bollywood title shouldn't hog US edge cache if its audience is in India. Trade: more cache policy management.
  • Prewarming launch content at edge — the cost of prewarming is tiny vs the origin storm it avoids. Trade: you must know what's launching when.
  • Not over-encoding — 100 qualities is waste; 4–6 sensible ones covers 99% of devices. Trade: coarse — some niche device gets "good enough", which is fine.
THE COST TRAP TO AVOID

Don't assume the most expensive architecture is best. A small regional service with 2,000 users doesn't need a global multi-CDN setup — it needs one object store, one CDN, and a monolith. Most "Netflix architecture" is earned at Netflix scale; applying it wholesale at startup scale is buying a freight train to deliver one package.

PART 18 — RIGHT-SIZE THE DESIGN

Three Architecture Alternatives

The correct design depends entirely on scale. Here are three, from scrappy to planetary.

A · SINGLE SERVER B · STORAGE + CDN C · LARGE DISTRIBUTED
Shape One server serves API + streams files from disk. Monolith API + object storage + CDN for video. Distributed services, multi-region, dedicated search/recs, full pipeline.
Advantages Dead simple, cheap, fastest to build. Video handled correctly; API still simple; scales to millions of viewers via CDN. Massive scale, flexibility, per-subsystem scaling, regional resilience.
Disadvantages Video saturates the one server instantly; dies at trivial load. API/DB still a single point; limited search/recs sophistication. Very expensive, complex to operate, overkill under ~100K users.
Cost Lowest. Low-medium; CDN+storage is the bulk. High — everything, all at once.
Complexity None. Low — one real addition (CDN). Very high — a platform team's full-time job.
Scalability Vertical only, tiny ceiling. Video scales via CDN (huge); API scales a bit. Everything scales independently, near-unbounded.
Best for Prototype, internal demo, < 1,000 users. A real streaming start-up: most of the value, fraction of the cost. Netflix-scale: millions concurrent, global, dedicated teams.
THE EVOLUTION STORY

The honest architecture answer is often "start at B, grow toward C, never overpay for A-too-long or C-too-early." Object storage + CDN is the leap that fixes the fundamental video problem; everything else (dedicated search, recs service, multi-region) is added only when its specific pain is measured. This "earn your complexity" arc is the same one from Days 18–19, applied to media.

PART 20 — THE INTERVIEW

20 Interview Questions & Model Answers

Click each for examiner intent, the simple answer, the strong architect answer, and the rookie mistake.

  1. How would you support millions of concurrent viewers?SCALE▸ VIEW ANSWERTesting: Do you understand that video and metadata scale differently?
    Simple answer: Use a CDN and scale APIs horizontally.
    Strong answer: "Viewing load is 99% video bytes, which the CDN absorbs near the user — my origin sees almost none of it. The remaining workload is metadata (small, cached, stateless), so I scale the API horizontally and use read replicas + async watch-history writes to protect the database. The concurrency problem is really a bandwidth problem, solvable at the edge."
    Common mistake: Thinking you need 2 million API servers or an exotic in-house network to handle it.
  2. Why use a CDN?CDN▸ VIEW ANSWERTesting: Grasp of geography + origin protection.
    Simple answer: It caches video near users.
    Strong answer: "A CDN turns the delivery problem from 'one datacenter serves the planet' into 'thousands of edges serve their neighborhoods'. It cuts startup latency from seconds to milliseconds, and — critically — the origin serves one copy per cache-miss, not one per viewer. That's the difference between my storage handling a trickle and my storage dying at 2M concurrent viewers."
    Common mistake: Describing CDN as just "faster" without the origin-protection economics.
  3. Why not store videos in SQL Server?STORAGE▸ VIEW ANSWERTesting: Know DB vs object store boundaries.
    Simple answer: It's too big and expensive.
    Strong answer: "Video is large, binary, write-once-read-many data — the exact opposite of what a relational database is optimized for. Storing petabytes there bloats cost, breaks backups, and hammers the connection pool on every fetch. I store video in object storage and keep metadata (title, key, where the file lives) in the database. Two tools, each doing what it's built for."
    Common mistake: Conflating "the DB references the video" with "the DB must hold the video".
  4. How would you handle peak traffic (a new series launches)?PEAK▸ VIEW ANSWERTesting: Pre-processing + edge strategy for bursts.
    Simple answer: Autoscale and cache.
    Strong answer: "Before launch: the content is already transcoded, and popular metadata/segments are prewarmed at the edge so there's no cold cache. During the spike: the CDN absorbs the video flood, stateless APIs autoscale, and the database is protected by caching + async write paths. The design does its hard work before midnight; the spike itself is mostly read traffic that the edge already owns."
    Common mistake: Treating the launch as a compute crisis instead of a cache/prewarm problem.
  5. How would you reduce video startup time?LATENCY▸ VIEW ANSWERTesting: Understand low-latency streaming levers.
    Simple answer: Use a CDN close to the user.
    Strong answer: "Five levers, in order of impact: (1) serve from the nearest edge via CDN; (2) start playback at a low bitrate so the first segment loads fast, then step quality up; (3) keep segment size small so the first buffer fills instantly; (4) prefetch/prime the player with the likely next title; (5) cache the title's manifest and metadata so the API answer is instant. Startup time is really 'time to first segment', cut all the way down the chain."
    Common mistake: Focusing on bandwidth numbers while ignoring segment size and low-start-quality.
  6. What happens if the CDN fails?FAILURE▸ VIEW ANSWERTesting: Failure resilience at the edge.
    Simple answer: Users can't watch.
    Strong answer: "A single edge/pop failing hurts only that region — I reroute to a neighboring edge or, at worst, the origin. A broader CDN outage is exactly why large platforms run multi-CDN: the app health-checks its video sources and fails over to the secondary CDN (or the origin) automatically. The API and catalog stay up regardless — video delivery degrades, the product doesn't die."
    Common mistake: Assuming CDN = single point of failure and panicking, or assuming it can never fail.
  7. How would you store watch history?DATA▸ VIEW ANSWERTesting: High-volume write-path design.
    Simple answer: A table with user + title + position.
    Strong answer: "Watch history is append-mostly, high-volume, and eventual-consistency-friendly — a viewer won't notice a one-second lag. So I capture position updates on an asynchronous path: in-memory/queued writes that batch-flush to the store, keeping the primary DB free of a 2M-viewer heartbeat storm. Read side is cached per user for instant 'Continue Watching'."
    Common mistake: Synchronously writing every position tick to the primary database.
  8. How would you scale the database?DB▸ VIEW ANSWERTesting: Read vs write scaling clarity.
    Simple answer: Add replicas and cache.
    Strong answer: "Reads first — streaming is read-heavy, so read replicas fan out catalog/search/history reads while the primary owns writes. Cache is the next layer, absorbing the hottest reads. Writes are the real ceiling: I push high-volume writes (history) async, and shard by tenant/user only when write volume truly exceeds one writer — with a documented trigger, not on day one."
    Common mistake: Jumping to sharding while the actual pressure is read-side and cacheable.
  9. What happens when a million users watch the same movie?HOTSPOT▸ VIEW ANSWERTesting: Hot-content handling.
    Simple answer: The CDN caches it once and serves everyone.
    Strong answer: "This is the case the CDN was built for: the first viewer (or prewarm) pulls each segment once, and a million viewers read from the edge. The danger is the cold start — a million simultaneous first-requests before any cache fill — which prewarming and low-start-quality solve. Hot content also moves up in the cache-eviction priority so it stays at the edge."
    Common mistake: Designing for million simultaneous unique requests when in reality it's one popular asset, massively reused.
  10. How would you design multi-region support?GEO▸ VIEW ANSWERTesting: Data residency + global delivery.
    Simple answer: Run in each region with a CDN.
    Strong answer: "Video: the CDN already delivers globally — that's mostly solved. The hard part is stateful data: run the API + database in each major region, replicate between them (async where latency is tolerable, sync where money/entitlement demands), and georoute users to the nearest healthy region. Watch regulation: some regions demand data residency, which forces local stores. The edge is easy; replicating the truth is the work."
    Common mistake: Assuming video delivery handles everything and ignoring that users' accounts/history must also be near them (and legally placed).
  11. How would you control cost?COST▸ VIEW ANSWERTesting: Bandwidth-cost maturity.
    Simple answer: Use a CDN and cheaper storage tiers.
    Strong answer: "Attack the biggest line item first — bandwidth. Higher cache hit-rate (prewarming, smart eviction, region-aware catalog), adaptive bitrate so we don't overpay for 4K nobody watches, and offline/lower-granularity encodes for the long tail. Then storage: lifecycle tiers move old content to cold classes. Then compute: process once, batch, use renewable capacity. Cost is a design output, not an accident."
    Common mistake: Optimizing server CPU costs (tiny) while bandwidth (huge) balloons unchecked.
  12. Why separate the search subsystem?SEARCH▸ VIEW ANSWERTesting: Specialized-store reasoning.
    Simple answer: Full-text search needs an index.
    Strong answer: "Relevance-ranked, typo-tolerant text search over a growing catalog isn't what a relational DB does best, and mixing it with transactional account traffic risks both. A dedicated search index handles ranking and speed, updated asynchronously from the catalog, and — because it's isolated — when search fails, browsing and playback continue unaffected."
    Common mistake: Running LIKE-queries against the primary at scale.
  13. What if the recommendation service is down?GRACEFUL▸ VIEW ANSWERTesting: Degradation paths for non-critical features.
    Simple answer: Show popular content instead.
    Strong answer: "Recommendations are non-critical and precomputed, so I serve the last cached list, or fall back to a 'popular in your region' ranked list. The home page degrades gracefully — slightly less personal, still useful — and no one loses the ability to browse, search, or watch. Not every subsystem gets a 99.9% SLA; the important thing is knowing which do and which don't."
    Common mistake: Giving recommendations the same availability budget as the playback gate.
  14. How would you identify the bottleneck in a slow system?OBSERVABILITY▸ VIEW ANSWERTesting: Systematic triage (Day 12 applied).
    Simple answer: Check metrics and traces.
    Strong answer: "Same chain every time: is it the edge (CDN hit-ratio, origin bandwidth), the API (p99, error rate, autoscaling), the cache (hit-ratio drop = DB under fire), or the database (query latency, connection pool, write queue depth)? I go signal to signal — a trace of a slow 'Play' shows exactly which hop ate the time. Metric scopes, trace locates, log explains."
    Common mistake: Guessing ("it's probably the DB") instead of reading the waterfall.
  15. How would you reduce cost by 40%?BUDGET▸ VIEW ANSWERTesting: Cost-priority judgment under pressure.
    Simple answer: Use cheaper servers.
    Strong answer: "In order of leverage: drop 4K to on-demand only (massive bandwidth + storage savings); move long-tail/old titles to cold storage; reduce encode rungs from 6 to 4; reserve/sample logs and metrics; trim non-essential replicas to on-call failover. Protected at all costs: the entitlement gate, the cache hit-rate, and the CDN prewarm on launches — those carry revenue and user trust."
    Common mistake: Cutting the cache or entitlement path because it's "redundant" — killing revenue to save pennies.
  16. Why asynchronous processing for encode?ASYNC▸ VIEW ANSWERTesting: Sync vs async line for heavy work.
    Simple answer: Encoding is slow; do it in the background.
    Strong answer: "Transcoding a 2-hour master takes minutes and is CPU-heavy but non-urgent. Blocking the upload request on it would freeze a tiny one-shot API call behind a long op — exactly backwards. So: upload persists the master and returns 'processing', a queue feeds worker pools that produce the quality ladder, and a completion event publishes 'ready to watch'. The work is retryable and idempotent; it's a textbook background job."
    Common mistake: Synchronously encoding in the request path, baking minutes of latency into an upload.
  17. How do you protect against unauthorized sharing?SECURITY▸ VIEW ANSWERTesting: Business-aware security balance.
    Simple answer: Limit devices, sign URLs.
    Strong answer: "Signed short-lived URLs prevent link-sharing; per-account device and concurrent-stream limits cap simultaneous use; and anomaly detection flags suspicious geography/behavior. But I also flag the business risk: over-aggressive anti-sharing drove real user backlash before. The architecture provides the knobs — signing, limits, detection — and the product decides how tight to turn them. Security here is a business dial, not a hammer."
    Common mistake: Treating sharing as purely technical, ignoring the customer-experience cost of enforcement.
  18. Single server vs distributed — how do you decide?SIZING▸ VIEW ANSWERTesting: Right-sizing vs resume-driven over-engineering.
    Simple answer: Depends on users.
    Strong answer: "The real lever is video, not user count: even 1,000 viewers at 5 Mbps needs 5 Gbps — a single server can't stream that. So the minimum correct design is object storage + CDN (Option B), even at modest scale. The rest — dedicated search, recs service, multi-region, multi-CDN — I add only when each specific pain is measured. Start with B, grow toward C on evidence."
    Common mistake: Two failure extremes: a single server streaming video, or a full Netflix stack for 500 users.
  19. Why signed URLs instead of public links?SECURITY▸ VIEW ANSWERTesting: Entitlement enforcement in delivery.
    Simple answer: Public links get shared.
    Strong answer: "Video bytes live at the edge, outside my application's memory, so the URL is the only lock between an entitled user and the content. A signed URL encodes who-may-access and when-it-expires, bound to a short window (and optionally device/session). A leaked link dies in minutes instead of living forever. Public links would make the CDN a free, un-gated publishing platform for my own content."
    Common mistake: Relying on "the CDN is obscure" instead of cryptographic signing.
  20. Explain your architecture in one minute to a CEO.COMMS▸ VIEW ANSWERTesting: Translation to business (Day 21 applied).
    Simple answer: "It's a streaming platform with a CDN."
    Strong answer: "Watch: 'Customers press play and video starts instantly because we keep copies of every movie on thousands of servers around the world, close to them, not in one building. The one building — our core — only handles accounts, payment, and the catalog, which is light lifting it does forever unaided. The big cost is exactly one thing, bandwidth, and every design choice exists to bend that number down. It fails rarely, and when it does, users in one region might wait a moment while everyone else keeps watching.' No tech terms, money and risk only."
    Common mistake: Starting with Kubernetes, object storage, and micro-frontends.

SUGGESTED ARCHITECT SOLUTION

  5. Main flow: Play = API authorizes + returns signed URL → CDN streams segments → adaptive quality switching client-side. Video never through the API.
  6. Storage: Object storage for masters/qualities/segments/thumbnails/captions; database for metadata + pointer keys only.
  7. CDN: Global edge network; prewarm popular + launch content; multi-CDN when a single provider's outage = real revenue loss.
  8. Database: Relational; strong consistency for user/subscription/entitlement; eventual for history/ratings; read replicas + async history writes.
  9. Caching: Movie details, home rails, prefs, hot search, precomputed recs; don't cache entitlement or money data.
  10. Search: Dedicated index, async updates from catalog, degradable (browse still works).
  11. Video processing: Async transcode into quality ladder + segments, idempotent, retry, DLQ, worker autoscaling; pre-process launches.
  12. Scaling: API horizontal; DB vertical→replicas→(later shard); search/processing horizontal; storage+CDN auto.
  13. Failure: The 14-scenario library; graceful degradation (recs→popular, search→browse, CDN region→neighbor).
  14. Security: Managed auth, entitlement check at play, signed short-lived URLs, TLS + at-rest encryption, device/stream limits, gateway rate limiting.
  15. Cost: Bandwidth-dominant; hit-rate, adaptive bitrate, cold tiers, encode-once; grow B→C on evidence.
  16. Trade-offs: Object-storage over DB, CDN over direct, eventual-over-strong for non-money, precompute-over-realtime recs, multi-region only when global.

MODEL ANSWER GUIDE

  1. 10M one title: The perfect CDN case — prewarm makes the first request a hit; edges serve 10M. Danger is cold-start + the detail-API burst; prewarm both.
  2. DB down: Failover to promoted replica; existing sessions may continue from cache/CDN; the playback gate is the critical path so it has the read replica + tested failover.
  3. Video in DB: Refuse on cost/scale/perf/backup — video is write-once-read-many binary for object storage; DB holds metadata + pointer.
  4. Why CDN: Geography (latency) + origin protection (one copy per miss, not per viewer). The 3.4 PB/day must flow at edges, not through one building.
  5. CDN down: Region-affected viewers reroute to neighbor edge/origin; multi-CDN + origin failover; the product degrades but doesn't die.
  6. Cut cost: Bandwidth first (hit-rate, adaptive bitrate, drop idle 4K), then storage tiers, then compute (encode once), then observability sampling.
  7. Regional outage: Active-active; re-route to healthy region; data replication keeps state; users get slightly higher latency, not an outage.
  8. Scale first: The API — cheapest, fastest, stateless horizontal scale; DB and processing have bigger engineering costs, defer until measured.
  9. Find bottleneck: Edge hit-ratio → API p99/errors → cache hit-ratio → DB latency/pool/queue. Trace the slow Play hop-by-hop.
  10. 40% cut: Grade-down 4K→on-demand, cold-tier old titles, fewer encode rungs, sample logs; never cut entitlement gate, cache, or prewarm.
  11. History consistency: Exact at the end of a session matters (write authoritative on stop/exit); intra-playback ticks can lag — a second of staleness is invisible, a DB write storm is not.
  12. Two CDNs: A "redundant" provider can still fail globally (config, DNS, routing). Multi-CDN is break-glass insurance for when streaming stops = revenue loss.
  13. API bottleneck proof: It's metadata-only (tiny vs video), stateless (scales horizontally), and cached (reads offloaded); the write path is rate-managed. The numbers say it scales, not faith.
  14. Biggest risk: Entitlement gate or CDN cost spiral at 2M concurrent — name one, with its metric (e.g., cache hit-ratio below threshold → cost explosion).
  15. Keep three: Object storage + CDN (video lives) + auth/catalog API (gate + discovery). Search/recs/history degrade to nothing and the core product still works.
DAY 22 — CLOSE

15 Things I Must Remember

The distilled wisdom of designing a video platform at scale. Short, practical, earned.

01

Ask before you draw.

Concurrent viewers, geography, catalog size — three numbers that reshape the entire design. Get them first.

02

Video and metadata are two different systems.

Tiny bytes (auth, catalog) vs massive bytes (video). Treat them with different scaling, storage, and failure rules.

03

Bandwidth dominates storage.

You move 3.4 PB/day but store only hundreds of TB. Delivery is the hard, expensive part — design for it.

04

Never stream video through the API.

The API authorizes and hands off a signed URL; the CDN delivers the bytes. Two machines, two jobs.

05

Video lives in object storage, not the database.

Large, binary, write-once-read-many → object storage. Small, structured, transactional → database. Never confuse them.

06

The CDN is your biggest cost and your salvation.

It absorbs the flood at the edge and it's the top line item. Every optimization is hit-rate engineering.

07

Transcode in the background, before launch.

Heavy, non-urgent work belongs in an async idempotent pipeline — never in the upload request, never at launch midnight.

08

Adaptive bitrate is the resilience trick.

Multiple qualities + segments = start low, step up, survive shaky networks. It's why smooth playback survives bad internet.

09

Strong for money, eventual for everything else.

Entitlement/subscription: strong. Watch history, ratings, recommendations: eventual. The line is "will a user notice/care".

10

Protect the database from write storms.

2M hearts = 2M position updates. Queue and batch history writes; the primary stays calm while viewers stream.

11

Search and recommendations are degradable.

When they fail, browse still works, popular still shows. Not every subsystem deserves a 99.9% budget — know which do.

12

Precompute the home page, don't compute it live.

Recommendations and popular rails are built offline and cached, so the busiest screen is always instant.

13

Start at Option B, grow toward C.

Object storage + CDN + monolith is the correct minimum. Distributed services are earned by measured pain, not ambition.

14

Security IS the business model.

A paid service's revenue is "only entitled users watch." Signed URLs, entitlement checks, device limits — core, not afterthought.

15

Cost is a design output.

Do not assume the most expensive architecture is best. Name the biggest cost (bandwidth) and design every choice to bend it down.

THE 60-SECOND INTERVIEW ANSWER: "How would you design a Netflix-like system?"

"The insight is that a streaming platform is really two systems wearing one brand. The first is a small, normal application — accounts, catalog, search, profiles — handling millions of lightweight metadata requests a second. The second is a delivery problem — moving petabytes of video daily. So I keep them separate: a standard stateless API over a relational database for the metadata, and object storage plus a global CDN for the video. When a user hits Play, the API checks their subscription and hands back a signed short-lived URL, and the CDN streams segments near the viewer at whatever quality their connection can handle — the API never touches a single video byte. That separation is what lets a hundred API servers serve tens of millions of users, because the heavy lifting happens at the edge, not in the core. Video is transcoded asynchronously into several qualities before release; watch history and recommendations are eventually consistent and precomputed so the busiest screens stay instant; and the whole thing is designed around one brutal cost law — bandwidth is the bill, so every choice, from adaptive bitrate to edge caching to dropping idle 4K, is made to bend that number down."

THE ARCHITECT'S POWER STATEMENT

"At scale you don't design for handling requests — you design for moving oceans of data efficiently, while every byte that never reaches your core is a byte you didn't pay for and a server you didn't have to protect."

You've now walked a real-world system from a blank whiteboard to a defended design. The craft is the same whether it's video, money, or messages: separate the heavy from the transactional, push bytes to the edge, precompute the expensive, and protect the truth. End of Day 22.
