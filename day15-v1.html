SECTION 01 — THE FOUNDATION

Why Distributed Systems Are Hard

A distributed system is multiple computers working together to appear as one. Your users see one app. Behind the scenes: many API servers, many database nodes, many cache instances, many queues — all across multiple data centers.

Why we distribute applications

Scale beyond one machineA single server has a ceiling. More servers = more requests served. More database nodes = more reads handled. This is the main reason.
AvailabilityOne server dies, another takes over. One data center fails, another keeps serving. The system keeps running — that is why you put it in multiple places.
LatencyA user in Singapore should not wait for a server in Virginia. Put servers near users — that is what distribution buys you.
Cost and resilienceSpread work across cheap commodity machines. Spread risk across multiple failure domains.

What distribution introduces

Every benefit above comes with a cost. The moment you have two nodes, you have the problems below. CAP is the formal name for one of them.

FIG. 15.1 — TWO APP SERVERS, TWO DB NODES — THE SIMPLEST DISTRIBUTED SYSTEM

Six problems introduced by distribution

  • Network failure — packets are lost, cables are cut, routers fail. A message sent is not a message received.
  • Latency — every network call takes time. A "fast" cross-data-center call is still 10–50 ms — and it adds up.
  • Partial failure — one node dies, others keep running. The system is half-dead. Handling half-dead is harder than handling fully-dead.
  • Data synchronization — two copies of the same data must be kept in sync. They will drift. Reconciliation is a design decision.
  • Duplicate requests — the network drops the response. The client retries. The server already processed it once. Now it processes twice. Idempotency is mandatory.
  • Data inconsistency — the user updates their address on node 1. Node 2 still has the old value. For a moment, the system lies. This is the heart of CAP.
THE ARCHITECT'S OPENING MOVE

Before you draw a distributed design, ask: "Does this need distribution at all?" Many systems do not — a single well-tuned server handles the load just fine. Distribution is a response to a problem, not a default. The day you distribute is the day one machine is genuinely not enough.

SECTION 02 — THE THEOREM

CAP — The Only Theorem You Must Get Right

CAP is a theorem from 2000 (Brewer, Gilbert & Lynch). It says one thing precisely — and that one thing is frequently misquoted.

FIG. 15.2 — THE CAP TRIANGLE, DRAWN CORRECTLY

Each letter in plain English

C — ConsistencyEvery read sees the latest write. If user A updates their address, user B reading that address a millisecond later sees the new value. No stale data, no exceptions. The system says "I don't know" rather than "here is old data."
A — AvailabilityEvery request gets a response — a successful one, not an error. The system is always up, always answering. The answer might be stale, but there is always an answer. No request times out waiting for agreement.
P — Partition ToleranceThe system keeps working even if the network between nodes breaks. A partition = two nodes that cannot talk to each other. P means the system continues to operate despite this — on both sides of the broken network.
The theoremIn a distributed system, network partitions will happen. When they do, you must choose: be consistent (refuse to answer rather than give stale data) or be available (answer even if the data may be stale). You cannot have both during a partition.

The most common misquote

DO NOT SAY THIS

"CAP means you can choose any two of the three." That is wrong. It implies you can turn off partition tolerance. You cannot — the network is outside your control. The real statement is: "When a partition happens, choose C or A." Before the partition, you can have all three. During the partition, you choose.

A REAL-WORLD EXAMPLE

Imagine two database replicas, one in New York, one in London. The transatlantic cable breaks (this happens). A user in London updates their address. A user in New York reads the same address a second later. If you are CP: New York refuses to answer — "the data is uncertain, try later." If you are AP: New York answers with the old address — "here is what I know, it might be stale." Both are correct designs for different problems.

SECTION 03 — THE PARTITION

Network Partition — Why It Is Not Optional

A network partition is the moment the network between your nodes stops working. Cables are cut. Routers crash. Switches fail. A cloud zone goes offline. The two sides of your cluster can no longer talk.

FIG. 15.3 — A NETWORK PARTITION: TWO ZONES, BOTH ALIVE, BOTH ISOLATED

Why it cannot be ignored

  • It happens in production. AWS had a 3-hour regional partition in 2017. Azure has had them. Kubernetes clusters have them. The network is the one thing you do not fully control.
  • It happens silently. No alarms go off at the exact moment. Nodes look healthy — each side thinks the other is dead. The split can last minutes or hours.
  • It creates divergence. Both sides accept writes. When the network recovers, you have two different histories. Reconciliation is not free — you must design it.
  • You cannot simply disable P. "Let's not worry about partitions" means "let's assume the network never breaks." You can say that — until it does.
THE CONSEQUENCE

Because P is a reality, every distributed system is either CP or AP during a partition. There is no third option. The question is never "should we be partition tolerant?" — it is "during a partition, will we be consistent or available?"

SECTION 04 — THE CHOICE

CP vs AP — Side by Side

Two real design paths. Both valid. The right one depends on what the business cannot afford.

DIMENSION CP — CONSISTENT · PARTITION-TOLERANT AP — AVAILABLE · PARTITION-TOLERANT
Behavior during partition Refuses to answer (returns error) when it cannot guarantee fresh data. Better to be unavailable than to lie. Always answers, even if the data is stale. Better to serve stale data than to refuse.
Advantage Data is always correct. No stale reads, no inconsistencies. Critical for financial, safety, or legal operations. System is always up. Users can always do things, even during a partition. Good for high-traffic, low-stakes systems.
Disadvantage Some requests fail during a partition. Users see errors. Business operations may stop temporarily. Some reads are stale. Data may diverge between nodes. Reconciliation needed after the partition heals.
Suitable for Banking, payments, inventory with strict counts, order processing, anything where "wrong data" = "lost money" or "legal trouble". Social media likes, product catalog reads, shopping cart, user preferences, comments — stale is annoying, not catastrophic.
Example systems PostgreSQL (single primary), MongoDB (with majority writes), Spanner, CockroachDB, ZooKeeper, etcd Cassandra, DynamoDB (default), CouchDB, Riak, DNS

What about CA?

CA means "consistent and available, but not partition-tolerant." In practice, CA is a single-node system. As soon as you distribute, you must handle partitions. Some systems advertise as "CA" — they mean "we assume no partitions, which is fine if you run one node or one tightly-coupled cluster." In a real multi-zone distributed system, CA is not an option.

THE ARCHITECT'S DECISION

Ask the business: "When the network breaks, is it worse to return stale data, or to return an error?" If stale data loses money — CP. If an error loses a user — AP. The answer comes from the business requirement, not from the database manual.

SECTION 05 — THE REAL WORLD

Eight Systems, Eight Decisions

Every piece of data in your architecture has its own CAP story. Same partition, different answers — because the business needs differ.

SYSTEM DURING A PARTITION CP OR AP WHY
Banking / Payments Refuse the transfer rather than risk double-charging. Return an error. CP Losing money is worse than a failed request. Stale balance = fraud risk.
Inventory (strict counts) Block the order if stock count is uncertain. CP Overselling inventory creates chargebacks, shipping chaos, and trust loss.
Shopping cart Let the user add items; reconcile after the partition. AP A refused "add to cart" loses the sale. A duplicated item is fixable at checkout.
Social media likes Accept the like; counts may be off by a few for a while. AP Like count accuracy is not business-critical. Availability is — users expect instant feedback.
Product catalog Serve from local cache even if the price may be a few minutes old. AP Catalog reads dominate. A price that is 5 minutes old is fine; a "catalog unavailable" page is not.
Order processing Accept the order locally; commit only when confirmed across replicas. CP Two orders with the same ID, or a lost order, is a disaster. Correctness beats speed.
Messaging / chat Deliver messages to local recipients; sync across after the partition. AP Users need to send messages now. Message order can be reconciled later.
Analytics / reports Run on locally available data; the report may be hours old. AP Reports tolerate staleness. An unavailable dashboard is a productivity loss; a slightly old dashboard is fine.
THE PATTERN

Financial, safety, and strict-count systems → CP. Read-heavy, user-experience-critical, stale-tolerant systems → AP. Most real systems have both kinds of data. Your job as an architect is to pick per data type, not per system. A single e-commerce platform is CP for payments and AP for the product catalog.

SECTION 06 — THE SPECTRUM

Strong vs Eventual Consistency

Consistency is not just "on or off." There is a spectrum. Most real systems live somewhere in the middle.

CONSISTENCY LEVELS — FROM STRONGEST TO WEAKEST

Linearizablestrongest
Sequential
Causal
Read-after-Write
Eventualweakest
STRONG EVENTUAL

What each level means in practice

LEVEL WHAT IT GUARANTEES COST WHEN TO USE
Strong (Linearizable) Every read returns the most recent write. As if all operations happened on one machine, in order. High latency, low throughput Financial balances, inventory counts, leader election
Sequential All clients see the same order of writes, but the order may lag real time. Lower latency than linearizable Chat logs, audit trails where order matters
Causal If event A causes event B, everyone sees A before B. Unrelated events can be seen in any order. Moderate latency Social feeds, comment threads
Read-after-write After you write something, your own subsequent reads will see it. Other users may not. Low overhead User profile updates — "I just changed my name, I see it now"
Eventual If no new writes happen, all replicas will eventually agree. No time guarantee. Lowest latency, highest throughput Likes, views, analytics, catalog reads

When eventual consistency is acceptable

  • Social feeds, likes, views — a like count being 3 seconds off is invisible to users.
  • Product catalog reads — a price that is 10 minutes old is acceptable; checkout still verifies before charging.
  • Analytics and reporting — dashboards can show "data updated every 15 minutes" without anyone noticing.
  • Cached user preferences — a theme change that takes a few seconds to propagate is fine.

When eventual consistency is dangerous

  • Financial balances — "your balance is $100" when it is really $10 causes overdrafts and fraud.
  • Inventory counts — selling the last item twice means an angry customer and a lost order.
  • Authentication state — "you are logged in" when you were just logged out is a security hole.
  • Legal or compliance data — "the record says X" when it actually says Y can trigger legal issues.

An e-commerce example — where inconsistency is OK and where it is not

USER UPDATES ADDRESSWrite goes to primary DB. Cache is invalidated. Replicas catch up in seconds.
ORDER SERVICE READS ITStaleness OK — the address is used for shipping, not money. AP here.
PAYMENT SERVICEStaleness NOT OK — must read from primary to avoid fraud. CP here.
REPORTINGStaleness OK — reports are built from yesterday's data. AP here.
THE ARCHITECT'S JOB

Do not pick "one consistency level for the whole system." Pick per operation. The same database can serve both CP and AP clients — you just route reads to replicas (eventual) for some and to the primary (strong) for others. That is how real systems work.

SECTION 07 — BEYOND CAP

PACELC — The Theorem for Normal Days

CAP talks only about partitions. But partitions are rare. What about the 99% of the time when the network is fine? PACELC (Abadi, 2012) extends CAP to answer that.

PACELC IN ONE SENTENCE

If there is a Partition, choose Availability or Consistency (PA/PC); Else choose Latency or Consistency (EL/EC).

What that means

During a partition (P)Same as CAP — pick Availability (A) or Consistency (C). The decision you already know.
When there is no partition (E)Now you can pick Latency (L) or Consistency (C). Faster reads (from local replica) mean potentially stale data. Stronger consistency (sync across nodes) means slower reads.
Example: DynamoDB (PA/EL)During a partition, favors availability. On normal days, favors latency — fast reads from local copies, with eventual consistency.
Example: PostgreSQL (PC/EC)During a partition, favors consistency. On normal days, also favors consistency — every read is strong, even if it costs latency.

Why architects should know PACELC

  • CAP only describes the rare partition moment. PACELC describes the day-to-day trade-off — which is what you actually live with.
  • Most database marketing talks about "consistency guarantees." PACELC asks: "What does the database sacrifice on a normal day — latency or consistency?"
  • Knowing PACELC lets you say: "Our system is PC/EC because we need strong consistency every day — we accept higher latency." That is an architect sentence.
INTERVIEW PHRASING

"CAP tells us what happens during a partition. PACELC reminds us that we also make a choice on normal days — usually between latency and consistency. I'd pick PC/EC for payments and PA/EL for the product catalog."

SECTION 08 — THE METHOD

The Architect's CAP Decision Framework

Do not pick CP or AP at the system level. Pick per piece of data and per operation. Walk these eight questions in order.

  1. What data is involved?Name it specifically: "order status," "payment amount," "product price," "like count." Different data has different tolerance for staleness.SAY: "this is the [specific] data we are talking about"
  2. What happens if it is temporarily inconsistent?Can a user see a stale price? An old address? A like count off by 5? Rank the damage: catastrophic / annoying / invisible.SAY: "the worst case of staleness is…"
  3. Can the business tolerate stale data?Ask the product owner. "Is it OK if a user sees their old email for 3 seconds?" The business decides — not the architect.SAY: "let's confirm with the business what staleness is acceptable"
  4. Can the request fail temporarily?If you choose CP, some requests return errors during a partition. Can users retry? Is that acceptable? A failed payment retry is fine; a failed login retry is not.SAY: "users will see an error — is retry acceptable?"
  5. Is the operation financial or business-critical?Money, inventory, legal, safety — always CP. Social, catalog, analytics — usually AP. The money line is sharp.SAY: "this touches money, so it must be CP"
  6. Can eventual consistency work?If the data can be wrong for a few seconds/minutes/hours without business impact, AP + eventual consistency is cheaper, faster, and more available.SAY: "eventual consistency is fine here, with reconciliation after"
  7. What recovery mechanism is required?If you choose AP, plan the reconciliation: last-write-wins, manual merge, conflict-free replicated data types (CRDTs)? This is a design decision, not an afterthought.SAY: "we will reconcile using [mechanism] after the partition heals"
  8. What monitoring is required?Track consistency lag, reconciliation queue size, partition duration. Alert when the lag exceeds the business tolerance. (Day 12's observability applies here.)SAY: "we need to monitor replication lag and reconciliation backlogs"
THE OUTPUT OF THIS FRAMEWORK

For each data type in your system, you should be able to write one sentence: "[Data] uses [CP or AP] with [strong/eventual] consistency because [business reason], and reconciles by [mechanism] if needed." If you cannot write that sentence, the design is not finished.

SECTION 09 — THE CASE

Case Study: CAP Across the E-Commerce SaaS

Same platform from previous days — multi-tenant SaaS, 10,000 companies, 1M users, 5,000 peak RPS, multi-zone on Azure/AWS. Each domain gets its own CAP decision.

DOMAIN CAP CHOICE CONSISTENCY REASON
Order creation CP Strong (linearizable) Duplicate orders, lost orders, or wrong order IDs are catastrophic. Must guarantee exactly-once semantics. Refuse during partition rather than create ambiguity.
Payment status CP Strong Double-charging or missing a payment is financial and legal. A refused payment is recoverable; a wrong payment is not.
Inventory counts CP Strong (with optimistic locking) Overselling inventory creates chargebacks, shipping chaos, and broken trust. Block the order if the count is uncertain.
Product catalog AP Eventual (minutes) Catalog reads dominate traffic. A price 5 minutes old is fine; a "catalog unavailable" page is not. Reconcile via replication lag.
Shopping cart AP Read-after-write for owner, eventual for others Users must see their own cart immediately. A duplicated item is fixable at checkout. Losing a sale to a refused "add" is worse.
Notifications (email, SMS) AP At-least-once delivery A delayed email is fine. A missing email loses trust. Send, queue retries, accept duplicates (idempotency handles them).
Reports / analytics AP Eventual (hours) Reports are built from yesterday's data. Staleness is acceptable; an unavailable dashboard is not. Dedicated read replica, possibly column-store.
Audit logs CP Strong (append-only) Missing or reordered audit entries break compliance. Must be linearizable and immutable. Writes are low volume — CP is affordable.
THE TAKEAWAY

One platform, eight domains, two different strategies. No single CAP choice for the whole system. This is the architect's job: pick per data type, defend per business reason, design per failure mode.

SECTION 10 — YOUR TURN FIRST

The Failure Scenario — Solve It Before Reading On

This is an interview question. Read the prompt. Form your answer on paper first. Then click to reveal the architect's ideal answer.

THE INCIDENT

Your e-commerce SaaS has two database replicas — one in US-East, one in EU-West. A network problem isolates them. They cannot talk. Users on both sides are still placing orders.

  • Should the system continue accepting orders?
  • What happens to consistency?
  • Which operations should fail?
  • Which operations can continue?
  • How can the system recover?
  • What data needs reconciliation?
  • Would you choose CP or AP?
IDEAL ARCHITECT ANSWER
  • Continue accepting? Not all of them. Read operations (catalog, cart view, search) can continue on each side independently — these tolerate staleness (AP).
  • Consistency: It diverges. Two users can order the same last inventory item, one in US and one in EU. Each replica thinks it has stock.
  • Operations that should fail: Inventory-deducting writes, payment authorizations, order finalization. These are CP — block them until consistency is confirmed, or route them to the primary (which may be unreachable from one side, in which case: return error).
  • Operations that can continue: Catalog reads, cart operations, user profile reads, browsing, search. These are AP — serve from local replica, accept staleness.
  • Recovery: When the network heals, replicas reconcile. Inventory uses last-write-wins with conflict detection (both decrements are checked; one may need to be refunded). Orders have unique IDs — no duplicates, but order sequence may differ. Payment provider is the source of truth for payments — reconcile against their records.
  • Data needing reconciliation: Inventory counts (primary risk), order sequence, any user profile edits made on both sides during the partition.
  • CP or AP? Mixed. CP for inventory and payments, AP for catalog and cart. This is not a single choice — it is per operation. In the interview, saying "CP" or "AP" as a blanket answer is wrong. The architect answer is "we partition our data by criticality."
SECTION 11 — THE INTERVIEW

15 CAP Interview Questions

Each question tests a specific concept. Answer out loud, then click to see what a strong answer covers.

  1. Explain CAP Theorem in under 60 seconds. What does it really say?CORE▸ WHAT A STRONG ANSWER COVERSLISTEN FORC = consistency (every read sees the latest write), A = availability (every request gets a response), P = partition tolerance (system works despite network failures). The theorem: during a partition, pick C or A — not both. "Pick any two" is the misquote.
  2. Why can't you turn off Partition Tolerance?CORE▸ WHAT A STRONG ANSWER COVERSLISTEN FORBecause the network is not under your control. Cables break, routers fail, cloud zones go offline. Saying "I'll just avoid partitions" means "I'll assume the network never fails" — a bet you will lose.
  3. What is the difference between CAP consistency and database ACID consistency?CONCEPT▸ WHAT A STRONG ANSWER COVERSLISTEN FORCAP consistency means "every read sees the latest write across the distributed system." ACID consistency means "the database state obeys its rules (constraints, types)." They are different Cs. A single database can have ACID and still participate in a CAP trade-off when replicated.
  4. A bank transfer is happening. Network partition. Should the system allow it?SCENARIO▸ WHAT A STRONG ANSWER COVERSLISTEN FORCP — refuse the transfer during the partition. Losing money is worse than a failed request. The user can retry. The bank account balance must be authoritative — any ambiguity is unacceptable.
  5. A social media like happens during a partition. What do you do?SCENARIO▸ WHAT A STRONG ANSWER COVERSLISTEN FORAP — accept the like, count may be off by a few. Reconcile after. The like count being wrong by 2 for a few minutes is invisible to users. A refused like is visible and annoying.
  6. Explain eventual consistency. When is it acceptable?CONCEPT▸ WHAT A STRONG ANSWER COVERSLISTEN FOREventual consistency = if no new writes happen, all replicas will eventually agree. No time bound. Acceptable for: likes, views, analytics, catalog reads, user preferences. Not acceptable for: financial balances, inventory counts, legal records.
  7. What is read-after-write consistency, and why does it matter?CONCEPT▸ WHAT A STRONG ANSWER COVERSLISTEN FORThe user who wrote something sees their own write immediately on subsequent reads. Other users may not. This is a common requirement for user-facing apps — "I changed my profile, I see the change right away." Achievable without full strong consistency.
  8. Your product catalog has 500K items. CP or AP?DESIGN▸ WHAT A STRONG ANSWER COVERSLISTEN FORAP — catalog reads dominate traffic, and a price being 5 minutes old is acceptable. Use read replicas for the reads. Verify the final price at checkout (where CP applies to the order and payment). Mixed consistency, per operation.
  9. What is PACELC, and why is it useful beyond CAP?CONCEPT▸ WHAT A STRONG ANSWER COVERSLISTEN FORPACELC extends CAP to the normal case. During a partition: A or C. Else (no partition): L (latency) or C (consistency). It describes what databases sacrifice on normal days — most pick latency (local reads) and accept eventual consistency.
  10. MongoDB or Cassandra — which is CP and which is AP, and why?DESIGN▸ WHAT A STRONG ANSWER COVERSLISTEN FORMongoDB (with majority writes): CP — refuses to write if quorum is not met. Cassandra (default): AP — accepts writes on any node, reconciles later. Both can be tuned. The answer is "it depends on configuration" — but default behavior is CP and AP respectively.
  11. Two users edit the same document simultaneously on different nodes. Network partitions. What happens?SCENARIO▸ WHAT A STRONG ANSWER COVERSLISTEN FORCP: refuse one of the writes (return error to the user). AP: accept both, reconcile later (last-write-wins, or a merge strategy). The answer depends on the document type — a shared legal contract is CP; a shared note can be AP with CRDTs for merging.
  12. What happens when AP meets a partition that lasts 2 hours?SCENARIO▸ WHAT A STRONG ANSWER COVERSLISTEN FORBoth sides keep accepting writes. Data diverges significantly. When the network heals, reconciliation queue explodes. Conflict resolution must be designed in advance. Some conflicts may need manual intervention. This is why AP needs a reconciliation plan — not just eventual consistency.
  13. Design a multi-region e-commerce platform. How do you apply CAP?DESIGN▸ WHAT A STRONG ANSWER COVERSLISTEN FORPer-operation choice: orders and payments are CP (strong, via primary in one region); catalog and cart are AP (local replicas); analytics is AP (replicated data warehouse). Reads from local replica for latency; writes routed to primary. This is the architect answer — not "the whole system is CP."
  14. Your system is AP. A partition heals. What must happen next?DESIGN▸ WHAT A STRONG ANSWER COVERSLISTEN FORReconciliation. Both sides send their writes to each other. Conflicts resolved by last-write-wins, manual merge, or CRDT. Reconciliation queue monitored. Alert if the queue grows beyond threshold. Reconciliation is a design decision — it must be planned, not improvised.
  15. Why might a senior engineer say "CAP doesn't apply to my system"?CONCEPT▸ WHAT A STRONG ANSWER COVERSLISTEN FORTheir system is not distributed — it is a single node, or tightly coupled in one data center with no network failure path. CAP is specifically about distributed systems with network partitions. For a single-node system, CAP is irrelevant. But if they later add replicas, CAP applies.
SECTION 12 — THE GRAVEYARD

Common Interview Mistakes

These are the answers that lose the interview. Know them so you can avoid them.

1 · "CAP means choose any two."Wrong. P is not a choice — the network fails whether you like it or not. The theorem says: during a partition, pick C or A. Saying "choose any two" reveals you did not understand the theorem.
2 · "We'll just disable Partition Tolerance."You cannot. The network is outside your control. What you can do is deploy in one data center — that makes partitions rare, but you lose availability from the other direction (single point of failure).
3 · Confusing CAP consistency with ACID consistency.They are different Cs. ACID is about database rules and transactions. CAP is about distributed reads seeing the latest writes. Mixing them up is a red flag in an interview.
4 · "AP means no consistency at all."Wrong. AP means eventual consistency — data converges over time. Many AP systems (DynamoDB, Cassandra) offer tunable consistency: you can choose strong reads for specific operations.
5 · "CP means the system is always unavailable."Wrong. CP means the system is unavailable during a partition. Most of the time, the network works, and a CP system is fully available. Partitions are rare — but when they happen, CP systems protect correctness.
6 · Naming databases without explaining the trade-off."I'd use Cassandra." Why? What trade-off does that imply? The interviewer wants to hear your reasoning — not your database shopping list. Name the trade-off first, then the tool.
7 · Ignoring business requirements."I'd choose AP." Why? What does the business need? If the business says "we cannot lose money," AP is the wrong choice for the payment path. The business decides — the architect translates to CP or AP.
8 · One CAP choice for the whole system."Our e-commerce platform is AP." Really? Even for payments? Even for inventory? Most real systems are mixed — CP for critical data, AP for the rest. Saying "AP" as a blanket answer is a junior answer.
THE TEST

If you can answer "why CP here and AP there?" for every piece of data in your system — with a business reason, not a database reason — you are thinking like an architect. If you cannot, the design is not finished.

DAY 15 — CLOSE

The Architect's CAP Mindset

Five rules from today. If you remember nothing else, these carry you through every distributed decision.

01

"Pick two" is not the theorem.

Partition tolerance is not a choice — networks fail. CAP says: during a partition, pick C or A. That is the whole statement. The rest is consequence.

02

Consistency is not the same everywhere.

Your database may need strong consistency. Your cache may not. Your reporting store definitely does not. CAP is per-operation, not per-system. The architect's job is to pick per data type.

03

The business decides C or A, not the architect.

"Can we lose money if data is stale?" — that is the real question. If the answer is yes, you need strong consistency. If the answer is no, eventual consistency is cheaper and faster. Ask the business first.

04

Partitions are rare but not zero.

You will not see one most days. You will see one on the day the CEO is demoing the product. Design for the partition — or design for the apology email.

05

Recovery is part of the design.

Whatever you pick during a partition, you must reconcile after it. Eventual consistency means you eventually converge — but someone still has to write the reconciliation logic.

CAP is not a quiz question. It is the daily design decision: "Should this read fail if the data might be stale, or should it return stale data and let the business decide?" Ask that question for every piece of data, and you are thinking like an architect.
