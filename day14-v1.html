SECTION 01 — THE BASICS

Back-of-the-Envelope Estimation

You do not need a calculator or a spreadsheet. You need simple math, clear assumptions, and the ability to say them out loud. Every architecture decision starts with a number.

What is Back-of-the-Envelope Estimation?

It is the architect's quick calculation — rough, honest, and useful. Not precise, but good enough to make decisions. The goal is to answer: "Is this design big enough? Where will it break? When do we need to change it?"

Why architects use it: In a system design interview, you cannot code a load test. You cannot run a benchmark. You have a whiteboard and a conversation. Estimation is how you prove your design works at scale — with numbers, not hope.

Assumptions you must clarify first

  • Registered users — total signups, not active people.
  • Daily active users (DAU) — who actually logs in each day. Usually 1–20% of registered.
  • Concurrent users — active right now. Usually 1–10% of DAU.
  • Requests per user per day — how many API calls, page loads, clicks one person makes. Varies widely: a weather app = 5, an e-commerce site = 100+.
  • Read/write ratio — most systems are 70–90% reads. Social media: 90%. E-commerce: 80%. Banking: 50/50 or write-heavy.
  • Peak factor — peak is not average. Typically 5–40× the average, depending on the business. E-commerce at Black Friday can be 40×. A dashboard tool: maybe 5×.

Core formulas

TRAFFIC

Daily Requests = Active Users × Requests/User/Day
Average QPS = Daily Requests / 86,400 // 86,400 = seconds in a day
Peak QPS = Average QPS × Peak Factor
Read QPS = Peak QPS × Read %
Write QPS = Peak QPS × Write %

STORAGE

One Year Storage = Records/Year × Avg Record Size
Total Storage = One Year Storage × Years + Overhead // ~30% for indexes, logs, backups

BANDWIDTH

Read Bandwidth = Read QPS × Avg Response Size
Write Bandwidth = Write QPS × Avg Request Size

CACHE

Cache Size = Items to Cache × Avg Item Size

QUEUE

Daily Messages = Events/Day × Messages/Event
Peak Queue Rate = Daily Messages / 86,400 × Peak Factor

Unit conversions you must know

DATETIME CONVERSION STORAGE CONVERSION
60 seconds = 1 minute 1,024 bytes = 1 KB (~1K)
3,600 seconds = 1 hour 1,024 KB = 1 MB (~1M)
86,400 seconds = 1 day — remember this 1,024 MB = 1 GB (~1B)
525,600 minutes = 1 year 1,024 GB = 1 TB
~31.5M seconds = 1 year 1,024 TB = 1 PB
In estimation, use 1K=1000, 1M=1,000,000, 1B=1,000,000,000. The 1024 difference is noise at this level.
THE RULE

State every assumption out loud. "I'm assuming 10% of registered users are active daily." The interviewer is not grading your math — they are grading whether you can think clearly about scale. If your assumption is wrong, say so and adjust. That is the whole skill.

Rules of Thumb

Memorize these. They appear in almost every estimation.

Record size Order: 1–5 KB; User profile: 2–10 KB; Log entry: 0.5–2 KB Used for storage calculation ASSUMPTION

Replication overhead Each replica = full copy of storage 2 replicas = 2× more storage FACT

ASSUMPTION VS FACT

Facts (86,400 seconds/day, 1K = 1024 bytes, 1 replica = 1× storage) are always correct. Assumptions (DAU ratio, peak factor, page size) must come from the interviewer or be stated clearly. In an interview: "I'll assume 10% DAU — please tell me if that's off and I'll recalculate."

SECTION 03 — THE METHOD

The 13-Step Estimation Method

Follow this order in every interview. Each step feeds the next. If you skip a step, the numbers that follow are wrong.

  1. Clarify requirementsWhat is the system? Who uses it? What are the core features? What numbers were given? What is missing?SAY: "let me clarify the scale before I start calculating"
  2. Estimate total registered usersGiven or estimated. This is the top of the funnel — never the active number.SAY: "1M registered users is the marketing number"
  3. Estimate daily active users (DAU)10% of registered is a safe default. Adjust for the type of app.SAY: "assuming 10% DAU, that's 100,000 active users"
  4. Estimate requests per user per dayHow many API calls, page loads, interactions? E-commerce: ~100. Social: ~200. Dashboard: ~20. State your assumption.SAY: "each user makes about 100 requests a day"
  5. Calculate average QPSDaily Requests / 86,400. This is the baseline — traffic never stays here.SAY: "10M / 86,400 = about 116 requests per second on average"
  6. Calculate peak QPSAverage QPS × peak factor (10–40×). Peak is when you design for.SAY: "with a 40× peak factor, that's about 4,600 peak RPS"
  7. Split read/writePeak QPS × read% and write%. Tells you if read replicas are needed.SAY: "at 80/20, that's 3,680 read RPS and 920 write RPS"
  8. Estimate storageRecords per year × record size. Add 30–50% overhead for indexes and metadata.SAY: "10M orders × 2KB = 20 GB, plus overhead = ~25 GB"
  9. Estimate bandwidthPeak RPS × payload size. This tells you if you need a CDN or bigger network.SAY: "4,600 RPS × 50KB = about 2.3 GB per second"
  10. Estimate cache sizeItems to cache × item size. If cache is bigger than memory, it will not work.SAY: "100K products × 4KB = ~400 MB cache — fits in Redis"
  11. Estimate queue volumeEvents per day × messages per event. Tells you queue throughput needs.SAY: "200K orders × 3 messages = 600K messages/day"
  12. Add growth and safety marginDouble your peak. Plan for 3× growth in 3 years. This is non-negotiable.SAY: "I'd design for 9,200 RPS — double the peak — and plan for 3× in three years"
  13. Identify the likely bottleneckWrite throughput to database? Cache memory? Network bandwidth? Queue consumers? The bottleneck drives your architecture.SAY: "at 920 write RPS, the database is the bottleneck — I need read replicas and possibly sharding"
HOW TO SPEAK IT IN AN INTERVIEW

"So I have 1M registered, I'll assume 100K daily active. Each user makes about 100 requests a day — mostly reads, like browsing products and searching. That's 10M daily requests, which is about 116 per second on average. Peak could be 40× that during sales events, so roughly 4,600 RPS. At 80/20 reads to writes, I'm looking at about 3,680 reads and 920 writes. The writes will pressure the database, so I'd add read replicas and consider caching for the read path."

SECTION 04 — PRACTICE

Three Worked Examples

Three systems, growing in complexity. Follow the 13-step method in each.

EXAMPLE 1 — SMALL APPLICATION (INTERNAL TOOLS)

Step 1: Internal project management tool for 500 employees
Step 2: 500 registered users
Step 3: 300 DAU (60% — internal tool, everyone uses it daily)
Step 4: 30 requests/user/day (clicks, edits, loads) // conservative — internal tool
Step 5: 300 × 30 = 9,000 daily requests → 9,000 / 86,400 ≈ 0.1 QPS average
Step 6: Peak factor 5× (internal — no spikes) → 0.1 × 5 = 0.5 peak QPS
Step 7: 70/30 read/write → 0.35 reads, 0.15 writes per second
Step 8: 9K records/year × 2KB = 18KB → negligible storage (kilobytes!)
Step 9: Bandwidth: 0.5 RPS × 10KB = 5 KB/s — nothing
Step 10: Cache: 500 projects × 10KB = 5 MB — trivial
Step 11: No queue needed — 0.5 QPS is tiny
Step 12: Even 2× margin = 1 QPS. ONE SERVER IS ENOUGH.
Step 13: No bottleneck. A single small VM handles this. Do not over-design.

EXAMPLE 2 — MEDIUM SAAS APPLICATION

Step 1: B2B analytics platform, 50,000 registered, 10,000 companies
Step 2: 50,000 registered
Step 3: 10,000 DAU (20% — B2B, serious users) // higher than consumer apps
Step 4: 50 requests/user/day (dashboards, queries, exports) // read-heavy
Step 5: 10K × 50 = 500K daily → 500,000 / 86,400 ≈ 6 QPS average
Step 6: Peak factor 10× (business hours) → 6 × 10 = 60 peak QPS
Step 7: 85/15 read/write → 51 read RPS, 9 write RPS
Step 8: 500K reports/year × 5KB = 2.5M KB ≈ 2.5 GB/year + 30% = ~3.3 GB
Step 9: 60 RPS × 20KB avg = 1.2 MB/s bandwidth
Step 10: 50K dashboards × 20KB = 1 GB cache — fits in Redis
Step 11: 10K email notifications/day × 1KB = 10 MB/day queue
Step 12: 2× margin = 120 QPS. Still manageable on 1–2 servers.
Step 13: Database write load (9 RPS) is fine. Reading heavy dashboards — cache is the real help. One server + cache is enough.

EXAMPLE 3 — LARGE-SCALE E-COMMERCE

Step 1: Multi-tenant e-commerce SaaS, 1M registered users
Step 2: 1,000,000 registered
Step 3: 100,000 DAU (10%) // realistic for large SaaS
Step 4: 100 requests/user/day (browse, search, cart, order, profile) // typical e-commerce
Step 5: 100K × 100 = 10M daily → 10,000,000 / 86,400 ≈ 116 QPS average
Step 6: Peak factor 40× (Black Friday, flash sales) → 116 × 40 ≈ 4,640 peak QPS
Step 7: 80/20 read/write → 3,712 read RPS, 928 write RPS
Step 8: 10M orders/year × 2KB = 20M KB ≈ 20 GB/year + 30% = ~26 GB
Step 9: 4,640 RPS × 50KB avg = 232 MB/s ≈ 1.86 Gbps bandwidth
Step 10: 200K products × 4KB = 800 MB cache — fits in Redis cluster
Step 11: 200K orders/day × 3 messages/order = 600K messages/day ≈ 7 messages/sec avg, peak ~280 msg/s
Step 12: 2× margin = 9,280 QPS. Need horizontal scaling — 20–40 API servers.
Step 13: BOTTLENECKS: Write RPS to database (928) — needs read replicas. Bandwidth (1.86 Gbps) — needs CDN. Queue (280 msg/s peak) — needs scaling consumers. Cache (800 MB) — Redis cluster for redundancy.
THE PATTERN

Example 1: one server. Example 2: one server + cache. Example 3: horizontal cluster + replicas + CDN + queue + cache cluster. The architecture grows with the numbers — not before.

SECTION 06 — NUMBERS DRIVE DESIGN

Capacity Planning: When Numbers Change Architecture

Estimation is not about being perfectly accurate. It is about knowing when your design stops working and what to do next.

NUMBER ARCHITECTURE DECISION WHY
< 100 QPS One server is enough. Simple monolith, one database, maybe a small cache. Any modern server handles this. Don't over-design.
100–1,000 QPS Start thinking about scale. Add caching, maybe one read replica. Monitor carefully. One server still works, but you are approaching limits during peak.
1,000–5,000 QPS Horizontal scaling needed. Multiple API servers behind a load balancer. Read replicas for heavy reads. CDN for static assets. Single server CPU and connections are maxed. The database becomes the bottleneck.
Read replicas when? When read QPS > 500 or read/write ratio is > 80/20 Primary cannot serve both reads and writes at high volume. Replicas absorb reads.
Caching important when? When repeated reads dominate. Product catalog, user profiles, configuration data. Cache saves a database query. At 3,000+ read RPS, cache is not optional — it is survival.
Sharding may be needed when? Write QPS > 2,000 or database storage > 1 TB and growing fast Vertical scaling and read replicas are maxed. The single writer cannot handle more writes.
Async processing useful when? When not every action must be instant. Email, notifications, reporting, data sync. Queue removes work from the critical path — the API answers fast, the background does the slow work.
CDN useful when? When static content is > 100 MB/s or users are globally distributed Serves images, CSS, JS from edge locations — saves your origin bandwidth and reduces latency.
DB optimization before servers Always. Fix queries and indexes before adding hardware. A bad query on 100 servers is still slow. A good query on 1 server is fast. Database performance is free if you find it first.
THE ARCHITECT'S MINDSET

Never add servers before fixing the database. Never shard before partitioning. Never partition before indexing. Never index before measuring. Each step costs less and works better than the one after it. Simple before complex, always.

SECTION 07 — THE ANSWER STRUCTURE

Interview Technique

When the interviewer asks an estimation question, structure your answer in four parts: clarify, calculate, conclude, caveat.

1. ClarifyRestate the problem and ask for missing numbers. "I'm assuming 10% DAU — is that right?"
2. CalculateWalk through the 13-step method out loud. Show each formula. Say each assumption.
3. ConcludeSummarize: "So at peak I'm looking at about 5,000 RPS — I'd need 15–20 API servers, read replicas for the database, a Redis cluster, and a CDN for static assets."
4. CaveatName the uncertainty: "These are rough numbers. In production I'd validate with load testing and adjust based on actual metrics."

How to answer specific questions

QUESTION ARCHITECT-STYLE ANSWER STRUCTURE
"How many servers do you need?" "I'd estimate peak RPS first: [calculate]. Then, one server handles about 200–500 QPS for our API complexity. At [X] peak RPS, I need [X/300] = [N] servers. With 2× safety margin, that's [2N]. Plus, I need separate servers for the database, cache, and queue."
"How much storage?" "Daily writes are about [X] records at [Y] KB each = [Z] GB/day. Per year that's [Z × 365] GB. Adding 30% for indexes and overhead, and planning 3× for backups, the total is about [total] TB."
"How much traffic?" "DAU is [X], requests per user is [Y], so daily requests = [X × Y]. Average QPS = [daily / 86,400]. Peak is about [factor]× higher = [peak QPS]. At 80/20 read/write, that's [reads] reads and [writes] writes per second."
"Can this database handle it?" "Write QPS is [X]. A single database typically handles [Y] write QPS comfortably. [If X < Y] Yes, with room to grow. [If X > Y] No — I'd add read replicas immediately and consider sharding if writes keep growing."
"How will it scale after 3 years?" "If traffic grows [factor]× in 3 years, peak will be [new peak]. The first change would be more API servers (horizontal, easy). The database would need read replicas and possibly sharding. Cache grows linearly — just add Redis nodes. Queue scales by adding consumers."
WHAT THE INTERVIEWER SCORES

Not whether your math is perfect. Whether you show your work, name your assumptions, reach the right conclusion (one server for 1 QPS, horizontal scaling for 5,000 QPS), and mention the bottleneck. A clean thought process beats a calculator every time.

DAY 14 — CLOSE

The Architect Who Counts

Five rules from today. If you remember nothing else, these are the whole of estimation and capacity planning.

01

State every assumption.

"I'm assuming 10% DAU." "I'm assuming 100 requests per user." "Peak factor is 40×." The numbers are not wrong — the assumptions are. And naming them is the whole point of the exercise.

02

Design for peak, not average.

116 QPS sounds like one server. 4,600 QPS sounds like twenty. The difference is one number: the peak factor. Always design for the worst reasonable hour, not the best.

03

Double your numbers.

A safety margin of 2× is not paranoia — it is the tax you pay for the thing you forgot to count. Without it, your architecture fails on launch day.

04

The bottleneck is always the database.

Until it is not — then it is the cache, or the queue, or the network. But it starts there. Fix the database before you add servers. Fix the query before you add replicas. Fix the index before you shard.

05

Estimation is a hypothesis, not a commitment.

Your numbers are wrong. That is not a failure — it is the starting point. Production monitoring (Day 12) will tell you the truth. Adjust the design based on real data, not your first guess.

An architect who cannot estimate is an architect who cannot plan. Every number you calculate today is a decision tomorrow. Make them honest, make them loud, and always — always — leave room for the unexpected.
