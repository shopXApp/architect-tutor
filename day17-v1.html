PART 1 · THE FOUNDATION

Thirteen Concepts, One Idea

Before any technical word, let's agree on one idea: instead of calling someone directly, you announce something happened, and whoever cares listens. Everything else in this tutorial flows from this single thought.

  1. 1 · What is an event?A message that says "something happened." For example: "a customer placed order #58211." The event carries the facts — the order ID, the customer, the total. It does not say what anyone should do next.AN EVENT IS A NEWS STORY, NOT AN INSTRUCTION
  2. 2 · What is event-driven architecture?A style of design where business areas talk to each other through events, not through direct calls. One area publishes an event; other areas subscribe to it and react in their own way.THE POST OFFICE INSTEAD OF THE PHONE
  3. 3 · Why do businesses use events?Because real life is event-driven. A customer orders, many things must happen next — payment, inventory, shipping, emails — but they are different jobs done by different teams. Events let each team work at its own pace without waiting for the others.DECENTRALIZE · INDEPENDENT · SCALABLE
  4. 4 · Normal request vs eventA request is: "Please do this for me now and tell me the answer." An event is: "Something just happened — whoever cares, react." A request has one caller and one answer. An event may have many listeners, or none.REQUEST = I NEED YOU · EVENT = I ANNOUNCE
  5. 5 · Synchronous processingThe caller waits for the answer. Like calling a restaurant and waiting on the phone until they confirm your order. If they are slow, you wait. If they are down, your call fails.ONE AT A TIME · CALLER BLOCKED
  6. 6 · Asynchronous processingThe caller sends the message and moves on. Like leaving a voicemail — you hang up and do other things. The listener picks it up when ready. Slower for urgent answers, but far better for scale.FIRE AND FORGET · CALLER FREED
  7. 7 · PublisherThe system that sends an event. For example, the Order service publishes "OrderCreated." It does not care who listens — it just announces.THE ANNOUNCER
  8. 8 · ConsumerA system that listens for events and reacts. Payment, Inventory, and Notification are all consumers of "OrderCreated." Each does its own job.THE LISTENER
  9. 9 · Message brokerThe post office between publishers and consumers. It receives events, stores them safely, and delivers them to every consumer that wants them. RabbitMQ, Kafka, Azure Service Bus — these are brokers.THE MIDDLEMAN · THE HUB
  10. 10 · QueueA line of messages. Each message is delivered to exactly one consumer. If five consumers listen, only one of them gets each message — good for load-sharing work.ONE MESSAGE · ONE CONSUMER
  11. 11 · TopicA channel where every message is delivered to every subscriber. If five consumers listen, all five get each message — good for broadcasting news.ONE MESSAGE · MANY CONSUMERS
  12. 12 · Why communicate through events?Because it decouples systems. The Order service does not need to know that Notification exists. Notification does not need to know that Order exists. They only know about the event. Each side can change, scale, and fail independently.LOOSE COUPLING · THE ARCHITECT'S GOAL
  13. 13 · When events should NOT be usedWhen the caller must have an answer immediately. Login, "get my balance," "is this product in stock at checkout" — these are requests, not events. Using events here would add complexity with no benefit.IF THE CALLER MUST WAIT, USE A DIRECT CALL
THE RESTAURANT ANALOGY

Imagine a busy kitchen. The waiter (publisher) places an order on the ticket rail. The chef, the grill cook, and the salad prep (consumers) each read their part and do their work. The waiter does not stand there telling each cook what to do — they just announce, and whoever is responsible reacts. That is event-driven architecture. The ticket rail is the broker.

PART 2 · THE EXAMPLE WE WILL USE ALL DAY

The Enterprise Order Management System

Seven business areas, one flow. We will use this system for every example, every diagram, every exercise.

CUSTOMERPlaces an order through the website or mobile app.
ORDERRecords the order and kicks off everything that follows.
PAYMENTCharges the customer's card.
INVENTORYReserves the items from stock.
SHIPPINGPrepares the package and sends it out.
NOTIFICATIONTells the customer what is happening.

And Reporting watches everything, builds dashboards and reports.

First — how it works with direct API calls

In the old design, the Order service calls each downstream service directly, one after the other. Like a phone chain:

FIG. 17.1 · SYNCHRONOUS DESIGN — EVERYTHING ON ONE CHAIN

The problems with this design

  • Slow customer experience. The customer waits while every downstream step finishes. If payment takes 2 seconds, inventory 1 second, shipping 3 seconds — the customer waits 6 seconds before seeing "order placed."
  • Fragile chain. If Inventory is down, the whole order fails. The customer sees an error even though the problem is in a back-end system they have never heard of.
  • Hard to scale. Peak hour on Black Friday? The whole chain must scale together — Order, Payment, Inventory, Shipping — even though each has different capacity needs.
  • Hard to change. Want to add a loyalty-points step? You must change the Order service. Want to replace the notification system? You must change the Order service. The Order service knows about everyone.

Now — the same system with events

Instead of calling each service, the Order service publishes an event: "OrderCreated." Payment, Inventory, Notification, and Reporting all subscribe to this event. Each does its own job. They do not wait for each other. They do not even know about each other.

THE SHIFT

The Order service no longer says "Payment, do your job." It says "an order just happened." Payment hears this and decides what to do. This is the whole idea of event-driven architecture. The caller announces; the listener decides.

PART 3 · THE EVENT FLOW

OrderCreated — What Happens Next

Let's follow one order through the event system, step by step. Each arrow is an event. Each reaction is a consumer doing its job.

FIG. 17.2 · THE EVENT FLOW — ORDER CREATED TO CUSTOMER CONFIRMATION

Step by step — in simple English

  1. Customer places an order. The Order service saves it to its database and marks it "placed."
  2. Order service publishes "OrderCreated." This event contains the order ID, customer, items, total. It does not say "Payment, do your job" — it just announces the fact.
  3. Payment service hears the event. It charges the customer's card. If the charge succeeds, it publishes "PaymentSuccessful." If it fails, it publishes "PaymentFailed."
  4. Inventory service hears the event. It reserves the items in the warehouse. Publishes "InventoryReserved" or "InventoryFailed."
  5. Shipping service hears "PaymentSuccessful." It prepares the package and arranges delivery. Publishes "OrderShipped."
  6. Notification service hears several events. It sends an email for each step: "your order is placed," "payment confirmed," "order shipped."
  7. Reporting service hears all events. It updates the merchant's dashboard — "5 orders this hour, 3 shipped, 2 pending."
THE KEY OBSERVATION

Notice what the Order service does not know. It does not know about Payment. It does not know about Inventory. It does not know about Notification. It only knows: "I published an event." Everything else is someone else's job. That is the architect's goal — each business area is independent.

WHAT ABOUT FAILURE?

What if Payment fails? The Inventory reservation must be undone. What if the customer's card is declined? The order must be marked "payment failed." These are the hard parts of event-driven design — and we will cover them carefully in Part 6 and beyond.

PART 4 · THE PICTURE

The Architecture Diagram

Let's draw the whole system in one picture. One client, one API, many services, one broker, one database per service.

FIG. 17.3 · THE FULL EVENT-DRIVEN ARCHITECTURE

Who publishes, who consumes

SERVICE PUBLISHES CONSUMES DATABASE
Order OrderCreated, OrderCancelled (only from the client) Order DB
Payment PaymentSuccessful, PaymentFailed OrderCreated Payment DB
Inventory InventoryReserved, InventoryFailed OrderCreated, PaymentSuccessful Inventory DB
Shipping OrderShipped, ShipmentDelayed PaymentSuccessful, InventoryReserved Shipping DB
Notification NotificationSent OrderCreated, PaymentSuccessful, OrderShipped Notification log
Reporting — All events Reporting DB / data warehouse

Which components communicate directly

  • Client ↔ API Gateway: direct. The client asks for things, the API answers.
  • API Gateway ↔ Order service: direct. The client places an order, the Order service handles it.
  • Order ↔ Payment, Inventory, Shipping, Notification, Reporting: through the broker. They do not talk to each other.

Step by step through the diagram

  1. Client (web or mobile) sends "place order" to the API Gateway.
  2. API Gateway authenticates the request and routes it to the Order service.
  3. Order service saves the order to its database and publishes "OrderCreated" to the broker.
  4. Broker delivers "OrderCreated" to Payment and Inventory (and any other subscriber).
  5. Payment charges the card, publishes "PaymentSuccessful" or "PaymentFailed."
  6. Inventory reserves the stock, publishes "InventoryReserved."
  7. Shipping listens for both "PaymentSuccessful" and "InventoryReserved" — when both are received, it prepares shipment.
  8. Notification listens to all events and sends customer messages.
  9. Reporting listens to everything and updates dashboards.
THE DESIGN AT A GLANCE

Each service owns its own data. Payment has its own database. Inventory has its own database. They do not share. Each service talks only to the broker. The broker is the only shared piece of infrastructure. If a service fails, the others keep working — they simply wait for it to come back and process the events it missed.

PART 5 · THE BENEFITS

Why Use Events?

Seven practical advantages. Each with a real example from the Order Management system.

1 · Less dependency between areasWhat it means. Order does not need to know that Notification exists. Notification does not need to know that Order exists. They only share the event format. Example. We can replace the Notification service with a completely new one (e.g., move from email to WhatsApp) without touching the Order code.
2 · Easier scalingWhat it means. Each service scales on its own. If Payment is slow, we add more Payment instances. The Order service does not need to scale too. Example. Black Friday: Payment handles 10× traffic with more instances. Order and Inventory stay at normal size.
3 · Background processingWhat it means. Work can happen later, not while the customer waits. Example. Generating a PDF invoice takes 3 seconds. We don't want the customer to wait 3 seconds to see "order placed." So Order publishes the event, the customer sees success, and the PDF is generated in the background.
4 · Better handling of traffic spikesWhat it means. The broker queues events when consumers are slow. No request is lost. Example. 1,000 orders arrive in one minute. The broker queues them. Payment processes 100 per minute. The queue grows, then shrinks. No order is dropped.
5 · Independent deploymentWhat it means. We can deploy a new version of Payment without redeploying Order. Example. Payment team releases a new feature on Tuesday. Order team releases a bug fix on Thursday. They do not block each other.
6 · Easier to add new consumersWhat it means. A new business area can start listening to existing events without changing the publisher. Example. Six months after launch, we add a "Loyalty Points" service. It subscribes to "OrderCreated" and awards points. The Order service is unchanged — it did not even know this new service existed.
7 · Better separation of responsibilitiesWhat it means. Each team owns one thing. Payment team owns payment. Inventory team owns stock. Reporting team owns dashboards. They are measured on their own area, not on the whole system. Example. The Payment team is responsible for payment success rate — not for shipping delays.
THE BUSINESS BENEFIT

Events let teams work independently. They can release on their own schedule. They can choose their own technology. They can fail without bringing down the whole system. This is what makes event-driven architecture attractive for large organizations — it matches the way businesses are structured.

PART 6 · THE PROBLEMS

Ten Problems Every Architect Must Know

This section is extremely important for an interview. Events are powerful, but they come with ten specific problems. The interviewer will test whether you know them — and whether you know how to handle each one.

Problem 1 · Duplicate Messages

WHYThe broker may deliver the same event more than once. Network hiccups, retries, or broker recovery after a crash can cause duplicates.
EXAMPLEPayment service receives "OrderCreated" twice. It charges the customer twice.
ARCHITECT RESPONSEDesign consumers to be idempotent — processing the same event twice has the same result as processing it once. We cover this deeply in Part 8.

Problem 2 · Message Loss

WHYHardware failure, bug, or misconfiguration. The broker loses an event before it reaches all consumers.
EXAMPLEInventory never hears "OrderCreated." The items are never reserved. The order ships without stock.
ARCHITECT RESPONSEUse durable queues and acknowledgements. The broker stores events on disk until consumers acknowledge receipt. Reconciliation jobs detect and repair missing events.

Problem 3 · Consumer Failure

WHYA consumer crashes, runs out of memory, or is deployed with a bug.
EXAMPLENotification service crashes. Emails are not sent for two hours.
ARCHITECT RESPONSEThe broker keeps the events. When Notification restarts, it picks up where it left off. Alerts fire when consumers are down too long.

Problem 4 · Broker Failure

WHYThe broker itself goes down — hardware failure, network partition, disk full.
EXAMPLERabbitMQ cluster loses quorum. New events cannot be published. Existing events are stuck.
ARCHITECT RESPONSERun the broker in a cluster with replication. Use multiple nodes in different zones. If one node fails, others take over. Monitor broker health carefully.

Problem 5 · Processing Delay

WHYA consumer is slow, the broker is overloaded, or the queue grows.
EXAMPLEShipping takes 30 seconds per order. The queue grows. Customers wait 10 minutes for confirmation.
ARCHITECT RESPONSEMonitor queue depth and processing time. Scale consumers horizontally. Add circuit breakers. Set SLAs on processing time.

Problem 6 · Messages in the Wrong Order

WHYMultiple consumers process events in parallel. Retries reorder events. Some brokers do not guarantee order across partitions.
EXAMPLE"OrderShipped" arrives before "PaymentCompleted." The system tries to ship before payment is confirmed.
ARCHITECT RESPONSEUse ordering guarantees per entity (e.g., all events for one order go to the same partition). Or design consumers to handle any order — each event carries enough context to be processed independently. We cover this in Part 9.

Problem 7 · Temporary Data Inconsistency

WHYEvents take time to flow. Between publishing and consuming, the data is out of sync across services.
EXAMPLEA customer checks their order status 5 seconds after placing it. The dashboard still says "pending."
ARCHITECT RESPONSEAccept eventual consistency. For data that must be exact (the customer's order confirmation), use a direct read from the source. For dashboards and reports, a short delay is acceptable.

Problem 8 · Difficult Troubleshooting

WHYEvents flow through many services. When something goes wrong, finding the broken link is hard.
EXAMPLEA customer complains they did not receive a confirmation email. Did the Order service publish the event? Did the broker deliver it? Did Notification process it? Where did it break?
ARCHITECT RESPONSEUse correlation IDs across all services. Log every event publish and consume. Build dashboards showing event flow per order. Tracing tools (like Zipkin or Jaeger) help follow one order through the whole system.

Problem 9 · Retry Problems

WHYRetries are necessary, but too many retries cause other problems — duplicates, delays, load.
EXAMPLEPayment retries a failed charge 10 times. The customer sees 10 pending transactions.
ARCHITECT RESPONSEUse exponential backoff (wait longer between retries). Limit retry count. Send failed events to a dead-letter queue for manual review. Never retry forever.

Problem 10 · Duplicate Business Actions

WHYEven with idempotency at the message level, the business action may be repeated. For example, sending the same email twice.
EXAMPLENotification sends the same "your order shipped" email three times. The customer gets annoyed.
ARCHITECT RESPONSETrack which actions have been taken per event. Store "notification_sent_for_event_X" before sending. If a retry arrives, check the record first.
THE INTERVIEW POINT

If an interviewer asks "what are the challenges of event-driven architecture?", and you can name 5 of these 10 with a practical answer for each, you pass the question. If you can name all 10 with the right architect response for each, you demonstrate real depth. These are the questions that separate senior architects from mid-level ones.

PART 7 · RELIABILITY

Ten Concepts Every Architect Must Know

These are the building blocks of a reliable event-driven system. Each one solves one of the problems from Part 6.

1 · RetryWhat it means. When a consumer fails to process an event, it tries again. Why we need it. Failures are often temporary — a database blip, a network hiccup. Example. Payment tries to charge a card, the bank is slow, it retries after 2 seconds and succeeds. Interview answer. "I use retries with exponential backoff — wait 1 second, then 2, then 4, then 8. Limit to 3–5 retries. After that, send to dead-letter queue."
2 · Dead-Letter Queue (DLQ)What it means. A separate queue where failed events go after all retries are exhausted. Why we need it. So we do not lose events, and we can investigate failures later. Example. An event fails 5 times. It moves to the DLQ. A developer inspects it, fixes the bug, and reprocesses. Interview answer. "Every consumer has a DLQ. I monitor DLQ depth — if it grows, something is broken."
3 · TimeoutWhat it means. A time limit on how long a consumer waits for a response. Why we need it. So the system does not hang forever waiting for a slow dependency. Example. Payment waits 30 seconds for the bank. After 30 seconds, it times out and retries. Interview answer. "I set timeouts based on the expected response time. If a bank normally responds in 2 seconds, I set a 30-second timeout — long enough for delays, short enough to not block forever."
4 · IdempotencyWhat it means. Processing the same event twice has the same result as processing it once. Why we need it. Because duplicates happen. Example. Payment receives "OrderCreated" twice. It charges the card only once. Interview answer. "I make every consumer idempotent. Payment checks 'have I already charged this order ID?' before charging." We cover this deeply in Part 8.
5 · Duplicate Message HandlingWhat it means. Detecting and ignoring duplicate events. Why we need it. Because the broker may deliver the same event more than once. Example. Each event has a unique ID. The consumer stores "processed event IDs." Before processing, it checks the list. Interview answer. "I use a deduplication table. Event ID + consumer name = unique key. If the key exists, skip the event."
6 · Message AcknowledgementWhat it means. The consumer tells the broker "I successfully processed this event." Why we need it. So the broker knows when to remove the event from the queue. Example. Payment processes an event, saves the result, then sends "ack" to the broker. If the consumer crashes before "ack," the broker redelivers the event. Interview answer. "I acknowledge only after the business action is complete. If I ack before saving, I risk losing the event on crash."
7 · Error HandlingWhat it means. How the system responds when something goes wrong. Why we need it. So failures are caught, logged, and handled gracefully. Example. A consumer catches an exception, logs it with the event ID, and decides whether to retry or send to DLQ. Interview answer. "I wrap every consumer in a try-catch. I log the error with full context. I classify errors as retryable (temporary) or fatal (permanent). Retryable go back to the queue. Fatal go to DLQ."
8 · Poison MessageWhat it means. An event that causes a consumer to fail every time it is processed. Why we need it. So one bad event does not block the whole queue. Example. An event has malformed data. Every time Payment tries to process it, it crashes. After 5 retries, it moves to DLQ. Interview answer. "I detect poison messages by counting retries. After N retries, the event goes to DLQ. A human inspects it."
9 · ReprocessingWhat it means. Processing an event again, usually after a bug fix. Why we need it. So we can recover from failures without losing data. Example. A bug caused 100 events to fail. We fix the bug, then reprocess the 100 events from the DLQ. Interview answer. "I can reprocess events from the DLQ. Because consumers are idempotent, reprocessing is safe — it does not duplicate the business action."
10 · MonitoringWhat it means. Watching the system to detect problems early. Why we need it. So we know when something is wrong before customers complain. Example. Monitor queue depth, processing time, error rate, DLQ size. Alert when queue depth exceeds a threshold. Interview answer. "I monitor four things: queue depth (is the queue growing?), processing time (is it slowing?), error rate (are events failing?), and DLQ size (are poison messages accumulating?). I alert on each."
THE RELIABILITY MINDSET

A reliable event-driven system assumes failure will happen. It does not ask "what if something goes wrong?" — it asks "when something goes wrong, how do we recover?" Every design decision in this part answers that question.

PART 8 · IDEMPOTENCY

Don't Charge the Customer Twice

Idempotency is the most important reliability concept for event-driven systems. If you remember nothing else from this tutorial, remember this: processing the same event twice should have the same result as processing it once.

The example

SCENARIO

Payment service receives the event: "PaymentRequested — Order #58211 — Amount $142.00"

The same event arrives three times. Why?

  • The broker delivered it twice (network hiccup).
  • The consumer crashed after processing but before acknowledging. The broker redelivered.
  • A retry mechanism fired unnecessarily.

What could go wrong

WITHOUT IDEMPOTENCYPayment charges the card three times. The customer is charged $426 instead of $142. They dispute the charges. The business loses money and reputation.
WITH IDEMPOTENCYPayment checks: "Have I already processed Order #58211?" The first time, no — it charges the card. The second and third times, yes — it skips the charge. The customer is charged $142 exactly once.
THE ARCHITECT'S JOBDesign every consumer to be idempotent. This is not optional. It is the foundation of reliable event processing.

Three practical solutions

Solution 1 · Idempotency Key

HOW IT WORKSEach event has a unique ID. Before processing, the consumer checks a database table: "Have I processed this event ID?" If yes, skip. If no, process and record the ID.
EXAMPLEEvent ID = "evt_58211_payment." Payment checks the "processed_events" table. The ID is not there. Payment charges the card, then inserts "evt_58211_payment" into the table. The second time the event arrives, the ID is found — skip.
STRENGTHSSimple. Works for any consumer. Easy to understand.
WEAKNESSESRequires a database table. The check-and-insert must be atomic (use a transaction).

Solution 2 · Business Key Check

HOW IT WORKSInstead of tracking event IDs, track the business action. "Have I already charged Order #58211?" Check the orders table for a payment record.
EXAMPLEPayment receives "OrderCreated" for Order #58211. It queries: "SELECT * FROM payments WHERE order_id = 58211." No record found. Payment charges the card and inserts a payment record. The second time, the record exists — skip.
STRENGTHSNo separate table needed. Uses existing business data.
WEAKNESSESOnly works if the business action leaves a record. Not suitable for actions that do not create a record (e.g., sending an email).

Solution 3 · Deterministic Processing

HOW IT WORKSThe consumer's logic is designed so that repeating it has no side effects. For example, "set order status to PAID" — running this twice still results in status = PAID.
EXAMPLEInventory receives "OrderCreated." It runs: "UPDATE inventory SET reserved = reserved + 5 WHERE product_id = 123." Wait — this is NOT idempotent! Running it twice reserves 10 items. The fix: "UPDATE inventory SET reserved = 5 WHERE product_id = 123 AND reserved = 0." Now it only runs once.
STRENGTHSNo extra tables. No extra checks.
WEAKNESSESHard to design for every action. Some actions (charging a card) cannot be made deterministic this way.

Which solution I prefer

My preference: Solution 1 (Idempotency Key) for most cases. It is simple, works for every consumer, and is easy to audit. I use Solution 2 when the business action naturally leaves a record (payments, orders). I use Solution 3 only when the action can be made truly deterministic (setting a status, updating a flag).

Why not Solution 3 alone? Because many business actions cannot be made deterministic. Charging a card is not idempotent by nature — you must track whether you have already charged.

THE INTERVIEW ANSWER

"I make every consumer idempotent using an idempotency key. Each event has a unique ID. Before processing, I check if I have already processed this ID. If yes, I skip. If no, I process and record the ID. This ensures that duplicate events — whether from broker redelivery, retries, or network issues — do not duplicate the business action."

PART 9 · ORDERING

What If Events Arrive in the Wrong Order?

Events are supposed to flow in order. But in distributed systems, they sometimes do not. Let's see what happens — and how to handle it.

The expected order

  1. OrderCreated — the customer places an order.
  2. PaymentCompleted — the payment succeeds.
  3. InventoryReserved — the items are reserved.
  4. OrderShipped — the package is shipped.

The problem

WHAT IF "ORDER SHIPPED" ARRIVES BEFORE "PAYMENT COMPLETED"?

Shipping receives "OrderShipped" first. It tries to prepare the package. But the payment has not been confirmed yet. Should it ship? Should it wait? What if the payment fails later?

Why this happens

  • Parallel consumers. Payment and Shipping run on different servers. Payment is slow. Shipping is fast. Shipping finishes first.
  • Retries reorder events. "PaymentCompleted" fails once, retries, and arrives after "OrderShipped."
  • Broker partitioning. In Kafka, events for the same order may go to different partitions if the partition key is not set correctly.

How the architect handles this

Approach 1 · Enforce ordering per entityUse a partition key based on the order ID. All events for Order #58211 go to the same partition. The broker delivers them in order. When to use. When ordering is critical (payment before shipping). Trade-off. Reduces parallelism — all events for one order go to one consumer.
Approach 2 · Design consumers to handle any orderEach event carries enough context to be processed independently. "OrderShipped" includes "payment_status = completed." Shipping checks this field before shipping. When to use. When ordering is not critical or when events can be self-contained. Trade-off. More complex event design.
Approach 3 · Wait for dependenciesShipping does not process "OrderShipped" until it has received both "PaymentCompleted" and "InventoryReserved." It stores incoming events and checks dependencies. When to use. When multiple events must arrive before an action can proceed. Trade-off. More complex consumer logic.
Approach 4 · Reject out-of-order eventsShipping receives "OrderShipped" but has not yet received "PaymentCompleted." It rejects the event and sends it back to the queue. It will be retried later. When to use. When ordering is critical and the system can tolerate retries. Trade-off. May cause delays if the missing event is slow.

My preference

I use Approach 1 (enforce ordering per entity) for critical flows. Payment before shipping is critical. I set the partition key to the order ID. All events for one order go to the same partition, and the broker delivers them in order.

For less critical flows, I use Approach 2 (self-contained events). Each event carries the context it needs. If "OrderShipped" arrives before "PaymentCompleted," Shipping checks the payment status and waits if needed.

THE INTERVIEW ANSWER

"For critical flows like payment-before-shipping, I enforce ordering by using a partition key based on the order ID. All events for one order go to the same partition, and the broker delivers them in order. For less critical flows, I design events to be self-contained — each event carries the context it needs to be processed independently."

PART 10 · CONSISTENCY

Immediate vs Eventual Consistency

In event-driven systems, data is not always up-to-date everywhere at the same time. The architect must decide: which data must be correct immediately, and which can be a few seconds old?

Immediate consistency

WHAT IT MEANSWhen a write happens, every reader sees the new data immediately. No delay. No lag.
WHEN WE NEED ITWhen the business cannot tolerate even a brief delay. Banking balances. Inventory at checkout. Appointment availability.
HOW TO ACHIEVE ITUse direct API calls, not events. The caller waits for the answer. The database is the single source of truth.

Eventual consistency

WHAT IT MEANSWhen a write happens, readers may see old data for a short time. The system catches up — eventually.
WHEN IT'S ACCEPTABLEWhen a short delay does not hurt the business. Dashboards. Reports. Email notifications. Product catalogs.
HOW TO ACHIEVE ITUse events. The write side publishes. The read side consumes and updates. There is a lag between write and read.

The Order Management example

DATA CONSISTENCY NEED WHY DESIGN
Order confirmation IMMEDIATE Customer must see "order placed" right away Direct API call. Order service writes to its database and responds.
Payment status IMMEDIATE Customer must know if payment succeeded or failed Direct API call. Payment service writes to its database and responds.
Inventory at checkout IMMEDIATE Customer must know if items are in stock Direct API call. Inventory service checks stock in real-time.
Shipping status EVENTUAL (seconds) Customer can wait a few seconds to see "shipped" Event-driven. Shipping publishes "OrderShipped." Customer portal reads from a read model.
Notification emails EVENTUAL (minutes) Customer can wait a few minutes for email Event-driven. Notification service processes events asynchronously.
Dashboard data EVENTUAL (minutes) Manager can see sales from 5 minutes ago Event-driven. Reporting service aggregates events into a dashboard.
Reports EVENTUAL (hours) Weekly reports can run on data from last night Event-driven. Reporting service writes to a data warehouse.

How the architect decides

The rule: If the user is actively waiting for the answer, use immediate consistency (direct API). If the user can check later, use eventual consistency (events).

Examples:

  • Customer clicks "place order" and waits for confirmation → immediate.
  • Customer checks their order status 5 minutes later → eventual.
  • Manager opens a dashboard in the morning → eventual.
  • Customer tries to buy the last item in stock → immediate.
THE INTERVIEW ANSWER

"I decide based on the user's expectation. If the user is actively waiting — placing an order, checking out, confirming payment — I use immediate consistency with direct API calls. If the user can check later — dashboards, reports, email notifications — I use eventual consistency with events. The key question is: 'Would the user notice or care if this data is 10 seconds old?'"

PART 11 · EVENT VS DIRECT API

When to Use Which

Not every operation should use events. Not every operation should use direct API calls. The architect must choose based on the situation.

SITUATION DIRECT API EVENT RECOMMENDATION WHY
Login ✓ — DIRECT API User waits for answer. Must be immediate.
Get customer details ✓ — DIRECT API User waits for answer. Must be immediate.
Create order ✓ — DIRECT API User waits for confirmation. Must be immediate.
Send email notification — ✓ EVENT User does not wait. Can happen in background.
Generate report — ✓ EVENT Takes time. User does not wait.
Payment processing ✓ ✓ DIRECT API (initial) + EVENT (downstream) Payment must be confirmed immediately. But downstream (inventory, shipping) can be event-driven.
Update dashboard — ✓ EVENT Dashboard can be a few seconds old.
Audit logging — ✓ EVENT Does not block the user. Can happen in background.
Inventory update ✓ ✓ DIRECT API (at checkout) + EVENT (after order) At checkout, must be immediate. After order, can be event-driven.
Notification (SMS/email) — ✓ EVENT User does not wait. Can happen in background.

The decision framework

Use Direct API when:The user is waiting. Login, get details, place order, check inventory at checkout. The user cannot proceed without the answer. The answer must be immediate. Banking balance, payment confirmation. A delay is not acceptable. The operation is simple. One service, one database, one response.
Use Events when:The user is not waiting. Send email, generate report, update dashboard. The user can check later. The answer can be delayed. Notifications, audit logs, analytics. A few seconds or minutes is fine. The operation involves many services. Order placed → payment → inventory → shipping → notification. Each service does its own job independently.
THE INTERVIEW ANSWER

"I ask two questions: 'Is the user waiting?' and 'Can the answer be delayed?' If the user is waiting and the answer must be immediate, I use direct API. If the user is not waiting and the answer can be delayed, I use events. Most systems use both — direct API for the critical path, events for everything downstream."

PART 12 · BROKERS COMPARED

RabbitMQ vs Kafka vs Azure Service Bus

Three popular message brokers. Each solves a different problem. The architect must choose based on the system's needs.

FACTOR RABBITMQ KAFKA AZURE SERVICE BUS
Type of problem Task queues, work distribution, traditional messaging Event streaming, log aggregation, high-throughput pipelines Enterprise messaging, Azure-native integration
Strengths Simple to set up. Flexible routing. Supports many protocols (AMQP, MQTT, STOMP). Good for task queues. Extremely high throughput. Durable storage. Replay capability. Good for event sourcing and stream processing. Fully managed. Integrates with Azure services. Good for enterprise scenarios.
Weaknesses Not designed for high-throughput streaming. Messages are deleted after consumption. Complex to set up and manage. Overkill for simple task queues. Vendor lock-in. Less flexible than RabbitMQ or Kafka.
When to choose Task queues, work distribution, traditional request-reply patterns. Moderate throughput. Event streaming, log aggregation, real-time analytics. High throughput. Need to replay events. Azure-native systems. Enterprise messaging. Need managed service.
When NOT to choose High-throughput streaming. Need to replay events. Simple task queues. Low throughput. Need flexible routing. Non-Azure systems. Need maximum flexibility.

The decision framework

Before choosing a broker, ask:

  • What is the throughput? Low (hundreds/sec) → RabbitMQ. High (millions/sec) → Kafka.
  • Do we need to replay events? Yes → Kafka. No → RabbitMQ or Service Bus.
  • Is this an Azure-native system? Yes → Azure Service Bus. No → RabbitMQ or Kafka.
  • Do we need flexible routing? Yes → RabbitMQ. No → Kafka or Service Bus.
  • Do we want a managed service? Yes → Azure Service Bus or Kafka on Confluent. No → self-hosted RabbitMQ or Kafka.
THE INTERVIEW ANSWER

"I choose based on the problem. For task queues and work distribution, I use RabbitMQ. For event streaming and high throughput, I use Kafka. For Azure-native enterprise messaging, I use Azure Service Bus. The key questions are: what is the throughput, do we need to replay events, and is this an Azure-native system?"

PART 13 · FAILURE SCENARIOS

Ten Failure Scenarios

In an interview, the interviewer will test whether you can handle failure scenarios. Here are ten common ones, with the architect's response for each.

Scenario 1 · Broker is down

PROBLEMThe message broker (RabbitMQ, Kafka, Service Bus) is unavailable.
IMPACTProducers cannot publish events. Consumers cannot receive events. The system is stuck.
ARCHITECT RESPONSEUse a broker cluster with replication. If one node fails, others take over. Monitor broker health. Alert immediately if the broker is down. Have a fallback plan (e.g., write events to a database and replay later).

Scenario 2 · Consumer is down

PROBLEMA consumer service (e.g., Payment) crashes or is deployed with a bug.
IMPACTEvents pile up in the queue. The consumer does not process them.
ARCHITECT RESPONSEThe broker holds the events. When the consumer restarts, it picks up where it left off. Monitor consumer health. Alert if a consumer is down for too long. Use multiple consumer instances for redundancy.

Scenario 3 · Database is down

PROBLEMThe consumer's database (e.g., Payment DB) is unavailable.
IMPACTThe consumer cannot save the result of processing the event. The event fails.
ARCHITECT RESPONSEThe consumer retries. If retries fail, the event goes to the DLQ. Monitor database health. Alert if the database is down. Use database replication for high availability.

Scenario 4 · Message is duplicated

PROBLEMThe broker delivers the same event twice.
IMPACTThe consumer may process the event twice, causing duplicate business actions (e.g., charging the customer twice).
ARCHITECT RESPONSEMake consumers idempotent. Use idempotency keys. Check if the event has already been processed before processing it again. (See Part 8 for details.)

Scenario 5 · Message is delayed

PROBLEMEvents are stuck in the queue. They are not being processed.
IMPACTDownstream services are waiting. The system is slow.
ARCHITECT RESPONSEMonitor queue depth and processing time. Alert if the queue grows. Scale consumers horizontally. Check if the broker or consumers are overloaded.

Scenario 6 · Message processed but acknowledgement fails

PROBLEMThe consumer processes the event successfully, but the acknowledgement to the broker fails.
IMPACTThe broker thinks the event was not processed. It redelivers the event. The consumer processes it again.
ARCHITECT RESPONSEMake consumers idempotent. The second processing should have no effect. Use transactions to ensure the business action and the acknowledgement are atomic.

Scenario 7 · Consumer processes but crashes before saving

PROBLEMThe consumer processes the event (e.g., charges the card), but crashes before saving the result to the database.
IMPACTThe business action happened, but the database does not reflect it. The event is redelivered.
ARCHITECT RESPONSEUse the transactional outbox pattern. Save the business action and the event processing in the same transaction. If the transaction fails, neither happens. If it succeeds, both happen.

Scenario 8 · One consumer becomes very slow

PROBLEMOne consumer (e.g., Shipping) is processing events very slowly.
IMPACTThe queue for that consumer grows. Events are delayed.
ARCHITECT RESPONSEMonitor processing time per consumer. Alert if a consumer is slow. Scale that consumer horizontally. Investigate why it is slow (database? external API?).

Scenario 9 · One customer generates huge traffic

PROBLEMOne customer places 10,000 orders in one minute.
IMPACTThe queue is flooded. Other customers' orders are delayed.
ARCHITECT RESPONSEUse per-customer rate limiting. Use separate queues for high-volume customers. Monitor per-customer traffic. Alert if one customer is generating unusual traffic.

Scenario 10 · Event schema changes

PROBLEMThe producer changes the event format (e.g., adds a new field, renames a field).
IMPACTConsumers that expect the old format may fail to process the event.
ARCHITECT RESPONSEUse schema evolution. Add new fields without removing old ones. Use versioning (e.g., OrderCreated_v1, OrderCreated_v2). Test consumers with the new schema before deploying. Use a schema registry (e.g., Confluent Schema Registry for Kafka).
THE INTERVIEW POINT

If the interviewer asks "what happens if X fails?", and you can name the impact and the architect's response, you pass the question. The key is to show that you think about failure modes proactively, not reactively.

PART 14 · INTERVIEW QUESTIONS

Twenty Questions an Architect Must Answer

These are the questions you will face in a Technical Architect interview. For each, I show four layers: what the interviewer is checking, a simple answer, a strong architect answer, and a common mistake.

  1. Why would you use event-driven architecture instead of direct API calls?DECISION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the benefits and when to apply them.
    SIMPLE ANSWEREvents let systems work independently and scale better.
    STRONG ARCHITECT ANSWERI use events when multiple services need to react to the same business event, when I want to decouple systems, when I need to handle traffic spikes, or when I want to add new consumers without changing the publisher. Direct API calls are better when the caller needs an immediate answer.
    COMMON MISTAKE"Events are always better." They're not — they add complexity. Use them when the benefits outweigh the costs.
  2. Why not use events everywhere?DECISION ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the trade-offs.
    SIMPLE ANSWEREvents add complexity and delay. Some operations need immediate answers.
    STRONG ARCHITECT ANSWEREvents introduce eventual consistency, which is not acceptable for all operations. Login, payment confirmation, and inventory checks at checkout need immediate answers. Events also add complexity — debugging is harder, ordering is harder, and you need to handle duplicates and failures. I use events only when the benefits (decoupling, scaling, background processing) outweigh these costs.
    COMMON MISTAKE"I use events for everything." This leads to a system that is hard to debug and has unpredictable latency.
  3. What is the difference between an event and an API call?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the fundamental difference.
    SIMPLE ANSWERAn API call is "do this for me now." An event is "this just happened — whoever cares, react."
    STRONG ARCHITECT ANSWERAn API call is synchronous — the caller waits for a response. An event is asynchronous — the publisher does not wait. An API call has one caller and one responder. An event can have many consumers, or none. An API call is a command. An event is a fact.
    COMMON MISTAKEConfusing the two. Using events when you need an immediate answer, or using API calls when you need to notify multiple systems.
  4. How do you handle duplicate events?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand idempotency.
    SIMPLE ANSWERI make consumers idempotent — processing the same event twice has the same result as processing it once.
    STRONG ARCHITECT ANSWERI use idempotency keys. Each event has a unique ID. Before processing, the consumer checks if it has already processed this ID. If yes, skip. If no, process and record the ID. I also use business key checks — for example, "have I already charged this order?" — and deterministic processing where possible.
    COMMON MISTAKE"I prevent duplicates at the broker level." You can't — the broker may deliver duplicates. The consumer must handle them.
  5. How do you guarantee an event is not lost?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand durability and acknowledgements.
    SIMPLE ANSWERI use durable queues and acknowledgements.
    STRONG ARCHITECT ANSWERI configure the broker to persist events to disk. Consumers acknowledge events only after successfully processing them. If a consumer crashes before acknowledging, the broker redelivers the event. I also use broker replication for high availability.
    COMMON MISTAKE"I acknowledge events immediately after receiving them." This risks losing events if the consumer crashes before processing.
  6. What happens if a consumer is down?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the broker's role.
    SIMPLE ANSWERThe broker holds the events. When the consumer restarts, it picks up where it left off.
    STRONG ARCHITECT ANSWERThe broker stores events in a durable queue. When the consumer is down, events accumulate. When the consumer restarts, it processes the backlog. I monitor queue depth and alert if it grows too large. I also use multiple consumer instances for redundancy.
    COMMON MISTAKE"The system stops working." It doesn't — the broker holds the events. The system is delayed, not broken.
  7. How do you handle retries?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand retry strategies.
    SIMPLE ANSWERI retry with exponential backoff and a maximum retry count.
    STRONG ARCHITECT ANSWERI use exponential backoff — wait 1 second, then 2, then 4, then 8. I limit retries to 3–5 attempts. After that, the event goes to a dead-letter queue for manual inspection. I classify errors as retryable (temporary) or fatal (permanent). Fatal errors go to DLQ immediately.
    COMMON MISTAKE"I retry forever." This can cause infinite loops and overload the system.
  8. How do you handle message ordering?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the challenges of ordering in distributed systems.
    SIMPLE ANSWERI use partition keys to ensure events for the same entity go to the same partition.
    STRONG ARCHITECT ANSWERFor critical flows (payment before shipping), I enforce ordering by using a partition key based on the order ID. All events for one order go to the same partition, and the broker delivers them in order. For less critical flows, I design events to be self-contained — each event carries the context it needs to be processed independently.
    COMMON MISTAKE"I assume the broker always delivers events in order." It doesn't — especially with multiple partitions and parallel consumers.
  9. What is eventual consistency?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand the trade-off between consistency and availability.
    SIMPLE ANSWERThe data will be correct eventually, but not immediately.
    STRONG ARCHITECT ANSWEREventual consistency means that after a write, readers may see old data for a short time. The system catches up — eventually. This is acceptable for dashboards and reports, but not for banking balances or inventory at checkout. I decide based on the user's expectation: if the user is actively waiting, I use immediate consistency. If the user can check later, I use eventual consistency.
    COMMON MISTAKE"Eventual consistency means the data is wrong." It's not wrong — it's just delayed.
  10. How would you debug a missing event?TROUBLESHOOTING ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you can troubleshoot event-driven systems.
    SIMPLE ANSWERI check the broker, the producer, and the consumer logs.
    STRONG ARCHITECT ANSWERI use correlation IDs to trace the event through the system. I check: did the producer publish the event? (Check producer logs.) Did the broker receive it? (Check broker metrics.) Did the consumer receive it? (Check consumer logs.) Did the consumer process it successfully? (Check consumer logs and database.) I also use dashboards to monitor event flow per order.
    COMMON MISTAKE"I check the consumer first." The problem may be upstream — the producer may not have published the event.
  11. How do you change an event schema without breaking consumers?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand schema evolution.
    SIMPLE ANSWERI add new fields without removing old ones.
    STRONG ARCHITECT ANSWERI use schema evolution. I add new fields without removing old ones. I use versioning (e.g., OrderCreated_v1, OrderCreated_v2). I test consumers with the new schema before deploying. I use a schema registry (e.g., Confluent Schema Registry for Kafka) to enforce compatibility. I also use the expand-and-contract pattern — add the new field, deploy, then remove the old field in a later deployment.
    COMMON MISTAKE"I change the schema and deploy all consumers at the same time." This is risky — if one consumer is not updated, it will fail.
  12. How do you prevent one consumer from slowing down the entire system?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand isolation.
    SIMPLE ANSWERI use separate queues for each consumer.
    STRONG ARCHITECT ANSWERI use separate queues or topics for each consumer. If one consumer is slow, it only affects its own queue. I also monitor processing time per consumer and alert if a consumer is slow. I scale slow consumers horizontally. I also use circuit breakers to prevent cascading failures.
    COMMON MISTAKE"I use one queue for all consumers." This means a slow consumer blocks all other consumers.
  13. What is a dead-letter queue?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand failure handling.
    SIMPLE ANSWERA queue where failed events go after all retries are exhausted.
    STRONG ARCHITECT ANSWERA dead-letter queue (DLQ) is a separate queue where events go after they fail repeatedly. This prevents poison messages from blocking the main queue. I monitor DLQ depth — if it grows, something is broken. I inspect DLQ events manually, fix the root cause, and reprocess them.
    COMMON MISTAKE"I don't use a DLQ." This means failed events are lost or block the main queue.
  14. What is idempotency?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand this critical concept.
    SIMPLE ANSWERProcessing the same event twice has the same result as processing it once.
    STRONG ARCHITECT ANSWERIdempotency means that repeating an operation does not change the result. For example, charging a card once is idempotent — charging it twice is not. I make every consumer idempotent using idempotency keys, business key checks, or deterministic processing. This ensures that duplicate events do not duplicate business actions.
    COMMON MISTAKE"Idempotency means the operation is fast." It has nothing to do with speed — it's about safety when repeating operations.
  15. How do you monitor an event-driven system?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand observability.
    SIMPLE ANSWERI monitor queue depth, processing time, and error rate.
    STRONG ARCHITECT ANSWERI monitor four things: queue depth (is the queue growing?), processing time (is it slowing?), error rate (are events failing?), and DLQ size (are poison messages accumulating?). I also use correlation IDs to trace events through the system. I build dashboards showing event flow per order. I alert on each metric.
    COMMON MISTAKE"I only monitor the broker." The broker is only one part — I also need to monitor producers and consumers.
  16. What is the transactional outbox pattern?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand how to reliably publish events.
    SIMPLE ANSWERSave the business action and the event in the same transaction.
    STRONG ARCHITECT ANSWERThe transactional outbox pattern solves the problem of reliably publishing events. Instead of publishing the event directly, I save it to an "outbox" table in the same transaction as the business action. A separate process reads the outbox and publishes events to the broker. This ensures that the business action and the event are atomic — either both happen, or neither happens.
    COMMON MISTAKE"I publish the event after saving to the database." If the publish fails, the business action happened but the event was not sent.
  17. What is the difference between a queue and a topic?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand messaging patterns.
    SIMPLE ANSWERA queue delivers each message to one consumer. A topic delivers each message to all subscribers.
    STRONG ARCHITECT ANSWERA queue is for work distribution — each message is processed by exactly one consumer. A topic is for broadcasting — each message is delivered to all subscribers. I use queues for task processing (e.g., send email). I use topics for event notification (e.g., order created — notify payment, inventory, and notification).
    COMMON MISTAKEUsing a queue when you need to notify multiple consumers, or using a topic when you need to distribute work.
  18. How do you handle poison messages?RELIABILITY ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand failure handling.
    SIMPLE ANSWERI detect them by counting retries, then send them to a DLQ.
    STRONG ARCHITECT ANSWERA poison message is an event that causes a consumer to fail every time it is processed. I detect poison messages by counting retries — after N retries, the event goes to the DLQ. I monitor DLQ depth. I inspect DLQ events manually, fix the root cause (e.g., malformed data), and reprocess them. I also use circuit breakers to prevent cascading failures.
    COMMON MISTAKE"I retry forever." This can cause infinite loops and block the queue.
  19. What is the difference between at-most-once, at-least-once, and exactly-once delivery?CONCEPT ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand delivery guarantees.
    SIMPLE ANSWERAt-most-once: events may be lost. At-least-once: events may be duplicated. Exactly-once: events are delivered exactly once.
    STRONG ARCHITECT ANSWERAt-most-once delivery means events may be lost, but are never duplicated. This is fast but unreliable. At-least-once delivery means events are never lost, but may be duplicated. This is reliable but requires idempotent consumers. Exactly-once delivery means events are delivered exactly once — no loss, no duplication. This is the hardest to achieve and requires coordination between the broker and the consumer. I use at-least-once delivery with idempotent consumers — this is the most practical approach.
    COMMON MISTAKE"I use exactly-once delivery." This is very hard to achieve and often not necessary. At-least-once with idempotency is usually sufficient.
  20. How do you test an event-driven system?DESIGN ▸ FOUR-LAYER ANSWER
    WHAT INTERVIEWER CHECKSWhether you understand testing challenges.
    SIMPLE ANSWERI test producers, consumers, and the broker separately, then test the whole system.
    STRONG ARCHITECT ANSWERI test at three levels: unit tests for individual components, integration tests for producer-broker-consumer flows, and end-to-end tests for the whole system. I use a test broker (e.g., embedded RabbitMQ or Kafka). I test failure scenarios — what happens if the broker is down, if a consumer crashes, if events are duplicated. I also test idempotency — processing the same event twice should have the same result as processing it once.
    COMMON MISTAKE"I only test the happy path." Event-driven systems have many failure modes — I need to test them all.
WHAT THE INTERVIEWER SCORES

Not whether you know the terms. Whether you understand the trade-offs, can explain to non-technical people, know when NOT to use events, and think about failure modes. A strong architect says "it depends" — and then explains what it depends on.

PART 17 · THE CLOSE

Ten Rules an Architect Should Remember About Events

If you remember nothing else from today, remember these ten rules. They are simple, practical, and they will guide every decision you make about event-driven architecture.

Rule 1Don't call. Announce. Listen. This is the whole idea. The publisher announces something happened. The listeners react. They do not know about each other.
Rule 2Events are facts, not commands. An event says "this happened," not "do this." The listener decides what to do.
Rule 3Make consumers idempotent. Processing the same event twice should have the same result as processing it once. This is non-negotiable.
Rule 4Acknowledge after processing, not before. If you acknowledge before processing, you risk losing events on crash.
Rule 5Use dead-letter queues. Failed events go to the DLQ after all retries are exhausted. Monitor DLQ depth.
Rule 6Retry with exponential backoff. Wait 1 second, then 2, then 4, then 8. Limit retries to 3–5.
Rule 7Use correlation IDs. Trace events through the system. Debugging without correlation IDs is impossible.
Rule 8Monitor queue depth, processing time, and error rate. These three metrics tell you if the system is healthy.
Rule 9Use events for background work, direct API for immediate answers. If the user is waiting, use direct API. If the user can check later, use events.
Rule 10Eventual consistency is a trade-off, not a failure. It is a deliberate choice: the read side may be slightly behind, but the system scales. The architect's job is to decide which data needs which level of consistency.

One-minute interview answer

"I use event-driven architecture when multiple services need to react to the same business event, when I want to decouple systems, when I need to handle traffic spikes, or when I want to add new consumers without changing the publisher. I use direct API calls when the caller needs an immediate answer — login, payment confirmation, inventory check at checkout. Events are for background work. Direct API is for immediate answers. The key is to make every consumer idempotent, use dead-letter queues for failures, and monitor queue depth, processing time, and error rate."

Memorize that answer. It covers the whole day. In an interview, say it — then fill in the details with the specifics of the system you are discussing.

DAY 17 — CLOSE

The Architect Who Announces

Five rules from today. If you remember nothing else, these carry you through any event-driven conversation.

01

Don't call. Announce.

The old way: Service A calls Service B, waits for an answer, then calls Service C. The new way: Service A announces "something happened." Services B and C listen and react. They do not know about each other. This is the whole idea.

02

Make it idempotent.

Duplicates will happen. Network hiccups, retries, broker recovery. If your consumer is not idempotent, you will charge the customer twice, send the email twice, reserve the inventory twice. Idempotency is not optional — it is the foundation of reliable event processing.

03

Acknowledge after, not before.

If you acknowledge an event before processing it, and then crash, the event is lost. Acknowledge only after the business action is complete. This ensures at-least-once delivery — the event may be processed twice, but it will never be lost.

04

Monitor the queue.

Queue depth, processing time, error rate, DLQ size. These four metrics tell you if the system is healthy. If the queue is growing, something is slow. If the error rate is increasing, something is broken. If the DLQ is growing, something is a poison message.

05

Events for background, API for immediate.

If the user is waiting — placing an order, checking out, confirming payment — use direct API calls. If the user can check later — dashboards, reports, email notifications — use events. The key question is: "Would the user notice or care if this data is 10 seconds old?"

An event-driven architect is not the person who knows the most about RabbitMQ or Kafka. An event-driven architect is the person who knows when to use events and when not to — and can explain why to someone who has never written a line of code. "Don't call. Announce. Listen." — three words, one idea, infinite possibilities.
